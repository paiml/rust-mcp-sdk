<assumption_delta_decision>
The `assumption-delta scan` fired `pluralization` on this phase. The real delta is not the phrases
it matched — it is D-11: the number of on-disk representations of "a package" went from ONE (the
OCI layout directory, which every shipped verb operates on) to TWO (a movable `.tar` plus the
working layout directory).

- **The noun that is now primary:** the **OCI layout** remains the identity-bearing form. Package
  identity IS the manifest digest that `pack_server` computes over the layout's blobs, and it is
  what `SubjectVerdict` compares an attestation's claim against.
- **Decision: `add-alongside`.** The tar is added as a pure carriage envelope with no identity of
  its own: it carries the layout's bytes, contributes nothing to the digest, and is discarded by
  `load`/`pull` the moment its contents are verified. Promoting it would give a transport wrapper
  authority over package identity, which is exactly backwards.
- **Accepted debt, and what would force a later promote:** if the platform ever assigns a digest to
  the *tar bytes themselves* — which is precisely the open question A4 raises about
  `getPackageArtifact`'s `payloadDigest` — the tar acquires an identity and this model must change
  to `promote` or to a two-identity model. Plan 02 writes A4 into `portability-v1.graphql`'s
  argument comments as an explicit question for exactly this reason.
- **Suggested (not required) invariant test:** a contract test asserting that the manifest digest of
  a layout is unchanged by a `save` -> `load` round trip, i.e. that tarring contributes nothing to
  identity. Plan 04's framing-rule work is the natural home if the executor wants it.
</assumption_delta_decision>

**The validated artifact model (review finding H1 — do not simplify this back into a byte bag).**
The reviewed draft defined `VerifiedArtifact` as `index_json: Vec<u8>` plus
`BTreeMap<hex, Vec<u8>>` and left the media type as "from the manifest". That is not implementable:
`OciLayout::write_blob(media_type, bytes)` (`layout.rs:108`) requires a `MediaType` for EVERY blob it
writes, including the manifest blob and the config blob, and a digest→bytes map carries none. The type
must therefore carry a validated MODEL, and it must never fabricate a descriptor to fill a gap:

```
struct VerifiedBlob { bytes: Vec<u8>, media_type: MediaType, size: u64 }

struct VerifiedArtifact {
    index: ImageIndex,                    // parsed from index.json, not raw bytes
    index_bytes: Vec<u8>,                 // the exact bytes as read, for byte-fidelity checks
    manifest_descriptor: Descriptor,      // THE one descriptor index.manifests() declares
    manifest: ImageManifest,              // parsed from the blob that descriptor addresses
    blobs: BTreeMap<String, VerifiedBlob>,// keyed by lowercase hex digest
    manifest_digest: ManifestDigest,      // derived LOCALLY over the manifest blob's bytes
}
```

Build it by WALKING THE DESCRIPTOR GRAPH, refusing at each step by name rather than defaulting:

1. `index.json` must be present and must deserialize as `ImageIndex`. Absent or unparseable is its own
   refusal — never an empty layout.
2. `index.manifests()` must have length exactly 1. Mirror `read_the_one_manifest`'s rule
   (`unpack.rs:55-69`) HERE, at the framing boundary, so the refusal happens before any write instead
   of after one. Name the observed count in the message.
3. That manifest descriptor's digest must resolve to a blob present in the tar. Record its `MediaType`
   and assert its declared `size` equals the blob's actual length. Parse the blob as `ImageManifest`.
4. Walk `manifest.config()` and every entry of `manifest.layers()`. Each must resolve to a blob present
   in the tar, with a matching digest and a matching declared size, and each contributes its
   descriptor's `MediaType` to that blob's `VerifiedBlob`. A descriptor pointing at a blob the tar does
   not carry is a DANGLING DESCRIPTOR refusal, naming the digest.
5. Close the graph in the other direction: every blob the tar carries must have been reached by exactly
   one descriptor in steps 3-4. A blob nothing references is an ORPHAN BLOB refusal, naming its hex.
   This is not fussiness — an unreferenced blob is bytes a producer smuggled in, and a reader that
   silently drops them is a reader whose output is not a function of its input.
6. Derive `manifest_digest` locally with `ManifestDigest::from_bytes` over the manifest blob's bytes.
   Never read a digest out of the archive and call it derived.

Two blobs claiming one hex is already impossible — duplicate archive PATHS are refused in step 0 by
`classify_entry`, and a hex uniquely determines a path.

- `read_verified(tar_bytes: &[u8]) -> Result<VerifiedArtifact>` — parses entries into memory, runs
  every framing and integrity gate and the descriptor-graph walk above, and touches the filesystem ZERO
  times. For the tracer, the gates that must already be live are: the entry path must be exactly
  `oci-layout`, `index.json`, or `blobs/sha256/<64 lowercase hex>`, anything else refused by name; plus
  the full graph walk. Task 3 adds the hostile-input gates and the byte caps.
- `write_layout(artifact: &VerifiedArtifact, staging: &Path) -> Result<OciLayout>` — reached only after
  `read_verified` returned `Ok`, so it performs no validation of its own. It calls `OciLayout::create`,
  then `write_blob(blob.media_type.clone(), &blob.bytes)` for each blob in `artifact.blobs` — the media
  type comes from the descriptor that referenced it, which is why step 3-4 above had to record it —
  then `write_index(&artifact.index)`. Every destination filename comes from `describe_blob`'s digest
  over bytes this code holds; the archive's own path strings are a lookup key during validation and
  never a filesystem destination. Name the parameter `staging`, not `dest`, so the call contract is
  visible at every call site.

**Transactional install (review findings H4 and M2 — one design closes both).**
The reviewed draft ordered `write_layout` → `detect_kind` → `unpack_*` and then claimed the destination
was byte-for-byte unchanged after ANY refusal. That claim was false for a whole class: `unpack_server`
performs substantive validation (manifest structure, required media types, config blobs, legacy shapes,
deserialization — `unpack.rs:625-660`), so a correctly content-addressed but semantically malformed
package WROTE the destination and only then failed. `OciLayout::create` compounds it: it writes the
marker and an empty index before any blob (`layout.rs:41`), so an IO error or an interruption under
`--force` leaves a half-replaced destination. Fix both by never writing the destination until the
package has been fully validated somewhere else:

- `install_layout(artifact: &VerifiedArtifact, dest: &Path, force: bool) -> Result<InstalledLayout>`
  is the only function `load` and `pull` call. It:
  1. refuses when `dest` exists and `force` is false, BEFORE anything else;
  2. creates a staging directory as a SIBLING of `dest` — in `dest`'s PARENT, not in the system temp
     directory. This is load-bearing: `std::fs::rename` across filesystems fails `EXDEV`, and a
     `tempfile::TempDir` with default placement lands on whatever `TMPDIR` names. Use
     `tempfile::Builder::new().prefix(...).tempdir_in(parent)?` so the guard still cleans up on drop;
  3. calls `write_layout` into that staging path;
  4. runs `detect_kind` and the matching `unpack_*` AGAINST THE STAGING LAYOUT. Any failure here
     returns `Err` with the staging guard dropping — the destination was never touched;
  5. only now installs: if `dest` exists (so `force` was true), `rename(dest, dest.with_extension(
     "replaced-<nanos>"))` first; then `rename(staging_path, dest)`; then remove the replaced
     directory. If the second rename fails, rename the replaced directory back and surface both errors;
  6. returns the unpacked result so the caller does not unpack twice.
  Persist the staging directory out of its `TempDir` guard (`into_path`) only at step 5, immediately
  before the rename, so every earlier return path is still guarded.

  Document the residual window honestly in the rustdoc rather than claiming atomicity: a crash between
  the two renames in step 5 leaves the previous layout under its `.replaced-<nanos>` name, and the
  error path names that directory to the operator. That is a NAMED window, not a silent one, and it is
  strictly smaller than the reviewed draft's (which could leave a destination containing a marker, an
  empty index and a partial blob set with no record that it had ever been complete).

  Attestation SUBJECT MISMATCH is deliberately NOT in this gate (D-15, unchanged): a package whose
  bytes are sound but whose claim is false is INSTALLED and then reported, exiting 1. Plan 03 wires
  that verdict. Say so in `install_layout`'s rustdoc so a later reader does not "tidy up" by moving the
  subject check into the staging gate and thereby harmonizing two verdicts 122 D-03 keeps apart.

- `write_tar(layout: &OciLayout, dest: &Path) -> Result<()>` — the `save` half. It reads

  anything — a writer that re-serialized `index.json` could silently "fix" a layout, and byte-exact
  writer-conformance (plan 04) would be untestable. Emits entries in a fixed order: `oci-layout`, then

injected cap and assert acceptance. Plan 07 keeps raw-byte fuzzing for panic/hang resistance only,
which is what fuzzing is actually good at (and what C-4 FUZZ requires).

Enforce the caps by reading through a bounded reader (`std::io::Read::take` over the entry, with the
running total threaded through), NOT by reading to the end and then measuring — Phase 113 recorded that
collecting an over-cap body before measuring it performs exactly the unbounded allocation the cap
exists to prevent, and a tar header's declared size is attacker-controlled input, an early-refusal
optimisation and never the authority. Refuse on overflow naming which cap tripped and which entry.

Mark `ArtifactLimits` and `read_verified_with_limits` `#[doc(hidden)]` with a rustdoc saying they are
a test/fuzz-facing seam, not stable public API — the same register the `#[path]` lib mounts use.

**The integrity gate.** After every entry is in memory and before any write, re-derive each blob's
digest with `ManifestDigest::from_bytes` and compare it to the hex in its own archive path. A mismatch
is refused naming the blob. Also require that `index.json` was present at all — an artifact without it
is refused rather than yielding an empty layout.

**Ordering is the invariant, not a detail.** `read_verified` must have no filesystem effect on any
path, success or failure. Enforce it structurally: keep every write in `write_layout`, keep
`write_layout` unreachable except through an owned `VerifiedArtifact` that only
`read_verified_with_limits` constructs, and state in both rustdocs that this split is the read-side
mirror of `pack_server`'s "a rejected pack adds neither a blob nor an index entry".

**And the SEMANTIC half of that invariant, which Task 2 installed and this task must test.** Framing
and integrity failures never reach a write because `read_verified` has no filesystem access at all.
Semantic failures — the class `unpack_server` rejects at `unpack.rs:625-660` — never reach the
DESTINATION because `install_layout` runs `detect_kind`/`unpack_*` against a staging sibling and
renames only on success. The reviewed draft claimed the broader property without the second half in
place; the tests below are what make the claim true rather than asserted. Craft at least two
semantically-malformed-but-content-addressed tars (for example: a manifest missing a required layer
media type; an envelope carrying the pre-0.2.0 legacy shape `detect_legacy_shape` rejects) and assert,
for each, non-zero exit AND destination absence, plus one `--force` variant asserting a pre-existing
destination is byte-for-byte unchanged.

**Concurrency, documented rather than claimed.** Add a rustdoc section stating what IS guaranteed —
every blob's file name is a digest of its own content, so no interleaving can produce a blob whose
bytes disagree with its name — and what is NOT: `index.json` is not content-addressed, `load` therefore
refuses an existing destination unless `--force`, and two concurrent `--force` runs into one destination
are unsupported. Do not overclaim atomicity the implementation does not provide.

**Property tests, in the lib target.** Under `#[cfg(test)]` in `artifact.rs`, using the `proptest`
dependency the workspace already carries: over arbitrary path strings, assert that any path

leading separator is always refused. Add a never-panics property over arbitrary byte slices fed to
`read_verified` (it must return `Ok` or `Err`, never unwind) — this is the same boundary plan 07's fuzz
target campaigns, and having the property here first is what makes that target's invariant meaningful.

**Integration cases.** In `tests/package_save_load.rs`, build hostile tars in-test with the `tar`

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| tar file -> `read_verified` | Fully untrusted bytes. A tar handed to `load` came from somewhere; nothing about its provenance is known at read time. |
| `config.toml` / `deploy.toml` -> `save` | Author-supplied but locally trusted; still parsed rather than assumed well-formed. |
| `VerifiedArtifact` -> `write_layout` | The one internal boundary that must stay one-way: nothing reaches `write_layout` that did not pass every gate. |
