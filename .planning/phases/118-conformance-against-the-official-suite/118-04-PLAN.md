<objective>
Build the purpose-built dual-version example the official conformance suite runs against (D-05),
and give it the tool / resource / prompt surface the **2025-11-25** scored set requires.

Purpose: D-05 chose a NEW example over reusing `t05_streamable_http_stateless` because an
overloaded example lets a change made for a docs or transport reason silently alter what
conformance measures — and a stateless-only server does not exercise the v1 session path D-04's
first run needs. RESEARCH measured that against the existing `s47_v2_stateless_mrtr`, the v1 leg's
protocol machinery is ALREADY conformant: every one of its 23 v1 failures was a *missing fixture*,
never a protocol defect. This plan supplies those fixtures.

Deliberately dual-purpose: this is also the runnable v2 example Phase 119's DOCS-06 needs. Build it
so Phase 119 can cite it rather than write a second one.

Output: `examples/s54_v2_dual_conformance.rs` with the dual accept-list, the v1 fixture tools, all
`test://` resources, and all named prompts. Plan 118-05 adds the v2 MRTR / input-required surface
and runs both measurements.

**Why this plan is Wave 2 and not Wave 1.** Tasks 2 and 3 obtain each fixture's expected payload by
RUNNING the pinned suite binary at `conformance/node_modules/.bin/conformance`. That binary exists
only after `npm ci --prefix conformance`, and `npm ci` in turn requires the committed
`conformance/package-lock.json` that plan **118-02 creates**. Neither the binary (generated,
gitignored) nor the lockfile-before-commit is visible to the `files_modified` overlap check, so a
same-wave placement would have been an INVISIBLE race: 118-04 could start before 118-02 had written
the lockfile and fail on a missing file. Self-sufficiency (having 118-04 run its own `npm ci`) does
NOT fix this — it still consumes the lockfile 118-02 authors. The honest fix is the declared
dependency, so `depends_on: ["118-02"]` and Wave 2 it is.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Conformance client -> example HTTP server | The suite drives arbitrary MCP requests, including deliberately malformed ones, across this boundary |
| Environment -> process | `PMCP_REQUEST_STATE_KEY` is a secret consumed from the environment |
| Localhost network -> bound socket | The example binds a TCP port on a developer machine and on CI runners |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-118-15 | Information Disclosure | `PMCP_REQUEST_STATE_KEY` leaking into logs or the startup banner | mitigate | The key is read from the environment and NEVER echoed; the banner prints the variable NAME only. Acceptance criterion asserts no `WARN` line and the captured banner is reviewed |
| T-118-16 | Spoofing | DNS rebinding against a locally bound example | mitigate | Bind loopback only (`127.0.0.1`), never `0.0.0.0`. `dns-rebinding-protection` is a SCORED scenario in BOTH requirement sets and must pass — it already passed at v1 against `s47` |
| T-118-17 | Tampering | Port hijack or a stale process from a previous run answering the suite | mitigate | A distinct port (8149) chosen away from `t04`/`t05` (8080/8081) and `s47` (8147); argv[1] override so CI can pick a free port; teardown is owned by plan 118-08's script trap |
| T-118-18 | Denial of Service | An example that keeps live session state serving untrusted requests | accept | The example is a test target bound to loopback, started and killed by CI. Session machinery is REQUIRED (D-04's v1 leg needs `server-session-lifecycle`); `::stateless()` would remove the very thing under test |
| T-118-19 | Repudiation | A scenario reporting a green tick on zero checks, so "conformant" means nothing | mitigate | Acceptance criteria require a nonzero check count per scenario and treat `0 passed, 0 failed` as a finding (RESEARCH measured `server-sse-polling` rendering as a tick on zero checks) |
| T-118-SC | Tampering | npm/pip/cargo installs | mitigate | This plan installs nothing; it consumes the suite already pinned and slopcheck-cleared by plan 118-02 from `conformance/node_modules` |
