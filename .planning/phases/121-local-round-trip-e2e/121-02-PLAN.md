<objective>
The PKG-04 round trip: a package packed in environment A, moved to a distinct environment B,
unpacked there, its required slots filled, and B serving a tool surface set-equal to A's —
fully offline against two independent `wiremock` backends.

Task 1 is this phase's **tracer**: the thinnest path that touches every layer PKG-04 needs
(package build, pack, layout move, unpack, slot resolution, real binary serving, tool-surface
capture, comparison) wired end to end and carrying a real runnable end-to-end verify. It is
production-quality test code, not a scaffold: the comparison helper it introduces is the same
helper plan 121-03's negative tests exercise, and the environment-capture helper is the same
one Task 3's scenario replay uses. Tasks 2 and 3 expand horizontally from that proven slice.

Purpose: this is the milestone's durable asset. It must survive an arbitrary number of
manifest-shape refactors, which is why every assertion is on served behaviour and none is on
manifest field names, layer ordering, or digest values. Parity strictness is fixed by D-07 —
the comparison is over `(tool name, inputSchema)` pairs, not tool names alone and not whole
`ToolInfo` values — and the success criteria this plan discharges are the ROADMAP text as
already corrected under D-05 (commit `91dd3978`), which routes SC2's set-equality assertion
through `required_slots`.

Output: `crates/pmcp-openapi-server/tests/roundtrip_e2e.rs` with four `#[tokio::test]`
functions and the shared helpers they and plan 121-03 depend on.
</objective>

Build these items, in this order:

**`EXPECTED_TOOL_NAMES`** — a `const [&str; 4]` holding `get-tube-status`,
`disrupted-lines-with-detail`, `validate_code`, `execute_code`. Its comment must record that
this list was captured by execution against the real binary on 2026-08-23, not inferred, and

**`london_tube_package_from_fixture(config_bytes) -> ServerPackage`** — adapted from
`pmcp-package/tests/common/mod.rs:138-213`. Parse the fixture's declared config slots with
`parse_declared_config_slots`, map each with a `slot_from_declaration`-style mapper into a
`ConfigSlot` built via `ConfigSlot::new(...)` plus `.with_config_key(...)`, and assemble the
`ServerPackage`. Deriving the PACKAGE's slots from the config this way is correct and desired;
do not confuse it with D-06's expected LITERAL, which must never be derived (Task 2).

**`copy_dir_recursive(from, to)`** — a small `std::fs`-only recursive directory copy. It must
be name-agnostic: it copies whatever entries it finds and knows nothing about the layout's
internal file names. No new dependency.

**`RoundTrip` (or equivalently-named struct) and `pack_a_and_move_to_b(...)`** — the shared
setup this task, Task 3 and plan 121-03 all use.

**Ownership is part of the contract, not an implementation detail.** The struct must OWN both
`TempDir` values as fields — an `_env_a: TempDir` and an `_env_b: TempDir` (underscore-prefixed
because nothing reads them; they are held for their `Drop`) — ALONGSIDE the `PathBuf`s and the
`UnpackedServer`. `TempDir` deletes its directory when dropped, so a helper that returns only
`a_layout_root: PathBuf`, `b_layout_root: PathBuf`, `restored_config_path: PathBuf` and
`unpacked` destroys both directories the moment it returns, and every path it just handed back
dangles. Add a comment on the two fields stating exactly that, so a later reader does not
"clean up the unused fields" (REVIEWS MEDIUM).

It must:
  - create environment A's `TempDir` and `OciLayout::create` a layout inside it;
  - `pack_server` the package with `BinaryMode::Referenced` (the config-only Shape A shape:
    a config-only package NAMES its binary rather than carrying it) and the fixture's bytes
    as the `ConfigFile`;
  - create environment B's `TempDir`, and BEFORE moving anything, assert that B's directory
    read-dir iterator yields nothing and that A's and B's layout root paths differ (D-11);
  - `copy_dir_recursive` A's layout root into B's, then `OciLayout::open` B's root and
    `unpack_server` it;
  - write the restored config bytes to a file inside B's `TempDir`, and return the struct —
    the two owned `TempDir`s, the two layout roots, the restored config path, and the
    `UnpackedServer` (Tasks 2 and 3 read `unpacked`'s config slots directly rather than
    unpacking a second time).
  Prove environment B's isolation ONLY this way — by path inequality and pre-move emptiness.
  Reading the layout's index, counting blobs, or inspecting media types to prove isolation is
  exactly the coupling SC4 forbids and plan 121-03's structural guard machine-checks.

**`capture_tool_surface(tester) -> Vec<(String, serde_json::Value)>`** — the CF-3 mitigation,
and all three parts are independent and all three are mandatory:
  1. call `test_tools_list()` explicitly and assert its `status` is
     `mcp_tester::report::TestStatus::Passed` BEFORE `list_tools()` is called;
  2. assert the returned vector is non-empty;
  3. assert the snapshot contains every one of `EXPECTED_TOOL_NAMES` — the positive floor.
     Emptiness alone does not catch "A and B both degraded to the same one tool".
  Project each `ToolInfo` to `(name.clone(), input_schema.clone())` per D-07 and sort the
  vector by name before returning. `ToolInfo` derives no `PartialEq`, `Eq` or `Hash`, so D-07's
  projection is forced by the type system, not a stylistic preference; `serde_json::Value` derives
  `PartialEq`, `Eq` and `Hash` but no `Ord`, so a sorted vector compared with `assert_eq!` is

  readable diff on failure. `description` and `output_schema` are excluded: all four tools
  carry no output schema today, and Phase 120's structured-output plumbing is still moving.
  Construct a FRESH `ServerTester` per environment — `ServerTester` memoizes its tool list

**`SurfaceMismatch`** — a plain enum with a hand-written `Display` impl (no new dependency).
It needs at minimum four variants: "a tool present in A is missing from B" carrying the tool
name; "a tool present in B is missing from A" carrying the tool name; "a tool's input schema
differs" carrying the tool name; and **a duplicate-tool-name variant carrying the repeated
name and which side it came from**. Every variant's `Display` output MUST name the specific
tool, because plan 121-03's negative tests assert on that text.

**`compare_tool_surfaces(a, b) -> Result<(), SurfaceMismatch>`** — the single comparison
helper. The positive path in this task and the negative paths in plan 121-03 both route
through it; if they do not, the red direction proves nothing about the green one.

**It must build a name-keyed map per side and reject duplicates BEFORE comparing** (REVIEWS
MEDIUM). Insert each `(name, input_schema)` pair into a `BTreeMap<String, serde_json::Value>`
for A and another for B, and return the duplicate-name variant the first time an insert
displaces an existing key. Sorting a `Vec` by name alone leaves the order of two entries with
the same name but DIFFERENT schemas undefined, so a duplicated registration could make the
comparison pass or fail depending on sort stability rather than on the property under test.
MCP tool names are meant to be unique, but "meant to be" is the assumption class this repo
keeps getting burned by — make it a checked precondition with its own error, then do the set
comparison over the two maps. The map keys also make the missing-from-A / missing-from-B /
schema-differs determination explicit rather than positional.

**`serve_environment(config_path, base_url, app_key) -> (SocketAddr, JoinHandle)`** — copy the

load-sensitive flakes.

  - Assert `compare_tool_surfaces(&snap_a, &snap_b)` is `Ok(())`, with a failure message that
