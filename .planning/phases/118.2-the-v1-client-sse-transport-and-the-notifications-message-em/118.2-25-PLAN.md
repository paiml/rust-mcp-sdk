<objective>
Serialise the two transport-wide sequences that are protected today only by an accident — the client's
outer transport guard — so that plan 23 can remove that guard without creating a new permanent
failure.

Purpose. Plan 23 removes the transport write guard from the client's send path, which is the right
fix for the send-path wedge. But the guard was doing a second job nobody wrote down: it made every
POST on a transport strictly one-at-a-time, and two things underneath depend on that.

First, the 401 refresh. `post_once` reads a TRANSPORT-WIDE `AuthProvider` out of the config and, on a
401, calls `on_unauthorized()` to EVICT the cached token, then rebuilds the request — and the rebuild
is where `get_access_token()` runs and the rotating refresh token is actually presented to the IdP.
The trait's own rustdoc states that division explicitly: evict here, so that the subsequent
`get_access_token()` returns a freshly-vended token. The trait carries no concurrency contract — its
documented guarantee is at-most-once per REQUEST, not per transport. With two POSTs in flight, both
can purge and, more importantly, both can VEND; against a rotating refresh token the second presents
an already-rotated one and fails, and its purge destroys the token the first just cached.
Refresh-token destruction is a recorded SDK blocker for the durable-agent deployment shape, so this is
a live configuration rather than a thought experiment.

**The guarded region is therefore drawn around the VEND, not around the purge.** Single-flighting only
`on_unauthorized` would leave both callers reaching `get_access_token` concurrently one step later —
the same defect, and invisible to any fence that counts purges. The lock ends after the retry request
is BUILT and before it is SENT.

Second, the session-stream restart. `post_body` reaches `start_sse` on the 202 branch, and
`start_sse` takes the abort handle, aborts, opens a GET across an await, clears the terminal latch and
respawns — a transport-wide read-modify-write with an await in the middle. Two overlapping calls can
each take a `None` handle, each open, and the second's stored handle can orphan the first's reader.
`close()` aborts exactly one `JoinHandle`, so the orphan outlives the transport.

**Why this plan lands BEFORE plan 23, not after.** Serialising something the outer guard already
serialises is a no-op — it costs nothing and changes no observable behaviour today. Doing it
afterwards would leave one or more commits in which the hazard is reachable and unprotected. The
order is free in one direction and lossy in the other.

**What the failure mode becomes.** Before: nothing, today, for a client that sends one call at a time
— and, for anyone holding two clones of one transport, an intermittent auth failure that destroys a
rotating refresh token and an orphaned reader `close()` cannot reach. After: a concurrent 401 produces
one refresh and the loser retries with the winner's token; a concurrent restart produces one reader.
A solo caller sees byte-identical behaviour. No caller loses a capability, and no new bound, deadline
or timeout is introduced anywhere.

Output: two serialisations, two deterministic fences, and the rustdoc that lets plan 23 make a
concurrency claim which is actually true.

**Locked decisions this plan preserves rather than revisits.** D-15's rule carries forward verbatim:
both fences are RED against the unfixed tree first. D-02's "no new public config" holds — nothing
configurable is added and no public signature changes. D-06's principle holds in its strongest form:
no trait is touched at all, so no external implementor is affected.
</objective>

**The 401 path, exactly as it stands.** `StreamableHttpTransport::post_once`
(`src/shared/streamable_http.rs:2461`) builds the request through
`build_request_with_middleware` — which is where `get_access_token()` is called — sends it at `:2474`,
returns early unless the status is 401, reads `self.config.read().auth_provider` at `:2505`, returns
the 401 unchanged when there is no provider, calls `provider.on_unauthorized().await?` at `:2511`,
rebuilds from a byte-identical body snapshot at `:2514`, and sends the retry at `:2520`. The retry is
structurally at-most-once: it returns directly, so there is no loop to go around twice. That property
must survive this plan unchanged.

**The client-side `AuthProvider` trait** is at `src/shared/streamable_http.rs:3996`, public, with
`get_access_token` and a defaulted `on_unauthorized`. Its rustdoc's "Retry guarantee" section says
the SDK invokes `on_unauthorized()` at most once per REQUEST — a per-request statement that says
nothing about two requests. It is NOT to be edited: the fix is in the transport.

**WHERE THE VEND ACTUALLY HAPPENS — the fact this plan is drawn around.** The trait rustdoc
(`:4000-4006`) divides the work: `on_unauthorized` EVICTS the cached token, and the SUBSEQUENT
`get_access_token()` "returns a freshly-vended token". That call is at
`Self::build_request_from_parts` (`src/shared/streamable_http.rs:2180`, inside the
`if let Some(auth_provider)` arm), reached from `post_once`'s retry rebuild at `:2513-2515` through
`build_request_with_middleware` (`:2128`). So the network round trip that presents a rotating refresh
token is in the REBUILD, not in the purge, and the guarded region has to reach it.

**`start_sse`** (`:1824`) in order: take-and-abort the existing handle; build the owned reader
context; `open_sse_once(cursor).await?` (which can return `Ok(None)` for a 405 and returns early);
the `StreamKind::Session`-scoped terminal-latch reset seam; then spawn and store the new handle. Its
callers are `send_with_options`'s resumption-cursor branch (`:2371`) and `post_body`'s 202
`InitializedNotification` branch (`:2603`). The reconnect loop deliberately does NOT call it — it
re-opens through `open_sse_once` because `start_sse` aborts `abort_handle` as its first act and a
recursive call would abort the task making the call. Read that comment before choosing where the new
serialisation goes.

**`close()` aborts exactly ONE `JoinHandle`** — the file states this at the abort-handle field's own
comment. That is why an orphaned reader is unreachable rather than merely redundant.

**The transport is `#[derive(Clone)]`** (`:1159`) with every field an `Arc`, a `watch` sender or an
atomic. Two clones share the config, and therefore the `AuthProvider`, and share the abort handle and
the terminal latch. That is what makes both hazards reachable TODAY, before plan 23 — and it is the
shape a durable agent holding one transport across concurrent tasks actually has.

**The synchronisation primitives already in this file**, so no dependency is added and no new idiom is
invented: `parking_lot::RwLock` for short non-await state (`config`, `terminal`, `abort_handle`) and
`tokio::sync::Mutex` for state held across an await (`receiver`, `:1382`). The refresh lock and the
restart lock are both held across awaits, so both are the latter.

**The harness.** `RecordingServer` in `tests/client_sse_stream.rs` is a raw HTTP/1.1 listener; `serve`
(`:700`) dispatches GET to `serve_get` and POST to `serve_post`. `open_get_connections()` (`:661`)

one live reader from two. `wait_for` and the `close_live` watch show the file's idioms for a
test-released gate and for why a `watch` is used rather than a `Notify`.
