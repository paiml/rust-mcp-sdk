<objective>
Close **BLOCKER 1**: the sticky terminal latch pre-empts an in-flight, SSE-delivered POST response,
permanently.

Purpose. `118.2-15` moved terminal stream reasons off the response FIFO onto a write-once latch, and
`drain_or_latch` (`src/shared/streamable_http.rs`, around `:876-889`) surfaces that latch the moment
`try_recv()` reports `Empty`. On the POST-answered-with-`text/event-stream` path this very phase
introduced for D-01, `post_body` spawns a DETACHED reader and returns `Ok(())` (around `:2252`)
BEFORE the answer lands on the queue. The queue is therefore legitimately, transiently empty while a
real answer is still on the wire — and the latch wins instantly, with a stale reason belonging to a
different stream.

Reachability is ordinary, not adversarial: the GET session stream spending its deliberately small
`MAX_SSE_RECONNECT_ATTEMPTS = 2` budget, a `405` on reconnect, or one earlier truncated streaming-POST
response. And because the latch is `Arc`-shared across every `#[derive(Clone)]` clone, written once,
and cleared by no constructor, no `start_sse` and no `close`, the FIRST trip permanently fails every
later `tools/call` against an SSE-answering server for the life of the process. Severity direction
WORSENED versus pre-closure, where a bad terminal reason could poison at most one call.

Fence 16 cannot reach it: its harness answers `content-type: application/json`
(`tests/client_sse_stream.rs`, around `:754`), so the response lands on the queue synchronously
inside `send()` and the queue-wins-over-latch rule fires. That is precisely why this defect shipped
green.

Output: a stream-scoped terminal reason, a latch gate that never answers a caller with a live POST
reader outstanding, a reset seam on a successful session re-open, and two new fences — one of them
the SSE-answered-POST shape the current fences miss.

**Locked decisions this plan preserves rather than revisits.** D-01 (both `text/event-stream` sites
read incrementally) is what makes an in-flight, off-queue answer possible at all — this plan does not
retreat from it. D-03 (bounded auto-reconnect under a budget) is untouched: the reconnect curve, the
budget and `MIN_SSE_RECONNECT_DELAY` all stay exactly as `118.2-14` left them; only what a spent
budget is allowed to ANSWER changes. D-04 (a bounded receive queue whose reader awaits capacity and
never drops a frame) is why the queue is still drained before anything else in `drain_or_latch`.
D-05 (a frame that fails to parse ends the stream with a named error) keeps its behaviour; the error
merely gains the name of the stream that raised it. 118.1's D-04 (each fence demonstrated RED against
the unfixed tree before its fix lands) governs task 1.
</objective>

**The latch, as `118.2-15` built it.** `TerminalReason { kind: TerminalKind, message: String }` is
stored in `StreamableHttpTransport::terminal: Arc<RwLock<Option<TerminalReason>>>` and woken through
`terminal_signal: Arc<watch::Sender<u64>>`, a GENERATION counter (a consumer only needs a wake edge).
`latch_terminal_reason(delivery, error)` is first-writer-wins: it returns early when the slot is
already `Some`, and bumps the generation only on the write that WON, after the write guard is
dropped. Five call sites latch today — `spawn_sse_reader` (a POST response stream that dropped),
`end_of_frame_stop`'s `Corrupt` arm, `deliver_sse_event`'s parse-failure arm, and `run_session_stream`
at all three of budget-exhausted / reconnect-405 / reconnect-open-failed.

**`ReaderDelivery` is the extension point.** Its own rustdoc says to extend the struct rather than add
parameters — `read_sse_body` and its helpers are already at clippy's `too_many_arguments` edge. It
carries `sender`, `terminal`, `terminal_signal` and `shutdown` today. Add the stream identity there.

**Two constructors feed it, and they must differ.** `reader_delivery()` builds the bundle;
`sse_reader_context()` calls `reader_delivery()` for the GET session reader, and `spawn_sse_reader()`
calls it for the detached POST reader. Give `reader_delivery` a `StreamKind` parameter so those two
call sites — the only two — state which they are. A default would silently mislabel the session
stream, which is the exact failure this plan is fixing.

**`drain_or_latch` has exactly one caller**, `Transport::receive`, so its signature is free to grow.
`receive()` subscribes to `terminal_signal` FIRST, then locks the receiver, then loops over
`drain_or_latch` and a `biased` select whose first arm is `receiver.recv()`. That ordering is
load-bearing and stays.

**`post_body`'s SSE branch is the race.** It does `drop(self.spawn_sse_reader(response.into_body()))`
and returns `Ok(())`. The reader is DETACHED on purpose: `abort_handle` belongs to the GET session
stream and parking a POST reader there would let the next `start_sse` tear down a call's own stream.
Any in-flight accounting must therefore be incremented SYNCHRONOUSLY in `spawn_sse_reader`, before
`tokio::spawn`, or `dispatch_request` can reach `receive()` first and observe a count of zero.

**`start_sse` already has the success point the reset seam needs.** It aborts the old handle, builds
the context, and does `let Some(body) = context.open_sse_once(cursor).await? else { return Ok(()) }`.
The `Some(body)` arm is a confirmed live re-open; the `None` arm is a `405` (the server offers no GET
stream) and must NOT reset.

**Error messages fences match on.** `reconnect_budget_exhausted` renders the substring
`reconnect budget`, which `tests/client_sse_stream.rs`'s `RECONNECT_PHRASE` matches on at two sites.
A stream-name PREFIX keeps that substring intact; rewording the middle of that message does not.

**The harness** (`tests/client_sse_stream.rs`): `serve` routes a POST by method through
`sse_post_methods` to `serve_post_sse` (a body held open forever, pumping pushed frames), otherwise
to `serve_post`, which answers `initialize`, then `call_answer(..)`, then a bare `202`. `call_answer`
builds the WHOLE HTTP response including its head; splitting the JSON body out of it is what lets the
same per-answer `call_marker(sequence)` numbering be reused for an SSE-delivered answer, which is
required for the "call 2 got call 2's marker" assertion. `close_get_streams_on_accept()` makes every
GET a `text/event-stream` with `content-length: 0` — the shape that spends the reconnect budget.
`advertise_tools()` must be on or `call_tool` fails its capability assertion before reaching the wire.
`SHIPPED_RECONNECT_BUDGET`, `RECONNECT_BOUND` and `RECONNECT_QUIET` are the constants fence 16 uses to
wait the budget out; reuse them rather than minting new ones.

<assumption_delta_decision>
The deterministic detector returned `detected: true` with a `pluralization` signal on
`D-01, second site` — and that signal is exactly right, which is why it is recorded rather than
waved through.

**What lost its monopoly.** Before Phase 118.2 this transport had ONE SSE stream: the GET session
stream. D-01 added a second KIND — one detached reader per streaming POST response. `118.2-15` then
minted a terminal-reason latch whose rustdoc says "the reason this **transport's** stream ended",
i.e. it names the TRANSPORT as the owner of a terminal reason. That singular noun is the assumption
BLOCKER 1 falsifies: the transport has N streams (one session plus one per in-flight streaming POST)
and one stream's terminal end is not the transport's.

**Decision: `promote`.** The primary noun becomes the STREAM. A terminal reason is a fact about the
stream that raised it (`StreamKind::Session` or `StreamKind::PostResponse`), and "the transport's
terminal reason" is demoted to a DERIVED view: the latched reason, surfaced only when no POST-response
reader is live. That is the promote-not-add-alongside move — the old transport-wide reading is kept
as a projection of the new per-stream fact, not maintained beside it as a still-required primary.

**Accepted debt named explicitly.** The latch remains a single slot rather than a per-stream map, so a
`PostResponse` reason from an earlier call can still be the one surviving reason a later caller sees
once the queue is empty and no reader is live. The reset seam bounds how long that can persist; the
full removal is per-id response ROUTING, already recorded in `deferred-items.md`. What would force a
later promote to a per-stream map: any change that lets two POST-response streams be terminally
distinguishable to a caller — which per-id routing is precisely the shape of.

**Companion invariant test (accepted, task 1).** Fence 21 is that invariant: a session-stream terminal
reason never answers a caller whose own POST-response stream is still live. It goes red the instant a
future change reintroduces the transport-as-owner assumption.
</assumption_delta_decision>
