Add the emitter family. **Synchronous, not `async`** — the sink is a synchronous
`Arc<dyn Fn(Notification) + Send + Sync>`; `report_progress` is `async` only because the
`ProgressReporter` TRAIT is, and D-06 adds no trait, so `async` would buy nothing and would force every
logging call site into an `.await`. Return `crate::Result<()>` (not `()`) so a future "sink refused"
signal is not a breaking change:

- `pub fn log(&self, level: LoggingLevel, message: impl Into<String>) -> crate::Result<()>`
- `pub fn log_with_data(&self, level: LoggingLevel, message: impl Into<String>, data: serde_json::Value) -> crate::Result<()>`
- `pub fn log_info(&self, message: impl Into<String>) -> crate::Result<()>`
- `pub fn log_warn(&self, message: impl Into<String>) -> crate::Result<()>`
- `pub fn log_error(&self, message: impl Into<String>) -> crate::Result<()>`

Behaviour, in one shared private helper that all five delegate to (so the filter rule exists once):
1. Compare `level` against `self.log_level.unwrap_or(DEFAULT_LOG_LEVEL)`. If `level < effective`, return
   `Ok(())` without constructing anything.
2. Build `LogMessageParams::new(level, message)` — `logger` defaults to `None`. Do NOT synthesise a
   logger value from the tool name; that would be a guess. `data` is set only by `log_with_data`.
3. Wrap in `ServerNotification::LogMessage(..)` and hand it to `self.log_sink`.
4. **D-08: no sink → `Ok(())`, silently dropped.** Matches `report_progress` (`:663`) exactly, so a
   handler stays callable outside a server — `RequestHandlerExtra::default()` is documented for "testing
   and simple tool invocations". State the accepted cost plainly in the method rustdoc: a misplumbed
   transport looks identical to a quiet handler, and the conformance fence is what catches it, so this is
   a production-diagnostics hole rather than a false-green in the gate.

**D-09: no rate limit.** `ServerProgressReporter` rate-limits to 100 ms and that is right for progress —
dropping an intermediate value loses nothing because the next supersedes it. Log records are not
idempotent: each one is the only copy of its information, and a rate limiter silently deletes evidence.
Say this in the rustdoc so the omission reads as a decision.

**Pitfall 4, stated in the rustdoc rather than discovered later.** On v2 the sink a record rides is
`new_v2_progress_queue()` — an `mpsc::channel(64)` with an explicit DROP-NEWEST `try_send` policy,
because the closure is synchronous and must not block. So a v2 handler emitting more than 64
notifications in one call loses the excess, and that is the progress queue's policy, not the emitter's.
Also note that the v2 vehicle is only attached when `v2_multi_frame_eligible` holds (era is V2 AND
`!config.enable_json_response` AND the request's `Accept` contains `text/event-stream`), so a v2 client
that asked only for JSON gets no log records at all — correct behaviour to document, not a bug to fix.
Do NOT make the emitter block; the sink signature is a synchronous `Fn(Notification)`.

**Do not gate emission on `ServerCapabilities.logging`** (`src/types/capabilities.rs:118`). The sink is
per-request and the capability is advisory; gating would make a correctly-plumbed server silently mute.
Document that servers SHOULD declare it (RESEARCH Open Question 6).

Write a rustdoc doctest on `log` that constructs `RequestHandlerExtra::default()` and calls `.log(..)`,
relying on D-08 to make it `Ok(())` with no server. Doctests are in the gate.
