# Phase 118.2 Plan 10: The Two Halves Meet — Summary

pmcp is now on **both** ends of a live v1 session stream carrying a handler-emitted
`notifications/message`, proven at the transport layer with zero new public API. And the era-matrix
arm that has been carrying the client gap was **not** flipped to `completed`, because measurement
falsified the flip — it was strengthened instead, so it now records *which* hop still fails rather
than implying the stream is dead.

## Task 1 — The joint fence

`tests/pmcp_both_ends_logging.rs`, 2 fences, both green in **1.1 s**.

| Fence | What it pins |
|---|---|
| `a_pmcp_client_receives_a_handler_log_record_over_a_live_v1_session_stream` | the record reaches pmcp's own `StreamableHttpTransport` over the live v1 session GET stream, matched on the SENTINEL, **and** arrives BEFORE the call's reply |
| `the_record_the_client_receives_carries_the_emitted_level` | the emitted `LoggingLevel::Info` survives the round trip as a TYPED level on the client side |

**Assertion layer: the transport.** `Client::notification_tx` is `None` at all three construction
sites (`src/client/mod.rs:406`, `:453`, `:496`), `ClientBuilder` has no field for it and no setter,
and the forwarding branch at `:3764` is therefore permanently dead — a `notifications/message` that
reaches a `pmcp::Client` is run through the middleware chain and dropped. So the fence drives
`Transport::receive()` and matches
`TransportMessage::Notification(Notification::Server(ServerNotification::LogMessage(..)))`.

**Sentinel, not variant.** `SENTINEL = "pmcp-both-ends-log-record-8c1e4f2a"`. The fence asserts the
message TEXT, so an unrelated `notifications/message` cannot satisfy it (T-118.2-10-03).
`grep -c 'timeout('` is **10**, against the plan's floor of 2.

**Ordering (the plan's step 5).** Arrival is recorded as a `Vec<Seen>` and the claim is
`record_index < reply_index`. That is the "while the tool call was still outstanding" half, expressed
as an ordering over the client's own receive queue rather than as a timing race: the reply had not
yet been observed when the record was. On v1 the record is framed onto the session stream by the
handler while it runs, and the reply is framed after the handler returns — which is what the fence
measures.

**Why the `tools/call` is issued on a transport clone rather than through `client.call_tool(..)`.**
The handshake DOES run through a real `pmcp::ClientBuilder`, so the GET stream is opened by the
shipped path (plan 01's `202` branch), and the client's transport clone shares every field behind an
`Arc`. But a real `call_tool` would park the client in `dispatch_request`'s wait loop, which drains
the same shared queue and drops every notification it sees — the record would be consumed before it
could be observed. Issuing the call on the observer makes the fence the single consumer. An idle
`pmcp::Client` runs no background receive loop, so nothing races it.

### No v2 arm — stated rather than left silent

The plan says to add a v2 arm "if it is cheap". It is not, at this layer: driving v2 through a raw
`StreamableHttpTransport` means setting `protocol_version` and `v2_mode`, which are private fields
written by `ClientBuilder::with_protocol_version` during negotiation — and going through
`ClientBuilder` puts the client's own wait loop back on the queue, which is the very thing this fence
avoids. Plan 07's `a_v2_handler_log_record_rides_the_multi_frame_post_body` already covers the v2
vehicle (with a raw reader), and plan 09's `tests/log_records_example_run.rs` covers both v2
directions of SEP-2575. The omission is recorded here rather than left silent, as the plan asks.

## Task 2 — The era-matrix arm: strengthened, not flipped

**The plan's `must_haves.truth` "asserts `completed`, not `no-live-stream`" is FALSIFIED by
measurement.** Reporting that rather than forcing it is the whole of this task.

### What was measured

The v1 arm's expectation was temporarily flipped to `completed` on BOTH trees so the assertion would
print the observed payload (`target/118.2-10-era-base.log`):

| Tree | Time | `detail` |
|---|---|---|
| base `cb5d1365` | **0.18 s** | `Protocol error: -32603 - Dispatch oneshot channel closed` |
| HEAD | **31.3 s** | `Protocol error: -32001 - Server request dispatch-1 timed out` |

The status is `no-live-stream` on both, because `era_target::undelivered()` reports that value for
**any** peer error — it is a catch-all, and the wire spelling did not have to move for the CAUSE to.

A scratch probe (a real `StreamableHttpTransport` against a real `StreamableHttpServer` whose tool
reaches for `extra.peer().sample(..)`, issuing the `tools/call` POST on one transport clone and
draining `receive()` on another) settled which cause it is, verbatim:

```
PROBE frame 0: Request { id: String("dispatch-1"), request: Client(CreateMessage(CreateMessageParams { .. })) }
PROBE frame 1: TIMEOUT
```

**Delivery is fixed.** The server's `sampling/createMessage` request reaches pmcp's own client over
the live v1 session stream. What fails is the ANSWER, and it is a lifecycle deadlock:

* the server holds the `tools/call` POST open for the whole duration of the handler, answering `202`
  only after it returns;
* `Client::dispatch_request` awaits `transport.send(..)` to COMPLETE before entering the receive loop
  that would dispatch the inbound request;
* so the client is parked inside its own `send()` while the handler waits on it, and the server's
  peer request expires. The first probe run measured this directly: `send within bound: Elapsed(())`
  at a 10 s bound.

**Not fixed here (Rule 4).** Both candidate fixes are `src/` behaviour changes to a core path with
their own ALWAYS-requirement package and semver verdict: either `Client::dispatch_request` overlaps
its outbound send with its receive loop, or the server answers the request POST `202` before running
the handler (detached dispatch). Choosing between them is a design decision, not a bug fix, and this
plan's `files_modified` are two test files. Recorded in `deferred-items.md` and appended to
`.planning/WINDOWS.md`.

### (a) The status constant — kept, and its rustdoc corrected

`DEP_STATUS_NO_LIVE_STREAM` stays in ACTIVE use, so it is neither deleted nor
`#[allow(dead_code)]`-annotated. Its rustdoc no longer claims "no live client stream existed to
deliver it on" — that is now false. It says what is true: the peer was present, the request was
issued, the answer never came back; the wire spelling is a CATCH-ALL that cannot by itself
distinguish the two causes, which is why the arm now also asserts the detail. The name still MATCHES
`era_target`'s exactly, per the block's stated greppability convention, and it is still re-spelled
rather than imported.

### (b) The arm — strengthened in both directions

Three new constants, all re-spelled locally: `DEP_RESULT_DETAIL_FIELD` (`"detail"`),
`DISPATCH_TIMEOUT_MARKER` (`"timed out"`) and `BASE_FAIL_FAST_MARKER`
(`"Dispatch oneshot channel closed"`). The assertion is

```rust
detail.contains(DISPATCH_TIMEOUT_MARKER) && !detail.contains(BASE_FAIL_FAST_MARKER)
```

fenced in BOTH directions because "which hop is missing" is a property of the PAIR — a one-directional
check would pass against an implementation whose text happened to contain both. It is **non-vacuous
by measurement**: it would have gone red at the phase base, where that same field read
`Dispatch oneshot channel closed`. Its failure message names the regression explicitly and points at
`binary(client_sse_stream)` and `binary(pmcp_both_ends_logging)`.

The tripwire's `IF THIS REPORTS \`completed\`` branch was rewritten to describe the CURRENT last hop
("a pmcp CLIENT has learned to ANSWER a server-to-client request issued while its own call is
outstanding") rather than the one that is now closed.

### (c) The module doc — the fixed state, with history kept

The `:609-625` paragraph is rewritten. It now:

* opens with the fixed state — the request is DELIVERED and the round trip stops at the ANSWER;
* names **Phase 118.2** and BOTH client defects as recorded history: the `start_sse(None)` call
  sitting inside `if !response.status().is_success()` when `202 Accepted` **is** a success status, so
  the branch was dead and no GET was ever issued (118.2-01); and the whole-body `collect()` waiting
  for an end-of-body a session stream never has (118.2-03), with 118.2-04's bounded reconnect on top;
* points at the new proof — `tests/pmcp_both_ends_logging.rs` is the pmcp-on-both-ends fence, while
  `tests/http_peer_roundtrip.rs` remains the server-half proof with its raw reader;
* carries the measured base-vs-now `detail` table and the lifecycle account above, so a future reader
  can tell a fix from a regression without re-deriving either.

Erasing the pre-fix state would have left a reader unable to tell whether the assertion was always
`no-live-stream` or had been through this. T-118.2-10-01 is discharged in its mirror image: the
threat register worried about a flipped assertion under stale prose; what shipped is an UNflipped
assertion under prose that now says exactly why it did not flip.

## Deviations from Plan

### 1. [Rule 1 — the plan's premise was falsified by measurement] the flip did not happen

Documented in full under Task 2. The plan's Task 2(a) instructs "switch the v1 arm's expectation to
`completed`" and its `must_haves.truths` names the flip. Measured reality is that the round trip still
does not complete, for a NEW reason. The plan's own objective — "a flipped assertion under prose that
still describes the broken state is worse than either alone" — argues directly for what was done
instead: keep the assertion honest, rewrite the prose to the measured state, and STRENGTHEN the arm so
the residual is pinned rather than implied.

Two of the plan's acceptance criteria are therefore unsatisfiable as written and are recorded rather
than worked around:

| Criterion | Status |
|---|---|
| "`deprecated_capabilities_complete_under_both_eras` asserts the `completed` status on the v1 arm" | **NOT met** — falsified by measurement; the arm asserts `no-live-stream` plus a detail that pins the cause |

Exactly 2 literal occurrences remain: the constant definition (`:487`) and one module-doc mention (`:645`) |

### 2. [Recorded, mechanism only] `git archive` instead of `git worktree`

The plan's RED procedure opens with `git worktree add ../pmcp-118.2-base <phase-base-sha>`. This
executor runs sequentially on the shared working tree under a standing prohibition on any
`git worktree` command and on `git stash`. `git archive <sha> | tar -x` into a scratch directory
produces the same tree while touching NO git state, which is strictly safer. The live `Cargo.lock` was
copied in because it is gitignored and would otherwise re-resolve. Evidence and cleanup are identical:
the RED was observed against the base tree, and `git worktree list` shows no leftover.

### 3. [Recorded, no change] the plan's Task 2 verify command cannot run as written

`--features "full" --manifest-path crates/pmcp-team-servers/Cargo.toml` fails with
`the package 'pmcp-team-servers' does not contain this feature: full` — and, piped into `tail`, it
**exits 0 while running zero tests**, which is precisely the false-green shape `make lint-plans`
exists to catch. `--all-features` (plan 08's recorded working spelling) was used instead. Worth
naming: the failing form was caught only because the output was read, not because the exit status
said anything.

### 4. [Beyond plan] the arm now asserts the `detail`

Not requested. Added under Rule 2: without it, the arm's expectation would be a bare catch-all that
reads identically before and after the phase's client work, so a REGRESSION of that work — the client
ceasing to hold a live stream — would leave this fence green. The assertion is measurably
discriminating (red at the phase base) and fenced in both directions.

### 5. [Beyond plan] a second fence on the level

`the_record_the_client_receives_carries_the_emitted_level` is one arm more than the plan named. The
level is what every consumer filters on; a record that arrives at the wrong severity is a record no
consumer can act on. Split from the ordering fence rather than appended to it, so a failure names
which property moved.
