<objective>
Close **CR-01**: a peer can drive pmcp's own client into an unbounded, zero-delay reconnect loop.

This is the phase's tracer slice — the thinnest path that runs end to end through every layer the
gap closure touches (recording harness -> hyper GET -> incremental reader -> reconnect loop -> a
server-side assertion), and the smallest change that proves the whole loop before anything expands
out from it.

Purpose: CR-01 is a **remote-triggerable client-side denial of service**, confirmed twice — by the
code review and independently by the verifier reading the merged source. A server (hostile, or a
broken proxy replaying a cached page) that answers every GET with `retry: 0` plus one SSE frame and
then closes the body drives the client into a tight loop: 100% of a core burned locally, a request
flood at the server, and a **fresh `auth_provider.get_access_token()` call per iteration**. Two
independently-documented decisions combine into it, and BOTH must be fixed:

1. `next_reconnect_delay` (`src/shared/streamable_http.rs:2849-2858`) clamps a peer-supplied
   `retry:` only from ABOVE (`:2851`). `SseEvent::retry` is `Option<u64>` milliseconds parsed
   straight off the wire, so `retry: 0` yields `Duration::ZERO`.
2. `run_session_stream` refunds the entire attempt budget on ANY single delivered event
   (`if delivered { attempt = 0; }`, `:2792-2793`).

**Why no existing fence catches it, measured rather than assumed.** The one fence that exercises the
retry-budget path — `reconnect_gives_up_after_the_retry_budget_with_a_named_error`
(`tests/client_sse_stream.rs:1433`) — uses `close_get_streams_on_accept()`, a stream that delivers
**nothing**, so `delivered` is always `false` and the reset arm is never taken. The verifier
confirmed by grep that no other fence name matches "reconnect" plus a delivered frame. The missing
fence is therefore part of the fix, not an extra.

Output: `MIN_SSE_RECONNECT_DELAY`, `RECONNECT_BUDGET_RESET_UPTIME`, `budget_reset_earned`, the
harness mode that produces a delivered-arm reconnect, the fence, and the unit + property coverage of
the pure delay function.
</objective>

**The four existing reconnect constants** (`src/shared/streamable_http.rs:493-540`), all private, all
lifted from the reference client's `streamableHttp.js` and all spelled in seconds because
`clippy::duration_suboptimal_units` requires it:
`INITIAL_SSE_RECONNECT_DELAY = Duration::from_secs(1)`,
`MAX_SSE_RECONNECT_DELAY = Duration::from_secs(30)`,
`SSE_RECONNECT_GROWTH: f64 = 1.5`,
`MAX_SSE_RECONNECT_ATTEMPTS: u32 = 2`.
`MAX_SSE_RECONNECT_DELAY`'s rustdoc reasons about the UPPER direction only ("an uncapped one lets a
peer park a client's reader task"). That rustdoc is now half the story and must say so.

**The reconnect loop's exact shape** (`run_session_stream`, `:2767-2832`), in order per iteration:
read the body; destructure `SseBodyEnd::Dropped { cause, delivered, retry }` (any other variant
returns); the budget refund; the `attempt >= MAX_SSE_RECONNECT_ATTEMPTS` terminal check; a
`sender.is_closed()` check; `tokio::time::sleep(next_reconnect_delay(attempt, retry))`; a second
`is_closed()` check; `attempt += 1`; `open_sse_once(self.reconnect_cursor())`.

**Where `delivered` and `retry` come from:** `drain_pending_events` (`:2313-2333`) sets
`progress.retry = Some(Duration::from_millis(millis))` from `event.retry` BEFORE delivery, and sets
`progress.delivered = true` after each successful send. `SseProgress::dropped` (`:2297`) carries both
into `SseBodyEnd::Dropped`.

**`std::time::Instant` is NOT currently imported** into `src/shared/streamable_http.rs` — only
`use std::time::Duration;` at `:27`. Add the import at that site; do not reach for
`tokio::time::Instant`, whose value changes under `tokio::time::pause()` and would make the uptime
arm's behaviour depend on whether a caller paused the clock.

**Cognitive-complexity budget.** `run_session_stream` is already split four ways specifically to
stay under the repo's PMAT cog-25 gate (see the comment block at `:2148-2152`). Adding an inline
`&&` with an `Instant::elapsed()` call pushes it back up. The uptime decision therefore goes into a
pure free function, which is also what makes it unit-testable with no clock manipulation.

**The test harness this fence extends** (`tests/client_sse_stream.rs`, shipped by 118.2-01 and
extended by 03/04 rather than rewritten):
- `Shared` (`:190-250`) — `request_lines`, `get_cursors`, `close_get_on_accept: AtomicBool`,
  `close_live: watch::Sender<u64>`, `frames_rx`, `open_gets`.
- `serve` (`:411-455`) dispatches: for a `GET ` request line it pushes the cursor slot, then either
  `serve_get_that_ends_at_once` (when `close_get_on_accept`) or `serve_get`.
- `serve_get_that_ends_at_once` (`:537-543`) is the model for the new mode: a `200` +
  `content-type: text/event-stream` + `cache-control: no-cache` + `content-length: 0` +
  `connection: close` head, flushed, then `shutdown()`. `connection: close` rather than a poolable
  socket is deliberate — it makes "this stream is over" unambiguous to hyper so the reconnect opens
  a NEW connection instead of racing a pooled one.
- `write_chunk` already exists for chunked writes (used by `pump_frames`).
- `progress_frame(id, token, progress, pad)` (`:740`) builds a complete SSE frame carrying `id:` and
  a `notifications/progress` payload. It does **not** emit a `retry:` field; the new mode needs one.
- Bounds: `BOUND = 5s`, `POLL = 10ms`, `RECONNECT_BOUND = 20s`, `RECONNECT_QUIET = 4s`.
- `SHIPPED_RECONNECT_BUDGET: usize = 2` (`:152`) is the in-test mirror of the private
  `MAX_SSE_RECONNECT_ATTEMPTS`. That mirroring is the file's established pattern for a private
  constant a fence must reason about; the new floor constant follows it.
- `RECONNECT_PHRASE: &str = "reconnect budget"` (`:1369`) is what the exhaustion error must contain.

**The v1 severability tripwire's naming constraint.** `tests/v1_severability_tripwire.rs` scans
`src/shared/streamable_http.rs` for the tokens `session_id`, `resumption_token` and `LAST_EVENT_ID`
