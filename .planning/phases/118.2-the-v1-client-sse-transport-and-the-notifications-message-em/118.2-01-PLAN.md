- A module doc stating the reliability doctrine and naming WHY: EPHEMERAL PORT (`127.0.0.1:0`, address
  read back from the bind), READINESS (bind before returning, never a fixed sleep as a synchronisation
  device), SHUTDOWN (sockets dropped, then `abort()`, then `await`), and EVERY await that crosses the
  wire wrapped in `tokio::time::timeout`. Record the measured reason: RESEARCH measured that
  `start_sse(None)` against a never-ending `text/event-stream` **does not return within 3 seconds** and
  a subsequent `receive()` also does not — so against the unfixed tree an unbounded await HANGS rather
  than fails, and a hung test reads as a slow test in CI rather than a red one, which would silently
  defeat the RED-first requirement.

Bounds as named constants, each carrying a one-line reason (never bare numbers):
- `BOUND: Duration = Duration::from_secs(5)` — upper bound on any single operation crossing the wire.
- `QUIET: Duration = Duration::from_millis(600)` — how long a listener is watched to prove NOTHING arrives.
- `BACKPRESSURE_FRAME_BYTES: usize = 8 * 1024` — per-frame payload size for fence 6, chosen so that
  `BACKPRESSURE_FRAME_COUNT` frames exceed any plausible kernel socket buffer (typically ≤ 256 KiB) and
  the SERVER-side write therefore genuinely blocks once the client stops reading. A frame small enough
  to fit in the socket buffer makes the fence vacuous — the kernel absorbs the whole push and nothing
  proves the reader ever hit a full queue.
- `BACKPRESSURE_FRAME_COUNT: usize = 128` — comfortably more than the receive-queue capacity task 2
  mints, so the queue is provably saturated.

Three rules that make the taxonomy hold:
1. **FIFO is the ordering guarantee.** The terminal `Err` is queued BEHIND every message already
   delivered, so a consumer sees all successfully parsed frames before the failure. That is why the
   error rides the channel rather than a side slot.
2. **At most ONE terminal error per reader.** Latch it: after a successful terminal send the reader
   returns immediately. A reader that could emit repeatedly would turn one corrupt frame into an error
   storm.
3. **A failed send means the receiver is gone.** `sender.send(..).await` returning `Err` means the last
   `StreamableHttpTransport` clone was dropped; the reader MUST return rather than retry. This is the
   task's termination signal and it is what makes "dropping the transport terminates the reader" true
   without a `Drop` impl (a `Drop` impl is impossible here: the transport is `Clone` and shares its
   abort handle, so one clone's drop would kill the original's stream).

*Rejected alternative, recorded so it is not re-derived:* a shared terminal-error slot
(`Arc<RwLock<Option<Error>>>`) consulted by `receive()`. It cannot work as a drop-in, because the
transport itself holds a `Sender` clone for its whole life, so `recv()` never returns `None` and
`receive()` would have to poll the slot on a timer — replacing a precise FIFO signal with a race.
