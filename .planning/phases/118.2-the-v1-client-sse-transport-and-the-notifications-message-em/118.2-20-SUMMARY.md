# Phase 118.2 Plan 20: Bound the Id-Mismatch Discard Summary

A mis-addressed response frame now costs the awaiting call a bounded, named, id-naming failure and costs
every other operation on that `Client` at most one 250 ms receive slice — and the comment that booked the
cost as "bounded by that request's own timeout" is gone, because that timeout does not exist.

## The Fix (Task 2)

**A. Half A, the lock.** `receive_bounded` replaces
`let m = self.transport.write().await.receive().await?;`. Once a mismatch has been observed it takes the
guard in an *inner scope*, awaits `receive()` under `tokio::time::timeout(slice, ..)`, and returns `Ok(None)`
when the slice expires — so the guard is dropped on the way out and the caller loops. `Ok(None)` means "no
message yet, the lock is released, ask again"; it is never an end of stream (a finished transport still
reports `Err`, as before).

**B. Half B, the wait.** `MISMATCH_DISCARD_TIMEOUT` (10 s) is armed on the **first** mismatch only, and
`MAX_ID_MISMATCH_DISCARDS` (32) caps the discards with a `TransportError::InvalidMessage` naming the count and
both ids in their typed `Debug` form. Both failures `return Err` from **inside** the inner future, so the
single WR-04 exit cleanup still reaps the pending `active_requests` entry — no second cleanup site was added.

**C. The ordinary path is unchanged.** With no deadline armed there is no ceiling, no `tokio::time::timeout`
and no cancellation. That non-change is load-bearing and is asserted by a comment at the branch and by
`a_fresh_budget_has_no_deadline_and_no_error`.

**D. The comment of record.** The third numbered point no longer says the cost is "bounded by that request's
own timeout". It names the two private constants that actually bound it, states plainly that
`RequestOptions::timeout` is a **public** field **not read** by `dispatch_request` so a caller who sets it gets
no protection from it, and records why plumbing it in was rejected.

`MismatchBudget::slice_until` is the ONE place the slice arithmetic happens — pure, total, and `None` is the
only expressible non-positive slice, so no negative or wrapped `Duration` is constructible by any caller.

## Adversarial Self-Check

Five cases reasoned about explicitly before committing. Two produced findings.

**1. Budget leaking across calls — clean.** `MismatchBudget::default()` is declared inside the inner async
block, immediately before the `loop`. One budget per `dispatch_request`; no sharing, no `self` field.

**2. A mismatch storm starving the ordinary path — clean, and capped.** Slices are re-acquired at most four
times a second, and tokio's `RwLock` is fair (FIFO semaphore), so a waiter queued while the guard was held gets
it before the discard loop re-takes it. Fence 23 passing at 6.985 s is the measurement. A waiter arriving in
the microseconds between release and re-request waits one extra slice — bounded, not starved.
`MAX_ID_MISMATCH_DISCARDS` bounds the storm itself.

**3. Cancel-safety of a trait-generic `receive()` — the plan's mitigation VERIFIED, and it is stronger than
the plan claimed.** The plan defends `T-118.2-20-05` as "confined to the post-mismatch path", which reduces
scope without making cancellation *safe* there. I checked the actual implementations rather than accepting the
argument:

- `StdioTransport::read_line` is **explicitly cancel-safe by construction** — it appends into a persistent,
  transport-owned `partial` buffer via `read_until` precisely so "a dropped future retains already-consumed
  bytes", and holds both guards across the read. The hazard I went looking for (a cancelled `read_line`
  losing a partial line and desyncing the stream) **does not exist** in this tree.
- `StreamableHttpTransport::receive` bottoms out in `mpsc::Receiver::recv()` under a `biased` select, which
  tokio documents as cancel-safe.
- `WebSocketTransport::receive` is `rx.recv().await` — likewise.

So all three real in-tree client transports are safe to slice. The residual is confined to **third-party**
`Transport` implementations, and only after a mismatch has been observed.

**4. Interaction with plan 19's terminal latch and `open_post_readers` gate — clean.** Slicing drops and
re-creates the `receive()` future every 250 ms, which re-subscribes to `terminal_signal` and therefore marks
the current generation as already-seen — a bump that landed while we were away is *not* delivered as a wake.
It does not matter: `receive()` calls `drain_or_latch` **immediately on entry, before the select**, so queue
and latch state are re-read directly on every re-entry. The generation is an optimisation for a parked
consumer, not the source of truth. No lost wakeup is introduced. The `receiver` mutex is also released each
slice, which is strictly more available than before.

**5. FINDING — the ceiling covers the rest of the call, not just "the discard".** Worth stating plainly
because the plan's own wording ("how LONG that discard is allowed to run") under-states it. Once armed, the
deadline stays armed for the life of that `dispatch_request`. So a peer that emits **one** stray frame at
t=0 and then answers **correctly** at t=15 s previously succeeded and now fails at 10 s. This is the mechanism
the plan specified — arming on the first mismatch is what makes the ceiling un-extendable (see decision 2), and
the alternative re-arming design is strictly worse — but it is a slightly wider behaviour change than
"wedged → bounded", and a downstream consumer with a slow-and-slightly-lenient peer can observe it. Flagged
for plan 118.2-21's `WINDOWS.md` disclosure rather than left to be discovered. Per-id response routing removes
discards entirely and therefore removes this too.

### [Rule 3 — Blocking] The plan's `grep == 0` criterion contradicts its own ordinary-path mandate

- **Found during:** Task 2.
- **Issue:** Task 2 requires `grep -c 'self.transport.write().await.receive()' src/client/mod.rs` to return 0,
  **and** requires the no-mismatch path to "behave EXACTLY as today: acquire the transport write lock, await
  `receive()` with no ceiling". Written the obvious way that path *is* literally
  `self.transport.write().await.receive().await`, so the two cannot both hold.
- **Fix:** the ordinary path binds the guard to a **named local** (`let mut transport = …; transport.receive().await`)
  instead of leaving it a temporary in a method chain. Semantically identical — either way the guard lives
  until `receive_bounded` returns — and it is the better spelling on the merits: the entirety of BLOCKER 2 was
  a temporary's lifetime being invisible at the call site.
- **Recorded honestly rather than banked:** `grep == 0` now passes, but **a reader must not conclude from that
  grep alone that no guard is ever held across a `receive()`**. One still is, on the ordinary path, by design
  and by the plan's own prohibition. The comment at that branch says so in as many words.

### ALWAYS requirements (CLAUDE.md), discharged explicitly

- **Unit** — the `mismatch_budget` submodule: 5 named tests covering the fresh budget, arm-on-first-discard-only
  (with real time advanced between discards, so a re-arming implementation could not coincidentally produce the
  same `Instant`), the cap firing at the limit and not one below, the cap error naming the count and both typed
  ids, and the slice at remaining-greater / remaining-less / remaining-exactly-zero / remaining-negative. 5/5 pass.
- **Property** — a new arm was needed and was added:
  `property_the_slice_never_exceeds_the_remaining_budget` generates remainders from 1 ms to 60 s and asserts the
  slice is never longer than the remainder, never longer than `MISMATCH_RECEIVE_SLICE`, and never zero. The
  ceiling is `Instant` arithmetic, and arithmetic that under-flowed would produce either a panic or an immediate
  spin, so the relationship between remainder and slice is the invariant worth generating over rather than any
  fixed pair. Placed in `mismatch_budget` beside what it constrains, not `#[ignore]`d.
- **Fuzz** — reasoned decision: **no new fuzz seam.** The existing `streamable_sse_frames` target fuzzes the SSE
  **parser**; this change is in the client's **correlation loop**, which consumes already-parsed
  `TransportMessage` values and never sees bytes, so that target does not and cannot cover it. The input space
  this change actually adds is a pair of `Instant`s and a discard counter — a numeric domain, generated
  exhaustively enough by the property arm above. Inventing a second fuzz target over a `Duration` pair would be
  ceremony, not coverage.
- **Example** — reasoned decision: **no new example.** This plan adds no public API — every symbol is private,
  `git diff … pub (fn|struct|enum|const|mod)` returns 0, and no variant was added to `Error` or `TransportError`
  — so there is no new surface for an example to demonstrate. The changed behaviour is exercised end to end by
  fences 23 and 24 against a real `pmcp::Client` over a real socket.
