# Phase 118.2 Plan 14: Bound the SSE reconnect loop on both sides (CR-01) Summary

**CR-01 is closed.** A peer answering every session-stream GET with `retry: 0` plus one SSE frame
now receives exactly `1 + MAX_SSE_RECONNECT_ATTEMPTS` = 3 GETs, spaced at no less than 500 ms, then
the named budget-exhaustion error — proven by a fence that was RED at **65 GETs in 7.9 seconds**
against the tree that shipped the defect.

## What CR-01 actually was, measured

CR-01 was a **remote-triggerable denial of service against pmcp's own client**, confirmed twice —
by the phase code review and independently by the verifier reading the merged source. Two
separately-reasonable decisions combined into it:

1. `next_reconnect_delay` clamped a peer-supplied `retry:` only from ABOVE. `SseEvent::retry` is
   `Option<u64>` milliseconds parsed straight off the wire, so `retry: 0` yielded `Duration::ZERO`.
2. `run_session_stream` refunded the ENTIRE attempt budget on any single delivered event
   (`if delivered { attempt = 0; }`).

Either alone is survivable. Together they are unbounded: a hostile server — or a broken proxy
replaying a cached page — writes one frame, closes the body, and the client refunds its whole budget
and immediately reconnects with zero delay, forever. Cost per iteration: 100% of a core locally, an
outbound HTTP request the peer never had to ask for, and a **fresh
`auth_provider.get_access_token()` call** — a third-party amplification target against the client
operator's own token endpoint (T-118.2-14-02).

### The RED measurement (`target/118.2-14-red.log`)

```
FAIL [   7.903s] pmcp::client_sse_stream
      reconnect_with_one_delivered_frame_and_zero_retry_stays_bounded
Summary [  12.846s] 15 tests run: 14 passed (1 leaky), 1 failed, 0 skipped
```

The assertion message recorded the observed wire traffic verbatim: **1 POST followed by 65
`GET / HTTP/1.1` lines**, against an expected 3, in a 7.9-second window bounded only by
`ZERO_RETRY_BOUND`. That number is the measurement of CR-01 and cannot be retaken now that the bug
is fixed. The 65 is a floor on the real-world rate, not a ceiling: it is what one loopback test
process achieved inside its own 8-second cap.

### Why no existing fence caught it

Measured, not assumed. The one fence exercising the retry-budget path —
`reconnect_gives_up_after_the_retry_budget_with_a_named_error` — uses `close_get_streams_on_accept()`,
a stream that delivers **nothing**, so `delivered` is always `false` and the refund arm is never
taken. Fence 15 is the arm's first coverage, which is why the fence is part of the fix rather than
an extra.

The bound reads:

```rust
// `.max().min()` rather than `Duration`'s `clamp`: clamp PANICS when
// `min > max`, and both operands here are constants a later edit could
// invert. The non-panicking spelling degrades an inverted pair to a
// value instead of to a panic inside a client's reader task.

    .max(MIN_SSE_RECONNECT_DELAY)
    .min(MAX_SSE_RECONNECT_DELAY);
```

### `tests/client_sse_stream.rs`

`reconnect_with_one_delivered_frame_and_zero_retry_stays_bounded` (fence 15) asserts four things
independently, so a partial fix cannot pass it:

- **COUNT** — the GET total settles at exactly `1 + SHIPPED_RECONNECT_BUDGET` and stays there
  through an observation window. Fails against the unfixed tree (65 observed).
- **FLOOR** — `instants[expected_gets - 1].duration_since(instants[0]) >= SHIPPED_MIN_RECONNECT_DELAY * budget`,
  measured SERVER-side at accept time. A **lower bound only**: CI load can only make it larger.
  Against a tree with the uptime gate but no floor, COUNT passes and this one fails.
- **TERMINAL** — the exhaustion error still reaches `Transport::receive()` carrying
  `RECONNECT_PHRASE`, drained in a bounded loop over `receive()` collecting `Ok(..)` until the first
  `Err(..)` so the fence survives plan 15 moving terminal errors onto a latch.
- **EQUIVALENCE** (the CONF-09 `empty` probe) — a zero-delivery body and a one-event body settle at
  the SAME GET count, pinned by the same `1 + SHIPPED_RECONNECT_BUDGET` expression in both fences
  rather than by duplicating fence 12.

Supporting harness: `deliver_one_frame_then_close_each_get(retry_ms)`, `get_instants()`,
`serve_get_that_delivers_one_frame_then_ends`, and the constants `SHIPPED_MIN_RECONNECT_DELAY`
(`:190`), `ZERO_RETRY_BOUND` (8 s), `ZERO_RETRY_QUIET` (1.5 s). The harness records **no new request
header** — the module's rule that a harness change must not be able to leak an `Authorization`
header into a CI log is intact.

## On the ALWAYS-fuzz requirement

CLAUDE.md asks every new feature for fuzz coverage. **No new fuzz target was added, deliberately.**
`next_reconnect_delay` is a pure two-argument function over `(u32, Option<Duration>)` with no
parsing, no allocation and no state; the two proptest arms cover its entire input space and assert
both the range invariant and purity. A `libfuzzer` target over the same two arguments would be a
slower proptest with a worse shrinker and no additional reach.

The reader path that DOES take untrusted bytes is already covered by `decode_sse_chunks_for_fuzz`
and `fuzz/fuzz_targets/streamable_sse_frames.rs` (shipped by 118.2-04). That existing target was
re-run at **20,000 runs, exit 0, no artifact under `fuzz/artifacts/streamable_sse_frames/`**, to
confirm this plan's edits leave the reader undisturbed. It was not re-run in the final session:
`fuzz/target` had been deleted to reclaim disk during the ENOSPC incident, and re-running would
rebuild several GB to re-confirm a result already recorded.

## Deviations from Plan

### 1. [Rule 1 — Bug] Four raw `Duration` subtractions in the new boundary tests tripped `clippy::unchecked_time_subtraction`

- **Found during:** Task 3, first `make quality-gate` run.
- **Issue:** `mod reconnect_delay_bounds` expressed "one millisecond either side of the bound" as
  `MIN_SSE_RECONNECT_DELAY - STEP`, `MAX_SSE_RECONNECT_DELAY - STEP` (twice) and
  `RECONNECT_BUDGET_RESET_UPTIME - Duration::from_millis(1)`. `Duration`'s `Sub` panics on
  underflow, and the gate's pedantic set rejects it.
- **Fix:** all four rewritten as `.saturating_sub(..)`. This is the same reasoning that chose
  `.max().min()` over `Duration::clamp` in the production code: the operands are constants a later
  edit could drive under `STEP`, and a panic is the worse degradation.
- **Files modified:** `src/shared/streamable_http.rs` (4 lines).
- **Commit:** `e1900ba2`.

### 2. [Rule 3 — Blocking, external] The volume filled mid-Task-3; the run resumed in a second executor session

- **Found during:** Task 3, first `make quality-gate` run.
- **Issue:** the root volume reached 0 bytes free during `cargo test --lib`. Every subsequent Bash
  call failed with ENOSPC. The gate died on ENOSPC, **not** on a check failure.
- **Fix:** the user freed space (138 GiB available on resume). `fuzz/target` had been deleted to
  reclaim space; the evidence logs under `target/` were preserved and verified intact before the
  resume. `make quality-gate` was re-run from the top and passed all 13 steps.
- **Not a code defect.** Recorded because it explains the two-session duration and why the fuzz
  target was not re-run in session 2.

### 3. [Rule 1 — Bug in the plan's own verify block] The `pmat` jq path in this plan's `<verify>` is wrong for pmat 3.15.0, and plans 15 and 17 carry the same line

- **Found during:** Task 3.
- **Issue:** the plan (and CLAUDE.md) specify
  `pmat analyze complexity --format json --max-cognitive 25 | jq -e '[.violations[] | select(.path | startswith("src/"))] | length == 0'`.
  On pmat **3.15.0** — the version CLAUDE.md pins for CI — the top-level keys are
  `["files", "summary", "top_files_limit"]`. There is no top-level `.violations`, and violation
  records key the path as `.file` with a `./` prefix, not `.path`. The command **errors**
  (`jq: error: Cannot iterate over null`, exit 5) rather than silently passing, so it fails closed —
  but it never measures anything.
- **Correct spelling, used here:**
  ```bash
  pmat analyze complexity --format json --max-cognitive 25 \
    | jq -e '[.summary.violations[] | select(.file | test("^\\./src/"))] | length == 0'
  ```
- **Second, worse shape found while investigating — a genuine false green.**
  `pmat analyze complexity --files src/shared/streamable_http.rs --max-cognitive 25` exits 0 and
  reports `total_files: 1, total_functions: 0` — it locates the file, parses **zero** functions from
  it, and reports zero violations. A per-file scoping of this command measures nothing while looking
  green. Only the repo-wide invocation is trustworthy.
- **Belt and braces:** the authoritative CI command `pmat quality-gate --fail-on-violation --checks complexity`
  was also run directly. `Quality Gate: PASSED, Total violations: 0`.
- **Not fixed in the sibling plans.** `118.2-15-PLAN.md:391` and `118.2-17-PLAN.md:341` carry the
  identical broken line. Editing another plan's verify block mid-execution is out of this plan's
  scope; their executors should substitute the corrected spelling above. Logged to `WINDOWS.md`.
