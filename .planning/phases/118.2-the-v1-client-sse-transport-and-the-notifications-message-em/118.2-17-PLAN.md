<objective>
Close **WR-01** (a reader parked on an idle-but-open stream never observes shutdown — task and socket
leak) and **WR-02** (the resumption cursor is shared across streams, so a reconnect can resume from
another stream's event id).

Purpose, WR-01: the phase's stated termination contract is a failing `sender.send(..)` plus a
`sender.is_closed()` check around the backoff sleep. Neither fires while the reader is parked in
`state.body.frame().await`. A server holding the session stream open with SSE keep-alive comments —
the standard idle keepalive — produces no events, so the reader never attempts a send and never
reaches the sleep. Dropping the transport does not help: `abort_handle` holds a `JoinHandle`, and
dropping a `JoinHandle` in tokio DETACHES rather than aborts, and there is no `Drop` impl on the
transport. A dropped transport therefore leaves a live task holding a live TCP connection until the
SERVER times it out. `close()` compounds it — it aborts only the GET handle, so every detached POST
reader (`drop(self.spawn_sse_reader(..))`) survives `close()` outright, and there is no bound on how
many exist. In a process that creates and drops transports repeatedly — a pool, a CLI loop, a test
suite — tasks and file descriptors accumulate.

The review also names why no existing fence catches it: fence 10 deliberately pushes a frame "purely
so the reader HAS a next send to fail". That crutch is the measurement gap, and removing it is part
of the fix.

Purpose, WR-02: `last_event_id` is one `Arc<RwLock<Option<String>>>` on the transport.
`deliver_sse_event` writes it from ANY stream, and the reconnect reads it back as the
`Last-Event-ID` header for the GET re-open. Since this phase, streaming POST responses are read
incrementally and therefore also write to it — concurrently, one writer per in-flight streaming POST.
MCP resumability is per-stream: a cursor minted on a POST response stream and replayed on the session
GET asks the server to resume from a position belonging to a different stream, which is a rejection,
a replay of the wrong frames, or a silent gap — and a silent gap is exactly the failure the reconnect
exists to prevent. The sharing pre-dates this phase; automatically CONSUMING it as a reconnect cursor
is what 118.2 added.

Output: a shutdown signal raced against the body read at both SSE sites, a per-reader cursor, three
new fences, and fence 10 rewritten without its crutch.

**Locked decisions this plan preserves rather than revisits.** D-03 (bounded auto-reconnect with
`Last-Event-ID`, routed through a paired accessor with a constant `full-v2` answer so that a SECOND
call-site `#[cfg]` does not accumulate) is the decision WR-02's fix sits directly on: the cursor
becomes per-reader, and `reconnect_cursor` keeps both its name and its paired shape precisely so
D-03's constraint still holds. D-01 (both `text/event-stream` sites read incrementally) is what
makes the shutdown race apply to the POST site as well as the GET one. D-04 (a bounded receive queue
whose reader awaits capacity and never drops a frame) is why the shutdown `select!` is `biased` with
the body arm first — a shutdown that discarded an already-available frame would drop exactly what
D-04 exists to protect. D-15's three fences are extended, never weakened, and 118.1's D-04 (each
fence demonstrated RED against the unfixed tree before its fix lands) governs task 1.
</objective>

**Plan 15 already created the delivery bundle** — one private struct grouping the `mpsc::Sender`, the
terminal latch and the terminal wake signal, threaded through `read_sse_body`,
`drain_pending_events`, `deliver_sse_event`, `SseReaderContext` and `spawn_sse_reader`. Its rustdoc
says this plan extends it rather than adding parameters. Add the shutdown handle there.

**Two watch channels, two different shapes, both deliberate.** Plan 15's `terminal_signal` is a
`watch::Sender<u64>` generation counter, because a consumer only ever needs a wake EDGE. This plan's
shutdown handle is a `watch::Sender<bool>` LEVEL, because a reader that subscribes AFTER `close()`
was called must still see that the transport is closed — `changed()` alone would never fire for it,
whereas `*receiver.borrow()` answers immediately. State that distinction in a comment at the second
field so a reviewer does not read it as inconsistency. Use `send_replace(true)` (or
`send_modify`) rather than `send`, which errors when no receiver exists.

**`tokio::sync::watch` needs no manifest change** — the root `Cargo.toml:191` already enables tokio's
`sync` feature. `tokio_util::sync::CancellationToken`, which the review suggests as an alternative,
would require adding a feature to the existing `tokio-util = { version = "0.7", features = ["rt"] }`
entry, i.e. a manifest edit this closure has no budget for.

**Borrow constraint in the select.** `read_next_sse_frame(&mut state)` (`src/shared/streamable_http.rs:2335`
onward) polls `state.body.frame()`, which borrows `state` mutably. The shutdown `watch::Receiver`
therefore must NOT live inside `SseReadState` — `changed()` also takes `&mut self`, and two mutable
borrows of `state` cannot coexist in one `tokio::select!`. Pass it as its own `&mut watch::Receiver<bool>`
parameter, owned as a local by `read_sse_body` via `delivery.shutdown.subscribe()`.

**Cancel-safety of the arms.** `mpsc::Sender::closed()` and `watch::Receiver::changed()` are both
cancel-safe. `hyper::body::Incoming::frame()` is only ever cancelled when a shutdown arm wins, at
which point the reader is terminating and the body is about to be dropped, so its cancel-safety is
not relied upon. Use `biased;` with the body arm FIRST, so a frame already available is always
consumed before a shutdown that arrived in the same wakeup — otherwise a burst-then-close server
loses its last frames.

**The three existing termination signals stay.** The failing `sender.send(..)`, the two
`sender.is_closed()` checks around the backoff sleep, and `close()`'s abort of the GET `JoinHandle`
are all still correct and must remain. This plan ADDS a fourth path for the case none of them covers.

**The reader's shutdown exit must be silent.** An intentional `close()` or a dropped transport is not
a corruption and not a lifecycle failure the application asked about; it must not latch a terminal
reason. Return the existing "ended, nothing further to send" variant, not a `Dropped` that the
reconnect loop would retry.

**WR-02's exact write and read sites:** `deliver_sse_event` writes the id (reached from
`drain_pending_events`, `:2327`); `SseReaderContext::reconnect_cursor` (`:2674-2696`) reads it back;
`sse_reader_context` (`:1260-1273`) and `spawn_sse_reader` (`:1299-1303`) both hand the same `Arc` to
their reader.

**The paired-accessor shape `reconnect_cursor` must keep.** Today it is a method with two `#[cfg]`
twins: the `v1-compat` one clones the shared field, the `full-v2` one is a `const fn` returning the
constant `None` whose rustdoc says "Do NOT 'improve' this by reading `last_event_id`". Turn it into a
paired FREE function taking `Option<&str>` — `Option<&str>` rather than `&Option<String>` because
clippy's pedantic `ref_option` fires on the latter — with the `v1-compat` twin returning an owned
copy and the `full-v2` twin ignoring its argument and returning `None`. Carry the existing rustdoc
warning across verbatim in spirit: the point of answering here is that the reconnect CALL SITE stays
free of a `#[cfg]`, and `tests/v1_severability_tripwire.rs` asserts both halves of that.

**Why a LOCAL, not a struct field.** Putting the per-reader cursor on `SseReaderContext` gives a
`full-v2` build a field that is written and never read, which is a `field is never read` warning
under `RUSTFLAGS="-D warnings"`. A local passed by `&mut` is used on every build.

**The tripwire's anti-vacuity floors.** `tests/v1_severability_tripwire.rs` enforces
`MIN_CLIENT_V1_OCCURRENCES = 20` and `MIN_CLIENT_STRIPPED_BYTES = 20_000` alongside the token scan,
and `the_last_event_id_const_and_its_reader_are_co_gated`. This plan only adds; confirm the binary is
still green rather than assuming it.

**The test harness** (`tests/client_sse_stream.rs`): `serve_get` holds a chunked
`text/event-stream` open forever and writes only frames a test pushes, so an idle-but-open GET needs
NO new harness mode — simply never push. `answer_post_with_sse(method)` (`:319`) plus
`push_post_frame` (`:337`) and `open_post_connections()` (`:332`) are the POST-side equivalents used
by existing fences 8-10; reuse whatever method string those fences already register.
`end_live_sse_streams()` (`:361`) closes EVERY live SSE body, GET and POST alike, via one `watch`
generation — that is the mechanism fence 20 uses to trigger the reconnect. `get_cursors()` (`:368`)
returns the `Last-Event-ID` each observed GET carried, `None` for a GET that carried none.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| remote MCP server -> pmcp client reader lifetime | a server that simply holds a stream open and sends nothing decides, today, how long a dropped client's task and socket survive |
| streaming POST response -> the session stream's resumption position | a cursor minted on one stream is currently consumed as the resume point of another |
| a host process -> its own file descriptors and task table | transports created and dropped in a loop accumulate live readers with no `Drop` impl and no bound |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-118.2-17-01 | Denial of Service | `read_next_sse_frame` parked in `body.frame()` | high | mitigate | A peer that keeps a stream open and idle controls how long a dropped transport's task and TCP connection survive — unbounded in a pool or CLI loop, and remotely chosen. | T-118.2-17-02 | Denial of Service | detached POST readers surviving `close()` | high | mitigate | `close()` aborts one `JoinHandle`; every reader spawned per streaming POST is detached and survives it, with no bound on how many exist. | T-118.2-17-03 | Tampering | cross-stream resumption cursor | medium | mitigate | A cursor minted on a POST response stream, replayed as `Last-Event-ID` on the session GET, asks the server to resume from a position belonging to a different stream — a rejection, a replay of the wrong frames, or a SILENT GAP. The silent gap is the worst of the three because it is exactly the failure the reconnect exists to prevent, and it is indistinguishable from a healthy resume. Closed by making the reconnect cursor per-reader; fenced by `a_post_stream_cursor_never_becomes_the_session_streams_last_event_id`. |
