# Phase 118.2 Plan 04: bounded reconnect, the fuzz seam, and the semver verdict

A pmcp client's session stream now survives a proxy blink. When the stream is DROPPED it is
re-opened carrying `Last-Event-ID`, under a two-attempt budget on the reference client's own
backoff curve; when that budget is spent the client says so, at `Transport::receive()`, in
words no consumer can confuse with corruption. When its owner calls `close()` — or simply
drops the last transport clone — the loop stops mid-backoff and issues nothing further. A
`full-v2` build cannot construct a cursor at all, and the file still has exactly ONE
`#[cfg]` at a call site.

## `SseReaderContext` — the field list, verbatim

```rust
struct SseReaderContext {
    client: Client<
        hyper_rustls::HttpsConnector<hyper_util::client::legacy::connect::HttpConnector>,
        Full<Bytes>,
    >,
    config: Arc<RwLock<StreamableHttpTransportConfig>>,
    protocol_version: Arc<RwLock<Option<String>>>,
    v2_mode: Arc<AtomicBool>,
    sender: mpsc::Sender<Result<TransportMessage>>,
    last_event_id: Arc<RwLock<Option<String>>>,
    on_resumption: Option<Arc<dyn Fn(String) + Send + Sync>>,
    max_collected_body_bytes: usize,
}
```

**There is no `abort_handle` field.** Measured, not asserted: `grep -n abort_handle
src/shared/streamable_http.rs` returns the transport's own field (`:677`), its initialiser
(`:770`), the two `start_sse`/`close` sites, the detached-POST comment, and five prose
mentions — none of them inside this struct. The reason is written at the struct:
`abort_handle` holds THIS TASK's own join handle, so a task owning that `Arc` owns its own
handle and dropping the last real transport clone would never release it. Fence 14 is what
would catch a regression.

`protocol_version` and `v2_mode` are both present because the shared request builder
genuinely reads both: `protocol_version` for the `MCP-Protocol-Version` header, `v2_mode`
for session-header suppression and the v2 routing headers. `protocol_version` is also
WRITTEN by the shared response-header processor on each re-open, so a reconnect keeps
tracking a version the server re-states.

## Where the shared-builder extraction landed

Three new members, no forked builder:

| Name | What it is |
|---|---|
| `struct RequestParts<'a>` | a BORROWED view of `config` / `protocol_version` / `v2_mode`, plus an `is_v2()` |
| `StreamableHttpTransport::build_request_from_parts` | the ONE request builder; `build_request_with_middleware(&self, ..)` is now a one-line wrapper over it |
| `StreamableHttpTransport::process_headers_from` | the ONE response-header processor; `process_response_headers(&self, ..)` is likewise a wrapper |

`capture_session_header`'s `#[cfg]` pair moved from `&self` to `&RequestParts<'_>` in the
same edit (gating either half alone is a compile break). Every pre-existing caller of
`build_request_with_middleware` and `process_response_headers` is unchanged — that is what
the wrappers are for.

A FOURTH member, `StreamableHttpTransport::build_sse_get_request`, is the one place the GET
that opens a session stream is constructed. `start_sse` reaches it through
`SseReaderContext::open_sse_once`, and so does every reconnect. T-118.2-04-07 — a reconnect
that silently drops its credentials — is closed structurally rather than by review: there is
no second builder to diverge.

Borrowed rather than owned, deliberately, so neither caller clones an `Arc` merely to build a
request.

## The shipped backoff constants

| Constant | Value | Source |
|---|---|---|
| `INITIAL_SSE_RECONNECT_DELAY` | `Duration::from_secs(1)` | reference `initialReconnectionDelay: 1000` |
| `MAX_SSE_RECONNECT_DELAY` | `Duration::from_secs(30)` | reference `maxReconnectionDelay: 30000` |
| `SSE_RECONNECT_GROWTH` | `1.5` | reference `reconnectionDelayGrowFactor: 1.5` |
| `MAX_SSE_RECONNECT_ATTEMPTS` | `2` | reference `maxRetries: 2` |

All four private, none on `StreamableHttpTransportConfig`, and **no `with_*` override was
added** — no caller in this repo needs one, and the plan said to expose one only if one did.
The durations are spelled in SECONDS rather than the reference's literal milliseconds because
`clippy::duration_suboptimal_units` requires it; the values are identical.

`next_reconnect_delay(attempt, server_retry)` computes
`min(INITIAL * GROWTH^attempt, MAX)`, and a server-provided SSE `retry:` WINS — as the
reference client's `_getNextReconnectionDelay` lets it. **Unlike the reference it is then
CLAMPED to `MAX_SSE_RECONNECT_DELAY`** (deviation 3 below). The function is non-panicking for
any `attempt`: an exponent that overflows `i32`, or an infinite product, falls back to the
maximum rather than unwrapping a `Duration` conversion.

## The call-site `#[cfg]` count is still 1, and it is now MECHANICAL

Before this plan the "only one `#[cfg]` at a call site in this file" rule was a comment
asking to be respected. It is now a test.
`tests/v1_severability_tripwire.rs::a_full_v2_build_names_no_resumption_cursor_on_reconnect`
counts `#[cfg(feature = "v1-compat")]` attributes governing a STATEMENT — a governed line
ending in `;`, excluding `use` / `const` / `static` / `type` / `mod` / `extern` items — and
asserts the count is **1** and that the one found contains `apply_resumption_header`. The
second assertion is the anti-vacuity guard: a classifier that matched nothing would fail it.

The classification is narrow on purpose. There are four OTHER `v1-compat` attributes inside
function bodies in the file, all struct-EXPRESSION fields in
`StreamableHttpTransportConfigBuilder::new` and `::build` (`session_id: None,`,
`on_resumption_token: None,` and their `build()` twins). A field ends with `,`; a statement
ends with `;`.

The one call-site gate MOVED, from `start_sse`'s body into `build_sse_get_request`'s. That is
what let `start_sse`'s own cursor parameter become an ordinary, ungated `cursor:
Option<String>` — it is now passed straight through by value on both feature sets, and the
gated-parameter pattern (`#[cfg] resumption_token` / `#[cfg(not)] _ignored_cursor`) survives
in exactly one function, the one that terminates it.

Tracked-token counts are unchanged over the whole edit — `session_id` 43, `resumption_token`
20, `LAST_EVENT_ID` 2, comment-excluding — so `MIN_CLIENT_V1_OCCURRENCES = 20` has the same
margin it had, and `the_client_transport_carries_no_ungated_session_state` still passes.

## The three terminal error texts, side by side

The whole point is that a consumer can tell a LIFECYCLE end from CORRUPTION.

| D | Family | Text |
|---|---|---|
| D-02 | `InvalidMessage` | *"a session-stream chunk pushed the buffered stream state past the {N}-byte parser bound; the buffered bytes were discarded and the stream was ended"* |
| D-05 | `InvalidMessage` | *"a session-stream frame did not parse as a JSON-RPC message ({cause}); the stream was ended. Frame: {<=200 chars}…"* |
| D-03 | `Request` | *"the session stream was dropped and its 2-attempt reconnect budget (MAX\_SSE\_RECONNECT\_ATTEMPTS) is exhausted after 2 attempt(s); {because}"* |

Two more D-03 ends, both `Request` and both deliberately NOT a re-handshake:

- 405 on reconnect — *"…reconnect attempt {n} was answered 405 Method Not Allowed: the server
  no longer offers a GET session stream, so there is nothing left to resume"*
- a failed re-open — *"…reconnect attempt {n} could not re-open it ({cause}); the stream was
  ended. The client deliberately does NOT re-handshake: a silent re-`initialize` would mint a
  new session and orphan every in-flight correlation"*

Distinctness is fenced in BOTH directions, because it is a property of the SET: fence 12
asserts the exhaustion text contains `"reconnect budget"` and contains neither
`"parser bound"` nor `"did not parse as a JSON-RPC message"`; fences 5 and 7 assert their own
texts do NOT contain `"reconnect budget"`. A one-directional check would pass against an
implementation that put the phrase in all three.

No new `TransportError` variant was minted — no semver event.

## What is retried, and what is not

`read_next_sse_frame` now returns `Option<SseFrameStop>` rather than `Option<Error>`, with
two variants that are not interchangeable:

- `SseFrameStop::Dropped` — a transport failure mid-body. Retryable on the session stream;
  delivered as-is on the POST stream, exactly as plan 01's taxonomy prescribes.
- `SseFrameStop::Corrupt` — a D-02 overflow. NEVER retried: re-opening would replay the same
  corruption against a peer that is already unwell (T-118.2-04-02).

`read_sse_body` returns `SseBodyEnd::{Dropped { cause, delivered, retry }, Ended}`. A D-05
parse failure and a gone `Receiver` both land in `Ended` — neither is a drop to chase.
`delivered` is what lets a stream that survived and then blinked earn a FRESH budget rather
than inheriting a spent one.

The POST site keeps plan 01's behaviour byte for byte: an ordinary end-of-body is silent, a
transport failure is delivered once as `TransportError::Request`. Only the GET site
reconnects — a POST response stream that ends is the call's ANSWER arriving.

### Fences 13 and 14 wait for the FIRST reconnect before cancelling

Written the obvious way — cancel during the first backoff — both would have PASSED against a
transport with no reconnect at all, because "no further GET arrives" is trivially true of a
client that never retries. They instead wait until `get_lines() >= 2`, which a
non-reconnecting tree never reaches, and assert `observed < 1 + SHIPPED_RECONNECT_BUDGET`
before cancelling so a fence that arrived after the budget was already spent fails loudly
rather than measuring nothing. That is why the RED run shows four failures and not two.

### Where the `full-v2` no-cursor assertion landed, and why

In `tests/v1_severability_tripwire.rs`, as
`a_full_v2_build_names_no_resumption_cursor_on_reconnect` — the plan's route (2), chosen
rather than skipped. `tests/client_sse_stream.rs`'s `#![cfg]` header REQUIRES `v1-compat`, so
a fence written there could not compile on the build whose behaviour it claims to measure.
The tripwire file sees the same bytes under `--features full` and `--features full-v2`, and
already owns every other severance-by-construction check. It asserts both halves of the
pattern: that `reconnect_cursor` is a `#[cfg]` PAIR with one half inside a `v1-compat` region
and one outside, and that the call-site gate count is still 1.

### No test-only backoff knob was added

The plan authorised one if the shipped backoff made fence 12 slower than `BOUND`. It does
not: 1.0 s + 1.5 s = 2.5 s of deliberate sleeping, which the fences wait out under a
`RECONNECT_BOUND` of 20 s and a `RECONNECT_QUIET` of 4 s. A knob would have had to be `pub`
to be reachable from `tests/` (a separate crate), putting a test-shaped affordance into
pmcp's public API and into its semver verdict. The fences measure the SHIPPED curve. Total
cost: the four reconnect fences run in 9–15 s.

## The fuzz seam, verbatim

```rust
#[cfg(any(feature = "fuzzing", test))]
#[doc(hidden)]
#[must_use]
#[allow(clippy::type_complexity)]
pub fn decode_sse_chunks_for_fuzz(
    chunks: &[&[u8]],
    max_buffer_size: usize,
) -> (
    Vec<std::result::Result<TransportMessage, String>>,
    Vec<bool>,
    Vec<usize>,
    Vec<usize>,
)
```

Its body is the PRODUCTION sequence — `SseParser::with_max_buffer_size`, then per chunk
`extend_from_slice` → `take_utf8_prefix` → `drain_sse_events` → the same
`StdioTransport::parse_message` call `deliver_sse_event` makes — and it reports the
PRODUCTION observers `sse_stream_overflow(&parser).is_some()` and `parser.buffered_bytes()`,
not reconstructions of them. Errors are flattened to `Display` strings so no private type
escapes and the seam has no lifetime entanglement, mirroring the analog.

**Four vectors, one more than `decode_listen_chunks_for_fuzz` returns** (deviation 4). The
fourth is `undecoded_tail_bytes`: this reader has a SECOND unbounded-growth candidate — the
byte buffer feeding the incremental UTF-8 decoder — and a target cannot assert a bound it
cannot observe. A decoder that stopped draining on some invalid sequence would grow that
buffer without limit while `buffered_bytes()` stayed perfectly flat.

The `#[allow(clippy::type_complexity)]` is annotated at the site: factoring the return into a
`pub type` alias would have added a SECOND public item, and this plan's semver claim is that
it adds exactly one.

### The target, and the anti-vacuity lesson it carries forward

`fuzz/fuzz_targets/streamable_sse_frames.rs` (185 lines) calls
`pmcp::shared::streamable_http::decode_sse_chunks_for_fuzz` across the crate boundary — it
does not re-implement the sequence, and it constructs no `hyper::body::Incoming` (nothing
outside hyper can). Two bounds, `[64, 8]`, for the reason the sibling target MEASURED: at 64
alone a 20 000-run campaign covered the overflow branch zero times. Three invariants: never
panics; `buffered_bytes() <= max_buffer_size` AND `undecoded_tail <= 3` after EVERY chunk;
and never fabricates — an `Ok` outcome requires the input to have carried one of `method` /
`result` / `error`, the three members `parse_message` dispatches on, checked only when the
input contains no backslash (a `\u`-escape could spell one indirectly and would report a
spurious crash).

The header states the lesson explicitly: do NOT assert "the overflow latch never clears" and
call it a bound. That assertion cannot fail for any input at any bound, which is how 20 000
green runs of `subscription_listen_frames` coexisted with exactly the unbounded-growth defect
it existed to catch. It is kept here as a subordinate note, not as a numbered invariant.

### The PROPERTY arm

Three `property_`-prefixed proptest arms in `src/shared/streamable_http.rs`'s `#[cfg(test)]`
module, in a new `sse_reader_properties` submodule, all driving the SAME seam:

- `property_arbitrary_bytes_never_panic_or_grow_the_reader`
- `property_chunked_arbitrary_bytes_never_panic_or_grow_the_reader`
- `property_a_valid_frame_survives_any_chunk_split` — a valid frame containing a multi-byte
  character, split at EVERY byte offset 1..80, asserting exactly one message decodes `Ok`.
  This is the arm that catches a reader that lost or duplicated an event across a chunk
  boundary; the other two only bound memory.

They are deliberately **not** `#[ignore]`d, so `make test-property`'s `-- --ignored property_`
selector does not pick them up. That mirrors the in-repo precedent they are modelled on
(`src/client/subscriptions.rs`'s `proptest!` block, likewise always-run) and is strictly more
coverage: they run in every `cargo test` and every `cargo nextest run` — they are part of the
3153 below — rather than only when someone remembers the property target. `make
test-property` itself still exits 0.

plan's instruction to "confirm it is reported as an addition and quote the line" rests on a
misconception about the tool. What CAN be confirmed, and is: the seam does not break
anything, on a default build it is not compiled at all (`fuzzing` is in neither `default` nor
`full`), and with `fuzzing` explicitly enabled the verdict is identical.

`start_sse`'s parameter was RENAMED (`resumption_token` → `cursor` on `v1-compat`). Parameter
names are not part of a Rust function's API contract and `cargo semver-checks` does not lint
them; the position and type are unchanged, so every caller compiles unchanged. Confirmed by
the verdict above and by the `full` and `full-v2` builds.

## Deviations from Plan

### 1. [Rule 2 — the plan's harness instruction would have broken the module's own rule]

- **Found during:** Task 1.
- **Issue:** the plan says to "record every request header of every GET". `tests/client_sse_stream.rs`
  states, at the field it would extend, that it records the request LINE only — "never a header, so
  a harness change cannot leak an `Authorization` header into a CI log". Recording the whole block
  would have made that comment false in the same edit that relied on it.
- **Fix:** an ALLOW-LIST of exactly one header NAME. `read_headers` looks at `content-length` and
  `last-event-id` and returns only their values; `Shared::get_cursors` holds
  `Vec<Option<String>>`, one slot per GET. Fence 11 asserts on the actual wire value —
  `cursors[0] == None` for the first open and `cursors[1] == Some("e7")` for the re-open — so the
  plan's requirement ("assert on the actual `Last-Event-ID` wire value rather than on a side
  effect") is met, and no credential can reach a log.
- **Files:** `tests/client_sse_stream.rs` · **Commit:** `0d59f88e`

### 2. [Rule 1 — a lost-wakeup race in the mechanism the plan implied]

- **Found during:** Task 1.
- **Issue:** the natural way to close a live SSE body on demand is `tokio::sync::Notify`.
  `notify_waiters()` wakes only the tasks ALREADY parked on it, so a close raised between two
  iterations of the harness's `select!` pump would be silently lost and the fence would hang to its
  bound rather than fail on its subject — the "a hung test reads as a slow test" failure the
  module's own header warns about.
- **Fix:** a `tokio::sync::watch` generation counter. Each connection `subscribe()`s before writing
  the head, so a close raised at any point after the connection was accepted is seen. The reason is
  written at the field.
- **Files:** `tests/client_sse_stream.rs` · **Commit:** `0d59f88e`

### 3. [Rule 2 — an uncapped peer-controlled sleep] the `retry:` clamp

- **Found during:** Task 2.
- **Issue:** the plan says a server-provided SSE `retry:` "WINS", and the reference client indeed
  applies it unclamped. `retry:` is remote input, so an unclamped one lets a peer park a client's
  reader task for a duration the peer chose — an availability lever handed to the peer for free.
- **Fix:** the value still WINS over the computed backoff, but is `.min(MAX_SSE_RECONNECT_DELAY)`.
  The divergence from the reference is stated in `MAX_SSE_RECONNECT_DELAY`'s and
  `next_reconnect_delay`'s rustdoc rather than left for a reader to discover.
- **Files:** `src/shared/streamable_http.rs` · **Commit:** `f6330b54`

### 4. [Rule 2 — a bound the target could not observe] the fourth return vector

- **Found during:** Task 3.
- **Issue:** the plan requires the target to assert that "the residual byte-buffer tail after
  `take_utf8_prefix` is at most 3 bytes", but the seam it also specifies — modelled on the analog's
  three-vector return — does not report that tail. The assertion would have been unwritable, or
  written against a reconstruction.
- **Fix:** `decode_sse_chunks_for_fuzz` returns FOUR vectors, the fourth being
  `undecoded_tail_bytes`. This is a real second unbounded-growth candidate: a decoder that stopped
  draining on an invalid sequence would grow it without limit while `buffered_bytes()` stayed flat.
  Both the fuzz target and the property arms assert it. The divergence from the analog is stated in
  the seam's `# Returns`.
- **Files:** `src/shared/streamable_http.rs`, `fuzz/fuzz_targets/streamable_sse_frames.rs` ·
  **Commit:** `be14c52e`

### 5. [Rule 3 — cog 29 against a cog-25 budget] `read_sse_body` was split

- **Found during:** Task 2, on the PMAT run.
- **Issue:** the shared body reader measured cognitive complexity **29**, over CLAUDE.md's 25.
- **Fix:** split along its natural seam into `drain_pending_events` (the per-EVENT rules) plus a
  `SseProgress` carrier; `read_sse_body` keeps the per-BODY rules. PMAT then reports 0 violations
  under `src/`. The harness's `serve` was likewise at 35 after task 1 and had its header-reading
  loop extracted into `read_headers`; both are now off the list.
- **Files:** `src/shared/streamable_http.rs`, `tests/client_sse_stream.rs` ·
  **Commits:** `f6330b54`, `be14c52e`

### 6. [Rule 3 — two lints, both mechanical]

- `clippy::duration_suboptimal_units` rejected `Duration::from_millis(1000)` and
  `from_millis(30_000)`; both are now `from_secs`, with the reference's millisecond spelling named
  in the rustdoc so the provenance survives.
- `clippy::type_complexity` fired on the seam's four-tuple return (the analog's three-tuple is
  under the threshold). An annotated `#[allow]` rather than a `pub type` alias, because an alias
  would have added a second public item and this plan's semver claim is that it adds exactly one.
- **Files:** `src/shared/streamable_http.rs` · **Commits:** `f6330b54`, `be14c52e`

### 7. [Recorded, no change] `open_sse_once` returns `Option`, not a bare body

- **Found during:** Task 2.
- **Issue:** the plan specifies `async fn open_sse_once(&self, cursor) -> Result<hyper::body::Incoming>`.
  `start_sse` has always tolerated `405 Method Not Allowed` by returning `Ok(())` without a stream,
  and a 405 has no body to return.
- **Resolution:** `Result<Option<hyper::body::Incoming>>`. `None` means 405, which the two callers
  treat DIFFERENTLY and correctly: the initial open returns `Ok(())` (the server simply does not
  offer a GET stream, an ordinary spec answer), while a RECONNECT ends the loop with a named error
  — a server that offered the stream a moment ago and now refuses it is not a stream that can be
  restored.

### 8. [Recorded, no change] the plan's RED expectation was "at least 3 failed"

The four fences as first drafted would have produced only TWO failures: fences 13 and 14 are
cancellation fences, and "no further GET arrives" is trivially true of a transport that never
reconnects. Rather than accept two vacuous fences, both were changed to wait for the FIRST
reconnect before cancelling — which a non-reconnecting tree never reaches. RED is therefore 4
failures, and neither fence can pass vacuously. Recorded because the fix is a property of the
fences, not of the count.
