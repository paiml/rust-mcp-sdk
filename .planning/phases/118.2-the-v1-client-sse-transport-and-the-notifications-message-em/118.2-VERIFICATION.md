## Bottom line

The prior verification (2026-08-18T04:30:00Z) failed truth 5 on three Criticals from
`118.2-REVIEW-closure-2.md`. Since then an **unplanned third gap-closure round** landed on this branch
— `e104dea6`, `d01b87e2`, `2d385d60`, `26447f94` — with no PLAN, no SUMMARY and no ledger entry. It
**deleted** the code both CR-01 and CR-02 were written against and replaced it with the per-id response
router that every earlier document names as the durable fix. Verdicts therefore had to be re-derived
from source, not re-checked against the old line numbers.

**Two of the three Criticals are genuinely gone, one is open-but-accepted, and one new defect of the
same class is present and unfenced.**

- **CR-01 — CLOSED.** Its mechanism no longer exists. There is no `receive_bounded`, no
  `tokio::time::timeout(slice, transport.receive())`, and no path in `src/client/mod.rs` that holds the
  transport write guard across an unbounded `receive()`. `pump_once` slices every receive at
  `PUMP_RECEIVE_SLICE` (250 ms) *inside* the guard, and the budget check runs in the caller's own loop
  between steps, so an armed caller can no longer be starved of its own deadline. Fence 26 passes.
- **CR-02 — HALF CLOSED, HALF SURVIVING AND NOW UNDISCLOSED.** The half that mattered most — one
  caller's answer being destroyed by another caller's pop — is fixed properly, by routing, and fenced
  (fence 25). The other half — the ceiling that re-arms itself across calls from the debris of the call
  it just killed — was **re-added under a new name** (`UNMATCHED_RESPONSE_TIMEOUT`,
  `MAX_UNMATCHED_RESPONSES`), and the source says so in its own rustdoc. `.planning/` contains zero
  mentions of either constant.
- **CR-03 — OPEN, ACCEPTED, DISCLOSED.** Unchanged in code. Deferred by explicit developer decision with
  a written rationale and a re-measured severity (`WINDOWS.md` entry 23), mirrored into the migration
  chapter, tripwire green. This is *not* the same thing as fixed and is not recorded as such here.
- **NEW — the CR-01 wedge moved to the SEND path.** `dispatch_request` holds the transport write guard
  across `post_once`, and the hyper client has no request timeout. A peer that accepts the POST and never
  answers wedges the whole `Client`, `close()` included, forever. Neither review nor prior verification
  saw this; no fence covers it; and the ledger's "waits at most one slice instead of indefinitely" is
  false for it.

**Separately, and judged separately as instructed: the documentation of record is no longer accurate
about the code.** `WINDOWS.md` entry 20 asserts a removal that did not happen; entries 13 and 20 and the
CONF-09 row locate their fixes by five symbols that no longer exist; the consumer-facing migration
chapter describes the pre-router client; and the third round is unrecorded everywhere. The disclosure
tripwire passes and cannot see any of it — it checks that marked ids are mirrored, not that mirrored
prose is still true.

written for the version that is fixed.

the CONF-09 row send a reader to five symbols that no longer exist, under a heading that says to locate
by symbol. The migration chapter — the one place a downstream consumer learns any of this — still
describes a client that discards mis-addressed frames in a loop. And the round that caused all of it has
no plan, no summary and no entry. The disclosure tripwire passes throughout, because it verifies that
marked ids are mirrored, not that mirrored prose is still true.
