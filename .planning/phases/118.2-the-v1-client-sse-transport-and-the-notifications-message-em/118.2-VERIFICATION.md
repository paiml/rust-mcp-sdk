# Phase 118.2: The v1 client SSE transport and the `notifications/message` emitter — Verification Report

**Phase Goal:** Close the two residuals Phase 118.1 measured and could not close within its own scope, so that the server-to-client channel 118.1 built is usable end to end by pmcp's OWN client, and a tool handler can emit MCP log notifications. Both were signed off as OPEN sub-items of G-3 at plan 118.1-13's D-10 gate (2026-08-11).

**Verified:** 2026-08-17
**Status:** gaps_found
**Re-verification:** No — initial verification

## Bottom line

**The four literal ROADMAP.md Success Criteria are achieved, and the evidence backing them is
real** — measured against the codebase directly, not just asserted by SUMMARYs, and independently
corroborated by the pinned official conformance suite (`GAP_ATTRIBUTABLE_FAILURES` 1 → 0,
`tools-call-with-logging` 0/2 → 2/0, the `2025-11-25` leg's exit status 1 → 0). CONF-09 and CONF-10
as literally worded are satisfied.

**But the phase's own prose goal — "usable end to end by pmcp's OWN client" — is not safely true.**
A code review completed just before this verification found two Critical defects in exactly the
client code this phase shipped, and I independently confirmed both by reading the merged source
directly (not by trusting the review's narrative):

1. A peer can drive pmcp's own client into an **unbounded, zero-delay reconnect loop** (`retry: 0`
   is clamped only from above; the retry budget resets on any single delivered frame). This is a
   remote-triggerable client-side DoS.
2. **Terminal stream errors are queued out-of-band and can silently pair one tool call's result with
   a different, unrelated call** — the receive loop returns on the first `Response` frame it pops
   with no id correlation. This is a data-correctness hazard, not merely a robustness nice-to-have.

Both are shipped in code from this phase (CR-01 entirely new in 118.2-04; CR-02's root cause
pre-exists but 118.2 is what supplies the out-of-band queue entries that make it reachable). Neither
is among the phase's own recorded WINDOWS.md open items — they were found by the reviewer and
confirmed here, not previously known-and-accepted. **The phase achieved its stated, narrowly-scoped
success criteria, but shipped the transport it built with two Critical correctness/safety defects
that undercut the phase's own "usable end to end" framing.** This is `gaps_found`, not `passed`.

### Known-and-accepted open items (correctly recorded, not silently closed)

Cross-checked against `.planning/WINDOWS.md` and the phase's `deferred-items.md` — these are
honestly recorded as OPEN, not swept under a `[x]`:

- **SEP-2575 v2 default** (WINDOWS.md #5): a v2 `tools/call` with no `_meta` logLevel still emits a
  log record because `DEFAULT_LOG_LEVEL` applies. Confirmed as OPEN, with the measurement ("pinned
  suite runs no `sep-2575-*` scenario") stated rather than glossed over.
- **Client lifecycle deadlock** (WINDOWS.md #6, #9; REQUIREMENTS.md CONF-09 row "STATED
  LIMITATIONS" (ii)): `Client::dispatch_request` awaits `transport.send(..)` before entering the
  receive loop while the server holds the POST open, so a pmcp client cannot ANSWER a
  server-to-client request issued during its own call. Correctly recorded as OPEN in both places,
  including a same-shape flake against the *reference* client (WINDOWS.md #9).
- **`LogMessageParams` `message`+`data` dual-emission** (WINDOWS.md #4/#8, both `fixed`):
  the earlier deviation (declared "not fixed" by 118.2-08) was subsequently REFUTED by measurement
  in 118.2-11 (suite regression 1/1→0/2) and then genuinely fixed in 118.2-13 (`data` now defaults
  to the message string, `cargo semver-checks` confirms no break). This is an honest, traceable
  correction-of-a-prior-claim, not a quietly dropped item — the record explicitly says the earlier
  premise was refuted.

None of these three known-open items are treated as new gaps by this verification; they are
correctly disclosed by the phase's own record-keeping. **CR-01 and CR-02 are a different category:

### Gaps Summary

The phase's four literal ROADMAP.md Success Criteria are met, extensively measured, and
corroborated by the official conformance suite — CONF-09 and CONF-10 are legitimately closeable as
worded. But this verification does not stop at the literal wording: the phase's own prose goal
promises the channel is "usable end to end by pmcp's OWN client," and two Critical defects in
exactly that client's code make that promise false in two concrete, reachable ways — an
attacker/misbehaving-server-triggerable unbounded reconnect loop, and a request/response
desynchronization that can hand one tool call's result to a different caller. Both were
independently confirmed by reading the merged source (not inferred from the review's prose alone).
Recommended next step: a small gap-closure plan applying the review's own suggested fixes (clamp
`retry:` from below and gate the budget reset on sustained uptime for CR-01; move terminal errors
off the response FIFO onto a sticky latch and add id correlation to `dispatch_request` for CR-02),
each backed by a new fence that exercises the specific arm the existing tests miss.
