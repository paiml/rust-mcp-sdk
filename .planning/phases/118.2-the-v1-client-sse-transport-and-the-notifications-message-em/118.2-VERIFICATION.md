# Phase 118.2: The v1 client SSE transport and the `notifications/message` emitter — Gap-Closure Verification Report

**Phase Goal:** Close the two residuals Phase 118.1 measured and could not close within its own scope, so that the server-to-client channel 118.1 built is usable end to end by pmcp's OWN client, and a tool handler can emit MCP log notifications.

**Verified:** 2026-08-17
**Status:** gaps_found
**Re-verification:** Yes — after gap-closure plans 14-18 (CR-01, CR-02, WR-01, WR-02, plus record-keeping)

## Bottom line

**This gap-closure round genuinely fixed one of the two Critical defects the prior verification found
(CR-01), and genuinely fixed both Warning-level defects it opportunistically took on (WR-01's body-read
race, WR-02's cursor sharing).** The reconnect-delay clamp is now two-sided, the attempt-budget refund is
uptime-gated, and the gap-closure's own code review — read and independently confirmed here, not merely
trusted — could not break CR-01's fix.

**But CR-02 is not closed. Its fix is present, and it is worse in one dimension than the defect it
replaced.** The prior verification's fifth truth — "the v1 client SSE transport this phase shipped is
safe to rely on end-to-end" — remains FAILED, for a NEW reason that only exists because of this
closure's own code:

1. **A sticky, unresettable, `Arc`-shared latch now pre-empts an in-flight, SSE-answered POST response.**
   Pre-closure, a bad terminal reason could poison at most one call. Post-closure, the same class of
   ordinary event (the session stream exhausting its two-attempt reconnect budget, a 405 on reconnect, a
   truncated streaming-POST response) trips the latch once and it never resets — every subsequent
   `tools/call` against an SSE-answering server on that `Client` fails permanently, for the life of the
   process, with a stale and unrelated diagnosis.
2. **The response-id correlation fix wedges the whole `Client` on a single mismatched frame.** The fix
   holds the transport write lock across an unbounded `receive().await` while discarding mismatched
   frames. The `deferred-items.md` entry that books this cost as "bounded by the caller's own timeout"
   is factually wrong — `pmcp::Client` has no request timeout anywhere in `dispatch_request`.

Both are shipped in code from this closure (plans 14/15/17), both were independently confirmed against
the merged source directly, and neither is disclosed in `WINDOWS.md` at the severity the review found —
entries 12/13 describe a "sticky receive()" and a "discard-on-mismatch" as accepted, bounded costs; the
review shows the first is unbounded in blast radius (permanent, not one-off) and the second is unbounded
in time (no timeout exists). **This is `gaps_found`, not `passed`.** The literal ROADMAP.md Success
Criteria (CONF-09, CONF-10 as worded) remain satisfied — that has not changed since the prior
verification — but the phase's own "usable end to end by pmcp's OWN client" framing is still not safely
true.

### Gaps Summary

**Genuine progress this round:** CR-01 (the unbounded zero-delay reconnect loop) is cleanly and
verifiably closed — the code review that found it could not break the fix, and this verification's own
spot-checks confirm the two-sided clamp and uptime-gated budget refund are in place. WR-02 (cross-stream
cursor confusion) is also cleanly closed. WR-01 is improved on its primary (body-read) axis with one
Warning-level residual on the queue-send axis.

**No genuine progress on the fifth truth.** CR-02 — the defect this phase's own goal text (`safe to rely
on end to end`) most directly names — is not closed. The gap-closure's fix trades the ORIGINAL
one-call-poisoning bug for two NEW Critical defects on the same code path:

1. A sticky latch that can answer a caller whose own SSE-delivered response is still in flight, with no
   way to ever clear it once tripped — turning a formerly transient failure into a permanent one for any
   server that answers POST with `text/event-stream`.
2. A response-correlation fix whose safety net (the caller's own request timeout) does not exist in
   `pmcp::Client` today, so the mismatch-discard loop can wedge the entire `Client` — not just the one
   mismatched call — for an unbounded amount of time while holding the transport write lock.

Both were independently confirmed against the merged source, not inferred from the closure's own
SUMMARY.md claims or from `118.2-REVIEW-closure.md`'s narrative alone. `deferred-items.md`'s
`T-118.2-15-03` entry, which books the second defect's cost as "bounded," rests on a premise this
verification found to be false.

**Recommended next step:** a second, narrower gap-closure plan that (a) scopes the terminal latch to the
stream that raised it, or converts it to a wake-only signal that never pre-empts a caller with an
in-flight answer, with a reset seam on successful reconnect; and (b) bounds the response-correlation
discard wait with a real timeout and stops holding the transport write lock across the await — plus a
fence that exercises fence 16's scenario against an SSE-answered POST, which is the exact shape the
current fences miss.
