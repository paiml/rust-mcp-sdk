# Phase 118.2: The v1 client SSE transport and the `notifications/message` emitter — SECOND Gap-Closure Verification Report

**Phase Goal:** Close the two residuals Phase 118.1 measured and could not close within its own scope, so that the server-to-client channel 118.1 built is usable end to end by pmcp's OWN client, and a tool handler can emit MCP log notifications.

**Verified:** 2026-08-18
**Status:** gaps_found

## Bottom line

**This round genuinely closed both Critical defects the prior verification found — and I re-derived that
conclusion from source, not from the summaries.** Plan 19's stream-scoped latch with an in-flight gate
and a reset seam closes BLOCKER 1's original trigger: a single caller whose SSE-answered POST response is
still in flight can no longer be pre-empted by a stale, unrelated, permanent reason, and a successful
`start_sse` re-open now actually clears the latch (`*self.terminal.write() = None;` at
`src/shared/streamable_http.rs:1728`). Plan 20's bounded discard closes BLOCKER 2's original trigger: a
solo caller who hits one mismatched-id frame now fails loudly at a named 10s ceiling instead of waiting
forever (`MISMATCH_DISCARD_TIMEOUT`, `MAX_ID_MISMATCH_DISCARDS`, confirmed by direct read of
`receive_bounded` and `MismatchBudget` in `src/client/mod.rs`). Plan 21's record corrections are also
genuinely true — `grep -c "bounded by that request"` returns 0, and the in-code comment at
`dispatch_request` now correctly states no `tokio::time::timeout` bounded the ordinary path and
`RequestOptions::timeout` is never read.

**But truth 5 is still FAILED, and for a third distinct reason.** This round's own code review
(`118.2-REVIEW-closure-2.md`) found that plans 19 and 20's fixes each introduce a new Critical defect on
the exact path they were meant to secure. I did not take that on trust: I read `receive_bounded`,
`MismatchBudget`, `drain_or_latch`, and the `open_post_readers` gate directly, and all three hold up as
real, reachable defects:

1. **CR-01** — the mismatch ceiling's `tokio::time::timeout` wraps only `transport.receive()`, not the
   lock acquisition ahead of it. Under two concurrent callers where one holds the lock on the
   deliberately-unbounded ordinary path, the OTHER, armed caller can block forever at
   `self.transport.write().await` — a statement the timeout never reaches. BLOCKER 2's underlying
   silent-wedge failure mode is still reachable; it now needs concurrency to trigger instead of a solo
   mismatch.
2. **CR-02** — `MismatchBudget` is correctly scoped per call, but the queue it reads from is shared and
   unfiltered, and a call's un-popped real answer is never drained on an `Err` exit. A peer whose honest
   latency ever exceeds 10s can turn ONE stray frame into a self-sustaining chain: call 1 times out at
   t=11 with its real answer un-drained, call 2 pops that leftover answer as its own first frame,
   mismatches, arms its own 10s ceiling, times out too, and so on — every later call fails, permanently.
   Round-1's code (no ceiling at all) would have succeeded, slowly, in this exact scenario; this round's
   fix turns a working-but-slow case into a permanent failure.
3. **CR-03** — the in-flight POST-reader gate (`open_post_readers`) is a transport-WIDE count answering a
   per-CALLER question. Under two concurrent POST readers, a caller whose own stream already latched its
   own correct diagnosis and exited can still be gated `None` forever by an unrelated reader belonging to
   a different call. This trades round 1's loud-but-wrong-and-immediate BLOCKER 1 for a silent, unbounded
   hang under concurrency — worse in kind.

None of the three is yet disclosed in `WINDOWS.md` or `REQUIREMENTS.md` — expected chronology, since the
review that found them scoped over the whole round's diff and necessarily ran after plan 21 (which owns
those documents) had already closed, not a new sin by plan 21 itself. But it means the documentation of
record currently overstates the transport's safety, and the next round must both fix the code and
disclose it. **This is `gaps_found`, not `passed`.** The literal ROADMAP.md Success Criteria (CONF-09,
CONF-10 as worded) remain satisfied — unchanged since the first gap-closure verification — but the
phase's own "usable end to end by pmcp's OWN client" framing is still not safely true.
