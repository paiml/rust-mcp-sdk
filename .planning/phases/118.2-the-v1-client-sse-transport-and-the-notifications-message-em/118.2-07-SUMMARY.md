# Phase 118.2 Plan 07: The Level Source, Both Eras, Both Ingress Paths — Summary

`LOG_LEVEL_REQUEST_META_KEY` has a production reader for the first time. v1's
`logging/setLevel` is captured at the HTTP ingress and stored PER SESSION; v2's
`io.modelcontextprotocol/logLevel` `_meta` key is read per request; `info` applies
when neither did; and the resolved answer is written onto the request's
`ProtocolContext` at **both** POST ingress paths, where plan 06's shared unit lifts
it onto the handler's `extra`.

## Where the Capture Landed

**The HTTP ingress, not the dispatch arm.**

The ingress is the ONE point that holds all four facts at once: the resolved era,
the already-validated session id, the raw body, and a `ProtocolContext` that is
still owned and mutable. Resolving there and writing the ANSWER onto the context
makes the emit-time read an `Option<LoggingLevel>` copy rather than a session-map
lock per record — and it leaves plan 08's dispatch arm with nothing to do but keep
answering the literal `{}` that Pitfall 8 pins.

`src/server/streamable_http_server/peer_channel.rs` is **byte-unchanged**
(`git diff --stat cb5d1365..HEAD -- …/peer_channel.rs` is empty). The rejected
carrier route was not taken: `attach_session_backchannel` returns early on
`!site.sessions_on || site.is_init_request`, and v2 has no sessions, so it
structurally cannot carry a v2 `_meta` level.

## The Resolution Helper, Verbatim

`src/server/streamable_http_server.rs:1677`:

```rust
fn resolve_request_log_level(
    state: &ServerState,
    era: Option<crate::types::protocol::Era>,
    sessions_on: bool,
    session_id: Option<&str>,
    raw_body: &[u8],
) -> Option<crate::types::LoggingLevel>
```

It parses the body ONCE and then, in order: runs the v1 capture
(`capture_v1_set_level`, `:1627`), returns the v2 `_meta` answer when the era is
`V2`, else returns the session's stored level when sessions are live, else `None`.

`sessions_on` is a PARAMETER rather than a re-read of `v1::sessions_active`, so
this layer consumes the decision the pipeline already made and never becomes a
second era resolver (Phase 112 D-11 / Phase 113 Pitfall 2).

### The precedence, verbatim from the rustdoc

> 1. **v2** — `params._meta["io.modelcontextprotocol/logLevel"]`, when the era is
>    `Era::V2`. Per request; v2 is session-free by construction, so nothing is
>    stored and nothing can leak into another request.
> 2. **v1** — the level this SESSION last set, when sessions are live for the
>    request and it carries a session id.
> 3. Otherwise **`None`**: leave `ProtocolContext::resolved_log_level` unset and
>    let `DEFAULT_LOG_LEVEL` (`info`, D-12) apply at emit time. `None` is not
>    "no logging" — it is "nothing overrode the default".

The two arms cannot both apply: arm 2's `sessions_on` is `false` on v2 by
`v1::sessions_active`, which is why this is a precedence list rather than a
conflict rule.

`V1State` is still a UNIT struct, the twin gained no `FORBIDDEN_STATE_TYPES` or
`FORBIDDEN_OPERATIONS` token, and
`the_v1_null_twin_declares_nothing_the_real_module_does_not` passes — 18/18 in the

**Why the SESSION and not the server (T-118.2-07-01).** `ServerState::server` is
one `Arc<tokio::sync::Mutex<Server>>` shared by every session; a level held there
would let client B's `setLevel` change client A's filtering. The per-session home
is also the correct LIFETIME: `setLevel` is retired on v2, so a `full-v2` build
allocates nothing for it.

**Why an unknown-id write is a NO-OP (T-118.2-07-02).** `get_mut`, never
`entry(..).or_insert(..)` — there is no insertion path in the function to reach,
so a caller cannot inflate the session map by guessing ids.

## The Malformed-Input Decision (CONTEXT.md left this to Claude's discretion)

**IGNORE-and-default, never reject.** A malformed level is:

* **not a panic** — `parse_peer_log_level` (`:1603`) deserializes through
  `LoggingLevel`'s OWN serde mapping and discards the error, so the parse can
  never disagree with the wire spelling either;
* **never echoed** — the peer's bytes reach no error message and no log line,
  following this crate's established `collected_body_over_cap` / `listen_overflow`
  rule (T-118.2-07-04, ASVS V7). Fenced by a sentinel chosen IN THE TEST
  (`NOT-A-LEVEL-2b7f1c`, a value that appears nowhere in `src/`, so the absence
  assertion cannot be satisfied by a source string the test never sent);
* **not fatal** — the request still serves and falls back to `info`.

**Rationale, stated at the parser:** the `_meta` key is an ADVISORY, per-request
diagnostic hint. Failing a whole tool call because a hint was misspelled converts
a logging preference into an availability failure (T-118.2-07-03, ASVS V5).

Nothing is gated on `ServerCapabilities.logging` (RESEARCH Open Question 6) — the
sink is per request and the capability is advisory; gating would make a
correctly-plumbed server silently mute.

## Which Form Fence 8 Took, and Why

**BEHAVIOURAL** — the plan's preferred form, not the structural fallback.

`handle_post_request` routes on `config.http_middleware.is_none()`, so an EMPTY
`ServerHttpMiddlewareChain` is enough to send every POST down the middleware
ingress path. No middleware behaviour is needed to prove the claim, only the
route, which makes the behavioural form cheap rather than disproportionate.
`the_level_is_honoured_behind_http_middleware_too` sets `debug` on that path and
asserts both records arrive.

Its discriminating power is measured, not assumed: RED #1 below removes the
middleware-path resolution and this fence — and only this fence — goes red.

"arrived or not" by the time the reply lands — no quiet window and no sleep. On v2
the whole multi-frame body is complete before any assertion runs.

## Known Divergences — Two Plan Predictions Falsified by Measurement

Both are recorded in `deferred-items.md`; the fences assert what is TRUE rather
than asserting the prediction away.

### 1. A malformed v1 `logging/setLevel` is rejected `400` / `-32601`, not answered `{}`

The plan states that a malformed `params.level` "stores-or-ignores and still
answers `{}`". The **v2 `_meta` half holds and is fenced**. The v1 RPC half does
not, for a PRE-EXISTING reason: a `level` that is not one of the eight
`LoggingLevel` spellings fails TYPED PARSING in `parse_transport_message_fast`, so
the message never becomes a `ClientRequest` and the transport answers `400` with
`-32601` long before this plan's capture runs. Making it answer `{}` means
changing the deserialization of the PUBLIC `ClientRequest::SetLoggingLevel`
variant, which is outside this plan's `files_modified` and carries its own semver
verdict.

**What this plan claims of that path DOES hold and is fenced:** no panic, the
peer's value is never echoed into the rejection, and nothing is stored (a later
tool call on the same session is still at the `info` default).

### 2. The middleware ingress path answers its reply INLINE

`build_response` (fast path) hands the reply to the session's SSE stream and
answers `202`; `build_success_response_with_middleware` always answers inline and
never consults the stream. This is a pre-existing divergence with nothing to do
with the log level — the RECORDS still reach the stream on both paths, because
they ride `attach_session_backchannel`'s shared session-keyed notification sink.
Fence 8 therefore awaits the POST (after which every record has already been
pushed) and then reads them off the stream, and says so at the fence.

### 3. `set_session_log_level`'s no-op is not wire-reachable today

`v1::validate_non_init_session` answers `404` before the capture runs, so a caller
cannot reach the write with an id the server never issued.
`a_set_level_for_an_unknown_session_id_inserts_no_session` therefore fences the
END-TO-END property rather than the no-op itself; the no-op remains as defence in
depth for a future call site that reaches the write without the validation, and a
mutation of it turns no fence red today. Recorded rather than dressed up.
