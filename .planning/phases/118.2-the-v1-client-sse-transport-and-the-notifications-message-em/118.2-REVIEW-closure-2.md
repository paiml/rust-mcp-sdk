# Phase 118.2, second gap-closure round: Code Review Report

## Summary

**The answer to the round's own framing question is yes, partially: this round repeats the
pattern.** Plan 19 closed BLOCKER 1's permanent-failure defect and opened a narrower permanent-hang
defect on the same path (CR-03). Plan 20 closed BLOCKER 2's *observable* shape — fence 23's probe
gets the lock, fence 24's call returns — but left the ceiling unenforced over the one wait that can
actually be indefinite (CR-01), and introduced a self-sustaining cross-call failure that is a
strictly worse regression than the disclosed single-call one (CR-02).

What is genuinely sound, and what I tried that failed to break it, is in "What I Could Not Break"
below. It is a real list, not a courtesy — the `PostReaderGuard` accounting, the 1→0 wake, and the
plan-19/plan-20 re-subscription interaction all survived deliberate attack.

The three Criticals share one root shape: **every new bound in this round is scoped to a single
call or a single await, while the state it guards is transport-wide and outlives the call.** The
mismatch budget is per-`dispatch_request` but the frames that arm it are per-transport. The
`open_post_readers` gate is per-transport but is used to answer a per-call question. The
`tokio::time::timeout` wraps `receive()` but not the lock that gates reaching it.

No structural-findings block was supplied; this report is narrative only.

## Critical Issues

### 🛑 CR-01: The discard ceiling does not cover the transport-lock acquisition, so BLOCKER 2's wedge is still reachable

**File:** `src/client/mod.rs:3846-3853` (the sliced branch), `:3831-3833` (the ordinary branch)

```rust
let received = {
    let mut transport = self.transport.write().await;   // <-- NOT inside the timeout
    tokio::time::timeout(slice, transport.receive()).await
};
```

**Issue.** `tokio::time::timeout` wraps `transport.receive()` only. `self.transport.write().await`
sits outside it. The ordinary branch at `:3831-3833` deliberately holds that same guard across an
*unbounded* `receive()` (disclosed, and correct on its own terms). Put those two facts together and
the ceiling can never fire: a caller that is armed cannot reach its own timeout while an unarmed
caller holds the lock, and the unarmed caller holds it for as long as the peer stays silent.
`Client` has no request timeout at all — `grep -c "tokio::time::timeout" src/client/mod.rs` returns
exactly the one occurrence added by this plan — so "as long as the peer stays silent" is unbounded.

**Concrete failure scenario.** `Arc<Client>` shared by two tasks, one transport, one `RwLock`:

1. Task A sends request id `1`; task B sends request id `2`. Both release the lock after `send`.
2. A reaches `receive_bounded` first with no deadline armed → takes the write guard → parks in an
   unbounded `receive()`.
3. B queues on `self.transport.write()`.
4. The server answers `2` (only). A pops it, `response.id != request_id` → `mismatch_budget.record()`
   arms the 10 s deadline → A releases the guard and loops.
5. B is ahead of A in the RwLock's FIFO queue, takes the guard, and parks in its own **unbounded**
   `receive()`. The server never sends `1`'s answer (it was A's request that failed server-side; or
   `2`'s answer was the last frame).
6. A is now blocked at `self.transport.write().await` — *before* the `timeout(slice, …)` it was
   supposed to be bounded by. A's deadline passes at t+10 s and nothing observes it.

Result: A hangs forever, B hangs forever, and `close()` — which also needs that write guard — hangs
forever. This is verbatim the wedge `118.2-20-SUMMARY.md` books as "BLOCKER 2 closed — the lock is
released", and `d0c5133f`'s commit message asserts as fact.

Fence 23 cannot see it: its probe is `cancel_request`, which takes the guard, does one `send`, and
returns. It measures that *a short* lock user gets a turn during a slice. It measures nothing about
a lock user who holds across an unbounded receive, which is precisely the other branch of the
function under test.

**Fix.** Put the lock acquisition inside the bound. `RwLock::write()` is cancel-safe (a dropped
acquire future simply leaves the queue), so nothing is lost:

```rust
let received = tokio::time::timeout(slice, async {
    let mut transport = self.transport.write().await;
    transport.receive().await
})
.await;
```

Add a fence with **two** concurrent `call_tool`s on one `Arc<Client>` where the server answers only
the second, and assert both calls return inside `MISMATCH_TIMEOUT_BOUND`.

### 🛑 CR-02: The armed ceiling is self-sustaining across calls — one stale frame permanently fails every later call on a peer slower than 10 s

**File:** `src/client/mod.rs:3924-3927` (`MismatchBudget::default()` per call), `:237` /
`MISMATCH_DISCARD_TIMEOUT`, `:3838-3843` (the ceiling), `:3990-3998` (the arming site)

**Issue.** The budget is correctly per-`dispatch_request`. The *frames that arm it* are not: an
answer that arrives after its own call has already returned stays on the shared transport queue and
is popped by the **next** call, which mismatches on it and arms its own 10 s ceiling on frame one.
Once the peer's genuine round trip exceeds `MISMATCH_DISCARD_TIMEOUT`, that call also times out
before its own answer lands, leaving *its* answer on the queue for the call after it. The failure
regenerates its own cause.

`118.2-20-SUMMARY.md` discloses the single-call version of this ("a peer that emits one stray frame
at t=0 and then answers correctly at t=15 s previously succeeded and now fails at 10 s"). It does
not disclose that the failure is self-sustaining, and it is that property — not the single failure
— that makes this the same class of defect as the round-1 latch: **one transient event becomes a
permanent, process-lifetime failure of a `Client`.**

**Concrete failure scenario.** A tool whose honest latency is 12 s (routine — the whole reason
Tasks exists), on any peer that ever emits one frame the client does not correlate. Two entirely
ordinary triggers for the initial stray frame: a lenient server that re-types `Number(1)` as
`String("1")` (the case the correlation comment at `:3948` names explicitly), or the *documented
workaround* for "`Client` has no request timeout" — a caller wrapping `call_tool` in
`tokio::time::timeout`, which abandons the call and leaves its answer to arrive later.

| t | event |
|---|---|
| 0 | call 1 sent |
| 1 | stray/late frame popped → mismatch → deadline armed at t=11 |
| 11 | **call 1 fails** `Error::Timeout(10000)` |
| 12 | call 1's real answer lands on the queue, unread |
| 13 | call 2 sent |
| 13 | call 2 pops call 1's answer → mismatch → deadline armed at t=23 |
| 23 | **call 2 fails** |
| 25 | call 2's real answer lands on the queue, unread |
| 26 | call 3 sent → … |

Every subsequent call on that `Client` fails, forever. Under the **round-1** code — the unbounded
discard that this plan replaced — call 2 discarded the stale frame and then received its own answer
at t=25 and **succeeded**. So this is a regression introduced by this round for the slow-peer case,
not merely a tightening.

**Fix.** Two independent mitigations, both cheap:

1. Do not let a stale frame arm the ceiling on its own. Arm on the first mismatch *and* require a
   minimum of e.g. 2 discards, or restart the deadline when a non-`Response` frame (progress
   notification) shows the call is alive; better, make the ceiling relative to *silence*, not to
   the first mismatch — `deadline = last_frame_seen + MISMATCH_DISCARD_TIMEOUT`, which a dripping
   peer still cannot extend because a drip **is** liveness for the transport.
2. Stop leaving the frames behind. On any `Err` exit from `dispatch_request`, drain and drop any
   already-queued frames addressed to `request_id`, or (the recorded correct shape) land per-id
   routing so a popped frame is delivered rather than discarded.

Add a fence: server latency 400 ms, `MISMATCH_DISCARD_TIMEOUT` overridden to 200 ms for the test,
one stray frame at the start, then assert **calls 2 and 3 succeed**.

### 🛑 CR-03: The in-flight gate is transport-global, so an unrelated live POST reader suppresses a caller's OWN latched terminal reason indefinitely

**File:** `src/shared/streamable_http.rs:1044-1047` (`drain_or_latch`'s gate), pinned as intended
by the unit test at `:5722` (`a_post_reader_in_flight_gates_a_reason_from_either_stream`)

```rust
if open_post_readers.load(Ordering::SeqCst) > 0 {
    return None;
}
```

**Issue.** `open_post_readers` is a transport-wide count and the latch is a single transport-wide
slot, but the question being answered is per-caller: "is *my* answer still on the wire?" The gate
suppresses **every** reason — including a `StreamKind::PostResponse` reason raised by the caller's
own, already-dead stream — for as long as **any** POST reader anywhere on the transport is live.
The unit test at `:5722` asserts this deliberately for both stream kinds, so it is designed-in
rather than accidental; the case that was not reasoned about is *two* concurrent readers.

**Concrete failure scenario.**

1. Call B's `tools/call` is answered `200 text/event-stream`; the server holds the body open (a slow
   tool, or a caller that abandoned B via its own `tokio::time::timeout` and left the reader
   running). `open_post_readers == 1`.
2. Call A's `tools/call` is answered `text/event-stream` too. `open_post_readers == 2`.
3. A's stream delivers a corrupt frame → `latch_terminal_reason` writes a `PostResponse` reason and
   bumps the wake → A's reader exits → `fetch_sub` returns `2`, so **no wake is raised** (only the
   1→0 transition wakes). `open_post_readers == 1`.
4. A's `dispatch_request` wakes on the latch bump, calls `drain_or_latch`: queue empty, count is 1
   → `None` → parks again.
5. B's stream stays open. A never learns that its own stream died. There is no request timeout in
   `Client`, so A hangs for the process lifetime.

Under the **round-1** code A received its own correct diagnosis immediately. Plan 19 traded a
common permanent-failure for a narrower permanent-hang on the same path — the exact trade
`T-118.2-19-03` and the `PostReaderGuard` rustdoc say must not be made ("trading BLOCKER 1's
permanent failure for a permanent unexplained HANG, which is not an improvement").

`118.2-19-SUMMARY.md` residual 5 names the ingredient ("a peer that holds a POST response body open
forever keeps the gate closed") but frames the cost as "the one input under peer control that
lengthens a wait". It is not a lengthened wait; with no timeout anywhere it is an unbounded hang,
and it applies to a caller whose failure is *already known and latched*. That is worse than
recorded, so it is in scope.

**Fix.** Do not let the transport-wide count answer a per-caller question. Smallest correct change:
gate only a `StreamKind::Session` reason, and surface a `PostResponse` reason immediately —
a POST stream that already ended is not "an answer on the wire":

```rust
let latched = terminal.read().as_ref().and_then(|reason| match reason.stream {
    StreamKind::PostResponse => Some(reason.to_error()),
    StreamKind::Session if open_post_readers.load(Ordering::SeqCst) == 0 =>
        Some(reason.to_error()),
    StreamKind::Session => None,
});
```

That still leaves WR-02 below (a `PostResponse` reason can belong to a different caller), so the
durable shape is a reason **per reader**, delivered to the caller that owns it — which is the same
per-id routing already recorded as the follow-up. Amend the `:5722` unit test, which currently pins
the defective behaviour, and add a two-concurrent-reader fence.

## Warnings

### ⚠️ WR-01: The reset seam clears a `PostResponse` reason too, and raises no wake — a concurrent `start_sse` can erase a diagnosis a parked consumer was about to read

**File:** `src/shared/streamable_http.rs:1728`

```rust
*self.terminal.write() = None;
```

**Issue.** The seam is justified entirely in terms of the session stream ("a confirmed live
re-open, and the ONE point at which a terminal reason stops being true"), but it is unconditional
over `TerminalReason::stream`. A `PostResponse` reason — which a successful GET re-open says nothing
about — is erased with it. And the clear raises no generation bump, so a consumer already parked
gets no re-poll.

**Concrete failure scenario.** An application with a supervision loop that re-opens the session
stream (fence 22's own supported pattern), racing a call whose POST stream just died:

1. Call A's POST reader latches a `PostResponse` reason (bump G+1) and exits (count 1→0, bump G+2).
2. A's `receive()` is woken but not yet scheduled.
3. The supervisor's `start_sse` completes its GET and executes `*self.terminal.write() = None`.
4. A runs `drain_or_latch`: queue empty, count 0, latch `None` → `None` → parks. No further wake
   source exists (the queue is empty, the session stream is healthy). A hangs.

**Fix.** Scope the clear the same way the latch is now scoped:

```rust
let mut slot = self.terminal.write();
if slot.as_ref().is_some_and(|r| r.stream == StreamKind::Session) {
    *slot = None;
}
```

The window between latch-write and consumer-read remains; closing it properly is the per-reader
reason in CR-03's fix.

### ⚠️ WR-02: `"this call's own POST response stream"` is asserted to callers that do not own the stream

**File:** `src/shared/streamable_http.rs:756-761` (`StreamKind::describe`), `:798`
(`to_error`'s `format!`)

**Issue.** The latch is still a single slot (`118.2-19-SUMMARY.md` residual 1 states this), so a
`PostResponse` reason raised by call A's stream can be the reason surfaced to call C. Before this
round the rendered text was unattributed and merely stale; now it makes a *positive, false* claim
of ownership — the precise failure mode BLOCKER 1 was about, restated with more confidence. An
operator reading "this call's own POST response stream ended: unparseable SSE frame `{`" for a call
whose stream was never opened investigates the wrong thing, which is the harm `T-118.2-19-02` cites
as the justification for the prefix in the first place.

**Concrete failure scenario.** Call A's SSE-answered POST hits a corrupt frame → latched. Call C is
answered `text/event-stream`; the server sends notifications and closes the body **without** a
result frame (legal — the reader treats a clean end as an end). C's guard drops, gate opens, C's
`receive()` surfaces A's latch and C is told its own stream ended, naming A's corrupt payload.

**Fix.** Until reasons are per-reader, render `PostResponse` neutrally — `"a POST response stream
ended"` — and reserve the possessive for the (future) case where ownership is actually known. Or
carry the owning `RequestId` in `TerminalReason` and only use the possessive when it matches.

### ⚠️ WR-03: The cancel-safety audit of record enumerates three transports; there are at least eight

**File:** `.planning/…/118.2-20-SUMMARY.md` ("all three real in-tree client transports are safe to
slice"), applied at `src/client/mod.rs:3846-3853`

**Issue.** The plan-20 self-check is explicitly framed as "I checked the actual implementations
rather than accepting the argument", and it checked `StdioTransport`, `StreamableHttpTransport`,
`WebSocketTransport`. `grep -l "impl Transport for" src/` returns eight more in-tree impls, of
which at least five are usable as `Client<T>`'s `T`: `HttpTransport` (`src/shared/http.rs:482`),
`SseOptimizedTransport` (`src/shared/sse_optimized.rs:569`), `PooledTransport`
(`src/shared/connection_pool.rs:627`), `WasmHttpTransport` (`src/shared/wasm_http.rs:274`),
`WasmWebSocketTransport` (`src/shared/wasm_websocket.rs:149`).

I read all five. The **conclusion holds** — four bottom out in `mpsc/Receiver::recv()` or
`StreamExt::next()`, and `WasmHttpTransport::receive` is `self.pending.take()` with no await at all
— so no in-tree transport loses a message under slicing. I also verified the `StdioTransport` claim
at `src/shared/stdio.rs:161-176`: `read_line` holds both guards and appends into the persistent
`partial` via `read_until`, so a dropped future genuinely retains consumed bytes. The claim is
right; the enumeration on record is wrong, and a summary that says "all three" is what a future
reader will trust when a ninth transport lands.

**Fix.** Correct the enumeration in `118.2-20-SUMMARY.md` (and mirror it in `deferred-items.md`),
listing the impls actually audited. Better, make it mechanical: a tripwire test that fails when
`grep -c "impl Transport for" src/` changes, pointing at the cancel-safety obligation.

### ⚠️ WR-04: Once armed, the ceiling bounds progress that has nothing to do with mismatches — including a human-in-the-loop elicitation

**File:** `src/client/mod.rs:3927` (the `receive_bounded` call sits above **all three** match arms),
`:4052-4064` (`TransportMessage::Request` — the server→client elicitation/sampling arm)

**Issue.** The known-open list discloses that "the mismatch ceiling arms on the first mismatch and
stays armed for the call's life, so a peer that emits a stray frame at t=0 then answers correctly at
t=15 s now fails at 10 s". That framing is about the *peer* being slow. The sharper instance is that
the ceiling also bounds work the **client and its user** are doing: the `TransportMessage::Request`
arm answers a server-initiated elicitation via `dispatch_host_request`, which for an
approval-gated or interactive host means waiting on a human. Ten seconds is not a human bound.

**Concrete failure scenario.** A `tools/call` on a lenient server that re-typed one id (one
discard, deadline armed at t+10). At t+3 the server sends `elicitation/create`. The host prompts a
user, who answers at t+40. The reply `send` succeeds, the loop continues — and the very next
`receive_bounded` returns `Error::Timeout(10000)`. The tool call fails and the user's answer is
already on the wire, so the server proceeds against a client that has given up.

**Fix.** Reset or extend the deadline on any frame that demonstrates the exchange is alive — a
`Notification`, or a `Request` the client answered. Both are liveness, and neither is a mismatch a
peer can spam to extend a wait it should not get (each one costs the peer a round trip and is
independently bounded).

### ⚠️ WR-05: The ceiling's error is undiagnosable — it names a fixed 10 000 ms, never the elapsed time, the discard count, or either id

**File:** `src/client/mod.rs:3838-3843`

```rust
return Err(Error::timeout(
    u64::try_from(MISMATCH_DISCARD_TIMEOUT.as_millis()).unwrap_or(u64::MAX),
));
```

**Issue.** The cap error at `:337-350` is exemplary — it names the count and both ids in typed
`Debug` form. The timeout error, which is the path that will actually fire in practice (the cap
needs 32 frames; the ceiling needs one), carries none of that. A caller sees `Timeout(10000)` on a
call that has been running for four minutes, with nothing linking it to a correlation failure. That
is exactly the "true but undiagnosable" outcome `MAX_ID_MISMATCH_DISCARDS`'s own rustdoc says the
cap exists to prevent — and the cap does not cover this path.

**Fix.** Fail with the same shape the cap uses:

```rust
return Err(Error::Transport(TransportError::InvalidMessage(format!(
    "waited {}ms past the first mis-addressed response frame for this request's own answer \
     (MISMATCH_DISCARD_TIMEOUT); discarded {} frame(s); awaiting {awaiting:?}",
    MISMATCH_DISCARD_TIMEOUT.as_millis(), budget.discards
))));
```

If the `Timeout` *kind* must be kept for fence 24's `matches!(error, pmcp::Error::Timeout(_))`, at
minimum log a `warn!` naming the awaited id and the discard count at the moment the ceiling fires.

## Info

### ℹ️ IN-01: `exhausted()`'s message says "consecutive" but the counter is never reset

**File:** `src/client/mod.rs:342-350`
**Issue:** `discards` accumulates for the life of the `dispatch_request` and is never reset;
`Notification` and `Request` frames are interleaved freely between discards. "discarded N
consecutive response frames" over-claims a contiguity the counter does not track.
**Fix:** drop "consecutive", or reset `discards` whenever a non-`Response` frame is handled.

### ℹ️ IN-02: The slice is computed before the lock is taken, so `MISMATCH_RECEIVE_SLICE`'s "at most one slice" is not literally true

**File:** `src/client/mod.rs:3835-3853`
**Issue:** `slice_until(deadline, now)` runs, then `self.transport.write().await` may block for an
arbitrary time, then the `slice` starts. One attempt can therefore overshoot the deadline by the
lock-wait, and the rustdoc's promise that another caller waits "at most one slice" holds only when
the lock is uncontended. Benign in itself (the next iteration's `slice_until` catches it) but it is
the same lock-wait blind spot CR-01 makes fatal.
**Fix:** subsumed by CR-01's fix — move the acquisition inside the timeout.

### ℹ️ IN-03: No unit arm observes `latch_terminal_reason`'s wake; only the guard's

**File:** `src/shared/streamable_http.rs:5390-5410` (`delivery_for`), `:5585` (the guard wake arm)
**Issue:** `delivery_for` drops both `watch::Receiver` halves deliberately, so the `latch_gate`
module measures the latch value but never that the *latch write* raises an observable generation
bump. `the_last_post_reader_out_wakes_a_parked_consumer` pins only the guard's half. Since CR-03's
scenario turns on precisely which of the two bumps fires, that asymmetry is worth closing.
**Fix:** keep a subscriber in `delivery_for` and assert the generation advances on the winning
latch write and does **not** advance on a losing one.

## What I Could Not Break

Recorded because the previous round's "this one I could not break" was load-bearing.

**`PostReaderGuard`'s accounting.** I went after leak, double-decrement, panic-mid-body,
`mem::forget`, and a spawn path with no guard. All held:

* `PostReaderGuard::acquire` has exactly one production call site
  (`streamable_http.rs:1880`), it is synchronous and precedes `tokio::spawn`, and the guard is moved
  into the future and bound to `let _in_flight = in_flight;` — a named binding, not `let _ =`, so
  it lives to the end of the task rather than dropping instantly. That distinction is one character
  wide and it is right.
* Every reader exit path drops it: clean end-of-body, mid-body transport failure, D-02/D-05
  corruption, the `SseFrameStop::Shutdown` race, a panic unwind, and a spawned future dropped before
  its first poll. There is no explicit decrement anywhere to get out of sync with, and no
  `mem::forget`/`ManuallyDrop` in the tree.
* Underflow needs a drop without a matching acquire; the type has no `Clone`, no public
  constructor, and one `acquire`.
* The `> 0` gate sits **after** the `Disconnected` arm, so a stuck reader cannot mask a genuinely
  gone `Receiver`. I checked that ordering specifically — reversing it would be a second hang.
* `spawn_sse_reader` is the only POST-reader spawn. `sse_reader_context`/`run_session_stream` is the
  session stream and correctly takes no guard; `subscriptions.rs:121`'s `post_streaming` body is a
  separate stream that never touches this queue or this latch.

**The 1→0 wake.** I tried to construct a lost wakeup four ways and could not:

* Park-between-check-and-notify: `receive()` calls `terminal_signal.subscribe()` **before** the
  receiver lock and before the first `drain_or_latch`, and the `watch::Receiver` persists across
  loop iterations, so a bump raised while the consumer is between the gate read and the `select!`
  is still an unseen generation when `changed()` is polled.
* Rapid 1→0→1 churn: the consumer wakes, re-reads a closed gate, re-parks — and the *new* reader's
  own eventual 1→0 raises another bump. No bump is consumed without the gate being re-read.
* Wake-while-holding-the-lock: the bump follows the `fetch_sub` and no lock is held at guard-drop
  time; `send_modify` (not `send`) is used, so a transport with no live receiver does not error.
* Spurious storms: only the 1→0 transition bumps, so N readers finishing produce exactly one wake.

**Plan 19 × plan 20 interaction on re-subscription.** `receive_bounded`'s slicing drops and
rebuilds the `receive()` future every 250 ms, and each rebuild `subscribe()`s afresh, marking the
current generation seen — so a bump landing between slices is *not* delivered as a wake. This is
harmless and the summary's reasoning is correct: `drain_or_latch` runs immediately on entry, before
the `select!`, so queue/latch/count are re-read directly on every re-entry. The generation is an
optimisation for a parked consumer, not the source of truth. I could not construct a case where a
sliced consumer misses a state change.

**Message-loss under slicing.** `StreamableHttpTransport::receive` can only be cancelled while
parked in the `select!`; `try_recv` returns synchronously and the `biased` queue arm returns before
any await point, so no already-popped message can be dropped by the outer timeout. I verified the
same property for the five transports plan 20's audit missed (WR-03).

**Fences 23 and 24.** Both are well built and neither is vacuous: fence 24 asserts the error
**kind** and a non-zero rendered bound (closing the WR-05 hole the first round found in fence 17),
and fence 23 has two independent vacuity guards including that the probe's
`notifications/cancelled` reached the wire. Fence 21 asserts call 1's *own* marker rather than mere
success. My criticisms of them are about what they do not reach (CR-01, CR-02, CR-03), not about
what they claim.
