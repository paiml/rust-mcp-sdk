# Phase 118.2 Plan 19: Scope the Terminal Latch to Its Stream Summary

`drain_or_latch` no longer answers a caller whose own SSE-delivered POST response is still on the wire, a
successful `start_sse` re-open clears the latch, and every terminal reason a caller sees names the stream that
raised it — closing BLOCKER 1, the permanent-failure defect the previous gap-closure round introduced.

Exactly the two new fences failed; all 20 pre-existing fences passed unchanged, so the `call_answer` split is
behaviour-preserving for every existing fence.

**Call 1's verbatim error text on the RED tree:**

> `Transport error: Request error: the session stream was dropped and its 2-attempt reconnect budget (MAX_SSE_RECONNECT_ATTEMPTS) is exhausted after 2 attempt(s); the peer ended the body`

It **does** contain `reconnect budget`. That string IS the pre-emption measurement: a `tools/call` that
succeeded on the wire came back reporting the GET session stream's reconnect failure, raised minutes earlier
on a different stream.

**Fence 22's measured `receive()` latency on the RED tree: 6.625 µs.** It *answered* rather than waited — the
latch was surfaced 6.6 microseconds after a *successful* session-stream re-open, proving the latch is never
cleared and the failure is permanent, not merely delayed.

Why fence 16 could not reach this: its harness answers `content-type: application/json`, so the response lands
on the receive queue synchronously inside `send()` and the queue-wins-over-latch rule always fires. Fence 21
answers the same call over `text/event-stream`, where `post_body` spawns a detached reader and returns `Ok(())`
before anything is delivered — the queue is legitimately, transiently empty while a real answer is on the wire.

## The Fix (Task 2)

**A. Stream identity.** `StreamKind` is stamped onto every `TerminalReason` and rendered by `to_error` as a
prefix (`the GET session stream ended: ...` / `this call's own POST response stream ended: ...`). The field is
load-bearing, not decorative — a field written and never read is a `dead_code` warning under `-D warnings`, and
the diagnosis is the point (T-118.2-19-02). Every existing message **body** is preserved verbatim, so the
`reconnect budget` substring `tests/client_sse_stream.rs` matches at four sites survives; pinned by
`to_error_names_the_stream_and_preserves_the_message_body`.

**B. The gate.** `open_post_readers: Arc<AtomicUsize>`, maintained *only* through the RAII `PostReaderGuard`.
`drain_or_latch` answers `None` — "keep waiting" — whenever the queue is empty AND the count is non-zero. The
`Disconnected` arm and the queue-wins-over-latch ordering are unchanged. The guard is acquired
**synchronously before `tokio::spawn`** (line 1848 precedes 1850); acquiring inside the task would let
`dispatch_request` reach `receive()` first and observe zero, which is the race itself.

**C. The reset seam.** `start_sse` writes `None` into `self.terminal` on the arm where `open_sse_once` yielded
a live body, before spawning the reader. Not on the `Ok(None)` 405 arm (nothing recovered — T-118.2-19-04),
not in `close()`, not in any constructor. There are exactly two production `terminal.write()` sites: the latch
write and this reset. `close()` contains zero references to `terminal`.

`Transport::receive`'s five-end-reason table gained the stream-naming note, its ordering rules gained a fourth,
and its STICKY section now states that sticky is not permanent.

## Deviations from Plan

### [Rule 2 - Missing critical functionality] The gate had a lost-wakeup hole; the last guard out now wakes

- **Found during:** Task 3, in the adversarial self-check the orchestrator required on this plan's own new
  concurrent state — specifically the case it named, `close()` racing an in-flight POST.
- **Issue:** A reader exiting **cleanly** latches nothing. Both `SseFrameStop::Shutdown` (the `close()` race)
  and an ordinary end-of-body return without calling `latch_terminal_reason`, so neither bumps the terminal
  wake generation. The plan's mechanism note ("the reader's exit bumps that wake when it latches") is true only
  on the latching path. A consumer that parked in `receive()` while the gate was CLOSED would therefore stay
  parked after the last reader was gone, with the latch surfaceable again and nobody to tell it — trading
  BLOCKER 1's permanent failure for a silent hang, which is exactly what T-118.2-19-03 exists to refuse.
- **Fix:** `PostReaderGuard` carries the wake sender and `send_modify`s the generation on the 1 → 0 transition
  only (`fetch_sub` returns the pre-decrement value). Earlier guards do not wake — while another reader is live
  the gate is still closed and a wake would only cause a spurious re-poll. The bump follows the decrement, and
  `receive()` subscribes before its first latch read, so a consumer parking between the two still observes an
  unseen generation: no new lost wakeup is introduced by the fix for the old one.
- **Files modified:** `src/shared/streamable_http.rs`
- **Commit:** `3f49bbad`
- **Pinned by:** `the_last_post_reader_out_wakes_a_parked_consumer`, which asserts both directions and that the
  count is zero at the moment the wake is raised.

### [Rule 1 - Plan verify command measures the wrong thing] `grep -c '^ *FAIL '` counts each failure twice

- **Found during:** Task 1.
- **Issue:** Task 1's verify block asserts `test "$(grep -c '^ *FAIL ' target/118.2-19-red.log)" -eq 2`. nextest
  prints every `FAIL` line **twice** — once inline as the test finishes, once in the final summary recap — so
  the raw count is 4 on a run with exactly 2 failing tests. Run as written the verify would have failed a
  correct RED capture.
- **Fix:** measured the count of **distinct failing test names** instead:
  `grep '^ *FAIL ' ... | awk '{print $NF}' | sort -u | wc -l` = **2**. The log's own
  `Summary [...] 22 tests run: 20 passed, 2 failed` states the same fact independently.
- **Not swept in:** no plan file was edited (prohibition), so this is recorded here for plan 21.

- **Fix:** verified the criterion's *intent* instead — production sites are exactly 2 (`:915` the latch write,
  `:1696` the reset seam) and `close()` contains zero references to `terminal`. The other 2 are the mandated

## Accepted Debt and Residuals — Named, Not Buried

1. **The latch is still a single slot, not a per-stream map.** A `PostResponse` reason from an earlier call can
   still be the one surviving reason a later caller sees, once the queue is empty and no reader is live. The
   reset seam bounds how long that can persist. Full removal is per-id response **routing**, already recorded
   in `deferred-items.md`. What would force a per-stream map: any change making two POST-response streams
   terminally distinguishable to a caller.
2. **WR-01's queue-send residual is NOT fixed here.** `deliver_sse_event`'s `sender.send(..).await` is a bare
   await not raced against shutdown, so a detached POST reader parked on a full 64-slot queue after `close()`
   still leaks a task and a socket. Transferred to plan 118.2-21 with its owner, per this plan's prohibitions
   (T-118.2-19-06).
3. **A peer can now cause more than one latched reason over a transport's life**, where before it could cause
   exactly one. Accepted (T-118.2-19-05): the reconnect budget and `MIN_SSE_RECONNECT_DELAY` bound how fast
   that cycle runs, and one diagnosis per genuine recovery cycle is the correct amount.
4. **Consumer-observable behaviour changes**, both strict improvements, both private-field changes with no
   semver event: (a) `receive()` no longer answers immediately with a latched reason while a streaming POST
   response is in flight — a consumer relying on the immediate stale answer now sees a wait; (b) the rendered
   text of every terminal reason gains a stream-name prefix. Plan 118.2-21 owns disclosing both in
   `WINDOWS.md`.
5. **A peer that holds a POST response body open forever keeps the gate closed for that transport.** This is
   D-01's existing shape, not new: `close()` and last-clone-drop both stop such a reader (fences 18 and 19 pass
   unchanged), and the reader's exit now wakes any parked consumer. Named here because it is the one input
   under peer control that lengthens a wait.
