# Phase 118.2 Plan 05: The `extra.log` Emitter Surface — Summary

`ServerNotification::LogMessage` gets its first production constructor: `extra.log(..)` and
`extra.log_with_data(..)` on `RequestHandlerExtra`, filtered by a `LoggingLevel` that now orders by
syslog severity rather than by string, with five fences pinning the no-sink contract, the wire shape,
the filter in both directions, and the downstream drop-newest loss policy.

## What Shipped

### The two methods, verbatim

```rust
pub fn log(&self, level: crate::types::LoggingLevel, message: impl Into<String>) -> Result<()>

pub fn log_with_data(
    &self,
    level: crate::types::LoggingLevel,
    message: impl Into<String>,
    data: serde_json::Value,
) -> Result<()>
```

Both are **synchronous**. `grep -c 'async fn log'` over non-comment lines of
`src/server/cancellation.rs` returns `0`; `grep -c 'pub fn log'` returns exactly `2`.

Both delegate to one private helper, `fn emit_log_record(&self, level, message: String, data:
Option<Value>)`, so the filter comparison exists in exactly one place — two copies of a filter is two
chances to get the direction wrong.

### The `Result<()>` disclaimer, verbatim from the rustdoc

> **`Ok(())` is NOT delivery acknowledgement**
>
> `Ok(())` means the record was handed to whatever sink this request has, or that there was none — it
> does NOT mean the client received it. The sink's type is `Fn(Notification) -> ()`: it returns unit
> and therefore *cannot* report failure, and the fallback `notification_tx` path in `Server` likewise
> ignores its own `try_send` result. Do not build retry logic on this `Result`. It exists so that a
> future "sink refused" signal is an additive change rather than a breaking one.

### `DEFAULT_LOG_LEVEL`

```rust
pub const DEFAULT_LOG_LEVEL: crate::types::LoggingLevel = crate::types::LoggingLevel::Info;
```

D-12, rustdoc'd with three reasons in weight order: it is conventional across MCP implementations;
`debug` and finer stay suppressed so a chatty handler cannot flood a client that never opted in; and
the conformance scenario emits at `info` or above, so an unconfigured server still passes it.

### `LoggingLevel` ordering

`PartialOrd, Ord` added to the derive list (`src/types/notifications.rs:233`). The declaration order
already *was* syslog severity order, so the derive yields the correct comparison for free. The added
rustdoc states why the derive is load-bearing and adds a do-not-reorder warning: the declaration order
IS the semantics, and a reorder would silently change every level filter in every downstream server.

## Observed Saturation Behaviour

The fence models `new_v2_progress_queue()`'s policy exactly: `mpsc::channel(4)` whose sink closure
`try_send`s and swallows the error. Feeding it `4 + 8 = 12` records produced:

- **(a)** all 12 `log(..)` calls returned `Ok(())`. The emitter never blocks and never reports
  downstream loss — which is precisely why the rustdoc must not claim acknowledgement.
- **(b)** the receiver held **exactly 4** records.
- **(c)** those 4 were `record-0 .. record-3` — the **FIRST** N, i.e. **drop-newest**, matching the
  vehicle rather than silently differing from it.

A fence that only checked the count could not have told drop-newest from drop-oldest, which is why (c)
is asserted as an ordered `Vec<String>` equality.

D-09's "no rate limit" is stated in the rustdoc as a property of the EMITTER, explicitly *not* as a
claim that no record can be dropped downstream. The rustdoc also records that the v2 vehicle attaches
only when the request is multi-frame eligible (v2 era AND not `enable_json_response` AND `Accept`
contains `text/event-stream`), so a v2 client that asked for JSON only receives no log records at all
— documented as correct behaviour for a client that declined the streaming channel.

`--ignored` filter plus a `property_` substring. An always-run exhaustive test is therefore invisible
to `validate-always` no matter how strong it is. So the file carries:

1. `log_levels_order_by_syslog_severity_not_by_string` — always-run, exhaustive over all 64 pairs.

`PROPTEST_CASES=1000 cargo test --features "full" --test log_emitter -- --ignored property_` reports
`1 passed, 1 filtered out`, and `make test-property` exits 0.

## Known Divergences

### `LogMessageParams` vs the vendored schema — `message` vs `data`

`schema/vendored/core-2026-07-28/schema.ts:2031` declares
`LoggingMessageNotificationParams` as `{ level, logger?, data }` — **`data` is REQUIRED and there is
no `message` member.** pmcp's `LogMessageParams` (`src/types/notifications.rs:161`) is the reverse: a
REQUIRED `message: String` and an OPTIONAL `data`, skipped when `None`.

So `extra.log(LoggingLevel::Warning, "hello")` emits
`{"method":"notifications/message","params":{"level":"warning","message":"hello"}}` — no `data` member
where the spec marks it required, plus a `message` member the spec does not define.

`a_log_record_serializes_as_the_spec_notifications_message_shape` asserts the shape pmcp emits TODAY
against literals, so this is a visible recorded fact and any future change to it is a deliberate,
reviewed edit rather than silent drift. **Owner: plan 08** — if the official conformance suite
validates `params.data`, the current shape fails it and the type change becomes in-scope work with its
own semver verdict.

`REQUIREMENTS.md:933` spans the whole arc: records reaching the client on **both** eras, the level

deliberately **not** run. CONF-10 closes when plan 08's conformance fence turns green.
