## Summary

The four claimed fixes are all really present, and three of them are correct in the narrow
sense they were scoped to:

* **CR-01** — `next_reconnect_delay` now bounds a peer `retry:` on both sides
  (`streamable_http.rs:3427-3437`), the refund is uptime-gated via `budget_reset_earned`
  (`:572-574`, `:3366`), and the boundary/property tests genuinely pin both ends. This one
  I could not break.
* **WR-02** — the reconnect cursor is a per-body local threaded through `read_sse_body`
  (`:3342`, `:2678`, `:3394`), the transport-wide `last_event_id` write is unchanged, and
  fence 20 actually arranges the only shape (GET + streaming POST live at once) that can
  distinguish them. Correct.
* **CR-02 / WR-01** — the mechanisms are present, but **both were fixed at one park point and
  one delivery point each, and the paths they did not cover are the same paths the fix was
  supposed to close.** Those are the two BLOCKERs below.

The two BLOCKERs are not re-reports of the booked deferrals. `T-118.2-15-03` books
*"the OTHER request waits out its caller's timeout"*; CR-02-A below is that the timeout it
names does not exist anywhere in `pmcp::Client`, and that the wait is taken while holding the
transport write lock. `T-118.2-15-03` says nothing about the latch pre-empting an
**in-flight** response, which is CR-02-B.

No structural-findings block was supplied, so this report is narrative only.

## Critical Issues

### CR-01: The sticky terminal latch pre-empts an SSE-delivered POST response, permanently failing every later tool call

**File:** `src/shared/streamable_http.rs:876-889` (`drain_or_latch`), `:2450-2484` (`receive`),
`:2252` (`post_body`'s SSE branch), `:1661-1681` (`spawn_sse_reader`), `:3373-3405`
(`run_session_stream`'s three latch sites)

**Issue:** `drain_or_latch` surfaces the latch the moment `try_recv()` reports *Empty*. On the
POST-answered-with-`text/event-stream` path — the path **this very phase introduced for D-01**
— `post_body` spawns a detached reader and returns `Ok(())` at `:2252`; the response is not on
the queue yet. `Client::dispatch_request` then calls `receive()`, the queue is legitimately
empty because the answer is still on the wire, and the latch wins. The call fails instantly
with a stale, unrelated diagnosis.

Reachability is ordinary, not adversarial. All of these latch and are all permanent:

* the GET session stream spending its (deliberately small, `MAX_SSE_RECONNECT_ATTEMPTS = 2`)
  reconnect budget — `:3373`;
* a `405` on reconnect — `:3399`;
* one earlier streaming POST response truncated mid-body — `:1679`.

None of those says anything about whether POST request/response works. A proxy that kills the
session stream three times in ~1.5 s is the routine event D-03 exists to survive; after it, an
SSE-answering server's every `tools/call` on that `Client` returns
`"reconnect budget exhausted…"` for the life of the process. There is **no way to clear the
latch**: it is `Arc`-shared across every `#[derive(Clone)]` clone, written once, and no
constructor, `start_sse`, or `close` resets it.

Fence 16 does not reach this. Its harness answers calls with
`content-type: application/json` (`tests/client_sse_stream.rs:754`), so `queue_from_caller`
puts the response on the queue *synchronously inside `send()`* and the "queue wins over latch"
rule fires. Swap that harness to `text/event-stream` — a shape the same test file already
supports via `answer_post_with_sse` — and the fence goes red. The pre-CR-02 code did not have
this failure: the reason was a single FIFO entry, so it could poison at most one call, not
every subsequent one.

The `receive()` rustdoc's framing ("the reason this **transport's** stream ended") is what
hides it: this transport has one GET session stream plus one reader per streaming POST, all
sharing one latch, and one stream's terminal end is not the transport's.

**Fix:** the latch must not be allowed to answer a caller who has an outstanding expectation
on a *different* stream. Two workable shapes, smallest first:

```rust
// (a) Scope the latch to the stream that raised it, and stop letting a POST-stream
//     end latch at all — a POST stream ending IS this call's answer failing to
//     arrive, and belongs to that call, not to the transport.
struct TerminalReason { kind: TerminalKind, message: String, stream: StreamKind }
// `drain_or_latch` surfaces only `StreamKind::Session` reasons, and only after
// the queue has been empty for the caller's whole wait, not on its first poll.

// (b) Make the latch a wake-and-diagnose rather than a pre-empt: keep it out of
//     the fast path entirely and let it win only in the `signal.changed()` arm,
//     i.e. only when the consumer was already parked with nothing in flight.
async fn receive(&mut self) -> Result<TransportMessage> {
    let mut signal = self.terminal_signal.subscribe();
    let mut receiver = self.receiver.lock().await;
    loop {
        if let Ok(queued) = receiver.try_recv() { return queued; }
        tokio::select! {
            biased;
            queued = receiver.recv() => return queued
                .ok_or_else(|| Error::Transport(TransportError::ConnectionClosed))?,
            _ = signal.changed() => {
                // the latch only answers a caller that was genuinely parked
                if let Some(reason) = self.terminal.read().as_ref() {
                    return Err(reason.to_error());
                }
            },
        }
    }
}
```

Either way, add a reset seam (`start_sse` clearing the latch on a successful re-open is the
obvious one) so a recovered transport is usable, and add a fence that runs fence 16's scenario
against `answer_post_with_sse` rather than against the JSON harness.

### CR-02: A mis-addressed response frame wedges the whole `Client` indefinitely — the "caller's own timeout" that bounds it does not exist

**File:** `src/client/mod.rs:3758-3765` (the discard), `:3721` (the lock-holding receive)

**Issue:** The correlation check is right; its cost is mis-booked. `deferred-items.md` records
`T-118.2-15-03` as *"bounded by the caller's own timeout rather than unbounded"*, and the
in-code comment at `:3747` repeats it. **`pmcp::Client` has no request timeout.**
`dispatch_request` wraps nothing in `tokio::time::timeout`; `RequestOptions::timeout` exists at
`src/shared/protocol.rs:29` and is never read by `Client`; `grep` for `tokio::time::timeout` in
`src/client/mod.rs` returns nothing. So the discard path is unbounded, not bounded.

It is worse than an unbounded wait for one call, because of the statement shape at `:3721`:

```rust
let response_message = self.transport.write().await.receive().await?;
```

The `RwLockWriteGuard` temporary lives to the end of the `let` **statement**, so the transport
write lock is held across `.receive().await`. A `dispatch_request` that is `continue`-ing on
mis-addressed frames therefore re-takes and re-holds that lock forever, and **every other
`send`/`call_tool`/`close` on that `Client` blocks behind it**. One frame with the wrong id —
from a hostile peer, or from a merely lenient one that re-types `Number(1)` as `String("1")`,
which the comment at `:3730-3735` explicitly says is now a wait — takes the client down with no
error, no log after the first `warn!`, and no recovery.

The project's own fence records the symptom: `tests/client_sse_stream.rs:701-711` asserts the
call is *still waiting* at `MISMATCH_BOUND` and treats that as the pass condition.

This is a behaviour regression versus the pre-delta code, which always made progress on any
`Response` frame. It is in scope even though the *discard* is booked, because the mitigation the
booking rests on is not real.

**Fix:** do not ship an unbounded wait. Minimum viable, in `dispatch_request`:

```rust
// bound the correlation wait, and do not hold the transport lock across it
const CORRELATION_WAIT: Duration = Duration::from_secs(60); // or from RequestOptions

let deadline = tokio::time::Instant::now() + CORRELATION_WAIT;
loop {
    let response_message = {
        let mut t = self.transport.write().await;
        match tokio::time::timeout_at(deadline, t.receive()).await {
            Ok(res) => res?,
            Err(_) => return Err(Error::timeout(CORRELATION_WAIT.as_millis() as u64)),
        }
    }; // guard dropped here, explicitly
    ...
}
```

and correct the `T-118.2-15-03` entry plus the `:3747` comment to say "unbounded until per-id
routing lands, or until the caller wraps the call in its own `tokio::time::timeout`". Also
consider capping consecutive discards (e.g. 32) and failing loudly rather than waiting.

## Warnings

### WR-01: WR-01's shutdown race does not cover a reader parked on a full receive queue, so `close()` still leaks the task and the socket

**File:** `src/shared/streamable_http.rs:3049` (`deliver_sse_event`), `:2780-2800`
(`drain_pending_events`)

**Issue:** The shutdown flag is raced against the *body read* (`:2885`) but not against the
*queue send*. `delivery.sender.send(Ok(message)).await` at `:3049` is a bare await under D-04's
await-capacity-never-drop policy. After `close()`, the application stops draining; a peer that
keeps writing fills the 64-slot queue and the reader parks in `send()` forever. `close()` does
not drop the `Receiver` (the transport is still alive), so the send never resolves, and the
abort at `:2501` reaches only the GET reader — every detached POST reader survives. That is the
exact leak WR-01 names, relocated one await down. Fence 19 misses it because its POST stream is
idle: the reader is parked in `body.frame()`, which *is* raced.

**Fix:** race the send too, and treat a shutdown there as a silent stop:

```rust
Ok(message) => tokio::select! {
    biased;
    sent = delivery.sender.send(Ok(message)) => sent.is_ok(),
    _ = delivery.shutdown_observed() => false, // `borrow()`-then-`changed()` helper
},
```

Add a fence: `close()` with the queue already at `CLIENT_RECEIVE_QUEUE_CAPACITY` and a peer
still writing must still reach `open_post_connections() == 0`.

### WR-02: `biased;` in `read_next_sse_frame` starves both shutdown arms while the body is continuously ready

**File:** `src/shared/streamable_http.rs:2885-2896`

**Issue:** `biased;` polls `state.body.frame()` first and returns on the first `Ready`. A peer
that keeps the body ready — a firehose, or simply a fast server on loopback — means
`delivery.sender.closed()` and `shutdown.changed()` are never polled at all, on any iteration.
So `close()` is not observed for as long as the peer keeps writing. The comment at `:2879-2883`
justifies the bias (don't lose a burst-then-close server's last frames) and that reasoning is
sound for the *frame* arm, but the conclusion drawn — that shutdown is now covered — only holds
for a body that goes idle. Combined with WR-01 above, a busy stream escapes both.

**Fix:** keep the bias but add a fairness escape, e.g. a frame counter that flips to an
unbiased `select!` (or checks `*shutdown.borrow()` inline) every N frames:

```rust
if state.frames_since_shutdown_check >= SHUTDOWN_CHECK_EVERY {
    state.frames_since_shutdown_check = 0;
    if *shutdown.borrow() || delivery.is_closed() { return Some(SseFrameStop::Shutdown); }
}
```

### WR-03: The `shutdown` flag is never reset, so `close()` permanently and silently disables SSE for the transport and every clone

**File:** `src/shared/streamable_http.rs:2498` (`close`), `:2687-2690` (`read_sse_body`),
`:1496-1538` (`start_sse`), `:2514-2518` (`is_connected`)

**Issue:** `close()` does `self.shutdown.send_replace(true)` and nothing ever sets it back to
`false`. `start_sse()` does not reset it. So after any `close()`:

* `start_sse()` issues the GET, gets a live body, spawns the reader, stores the handle and
  returns `Ok(())` — and the reader immediately returns `SseBodyEnd::Ended` at `:2689`. The
  caller is told the stream opened. It did not.
* every subsequent streaming-POST reader dies the same way at `:2689`, so an SSE-delivered
  response is silently dropped and its `dispatch_request` hangs (no latch is written on the
  shutdown path, by design — `:2742`).
* `is_connected()` still returns `true` unconditionally (`:2517`), so nothing tells the caller.

Because `shutdown` is `Arc`-shared and `StreamableHttpTransport` is `#[derive(Clone)]`, one
component closing its clone permanently disables SSE on every other clone. Pre-delta, `close()`
aborted the shared `abort_handle` (already a shared-kill) but the transport recovered on the
next `start_sse`.

**Fix:** either reset the flag at the top of `start_sse` (`self.shutdown.send_replace(false);`)
and document close-then-restart as supported, or make close terminal *observably*: have
`start_sse`/`send` return `Err(TransportError::ConnectionClosed)` when `*self.shutdown.borrow()`
and have `is_connected()` return `!*self.shutdown.borrow()`.

### WR-04: The test mocks re-address *every* response once any request has been recorded, silently rewriting unsolicited-frame fixtures

**File:** `src/client/mod.rs:5352-5400`, `tests/common/mock_paginated.rs:42-90`,
`tests/property_tests.rs:391-437`

**Issue:** `addressed_to_the_pending_request` rewrites the id of any `TransportMessage::Response`
whenever `last_request_id()` is `Some`. Its rustdoc says "a mock with no recorded request yet is
left alone, so a test that exercises an UNSOLICITED frame keeps the id it wrote" — but that is
only true *before the first request*. After any request has been sent, a fixture deliberately
carrying a foreign id is silently converted into a matching one, so a test written to prove the
client rejects a stray response would now prove nothing and still pass. Making the mock
conformant is right; making it unconditionally conformant removes the only local way to write a
negative case.

Separately, the same ~40-line pair (`addressed_to_the_pending_request` + `last_request_id`) is
copy-pasted verbatim into three files with three near-identical doc blocks.

**Fix:** gate the rewrite on an explicit opt-out so negative fixtures stay expressible, and lift
the shared pair into `tests/common/`:

```rust
// tests/common/id_echo.rs
pub fn echo_id(sent: &[TransportMessage], m: TransportMessage) -> TransportMessage { ... }
// mock: `if self.echo_ids { echo_id(..) } else { message }`
```

### WR-05: Fence 17 passes on any error, including ones that never reach the correlation check

**File:** `tests/client_sse_stream.rs:707-726`

**Issue:** the `match outcome` treats `Err(_still_waiting)` **and** `Ok(Err(_not_an_answer))` as
passing, panicking only on `Ok(Ok(_))`. So a future regression in which `call_tool` fails early —
a transport error, a capability refusal, a handshake change — keeps the fence green while never
executing `if response.id != request_id` at all. The `calls_observed(&server) == 1` assertion
guards only that the POST went out, not that the correlation branch ran. Given fence 17 is *the*
fence for CR-02's correlation half, that is a meaningful hole.

**Fix:** assert the intended shape and let the tolerated one be explicit:

```rust
match outcome {
    Err(_still_waiting) => {},
    Ok(Err(e)) => panic!(
        "the call must be STILL WAITING, not failed for an unrelated reason — a fence that \
         accepts any error stays green when the correlation branch is never reached: {e}"
    ),
    Ok(Ok(result)) => panic!(...),
}
```

If an early error really is an acceptable outcome on some platform, assert on its *kind* rather
than accepting the whole `Err` space.

### IN-03: The reconnect floor is applied only to peer `retry:`, not to the computed curve

**File:** `src/shared/streamable_http.rs:3427-3444`
**Issue:** `MIN_SSE_RECONNECT_DELAY` bounds the `server_retry` branch only. The curve branch
satisfies the floor purely because `INITIAL_SSE_RECONNECT_DELAY` (1 s) happens to exceed it and
`SSE_RECONNECT_GROWTH >= 1`. `property_next_reconnect_delay_stays_inside_both_bounds`
(`:5079-5096`) asserts the floor for the `None` case too, so lowering `INITIAL` below 500 ms
would red the property test rather than the code — the right failure, but the coupling is
implicit.
**Fix:** apply the bound once at the exit rather than per-branch:
`computed.max(MIN_SSE_RECONNECT_DELAY).min(MAX_SSE_RECONNECT_DELAY)`.

### IN-04: `spawn_sse_reader`'s write-only cursor local

**File:** `src/shared/streamable_http.rs:1661`
**Issue:** documented as deliberate ("written and never read back"), and it is genuinely needed
to satisfy the shared `read_sse_body` signature. Recording it so a later reader does not
"clean it up" and accidentally re-share the cursor, which is WR-02 all over again.
**Fix:** none required; the existing comment covers it. Optionally make it
`let mut _unused_post_cursor` to signal intent at the binding rather than only in prose.
