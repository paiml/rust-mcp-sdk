# Phase 118.2 Plan 13: Every Emitted Log Frame Now Carries `data` — Summary

`extra.log(level, message)` emitted `{"level":"info","message":"..."}`. The MCP
schema declares `data` REQUIRED with **no `message` member at all**, and the
official reference client's `z.unknown()` is non-optional under the bundled zod
v4 — so every frame pmcp sent was dropped on the floor. `emit_log_record` now
defaults `data` to the message string. **No Rust API changed.**

## The One-Line Change

`src/server/cancellation.rs`:

```rust
let data = data.unwrap_or_else(|| serde_json::Value::String(message.clone()));
let params = crate::types::LogMessageParams::new(level, message).with_data(data);
```

replacing the `let mut params = …; if let Some(data) = data { … }` shape.

Three properties the plan asked for, all held and all fenced rather than
asserted-about:

| Property | How it holds | Fence |
|---|---|---|
| `log_with_data` passes through verbatim | the `Some` arm moves the caller's value; nothing overwrites it | `an_explicitly_supplied_data_value_survives_verbatim` |
| the level short-circuit still precedes any allocation | the default is applied AFTER both early returns, unchanged in position | `a_below_bar_record_never_reaches_the_sink_and_builds_no_payload` |
| the message is not cloned twice | the `clone` is inside `unwrap_or_else`, so it runs only in the `None` arm | — |

On the clone: **one** extra allocation is the floor, not a concession. The frame
genuinely carries the text twice, under `data` and under `message`. The
alternative — moving the `String` into `Value::String` and reading it back out by
reference for `LogMessageParams::new(level, &str)` — allocates exactly the same
once via `Into<String>`, while being harder to read. Recorded in a comment so the
next reader does not "optimize" it into a double clone.

## Why This Is a Fix, and What It Supersedes

Plan `118.2-08` concluded *"no suite scenario validates an emitted notification's
params"* and on that basis **DECLARED** the divergence rather than fixing it.
Plan `118.2-11` measured the premise **false**:

* `WireSchemaValid` is **not a scenario**. It is a check that runs *inside*
  scenarios and validates every frame the implementation sends. At the held
  `0.2.0-alpha.11` pin it newly failed with `messagesValidated: 10`, quoting all
  three frames as
  `LoggingMessageNotification/params: must have required property 'data'`.
* `2025-11-25:tools-call-with-logging` went **1/1 → 0/2**; the v1 leg **72/2 →
  71/3**.
* Reproduced directly against the pinned bundle:

  ```
  {level:'info', message:'Tool execution started'}  -> parse ok: false
      invalid_type at params.data: expected nonoptional, received undefined
  {level:'info', data:'Tool execution started'}     -> parse ok: true
  ```

Both halves of that record are now corrected in-tree: the rewritten fence, the
`deferred-items.md` resolution section, and `WINDOWS.md` entry 4 marked `fixed`.
Anything still in this repo saying "do not change `LogMessageParams`" is stale
guidance written on a falsified premise.

**Option A, not C or D.** `message` stays on the wire as a pmcp extension — legal
(the schema does not close `additionalProperties`), tolerated (the reference
client strips unknown members), and measured (the `data`-bearing frame parses
`ok: true` with `message` present). D — changing only the conformance fixture —
was rejected by the user as gaming the referee: it turns the suite green while
every real `extra.log` caller keeps emitting non-conformant frames.

## The Fences

`tests/log_emitter.rs`, 21 → **24** always-run, plus a second property arm.

| Fence | Kind | Pins |
|---|---|---|
| `a_plain_log_emits_the_required_data_member_carrying_the_message` | wire | `data` present and equal to the message; `level` and `message` survive; `logger` still ABSENT |
| `an_explicitly_supplied_data_value_survives_verbatim` | regression guard | a JSON **object** (not a string) passes through byte-for-byte — a naive "always overwrite with the message" implementation is caught |
| `a_below_bar_record_never_reaches_the_sink_and_builds_no_payload` | ordering | every level strictly below the bar, through BOTH emitters, reaches nothing — and the bar itself still delivers, so it is not passing because the emitter went silent |
| `the_emitted_frame_satisfies_the_vendored_schemas_required_data_member` | measured | REWRITTEN from `the_vendored_schema_requires_data_where_pmcp_emits_message`; still reads the in-repo vendored schema (MEMBER lines only), payload half inverted |
| `property_every_delivered_log_frame_carries_a_data_member` | property | the invariant over arbitrary messages × every level at or above the bar |

The property arm's message generator deliberately includes the empty string and
text containing quotes and braces: `""` is what a "default only when non-empty"
bug slips through, and the rest breaks a default implemented by string
concatenation rather than `Value::String`.

The rewritten fence keeps its valuable half deliberately — it READS
`schema/vendored/core-2026-07-28/schema.ts` rather than a hardcoded copy, filtered
to member lines because the `data` member's own doc comment says "such as a string
message" and would satisfy a naive absence assertion. A schema re-vendor still
moves it.

## Still-Open Items This Plan Did Not Close

Both were explicitly out of scope and remain in `WINDOWS.md` and
`deferred-items.md`:

* **SEP-2575 v2 default** (118.2-09, entry 5): a v2 `tools/call` with no `_meta`
  logLevel still receives a log record, because `resolve_request_log_level`
  returns `None` and `DEFAULT_LOG_LEVEL` applies. Correct on v1, wrong on v2. Not
  externally observable at the current pin — the v2 leg runs no `sep-2575-*`
  scenario.
* **Client lifecycle deadlock** (118.2-10, entry 6): `Client::dispatch_request`
  awaits `transport.send(..)` before entering the receive loop that dispatches the
  inbound request, while the server holds the `tools/call` POST open for the whole
  handler. This is why `tests/pmcp_both_ends_logging.rs` asserts at the transport
  layer rather than through a full round trip — and it still passes unchanged
  here (2/2), so the shape change did not disturb the joint delivery proof.
* **`WINDOWS.md` entry 8** stays OPEN by design: it is a claim about the referee's
  verdict, and only plan 11 can close it. Entry 4 — the in-tree divergence — is
  marked `fixed`.
