# Phase 118.2 Plan 15: Latch terminal stream reasons and correlate response ids (CR-02) Summary

**CR-02 is closed, both halves.** A pmcp client whose session stream died while the application
was idle can now make a tool call that succeeds and describes itself; a second call immediately
after receives its own response; and a response bearing an id that is not this call's is never
returned as this call's answer. All three are proven through a real `pmcp::Client`, and
`cargo semver-checks` confirms the whole change is additive.

## What CR-02 actually was, measured

CR-02 was a **data-correctness hazard**, not a robustness nicety, and both halves were confirmed
in the merged source by the phase verifier before this plan existed.

### Half 1 — every terminal reason rode the response FIFO

Every terminal reason this phase introduced (D-02 overflow, D-05 parse failure, D-03 budget
exhaustion, a `405` on reconnect, a failed re-open, a dropped POST stream) was delivered by
pushing `Err(..)` onto the **same** `mpsc<Result<TransportMessage>>` the responses ride. The old
`Transport::receive` rustdoc documented this as intentional, on FIFO-ordering grounds.

The queue has exactly one consumer — `Client::dispatch_request` — so a reason raised while the
application was **idle** sat in the queue and failed the next, unrelated request.

### Half 2 — the receive loop did not compare ids

`Client::dispatch_request` returned on the FIRST `TransportMessage::Response` it popped with **no
comparison of `response.id` against `request_id`**, and unconditionally removed `request_id` from
`active_requests`. Once one out-of-band entry desynchronised the queue, call *n+1* silently
received call *n*'s result.

The missing id check pre-dates this phase. What 118.2 supplied is the *stock of out-of-band queue
entries* that made the desync reachable with no server-side bug at all.

`grep -v '^[[:space:]]*//' src/shared/streamable_http.rs | grep -c 'send(Err('` → **0**.

`Ok(msg)` deliveries are untouched: they still ride the queue with D-04's await-capacity,
never-drop policy exactly as it was.

The rewritten `receive` reads:

```rust
// Subscribed FIRST, before the queue lock and before the first latch
// read, so there is no lost-wakeup window ...
let mut signal = self.terminal_signal.subscribe();
let mut receiver = self.receiver.lock().await;
loop {
    if let Some(outcome) = drain_or_latch(&mut receiver, &self.terminal) {
        return outcome;
    }
    tokio::select! {
        biased;   // the QUEUE is polled first
        queued = receiver.recv() => { ... },
        signalled = signal.changed() => { ... },
    }
}
```

The `biased` select is what makes fence 16 pass: a queued message ALWAYS wins over a latch that
is already set.

### The rustdoc rewrite

The five-row taxonomy table keeps every row — including the ordinary-EOF row **exactly as it
stood**, since WR-05 is out of scope — but the delivery column now names the latch for the four
terminal rows. Numbered rule 1 was replaced entirely: the ordering guarantee is now "every
message already queued is delivered before the reason is surfaced, because the queue is drained
before the latch is consulted", not an argument about which channel the reason rides. Rule 2 was
replaced with the write-once transport-wide rule. Rule 3 is unchanged.

The old rationale sentence is gone:
`grep -c 'that is why the reason rides the queue' src/shared/streamable_http.rs` → **0**.

The required sticky paragraph is present as a `#` heading a consumer will read — *"The terminal
reason is STICKY — stop on it, do not loop"* — stating that every subsequent `receive()` returns
the same error immediately, that a consumer that loops and merely logs will spin instead of hang,
and that **the contract is to stop on a terminal error**. That paragraph is the whole mitigation
for T-118.2-15-04, so it is required rather than optional.

quote for a private field, because it does not report additions at all — it reports lints that
FIRED. The meaningful claim is therefore that **nothing fired**: 223 of 223 checks pass, 30 skip,
and the verdict line is `no semver update required`. That is the same shape 118.2-04 and 118.2-13
each recorded. Nothing fired, so no additive alternative had to be designed.

`Transport::receive`'s signature is unchanged, which is why the verdict is clean — the measured

### 4. [Design, recorded not a defect] `Arc<watch::Sender<u64>>` rather than the plan's bare `watch::Sender<u64>`

- **Found during:** Task 2, writing the field.
- **Issue:** `StreamableHttpTransport` is `#[derive(Clone)]`, so every field must be `Clone`.
  `watch::Sender` **does** implement `Clone` in the tokio versions vendored locally (1.47.1,
  1.48.0, 1.49.0 all carry `impl<T> Clone for Sender<T>`), and the lockfile resolves 1.52.0 — but
  this crate's manifest declares `tokio = "1.46"` as its minimum, and **1.46 is not vendored here
  to measure against**.
- **Disposition:** wrapped in `Arc`. It costs nothing (one shared sender, `send_modify` and
  `subscribe` both work through `&`), it keeps the declared version floor honest rather than
  resting on an unverified version claim, and it removes any ambiguity about what `send_modify` on
  a second producer would mean. Recorded because it is a visible departure from the plan's stated
  field type, and the reason is a measurement gap rather than a preference.

## Stated limitation, and the follow-up that removes it

**A discarded frame is gone.** If a mismatched response was the answer to some *other* in-flight
request on the same `Client`, that request now waits out its caller's timeout instead of receiving
its answer. That is strictly better than the pre-fix behaviour — one caller silently receiving
another caller's tool result is a cross-request data leak inside one process — and it is bounded
by the caller's own timeout rather than unbounded. But it is a real cost, accepted deliberately
and recorded as `T-118.2-15-03` (Denial of Service, medium, **accept**).

**The identified follow-up, named so it is not lost: per-id response ROUTING** — the
`active_requests` map carrying a response channel per id, so a popped frame is *delivered to its
owner* instead of discarded. That is a redesign of how `Client` consumes its transport, not a
comparison, and it belongs in its own plan with its own concurrency fences. It is **explicitly
not this closure's work**, and it is written into this phase's `deferred-items.md` under its own
heading (`## DEFERRED (118.2-15): per-id response ROUTING, and the cost of discard-on-mismatch`)
so it does not collide with plan 16's appendix.

## On the ALWAYS-fuzz requirement

CLAUDE.md asks every new feature for fuzz coverage. **No new fuzz target was added,
deliberately.** This plan's new surface is a private latch (a write-once `Option` slot and a
monotonic counter) and one equality comparison — neither takes untrusted BYTES. The classifier
`terminal_reason_of` is total over `&Error` with no parsing and no allocation beyond a `String`
clone, and its every arm has an asserting call site.

The reader path that DOES take untrusted bytes is unchanged by this plan and is already covered
by `decode_sse_chunks_for_fuzz` and `fuzz/fuzz_targets/streamable_sse_frames.rs` (shipped by
118.2-04, re-run at 20,000 runs with no artifact during plan 14). It was **not re-run here**:
`fuzz/target` was deleted during plan 14's ENOSPC incident, rebuilding it costs several GB on a
volume this phase has already exhausted once, and the bytes-in path this plan touches is only the
`Err` DELIVERY arm — the parse and overflow decisions themselves are byte-identical. That is a
stated omission, not an oversight.
