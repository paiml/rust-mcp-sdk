# Phase 118.2: Code Review Report

**Reviewed:** 2026-08-17
**Depth:** standard (per-file, language-aware; cross-file tracing where the reader/consumer boundary demanded it)
**Diff base:** `cb5d1365..HEAD`
**Status:** issues_found

## Summary

The **server half is sound.** `emit_log_record` (`src/server/cancellation.rs:893`) does exactly what
it claims: both early returns precede any allocation, `data` defaults only in the `None` arm, and
`log_with_data`'s value is moved through verbatim. `LoggingLevel`'s variants are declared in syslog
order so the `Ord` derive is correct, the per-session level is stored with `get_mut` (no insert path,
so no session-map growth from a guessed id), and cross-session bleed is structurally impossible —
the level lives on `SessionInfo`, is read back only for the id the session pipeline validated, and
travels to the emitter on the per-request `ProtocolContext`. `parse_peer_log_level` never panics,
never echoes peer bytes and never rejects. I found no defect in that half beyond two low-severity
notes (IN-03, IN-06).

The **client SSE half has real defects**, and they are concentrated exactly where the phase asked
for scrutiny: the reconnect loop's budget accounting and the delivery of terminal errors.

Two are Critical:

- the reconnect budget resets on *any* delivered event and a peer-supplied `retry:` is clamped only
  from **above**, so a server that emits one frame and closes — with `retry: 0` — drives the client
  into an unbounded, zero-delay reconnect loop (CR-01);
- terminal stream errors are pushed onto the *same* mpsc the responses ride, whose only consumer is
  the per-request dispatch loop. An error raised while no request is in flight sits in the queue and
  fails the *next, unrelated* request — and because that loop returns on the first `Response`
  regardless of id, the queue then stays permanently desynchronised (CR-02).

Six Warnings cover the reader's termination story (a reader parked on an idle-but-open stream never
observes shutdown), a cross-stream resumption cursor, a `start_sse` TOCTOU that can leave an
untracked second session reader, a missing 401 refresh on reconnect, an EOF path that contradicts
the taxonomy the phase documented, and a `logging/setLevel` that reports success while discarding
the level.

Bounded-read caps are correctly enforced on **both** SSE paths (GET at
`streamable_http.rs:2775-2781`, POST at `:1303-1311`, both through `SseParser::with_max_buffer_size`
at the transport's `max_collected_body_bytes`), `feed_complete_body`'s deletion reintroduced no
unbounded sibling, and the `v2_bounded_reads_tripwire` ALLOWLIST is genuinely bidirectional (a count
that *rises* fails, and a dead entry whose count *fell* also fails). The fuzz target asserts SIZES
after every chunk, not a latch, and its header explicitly records why the latch assertion is
tautological. I could not find a fence in this phase that passes vacuously; the two candidates I
chased (IN-01, IN-02) fail loudly rather than silently.

## Critical Issues

### CR-01: A peer can drive the client into an unbounded, zero-delay reconnect loop

**File:** `src/shared/streamable_http.rs:2792-2794` (budget reset), `:2849-2858` (`next_reconnect_delay`)

**Issue:** Two independently-documented decisions combine into a defect neither one names.

1. `run_session_stream` resets the budget on **any** delivered event:

   ```rust
   if delivered {
       attempt = 0;
   }
   if attempt >= MAX_SSE_RECONNECT_ATTEMPTS { /* terminal error */ }
   ```

   `delivered` is set by `drain_pending_events` (`:2330`) after a *single* successful send. So one
   frame is enough to refund the entire budget.

2. `next_reconnect_delay` lets a server-provided SSE `retry:` win, clamped only from above:

   ```rust
   if let Some(retry) = server_retry {
       return retry.min(MAX_SSE_RECONNECT_DELAY);
   }
   ```

   `SseEvent::retry` is `Option<u64>` milliseconds parsed straight off the wire
   (`src/shared/sse_parser.rs:592-594`), so `retry: 0` yields `Duration::ZERO`. There is **no lower
   bound**. The rustdoc at `MAX_SSE_RECONNECT_DELAY:506-512` reasons only about the upper direction
   ("an uncapped one lets a peer park a client's reader task").

**Failure scenario:** a server (hostile, or merely a broken proxy replaying a cached error page)
answers every GET with

```
retry: 0
id: 1
data: {"jsonrpc":"2.0","method":"notifications/progress","params":{...}}

```

and then closes the body. Per iteration the client: delivers the event → `attempt = 0` → passes the
`attempt >= 2` check → `sleep(Duration::ZERO)` → re-opens. This is a **tight, unbounded loop**:
100% of a core burned on the client, a request flood at the server, and a fresh
`auth_provider.get_access_token()` call per iteration (`build_request_from_parts:1436-1439`). The
loop only stops if the application stops draining `receive()` (backpressure) or the transport is
dropped. Without `retry:` at all the same construction still loops **forever** at one GET per
second.

T-118.2-04-01 is claimed mitigated by `MAX_SSE_RECONNECT_ATTEMPTS = 2`, and fence 12
(`tests/client_sse_stream.rs::reconnect_gives_up_after_the_retry_budget_with_a_named_error`) asserts
the GET count settles at `1 + budget` — but it uses `close_get_streams_on_accept()`, i.e. a stream
that delivers **nothing**. The `delivered` reset arm is exactly the arm no fence exercises.

**Fix:**

```rust
/// Never wait less than this before re-opening, even when a peer asks for zero.
/// `retry:` is remote input in BOTH directions: an uncapped value parks the
/// reader, and a zero value turns the loop into a request flood.
const MIN_SSE_RECONNECT_DELAY: Duration = Duration::from_millis(500);

fn next_reconnect_delay(attempt: u32, server_retry: Option<Duration>) -> Duration {
    if let Some(retry) = server_retry {
        return retry.clamp(MIN_SSE_RECONNECT_DELAY, MAX_SSE_RECONNECT_DELAY);
    }
    // ... unchanged
}
```

and make the budget refund conditional on the stream having actually been healthy, rather than on a
single frame:

```rust
/// A re-opened stream earns a fresh budget only if it stayed up long enough to
/// be a working stream rather than a one-frame bounce.
const RECONNECT_BUDGET_RESET_UPTIME: Duration = Duration::from_secs(30);

let opened_at = Instant::now();
let end = read_sse_body(..).await;
// ...
if delivered && opened_at.elapsed() >= RECONNECT_BUDGET_RESET_UPTIME {
    attempt = 0;
}
```

Add a fence that pushes one frame per body before closing (the harness already has
`push_frame` + `end_live_sse_streams`) and asserts the GET count is still bounded.

### CR-02: Terminal stream errors are queued out-of-band and fail an unrelated — possibly future — request

**File:** `src/shared/streamable_http.rs:1316-1321`, `:2275`, `:2489-2491`, `:2799-2803`, `:2820`, `:2826`
**Consumer:** `src/client/mod.rs:3721`

**Issue:** every terminal reason this phase introduced (D-02 overflow, D-05 parse failure, D-03
budget exhaustion, 405-on-reconnect, failed re-open, POST-stream drop) is delivered by pushing
`Err(..)` onto the *same* `mpsc::Sender<Result<TransportMessage>>` that carries responses. The
`Transport::receive` rustdoc (`:2058-2063`) justifies this as "FIFO is the ordering guarantee … a
terminal `Err` is queued BEHIND every message already delivered".

That reasoning assumes a consumer is waiting. The only consumer is `Client::dispatch_request`:

```rust
loop {
    let response_message = self.transport.write().await.receive().await?;   // <- `?`
```

So the error is delivered to *whichever request happens to be awaiting*, and if none is awaiting it
**persists in the queue** until the next one.

**Failure scenario (queue poisoning + desync):**

1. The application is idle. A proxy idle-timeouts the session stream; the client burns its two
   reconnects and the reader pushes `Err("the session stream was dropped and its 2-attempt reconnect
   budget … is exhausted")`. Nobody is in `receive()`. The error sits in the queue.
2. Ten minutes later the application calls `tools/call`. The POST succeeds (200 + JSON). The
   dispatch loop's first `receive()` pops the **stale** error and `?` returns it — the call fails
   with a session-stream message that has nothing to do with it.
3. The real response for that call is now sitting in the queue. The dispatch loop returns on the
   first `TransportMessage::Response(..)` **without checking the id** (`src/client/mod.rs:3723-3735`),
   so the *next* tool call pops the *previous* call's response and returns it as its own.

Step 3 is a data-correctness hazard: one tool call receives another call's result. The missing id
correlation pre-dates this phase; what is new is that the phase created a supply of out-of-band
queue entries that makes the desync reachable without a server bug. The "at most ONE terminal error
per reader" invariant does not bound this either — there is one GET reader plus one detached reader
per streaming POST, each entitled to its own terminal error.

**Fix:** do not put the terminal reason in the message FIFO. Latch it on the transport and surface
it only when the queue is genuinely empty:

```rust
// on StreamableHttpTransport
terminal: Arc<RwLock<Option<Error>>>,

async fn receive(&mut self) -> Result<TransportMessage> {
    let mut receiver = self.receiver.lock().await;
    loop {
        match receiver.try_recv() {
            Ok(message) => return message,
            Err(TryRecvError::Empty) => {},
            Err(TryRecvError::Disconnected) => {
                return Err(Error::Transport(TransportError::ConnectionClosed))
            },
        }
        if let Some(error) = self.terminal.read().clone() {
            return Err(error);          // sticky, not one-shot
        }
        match receiver.recv().await { .. }
    }
}
```

Independently — and worth its own follow-up even if the latch lands — `dispatch_request` must
compare `response.id` against `request_id` and keep looping on a mismatch, so that no future
out-of-band entry can permanently pair request *n+1* with response *n*.

## Warnings

### WR-01: A reader parked on an idle-but-open stream never observes shutdown — task and socket leak

**File:** `src/shared/streamable_http.rs:2767-2832` (GET), `:1299-1323` (POST), `:2084-2097` (`close`)

**Issue:** the phase's stated termination contract is (a) `sender.send(..)` returning `Err`, and (b)
`sender.is_closed()` checked around the backoff sleep. Neither fires while the reader is parked in
`state.body.frame().await` inside `read_sse_body`. A server holding the session stream open with SSE
keep-alive comments (`: ping\n\n`, the standard idle-keepalive) produces **no events**, so the reader
never attempts a send and never reaches the sleep.

Dropping the last transport clone does not help: `abort_handle` holds a `JoinHandle`, and dropping a
`JoinHandle` in tokio *detaches* rather than aborts. There is no `Drop` impl on the transport
(verified: `grep 'impl Drop' src/shared/streamable_http.rs` is empty). So a dropped transport leaves
a live task holding a live TCP connection until the *server* times it out. In a process that creates
and drops transports repeatedly (a pool, a CLI loop, a test suite), tasks and file descriptors
accumulate.

`close()` compounds it: it aborts only the GET handle. Every detached POST reader
(`drop(self.spawn_sse_reader(..))`, `:1893`) survives `close()` outright, and there is no bound on
how many exist — one per streaming POST response.

Fence 10 (`a_post_sse_reader_terminates_when_its_owning_transport_is_dropped`) does not catch this
because it deliberately pushes a frame "purely so the reader HAS a next send to fail".

**Fix:** give the reader a shutdown future to race, rather than relying on a send it may never make:

```rust
// in read_next_sse_frame / read_sse_body
tokio::select! {
    frame = state.body.frame() => { /* existing arm */ },
    () = sender.closed() => {
        state.done = true;
        return Some(SseFrameStop::Dropped(Error::Transport(
            TransportError::Request("the transport went away".into()),
        )));
    },
}
```

`mpsc::Sender::closed()` resolves the instant the `Receiver` drops, covering both the dropped-transport
and the closed-transport cases without a `Drop` impl. For `close()`, additionally hold a
`tokio_util::sync::CancellationToken` (or a `watch` channel) on the transport, clone it into
`SseReaderContext` and into `spawn_sse_reader`, and cancel it in `close()` so detached POST readers
stop too. Then rewrite fence 10 *without* the "push one frame" crutch.

### WR-02: The resumption cursor is shared across streams, so a reconnect can resume from another stream's event id

**File:** `src/shared/streamable_http.rs:1302` and `:1267` (same `Arc` handed to both readers), `:2481` (write), `:2678` (read)

**Issue:** `last_event_id` is one `Arc<RwLock<Option<String>>>` on the transport. `deliver_sse_event`
writes it from **any** stream, and `SseReaderContext::reconnect_cursor` reads it back as the
`Last-Event-ID` header for the GET re-open. Since this phase, streaming POST responses are read
incrementally and therefore also write to it — concurrently, one writer per in-flight streaming POST.

MCP resumability is per-stream: the client resumes *the stream the id came from*. A cursor minted on
a POST response stream, sent as `Last-Event-ID` on the session-stream GET, asks the server to replay
from a position that belongs to a different stream. Depending on the server's event store that is
either a rejection, a replay of the wrong frames, or a silent gap — and a silent gap is exactly the
failure the reconnect exists to prevent.

The sharing itself pre-dates this phase; *automatically consuming it as a reconnect cursor* is new
(before 118.2 a cursor only ever reached the wire when the application passed one explicitly via
`SendOptions`).

**Fix:** make the cursor per-reader. `SseReaderContext` should own its own
`Option<String>` cursor updated by its own `read_sse_body`, and `spawn_sse_reader` should own a
separate one; keep the transport-wide `last_event_id` field for the public
`StreamableHttpTransport::last_event_id()` accessor and the `on_resumption` callback only. That is a
signature change to `read_sse_body`/`deliver_sse_event` (pass `&mut Option<String>` plus the shared
`Arc` for reporting), not a structural one.

### WR-03: `start_sse` has a TOCTOU on `abort_handle` that can leave a second, untracked session reader

**File:** `src/shared/streamable_http.rs:1153-1194`

**Issue:**

```rust
let handle = self.abort_handle.write().take();   // (1) lock taken and released
if let Some(handle) = handle { handle.abort(); }
...
let handle = tokio::spawn(...);                  // (2) spawn
*self.abort_handle.write() = Some(handle);       // (3) lock retaken
```

The lock is released between (1) and (3). `start_sse` takes `&self`, and
`StreamableHttpTransport` is `Clone` with all state shared, so two clones can interleave: both take
`None` at (1), both spawn at (2), and the second store at (3) overwrites — and thereby **detaches** —
the first handle. The result is two live GET session streams: duplicate frame delivery, two writers
racing on `last_event_id` (see WR-02), and one reader that neither `close()` nor a later `start_sse`
can ever stop (per WR-01 it may then never stop at all).

Reachable paths that call `start_sse` off `&self`: the 202 branch of `post_body` (`:1818`) and
`send_with_options`'s resumption branch (`:1605-1607`). Fence 4
(`repeated_initialized_notifications_leave_exactly_one_live_reader`) exercises the sequential case
only.

**Fix:** hold the guard across the whole swap, or serialise the operation:

```rust
async fn start_sse(&self, cursor: Option<String>) -> Result<()> {
    // Serialize the whole abort/open/store sequence: the lock cannot be held
    // across the `.await` on the open, so a dedicated async mutex is what makes
    // "at most one session reader" an invariant rather than a race.
    let _open = self.sse_open_lock.lock().await;
    ...
}
```

with `sse_open_lock: Arc<tokio::sync::Mutex<()>>` on the transport (private field, semver-invisible
for the reasons already recorded at `max_collected_body_bytes`).

### WR-04: A reconnect GET gets no 401 refresh, unlike every POST

**File:** `src/shared/streamable_http.rs:2706-2730` (`open_sse_once`) vs `:1696-1739` (`post_once`)

**Issue:** `post_once` implements the single-shot refresh: on `401` it calls
`provider.on_unauthorized()` and retries once with a byte-identical body. `open_sse_once` treats any
non-2xx — including `401` — as a hard failure, and on the reconnect path that failure is terminal:
the loop sends `reconnect_open_failed(..)` and returns.

**Failure scenario:** a bearer token expires. The gateway drops the idle session stream (a routine
consequence), the client reconnects, the reissued GET is answered `401`, and the session stream is
lost **permanently** with a message that names the refusal to re-handshake — while POSTs on the same
transport continue to work fine after their own refresh. Server-to-client requests (sampling, roots,
elicitation) are dead from that point with no recovery path short of rebuilding the client.

The phase's own T-118.2-04-07 mitigation ("ONE `build_sse_get_request` over ONE
`build_request_from_parts`, there is no second builder to diverge") covers header *construction* but
not the *response* handling, which is where the divergence actually is.

**Fix:** factor the refresh out of `post_once` and call it from `open_sse_once`:

```rust
if response.status() == StatusCode::UNAUTHORIZED {
    if let Some(provider) = self.config.read().auth_provider.clone() {
        provider.on_unauthorized().await?;
        let retry = StreamableHttpTransport::build_sse_get_request(&self.request_parts(), cursor).await?;
        response = self.client.request(retry).await.map_err(..)?;   // at most once
    }
}
```

Fence it with a harness that answers the first GET `401` and the reconnect `200`.

### WR-05: An ordinary EOF on the session stream escalates to an application-visible error, contradicting the documented taxonomy

**File:** `src/shared/streamable_http.rs:2054` (the doc row), `:2266-2268` and `:2796-2804` (the behaviour)

**Issue:** the `Transport::receive` taxonomy table states:

> | Ordinary EOF, or a deliberate `close` / last-transport-drop | NOTHING — the reader exits silently | this keeps awaiting, exactly as before |

That row is **false for the session stream**. `read_sse_body` maps end-of-body to
`progress.dropped(None)` → `SseBodyEnd::Dropped { cause: None, .. }`, which the reconnect loop
retries and, once the budget is spent, converts into
`reconnect_budget_exhausted(attempt, None)` = `"… the peer ended the body"` — a hard `Err` on the
receive queue. The MCP spec permits a server to close an SSE stream at any time; a server that
simply does not hold GET streams open (answering `200` + immediate EOF) now costs the client three
GETs and an application-visible transport error on every connection.

Combined with CR-02, this is the *most likely* real-world trigger for the queue poisoning described
there.

**Fix:** pick one and make the doc and the code agree. The lower-risk option is to keep reconnecting
but not to escalate a clean EOF: track whether any body in the burst ended with `cause: Some(..)`
and, if none did, exit silently after the budget (optionally `tracing::warn!`). If escalation is
intended, correct the table row and say plainly that a clean EOF on the session stream is retried
and then reported.

### WR-06: `logging/setLevel` reports success while silently discarding the level (stateless deployments, and batches)

**File:** `src/server/streamable_http_server.rs:1627-1650` (`capture_v1_set_level`), `src/server/core.rs` (`set_logging_level_response`)

**Issue:** `capture_v1_set_level` returns early when `!sessions_on` or when there is no session id,
but `set_logging_level_response` still answers the mandated literal `{}`. A stateless v1 deployment
therefore tells every client "level set" and then applies `DEFAULT_LOG_LEVEL` to every request
forever. A client that asked for `debug` silently receives none, and a client that asked for `error`
silently receives `info` chatter it explicitly declined — the second direction is the one that
matters, because it is unsolicited data on a channel the client tried to quiet.

Second instance, same function: the method is read as `body.get("method")`, which is `None` for a
JSON-RPC **batch** (a top-level array). If the v1 ingress accepts batches — the client's own
`post_body` parses batch responses at `:1960` and `:2007`, so batching is a live shape in this
codebase — a `logging/setLevel` inside a batch is answered `{}` by dispatch and never captured.

**Fix:** in the stateless case, either (a) keep answering `{}` and document the limitation on
`set_logging_level_v1_result`, or better (b) resolve the level per-request from the body on the
stateless path too (the value is right there in `raw_body_json`'s parse) rather than only from the
session map. For the batch case, iterate array entries:

```rust
let frames: SmallVec<[&Value; 1]> = match body {
    Some(Value::Array(items)) => items.iter().collect(),
    Some(value) => smallvec![value],
    None => return,
};
for frame in frames { /* existing per-frame capture */ }
```

## Info

### IN-01: The structural fences strip `//` comments only

**File:** `tests/log_emitter.rs:557-568` (`code_lines`), `:1848` (`squeezed_code`)

`code_lines` filters lines whose trimmed start is `//`. A `/* … */` block comment — or a string
literal — containing e.g. `attach_request_log_sink(extra, None)` would satisfy
`both_dispatch_roots_attach_the_log_sink` without either root calling anything. The fence's own
docstring says "A claim satisfied by a doc comment is not a claim", which is the right instinct;
the filter just doesn't cover block comments. Low likelihood, cheap fix: reuse the comment stripper
`tests/v1_severability_tripwire.rs:435-568` already implements (it handles line comments, block
comments and raw strings) instead of a second, weaker one.

### IN-02: Fences 13 and 14 are timing-fragile under load

**File:** `tests/client_sse_stream.rs` (`closing_during_reconnect_backoff_issues_no_further_get`, `dropping_the_transport_during_backoff_issues_no_further_get`)

Both wait for `get_lines() >= 2` and then assert `observed < 1 + SHIPPED_RECONNECT_BUDGET`, i.e.
`observed == 2`. The window before the third GET is the 1.5 s second backoff; on a loaded CI box the
10 ms poll plus the assertion can land after it, and the fence fails for a scheduling reason rather
than a defect. This fails in the *safe* direction (loudly, not vacuously) — the anti-vacuity design
in the summary is correct — but it is a flake source in a suite that already carries one known
1-in-9 conformance flake. Consider having the harness hold the second GET open until the test
signals, so the third GET cannot be scheduled at all before `close()`/`drop`.

### IN-03: The request body is fully re-parsed a third time per POST

**File:** `src/server/streamable_http_server.rs:1687` (`raw_body_json` inside `resolve_request_log_level`), called at `:4629` and `:5421`

`resolve_request_log_level` performs its own `serde_json::from_slice::<Value>` over the whole
peer-supplied body, in addition to the parses the era classification and the MRTR extraction already
did. Correctness-neutral and out of v1 performance scope, but it is a third full deserialization of
untrusted input on the hot ingress path and the parsed `Value` is already in hand at both call sites'
enclosing scope. Threading the existing parse through would remove it.

### IN-04: `pub` closure field with `#[allow(dead_code)]`

**File:** `src/server/cancellation.rs:225` (`pub log_sink`), `:231` (`pub log_level`)

Both are `pub` fields carrying live capability handles, marked `#[allow(dead_code)]` (following the
existing `progress_reporter` precedent). Any code holding a `&mut RequestHandlerExtra` can swap the
sink; `examples/s54_v2_dual_conformance.rs` already reads `extra.log_level` directly rather than
through an accessor, which pins the field name into the public API. Accessors (`log_sink_is_attached()`,
`log_level()`) plus private fields would be the safer shape, and the struct is `#[non_exhaustive]`
so nothing prevents it going forward.

### IN-05: The v1 capability arm now spends ~60 s waiting out a dispatch budget

**File:** `crates/pmcp-team-servers/tests/era_matrix.rs` (`v1_capability_arm`)

The arm pins `DISPATCH_TIMEOUT_MARKER = "timed out"` for two tools, each of which waits out the
server's dispatch budget (~30 s, per the module doc's own measurement: "BASE, in 0.18 s … NOW, in
~30 s"). That is a deliberate, documented record of the open client-lifecycle deadlock and the
negative assertion against `BASE_FAIL_FAST_MARKER` makes it non-vacuous — but it converts a
sub-second test into a minute-long one in a suite that runs `--test-threads=1` in CI. Worth pinning
a shorter server-side dispatch budget in the fixture if one is configurable.

### IN-06: `parse_peer_log_level`'s "no rejection" rule is right; one consequence is worth stating in the rustdoc

**File:** `src/server/streamable_http_server.rs:1603`

A misspelled `_meta` level silently falls back to `info` — correct for an advisory hint. But on v2
that same fallback is what makes a *missing* key indistinguishable from a *malformed* one, which is
the mechanism behind the already-recorded SEP-2575 default (WINDOWS.md, not re-reported here).
When that item is fixed, `parse_peer_log_level` returning `None` for both "absent" and "garbage" will
need to become a three-way answer (`Absent` / `Invalid` / `Level`), or a v2 client will be able to
re-enable logging it is prohibited from receiving simply by sending a malformed level. Worth a
forward-looking note at the function so the fix does not land halfway.

## What I checked and found sound

Recorded so the next reviewer does not re-derive it:

- **`emit_log_record` (`src/server/cancellation.rs:893-931`)** — level short-circuit and the no-sink
  return both precede payload construction; `data.unwrap_or_else(|| Value::String(message.clone()))`
  clones only in the `None` arm; `log_with_data`'s value is moved and never overwritten.
  `LoggingLevel` variants are in ascending syslog order so the `Ord` derive matches the doc.
- **Level isolation** — per-session storage via `get_mut` (`v1_session.rs:319-326`) has no insert
  path, so an unknown/guessed session id cannot grow the map; the v2 arm is per-request off `_meta`
  with nothing stored; the two arms are mutually exclusive by `sessions_active`. No cross-session
  bleed found. A below-threshold record constructs and leaks nothing.
- **Bounded reads** — both SSE sites build `SseParser::with_max_buffer_size(max_collected_body_bytes)`;
  `read_next_sse_frame` polls `sse_stream_overflow` once per chunk and ends the stream on the latch;
  `take_utf8_prefix` retains ≤3 bytes (property-tested); `feed_complete_body`'s deletion left no
  unbounded entry point and the tripwire's ALLOWLIST fails on both a risen count and a dead entry.
- **Fuzz seam** — `decode_sse_chunks_for_fuzz` drives the production sequence and reports the
  production observers; the target asserts sizes after every chunk at two bounds and documents why
  the latch assertion is tautological.
- **`v2_routing_headers`, `truncate_sse_frame`, `collect_body_within_cap`** — non-panicking on
  arbitrary input; the error paths echo no unbounded peer content.
