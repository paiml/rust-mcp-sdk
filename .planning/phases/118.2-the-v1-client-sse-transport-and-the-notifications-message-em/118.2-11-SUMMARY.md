**(a) D-16 is delivered by a one-word addition, not by new exit-code logic.** The clause guarding
`FULLY_SCORED_GREEN_REVISIONS` already asserts the revision's *own* suite exit status is 0 alongside an
independently re-derived scored-failure count — its own message calls these "two INDEPENDENT
authorities on the same fact." The false green it closes: a check-count floor is satisfiable by a run
that FAILS, and until now the v1 leg had only a check-count floor.

**(b) The scored floor is now per-revision**, via `min_scored_scenarios_for_rev`, deliberately shaped
like the adjacent `min_checks_for_rev` (including a `fail` arm for an undeclared revision, so a future
revision cannot join the list with no floor and satisfy "every scored scenario is green" vacuously).
The v1 leg has 30 scored scenarios (33 run, minus 3 the suite itself classifies as not-scored), so the
shared floor of 37 would have rejected it. **Splitting, not lowering:** a shared 30 would have silently
weakened the v2 guard by 7 scenarios.

**(c) The blocking list was WIDENED, not shortened — a deliberate deviation from the script's own
comment.** That comment instructed "MOVE 2025-11-25 here and delete its entries from
`BLOCKING_GREEN_SCENARIOS`". Following it would drive `blocking_listed` to 0 and violate
`MIN_BLOCKING_GREEN_SCENARIOS`, a floor whose own comment says **NEVER LOWERED** — the widening would
have broken the run. All 29 entries are kept, `tools-call-with-logging` is added as a 30th, and the
floor is raised to 30. Strictly stronger in both directions: the whole-scored-set clause now covers the
leg universally *and* the named list still cannot be quietly shortened. The rationale is written into
the comment, which no longer instructs deletion.

**(d) Stale prose corrected.** Three places still asserted the v1 leg exits 1 on
`tools-call-with-logging` "for which the SDK has no handler-facing emitter": the header's headline
numbers (§0), the exit-status rationale, and the `DECLARED NON-CONFORMANCE` block the script prints on
every run. All three are now accurate. Leaving them would have made the script print a false claim on
every CI run.

### What was deliberately NOT claimed

Booked with **eight stated limitations**, written into the rows rather than omitted. Two of them are
open findings that a reader of these green numbers could otherwise mistake for fixed:

1. **SEP-2575 on v2 is not fixed.** A v2 `tools/call` with no
   `_meta["io.modelcontextprotocol/logLevel"]` still gets a log record (`resolve_request_log_level`
   returns `None`, `DEFAULT_LOG_LEVEL` applies). Measured: the pinned suite runs **no** `sep-2575-*`
   scenario on the v2 leg, so it is **not externally observable** — and therefore not something these
   green numbers speak to either way. `WINDOWS.md` entry 5, OPEN.
2. **The client lifecycle deadlock is open.** `Client::dispatch_request` awaits `transport.send(..)`
   before entering its receive loop while the server holds the `tools/call` POST open, so a pmcp client
   cannot ANSWER a server-to-client request issued during its own call. **Delivery is fixed; the answer
   path deadlocks.** `WINDOWS.md` entry 6, OPEN — and it is the same defect as the elicitation flake
   above.

The other six: the v2 progress-queue's 64-slot DROP-NEWEST bound; JSON-only v2 clients receiving no
records by design; `extra.log` with no sink being silently `Ok(())` (D-08); the deferred Client-level
notification observation API (`WINDOWS.md` entry 7) which is why the D-15.3 joint fence asserts at the
transport layer; the suite never exercising pmcp as a *client* by construction; and the elicitation
flake.

**CONF-07 was AMENDED, not replaced** — both of its named preconditions (client transport, log
emitter) are recorded as closed, with 118.1's original booking evidence left intact, and with the
answer-path caveat explicitly *not* swept up.

**CONF-10's row was AMENDED** with the suite score it had deferred to this plan, and with the

### 4. [Rule 1 — bug, caused by this plan] The gate-wiring fence caught the constant rename

`make quality-gate` failed with `tests/ci_conformance_gate_wiring.rs::the_zero_check_gate_and_the_check_floors_are_declared`:

would have shipped broken.

### 5. [Rule 3 — blocking, out of scope] `cargo audit` red on `RUSTSEC-2026-0257`

`deferred-items.md` so the diagnosis is not repeated. Commit `324378da`. The 7 pre-existing allowed
warnings (including `paste` via `umya-spreadsheet`) were left untouched.
