<objective>
Hoist the notification sink to a shared per-request unit (D-07) so a handler's `extra.log(..)` reaches
a client on both native dispatch roots.

Purpose: `ServerProgressReporter::new` takes `Arc<dyn Fn(Notification) + Send + Sync>` — a sink that
already carries **any** `Notification` — and it is already plumbed into both roots. But
`progress_reporter_for` (`src/server/mod.rs:1314`) only builds it when `req._meta` carries a progress
token, so today the sink is `None` for every call that did not ask for progress. One function builds
the sink for a request; the progress-token gate then applies **only** to the `ProgressReporter`, and the
log sink is unconditional.

**Both roots or neither.** CONTEXT.md names changing one and not the other as "the phase's most likely
silent defect", and 118.1 spent real effort collapsing exactly this class of divergence
(`completion/complete` had two dispatchers giving two *different* wrong answers). The precedent to copy
is `attach_request_peer` (`src/server/core.rs:4514`), created by 118.1 for precisely this reason.

**The asymmetry to size for:** `ServerCore` has **no `notification_tx` of any kind** — that field exists
only on `Server` — and all four of `ServerCore`'s `RequestHandlerExtra::new` sites pass
`progress_reporter: None` unconditionally. So `ServerCore`'s fallback argument to the shared unit is a
literal `None`, and its only possible sink is the request-scoped `TransportBackchannel`.

Output: one unit, two call sites, and fences proving both roots and the precedence rule.
</objective>

The pattern to twin, `src/server/core.rs:4485-4532` — `attach_request_peer(extra, global)`. Its rustdoc
states the rule verbatim: "the precedence rule is the kind of thing two roots must never disagree about,
and a rule spelled twice is kept in step by a comment instead of by the compiler. Both roots previously
carried this body verbatim." It also carries an `# Ordering` section: "Every dispatch site calls this
AFTER its `tool_authorizer` check, so an unauthorized caller returns before a handler body ever runs."
Its body clones the request-scoped value out of the borrow BEFORE `with_peer` consumes `extra`:

```
#[cfg(not(target_arch = "wasm32"))]
pub(crate) fn attach_request_peer(extra, global: Option<&Arc<dyn PeerHandle>>) -> RequestHandlerExtra {
    let request_scoped = extra.protocol_context.as_ref()
        .and_then(ProtocolContext::transport_backchannel)
        .and_then(TransportBackchannel::peer)
        .cloned();
    if let Some(peer) = request_scoped { return extra.with_peer(peer); }
    if let Some(peer) = global { return extra.with_peer(peer.clone()); }
    extra
}
```

Root-B delegation with its wasm arm, `src/server/core.rs:747-756`:

```
#[inline]
fn attach_peer(&self, extra: RequestHandlerExtra) -> RequestHandlerExtra {
    #[cfg(not(target_arch = "wasm32"))] { attach_request_peer(extra, self.peer_handle.as_ref()) }
    #[cfg(target_arch = "wasm32")] { extra }
}
```

Root-A's sink resolver, ALREADY correct and already preferring the request-scoped backchannel —
`src/server/mod.rs:1282-1300`, `fn progress_notification_sink(&self, protocol_context) -> Option<Arc<dyn Fn(Notification) + Send + Sync>>`:
it returns the `TransportBackchannel::notification_sink` when present, else derives a closure from

The gate D-07 removes for the LOG path only, `src/server/mod.rs:1313-1322`:

```
fn progress_reporter_for(&self, meta, protocol_context) -> Option<Arc<dyn ProgressReporter>> {
    let token = meta.and_then(|meta| meta.progress_token.as_ref())?;   // <- gate STAYS here

}
```

The v1 sink that already exists on every non-`initialize` v1 session request —
`src/server/streamable_http_server/peer_channel.rs:506-517` builds `session_notification_sink` routing

Pitfall 12 — the move that makes ordering matter: `ServerCore::handle_request`'s tool arm moves

captured BEFORE that move. Read the sink back off `extra.protocol_context` AFTER construction — which is
exactly what `attach_request_peer` does — rather than capturing it before the move.
