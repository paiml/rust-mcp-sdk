## User Constraints (from CONTEXT.md)

### Locked Decisions

#### The client SSE read

- **D-01: Both whole-body collect sites become incremental reads.** The GET stream
  (`src/shared/streamable_http.rs:1002`) *and* the POST-response SSE (`:1543`). The roadmap names
  only the GET, but the POST case is the more consequential of the two: in StreamableHTTP a POST
  that answers `text/event-stream` stays open and can carry notifications **and server-to-client
  requests** before the response frame. Collecting it whole means progress arrives only after the
  call ends, and **in-tool elicitation over a POST stream deadlocks outright** — the client cannot
  answer a request it has not parsed yet.
  - The parser is not the missing piece. `SseParser::feed(&mut self, data: &str)`
    (`src/shared/sse_parser.rs:382`) is already incremental and already hardened. What is missing
    is a streaming read feeding it.

- **D-02: The collected-body cap becomes the parser bound.** Build the streaming parser with
  `SseParser::with_max_buffer_size(self.max_collected_body_bytes)` — 16 MiB default
  (`DEFAULT_MAX_COLLECTED_BODY_BYTES`, `:454`), already user-overridable through
  `with_max_collected_body_bytes`. **No new public config.**
  - *Why this is safe:* the parser bound is already the product of Phase 113's gap-closure round —
    latching overflow that survives `reset`, a bound over retained-state-plus-chunk with two
    independently sufficient enforcement points (review CR-01/CR-02, T-113-86). Its own rustdoc
    already prescribes the response: *"end the stream with an error naming the limit, not to keep
    parsing."*
  - *Known interaction, from the parser's own source:* the bound is evaluated over the chunk
    **total**, so "a chunk carrying many individually small COMPLETE events is refused whenever the
    chunk TOTAL exceeds the limit … behaviour depends partly on how the transport frames its
    reads." At 16 MiB this is not reachable by real MCP frames, but a planner lowering the bound
    must know the coupling exists.
  - *Rejected:* a separate `max_sse_buffer_bytes` knob (a second number users must reason about);
    a lifetime byte budget (a v1 session stream is meant to live as long as the session, so any
    lifetime ceiling is a timer on legitimate use).

- **D-03: Bounded auto-reconnect with `Last-Event-ID`.** The parser already tracks
  `last_event_id()`, and `apply_resumption_header` already exists.
  - *Why not "surface and stop":* real deployments idle-drop long-lived streams routinely (ALB
    ~60s, Cloudflare, API gateways). Without reconnect this phase's fix silently regresses to
    `NO_LIVE_STREAM` the first time a proxy blinks — the exact symptom it exists to remove.
  - **⚠ Constraint the planner must resolve:** `apply_resumption_header` is
    `#[cfg(feature = "v1-compat")]`, and it is *the only `#[cfg]` at a call site in that file* (the
    file's own comment says so and asks that a second one not accumulate). On a `full-v2` build
    there is no `Last-Event-ID` to send. Reconnect on `full-v2` therefore either resumes nothing or
    does not happen — decide which, and route it through a paired accessor with a constant
    `full-v2` answer rather than a second call-site `#[cfg]`.
  - Retry count and backoff are Claude's discretion (see below).

- **D-04: Bounded receive queue; the reader awaits capacity.** The channel is
  `mpsc::unbounded_channel()` today (`:598`), which was implicitly bounded by the whole-body
  collect. Once the stream never ends, an unbounded queue makes D-02's per-event bound a paper
  guarantee.
  - Real TCP backpressure: when the consumer is behind, the reader stops pulling and the server's
    window closes. **Never drops a frame** — which matters because this queue carries
    `sampling`/`roots`/`elicit` **requests**, and a dropped request strands a correlation until it
    times out, unlike a dropped progress notification.
  - *Deliberately NOT the server-side precedent.* `V2_PROGRESS_QUEUE_CAPACITY = 64` drop-newest is
    correct for progress frames and wrong here, for the reason above. The two directions are
    allowed to differ; say so in the code rather than letting a reader assume drift.
  - *Accepted risk:* a consumer that never drains wedges the stream. The reader is already its own
    spawned task, so backpressure lands on the reader, not the consumer.

- **D-05: A frame that fails to parse ENDS the stream with a named error.** Today
  `if let Ok(msg) = parse_message(..)` drops it silently (`:1051`). A frame the client cannot parse
  may be a server-to-client request, and swallowing it produces a hang with no signal at either
  end. Same treatment as parser overflow, so corruption has **one** story rather than two.

#### The emitter

- **D-06: `RequestHandlerExtra` only — no trait changes anywhere.** `extra.log(..)`, mirroring
  `report_progress` (`src/server/cancellation.rs:657`). **No `PeerHandle` method.**
  - Criterion 3's `cargo semver-checks` verdict is therefore a clean *"no public trait surface
    touched"* rather than *"additive with a default body"*. External `PeerHandle` implementors are
    unaffected rather than defaulted-around.
  - *Note for the planner:* the roadmap's criterion 3 anticipated a defaulted `PeerHandle` method
    and justified the phase split partly on that basis. That justification does not evaporate — the
    client-transport work is reason enough — but do not add the trait method just because the
    roadmap's prose implies one.

- **D-07: The notification sink hoists to a shared per-request unit.** `ServerProgressReporter::new`
  takes `Arc<dyn Fn(Notification) + Send + Sync>` — a sink that already carries **any**
  `Notification`. It is already plumbed into both dispatch roots. But `progress_reporter_for`
  (`src/server/mod.rs:1314`) only builds it when `req._meta` carries a progress token, so today the
  sink is `None` for every call that did not ask for progress.
  - One function builds the sink for a request. The progress-token gate then applies **only** to the
    `ProgressReporter`; the log sink is unconditional.
  - **Both roots call the shared unit** — `ServerCore::handle_request` (`src/server/core.rs`) and
    `Server::handle_request_with_context` (`src/server/mod.rs`). This is the same pattern 118.1 used
    for `attach_request_peer`, which exists precisely because those twin roots drift.

- **D-08: No sink → `Ok(())`, silently dropped.** Matches `report_progress` exactly
  (`cancellation.rs:663`). Handlers stay callable outside a server — `RequestHandlerExtra::default()`
  is documented for "testing and simple tool invocations" — without special-casing.
  - *Accepted cost, stated plainly:* a misplumbed transport looks identical to a quiet handler. The
    conformance fence catches it (a test asserting logs arrive fails loudly when none do), so this
    is a production-diagnostics hole, not a false-green in the gate.

- **D-09: No rate limit on the emitter.** `ServerProgressReporter` rate-limits to 100ms, and that is
  right for progress: dropping an intermediate value loses nothing because the next supersedes it.
  Log records are not idempotent — **each one is the only copy of its information**, and a rate
  limiter silently deletes evidence. D-04's queue backpressure already bounds the downstream.

#### Level filtering

- **D-10: Filter on both eras.** Honour v1's `logging/setLevel` and read v2's
  `io.modelcontextprotocol/logLevel` per-request `_meta` key.
  - `LOG_LEVEL_REQUEST_META_KEY` (`src/server/streamable_http_server.rs:1429`) exists and is
    referenced **only** by the `V2_RETIRED_METHODS` table (`:1485`). v2 today advertises a
    replacement mechanism that does nothing. Closing that is part of this decision.

- **D-11: The v1 level lives in the existing `v1::V1State` session map.** Confirmed:
  `ServerState.server` is one `Arc<tokio::sync::Mutex<Server>>` shared by every session
  (`streamable_http_server.rs:479`). Putting the level there would let client B's `setLevel` change
  client A's filtering.
  - The per-session home already exists and is **already v1-gated**, which matches `setLevel`'s life
    exactly since v2 retired it. On a `full-v2` build `V1State` is a zero-sized twin, so those builds
    allocate nothing for a mechanism they do not have — structural, not a runtime branch someone can
    forget to take (SMPL-02 / D-03 / D-10 of the v1 pairing).
  - *Plumbing question left to research:* `logging/setLevel` arrives as a JSON-RPC request and the
    session identity is known at the HTTP layer. Whether the level is captured by intercepting at
    that layer (as `V2_RETIRED_METHODS` does) or by reaching session state through the
    `ProtocolContext` already threaded into dispatch is an implementation choice, not a locked one.

- **D-12: Default level is `info`.** Conventional across MCP implementations; `debug` and finer are
  suppressed until asked for, so a chatty handler cannot flood a client that never opted in. The
  conformance scenario emits at `info` or above and therefore passes unconfigured.

- **D-13: Both dispatch roots must agree about `setLevel`.** Today
  `Server::process_client_request` answers `Ok(json!({}))` for `SetLoggingLevel` with **no era
  branch anywhere in `src/`** — the v2 retirement is enforced only at the HTTP layer.
  `crates/pmcp-team-servers/tests/era_matrix.rs` flags this in its module doc: *"the REPLACEMENT
  mechanism works … only the retirement of the old RPC is missing."*
  - The `Server` arm stores-and-honours on v1 and retires on v2. 118.1 spent real effort collapsing
    exactly this class of divergence (`completion/complete` had two dispatchers giving two
    *different* wrong answers); leaving a known one open invites the next reader to trust the wrong
    root.
  - This arm is the `Subscribe | Unsubscribe | SetLoggingLevel | Ping` residual. **Only
    `SetLoggingLevel` is in scope** — do not unify the other three here.

## Summary

This phase has **three** defects to close on the client side, not the one the roadmap names, and the
extra one is the load-bearing one. I measured it with a live probe in this session: **pmcp's
`StreamableHttpTransport` never issues a GET at all.** The `start_sse(None)` call that is supposed to
open the session stream after `notifications/initialized` sits inside `if !response.status().is_success()`
at `src/shared/streamable_http.rs:1466`, and `202 Accepted` **is** a success status
(`http::StatusCode::is_success` is `(200..300)`), so that branch is dead code. A probe that stood up a
recording TCP listener and drove a real `pmcp::ClientBuilder` through `initialize` observed
**two POSTs and zero GETs**. Fixing only the whole-body read (D-01/D-02) would leave
`deprecated_capabilities_complete_under_both_eras` reporting `no-live-stream` exactly as it does
today, because there would still be no stream to read.

The second defect is the one the roadmap and CONTEXT.md name, and I confirmed it independently:
against a `text/event-stream` response that delivers one complete `message` event and then never
ends, `StreamableHttpTransport::start_sse` **does not return within 3 seconds** and the already-delivered
event never reaches `Transport::receive()`. Both `collect_body_within_cap` call sites (`:1002` GET,
`:1543` POST) have this shape. The good news is that the replacement is already written and reviewed
elsewhere in the crate: `src/client/subscriptions.rs` contains a complete incremental
`hyper::body::Incoming` → `take_utf8_prefix` → `SseParser::feed` → bound-check reader
(`sse_payload_stream` / `read_next_frame` / `drain_sse_payloads` / `listen_overflow`), built for
`subscriptions/listen` in Phase 113 and hardened by that phase's CR-01/CR-03 review round. This
phase should lift its shape, not invent one. CONTEXT.md's "Reusable Assets" list does not name it,
and it is the single largest de-risking asset available.

On the emitter side the shape is simpler than CONTEXT.md's D-07 assumes in one respect and harder in
another. Simpler: the v1 notification sink **already exists on every non-`initialize` v1 session
request** — `peer_channel::attach_session_backchannel` builds `session_notification_sink` (which
routes through `v1::route_to_session_stream`) and hangs it on the request's `ProtocolContext`, and
`Server::progress_notification_sink` already resolves it. Only the progress-token gate in
`progress_reporter_for` stands between that sink and a log emitter. Harder: `ServerCore` has **no
notification channel of any kind** — `notification_tx` exists only on `Server`, and all four of
`ServerCore`'s `RequestHandlerExtra::new` sites pass `progress_reporter: None` unconditionally. So
D-07's "shared unit called by both roots" is real work on the `ServerCore` side, and its only
possible sink there is the request-scoped `TransportBackchannel`, not a server-wide channel.

**Primary recommendation:** Split the phase into a client wave and an emitter wave, and make the
client wave's FIRST task the 202/`is_success` fix with a request-line-recording fence, because it is
one line, it is invisible in code review, and every downstream client fence is vacuous without it.
Lift `src/client/subscriptions.rs`'s reader shape verbatim for D-01/D-02 rather than writing a second
one. On the emitter, build one `attach_request_log_sink(extra, fallback)` unit mirroring
`attach_request_peer` exactly, and store the v1 level in `V1State`'s existing session map behind a
paired accessor with a `full-v2` twin.

### Pattern 1: The incremental SSE reader (lift this verbatim)

**What:** Read one `hyper` frame, append to a byte buffer, drain the decodable UTF-8 prefix, feed the
parser, check the latching overflow flag, emit completed events.
**When to use:** Both D-01 sites. This is the ONLY correct shape in this crate; there are two live
instances of it already.
**Example:**

```rust
// Source: src/client/subscriptions.rs (read this session) — the `subscriptions/listen`
// reader, built in Phase 113 and hardened by that phase's CR-01/CR-03 round.
struct PayloadState {
    body: hyper::body::Incoming,
    parser: SseParser,
    bytes: Vec<u8>,          // bytes received but not yet decodable as complete UTF-8
    pending: VecDeque<String>,
    done: bool,
}

async fn read_next_frame(state: &mut PayloadState) -> Option<Error> {
    match state.body.frame().await {
        None => { state.done = true; None }                  // end of body
        Some(Err(e)) => { state.done = true; Some(Error::Transport(TransportError::Request(e.to_string()))) }
        Some(Ok(frame)) => {
            if let Some(chunk) = frame.data_ref() {
                state.bytes.extend_from_slice(chunk);
                let text = take_utf8_prefix(&mut state.bytes);
                state.pending.extend(drain_sse_payloads(&mut state.parser, &text));
                if let Some(error) = listen_overflow(&state.parser) {
                    state.done = true;                       // parser DISCARDED bytes — stream is corrupt
                    return Some(error);
                }
            }
            None                                             // a trailers frame carries no data
        }
    }
}
```

The three properties that make it correct, each of which a fresh implementation typically gets wrong:

1. `take_utf8_prefix` runs in the **same** loop iteration as the append, so the residual in `bytes`
   is at most a 3-byte incomplete-character tail. That is what lets the tripwire's ALLOWLIST entry
   say the accumulation is bounded.
2. `overflowed()` is polled **once per chunk**, and the flag **latches**, so a caller cannot miss it.
3. End-of-body drains `pending` **before** the `done` check ends the stream, so trailing complete
   events are not lost.

### Pattern 2: One shared unit called by both dispatch roots

**What:** A free function that takes `RequestHandlerExtra` plus the root's own fallback and returns
the augmented `extra`. Both `ServerCore::attach_peer` and `Server::attach_peer` delegate to it.
**When to use:** D-07's log-sink hoist. The twin roots have a documented history of drift
(`completion/complete` had two dispatchers giving two *different* wrong answers).
**Example:**

```rust
// Source: src/server/core.rs:4514 (read this session) — created by Phase 118.1 for exactly
// this reason. Its rustdoc states the rule: "the precedence rule is the kind of thing two
// roots must never disagree about, and a rule spelled twice is kept in step by a comment
// instead of by the compiler."
#[cfg(not(target_arch = "wasm32"))]
pub(crate) fn attach_request_peer(
    extra: RequestHandlerExtra,
    global: Option<&Arc<dyn PeerHandle>>,
) -> RequestHandlerExtra {
    let request_scoped = extra
        .protocol_context
        .as_ref()
        .and_then(ProtocolContext::transport_backchannel)
        .and_then(TransportBackchannel::peer)
        .cloned();
    if let Some(peer) = request_scoped { return extra.with_peer(peer); }
    if let Some(peer) = global { return extra.with_peer(peer.clone()); }
    extra
}
```

The log-sink twin has the **same** precedence shape: request-scoped `TransportBackchannel::notification_sink`
first, then the root's fallback (`Server`'s `notification_tx`-derived closure; `ServerCore` has none,
so its fallback is a literal `None`).

### Pattern 3: The paired v1 accessor with a constant `full-v2` twin

**What:** A v1-only read is expressed as two `#[cfg]`-selected functions with identical signatures,
so the *call site* carries no `#[cfg]`.
**When to use:** D-03's reconnect cursor and D-11's session log level.
**Example:**

```rust
// Source: src/shared/streamable_http.rs:714-729 (read this session)

    self.config.read().on_resumption_token.clone()
}

/// The null twin: a `full-v2` build has no resumption cursor to report, so
/// the answer is the constant `None`.

#[allow(clippy::unused_self)]
const fn resumption_callback(&self) -> Option<Arc<dyn Fn(String) + Send + Sync>> { None }
```

**The D-03 resolution this unlocks.** `start_sse`'s parameter keeps the same **position and type** on
both feature sets (only its *name* differs: `resumption_token` vs `_ignored_cursor`). So a reconnect
loop can call `self.start_sse(self.reconnect_cursor())` — or, better, an internal
`open_sse_once(cursor)` — with **no new `#[cfg]` at the call site**, provided `reconnect_cursor()` is
itself a paired accessor returning `self.last_event_id()` on v1 and the constant `None` on `full-v2`.
That satisfies both D-03's instruction and the file's own "do not let a second call-site `#[cfg]`
accumulate" rule, and it leaves `apply_resumption_header` as the single existing exception.

**Naming constraint:** the new accessor must NOT contain the substrings `session_id`,
`resumption_token`, or `LAST_EVENT_ID` unless it is inside a `v1-compat` gate — see Pitfall 7.

### Anti-Patterns to Avoid

- **Calling `self.start_sse(..)` from inside the reader task to reconnect.** `start_sse` takes and
  `abort()`s `self.abort_handle` as its very first act, so the task would abort itself. The retry
  loop belongs *inside* the one spawned task.
- **Restarting the SSE stream on every outbound notification.** The dead 202 branch guards on
  `is_notification` (any notification). The TS SDK guards on `isInitializedNotification`
  specifically. Copying the broad predicate would tear down and re-open the session stream on every
  `notifications/cancelled` / `notifications/progress` the client sends.
- **Deleting `collect_body_within_cap` from `streamable_http.rs`.** It still has two callers
  (`collect_capped_body` at `:695`, `jsonrpc_error_envelope` at `:1330`) and a tripwire asserts
  exactly two `.collect().await` sites exist across the scanned scope.
- **Reusing `V2_PROGRESS_QUEUE_CAPACITY`'s drop-newest policy for the client receive queue.** D-04
  forbids it, and the reason is that this queue carries *requests*, not supersedable progress.
- **Emitting a log record before the `tool_authorizer` check.** Every dispatch site calls
  `attach_peer` AFTER authorization, precisely so an unauthorized caller never reaches a handler
  body. The log sink must be attached at the same point, not earlier.
- **Adding a field to `StreamableHttpTransportConfig`.** It is externally constructible with all-`pub`
  fields and three struct-literal rustdoc examples; adding a field trips
  `cargo semver-checks`'s `constructible_struct_adds_field` and forces a MAJOR bump. Every knob goes
  on the transport struct (all-private fields) as an inherent `with_*` method. This is measured, not
  assumed — plan 113-17 recorded it.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|

## Common Pitfalls

### Pitfall 1: Fixing the whole-body read and leaving the GET unsent (THE headline risk)

**What goes wrong:** The plan implements D-01/D-02 perfectly, all the new unit tests pass, and
`deprecated_capabilities_complete_under_both_eras` still reports `no-live-stream`. The phase looks
half-broken and the cause is invisible in a diff of the reader.
**Why it happens:** `start_sse` has exactly two production callers. One (`:1299`) requires the caller
to pass `SendOptions::resumption_cursor`, which nothing does. The other (`:1476`) is inside
`if !response.status().is_success() { … if response.status() == StatusCode::ACCEPTED { … } }` — and
`202` satisfies `is_success()` (`http-1.4.0/src/status.rs:182`: `(200..300).contains(&self.0.get())`).
So the branch is dead code.
**MEASURED:** a probe stood up a recording TCP listener, answered `initialize` with a 200 JSON result
carrying `Mcp-Session-Id: s1` and answered `notifications/initialized` with `202 Accepted`, then drove
a real `pmcp::ClientBuilder::new(StreamableHttpTransport::new(cfg)).build()` through
`client.initialize(...)`. Observed request lines: `["POST / HTTP/1.1", "POST / HTTP/1.1"]`.
**GET count = 0.**
**How to avoid:** Make this the FIRST task of the client wave, with its own fence that asserts a GET
is observed. Mirror the TS SDK: check for the *initialized* notification specifically, not any
notification (`client/streamableHttp.js:370-377`).
**Warning signs:** any client fence that passes without the server ever logging a GET.

### Pitfall 2: Assuming `start_sse` merely mis-parses rather than hangs

**What goes wrong:** A plan treats the whole-body read as "the events arrive late" and writes a fence
with a generous timeout, expecting eventual delivery.
**MEASURED:** against a `text/event-stream` response that delivered one complete
`id: e1 / event: message / data: {…}` frame and then held the socket open, `start_sse(None)` **did not
return within 3 seconds**, and a subsequent `Transport::receive()` **also did not return within 3
seconds**. The already-delivered, already-complete event never reached the channel.
**Why it happens:** `collect_body_within_cap` awaits `Limited::new(body, cap).collect()`, which
completes only at end-of-body. A session stream has no end-of-body.
**How to avoid:** Every client fence must wrap its awaits in `tokio::time::timeout`. An unbounded
await against this defect *hangs* rather than failing, and a hung test reads as a slow test in CI.
This is already the stated reliability doctrine of `tests/http_peer_roundtrip.rs`.

### Pitfall 3: The joint fence has no client-side observation API

**What goes wrong:** D-15.3 asks for "pmcp's own client receives a `notifications/message` over a live
stream." A plan writes it against `pmcp::Client` and discovers there is no way to see a notification.
**Why it happens:** `Client.notification_tx: Option<mpsc::Sender<Notification>>` is initialised to
`None` at all three construction sites (`src/client/mod.rs:406`, `:453`, `:496`), `ClientBuilder` has
no field for it and no setter, and the only other reference is the `Clone` impl at `:5263`. The
forwarding branch at `:3764` is therefore permanently dead.
**How to avoid:** Two options, both legitimate — the planner should choose explicitly:
- **(a)** Assert at the transport level: drive `StreamableHttpTransport::receive()` directly and match
  `TransportMessage::Notification(Notification::Server(ServerNotification::LogMessage(..)))`. Zero new
  public API, satisfies "pmcp on both ends" literally, and keeps the semver verdict trivially clean.
- **(b)** Add a client notification-observation API (e.g. `ClientBuilder::on_notification(..)` or
  `Client::subscribe_notifications() -> Receiver<Notification>`). Additive, but it is *new scope* the
  phase did not plan for, and it needs its own ALWAYS-requirement package (fuzz/property/unit/example).

Recommendation: **(a)** for the fence, and record (b) as a deferred item. A dead `notification_tx`
field is a real DX gap but it is not this phase's residual.

### Pitfall 4: The v2 log vehicle drops records, which contradicts D-09's rationale

**What goes wrong:** D-09 declines a rate limiter because "each log record is the only copy of its
information." But on v2 the sink the record rides is `new_v2_progress_queue()` — an
`mpsc::channel(V2_PROGRESS_QUEUE_CAPACITY)` with `V2_PROGRESS_QUEUE_CAPACITY = 64` and an explicit
**DROP-NEWEST** `try_send` policy (it must be non-blocking: the closure is synchronous and runs on the
handler's task).
**Why it happens:** the v2 vehicle was designed for progress frames, where dropping is correct.
**How to avoid:** Do not silently inherit it. Either (i) state the limitation plainly in the phase
summary and in the sink's rustdoc — "a v2 handler emitting more than 64 notifications in one call
loses the excess, and this is the progress queue's policy, not the emitter's" — or (ii) raise the
capacity for the combined stream. Do NOT make the emitter block; the sink signature is a synchronous
`Fn(Notification)`.
**Also note:** the v2 vehicle is only attached when `v2_multi_frame_eligible` holds — era is V2 **and**
`!config.enable_json_response` **and** the request's `Accept` contains `text/event-stream`. A v2 client
that asked only for JSON gets no log records at all, by design. That is a correct behaviour to
document, not a bug to fix here.

### Pitfall 5: `feed_complete_body` loses both production call sites

**What goes wrong:** After D-01 lands, `SseParser::feed_complete_body` has zero non-test callers.
Under `-D warnings` that is a `dead_code` failure, and the function's own rustdoc explicitly names
both call sites ("`StreamableHttpTransport::post_body` (the POST response) and
`StreamableHttpTransport::start_sse` (the GET SSE stream)") as the discharge of its byte-cap
precondition. That prose becomes false the moment the plan lands.
**How to avoid:** Decide in the plan, don't discover it at build time. Either delete
`feed_complete_body` (and its `#[test] feed_complete_body_bypasses_the_bound` at
`src/shared/sse_parser.rs:1630`, plus the ALLOWLIST justification prose in
`tests/v2_bounded_reads_tripwire.rs` that cites it), or keep it `#[cfg(test)]`. Deleting is cleaner
and is a strict reduction in attack surface — the rustdoc itself calls a public unbounded parser
entry point "an attractive nuisance."
**Warning sign:** a plan that edits `streamable_http.rs` without touching `sse_parser.rs`'s rustdoc.

### Pitfall 6: The bounded-reads tripwire will fire on the new accumulation site

**What goes wrong:** `tests/v2_bounded_reads_tripwire.rs` scans `src/shared/`, `src/server/auth/`
plus four named files for `extend_from_slice(`, `push_str(`, `.extend(`, `.append(` and reports
"NEW accumulation site(s)" for any `(path, needle)` pair not in `ALLOWLIST`, or "COUNT ROSE" if an
existing entry's count is exceeded. **`src/shared/streamable_http.rs` has NO entry today.** The
incremental reader adds at least `bytes.extend_from_slice(chunk)` and probably a `.extend(`.
**How to avoid:** Plan the ALLOWLIST entry as part of the same task, with a real justification —
`every_whole_body_exemption_carries_a_substantive_justification` enforces a minimum length, and
`report_dead_entry` fails in the other direction if the count is set too high. Model the wording on
the existing `src/client/subscriptions.rs` `extend_from_slice(` entry, which is the same mechanism.
**Second tripwire in the same file:** `the_two_known_capped_whole_body_reads_are_found_and_classified_bounded`
asserts **exactly 2** shipped `.collect().await` sites, one in `src/shared/http.rs` and one in
`src/shared/streamable_http.rs`, both `Limited::new(`-wrapped. Removing the *call sites* is fine —
the count is over the `collect_body_within_cap` **helper bodies**, which must stay (they still serve
`collect_capped_body` and `jsonrpc_error_envelope`).

### Pitfall 7: The v1 severability tripwire governs identifier NAMES in the client transport

**What goes wrong:** A new helper named `reconnect_resumption_token` or `sse_session_id` lands
outside a `#[cfg(feature = "v1-compat")]` region and `the_client_transport_carries_no_ungated_session_state`
turns red on a token match, not on a behaviour.
**Why it happens:** `tests/v1_severability_tripwire.rs` scans `src/shared/streamable_http.rs` for
`CLIENT_V1_TOKENS = ["session_id", "resumption_token", "LAST_EVENT_ID"]` and requires every
occurrence outside `#[cfg(test)]` to sit inside a `v1-compat` gate. It also enforces
`MIN_CLIENT_STRIPPED_BYTES = 20_000` and `MIN_CLIENT_V1_OCCURRENCES = 20` as anti-vacuity floors.
**How to avoid:** name the paired reconnect accessor with none of those substrings —
`reconnect_cursor` is safe, `last_event_id` (lowercase) is not a tracked token.
**The null-twin half:** if D-11 adds anything to `src/server/streamable_http_server/v1_session.rs`,
`v1_session_off.rs` must gain a signature-identical constant-answering twin, and that twin must
contain none of `FORBIDDEN_STATE_TYPES` (`HashMap`, `BTreeMap`, `RwLock`, `Mutex`, `DashMap`,
`SessionInfo`, `InMemoryEventStore`, `Arc<dyn EventStore`) nor any of `FORBIDDEN_OPERATIONS`
(`.read()`, `.write()`, `.lock()`, `.insert(`, `.remove(`, `.entry(`, `.get_mut(`, `.contains_key(`,
`tokio::spawn`, `LAST_EVENT_ID`, `MCP_SESSION_ID`, `.headers()`, `headers.get`). `V1State` in the twin
must remain a **unit** struct (`struct V1State;`), and
`the_v1_null_twin_declares_nothing_the_real_module_does_not` fails if the twin declares a name the
real module lacks.

### Pitfall 8: `logging/setLevel` must keep returning a literal empty object

**What goes wrong:** D-13's "store and honour on v1" arm returns the stored level, or `null`, or an
acknowledgement object, and the currently-green `2025-11-25:logging-set-level` scenario goes red —
which would *reduce* the blocking surface the gate claims.
**MEASURED** from the pinned suite bundle: the scenario does
`const r = await n.request('logging/setLevel', { level: 'info' })` and then
`r && Object.keys(r).length > 0 && i.push('Expected empty object {} response')`. **Any non-empty
object is a FAILURE.**
**How to avoid:** the v1 arm stores the level and still answers `Ok(json!({}))`. That is a pure
addition to the existing behaviour, which is why D-13 is low-risk.

### Pitfall 9: The `era_matrix` v1 arm asserts the level is NOT honoured

**What goes wrong:** D-11 makes the v1 session level real, someone updates
`crates/pmcp-team-servers/src/conformance/era_target.rs::observed_log_level` to report it, and
`v1_capability_arm` fails — because that arm calls `client.set_logging_level(Debug)` first and then
asserts `levelSource == "server-default"` **and** `observedLevel != "debug"`.
**Why it happens:** the era target's `observed_log_level` currently reads the v2 `_meta` key only,
gated on `extra.era() == Some(Era::V2)`, and falls back to `("info", "server-default")`. The
assertion exists to make baseline row ERA-12 (`ignored` on v1 → `honored` on v2) observable.
**How to avoid:** decide explicitly. Either leave `era_target` alone (the test keeps passing and the
new v1 level is proven by a different fence), or update `era_target` **and** `era_matrix`'s v1 arm
together, introducing a third `levelSource` value (e.g. `v1-set-level`) so the ERA-12 contrast is
preserved rather than erased. Do not change one without the other.

### Pitfall 10: The v1 leg cannot join `FULLY_SCORED_GREEN_REVISIONS` without splitting the floor

**What goes wrong:** D-16's gate hardening adds `2025-11-25` to `FULLY_SCORED_GREEN_REVISIONS` in
`scripts/run-conformance-suite.sh` and the run fails with *"the '2025-11-25' run had only 30 scored
scenario(s); the floor is 37."*
**Why it happens:** `MIN_SCORED_SCENARIOS_PER_FULLY_GREEN_REVISION = 37` (line 265) is a **single**
constant applied per-revision at line 859. 37 is the *v2* measurement; the v1 leg has 30 scored
scenarios (29 in `BLOCKING_GREEN_SCENARIOS` + `tools-call-with-logging`).
**How to avoid:** make the floor per-revision (a lookup keyed by revision, or a second constant
`MIN_SCORED_SCENARIOS_V1=30`) in the same edit. Lowering the shared constant to 30 would silently
weaken the v2 guard — do not do that. The script's own comments already anticipate this edit
("when it lands, MOVE 2025-11-25 here and delete its entries from BLOCKING_GREEN_SCENARIOS below —
that is a widening, not a rewrite"), but they do not mention the floor.

### Pitfall 11: The example fixture still uses `tracing`, not MCP

**What goes wrong:** `extra.log(..)` ships, the SDK is correct, and `tools-call-with-logging` stays
red because the fixture never calls it.
**Why it happens:** `examples/s54_v2_dual_conformance.rs:870` handles
`"test_tool_with_logging" | "test_logging_tool"` by emitting three `tracing::info!` lines with 50 ms
spacing. `tracing` records go to the process's subscriber, never to the MCP wire.
**MEASURED** requirement from the pinned suite: the scenario calls `setLoggingLevel('debug')`, then
`callTool({ name: 'test_tool_with_logging', arguments: {} })`, then sleeps **200 ms**, then requires
**at least 1** notification (`length === 0` ⇒ "No log notifications received") and **at least 3**
(`length < 3` ⇒ "Expected at least 3 log messages, got N").
**How to avoid:** rewrite the arm to call `extra.log(..)` three times. Keep the ≥3 count and keep the
inter-record spacing well inside the 200 ms budget (3 × 50 ms = 150 ms is already tight; the whole
call plus 200 ms must contain all three). The example already declares
`capabilities.logging = Some(LoggingCapabilities::default())` at `:1729`, so no capability change is
needed for v1.

### Pitfall 12: Attaching the sink at the wrong point in dispatch

**What goes wrong:** a handler that failed `tool_authorizer` still gets a live sink, or the sink is
attached before `ProtocolContext` is moved into `extra`.
**Why it happens:** `ServerCore::handle_request`'s tool arm moves `protocol_context` into
`RequestHandlerExtra::with_protocol_context(protocol_context)` at `:867`, and several values
(`create_trigger`, `validation_era`) are deliberately captured *before* that move. The log sink read
must therefore either happen before the move or read back through `extra.protocol_context` (which is
what `attach_request_peer` does).
**How to avoid:** copy `attach_request_peer`'s shape exactly — read from `extra.protocol_context`
*after* construction, and call it at the same site, which is already after the authorizer check.

**Recommended `extra.log` shape** (Claude's-discretion item, research's pick):

```rust
/// Emit one MCP `notifications/message` log record for this request.
pub fn log(&self, level: LoggingLevel, message: impl Into<String>) -> crate::Result<()>;

/// The same, carrying the spec's arbitrary JSON `data` payload.
pub fn log_with_data(&self, level: LoggingLevel, message: impl Into<String>, data: serde_json::Value)
    -> crate::Result<()>;

// Convenience wrappers, thin: debug/info/notice/warning/error/critical/alert/emergency.
pub fn log_info(&self, message: impl Into<String>) -> crate::Result<()>;
pub fn log_warn(&self, message: impl Into<String>) -> crate::Result<()>;
pub fn log_error(&self, message: impl Into<String>) -> crate::Result<()>;
```

Rationale for each choice:
- **`LoggingLevel` enum primary, wrappers secondary.** The enum is the wire type; wrappers are ergonomic
  sugar. Shipping only wrappers would make the 8-level syslog set unreachable.
- **Synchronous, not `async`.** The sink is `Arc<dyn Fn(Notification) + Send + Sync>` — a synchronous
  closure. `report_progress` is `async` only because the `ProgressReporter` *trait* is; there is no
  trait here (D-06), so `async` would buy nothing and would force every logging call site into an
  `.await`. **⚠ Cross-check against D-04:** if the planner later wants the emitter to apply
  backpressure it would need `async`; the server-side sinks today are both non-blocking
  (`try_send` / best-effort), so synchronous is correct for what exists.
- **`Result<()>`, not `()`.** Matches `report_progress` and leaves room for a future "sink refused"
  signal without a breaking change.
- **`logger` defaults to `None`.** `LogMessageParams::new` already defaults it, and a synthesised value
  (e.g. the tool name) would be a guess. Expose `with_logger` through `log_with_data`'s sibling if a
  caller needs it.
- **`data` is `serde_json::Value` and optional.** The spec's field is arbitrary JSON; forcing `String`
  would make structured logging impossible and forcing `Value` on every call would be noise.

## Open Questions

1. **Where is the v1 `logging/setLevel` level captured?**
   - What we know: the method arrives as a JSON-RPC request; session identity is known at the HTTP
     layer (`ServerState` + the request's `Mcp-Session-Id`); the v2 retirement is already enforced at
     the HTTP layer via `V2_RETIRED_METHODS`; and `ProtocolContext` is already threaded into dispatch.
   - What's unclear: whether to intercept at the HTTP layer (symmetric with retirement, but adds a
     second method-string special case to the ingress) or to reach session state through the context
     from the `Server` dispatch arm (symmetric with D-13, but the arm would need a handle to `V1State`).
   - Recommendation: capture at the HTTP layer next to the retirement table, and thread the *resolved*
     level onto the request's `ProtocolContext`/`RequestHandlerExtra` so the dispatch arm only has to
     answer `Ok(json!({}))`. That keeps `V1State` reachable from the one layer that already owns it,
     and keeps the filter read O(1) at emit time instead of a lock per record. CONTEXT.md explicitly
     leaves this to the planner.

2. **Does the reconnect loop re-issue `initialize`?**
   - What we know: on v1 the session id is carried in a header the transport already stores; a
     reconnect GET with `Mcp-Session-Id` + `Last-Event-ID` should resume the same session.
   - What's unclear: what the server does if the session was reaped while the client was disconnected
     (404? new session?) and whether the client should surface that or re-handshake.
   - Recommendation: reconnect only re-issues the GET. A 404/expired-session response ends the retry
     loop with a named error rather than silently re-handshaking — a silent re-handshake would mint a
     new session id and orphan every in-flight correlation.

3. **Should `extra.log(..)` be `async`?**
   - What we know: both server-side sinks are synchronous, non-blocking closures
     (`Fn(Notification)`); `route_to_session_stream` uses an unbounded `send`, `new_v2_progress_queue`
     uses `try_send` with drop-newest.
   - What's unclear: whether a future backpressuring sink would force a breaking change.
   - Recommendation: ship synchronous. If backpressure is ever needed, add an `async fn log_await(..)`
     alongside — additive — rather than pre-emptively making every call site `.await`.

4. **Which fence proves D-15.3, and at what layer?** See Pitfall 3. Recommendation: transport-level,
   with the `Client`-level notification API deferred.

5. **Does the era target change for D-11?** See Pitfall 9. Recommendation: leave `era_target` alone
   in this phase and prove the v1 level with a dedicated in-tree fence, so `era_matrix`'s ERA-12
   contrast is not disturbed while the phase is also moving `DEP_STATUS_NO_LIVE_STREAM`.

6. **Is `ServerCapabilities.logging` required for the emitter to fire?** (Claude's discretion,
   undiscussed.) The example already declares it (`:1729`). Recommendation: do **not** gate emission
   on the declaration — the sink is per-request and the capability is advisory; gating would make a
   correctly-plumbed server silently mute. Document that servers SHOULD declare it, and consider a
   `debug_assert`/`tracing::warn!`-once if a record is emitted by a server that did not.

### Known Threat Patterns for a long-lived client SSE reader

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Peer streams unterminated `data:` lines forever, growing client heap | Denial of Service | `SseParser::feed`'s unconditional retained-state-plus-chunk pre-check under `max_collected_body_bytes` (D-02); latching `overflowed()` polled once per chunk; end the stream (T-113-86) |
| Peer streams valid frames faster than the consumer drains, growing the channel | Denial of Service | D-04's bounded `mpsc::channel(N)` + reader awaits capacity ⇒ real TCP backpressure. Never drop — the queue carries requests |
| Peer sends a malformed frame to make the client silently skip a server→client request, hanging both ends | Denial of Service / Tampering | D-05: end the stream with a named error rather than `if let Ok(..)`-dropping |
| Peer's frame content is echoed into the client's logs via an error `Display` | Information Disclosure / log injection | Bound and/or omit the echo, per `MAX_ECHOED_FRAME` and the `collected_body_over_cap` "echo no body content" rule |
| Multi-byte UTF-8 split across a TCP segment corrupted to U+FFFD | Tampering | `take_utf8_prefix`, never per-chunk `from_utf8_lossy` |
| Reconnect storm against a server that keeps closing the stream | Denial of Service (self-inflicted, against the server) | Bounded retry count + exponential backoff with a max delay (D-03) |
| A peer-influenced `Last-Event-ID` written onto the wire on a `full-v2` build | Tampering | Already controlled: `LAST_EVENT_ID` and its single reader are co-gated under `v1-compat` and the tripwire enforces it (T-117-53/54) |
| Client A's `logging/setLevel` changing client B's filtering | Tampering / Information Disclosure | D-11: per-session storage in `V1State.sessions`, never the shared server lock |
| A handler floods a client that never asked for verbose logs | Denial of Service | D-12's `info` default; `debug` and finer suppressed until requested |

**Confidence:** HIGH

### Key Findings

1. **A third, unnamed client defect exists and is the load-bearing one.** `start_sse` is **never
   called** on the normal handshake path — the `202 Accepted` branch that should open the GET SSE
   stream sits inside `if !response.status().is_success()` and `202` **is** a success status.
   MEASURED with a live probe: two POSTs, **zero GETs**. Fixing only D-01/D-02 would leave the
   era_matrix fence reporting `no-live-stream` unchanged.
2. **The named defect is a hang, not a delay.** MEASURED: `start_sse` against a never-ending
   `text/event-stream` that had already delivered one complete event **did not return within 3 s**,
   and `receive()` never yielded the event. Every client fence must use `tokio::time::timeout`.
3. **The incremental reader is already written and reviewed.** `src/client/subscriptions.rs`
   (`sse_payload_stream` / `read_next_frame` / `drain_sse_payloads` / `listen_overflow`) is a complete
   `hyper::body::Incoming` → `take_utf8_prefix` → `SseParser::feed` → bound-check loop, split
   precisely to stay under the cog-25 budget. Lift its shape; do not write a second one. CONTEXT.md's
   reusable-assets list does not name it.
4. **`ServerCore` has no notification channel at all** (`notification_tx` is a `Server`-only field;
   all four `ServerCore` `RequestHandlerExtra::new` sites pass `progress_reporter: None`). Its only
   possible sink is the request-scoped `TransportBackchannel`. Conversely, the **v1 sink already
   exists** on every non-`initialize` v1 session request — only `progress_reporter_for`'s
   progress-token gate stands between it and a log emitter.
5. **`pmcp::Client` has no notification-observation API** — `notification_tx` is always `None` and
   `ClientBuilder` has no setter, so the forwarding branch is dead. D-15.3's joint fence must either
   assert at the `Transport::receive()` level (recommended) or add new public API.
6. **Five hard constraints measured from external referees and in-tree tripwires:** the suite's
   `logging-set-level` requires a **literal `{}`** response (so D-13 must store-and-still-return-`{}`);
   `tools-call-with-logging` needs **≥3** records within a 200 ms window after `setLoggingLevel('debug')`;
   `MIN_SCORED_SCENARIOS_PER_FULLY_GREEN_REVISION=37` blocks the 30-scenario v1 leg from joining
   `FULLY_SCORED_GREEN_REVISIONS` unless the floor becomes per-revision; the bounded-reads tripwire
   will fire on the new accumulation site in `streamable_http.rs` (no ALLOWLIST entry exists today);
   and the v1 severability tripwire governs identifier **names** (`session_id`, `resumption_token`,
   `LAST_EVENT_ID`) in the client transport.
