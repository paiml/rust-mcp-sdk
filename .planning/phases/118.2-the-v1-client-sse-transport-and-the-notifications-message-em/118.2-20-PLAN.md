<objective>
Close **BLOCKER 2**: the id-mismatch discard loop holds the transport write lock across an unbounded
`.receive().await`, so one mis-addressed frame wedges the entire `Client` — and the safety net the
record claims bounds it does not exist.

Purpose. `118.2-15` added response-id correlation to `Client::dispatch_request`. The correlation
itself is right. Its cost is mis-booked, in two compounding ways:

1. **The statement shape.** `let response_message = self.transport.write().await.receive().await?;`
   holds the `RwLockWriteGuard` temporary across `.receive().await`, because the guard lives to the
   end of the `let` STATEMENT. The mismatch-discard loop `continue`s rather than returning, so it
   re-takes and re-holds that lock indefinitely on every mismatched frame — and every other `send`,
   `call_tool` and `close` on that `Client` blocks behind it. One frame with a re-typed id, from a
   hostile peer or a merely lenient one, takes the client down with no error, no log after the first
   `warn!`, and no recovery.
2. **The premise.** The in-code comment at the discard site and the `T-118.2-15-03` ledger entry both
   assert the wait has a ceiling supplied by the caller's own request timeout. It does not.
   `src/client/mod.rs` contains ZERO occurrences of `tokio::time::timeout`, and
   `RequestOptions::timeout` (`src/shared/protocol.rs:29`) is never read by `Client`. The wait is
   unbounded, and the disposition that booked it as bounded is a documentation-of-record error the
   verification classified as a Blocker in its own right.

The project's own fence records the symptom rather than catching it: fence 17 asserts the call is
STILL WAITING at `MISMATCH_BOUND` and treats that as its pass condition.

Output: a bounded, lock-releasing discard path with a capped discard count and two named failures, two
new fences — one per half, because one fence cannot stand for both — a tightened fence 17, and a
corrected comment of record.

**Locked decisions this plan preserves rather than revisits.** The correlation check itself
(`118.2-15`, CR-02 half 2) stays exactly as it is: typed structural `RequestId` equality, a
mismatched frame DISCARDED rather than re-queued because a `Transport` consumer holds no producer
handle, and nothing removed from `active_requests` on the discard path so the WR-04 single-exit
cleanup remains the only other removal site. What changes is only how LONG that discard is allowed to
run and how much of the `Client` it is allowed to hold while running. The send-then-receive ordering
`WINDOWS.md` entry 6 records is deliberately untouched.
</objective>

<!-- Contracts the executor needs, so it does not have to re-derive them. -->

**`dispatch_request`'s shape.** It registers the id in `active_requests`, builds a
`MiddlewareContext`, and runs EVERYTHING else inside one inner `async` block whose result is awaited
and then funnelled through a single WR-04 exit cleanup that removes the pending entry on any `Err`.
The receive loop lives inside that inner block and matches three `TransportMessage` variants:
`Response` (correlate, then return), `Notification` (forward and continue) and `Request` (answer from
the host registry, send the reply, and continue). Any new error must be returned from inside that
inner block so the single-exit cleanup still runs — do not add a second cleanup site.

**Cancel-safety, which is what makes a bounded receive legal here.**
`StreamableHttpTransport::receive()` subscribes to a `watch` generation, locks its receiver, and
selects over `mpsc::Receiver::recv()`, which tokio documents as cancel-safe: dropping the future
loses no message. That is the transport this phase is about. It is NOT true of every `Transport`
implementation, which is exactly why the slice is confined to the post-mismatch path.

**Errors available without a public-API event.** `Error::timeout(duration_ms: u64)`
(`src/error/mod.rs:356`) constructs the existing `Error::Timeout(u64)` variant, which already maps to
`ErrorCode::REQUEST_TIMEOUT`. `TransportError::InvalidMessage(String)` (`src/error/mod.rs:268`)
already exists and renders as `Invalid message format: {0}`. Both are reachable today; neither
addition is needed and neither may be added.

**The lock the fence must contend for.** `Client::send_notification` is
`self.transport.write().await.send(message).await` — the SAME `RwLock<T>` `dispatch_request` holds.
`Client::cancel_request(&self, &RequestId)` reaches it with no capability assertion and no response
expected, and the recording harness answers a notification POST with a bare `202`. That makes it the
cleanest second operation for the lock fence: it needs the lock, it takes `&self` so it can run
concurrently with a `call_tool` on the same `Client`, and it puts no `Response` frame on the queue to
confuse the discard loop.

**The harness, after plan 118.2-19.** `answer_the_next_call_with_a_mismatched_id()` arms exactly ONE
mis-addressed answer, consumed on use, and `MISMATCHED_CALL_ID` is a literal no pmcp client request
can produce. `calls_observed(&server)` counts `tools/call` POST bodies and is the vacuity guard both
existing correlation fences use. Plan 19 added `answer_calls_with_sse()`, `call_answer_body(..)` and
`serve_post_sse_answer(..)`; this plan does not need them but must not break them.

**Fence 17's known hole.** `118.2-REVIEW-closure.md`'s WR-05 records that fence 17's `match outcome`
treats both `Err(_still_waiting)` and `Ok(Err(_not_an_answer))` as passing, panicking only on
`Ok(Ok(_))` — so a future regression in which `call_tool` fails early keeps the fence green while the
correlation branch never executes. Post-fix the intended outcome at `MISMATCH_BOUND` (2 s) is still
`Err(_still_waiting)`, because this plan's ceiling is well above 2 s.
</interfaces>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| remote MCP server → every operation on one `pmcp::Client` | a peer that emits one response frame with the wrong id decides, today, whether that client ever does anything again |
| one caller of a shared `Client` → every other caller of it | the transport write lock is the shared resource; a caller stuck in a discard loop holds it |
| a documentation-of-record claim → an operator's risk assessment | a ledger entry booking an unbounded cost as bounded causes a real risk to be treated as already mitigated |
