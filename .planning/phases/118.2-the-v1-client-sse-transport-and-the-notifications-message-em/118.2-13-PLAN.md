<objective>
Make every `notifications/message` frame pmcp emits carry the `data` member the MCP schema requires,
by defaulting `data` to the message string when the caller did not supply one (decision **Option A**,
taken by the user at plan 118.2-11's blocking-human checkpoint on 2026-08-17).

Purpose: plan 118.2-11 MEASURED the official suite at the held `0.2.0-alpha.11` pin and found the
`2025-11-25` leg had regressed from `72 passed, 2 failed` to `71 passed, 3 failed`, entirely on one
scenario — `tools-call-with-logging`, 1/1 to 0/2. Root cause, reproduced directly against the pinned
bundle:

```
{level:'info', message:'Tool execution started'}  -> parse ok: false
    invalid_type at params.data: expected nonoptional, received undefined
{level:'info', data:'Tool execution started'}     -> parse ok: true
```

`schema/vendored/core-2026-07-28/schema.ts:2031-2044` declares `LoggingMessageNotificationParams` as
`level`, optional `logger`, and **`data: unknown` REQUIRED, with no `message` member at all**. pmcp's
`LogMessageParams` (`src/types/notifications.rs:161-172`) is the mirror image: `message: String`
required, `data: Option<Value>` skipped when `None`. `extra.log(..)` passes `None`, so the frame ships
without `data`. The reference client's `LoggingMessageNotificationParamsSchema` uses `z.unknown()`,
which is **non-optional under the bundled zod v4**, so it drops the frames on the floor.

**Why this is a fix and not a workaround.** The suite's own wire validator (`WireSchemaValid`, which
newly FAILS with `messagesValidated: 10` and quotes all three frames as
`LoggingMessageNotification/params: must have required property 'data'`) is independent proof that the
frames genuinely reach the socket. This phase's emitter works. Only the shape is wrong, and only for
the `extra.log` path that supplies no data.

**This refutes plan 118.2-08's premise, on the record.** Plan 08 concluded that no suite scenario
validates an emitted notification's params, and on that basis DECLARED the divergence rather than
fixing it. `WireSchemaValid` is not a scenario — it is a check that runs *inside* scenarios and
validates every frame the implementation sends. Plan 08's fence held over the scenarios it enumerated
and missed the check that adjudicates. Do not treat plan 08's "do not change this" note as binding;
it was written on a premise measurement has since falsified.

**Scope discipline — this is Option A, not C.** Do NOT remove `message` from `LogMessageParams`, do
NOT make `data` non-optional in the Rust type, and do NOT touch `LoggingLevel`, the sink, or the level
resolver. The Rust API must come out of this plan byte-compatible; the whole point of Option A over
Option C is that it buys conformance with no semver event. `message` stays on the wire as a pmcp
extension — the reference client strips unknown members, it does not reject them (measured above: the
`data`-bearing frame parses `ok: true` even though pmcp will also send `message`).

**Do NOT touch the gate.** `scripts/run-conformance-suite.sh`, `conformance/package.json` and the
`BLOCKING_GREEN_SCENARIOS` list belong to plan 118.2-11, which resumes its tasks 2-3 after you.
D-21 (no allowlist, gate scoped to passing surfaces) is intact and stays that way. Re-measuring the
suite is plan 11's job, not yours — your job is to make the frame right and fence it in-tree.
</objective>
