# Phase 118.2 Plan 03: the SECOND collect site — the POST response that answers `text/event-stream`

The pmcp client now reads a `text/event-stream` POST response as a live stream instead of a
body it waits to end. A notification carried on such a response reaches `receive()` before
the result frame; a **server-to-client request** carried on it is parsed and ANSWERED while
the stream is still open — the in-tool elicitation deadlock D-01 named; and the reader
terminates with its transport rather than outliving it. `SseParser::feed_complete_body`,
which lost its last production caller in the same edit, is gone along with all three of its
co-located dependants.

## One reader, two sites

`start_sse`'s reader loop was **extracted** into a new inherent method rather than copied:

```rust
fn spawn_sse_reader(&self, body: hyper::body::Incoming) -> tokio::task::JoinHandle<()>
```

Everything the two sites must agree on lives inside it — the parser bound (D-02, the
transport's `max_collected_body_bytes`), the resumption-cursor write, the message-event
filter, the D-02/D-05 terminal-error taxonomy, and D-04's await-capacity delivery. Measured:

```
$ grep -n 'read_next_sse_frame' src/shared/streamable_http.rs
1183:  if let Some(error) = read_next_sse_frame(&mut state).await   <- the ONE call site
2030:  async fn read_next_sse_frame(...)                            <- the ONE definition
2090:  /// [`read_next_sse_frame`] ...                              <- a doc link

$ grep -n 'spawn_sse_reader' src/shared/streamable_http.rs   (call sites only)
1137:  let handle = self.spawn_sse_reader(response.into_body());   <- GET session stream
1718:  let _ = self.spawn_sse_reader(response.into_body());        <- POST response
```

One definition, one loop, two consumers. `SseReadState::new` likewise appears exactly once.

The POST branch is decided **before** the collect, which is the whole point:

```rust
if content_type.contains(TEXT_EVENT_STREAM) {
    let _ = self.spawn_sse_reader(response.into_body());
    return Ok(());
}
let body_bytes = Self::collect_body_within_cap(response, self.max_collected_body_bytes).await?;
```

The JSON and non-SSE branches are untouched and still go through `collect_body_within_cap`.

### The reader is DETACHED, and why

The GET reader's handle goes into `self.abort_handle`; the POST reader's does not. That slot
is the session stream's, and `start_sse` aborts whatever it holds as its FIRST act — parking
a call's own POST reader there would let an unrelated re-open tear down a live tool call. The
POST reader's lifetime is the send-failure rule instead (118.2-01 task-2 rule 3): a failed
`sender.send` means the `Receiver` was dropped, so the reader RETURNS, dropping the response
body and closing the connection. Fence 10 measures exactly that, at the server.

There is deliberately no `Drop` impl to lean on: `StreamableHttpTransport` is `Clone` and
shares its abort handle, so one clone's drop would kill the original's stream.

### Not routed through `post_streaming` — the plan asked for the reason

The plan offered routing this branch through `post_streaming` "if the restructure makes that
natural". It does not, and the reason is not aesthetic: by the time the content type is
known, `post_body` has already run `post_once` (including the single-shot 401 retry) and
`process_response_headers`, and it holds the response. `post_streaming` is exactly
`post_once` + `process_response_headers`, so calling it here would issue a **second POST** —
a duplicate JSON-RPC frame on the wire. The 202 arm and the non-2xx / error-envelope arms
also sit between the two, so there is no earlier point at which the branch is decidable.
What was reused instead is `post_streaming`'s *contract*, quoted below.

## The streaming response-middleware contract, as stated in `post_body`'s rustdoc

> # A `text/event-stream` answer is a STREAM, not a body
>
> When the response's `Content-Type` is `text/event-stream` this method hands the LIVE body
> to [`Self::spawn_sse_reader`] and returns as soon as the stream is open, rather than
> collecting the body first. Such a response stays open for the whole call and can carry
> notifications **and server-to-client requests** before its result frame; collecting it
> whole would deliver every one of them only after the call ended, and an in-tool elicitation
> over a POST stream would deadlock outright — the client cannot answer a request it has not
> parsed yet (Phase 118.2, D-01).
>
> On that path the HTTP response-**BODY** middleware chain is deliberately NOT run, exactly
> as [`Self::post_streaming`] states for the `subscriptions/listen` body: the chain processes
> a complete `Vec<u8>` body, and a stream has none by construction.
> [`Self::process_response_headers`] still runs, so HEADER-level middleware behaviour is
> unchanged. A deployment with a body-rewriting middleware sees it applied to JSON POST
> responses and not to a streaming one.

Same decision, same precedent, same wording as the GET path took in 118.2-01. T-118.2-03-06
is `accept`, and this rustdoc is what turns it from a discovery into a stated contract.

### What the three fences actually assert

1. **`a_notification_on_a_post_sse_body_arrives_before_the_result_frame`** — the send returns as
   soon as the stream is open; a pushed progress notification reaches `receive()` within `BOUND`
   while `open_post_connections() >= 1`; and ONLY THEN is the result frame pushed and observed.
   "Before" is an ordering fact, not a timing coincidence.
2. **`a_server_to_client_request_on_a_post_sse_body_is_parsed_before_the_result_frame`** — a real
   `pmcp::Client` issues `ping()`, the harness answers that POST with an open SSE stream and
   pushes a server-to-client `ping` REQUEST on it. The fence asserts the client POSTs a JSON-RPC
   **result** for that id — read out of `RecordingServer::post_bodies()`, i.e. the client's actual
   answer on the wire — while the original stream is still open. Only then is the result frame
   pushed and the call awaited to `Ok`. `ping` is the vehicle because `Client`'s host dispatch
   answers an inbound ping with an empty-object success and no registered handler, so the fence
   measures the transport's parse-and-deliver path rather than a handler registration.
3. **`a_post_sse_reader_terminates_when_its_owning_transport_is_dropped`** — every transport clone
   is dropped, then ONE frame is pushed purely so the reader HAS a next send to fail. The fence
   asserts a **server-observed** connection close (`open_post_connections() == 0`, from the
   harness's own accept-side counter), then holds a `QUIET` window and asserts both the counter
   and `frames_written()` are unmoved. A reader that ignores its send result keeps the body — and
   therefore the connection — alive, and this fence stays red.

## Harness additions (plan 04 extends these)

`RecordingServer` gained: `answer_post_with_sse(method)`, `post_bodies()`,
`open_post_connections()`, `push_post_frame(frame)`, a second frame channel, and a second
open-connection counter. `serve_get`'s body was factored into `serve_sse_body(reader, write,
shared, open, source)` so the GET and POST streams are the same code on different counters and
sources — deliberately separate sources, because fence 9 has a GET session stream and a POST
stream open at the same time and a shared source would deliver each frame to whichever polled
first.

POST bodies are recorded **parsed**, and headers still are not. The module's
"never a header, so a harness change cannot leak an `Authorization` header into a CI log" rule
is intact and restated at the new field: a POST body here is a JSON-RPC frame the test itself
caused the client to emit, never a credential.

  `post_response_at_the_cap_parses_normally`, `raising_the_cap_admits_a_body_the_lower_one_refuses`
  and `an_over_cap_v2_error_envelope_falls_back_to_the_status_error` passed untouched.

### 2. [Rule 2 — the plan said "reuse the reader"; there was no reader to reuse]

- **Found during:** Task 2.
- **Issue:** 118.2-01 left the reader LOOP inline in `start_sse`; only the four free functions
  under it were shared. Handing the POST body to "the same reader" therefore meant either
  duplicating a 20-line loop — two copies of the terminal-error rules, exactly the drift the
  four-way split exists to prevent — or extracting it.
- **Fix:** extracted `StreamableHttpTransport::spawn_sse_reader`. The plan's success criterion
  ("ONE reader; a single definition with two consumers") is met at the loop level, not merely at
  the helper level. `start_sse` is otherwise unchanged and still owns the abort-handle bookkeeping.
- **Files:** `src/shared/streamable_http.rs` · **Commit:** `8b19602d`

### 3. [Rule 2 — a lifetime decision the plan did not state] the detached POST handle

- **Found during:** Task 2.
- **Issue:** the plan says to hand the body to the shared reader but not what to do with the join
  handle. Storing it in `self.abort_handle` (the obvious symmetry with `start_sse`) is an active
  bug: `start_sse` aborts that slot as its first act, so a `notifications/initialized` arriving
  during a tool call would kill that call's own response stream — and conversely a POST reader
  would silently displace the session stream's handle, leaking it.
- **Fix:** the POST reader is detached, with the reason written at the site and in
  `spawn_sse_reader`'s rustdoc. Its lifetime is the send-failure rule, which fence 10 measures
  directly.
- **Files:** `src/shared/streamable_http.rs` · **Commit:** `8b19602d`

### 4. [Recorded, no change] nextest reports one POST-stream test as `LEAK`

- **Found during:** Task 2.
- **Issue:** `post_response_over_the_parser_bound_ends_the_stream_with_a_named_error` is
