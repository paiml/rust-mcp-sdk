Purpose: real deployments idle-drop long-lived streams routinely (ALB ~60 s, Cloudflare, API
gateways). Without reconnect, this phase's fix silently regresses to `NO_LIVE_STREAM` the first time a
proxy blinks — the exact symptom it exists to remove.

Three hard constraints the implementation must resolve rather than discover:
- **`start_sse` aborts `self.abort_handle` as its very first act** (`:930-936`), so a recursive
  `self.start_sse(..)` call from inside the reader task would abort the task making the call. The
  retry loop lives INSIDE the one spawned task.
- `apply_resumption_header` is `#[cfg(feature = "v1-compat")]` and is **the only `#[cfg]` at a call
  site in this file** — the file's own comment says so and asks that a second one not accumulate. The
  reconnect cursor therefore goes through a PAIRED ACCESSOR with a constant `full-v2` answer, not a
  second call-site `#[cfg]`.
- **The spawned task cannot borrow `&self`** (cross-AI review finding 4, CONFIRMED). Plan 01's reader
  task receives only a cloned sender, resumption callback and last-event-id. Reissuing an
  authenticated, middleware-aware GET needs the hyper client, the URL, the config and the
  request-building path, and a `&self` helper is not callable from a `'static` task. Task 2 therefore
  defines an OWNED `SseReaderContext` before writing a line of the loop.

Output: the owned reader context, the reconnect loop, the cancellation contract, the public fuzz seam
and its target, the severance build, and the recorded semver verdict.

**The retry loop.** It lives INSIDE the single spawned reader task and operates on the

builds the context, calls it once for the initial open, spawns the task, and stores the handle. The
retry loop then owns the attempt counter and the sleep.

Loop shape:
- on end-of-body or a transport IO error from `read_next_sse_frame`, increment the attempt counter;
- if the counter exceeds `MAX_SSE_RECONNECT_ATTEMPTS`, end the stream with a NAMED error stating the
  budget was exhausted and how many attempts were made, delivered through plan 01's terminal-error
  taxonomy: `Err(Error::Transport(TransportError::Request(..)))`, sent ONCE, then the task returns. It
  must be textually distinguishable from the D-02 overflow error and the D-05 parse error, both of
  which use `TransportError::InvalidMessage`, so a consumer can tell a lifecycle end from corruption.
  Do not go quiet;
- **before every sleep and again immediately after it, check `ctx.sender.is_closed()` and RETURN if it
  is true.** This is what makes fences 4 and 5 pass: a `close()` or a dropped transport during backoff
  must not be followed by another GET. Without the post-sleep check the loop wakes up and reconnects to
  a peer nobody is listening to;
- otherwise sleep `min(INITIAL_SSE_RECONNECT_DELAY * SSE_RECONNECT_GROWTH^attempt, MAX_SSE_RECONNECT_DELAY)`,
  unless the last received `SseEvent::retry` gave a server-provided value, which WINS (the reference
  client does this and `SseEvent` already carries the field);
- re-open with `ctx.reconnect_cursor()` as the cursor argument. The call site carries NO `#[cfg]`;
- reset the attempt counter after a successful re-open that delivers at least one frame, so a stream that
  survives for hours and then blinks again gets a fresh budget rather than inheriting an old one. State
  this in a comment — it is a deliberate choice, not an oversight;
- an overflow or parse-failure end (plans 01/03's D-02 / D-05 paths) is a CORRUPTION end, not a transport
  drop: it must NOT be retried. Retrying a stream the peer is corrupting is a reconnect storm against a
  server that is already misbehaving. Distinguish the two end reasons explicitly.

**Do NOT re-issue `initialize` on reconnect.** Reconnect re-issues the GET only. A 404 / expired-session
