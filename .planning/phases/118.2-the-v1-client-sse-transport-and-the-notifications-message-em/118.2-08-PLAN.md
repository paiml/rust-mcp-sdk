<objective>
Make both native dispatch roots agree about `logging/setLevel` (D-13): store-and-honour on v1 while
still answering a literal `{}`, retire on v2.

Purpose: `Server::process_client_request` answers `Ok(json!({}))` for `SetLoggingLevel` today with **no
era branch anywhere in `src/`** — the v2 retirement is enforced only at the HTTP layer.
`crates/pmcp-team-servers/tests/era_matrix.rs` flags this in its module doc: "the REPLACEMENT mechanism
works … only the retirement of the old RPC is missing." 118.1 spent real effort collapsing exactly this
class of divergence — `completion/complete` had two dispatchers giving two *different* wrong answers —
and leaving a known one open invites the next reader to trust the wrong root.

**Scope discipline.** This is the `Subscribe | Unsubscribe | SetLoggingLevel | Ping` residual arm. Only
`SetLoggingLevel` is in scope. Do NOT unify the other three — they are a recorded, owned residual and
CONTEXT.md defers them explicitly.

**Pitfall 8, MEASURED, is the sharp edge.** The pinned suite's `2025-11-25:logging-set-level` scenario
does `const r = await n.request('logging/setLevel', { level: 'info' })` and then
`r && Object.keys(r).length > 0 && i.push('Expected empty object {} response')`. **Any non-empty object
is a FAILURE.** That scenario is currently GREEN and is one of the 29 entries in
`BLOCKING_GREEN_SCENARIOS`. Returning the stored level, `null`, or an acknowledgement object would
reduce the blocking surface the gate claims — a regression dressed as an improvement.

Output: one arm, two roots, one measured response shape.
</objective>
