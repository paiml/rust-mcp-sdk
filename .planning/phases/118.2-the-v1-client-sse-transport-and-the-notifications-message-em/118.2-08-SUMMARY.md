# Phase 118.2 Plan 08: One Arm, Two Roots, One Measured Response Shape — Summary

`logging/setLevel` had two native dispatchers giving two different answers on
every era: `Server::process_client_request` answered `json!({})` with **no era
branch anywhere in `src/`**, and `ServerCore`'s `_ =>` catch-all answered
`-32601` on **both** eras. Both now call one era-branched unit — a literal `{}`
on v1, `-32601` on v2 — and the three-method residual they leave behind is
recorded, not silently shrunk.

## The Shared Unit

`src/server/core.rs:431`:

```rust
#[cfg(not(target_arch = "wasm32"))]
pub(crate) fn set_logging_level_response(
    id: RequestId,
    era: Option<crate::types::protocol::Era>,
) -> JSONRPCResponse
```

with three companions beside it:

| Item | Line | What |
|---|---|---|
| `METHOD_NOT_SUPPORTED_MESSAGE` | `:370` | ONE literal, read by the `_ =>` catch-all AND by the v2 retirement |
| `set_logging_level_is_retired(era)` | `:378` | `const fn`; `Some(V2)` only — `None` is v1, because a server that never opted in has always been on v1 |
| `set_logging_level_v1_result()` | `:406` | the literal `{}`, with Pitfall 8 quoted at it |

It returns a **full `JSONRPCResponse`**, not a `Result<Value>`, which is what
lets both roots call it — see the adapter decision below.

## Both Call Sites

| Root | Site | Line |
|---|---|---|
| `ServerCore` | its own dispatch arm, ahead of the `_ =>` catch-all | `src/server/core.rs:4408` |
| `Server` | **ADAPTER (b)** in `handle_client_request` | `src/server/mod.rs:2029` |
| `Server` (secondary) | `process_client_request`'s own arm, calling `set_logging_level_v1_result()` | `src/server/mod.rs:2116` |

Both read the era through the projection the plan named,
`protocol_context.as_ref().map(|ctx| ctx.era)` — the ALREADY-RESOLVED value, so
this layer never becomes a second era resolver.

### Why `Server` uses an adapter and not the residual arm's neighbourhood

The plan asks for the arm inside `process_client_request`. **It cannot carry the
v2 answer.** `Server::create_response` (`mod.rs:2133`) maps *every* `Err` from
that function to `error_codes::INTERNAL_ERROR` — a hard-coded `-32603` — so a
`-32601` cannot travel through its `Result<serde_json::Value>` return type at
all.

Two ways out, one taken:

* **Rejected:** make `create_response` read `Error::error_code()`. That would
  silently change the wire code of every other handler that returns an
  `Error::Protocol`, `Timeout`, `Authentication`, `RateLimited` or
  `CircuitBreakerOpen` — a broad, unmeasured behaviour change smuggled in behind
  a two-line conformance fix.
* **Taken:** intercept above `process_client_request`, in `handle_client_request`,
  which returns `JSONRPCResponse` directly. This is not an invention — it is
  **ADAPTER (a)**'s existing pattern for `tasks/*`, whose own comment states the
  identical reason ("returning a full `JSONRPCResponse` DIRECTLY — no
  `JSONRPCResponse -> Result<Value>` round-trip and no double-wrap, so the FROZEN
  `-32002` pending code survives unchanged"). The new block is labelled
  **ADAPTER (b)** and says so.

`process_client_request` still gets its own `SetLoggingLevel` arm — the match is
exhaustive and the function is called directly by tests — and that arm calls
`set_logging_level_v1_result()` rather than re-typing `json!({})`, so the shape
Pitfall 8 measures lives in exactly one place. Its comment names the
`create_response` constraint so the next reader does not "fix" the missing era
branch there.

## The Error Constructor, and Where the Two Layers Deliberately Differ

**Shared: the CODE.** Both layers emit
`crate::types::protocol::error_codes::METHOD_NOT_FOUND` — one definition, read by
name at both sites. That is the acceptance criterion's substance and it holds.

**Not shared: the message text.** The HTTP ingress builds
`"Method not found: logging/setLevel (retired in MCP 2026-07-28; use
io.modelcontextprotocol/logLevel)"` from `V2_RETIRED_METHODS` +
`v2_retirement_message`. Those live in `src/server/streamable_http_server`, which
is gated behind `feature = "streamable-http"`; `src/server/core.rs` is not, so it
**cannot reference them** without relocating the whole table (which itself
depends on `LOG_LEVEL_SET_METHOD` and `LOG_LEVEL_REQUEST_META_KEY`, both private
to that file).

Given the choice, the dispatch root reuses **its own** `"Method not supported"`,
now hoisted into `METHOD_NOT_SUPPORTED_MESSAGE`. The argument is positive, not
resigned: on this root, `ping`, `resources/subscribe` and
`resources/unsubscribe` are all refused with exactly that string through the
`_ =>` catch-all. Giving `logging/setLevel` a different message would create a
*new* inconsistency on the root this plan is unifying. The split is also
precedented and already documented in-tree — `map_unparsed_body_for_v2`'s
rustdoc records the same thing for the two pre-existing v2 rejection routes:
"Both routes emit the same code and the same status … only the message text
differs."

## Which Route Fence 2 Took, and Why

**IN-PROCESS, through each root's own era-bearing dispatch entry — not over
HTTP** — and it lives in `src/server/core.rs`, not `tests/log_emitter.rs`.

Two independent reasons, both structural:

1. **HTTP cannot reach it.** `retire_v2_method` refuses a v2 `logging/setLevel`
   at the header gate, long before any dispatcher sees it. A wire fence would
   prove the *pre-existing* transport retirement and say nothing about the arm
   this plan added — and the whole of D-13 is that the DISPATCH root was the
   layer with it wrong.
2. **An integration test cannot construct the input.**
   `ClientRequest::SetLoggingLevel` carries no `_meta` — it is one of the
   variants `request_meta_value` (`core.rs:4452`) enumerates as non-`_meta`-bearing
   — so `resolve_ingress_protocol_context` always yields `None` for it. The only
   PUBLIC dispatch entry, `ProtocolHandler::handle_request`, therefore *always*
   resolves `era == None` and can exercise the v1 branch only. `Server` does not
   even implement `ProtocolHandler`: its `handle_request` is a private inherent
   method. The era-bearing seams are `Server::handle_request_with_context`
   (`pub(crate)`) and `ServerCore::handle_request_internal` (private to
   `core.rs`), and `core.rs` is the only file that can reach **both** — which
   makes it the only place the twin-root claim is expressible at all.

This is the 118.2-06/07 precedent applied again: behavioural fences beside the
units, a structural + name-existence guard in the public fence file. Recorded as
a deviation below rather than weakening the fence.

## THE VERDICT — `LogMessageParams` `message` vs `data`

Plan 05 handed this decision here with an explicit trigger: *"if the official
suite validates `params.data`, the current shape fails it and the type change
becomes in-scope work with its own semver verdict."*

**The trigger has NOT fired. Measured, not assumed.**

The pinned suite *does* bundle the schema — its `LoggingMessageNotification`
definition carries `required: ['data','level']`, and the in-repo
`schema/vendored/core-2026-07-28/schema.ts:2031` says the same — but **no
scenario validates the params of an emitted `notifications/message`**. The suite
contains exactly two logging scenarios:

| Scenario | What it inspects |
|---|---|
| `2025-11-25:logging-set-level` | ONLY the RPC's response (`Object.keys(r).length > 0`). It never reads a notification. |
| `sep-2575-server-no-log-without-loglevel` | NEGATIVE: asserts NO `notifications/message` frame appears for a request that did not set `_meta["io.modelcontextprotocol/logLevel"]`. It looks for **absence**, and reports `untestable` when the server does not expose the diagnostic tool `test_logging_tool`. |

So pmcp's `{"level":"warning","message":"hello"}` costs **zero conformance
points today**.

**Verdict: DECLARED, not fixed.** Against changing it now:

1. It is a **breaking change to a public type** (`LogMessageParams`'s serde
   shape). pmcp is at 2.18.0 with no open breaking-change window.
2. Choosing the replacement is a **design decision**, not a bug fix: does
   `message` become `data`? does `log(..)` set `data` to a JSON string and keep
   `message` as an extension (legal — the schema does not close
   `additionalProperties`)? That belongs to a semver phase.
3. `src/types/notifications.rs` is outside this plan's `files_modified`, and the
   dispatch arm this plan changed has nothing to do with the notification
   payload.

**But it is now MECHANIZED rather than prose.**
`the_vendored_schema_requires_data_where_pmcp_emits_message` reads the in-repo
vendored schema (member lines only — the `data` member's own doc comment says
"such as a string message", so an absence assertion over the raw body would be
satisfied by prose) and the live emitted payload, and asserts **both** sides of
the disagreement. The day either side moves, it is a red test rather than a note
in a summary nobody re-reads. Recorded in `deferred-items.md` and appended to
`.planning/WINDOWS.md` so it is visible at ship time.

## The Other Two Items Handed to This Plan

**The malformed-`logging/setLevel` `400`/`-32601` finding (118.2-07): OPEN, not
fixed.** Making a malformed `params.level` answer `{}` means loosening the
deserializer of the PUBLIC `ClientRequest::SetLoggingLevel` variant — a

literal `{}` — now pinned on both ingress paths and in-process. Left OPEN in
`WINDOWS.md` deliberately: a human at ship time should see it, because it IS a
divergence between a plan's stated contract and the code — just not one this
phase should close.

**`set_session_log_level`'s unreachable no-op (118.2-07): reviewed, unchanged.**
It is defence in depth for a call site that reaches the write without
`validate_non_init_session`. Deleting a control because no fence can red it today
is deleting it for the exact reason it is working. This plan touches neither the
session store nor the ingress.
