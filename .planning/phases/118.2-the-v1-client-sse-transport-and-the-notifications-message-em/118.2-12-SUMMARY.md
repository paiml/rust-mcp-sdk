## Deviations from Plan

### 1. [Rule 2 — missing critical correctness] § 10's mandated `gh api … compare` command is broken

README § 11 step 2 mandates re-running the § 10 comparison at every re-pin. It now returns
`404 Not Found`:

```
$ gh api repos/modelcontextprotocol/conformance/compare/a8651182…...c321dd32…
{"message":"Not Found", … "status":"404"}
```

**Diagnosed rather than assumed, across five bounded probes**, because a 404 here could have meant the
package pin had been orphaned by an upstream history rewrite — which would be a serious finding about
the referee:

| Probe | Result | Rules out |
|---|---|---|
| `gh api …/commits/<each sha>` | both resolve, with dates and messages | the SHAs being gone |
| `gh api repos/modelcontextprotocol/conformance` | public, unarchived | repo access |
| `compare/main...main` on the **same** repo | `identical` | endpoint access / token scope |
| `compare/main...<main HEAD sha>` | `identical` | full-SHA form being rejected |
| `compare/main...main` on an **unrelated** public repo | **also 404** | anything specific to this repo |

**Verdict: an upstream GitHub API behaviour change, not a pin problem.** `c321dd32…` is still in `main`'s
first 100 commits, so it is emphatically not orphaned.

**Fix:** the verdict was re-derived by a different endpoint that needs no compare —

```
$ gh api ".../commits?sha=c321dd32…&per_page=30" --jq '.[].sha' | grep -n 'a8651182…'
15:a865118206d4d8cc8dbc5f5201607839281d0c3b
```

Line **15** ⇒ the package pin is **14 commits ahead**, `behind_by: 0` — *identical to the compare
endpoint's last working answer*. Both the diagnosis and the substitute command are written into § 10, so
the next re-pin is not blocked by a procedure step that no longer works. Committed in `f60c20c3`.

### 2. [Rule 1 — bug, caused by this plan] My own prohibition sentence broke the exemption count

The plan's acceptance criterion is `grep -cE '\-\-expected-failures'` showing **no new occurrence**. My
new comment block contained the sentence *"D-21 still admits no `--expected-failures`…"* — a
**prohibition**, but one that took the literal count 1 → 2 and would have forced every future reviewer to
adjudicate a false positive against a blunt mechanical check. Reworded to "no expected-failures flag …
(the sole mention of that flag remains the § 9 prohibition at the head of this script)". Count back to
**1 → 1**. Meaning preserved, mechanical check clean. Folded into `fff0d95a`.

### 3. [Rule 3 — blocking, operational] `slopcheck` must run from a neutral directory

`slopcheck install -e npm <pkg>` literally executes `npm install <pkg>` in the **current working
directory**, and `npm install` walks *up* the tree for a manifest. Run from this repository — which has
no root `package.json` — it reached `~/package.json` and audited that project's **1 927 packages**,
printing npm's output and **no `1 OK` verdict at all**. A reader skimming for green would have seen 114
vulnerabilities from an unrelated tree.

Verified it caused no harm: `git status --short` showed no new repo change, and `~/package.json` already
listed the package with an mtime of 2026-08-09 (unmodified). Re-run as `cd /tmp && slopcheck install -e
npm …` it returns `1 OK`, exit 0. Recorded in README § 13 so the next re-pin does not repeat it.

### 4. [documented, not a defect] The measurement was taken twice, not once

The plan says *"ONCE. Not until it passes."* That instruction guards against re-rolling a red run until
it turns green. Both runs here are recorded and **both are green and identical**:

- `target/118.2-12-conf-newpin.log` — Task 1's measurement, taken **before** any edit. **This is the
  measurement**, and the delta table is computed from it alone.
- `target/118.2-12-conf-final.log` — Task 2's own `<verify>` block, which re-runs the script after the

No run was discarded, and no run was repeated after a failure.
