**How the type is spelled (REVIEWS fable (d) — this was unspecified and is a real trap).**
`PromptArgumentType` (`src/types/prompts.rs:112-125`) derives
`Debug, Clone, Copy, PartialEq, Eq, Default, Serialize, Deserialize` and has **no `Display`
impl** — MEASURED: `grep -rn "impl.*Display.*for PromptArgumentType" src/` returns nothing. So
the only formatter a writer reaches for by reflex is `{:?}`, which is exactly the
Debug-in-a-digested-body hazard this phase forbids everywhere else. Write an explicit four-arm
`match` to these exact lowercase literals, matching the type's own
`#[serde(rename_all = "lowercase")]` wire spelling: `String => "string"`,
`Number => "number"`, `Integer => "integer"`, `Boolean => "boolean"`. The enum is not marked
`#[non_exhaustive]` today, so the match is exhaustive with no catch-all; if a variant is added
later the compiler points at this match, which is the desired failure mode.

**`render_step` extensions** — beyond the tracer's tool line and binding line, add: one bullet
per entry of `WorkflowStep::arguments()` (an `IndexMap`, insertion order, safe) mapping the
argument name to `render_data_source`; one line per `WorkflowStep::resources()` entry naming
the resource; one line per template binding; and, when `WorkflowStep::guidance()` is `Some`, a
final line beginning `Judgment: ` carrying the guidance verbatim.

**The determinism landmine.** `WorkflowStep::template_bindings()` returns
`&HashMap<String, DataSource>` — the ONE nondeterministic accessor in the entire input
surface, and D-11 puts it in the body. At the top of `render_step`, collect it into a
`BTreeMap<&str, &DataSource>` and iterate that. Byte order via `String`'s `Ord` is the right
key precisely because it is locale-independent; a locale-aware collation would break
byte-equality across machines. Everything else — `wf.arguments()`, `step.arguments()`,
`wf.steps()`, `wf.instructions()`, `step.resources()` — is an `IndexMap` or a slice and is
already ordered.

**`render_data_source(ds: &DataSource) -> String`** — three named arms plus the mandatory
`_ =>` constant-literal arm (`DataSource` is `#[non_exhaustive]`). `PromptArg(name)` describes
it as the named input. `StepOutput { step, field: None }` describes it as the result of the
named step; `field: Some(f)` describes it as that field of that step's result.
`Constant(v)` renders `serde_json::to_string(v)` — compact and single-line, because multi-line
pretty JSON inside a markdown bullet is a readability and diff hazard. `serde_json` is built
with `preserve_order` (`Cargo.toml:119`), so object keys emit in construction order: that is
deterministic for a given workflow, which is what SC-2 requires, but it is NOT canonical —
two semantically identical workflows that wrote their keys in different orders render
differently.

**Decision on gemini's Finding 4: do NOT sort the keys. Document and PIN the behaviour
instead.** Sorting was the reviewer's alternative and it is the wrong trade here: the rendered
constant is documentation of what the workflow will actually SEND, and because `preserve_order`
is on, the sent JSON is in construction order too. A sorted render would make the manual
procedure disagree with the call it describes — a worse defect than the one it fixes, and one a
manual runner would act on. Two obligations follow, both mandatory:
1. The helper's doc comment states plainly that **constant key order is digest-significant**:
   reordering the keys of a `json!` literal in a workflow definition changes the rendered body
   and therefore the published `sha256`, so it is a CHANGELOG-worthy change under D-14 exactly
   like a render change. Say so in those terms, so nobody later mistakes `preserve_order` for
   canonicality.
2. Task 2 carries `constant_key_order_is_digest_significant`, asserting the two orderings
   render DIFFERENTLY. Pinning the difference is what makes it a decision rather than an
   accident a future reader "fixes" by sorting.

Do NOT render tool descriptions or input schemas anywhere (D-12). Do NOT add a third
frontmatter key (D-13). Do NOT render either excluded server-execution accessor (D-11).
