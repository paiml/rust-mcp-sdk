## RECORDED DEVIATION FROM LOCKED D-02 — `SkillProjection::build()`'s return type

**This is the finding all three review lanes raised, and the only unanimous one.** It is
recorded here as an explicit deviation rather than left to be discovered inside an
implementation plan.

- **Locked text, `126-CONTEXT.md` D-02:** "the builder's `build() -> Result<Skill>` is where
  strict checks live."
- **Locked text, `126-CONTEXT.md` D-10:** "structured warnings returned from `build()`, so
  tests assert on data instead of installing a subscriber and callers can act on them."
- **These are literally incompatible.** `Result<Skill>` cannot carry a warning vector.

**Resolution:** plan 126-01 Task 1 is a `checkpoint:decision` / `gate="blocking-human"` on
exactly this question, with three options (`output-struct` / `tuple` / `pair`) and
`output-struct` — `pub fn build(self) -> Result<ProjectionOutput>` with
`pub struct ProjectionOutput { skill, warnings }` — recommended, because it is the only option
that stays additive under a future field and because codex and gemini proposed it
independently.

**The executor's obligation here:** implement whichever option the gate returned, and then
record the deviation in three places — (1) `126-04-SUMMARY.md`, naming D-02's literal wording
and the shape actually shipped; (2) the `build()` rustdoc, in one sentence, so a reader of the
API sees the reasoning; (3) plan 126-06's CHANGELOG entry. A locked-decision change that
appears only as a signature in a diff is exactly what the reviews objected to.

Throughout the rest of this plan, `build()`'s success value is written as
`⟨build-output⟩`. Where the original text said `build()?.0.body()`, read
`⟨build-output⟩.body()` — `.0` under `tuple`, `.skill` under `output-struct`.
</decision_deviation>

<d07_d10_resolution>
## RESOLVED: D-07 and D-10 are not simultaneously satisfiable as written (codex, verified against source)

**The claim, checked.** D-07 says a bare `as_skill()` holds no tool map and therefore cannot
generate SC-6 diagnostics. D-10 says warnings are delivered through two channels, one of them
`tracing::warn!` on the infallible path. Codex argued these cannot both hold for the SC-6
warning specifically. **Verified against the tree this session and the argument is correct:**

- `ToolAnnotations` is reachable only through `crate::types::ToolInfo::annotations`
  (`src/types/tools.rs:216-218`).
- `SequentialWorkflow` and `WorkflowStep` expose no annotations at all — `WorkflowStep::tool()`
  returns a `ToolHandle`, which carries a name.
- Therefore `as_skill()`, which receives only `&SequentialWorkflow`, **structurally cannot
  observe** whether any step's tool is destructive. It is not that it declines to log the SC-6
  warning; it cannot compute it.

**Resolution (adopted — this is codex's option 1 combined with option 3, and it is the only
one that makes every remaining claim true):**

1. **`build()` emits BOTH channels for everything it can see.** It returns the structured
   warning vector AND emits each warning through `tracing::warn!(target: "mcp.skills", …)`.
   The builder path therefore genuinely has two channels, including for SC-6.
2. **`as_skill()` emits `tracing::warn!` for the warnings it CAN observe** — the D-15 slug
   fallback and the empty-description substitution. Both are computable from the workflow
   alone.
3. **SC-6 gate warnings have exactly ONE delivery channel: the structured return from
   `build()`.** This is stated as a limitation in `as_skill()`'s rustdoc, in
   `SkillProjection::new`'s rustdoc, and in the module rustdoc (plan 126-06 Task 2) — a caller
   who expects `as_skill()` to warn about a destructive step and gets silence must be able to
   find out why, and the answer is "supply a tool map through the builder".
4. **The phrase "two delivery channels" is REMOVED wherever it was applied to SC-6.** It was
   false. It survives only in the narrower form stated in point 1.

This narrows D-10's wording. The narrowing is recorded here, in the module docs, in
`126-04-SUMMARY.md` and in the CHANGELOG — it is not a silent reinterpretation.
</d07_d10_resolution>

  <action>
Define the builder and its warning type in `src/server/skills/projection.rs`.

**`ProjectionWarningKind`** — a public `#[non_exhaustive]` enum with three variants:
one for a side-effecting step carrying gate-like guidance (the SC-6/D-09 warning), one for a
step whose gate check could not be performed because the tool carries no annotations or is
absent from the map (the D-08 distinct note), and one for the slug fallback having been used.
`#[non_exhaustive]` keeps future kinds additive.

**`ProjectionWarning`** — a public struct (NOT an enum, so added fields stay additive) with
private fields and four accessors: `kind() -> ProjectionWarningKind`, `step() -> Option<&str>`,
`tool() -> Option<&str>`, `message() -> &str`. Derive `Debug` and `Clone`. Its rustdoc MUST
state why it is public where the module's own `SkillDiagnostic` is deliberately crate-private:
D-10 requires `build()` to RETURN warnings so tests assert on data rather than installing a
`tracing` subscriber and so callers can act on them. Cite `SkillDiagnostic` by name in that
rustdoc. Without this note a future reader "fixes" the asymmetry and breaks `build()`'s
signature.

**`SkillProjection<'w>`** — holds `workflow: &'w SequentialWorkflow` and
`tools: Option<HashMap<String, Option<ToolAnnotations>>>`.

- `pub fn new(workflow: &'w SequentialWorkflow) -> Self` — `tools` starts `None`, which is
  what distinguishes "no tool map supplied" (zero diagnostics, D-07) from "supplied but this
  tool is unannotated" (the unverifiable note, D-08). Do not collapse those two states into
  one empty map.
- `#[must_use] pub fn with_tools(mut self, tools: impl IntoIterator<Item = crate::types::ToolInfo>) -> Self`
  — collapse to `HashMap<String, Option<ToolAnnotations>>` keyed by `ToolInfo::name`. Take
  `crate::types::ToolInfo`, never `workflow::conversion::ToolInfo`: the latter has three
  fields and structurally cannot carry `annotations`, which is exactly why
  `WorkflowPromptHandler.tools` is useless for SC-6 and why the warning is a builder-path
  capability. The `IntoIterator` form accepts a `Vec<ToolInfo>` straight off a `tools/list`
  result; a `&HashMap` parameter would force callers to build a map they do not otherwise
  need.
- **`build`'s terminal signature is whatever plan 126-01 Task 1's gate returned** — see
  `<decision_deviation>` above. Under the recommended `output-struct` answer that is
  `pub fn build(self) -> Result<ProjectionOutput>` with
  `pub struct ProjectionOutput { skill: Skill, warnings: Vec<ProjectionWarning> }` carrying
  public accessors `skill()`, `warnings()` and an `into_parts()` consuming accessor, plus a
  rustdoc stating that the struct exists (rather than a tuple) so a later phase can add a field
  without a breaking change. Do NOT invent a fourth shape; implement the gate's answer.
  Its rustdoc needs an `# Errors` section naming **both** failure conditions: the D-15 case
  where the workflow name normalizes to nothing legal, and (REVIEWS finding 6) an empty
  workflow description, which would otherwise render an agentskills-illegal frontmatter value.
  `# Errors` is not optional — `#![warn(missing_docs)]` plus `RUSTDOCFLAGS="-D warnings"` in
  `make doc-check` makes it a build failure.

**Fallibility split (D-02).** `build()` calls `slugify(wf.name())` and returns
`Err(Error::validation(..))` on `None`, pushing a strict caller to rename; it likewise returns
`Err` when `wf.description()` is empty after trimming. `as_skill()` on either input warns via
`tracing` and substitutes (`fallback_slug` for the name; the pinned
`Projected from the {slug} workflow.` literal for the description, per plan 126-01 Task 4 step
3d). Both then call the SAME `render_body`. Do not write a second render path: an identity test
asserts `⟨build-output⟩.body() == wf.as_skill().body()`.

**Description legality stops there — no length bound is invented.**
`.claude/skills/spike-findings-rust-mcp-sdk/references/sep-2640-conformance.md` states the
digest format, the `≤512 files / ≤16 MiB` per-skill limits and the name-identity rule, and
states **no description length limit**. Record that absence in the rustdoc rather than guessing
a number; the existing `exceeds_skill_limits` warning already covers a pathologically large
body. The escaping half of description legality is plan 126-01 Task 4's and must not be
re-implemented here.

**Nothing panics.** `build()` returns `Err`; it does not `panic!` inside a `Result`-returning
function. That was precisely Phase 125's still-open WR-03 finding at
`src/server/builder.rs:1501`, and D-15 names it.

**Re-export.** Add `pub use projection::{ProjectionWarning, ProjectionWarningKind,

`src/server/skills/mod.rs` under the existing re-export comment block, so the canonical
