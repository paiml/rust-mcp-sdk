**Body shape — and the REVIEWS finding-3 correction, which is mandatory.** The original plan
said "`String::from_utf8_lossy(data)` once, then split the lossy string by byte length
quarters." **That itself panics.** `from_utf8_lossy` output contains multi-byte characters,
including the `U+FFFD` it inserts for every invalid sequence; an arbitrary quarter index is not
guaranteed to be a char boundary, and `&s[..len/4]` panics on `byte index N is not a char
boundary`. The crash surfaces inside the harness and gets attributed to `as_skill()` — a false
positive that costs a debugging cycle and, worse, could be "fixed" by adding a guard to
production code that never had the defect.

Do it in this order instead: **split the ORIGINAL `data: &[u8]` slice into four contiguous
byte chunks first** (`data.chunks(data.len() / 4 + 1)`, or four explicit ranges over the raw
bytes), **then call `String::from_utf8_lossy` on each chunk independently.** Slicing a `&[u8]`
by any index is always safe, and each chunk is independently lossy-decoded into a valid
`String`. The equivalent alternative, if a single decode is preferred, is to split the decoded
string on `char_indices()` / `is_char_boundary()` — but the byte-chunk-first form is simpler
and has no boundary arithmetic at all. Write the reason into the target's header comment: a
later editor optimising "four decodes into one" reintroduces exactly this panic.

Do not add an `arbitrary` derive — it would need a new dependency and this phase adds none.
Delegate to one named `check_projection(...)` helper rather than inlining the logic, matching
the analog.
