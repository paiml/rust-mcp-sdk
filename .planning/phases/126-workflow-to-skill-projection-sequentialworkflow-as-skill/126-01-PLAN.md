  <decision>Choose the public return type of `SkillProjection::build()` before plan 126-04 ships it, and record the choice as an explicit deviation from whichever locked decision's literal wording it does not match.</decision>
  <context>
**This gate replaces the one the reviews rejected.** The original Task 1 asked whether to
proceed with an infallible `as_skill() -> Skill`. That is settled: D-02 is locked in
`126-CONTEXT.md` and approved in `126-DISCUSSION-LOG.md`, so the gate reduced no uncertainty

Proceed with `as_skill(&self) -> Skill` per D-02 without asking.

The real conflict: **two locked decisions have literally incompatible wording.**
- **D-02** says the builder's terminal is `build() -> Result<Skill>`.
- **D-10** says structured warnings are *returned from `build()`* so tests assert on data
  instead of installing a `tracing` subscriber.

`Result<Skill>` cannot carry a warning vector. The originally planned
`Result<(Skill, Vec<ProjectionWarning>)>` resolves it but is an **unrecorded deviation from
locked wording** — the one finding ALL THREE review lanes raised, with codex and gemini
independently proposing the same remedy. A public return type on a published 2.x crate is
one-way, so this is a human decision, not a planner one.

Whatever is chosen, plan 126-04 MUST record it as a deviation in its `<decision_deviation>`
block and in `126-04-SUMMARY.md`, and plan 126-06 MUST name it in the CHANGELOG entry.
  </context>
  <options>
    <option id="output-struct">
      <name>`build(self) -> Result<ProjectionOutput>` with `pub struct ProjectionOutput { skill, warnings }`</name>
      <pros>Named, self-documenting, and ADDITIVE — a later phase can add a field (e.g. the manifest, or a `strict` verdict) without a breaking signature change, which neither a tuple nor a `Skill` allows. Proposed independently by codex and gemini. Deviates from D-02's literal `Result<Skill>` only in the success type's name, and satisfies D-10 exactly.</pros>
      <cons>One more public type on the crate's surface. Callers who want only the skill write `.build()?.skill` rather than `.build()?`.</cons>
    </option>
    <option id="tuple">
      <name>`build(self) -> Result<(Skill, Vec<ProjectionWarning>)>` — as originally planned</name>
      <pros>No new type. Satisfies D-10 directly.</pros>
      <cons>Every caller unpacks, including those that do not want warnings. Not extensible — adding a third element is a breaking change. All three lanes called it awkward.</cons>
    </option>
    <option id="pair">
      <name>`build(self) -> Result<Skill>` plus `build_with_warnings(self) -> Result<(Skill, Vec<ProjectionWarning>)>`</name>
      <pros>Honors D-02's literal wording exactly, and mirrors the module's own `with_reference` / `try_with_reference` pairing habit. Gemini's Option A.</pros>
      <cons>Deviates from D-10's literal wording instead (warnings are no longer returned from `build()`); `build()` would have to discard warnings or log-only, which is the very asymmetry D-10 exists to remove. Two terminals to keep in sync.</cons>
    </option>
  </options>

It is the only option that is additive under a future extension, it satisfies D-10's requirement literally, and it deviates from D-02 in the least load-bearing way (the success type's name, not its fallibility). **3b. `yaml_double_quoted(s: &str) -> String` — the REVIEWS finding-1 fix, and the single most
important function in this task.**

The originally planned `description: {workflow description verbatim}` is a raw concatenation
and it is unsafe. `SequentialWorkflow::new` validates nothing, so an ordinary description like
`Refund an order: fast path`, `Handle #123`, `[urgent] refund`, `"quoted"`, `- dash`, `---`, or
anything containing a newline reaches `parse_frontmatter_value`, which hands the block to
`serde_yaml`. The failure is worse than a parse error: `build_artifact_inner` **downgrades it
to a diagnostic** and sets `frontmatter = None`, and `validate_names` then `continue`s — so the
skill serves with no `name` in its `skills/list` entry, SC-1's identity check is SKIPPED rather
than enforced, and nothing in the test suite goes red. A newline in the description can inject
an entire additional key.

Emit BOTH frontmatter values as **YAML double-quoted scalars**, always, unconditionally. For a
workflow named `refund_flow` described `Refund an order: fast path`, the emitted block is four
lines: the delimiter `---`; then `name: ` followed by `yaml_double_quoted(slug)`, which renders
as the eight characters `refund-flow` wrapped in `"`; then `description: ` followed by
`yaml_double_quoted(description)`, which wraps the description in `"` with its `: ` intact
because a double-quoted scalar does not treat `: ` as a mapping indicator; then the closing
delimiter `---`.

`yaml_double_quoted` returns the value WITH its surrounding `"` characters, escaping in exactly
this order: `\` becomes `\\`; `"` becomes `\"`; then every `char` for which `is_control()`
holds becomes a YAML double-quoted escape — `\n`, `\r`, `\t` for those three, and `\xNN`
(lowercase hex, zero-padded to two digits) for every other C0/C1 control. Every other
character, including all non-ASCII, is emitted verbatim: a double-quoted YAML scalar carries
UTF-8 directly and re-encoding it would break the verbatim-description contract (D-13).

**Always quote, never conditionally.** Two reasons, both measured, and both belong in the
function's doc comment:
1. A slug is `[a-z0-9-]` but that alphabet still contains YAML type-alikes. `slugify("True")`
   yields `true` and `slugify("123")` yields `123`; unquoted, those parse to a YAML boolean and
   a YAML integer, `validate_names`' `.and_then(serde_json::Value::as_str)` returns `None`, and
   the name-identity rule silently skips the skill — the exact defect class this fix exists to
   close.
2. Conditional quoting makes the emitted bytes depend on a predicate over author text, and
   those bytes are a published digest (D-14). Unconditional quoting keeps the shape constant.

**Do NOT reach for `serde_yaml::to_string` to produce these bytes.** Its quoting style
(plain / single / double) and its line-wrapping are emitter heuristics whose exact output this
plan cannot verify at planning time, and D-14 makes the bytes a supply-chain pin. Use
`serde_yaml` as the **test ORACLE** instead — the round-trip suite parses the emitted block
back through the crate's own `parse_frontmatter_value`, which IS `serde_yaml`. Encoder
hand-written, decoder library-verified, over a `".*"` proptest domain.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server author -> projection input | `SequentialWorkflow` name/description/step names/guidance are author-supplied strings. Same trust level as the rest of the server's source, but they reach a log sink and a digested, served document. |
