**Layer 1 — the test helper, and it is BOUNDED.** Add a single new public function to
`tests/common/example_process.rs`:
`pub fn run_example_to_completion(rel_path: &str, args: &[&str], timeout: Duration) -> std::process::Output`.

The `timeout` parameter is mandatory and has no default. This is not a stylistic preference: the
module header already states the rule at `:14-19` ("Timeouts are ARGUMENTS, not constants"), and
both existing socket helpers take a caller-supplied budget. A run-to-completion helper that simply
waits for the child would be the one path in this module with no ceiling, and a deadlocked or
non-terminating example would HANG the integration suite rather than fail it — five legs across
this plan and 119-04 call this helper, two of them socket-driving clients.

It reuses the module's existing `target_dir()`, the same `binary.is_file()` assertion shape
`spawn_example` uses, and the same `assert_binary_is_not_stale` call. It differs from
`spawn_example` in three ways, each deliberate:

  1. **Both streams are piped AND drained.** `spawn_example`'s own rustdoc (`:79-83`) records that
     piping without draining wedges the child on a full pipe buffer and presents as a bind timeout.
     So: take the child's `stdout` and `stderr` handles and move each into its own
     `std::thread::spawn` reader that reads to end into a `Vec<u8>`, started BEFORE the wait begins.
     Reading one stream to end and only then touching the other is exactly the deadlock this
     avoids — do not do that.
  2. **The wait has a deadline.** Poll `child.try_wait()` against `Instant::now() + timeout`,
     sleeping 50 ms between polls to match `wait_until_listening`'s cadence. On a clean exit, join
     both reader threads and return a `std::process::Output` carrying the status and both captured
     buffers, so callers keep the same shape they would have had.
  3. **Expiry kills, reaps, and REPORTS.** When the deadline passes with the child still running,
     call `kill()` and then `wait()` on it — kill alone leaves a zombie — join the readers with
     whatever they captured so far, and PANIC. The panic message must name the binary path, the
     elapsed budget, the exact `cargo build` command that rebuilds it, and both partial streams as
     lossy UTF-8. A timeout that prints nothing is indistinguishable from the hang it replaced.

Give it a rustdoc block that states why it exists beside `spawn_example`
(run-to-completion legs assert on the banner the example PRINTS; the stream-discarding stdio mode
and `wait_until_listening` are wrong for a binary that binds no socket), why the drain threads are
load-bearing rather than defensive, and record the
`assert_binary_is_not_stale` limitation for non-root examples: the guard's roots are the root
`examples/<name>.rs` path and root `src/`, so for a `crates/*/examples/` binary the first root
resolves to a non-existent path and `crates/*/src/` is never consulted — the guard still compares
against root `src/`, so it is not vacuous, but it is weaker than its rustdoc advertises. State
this limitation in the doc comment; do not silently inherit it.
