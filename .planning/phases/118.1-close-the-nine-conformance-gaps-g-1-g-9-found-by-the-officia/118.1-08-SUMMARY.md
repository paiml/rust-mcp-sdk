## Task 2 — The Fence, and Which Rows Were RED

`tests/v1_handler_client_capabilities.rs`, 736 lines, 5 cases. Every case drives a **real `initialize` handshake over the wire**; nothing constructs a `ProtocolContext`.

### The advertised set is distinctive, and the driver is raw for a measured reason

The v1 handshake advertises `roots.listChanged: true` + `sampling.models: ["g9-model"]` + `experimental["io.pmcp.test/g9-marker"]: "v1-handshake"`. `ClientCapabilities::default()` serialises to `{}`, so a fold that fabricated a default cannot satisfy any assertion, and a *partial* fold (say, `roots` only) fails too.

The driver is a **raw duplex wire driver, not `pmcp::Client`** — measured, not stylistic. `Client::initialize` calls `derive_host_capabilities` (`src/client/mod.rs:663-693`), which FORCES `sampling`, `elicitation` and `roots` to `None` unless a matching host handler is registered. Driving through `Client` would have silently flattened two of the three distinctive signals before they reached the wire.

`ClientCapabilities` derives no `PartialEq`, so comparisons go through `serde_json::to_value` on both sides.

## Task 3 — The Fold

### One shared unit, two call sites

`src/server/core.rs` gained three functions:

- `v1_capability_fold_applies(Option<&ProtocolContext>) -> bool` — the guard. True for `None` (non-opted-in) and for `Some(era = V1)` with an empty capabilities field; **false for `Some(era = V2)` and for an already-populated field**. This is the one-directionality, expressed as a predicate rather than a comment.
- `v1_fallback_version(&[ProtocolVersion]) -> Option<ProtocolVersion>` — the first v1 entry in the accept-list, mirroring `resolve_negotiated_version`'s absent-signal arm exactly so a synthesised context names the same version the shared resolver would have.
- `fold_v1_handshake_capabilities(context, handshake_capabilities, accept_list) -> Option<ProtocolContext>` — the fold itself.

`git grep -n 'with_client_capabilities' -- src/server/` shows **exactly two non-test call sites, both inside `fold_v1_handshake_capabilities`** (`core.rs:4515`, `:4524`). No site holds a copy, so no twin-naming comment was needed.

Called from the two dispatch roots, and nowhere else:

- `ServerCore::handle_request` (the `ProtocolHandler` impl) — the only production caller of `handle_request_internal`
- `Server::handle_request_with_context` — the seam both `Server::handle_request` and `streamable_http_server.rs:3347` funnel through

### Where the lock is read, exactly once

At each root, immediately after the MRTR ingress and before dispatch:

```rust
let handshake_capabilities = if v1_capability_fold_applies(protocol_context.as_ref()) {
    self.client_capabilities.read().await.clone()
} else {
    None
};
let dispatch_context = fold_v1_handshake_capabilities(
    protocol_context.clone(),
    handshake_capabilities,
    &self.supported_protocol_versions,
);
```

Three properties this shape buys (T-118.1-08-02):

1. **One read per dispatch**, not one per site — nine reads collapse to one.
2. **v2 traffic never touches the lock**, because the guard short-circuits first.
3. **No deadlock.** The read guard is a temporary dropped at the end of the `let` statement, well before the `Initialize` arm a few lines down takes the *write* lock. `client_capabilities()` itself was not changed to read the lock, for the reason the plan names: it is a sync method on a value already moved into the handler.

### The egress deliberately keeps the UNFOLDED context

Both dispatchers already cloned `protocol_context` into dispatch and kept the original for `mrtr.finish` and `inject_v2_result_envelope`. The fold produces a separate `dispatch_context` binding that replaces only the dispatch clone. The fold is a handler-visibility concern; it cannot alter a wire shape, and the clone count is unchanged.

### Why a context is SYNTHESISED when none resolved

The default accept-list is **v1-only** (`SUPPORTED_PROTOCOL_VERSIONS`, four v1 versions), so `is_v2_opted_in` is false and `resolve_ingress_protocol_context` returns `Ok(None)` for **every request on a stock server** (D-04). That is the majority case, not an edge case: folding only into an existing context would have left G-9 open for the default server. So when the lock holds a value the context is built from `Era::V1` plus `v1_fallback_version(accept_list)`.

**Blast radius, checked before writing it:** every production consumer of `Option<Era>` treats `None` and `Some(V1)` identically — `v1_initialize_gate_applies`, `task_dispatch::is_v1_task_era`, `tasks_list_serves_on_era`, `project_caching_hints`, and `inject_v2_result_envelope`'s `Some(Era::V2)`-only envelope branch. `git grep -n '\.era()' -- src/` finds no production branch on `extra.era()` at all; every hit is a test or a comment. The only observable change is `extra.era()` / `extra.protocol_version()` going from `None` to `Some(V1)` for a handshaked, non-opted-in server — which is *more* accurate, not less.

**Synthesis is gated on the lock holding a value**, so a server that never saw an `initialize` keeps `era() == None`. That is what let the two pre-existing "non-opted-in → `era == None`" assertions (`core.rs` `prompt_resource_protocol_context_via_dispatch_core`, `mod.rs` its twin) stay green with no edit, and it is asserted directly by case 5.

### Threading the three context-less sites

| Site | Change |
|---|---|
| `ServerCore::handle_list_resources` | new `protocol_context` param + `.with_protocol_context(...)`; caller in `handle_request_internal`'s `ListResources` arm |
| `Server::handle_list_resources` | same shape; caller in `process_client_request` |
| `Server::handle_create_message` | same shape; caller in `process_client_request` |

All three are private `async fn`s. **No public signature changed**, so nothing was DEFERRED.

`sampling/createMessage` deserves its own note, because the plan floated it as a possible NO-OP ("a server-to-client path where a client handshake has no meaning"). It is not: this arm serves an **inbound** `ClientRequest::CreateMessage`, so a client handshake is exactly as meaningful as it is for `tools/call`. The server-to-client direction is a `ServerRequest::CreateMessage` dispatched through `src/server/peer_impl.rs:60,82`, which builds no `RequestHandlerExtra` at all. The rustdoc at the site records this so the question is not re-opened.

### The security paragraph, copied verbatim

`fold_v1_handshake_capabilities`'s rustdoc carries the accessor's paragraph word-for-word:

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `client_request` tripped `clippy::needless_pass_by_value`**

- **Found during:** Task 3, `make lint`
- **Issue:** `fn client_request(method: &str, params: Value)` built its envelope with `json!({...})`, which BORROWS its interpolated values, so `params` was passed by value but never consumed. `make lint` runs with `-D warnings`, so the whole gate failed.
- **Fix:** assemble the envelope through a `serde_json::Map` and `insert` `params` by move — the same route `tests/common/duplex.rs`'s `era_signalling_request` documents for this exact lint.
- **Files modified:** `tests/v1_handler_client_capabilities.rs`
- **Commit:** `f3b17eb0`

**2. [Rule 3 - Blocking] Non-exhaustive struct literals in the fence**

- **Found during:** Task 2, first compile
- **Issue:** `ListResourcesResult` and `CreateMessageResult` are `#[non_exhaustive]`, so an integration-test crate cannot build them with struct-expression syntax; `CreateMessageResult` also has no `role` field (it has `usage`).
- **Fix:** use the real constructors `ListResourcesResult::new(vec![])` and `CreateMessageResult::new(Content::text("ok"), "g9-model")`.
- **Files modified:** `tests/v1_handler_client_capabilities.rs`
- **Commit:** `08d866ac`

### Design deviations from the plan's letter

**3. The fold sits at the two DISPATCH ROOTS, not at the nine construction sites.**

The plan said "at each FOLD site … build or augment the `ProtocolContext`" and then, in the same breath, "prefer ONE shared helper called from both dispatchers over nine copies … nine copies of a lock read is exactly the drift this repo keeps paying for". Those two sentences pull in opposite directions once the sites are enumerated, and the second one wins on its own reasoning. Folding one frame up — at the chokepoint all nine sites already receive their context from — satisfies "one shared helper, two call sites" *and* "read the lock ONCE per dispatch" *and* means a future tenth construction site inherits the fix rather than forgetting it. The plan's threading requirement is unaffected: the three context-less sites still needed the parameter, they just receive an already-folded value instead of folding it themselves.

**4. `sampling/createMessage` was dispositioned THREAD-THEN-FOLD, not NO-OP.**

Reason in Task 3 above. The plan explicitly left the disposition open ("They are NOT automatically out of scope — each needs an explicit disposition"), so this is the plan's own process reaching a verdict, not a departure from it.
