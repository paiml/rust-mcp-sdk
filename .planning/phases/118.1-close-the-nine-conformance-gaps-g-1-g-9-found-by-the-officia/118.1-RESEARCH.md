### Locked Decisions

> ### G-1 / G-2 — the embedded-resource wire format
>
> **Root cause, established during discussion and not previously written down:**
> `Content::Resource` is doing double duty for two *different* spec types.
> `ReadResourceResult.contents` already gets a custom projection
> (`resource_contents_serde`, `src/types/content.rs:325`) that strips the `type` tag and emits
> flat `uri`/`text`/`mimeType` — and that is **spec-correct**, because `ResourceContents` *is*
> flat (`schema.ts:1514-1560`). The defect is only in the *other* position:
> `CallToolResult.content` and `GetPromptResult.messages[].content`, where the derived
> `Serialize` emits that same flat shape but the spec wants
> `EmbeddedResource { type: "resource", resource: TextResourceContents | BlobResourceContents }`
> (`schema.ts:1734-1745`).
>
> - **D-01: Fix the default; keep the flat projection.** `Content::Resource`'s derived
>   `Serialize` emits the spec `EmbeddedResource` shape; `resource_contents_serde` keeps emitting
>   flat for `ReadResourceResult`. Both positions become spec-correct on both eras. **The Rust
>   API is unchanged** — all 130 call sites keep compiling; only emitted bytes change. G-2 (blob)
>   is the same edit, because `resource` is `TextResourceContents | BlobResourceContents`.
>   - `_meta` and `annotations` sit at the **content level** in the spec, *outside* `resource`
>     (`schema.ts:1740-1744`). The MCP Apps widget path that destructures `{ uri, meta, .. }`
>     reads `_meta` at content level and is therefore already correct — nesting `resource` does
>     not disturb it.
> - **D-02: Ships as a 2.x minor, as a conformance FIX.** pmcp is at 2.18.0 and v2.5 is declared
>   additive/no-3.0; that promise holds. The Rust API semver contract is unbroken, and reliance
>   on the flat shape was reliance on a bug that made pmcp incompatible with every other MCP
>   implementation. Requires a prominent CHANGELOG wire-change callout and a migration note.
>   **No opt-out escape hatch.**
> - **D-03: Tolerant reader, strict emitter.** Accept BOTH nested and flat on input; emit only
>   nested. This also fixes a **second defect found during discussion that the suite could not
>   have caught**: `Content` has only the derived `Deserialize` (no manual impl), so with
>   `#[serde(tag = "type")]` and a required top-level `uri`, a spec-conformant
>   `{"type":"resource","resource":{...}}` from any other SDK's server **fails to parse today** —
>   pmcp as a *client* cannot read a conformant embedded resource. The suite tests pmcp as a
>   server, which is why this never surfaced. The tolerance is a documented compatibility
>   affordance, not a second supported format.
> - **D-04: Fenced by spec-derived byte literals + the suite as external oracle.** Extend the
>   `tests/v1_lists_golden.rs` byte-literal pattern to the tool-result and prompt-message
>   embedded-resource positions on BOTH eras, with expected bytes **derived from the vendored
>   `schema.ts`, not from pmcp's own serializer output**. Add a flat-input round-trip test for
>   the tolerant reader. **Each fence must be demonstrated RED against the unfixed tree before
>   the fix lands.**
>   - *Why this matters:* `cargo semver-checks` and `cargo public-api` are **structurally blind**
>     here — they read the Rust API surface, and D-01 changes no signature. The milestone's
>     Pitfall-5 semver guard will pass green on a wire break. So will the existing goldens:
>     `v1_lists_golden.rs` pins `tools/list`, `prompts/list`, `resources/list`,
>     `resourceTemplates/list` and `resources/read`, but **nothing pins a tool result carrying an
>     embedded resource** — the blind spot sits exactly where the fix lands.
>   - Known test to flip: `test_content_resource_meta_serialization` (`src/types/content.rs`)
>     asserts `json["uri"]` at top level.
>

## Summary

Every one of the nine gaps was localized to specific source lines and, where the referee's
expectations mattered, cross-checked against **the pinned suite's own bundled scenario code**
(`conformance/node_modules/@modelcontextprotocol/conformance/dist/index.js`, 0.2.0-alpha.11 —
already installed in this tree) and against the digest-fenced vendored schema. That gives an
oracle stronger than prose: the exact probe bodies, the exact expected codes, and the exact
required result fields are quoted below. Seven of the nine (G-1, G-2, G-4, G-5, G-6, G-7, G-8)
are small, well-bounded edits at chokepoints that already exist. G-9 is a three-site threading
change. **G-3 is not a wiring change — it is missing transport infrastructure**, and it carries a
deadlock hazard that will bite any naive implementation.

Three findings contradict or materially extend the phase's locked assumptions and the planner
must resolve them before decomposition:

1. **D-01's "the Rust API is unchanged" is true for the nesting and false for the rest of the
   cluster.** Nesting `resource` is pure serde. But G-2 needs a `blob` carrier and D-06 adds
   `annotations`, and `Content` is a public, *exhaustive*, non-`#[non_exhaustive]` enum whose
   `Resource` variant is a struct variant. `cargo semver-checks --list` classifies
   `enum_struct_variant_field_added`, `enum_variant_added` and `enum_variant_marked_non_exhaustive`
   **all as `major`** — there is no representation of blob or annotations on this type that
   `cargo semver-checks` will call additive. This collides head-on with D-02 ("ships as a 2.x
   minor") and with the v2.5 additive/no-3.0 milestone constraint. The in-repo blast radius is
   small and measured (18 field-bearing sites, 6 of them in `src/`), so the question is purely
   about the published contract, not about churn. **This needs a human decision, not a planner
   judgement call.**
2. **G-3's scope is wider than "wire the peer handle onto the HTTP path".** The streamable-HTTP
   transport has *no server→client correlation loop at all*: an inbound `TransportMessage::Response`
   is answered `202 Accepted` and discarded
   (`streamable_http_server.rs:3955-3957` and `:4083-4085`). Worse, the response POST would
   deadlock against the in-flight tool call, because `dispatch_request_or_retire` holds
   `state.server.lock().await` for the whole handler while the response POST takes that same
   mutex in `resolve_v2_gate` and `extract_and_validate_auth` *before* reaching its 202 arm.
3. **G-3 has a v2 half nobody has scoped.** `tools-call-with-progress` is in the **2026-07-28**
   requirement set and fails on the v2 leg (`118-05-SUMMARY.md:383-390`). On v2 there are no
   sessions and GET answers 405, so the only vehicle is an SSE-framed POST response — and
   `grep -c 'text/event-stream'` over the transport finds **zero emitters** outside the two
   `Accept`-header validators. `build_sse_response_from_single_message` frames exactly one
   message and is the seam to grow.

**Primary recommendation:** Sequence the phase as Wave 1 (G-1/G-2, gated behind a blocking human
decision on the semver posture) → Wave 2 (G-4/G-5) → Wave 3 (G-6/G-7/G-8) → Wave 5 (G-9) →
Wave 4 (G-3, largest and riskiest, last) → re-measure once → widen the gate → re-pin. Implement
G-1's emitter as a hand-written `impl Serialize for Content` over a **borrowed** wire shadow enum
plus a derived `Deserialize` via `#[serde(try_from = "…")]` — the in-repo precedent is
`crates/pmcp-package/src/digest/canonical.rs:46`. Implement G-5 as a **method-string** retirement
at the v2 ingress, never as a `Request`-variant match, because the suite's probes fail typed
parsing before a variant exists.

| Instead of | Could Use | Tradeoff |
|---|---|---|
| Hand-written `impl Serialize for Content` over a borrowed shadow | `#[serde(into = "WireContent")]` | Simpler (pure derive), but requires `self.clone()` on **every** serialization — a full deep clone of a base64 blob per tool result. ### Pattern 1 — `Content`: strict emitter, tolerant reader, via a shadow wire type

**What:** Keep `Content`'s public shape. Replace its *derived* `Serialize` with a hand-written
impl that serializes a **borrowed** shadow enum matching the spec exactly, and replace its
derived `Deserialize` with `#[serde(try_from = "WireContentIn")]` where `WireContentIn` accepts
both the nested and the legacy flat resource shape.

**When to use:** Whenever a public Rust type's ergonomic shape and its wire shape must diverge and
`#[serde(with)]` is unavailable — which is always the case for an enum *variant*, because serde
provides no per-variant serialization hook. `[VERIFIED: serde has field-level and container-level
`with`/`into`/`try_from`; there is no variant-level equivalent — confirmed by the absence of any
such attribute in serde 1.0.228's derive and by the codebase's own workaround at
`resource_contents_serde`, which is a *field*-level `with` on the containing struct]`

**Why not the three alternatives:**
- `#[serde(with)]` on the variant — does not exist.
- `#[serde(into = "WireContent")]` at the container — works, but forces `Content: Clone` and a
  deep clone on every serialization. For a base64 blob in a tool result that is a real cost.
  Acceptable fallback if the borrowed shadow proves awkward.
- Full manual `Serialize`/`Deserialize` visitors for the enum — throws away the derive for the
  four unaffected variants.

**The `Deserialize` side is the one that must be `try_from`,** because the tolerant reader has to
inspect the payload before deciding. `try_from` keeps the derive on the shadow.

**Key ordering constraint:** `serde_json` is built with `preserve_order`
(`tests/v1_lists_golden.rs:22-24`), so **the field declaration order of the shadow struct is the
wire key order** and is pinned by D-04's byte literals. Declare in schema order:
`type`, `resource` (`{uri, mimeType, text|blob}`), `annotations`, `_meta`.

### Pattern 4 — the three-way `_meta` / header classifier (G-6 + G-8 together)

**What:** `classify_era_cell` today is a 2×2 over `(header_is_v2, meta_is_v2)`, and
`resolve_protocol_context` collapses "the `protocolVersion` key is absent" with "the version is
unsupported". The suite requires three distinguishable outcomes. Derived from the suite bundle
`[VERIFIED: dist/index.js @ 366019, 370104, 371612]`:

| Condition | Required code | Required HTTP | Suite check |
|---|---|---|---|
| `params._meta` absent entirely | `-32602` | 400 | `RequestMetaInvalid` (`missing-meta`, rpcId 101) + `HttpServerMetaInvalid400` |
| `_meta` present, `io.modelcontextprotocol/protocolVersion` key absent | `-32602` | 400 | `RequestMetaInvalid` (`missing-protocol-version`, rpcId 102) |
| `_meta` present, `io.modelcontextprotocol/clientCapabilities` key absent | `-32602` | 400 | `RequestMetaInvalid` (`missing-client-capabilities`, rpcId 104) |
| `_meta` present, `io.modelcontextprotocol/clientInfo` key absent | **success** | **200** | `RequestMetaClientInfoOptional` (rpcId 105) — *clientInfo is a SHOULD; do NOT make it required* |
| `protocolVersion` present and **equal** to the header, but unsupported | `-32022` + `data.supported[]` + `data.requested` | 400 | `ServerUnsupportedVersionError` + `HttpServerUnsupportedVersion400` (rpcId 301) |
| `protocolVersion` present and **different** from the header | `-32020` | 400 | `HttpServerHeaderMismatch400` (rpcId 302) |

**Two ordering facts that make G-8 a pure ordering fix:** at rpcId 302 the suite sends
`_meta.protocolVersion = "v999.0.0"` with header `MCP-Protocol-Version: 2026-07-28`; pmcp resolves
the `_meta` version *first*, fails the accept-list, and returns `-32022`
(`negotiation_error_to_gate_reject`) — the header/`_meta` disagreement never gets a chance to
classify. **Run the agreement check before the accept-list check.** At rpcId 301 header and
`_meta` agree (both `v999.0.0`), so the accept-list check must still fire and produce `-32022`.

**HTTP status comes for free:** `v2_status_for_code` already maps `INVALID_PARAMS` → 400
(`streamable_http_server.rs:735-747`) `[VERIFIED: source]`. The only reason the current
`missing-client-capabilities` probe sees 200 is that pmcp does not reject it at all —
`parse_reserved_object` (`src/types/protocol/context.rs:420-432`) returns `Ok(None)` for an absent
key.

**Compatibility risk to check before implementing:** making `clientCapabilities` mandatory on
every v2 request will reject any existing v2 caller that omits it. pmcp's own `Client` emits it
(`src/client/mod.rs:157-159, 7188`) and the test helper `default_client_capabilities()`
(`tests/common/v2.rs:556`) does too, so the in-tree surface is safe — but the v2 test corpus
(`tests/v2_*.rs`, ~20 files) must be swept for hand-built `_meta` objects that omit the key.

### Pattern 5 — `server/discover.supportedVersions` (G-7)

**The spec type** `[CITED: schema/vendored/core-2026-07-28/schema.ts:678-696 and
schema.json $defs.DiscoverResult]`:

```
DiscoverResult extends CacheableResult:
  required: supportedVersions (string[]), capabilities, resultType, ttlMs, cacheScope
  optional: instructions, _meta
```
There is **no** `protocolVersion` and **no** top-level `serverInfo` in the spec type. pmcp's
`ServerDiscoverResult` carries both. The schema does not set `additionalProperties: false`, so
the extras are tolerated — and **removing them would be `struct_field_missing` = major**. Leave
them; add the missing field.

**Additivity is clean here.** `ServerDiscoverResult` is `#[non_exhaustive]`
(`src/types/protocol/mod.rs:626-628`) `[VERIFIED: source]`, and its own rustdoc already records
the reasoning: *"Adding this field is additive rather than a major bump because this struct is
`#[non_exhaustive]`, so `cargo semver-checks`' `constructible_struct_adds_field` does not fire."*
This is the one type in the phase where a field addition is free.

**The correlation requirement** `[VERIFIED: dist/index.js @ 370104]`: `ServerUnsupportedVersionError`
asserts `error.data.supported` is a non-empty array **every element of which appears in the
discover result's `supportedVersions`**. So both must be sourced from the same
`Server::supported_protocol_versions()` value. That value must be threaded into
`build_discover_response` (currently takes only `capabilities`, `info`, `protocol_context` —
`src/server/core.rs:1944-1949`) via `Server::handle_discover` (`src/server/mod.rs:1502-1513`).

**Free bonus, WARNING-severity:** `ServerIdentifiesInResultMeta` wants
`result._meta["io.modelcontextprotocol/serverInfo"]` with `name` + `version`, and its failure
message distinguishes *"serverInfo found only in the pre-#3002 result body, not in `_meta`"*.
`inject_v2_result_envelope` already owns `RESERVED_SERVER_INFO_KEY`
(`src/server/core.rs:1568`) — verify at implementation time whether it writes into `_meta` or at
the top level, and if the latter, this is a one-line extra win.

### Pattern 6 — G-3 over v1 stateful HTTP: reuse the session SSE stream, bypass the mutex inbound

**Outbound (server → client) already has a vehicle.** `V1State.sse_streams` is a
`HashMap<session_id, mpsc::UnboundedSender<TransportMessage>>`
(`v1_session.rs:121, 148`), and `route_to_session_stream` (`:292`) hands a `TransportMessage` into
it. `Server::run()`'s drain task does exactly the same job against a `Transport`. So:

1. At `StreamableHttpServer` construction, build a `ServerRequestDispatcher` +
   `DispatchPeerHandle` **once** and store the `Arc<ServerRequestDispatcher>` on `ServerState`
   (NOT inside the `Mutex<Server>` — see Pitfall 3), and set `Server::peer_handle` so
   `attach_peer` (`src/server/mod.rs:1207-1216`) starts populating `extra.peer`.
2. Spawn a drain task per session (or one shared drain that routes by session) that wraps each
   `(correlation_id, ServerRequest)` as `TransportMessage::Request` and calls
   `route_to_session_stream`.
3. **Inbound correlation:** classify a JSON-RPC *response* envelope at the very top of
   `handle_post_request`, before `resolve_v2_gate` and before `extract_and_validate_auth`, and
   hand it straight to `dispatcher.handle_response(...)`, returning 202. This is the deadlock
   fix, not an optimization.

**Session→peer binding is required for correctness.** A peer handle must route to *the session
that issued the request*, otherwise a second client's SSE stream receives another client's
`sampling/createMessage`. `Server::peer_handle` is a single field, so a single global handle
cannot express this. Two viable shapes:
 - a `SessionPeerHandle` constructed per request and injected via `extra.with_peer(...)` at the
   HTTP dispatch site (mirrors `peer_impl.rs`'s documented "constructed fresh-per-request" model),
   which requires a seam to inject a peer into `RequestHandlerExtra` from the transport rather
   than from `Server`; or
 - a session-keyed router inside one dispatcher, with the session id threaded on the request.

The first is closer to the existing design and to `ServerCore::with_server_request_dispatcher`.

### Pattern 7 — G-3 over v2 stateless HTTP: multi-frame SSE on the POST response

On v2 there are no sessions (`sessions_active_for(_, Some(Era::V2)) == false`, pinned by
`sessions_active_truth_table`) and GET answers 405 (`v2_verb_rejection`). `[VERIFIED: source]`
The only channel is the POST response body. The suite's own client already handles this: its
stateless request helper checks `content-type` for `text/event-stream` and drains SSE frames until
it sees the frame whose `id` matches the request `[VERIFIED: dist/index.js, functions `St`/`Ct`]`.

pmcp currently **never** emits `text/event-stream` on a POST response — the only occurrences of
that string in the transport are the two `Accept`-header validators at
`streamable_http_server.rs:1833-1867` `[VERIFIED: grep]`. `build_response`
(`:1974-1994`) either returns JSON or, for v1 with a session, routes to the stream, or frames one
message with `build_sse_response_from_single_message`. The v2 progress path needs that last helper
generalized to a **stream** that emits queued `notifications/progress` frames as they arrive and
then the final result frame.

The suite's related v2 check `HttpServerNoIndependentRequestsOnStream` constrains this: the
response stream may carry only `IncompleteResult` chunks and notifications, **never** an
independent top-level JSON-RPC request. So on v2 the stream is a notification channel, not a
server→client-request channel; server→client *requests* on v2 remain MRTR
(`InputRequiredResult`), which already works.

### Pattern 8 — G-9: thread the v1 handshake capabilities into `ProtocolContext`

`RequestHandlerExtra::client_capabilities()` reads
`protocol_context.client_capabilities` (`src/server/cancellation.rs:406-410`), which
`resolve_protocol_context` populates only from the v2 `_meta` key
(`src/types/protocol/context.rs:381-388`). The v1 handshake writes to a different place:
`*self.client_capabilities.write().await = Some(init_req.capabilities.clone())`
(`src/server/mod.rs:1684`), reachable publicly via `get_client_capabilities()` (`:972`).

**The fix is one-directional and safe:** at each `RequestHandlerExtra` construction site, when the
resolved era is V1 (or no context resolved) and the server-level lock holds a value, build/augment
a `ProtocolContext` with `.with_client_capabilities(...)`. Construction sites to change, all three
in parity:

| Site | File |
|---|---|
| High-level `Server` tool dispatch | `src/server/mod.rs:2090-2101` (`.with_protocol_context(protocol_context)`) |
| `ServerCore` tool dispatch | `src/server/core.rs:636-651` |
| wasm mirror | `src/server/wasm_core.rs` — **no `RequestHandlerExtra` at all** (it dispatches on method strings and supports only `initialize`/`tools/list`/`tools/call`); `RequestHandlerExtra` is a zero-field stub on wasm32 (`src/server/mod.rs:162`). Verify and record "no change needed" explicitly rather than leaving it unstated. |

Prompt and resource handlers construct `RequestHandlerExtra` too — grep
`RequestHandlerExtra::new(` across `src/` and cover **all** of them, not just `tools/call`.

**Do not** make `client_capabilities()` read the server lock directly: it is a sync method on a
value that is moved into the handler, and the lock is already held by the dispatch path.

### Anti-Patterns to Avoid

- **Deriving the golden literals from pmcp's own serializer.** D-04 forbids it and Phase 115
  reopened four times on exactly this shape (a fence that consults the rule it is checking). Type
  the bytes by hand from `schema.ts`, and cite the line.
- **A second correlation authority for G-3.** `peer_impl.rs:5-9` names this as the anti-pattern
  the `ServerRequestDispatcher` exists to prevent.
- **Matching on parsed `Request` variants for era retirement.** Pitfall 4.
- **"Fixing" `negotiate_protocol_version`.** Out of scope by 118.1 D-domain and Phase 112.
- **Re-recording `tests/v1_lists_golden.rs`.** None of the five fixtures there carries an embedded
  resource in a tool/prompt position, so G-1 should not touch them. If one goes red, that is a
  real v1 wire break in a list/read response and the change is wrong.
- **Lowering `MIN_CHECKS_V1=66` / `MIN_CHECKS_V2=178`.** `scripts/run-conformance-suite.sh:187-188`;
  the README rule is "a floor is never lowered". Closing gaps RAISES executed-check counts.

## Common Pitfalls

### Pitfall 1 — **The G-2/annotations field addition is semver-MAJOR on every representation**

**What goes wrong:** D-02 locks "ships as a 2.x minor" and D-01 asserts "the Rust API is
unchanged". That holds for nesting `resource` (pure serde) but **not** for adding a `blob` carrier
or `annotations` to `Content::Resource`.

**Measured** `[VERIFIED: cargo semver-checks 0.49.0 --list, run locally]`:

| Lint | Severity | Applies to |
|---|---|---|
| `enum_struct_variant_field_added` — *"An enum's exhaustive struct variant has a new field."* | **major** | Adding `blob`/`annotations` to `Content::Resource { .. }` |
| `enum_variant_added` — *"An exhaustive enum has a new variant."* | **major** | Adding a separate `Content::EmbeddedResource(..)` variant instead |
| `enum_variant_marked_non_exhaustive` | **major** | Marking `Content::Resource` `#[non_exhaustive]` to make *future* additions minor |
| `enum_struct_variant_changed_kind` | **major** | Converting the struct variant to a newtype variant |
| `enum_non_exhaustive_struct_variant_field_added` | *minor* | Only available if the variant were **already** `#[non_exhaustive]` — it is not (`src/types/content.rs:60-62` has no such attribute; only `Annotations` at `:21` and `ResourceLinkContent` at `:214` do) |

There is **no** path to blob-or-annotations on this type that semver-checks calls additive.

**Why it happens:** `Content` was declared exhaustive in the v1 era and the 2025-11-25 work
(`Audio`, `ResourceLink`) landed during the v2.0 major window, so the constraint never bit.

**In-repo blast radius, measured** (brace-matched scan over `git ls-files '*.rs'`):
**18 field-bearing** `Content::Resource { … }` sites (construction or exhaustive pattern) — 6 in
`src/` (`composition/mcp_client.rs:367`, `server/simple_resources.rs:38/58/350`,
`types/content.rs:398/435`), 12 outside (`benches/`, `cargo-pmcp/src/templates/mcp_app.rs:251,464`,
`crates/pmcp-server/src/resources/docs.rs:106`, four `examples/`, `tests/protocol_invariants.rs:122`,
`tests/toolresult_property_tests.rs:23`, two spike copies). **46** sites already use a `..` rest
pattern and are unaffected. So the *repo* cost is trivial; the *published contract* cost is not.

**How to avoid / resolve — this is a decision, not a technique.** Present the planner with three
dispositions and make the choice a `checkpoint:human-verify gate="blocking"` **before** Wave 1
writes code:

- **(A) Accept a documented major-lint delta in a 2.x minor.** Batch every breaking change into
  one edit: add `blob` + `annotations`, mark the variant `#[non_exhaustive]` *at the same time*
  (so all future spec fields are minor), and ship constructors (`Content::resource_with_blob`,
  `.with_annotations`). Record the accepted `cargo semver-checks` delta explicitly in the phase
  gate rather than letting it read as a regression. Contradicts the letter of "provably still
  additive"; note `#[non_exhaustive]` on the variant makes external struct-literal construction
  impossible *forever*, so the constructors are mandatory, not optional.
- **(B) Split the cluster.** G-1 (nesting) lands now as a genuine wire-only, semver-clean fix;
  G-2 (`blob`) and `annotations` are **DEFERRED** under D-10 with a named owner and a 3.0 trigger.
  Cost: `resources-read-binary` stays red (2 checks) and `tools-call-embedded-resource`'s blob
  branch is untested. D-10 already provides the machinery for this outcome.
- **(C) Defer the whole cluster to 3.0.** Rejected on its face — G-1 is the largest single source
  of red scenarios (4 of 11 v1 scored failures, 4 of 7 v2).

**Warning signs:** a plan that says "cargo semver-checks 223/223 no update required" as a Wave-1
acceptance criterion. Under (A) that criterion is unsatisfiable and its presence means the
decision was never made.

### Pitfall 2 — G-2 has TWO emitters, and the flat one is easy to forget

**What goes wrong:** the nested `EmbeddedResource` fix makes `tools-call-embedded-resource` green
but leaves `resources-read-binary` red, because `ReadResourceResult.contents` goes through
`resource_contents_serde::serialize` (`src/types/content.rs:325-376`), whose private shadow struct
`Rc<'a>` has exactly four fields: `uri`, `mime_type`, `text`, `meta`. **No `blob`.**
`[VERIFIED: source]`

The suite's requirement `[VERIFIED: dist/index.js @ 447562]`: `resources/read` on
`test://static-binary` must return `contents[0]` with `uri`, `mimeType` **and** `blob`. The
measured failure is literally `Content missing uri; Content missing blob field`.

**How to avoid:** treat "`Rc<'a>` gains a `blob` field, and `resource_contents_serde::deserialize`
learns to read one" as a task line item in the same plan as the nested emitter, with its own
golden. Field order in `Rc<'a>` is wire order (`preserve_order`) — keep `uri, mimeType, text,
blob, _meta` or whatever the golden pins, consistently.

### Pitfall 3 — **G-3 will deadlock if the inbound response POST is not routed before the server mutex**

**What goes wrong:** `dispatch_request_or_retire` (`streamable_http_server.rs:2975-3005`) does
`let server = state.server.lock().await;` and then `.handle_request_with_context(...).await` —
**the tokio mutex is held for the entire duration of the tool handler.** A handler that awaits
`peer.sample()` therefore holds it while waiting for the client's answer.

The client's answer arrives as a POST. On the fast path
(`handle_post_fast_path_inner:3593-3648`), the stages before the
`TransportMessage::Response(_) => 202 Accepted` arm are:
`read_and_classify_fast` → `resolve_v2_gate` (which calls `run_v2_header_gate`, taking
`state.server.lock().await` **twice** at `:1483` and `:1499`) → `extract_and_validate_auth`
(`:2049`, another lock). `[VERIFIED: source]` All three block on the mutex the parked handler
holds. **Guaranteed deadlock**, bounded only by the dispatcher's own timeout.

**Why it happens:** the transport was designed with no server→client channel, so no path ever
needed to re-enter while a handler was in flight. `Server::run()` solved the same problem with the
Phase-108 Transport Actor (`src/server/mod.rs:1176-1200`): a single owning actor task plus
unbounded `send_tx`/`request_tx` channels, precisely so *"an in-tool `peer.sample()` /
`.list_roots()` round-trip cannot deadlock the loop"*. The HTTP transport has no equivalent.

**How to avoid:** classify a JSON-RPC **response** envelope (an object with `id` and
`result`/`error` and no `method`) at the very top of `handle_post_request`, before any of the
three lock sites, and hand it directly to an `Arc<ServerRequestDispatcher>` living on
`ServerState`. Return 202. The dispatcher must NOT live behind `Mutex<Server>`.

**Warning signs:** a plan task that says "wire `peer_handle` in `make_server_state`" and nothing
about the inbound path. A test that passes because the tool never actually awaits the peer. Add a
**timeout-bounded** integration test — a hung test looks like a slow test in CI.

### Pitfall 4 — G-5's suite probes never become a typed `Request`

**What goes wrong:** a fix that adds `ClientRequest::Initialize(_)` and
`ClientRequest::SetLoggingLevel{..}` to `v2_retired_method_of` will appear to work in unit tests
and change nothing against the suite. The suite sends `params: {_meta: <full meta>}` and nothing
else `[VERIFIED: dist/index.js @ 374371]`. `InitializeParams` requires `protocolVersion`,
`capabilities`, `clientInfo`; `SetLoggingLevel` requires `level`. Both fail the typed parse, so
`dispatch_request_or_retire` — which takes a `Request` — is never reached. They currently reach
`map_unparsed_body_for_v2` instead, whose own rustdoc records the consequence as a
*"KNOWN LIMITATION"*: a known method with bad params is reported as `-32601`/404. That is why
`initialize` and `logging/setLevel` already **pass** — for the wrong reason — and only `ping`
(which parses fine and answers `{}` at 200) fails.

**How to avoid:** retire on the method **string**, at the ingress. And do **not** validate the fix
against those two suite checks (they were already green); validate it with a direct wire test that
sends `initialize` and `logging/setLevel` with *well-formed* params on v2 and asserts 404 +
`-32601`. This is exactly the 118.1 `<specifics>` warning made concrete.

**Warning signs:** a Wave-2 acceptance criterion of the form "`server-stateless` gains 2 checks".
It will gain **1** (`ping`), and the other two were never lost.

### Pitfall 6 — a `#[serde(try_from)]` container attribute changes error messages and Debug output paths

### 2 — shadow wire type + tolerant reader (the recommended G-1/G-2 mechanism)

```rust

//   #[serde(try_from = "String", into = "String")]

/// The SPEC wire shape for an embedded resource, borrowed from a `Content::Resource`.
#[derive(Serialize)]
#[serde(rename_all = "camelCase")]
struct EmbeddedResourceWire<'a> {
    // field order IS wire order (serde_json `preserve_order`, Cargo.toml:55)
    uri: &'a str,
    #[serde(skip_serializing_if = "Option::is_none")]
    mime_type: &'a Option<String>,
    #[serde(skip_serializing_if = "Option::is_none")]
    text: &'a Option<String>,
    #[serde(skip_serializing_if = "Option::is_none")]
    blob: &'a Option<String>,
    #[serde(rename = "_meta", skip_serializing_if = "Option::is_none")]
    meta: &'a Option<serde_json::Map<String, serde_json::Value>>,
}

// Emitter: hand-written, BORROWED (no clone of a base64 blob per response).
// Only the Resource arm is hand-shaped; the other four delegate to the same
// derived shapes they have today via a `#[derive(Serialize)]` shadow enum.

// Reader: derived, via the container attribute — the tolerant half lives in
// `WireContentIn`, whose Resource variant accepts EITHER
//   {"type":"resource","resource":{...}}            (spec, D-03 emit shape)
//   {"type":"resource","uri":...,"text":...}        (legacy pmcp flat, D-03 accept-only)
// e.g. with an inner `#[serde(untagged)] enum ResourcePayload { Nested{resource: ..}, Flat{uri: ..} }`
#[derive(Debug, Clone, Deserialize)]
#[serde(try_from = "WireContentIn")]
pub enum Content { /* unchanged public shape */ }
```

## Security Domain

`security_enforcement` is not set to `false` in `.planning/config.json`, so this section is
included.

### Applicable ASVS categories

| ASVS category | Applies | Standard control in this phase |
|---|---|---|
| V2 Authentication | no | No auth surface changes. G-3 must NOT bypass `extract_and_validate_auth` for *requests* — only for inbound *responses*, which carry no authority (see below). |
| V3 Session Management | **yes** | G-3's v1 path keys the server→client channel by `Mcp-Session-Id`. A peer handle bound to the wrong session delivers one client's `sampling/createMessage` into another client's SSE stream. The existing `route_to_session_stream` gate (`sessions_on`) exists because of exactly this defect (T-113-07, `streamable_http_server.rs:1965-1973`). |
| V4 Access Control | **yes** | `peer_impl.rs`'s module doc states the invariant: *"Peer calls inherit the originating tool's authorization context. Tool-level authz runs BEFORE the dispatch site wires `peer`."* Any HTTP peer injection must preserve that ordering. |
| V5 Input Validation | **yes** | Two surfaces: (a) the D-03 tolerant reader parses **untrusted** server output when pmcp acts as a client — fuzz it; (b) G-3's inbound correlation accepts a client-supplied `id`/correlation token — it must be bounded, must not allocate per unknown id, and must not be usable to cancel or forge another session's pending request. |
| V6 Cryptography | no | No crypto changes. `PMCP_REQUEST_STATE_KEY` and the AEAD `requestState` codec are untouched. |
| V7 Error Handling & Logging | **yes** | G-6/G-8 change what error codes and messages reach the wire. Error `message` strings must not echo attacker-controlled `_meta` content verbatim (the existing rejections use `&'static str` constants — keep that discipline). |

### Known threat patterns for this stack

| Pattern | STRIDE | Standard mitigation |
|---|---|---|
| Cross-session response injection: a client POSTs a JSON-RPC response with a correlation id it did not receive, resolving another session's pending `sampling/createMessage` | Spoofing / Tampering | Correlation ids must be server-minted, unguessable, and **scoped to the session that received the request**. `ServerRequestDispatcher` mints them; the HTTP inbound path must verify session ownership before calling `handle_response`. This is a NEW attack surface the phase creates. |
| Unbounded pending-request growth: a client opens an SSE stream, triggers N tools that each park on a peer call, and never answers | DoS | The dispatcher already has `with_timeout(..)`. Ensure the HTTP path configures one and that a timed-out peer call releases the server mutex. |
| Deadlock as a DoS: one parked handler holding `Mutex<Server>` stalls **every** request on the transport | DoS | Pitfall 3's fix is also the security control. A single malicious tool call would otherwise take the whole server offline. |
| Memory amplification via the tolerant reader: a hostile flat/nested hybrid causing repeated buffering | DoS | `try_from`-based deserialization buffers the value once; keep the existing `MAX_*` body bounds (`v2_bounded_reads_tripwire.rs` guards these) and add a fuzz invariant on allocation shape. |
| Blob content treated as text: a `blob` field carrying a base64 payload rendered as `text` by a lenient reader | Tampering / Injection | The nested `resource` is `TextResourceContents | BlobResourceContents` — an XOR in the spec. The reader must not accept both `text` and `blob` on the same object; reject or prefer deterministically and document which. |
| Capability spoofing via G-9: a v1 client's self-reported `initialize` capabilities becoming an authorization input | Elevation of Privilege | `RequestHandlerExtra::client_capabilities()`'s rustdoc already states these are SELF-REPORTED and MUST NOT anchor authorization. G-9 widens *who can read* them; keep that warning and repeat it on the new v1 path. |
