## Decisions Made

- **Each golden is TWO tests, not one test with two legs.** A single test would run v1 then v2, and the v1 assertion panics — so the v2 leg would be *unreachable* for the entire life of this plan. A v2 leg that never reached the server (bad header, malformed `_meta`, a 400) would then be indistinguishable from a v2 leg that simply had not run yet, and the "both eras" claim would be unfalsifiable until 118.1-03. Splitting them produced the 8 independent failures above, including the four v2 ones that prove the v2 path works end to end today.
- **The two legs pin different amounts, deliberately.** The v1 leg (`spawn_stateless_config`, `enable_json_response: true`) pins the FULL frame byte for byte. The v2 leg (`spawn_default_config`, SSE-framed) pins the content ITEM as a byte-exact substring plus the era witness. Pinning the full v2 frame would make CONF-04's fence fail whenever Phase 112's envelope or Phase 115's caching hints changed — two files in charge of the same bytes. The v2 raws above show exactly what would have been swept in: `resultType`, a namespaced `_meta` `serverInfo`, and on `resources/read` also `ttlMs`/`cacheScope`.
- **ONE v2-opted-in fixture server serves both legs.** The REQUEST selects the era, which is strictly stronger than pointing a v1 body at a server that could not have answered v2 anyway. `tests/v1_lists_golden.rs` deliberately does the opposite because D-11 freezes the NOT-opted-in configuration's bytes; that is a different claim from this file's.
- **Goldens 3 and 4 are authored through `serde_json::from_value::<Content>` of the flat legacy JSON.** There is no typed route: `Content::Resource` carries neither `blob` nor `annotations` today, and `Content::resource_with_text` is the only resource constructor. Deserializing the flat object is the only authoring path that COMPILES on the unfixed tree, and it doubles as a D-03 tolerant-reader exercise from the flat direction. Today `Content` has no `deny_unknown_fields`, so both fields are silently dropped — which is *why* those two goldens are red.
- **The leak guard does not flag flat `ReadResourceResult.contents` elements.** They carry no `type` tag (the projection strips it), so they never match the guard's precondition — and the negative control asserts that acceptance explicitly, because a guard that forbade the flat contents shape would forbid the very shape D-01 requires there.
