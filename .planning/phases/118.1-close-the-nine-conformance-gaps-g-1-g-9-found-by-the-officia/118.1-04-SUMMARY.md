## The `@maxItems 100` enforcement strategy

`schema/vendored/core-2026-07-28/schema.ts:2649` annotates `values: string[]` with
`@maxItems 100` in prose that no generated Rust type carries.

**Truncate, do not reject.** A provider returning 150 candidates is not malformed — it is more
specific than the wire allows — and refusing the whole answer would turn a working completion
into an error. The truncation reports itself:

| Provider returns | `values.len()` | `hasMore` | `total` |
|---|---|---|---|
| 7, `has_more: false` | 7 | `false` | `Some(7)` |
| 100, `has_more: false` | 100 | `false` | `Some(100)` |
| 101, `has_more: false` | 100 | **`true`** | `Some(101)` — the TRUE total, dropped element included |
| 3, `has_more: true` | 3 | `true` | **`None`** — the true total is unknown |

`has_more` is set when the provider itself reported more **or** when this function dropped
elements, so a client can never read a truncated list as exhaustive. `total` is emitted only when
the provider returned everything it had; inventing a total when the provider says more exist
would be worse than omitting an optional field.

This closes **T-118.1-04-01** (unbounded `values` from a peer-driven provider). It is asserted
three ways: a deterministic unit test per row above
(`src/server/core.rs` `tests::completion`), a proptest over lengths `0..250` driven through the
real `ServerCore` dispatcher, and — critically — the proptest restates the bound as
`SPEC_MAX_VALUES = 100` from the schema rather than importing `MAX_COMPLETION_VALUES`, because a
fence that reads the same constant as the implementation cannot catch a wrong constant.

**T-118.1-04-02** (a file-backed provider enumerating paths) is ACCEPTED as the threat register
specified: `FileCompletionProvider` is opt-in, registered by the server author, and already
scoped by `with_base_dir`. No new access-control surface was added in this plan.

## Decisions Made

1. **A single, server-wide provider — not a name-keyed registry.** The spec routes every
   `completion/complete` to one seam and passes the `ref` (`ref/prompt` / `ref/resource`) as
   data. A per-name registry would invent a dispatch dimension the protocol does not have. This
   is the `resources` shape the plan specified, not the `prompt` shape.
2. **The `ref` travels in `CompletionRequest::context`.** That type has no dedicated ref slot and
   is public, so extending it would be a breaking change for a plan whose whole point is a
   conformance fix. The context keys are spelled exactly as the wire discriminators
   (`ref/prompt`, `ref/resource`), so a provider matching on them is matching on the protocol's
   vocabulary, not an SDK alias. Exposed as `pub(crate)` constants
   (`COMPLETION_REF_PROMPT_KEY` / `COMPLETION_REF_RESOURCE_KEY`) so the tests cannot re-spell
   them.
3. **`ServerCore` takes the provider via `with_completions`, not `ServerCore::new`.**
   `ServerCore::new` is `pub` and already carries `#[allow(clippy::too_many_arguments)]` with 18
   parameters; adding a nineteenth would break every external `ServerCore::new` call site for a
   field that has a working additive precedent (`with_suppress_double_wrap`,
   `with_server_request_dispatcher`, `with_supported_protocol_versions`).
4. **A failing provider surfaces its error as `-32603 INTERNAL_ERROR`, not an empty array.**
   Swallowing a provider failure into `values: []` would make a broken provider indistinguishable
   from an unregistered one. Pinned by `a_failing_provider_surfaces_its_error`.
5. **The example's provider values are prefixed `test`.** `StaticCompletionProvider` filters by
   prefix against `partial`, and the suite sends `argument.value = "test"`. A provider whose
   values could not match would exercise the seam without demonstrating it — the scenario would
   still score (an empty array is a pass) but the artifact would prove nothing.
6. **The provider-reachability tests drive an EMPTY partial.** Same filter, opposite direction:
   `PROVIDER_VALUES` are deliberately un-`test`-prefixed so they cannot be confused with the
   example's, which means the suite's `"test"` partial would filter them all out. Those two tests
   are about the seam being wired, not about the filter working.
