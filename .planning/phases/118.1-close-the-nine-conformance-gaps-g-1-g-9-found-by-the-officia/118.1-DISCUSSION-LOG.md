## G-1 wire-format route

### Q1 — How should G-1 close the EmbeddedResource nesting gap?

| Option | Description | Selected |
|--------|-------------|----------|
| Fix the default, keep flat projection | Derived `Serialize` emits spec `EmbeddedResource`; `resource_contents_serde` keeps `ReadResourceResult` flat. Rust API unchanged, wire output changes on both eras. | ✓ |
| Era-gate it: v2 nests, v1 stays flat | Projection chokepoint in the `project_caching_hints` shape. No v1 break, but knowingly leaves v1 non-conformant on an era-independent gap. | |
| New additive `Content` variant | `Content::EmbeddedResource` beside the flat `Resource`, deprecating the latter. Non-breaking, but conformance only improves as 130 call sites migrate. | |

**User's choice:** Fix the default, keep flat projection.
**Notes:** Scouting reframed the option set before the question was asked — `Content::Resource`
serves two different spec types, and the flat shape is *correct* for `ReadResourceResult`
(`ResourceContents` is flat) and *wrong* only in the tool/prompt position. Two sub-questions
resolved as facts rather than choices: `_meta` and `annotations` sit at content level in the spec
(`schema.ts:1740-1744`), so the MCP Apps widget path is already correct; and `resource` being
`TextResourceContents | BlobResourceContents` means G-2 rides the same edit.

### Q2 — pmcp is at 2.18.0 and v2.5 is declared additive/no-3.0. How does the wire change ship?

| Option | Description | Selected |
|--------|-------------|----------|
| 2.x minor — conformance fix | Spec non-conformance is a defect, not a contract. Rust API semver unbroken. CHANGELOG wire-change callout + migration note. | ✓ |
| 2.x minor + one-release opt-out | Server-side flag restoring flat bytes for one cycle, defaulting to spec-correct. | |
| Hold for 3.0 | Treat the wire format as public contract; defer G-1 and G-2 to a major. | |

**User's choice:** 2.x minor — conformance fix. No opt-out.
**Notes:** Presented alongside the finding that `cargo semver-checks` and `cargo public-api` are
structurally blind to this change, and that the existing golden suite's blind spot is precisely the
tool-result embedded-resource position.

### Q3 — What should pmcp ACCEPT on the read side once it emits the nested shape?

| Option | Description | Selected |
|--------|-------------|----------|
| Tolerant reader, strict emitter | Accept both shapes in, emit only nested. Fixes the client-side parse defect; tolerance documented as a compatibility affordance. | ✓ |
| Strict both ways | Accept only nested. Smallest code; immediately breaks pmcp clients against 2.18-and-earlier servers. | |
| Tolerant now, strict at 3.0 | Same tolerance, plus deprecation and a `tracing` warning on the flat path. | |

**User's choice:** Tolerant reader, strict emitter.
**Notes:** The question was prompted by a defect found mid-discussion: `Content` has only the
derived `Deserialize`, so a spec-conformant `{"type":"resource","resource":{...}}` from another
SDK's server fails to parse today. The conformance suite tests pmcp as a *server* and could never
have caught it.

### Q4 — What proves D-01 landed and stays landed?

| Option | Description | Selected |
|--------|-------------|----------|
| Spec-derived byte literals + conformance oracle | Extend `v1_lists_golden.rs` to the tool/prompt embedded-resource positions on both eras, bytes derived from vendored `schema.ts`, each fence demonstrated RED first. | ✓ |
| Conformance scenarios only | Let the four suite scenarios flipping green be the proof. | |
| Structural assert on the serialized shape | Assert a `resource` object exists rather than pinning bytes. | |

**User's choice:** Spec-derived byte literals + conformance oracle.
**Notes:** Option 3 was presented with its own counter-argument — this repo has been bitten four
times by fences that restate the code's own rule, which is exactly what a structural assert written
against pmcp's serializer would be.
