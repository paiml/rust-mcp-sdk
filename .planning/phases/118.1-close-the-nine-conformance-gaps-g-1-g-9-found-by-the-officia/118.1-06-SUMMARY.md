# Phase 118.1 Plan 06: Close G-6 and G-8 — the Three-Way v2 `_meta` Rule Summary

The v2 `_meta` gate stopped being a 2x2 era matrix. An ABSENT required key and a PRESENT-but-
disagreeing `protocolVersion` are now different verdicts with different spec-allocated codes, and
the header/`_meta` agreement check moved ahead of the accept list.

## Task 1 — The Blast-Radius Sweep (RESEARCH assumption A4 is FALSIFIED)

assumed. **RESEARCH assumption A4 — that the in-tree surface is safe — is FALSE.** Six sites had
to be fixed, spanning `tests/`, `src/` unit tests and `examples/`.

### The property test's oracle is genuinely independent

`referee_verdict` is a hand-written transcription of the suite's rule that calls **nothing** from
`pmcp` except the three error-code constants it compares against. The six literal tests above are
its calibration — each is one point on the surface, asserted separately against the referee's own
rpcId. This is the shape RESEARCH demands after Phase 115 reopened four times on properties whose
oracle was the predicate under test.

The matrix is `HeaderCase{V2, Legacy, Unsupported, Absent} x MetaCase{Absent, NoVersion, V2Version,
LegacyVersion, UnsupportedVersion} x caps{true,false}` = 40 cells, sampled 120 times over one
long-lived server and one runtime.

### Two corrections the plan's test sketch required

1. **The v1 half needs a session.** `spawn_default_config` is STATEFUL, so a v1 non-`initialize`
   request with no `Mcp-Session-Id` answers `-32600 "Session ID required for non-initialization
   requests"` — a v1 session guard with nothing to do with `_meta`. The first RED run showed exactly
   that. The v1 control and the property test now mint a session with a v1 `initialize` first and
   carry `Mcp-Session-Id` on every request (v2 ignores it). The plan's instruction to use
   `spawn_default_config` was still correct and is unchanged — `stateless()` would have made the
   per-request era gate vacuous.
2. **The property test drives `tools/list`, not `server/discover`.** `server/discover` is v2-ONLY:
   on v1 it correctly answers `-32601`, which would have made every v1 cell of the matrix a
   rejection for a reason unrelated to `_meta`. The six literal rows still target `server/discover`,
   exactly as the referee does. Exercising the rule on a second method strengthens the claim — it is
   a transport gate, so it is method-independent.
3. **The v1 control and the proptest are `#[cfg(feature = "v1-compat")]`-gated**, following the
   sibling pattern in `tests/v2_stateless_http.rs`: on a `--no-default-features --features full-v2`
   build there is no v1 half to contrast against. The six v2 rows stay ungated and keep running on
   the severed build.

## Task 3 — What Landed

### The three-way classifier

`V2Classification` and `classify_era_cell` were **deleted**. In their place:

```rust
enum V2MetaVerdict {
    Defer,                          // no v2 signal, or a carrier only the resolver can diagnose
    MissingRequired(&'static str),  // -32602
    Disagreement(&'static str),     // -32020
    Enforce,                        // both sides agree on 2026-07-28
}
```

`classify_v2_meta_version(header, raw_meta)` is pure, total and non-panicking, reading an
already-decoded header classification and an already-parsed JSON value. Named predicates —
`raw_meta_protocol_version` and `raw_meta_object_has_key` — carry the two reads, so nothing nests.

Deleting `classify_era_cell` rather than leaving it in place was necessary, not cosmetic: with the
three-way rule in front of it, **both** of its `Reject` arms became unreachable. An unreachable
branch with a passing test asserting it is precisely the false green this phase exists to remove.
Its truth-table test was replaced by `classify_v2_meta_version_covers_every_row`, which pins
fourteen literal rows including the three the 2x2 could not express.

### The ordering fix, quoted in order (the acceptance criterion)

From `src/server/streamable_http_server.rs`, inside `run_v2_header_gate`:

```rust

// :1806

    return (None, V2GateOutcome::Reject { code: HEADER_MISMATCH, message: message.to_string(), data: None });

```

`1806 < 1826`. That is the whole of G-8: the disagreement check already existed, it just ran after
the accept list had already failed the request with `-32022`.

The rest of the gate, in order:

```rust
// :1841
let outcome = classify_v2_request(headers, verdict, body_method, body_name.as_deref());
// :1846  — v2 METHOD RETIREMENT (plan 05)
let outcome = retire_v2_method(outcome);
// :1850  — the required clientCapabilities key
let outcome = require_v2_client_capabilities(outcome, raw_meta.as_ref());
```

### Why the rule is split across two positions

This is the one structural decision the plan left open, and it is deliberate.

- The **version half** (absent `_meta`, absent `protocolVersion`, disagreement) must precede era
  resolution: without a protocol version there is no era, and "is this method retired on v2?" is not
  a well-formed question until there is one.
- The **`clientCapabilities` half** runs AFTER `retire_v2_method`. A method the 2026-07-28 schema
  REMOVED has no params contract to violate; answering `-32602 your params are wrong` for a method
  that does not exist is both misleading and a regression risk against the suite's five
  `HttpServerMethodNotFound404*` checks. Measured: the suite sends the full `_meta` on those probes,
  so both orderings pass it today — the ordering was chosen on the principle, and it makes the
  refusal correct for any future caller that does not.

### The v2-only scope, and what was NOT changed

`parse_reserved_object`'s `Ok(None)` contract for an absent key is **UNCHANGED**, and
`resolve_protocol_context` was not touched at all. The plan offered the alternative of adding a
v2-scoped inspection inside the resolver; that was declined. The reason is `resolve_negotiated_version`'s
`None` arm — it IS the v1 fallback (`src/types/protocol/context.rs:415-421`), so any hard
requirement there rejects every v1 request on the server (T-118.1-06-03). The transport gate already
holds both halves of what the rule needs: the header, and the raw body. The executable proof is
`v1_requests_omitting_client_capabilities_are_still_served`, which sends a v1 `tools/list` carrying a
`_meta` with a v1 `protocolVersion` and **no** `clientCapabilities` and asserts 200 with a `tools`
array — the shape that would trip a rule keyed on "`_meta` is present".

`src/types/protocol/context.rs` appears in the plan's `files_modified` list and was **NOT** modified.
It did not need to be: `RESERVED_PROTOCOL_VERSION_KEY` and `RESERVED_CLIENT_CAPABILITIES_KEY` are
already `pub(crate)`, so the gate reads the SAME constants the resolver reads and the two cannot
drift.
