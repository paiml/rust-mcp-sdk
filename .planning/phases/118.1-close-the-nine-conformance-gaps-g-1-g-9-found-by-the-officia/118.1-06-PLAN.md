<objective>
Close G-6 and G-8 together: turn the v2 `_meta` gate from a 2x2 era classifier into a three-way rule
that distinguishes an ABSENT required key from a MALFORMED one, and run the header/`_meta` agreement
check BEFORE the accept-list check so a disagreement answers `-32020` instead of `-32022`.

Purpose: `_meta` validation currently answers `-32020` where the spec wants `-32602` plus HTTP 400,
and never rejects a missing `clientCapabilities` at all — `parse_reserved_object` returns `Ok(None)`
for an absent key. G-8 is a pure ORDERING defect: pmcp resolves the `_meta` version first, fails the
accept list, and returns `-32022`, so the disagreement never gets a chance to classify.

Output: a three-way classifier, corrected check ordering, and a six-row truth table proved by literal
contract tests plus a property test.
</objective>

From `conformance/node_modules/@modelcontextprotocol/conformance/dist/index.js` at offsets 366019,
370104 and 371612, the full required behaviour. All probes target `server/discover`:

| Condition | Required code | Required HTTP | Suite check (rpcId) |
|---|---|---|---|
| `params._meta` absent entirely | `-32602` | 400 | `RequestMetaInvalid` missing-meta (101) + `HttpServerMetaInvalid400` |
| `_meta` present, `io.modelcontextprotocol/protocolVersion` key absent | `-32602` | 400 | `RequestMetaInvalid` missing-protocol-version (102) |
| `_meta` present, `io.modelcontextprotocol/clientCapabilities` key absent | `-32602` | 400 | `RequestMetaInvalid` missing-client-capabilities (104) |
| `_meta` present, `io.modelcontextprotocol/clientInfo` key absent | **success** | **200** | `RequestMetaClientInfoOptional` (105) — clientInfo is a SHOULD, do NOT make it required |
| `protocolVersion` present, EQUAL to the header, but unsupported | `-32022` + `data.supported[]` + `data.requested` | 400 | `ServerUnsupportedVersionError` + `HttpServerUnsupportedVersion400` (301) |
| `protocolVersion` present, DIFFERENT from the header | `-32020` | 400 | `HttpServerHeaderMismatch400` (302) |

On EVERY one of these, `HttpServerErrorJsonrpcId` additionally requires the error response to echo
the request id.

The ordering fact that makes G-8 a pure ordering fix: at rpcId 302 the suite sends
`_meta.protocolVersion = "v999.0.0"` with header `MCP-Protocol-Version: 2026-07-28`. pmcp resolves
the `_meta` version first, fails the accept list in `resolve_negotiated_version`, and returns
`-32022` through `negotiation_error_to_gate_reject`. At rpcId 301 header and `_meta` AGREE (both
`v999.0.0`), so the accept-list check must still fire and produce `-32022`.

Today's classifier — `src/server/streamable_http_server.rs:970-988`,
`fn classify_era_cell(header: HeaderProtocolVersion, meta_is_v2: bool) -> V2Classification`, a 2x2
over `(header_is_v2, meta_is_v2)` returning `Enforce`, `Legacy`, or `Reject(HEADER_MISMATCH, msg)`
with `&'static str` messages.

Today's absent-vs-malformed collapse — `src/types/protocol/context.rs:420-437`,
`fn parse_reserved_object` returns `Ok(None)` for an absent key and `MalformedMeta` for a present
but undeserializable one. `resolve_protocol_context` (`:356-392`) calls it for both
`RESERVED_CLIENT_INFO_KEY` and `RESERVED_CLIENT_CAPABILITIES_KEY`.

CRITICAL SCOPE CONSTRAINT: `resolve_protocol_context` serves BOTH eras — its `None` arm at
`resolve_negotiated_version:415-421` is the v1 fallback. The required-key rule is V2-ONLY and must
live in the transport gate, not in the shared resolver. See the Architectural Responsibility Map:
"The rule is a header/body cross-check plus a required-field check — both transport-layer, both
already resident in the gate."

HTTP status comes free: `v2_status_for_code` (`:735-747`) already maps `INVALID_PARAMS` to 400.

Error-code constants by name from `src/types/protocol/error_codes.rs`: `INVALID_PARAMS:71`,
`HEADER_MISMATCH:191`, `UNSUPPORTED_PROTOCOL_VERSION:233`. Never type an integer.
