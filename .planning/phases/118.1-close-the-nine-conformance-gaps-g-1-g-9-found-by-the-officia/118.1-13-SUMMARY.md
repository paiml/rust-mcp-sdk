#### (i) The three elicitation failures — a STALE FIXTURE, provably not an SDK gap

All three come from one place, `examples/s54_v2_dual_conformance.rs:934-940`:

```rust
// All three elicitation tools hit the same wall: pmcp's
// `PeerHandle` exposes `sample`, `sample_with_tools`, `list_roots`
// and `progress_notify` — there is no `elicit`, and the
// `ElicitationManager` that would issue one is not reachable from a
// handler. Recorded as an SDK gap in this plan's SUMMARY.
"test_elicitation"
| "test_elicitation_sep1034_defaults"
| "test_elicitation_sep1330_enums" => Err(pmcp::Error::internal(
    "no server->client channel on this transport: elicitation/create cannot be issued",
)),
```

**Every factual claim in that comment is now false.**

| Claim in the comment | Measured reality |
|---|---|
| "there is no `elicit`" | `PeerHandle::elicit` is declared at `src/shared/peer.rs:172` and implemented at `src/server/peer_impl.rs:114` (plan 09, D-07). |
| "not reachable from a handler" | `tests/http_peer_roundtrip.rs:924` `http_peer_elicit_completes_over_a_v1_session` **PASSES** — a tool handler calls `extra.peer().elicit(...)` and the round trip completes over v1 stateful HTTP. |

The suite corroborates from the other side: on the same v1 leg, `tools-call-sampling` and
`tools-call-with-progress` — which use the *same* transport seam — both moved to
`2 passed, 0 failed`. The transport works; only these three tool bodies never learned to use it.

The example is the measurement target, so a stale hardcoded refusal in it produces a **false

#### (ii) `tools-call-with-logging` — a GENUINE SDK surface absence

Failure text: `No log notifications received`. The scenario wants server→client
`notifications/message` records emitted *during* a tool call.

Searched exhaustively:

- `PeerHandle` (`src/shared/peer.rs:74`) is exactly `{ sample, sample_with_tools, list_roots, elicit, progress_notify }`. No log method.
- `RequestHandlerExtra` (`src/server/cancellation.rs`) exposes `report_progress`, `report_percent`, `report_count` — and no logging analogue.
- `ServerNotification::LogMessage` (`src/types/notifications.rs:135`) is **constructed only in tests**: `src/types/notifications.rs:278`, `src/types/subscriptions.rs:920`, `src/server/subscriptions.rs:1459`. No production code path emits it. The remaining two hits (`src/shared/protocol_helpers.rs:404,1044`) are serialisation match arms.
- The example's `test_tool_with_logging` uses `tracing::info!`, which reaches the process's tracing subscriber and never the MCP wire.

So this one is real, and it sits in **G-3's `notification_tx` half** as the gap table words it
("`notification_tx` and `peer_handle` are set **only** in `Server::run()`"). Plans 10/11 wired
the peer handle and the progress path; nothing wired — or exposed — a handler-facing log
notification. Adding one is a new public trait method, i.e. **Rule 4 architectural**, and is
correctly out of scope for a measurement plan.

**Worth the developer's attention:** CONF-07's own text does *not* ask for this. It asks for
`peer.sample()` / `peer.list_roots()` / `peer.elicit()` over v1 HTTP, progress on both eras,
and `set_result_meta` on the verbatim path — all three of which measure green in-tree. The
requirement as written is satisfied; the suite scenario attributed to G-3 exercises a
capability no requirement in this phase ever asked for.

**The OWS residual is REFUTED.** `headerValue` was `"  test_elicitation  "`, `bodyValue` was
`"test_elicitation"`, and the server answered **HTTP 200** having routed the call to that tool.
pmcp trims the OWS correctly per RFC 9110 §5.5. The check fails only because the tool it
happened to pick then returned the stale elicitation error from (i). In run 1 the suite's
arbitrary `tools/list` pick landed on a benign tool and the same check passed.

**The oscillation SURVIVES, and 118-08's prediction is REFUTED as stated.** 118-08 predicted
closing G-3 would remove it. G-3's *transport* is closed — and the oscillation remains, because
the fixture never used the transport. The prediction was right about the mechanism
(elicitation) and wrong about the cure (the transport was not the blocker). D-09 said to decide
this after measurement; measured, it is decided.

Both residuals therefore collapse into one root cause: **the stale elicitation fixture**.
Fixing it would close 4 of the 5 remaining non-Tasks items in one change — the three scored v1
scenarios *and* the v2 oscillation — leaving only `tools-call-with-logging`.

`http-header-validation` is `pending`/not-scored, so this flap does **not** disturb the v2
leg's exit 0 in either run. It is nonetheless a real nondeterminism in a check the repo will
want to depend on, and plan 14 must not write a v2 pass-count assertion that assumes 142.

### 1. [Rule 3 — blocking issue] No `timeout(1)` on this macOS host

- **Found during:** Task 1, first suite invocation.
- **Issue:** `scripts/run-conformance-suite.sh` fence 9 requires a real `timeout(1)`;
  macOS ships none and coreutils is not installed. The script correctly refused to run
  (`FAILURE: no timeout(1) on PATH`, exit 1).
- **Why not `brew install coreutils`:** a package-manager install is not an auto-fixable
  deviation for an executor agent.
- **Fix:** a faithful `timeout(1)` stand-in written to `target/118.1-13-bin/timeout`
  (gitignored) and reached only via a `PATH` prefix for the single suite command. **The
  repository is untouched and `scripts/run-conformance-suite.sh` is byte-identical** — the
  script resolves `timeout` from `PATH` exactly as it would a brew-installed one.
- **Proven against all four contract points before use**, because a wrong shim could convert
  a hang into a pass — the precise false-green class this phase exists to eliminate:

  | Contract | Test | Result |
  |---|---|---|
  | propagates a zero exit | `timeout 5 sh -c 'exit 0'` | `0` |
  | propagates a nonzero exit | `timeout 5 sh -c 'exit 7'` | `7` |
  | kills on timeout, exits 124 | `timeout 2 sh -c 'sleep 30'` | `124` in **2s**, not 30 |
  | kills the whole process group | `timeout 2 sh -c 'sleep 47 & sleep 47'` | `124`, `pgrep -fl "sleep 47"` → none survived |
  | command-not-found | `timeout 5 /nonexistent/binary` | `127` |

- **CI is unaffected:** Ubuntu runners ship coreutils, so this is a local-host accommodation only.

### 2. [Rule 3 — blocking issue] `PMCP_REQUEST_STATE_KEY` not set

- **Issue:** fence 8 refuses to run without it, correctly — the target example silently derives
  a per-process key otherwise, so the MRTR surface would measure a different server than CI's.
- **Fix:** exported the **same non-production constant CI uses** (`.github/workflows/ci.yml:640`)
  for the run only, never committed and never echoed. Using CI's exact value is what keeps the
  local and CI measurements comparable, which is the fence's stated purpose.

### 3. Tasks 2 and 3 not executed — see "STATUS" above

Not a deviation of convenience: both are gated behind `GAP_ATTRIBUTABLE_FAILURES == 0` by their
own acceptance criteria.

### Nothing was softened

No disposition was weakened, no residual bucket widened to absorb a gap-attributable failure,
and nothing was carried forward to plan 14. The literal attribution set was used exactly as the
