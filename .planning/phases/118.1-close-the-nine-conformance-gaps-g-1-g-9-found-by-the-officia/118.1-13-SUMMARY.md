## The oscillation: my prediction was wrong, and the real cause is broader

`ServerAcceptsWhitespaceHeaderValue` passed in **both** post-fix full runs. That is not evidence
— it also passed in pre-fix run 1. The check depends on `tools/list` ordering, which is a
HashMap iteration order: **re-rolled once per server process and constant within one process**.
An early 10-run probe against a single server returned 10/10 SUCCESS and proved nothing; it
sampled one ordering ten times. That probe was discarded.

`target/118.1-13-bin/ows-oscillation-probe.sh` restarts the server for **every** trial:

| Trials (fresh processes) | SUCCESS | FAILURE |
|---|---|---|
| 14 | **11** | **3** |

**The oscillation survives.** The three failures, with the tool each trial happened to pick:

| Tool picked | Failure | Elicitation-related? |
|---|---|---|
| `test_sampling` (×2) | `Validation error: test_sampling requires prompt` | **No** |
| `test_elicitation_sep1034_defaults` (×1) | `no server->client channel on this transport` | Yes — but correctly |

**The real cause is the check's own design.** It picks an arbitrary tool from `tools/list` and
calls it with an OWS-padded `Mcp-Name` and **no arguments**, requiring a non-error response.
Any tool that legitimately errors on an argument-free call fails it. `test_sampling` requires a
`prompt` and says so — that was never elicitation, never G-3, and would have flapped identically
before this phase began.

The third failure is the **kept** refusal firing correctly: in `http-header-validation` the
client holds no live stream, so `extra.peer()` is genuinely `None` and the tool refuses rather
than hanging. That is the right behaviour — and it is why the refusal was kept rather than
deleted.

### The RFC 9110 OWS-trimming residual is REFUTED, on 14 samples

In every one of the 14 trials the server **trimmed the OWS and routed correctly**:
`headerValue "  <tool>  "` → `bodyValue "<tool>"`, `responseStatus 200`. pmcp honours RFC 9110
§5.5. The check's failures are entirely about what the selected tool then does. The residual
118-05 suspected does not exist.

### What this hands plan 14

**Plan 14 must not write a v2 pass-count assertion.** The v2 total flaps between 141 and 142 on
a measured ~21% per-process rate, in a `pending`/not-scored check, for reasons that are not SDK
defects. A v2 **`exit == 0`** or **scored-failures == 0** assertion is the shape the evidence
supports. The v1 leg still exits 1 and cannot carry an exit assertion, but its check floor can
rise 66 → **74**.
