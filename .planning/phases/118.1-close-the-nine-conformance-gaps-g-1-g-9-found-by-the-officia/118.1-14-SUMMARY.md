## Task 1 — the widening

### The mechanism, and why

The plan offered two shapes: an additional prefix list, or an explicit array of scenario names.
The measurement made a third shape available and it is strictly stronger than either, so the
gate uses **two clauses, each matched to what its leg can actually support**:

| Leg | Clause | Why this shape |
|---|---|---|
| `2026-07-28` | `FULLY_SCORED_GREEN_REVISIONS` — the **entire scored set** green AND the suite's own exit status 0 | **Universally quantified.** No enumeration exists to be shortened, so the one abuse direction an inclusion list has is closed by construction. Strictly stronger than listing all 37 names. |
| `2025-11-25` | `BLOCKING_GREEN_SCENARIOS` — 29 **named** scenarios, each PRESENT and entirely green | That leg cannot carry the universal clause: its 30th scored scenario fails. An explicit array is more legible and more brittle in the right direction; a prefix list would silently admit a future scenario. |

A **prefix list was rejected**: `input-required-result-` works as a prefix because MRTR is a
coherent family, but the 29 v1 scenarios share no prefix, and inventing one would mean a re-pin
that added `tools-call-anything-new` would be admitted to a blocking gate without anyone
deciding to admit it.

### Why the inclusion list is not the forbidden shape

This is the distinction D-21 exists to protect and it is worth stating precisely:

|  | Known-fail allowlist (FORBIDDEN) | Inclusion list (what this is) |
|---|---|---|
| What an entry says | "this failure is acceptable" | "this scenario must be green" |
| Effect of ADDING an entry | turns a RED run GREEN | makes the gate STRICTER |
| Can it silence a failure? | **yes — that is its purpose** | **no** — a failing scenario cannot satisfy "entirely green" |
| Abuse direction | addition | deletion |
| What closes the abuse direction | nothing | `MIN_BLOCKING_GREEN_SCENARIOS`, a floor |

A listed scenario **absent** from the results also fails, so a re-pin that renames one cannot
silently stop checking it while the gate stays green.

## Deviations from Plan

### 1. [Rule 3 — blocking issue] No `timeout(1)` on this macOS host, and MY FIRST SHIM WAS WRONG

Fence 9 needs a real `timeout(1)`; macOS ships none and coreutils is not installed. Installing a
package is not an auto-fixable deviation, so — as in 118.1-13 — a stand-in lives in gitignored
`target/118.1-14-bin/timeout`, reached only via a PATH prefix.
**`scripts/run-conformance-suite.sh`'s timeout handling was NOT modified; the file's `TIMEOUT_BIN`
detection is byte-identical to what it was.** CI runners ship coreutils and are unaffected.

**The first version of that shim was defective, and it cost three wasted runs.** It ended with:

```bash
kill -TERM "$watcher"
wait "$watcher"
```

where `$watcher` was a subshell blocked in `sleep "$duration"`. **Bash does not interrupt a
foreground child to run a signal handler** — the subshell defers the SIGTERM until `sleep`
returns — so `wait "$watcher"` blocked for the *full remaining budget*. The v1 leg finished in
~4 minutes, the script then sat silent for the remaining ~11 of a 900 s budget, the timer fired,
wrote its marker, and the completed run was reported as a **TIMEOUT it never hit**.

That is a false RED, and its mirror image is a false GREEN. **Plan 118.1-13's five contract
points would not have caught it** — every one of them uses a short duration, and the defect only
appears when a command finishes EARLY under a LONG budget. The proof harness now carries a
seventh point that tests exactly that, plus a sixth for pipe/PIPESTATUS behaviour:

| # | Contract | Result |
|---|---|---|
| 1 | propagates a zero exit | `0` |
| 2 | propagates a nonzero exit | `7` |
| 3 | kills on timeout, exits 124 | `124` in **2s**, not 30 |
| 4 | kills the whole process group | `124`; `pgrep` finds no survivor |
| 5 | command-not-found | `127` |
| 6 | stdout survives a pipe; caller's `PIPESTATUS[0]` is the shim's | `3`, body intact |
| 7 | **a command that finishes EARLY returns IMMEDIATELY** | `5` in **2s**, not after 900 |

`ALL CONTRACT POINTS PASS`. Point 4 also needed its settle window widened from 1 s to 5 s: the
shim escalates TERM→KILL after 2 s, so a 1 s settle sampled the reaping window and reported a
phantom survivor. Recorded because it is the same class of error as the shim bug — a control
that measures the wrong instant.

### 3. [Rule 2 — missing critical functionality] The stale-example-binary hazard

`deferred-items.md` names **plan 118.1-14 as owner** of this and asks for the durable fix. It is
outside this plan's `files_modified`, and it is a false-green class defect in a phase that exists
to eliminate them, so it was fixed: `tests/common/example_process.rs::spawn_example` now fails
when the example binary is older than the newest of `examples/<name>.rs` and every `.rs` under

The `src/` half is load-bearing: the measured Wave-10 case came from `src/shared/peer.rs` and
`src/server/streamable_http_server.rs` while the example source had **not** moved, so comparing
against the example source alone would have missed it entirely.

**Proved load-bearing, not merely present** — and it could not be proved through
`cargo nextest run`, because nextest's build step re-uplifts the example binary and resets its
mtime, undoing the backdate. The test binary was executed directly:

| Control | Example binary | Result |

| A | fresh | exit **0** |
| B | backdated to 2020-01-01 | exit **101**, assertion naming both the stale binary and the newer source |

17/17 across the three affected legs (`v2_sse_progress`, `completion_complete`,
`embedded_resource_example_run`) with a fresh binary.

**A related fact worth recording:** `cargo nextest run` DOES rebuild examples (unlike
`cargo test --test <name>`, which the deferred item correctly identified). So the hazard is
narrower than feared for nextest users — and the assertion is still the durable guard for the
