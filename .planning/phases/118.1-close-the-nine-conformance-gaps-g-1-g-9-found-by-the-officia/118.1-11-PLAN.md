## WHERE THE INJECTION ACTUALLY HAPPENS (revised after cross-AI review)

The previous revision of this plan said "inject via `RequestHandlerExtra::with_peer(...)` at the
HTTP dispatch site". That is impossible and both external reviewers proved it:
`streamable_http_server.rs:3001-3004` calls
`handle_request_with_context(id, request, auth_context, protocol_context)` — four parameters, no
peer seam — and `RequestHandlerExtra` is constructed much deeper, inside
`Server::call_tool_with_context` (`src/server/mod.rs:2084`) and `ServerCore::handle_call_tool`
(`src/server/core.rs:638`). The corrected seam changes NO dispatch signature. Three steps:

**Step A — the transport attaches the backchannel to the context it already owns.** Inside
`dispatch_request_or_retire` (`src/server/streamable_http_server.rs:2976-3005`), before taking the
server lock, build a `TransportBackchannel` (plan 10, `src/types/protocol/context.rs`) carrying a
`SessionPeerHandle` bound to this request's session plus a notification sink, and fold it into the
`protocol_context` with `with_transport_backchannel(...)`. `dispatch_request_or_retire` is a private
function in this module, so it gains a sixth parameter `session_id: Option<&str>` with no semver
consequence. Its two callers already have the value in scope: `handle_fast_path_request`
(`:2571-2596`) has both `session_id: Option<&String>` and `response_session_id`, and the
`HttpIngress::Public(TransportMessage::Request { .. })` arm of `dispatch_message_with_middleware`
(`:4034-4044`) has `response_session_id` destructured from `MiddlewareDispatch`. Pass the id the
RESPONSE will carry (`response_session_id`), borrowed, not moved. Attach the peer half ONLY when
v1 sessions are active for this request (`sessions_on`) — v2 has no session stream and
server-to-client requests stay MRTR there.

**Step B — `attach_peer` prefers the request-scoped peer.** Both
`Server::attach_peer` (`src/server/mod.rs:1208-1217`) and `ServerCore::attach_peer`
(`src/server/core.rs:532-538`) receive `extra` AFTER the builder chain has already applied
`.with_protocol_context(protocol_context)` (read `src/server/mod.rs:2084-2101` and
`src/server/core.rs:638-651`: `attach_peer` wraps the entire chain). `RequestHandlerExtra.protocol_context`
is a `pub` field (`src/server/cancellation.rs:231`). So each `attach_peer` reads
`extra.protocol_context.as_ref().and_then(ProtocolContext::transport_backchannel)` FIRST and, when
it yields a peer, applies that one; otherwise it falls back to `self.peer_handle` exactly as today.
No call site changes.

**Step C — the progress channel, which is a DIFFERENT channel and was previously missed.** The
conformance target calls `extra.report_progress(...)` (`examples/s54_v2_dual_conformance.rs:805`),
which reads ONLY `RequestHandlerExtra.progress_reporter` (`src/server/cancellation.rs:628-640`) and
returns `Ok(())` silently when it is `None`. That reporter is built in
`Server::call_tool_with_context` at `src/server/mod.rs:2039-2056` from
`req._meta.progress_token` AND `self.notification_tx` — and `notification_tx` is assigned only by
`Server::run()`, which `StreamableHttpServer` never calls. Fixing `PeerHandle::progress_notify`
alone would therefore change nothing the suite observes. The fix is to make that construction fall
back to the transport-supplied sink: keep the `progress_token` lookup exactly as it is, and resolve
the sender as "the `TransportBackchannel`'s `notification_sink` if present, else
`self.notification_tx`". The sink's type was chosen in plan 10 to be
`Arc<dyn Fn(Notification) + Send + Sync>`, which is `ServerProgressReporter::new`'s second parameter
verbatim (`src/server/progress.rs:91-94`), so no adapter is needed. Mirror the same fallback in
`ServerCore::handle_call_tool` if that dispatcher builds a reporter.

`Server::attach_peer` — `src/server/mod.rs:1205-1217` — applies `self.peer_handle` when set. It is a
SINGLE field on `Server`, so it cannot express "the session that issued this request". A handle set
there would be shared by every concurrent v1 session. That is the misbinding the two-session test
catches, and it is why Step B prefers the request-scoped handle over it rather than replacing it.

The two invariants that must survive, from `src/shared/peer.rs:12-23`:
- Session isolation: "Peer handles are constructed fresh-per-request by the dispatch site."
- Authorization ordering: "Peer calls inherit the originating tool's authorization context.
  Tool-level authz runs BEFORE the dispatch site wires `peer` — an unauthorized caller never reaches
  the handler body and therefore never sees `extra.peer()`."

The era-matrix G-3 tripwires and their own instructions:
- `crates/pmcp-team-servers/tests/era_matrix.rs:664-681` — the loop over
  `["dep__request_sampling", "dep__list_roots"]` asserting `DEP_STATUS_CAPABILITY_NOT_OFFERED`, whose
  message says: "If this now reports `{DEP_STATUS_COMPLETED}`, G-3 HAS BEEN FIXED: the peer handle
  now reaches the HTTP dispatch path. That is good news — update THIS assertion and re-measure
  baseline rows ERA-13/ERA-14, whose v1 token is `absent` for exactly this reason".
- The module rustdoc at `:580-600` describes G-3 (and G-9) as measured reality; it names
  `src/server/mod.rs:1173` and `src/types/protocol/context.rs:384-390` as the causes. Both are now
  closed — G-9 by plan 08, G-3 by plans 10 and 11 — so this doc block is stale and must be rewritten,
  not just the assertions.
- `DEP_STATUS_CAPABILITY_NOT_OFFERED` is defined at `:466`; `DEP_STATUS_COMPLETED` is the target.
- Baseline rows ERA-13 and ERA-14 in `crates/pmcp-team-servers/baselines/era-deltas.yaml` carry the
  v1 token `absent` for exactly this reason and move with the flip.

The reference working wiring — `src/server/mod.rs:1160-1174` builds the dispatcher plus a
`DispatchPeerHandle` once, and `attach_peer` applies it. The HTTP equivalent must apply a
session-bound handle at the dispatch site instead.
