The injection seam that already exists — `src/server/cancellation.rs:521-536`:
`pub fn with_peer(mut self, peer: Arc<dyn crate::shared::peer::PeerHandle>) -> Self` and
`pub fn peer(&self) -> Option<&Arc<dyn PeerHandle>>`. `RequestHandlerExtra` can therefore receive a
peer from the TRANSPORT, not only from `Server::attach_peer`.

`Server::attach_peer` — `src/server/mod.rs:1205-1217` — applies `self.peer_handle` when set. It is a
SINGLE field on `Server`, so it cannot express "the session that issued this request". A handle set
there would be shared by every concurrent v1 session. That is the misbinding the two-session test
catches.

The two invariants that must survive, from `src/shared/peer.rs:12-23`:
- Session isolation: "Peer handles are constructed fresh-per-request by the dispatch site."
- Authorization ordering: "Peer calls inherit the originating tool's authorization context.
  Tool-level authz runs BEFORE the dispatch site wires `peer` — an unauthorized caller never reaches
  the handler body and therefore never sees `extra.peer()`."

The era-matrix G-3 tripwires and their own instructions:
- `crates/pmcp-team-servers/tests/era_matrix.rs:664-681` — the loop over
  `["dep__request_sampling", "dep__list_roots"]` asserting `DEP_STATUS_CAPABILITY_NOT_OFFERED`, whose
  message says: "If this now reports `{DEP_STATUS_COMPLETED}`, G-3 HAS BEEN FIXED: the peer handle
  now reaches the HTTP dispatch path. That is good news — update THIS assertion and re-measure
  baseline rows ERA-13/ERA-14, whose v1 token is `absent` for exactly this reason".
- The module rustdoc at `:580-600` describes G-3 (and G-9) as measured reality; it names
  `src/server/mod.rs:1173` and `src/types/protocol/context.rs:384-390` as the causes. Both are now
  closed — G-9 by plan 08, G-3 by plans 10 and 11 — so this doc block is stale and must be rewritten,
  not just the assertions.
- `DEP_STATUS_CAPABILITY_NOT_OFFERED` is defined at `:466`; `DEP_STATUS_COMPLETED` is the target.
- Baseline rows ERA-13 and ERA-14 in `crates/pmcp-team-servers/baselines/era-deltas.yaml` carry the
  v1 token `absent` for exactly this reason and move with the flip.

The reference working wiring — `src/server/mod.rs:1160-1174` builds the dispatcher plus a
`DispatchPeerHandle` once, and `attach_peer` applies it. The HTTP equivalent must apply a
session-bound handle at the dispatch site instead.

| session A stream vs session B stream | Both server-to-client REQUESTS and progress NOTIFICATIONS are now routed by session |

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-118.1-11-01 | Information Disclosure | Session-to-peer misbinding delivering one client's `sampling/createMessage` or progress frame onto another client's stream — the T-113-07 class | mitigate | The handle is session-bound and constructed per request; the two-session isolation test covers BOTH the request path (Task 1) and the notification path (Task 2); a global handle fails those tests and only those |
| T-118.1-11-02 | Elevation of Privilege | Wiring the peer before tool-level authorization would let an unauthorized caller reach the back-channel | mitigate | The injection point is placed after the existing authz point; the SUMMARY records both file and line, proving the ordering, per the invariant at `src/shared/peer.rs:19-23` |
