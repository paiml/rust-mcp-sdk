# Phase 118.1 Plan 10: The StreamableHTTP Server-to-Client Channel Summary

**The StreamableHTTP transport now has a server-to-client channel and, more importantly, no longer deadlocks: an inbound JSON-RPC response is correlated and answered before any of the three sites that take the server mutex, so a parked tool handler can no longer take the whole transport offline.**

## Accomplishments

### The deadlock is gone, and it was real

`dispatch_public_request` holds `state.server.lock().await` for the entire duration of a tool
handler. Before this plan every inbound POST passed through `run_v2_header_gate` (which takes that
mutex twice — the accept-list read and the negotiation read) and `extract_and_validate_auth` (a
third) before it was ever classified. The measurement is in the fence's Task-1 run:

```
an inbound response POST must not hang behind a parked tool handler: still unanswered after 1s
while a handler holds Mutex<Server>. The inbound response is not classified before
run_v2_header_gate / extract_and_validate_auth.
```

After Task 3 that test passes in 48 ms. The guard is not a proxy for the hazard; it is the hazard.

### Correlation ownership, and the leak the plan predicted

`ServerRequestDispatcher` gained `owners: Arc<RwLock<HashMap<String, String>>>`, `dispatch_owned`,
`owner_of` and `fail_pending`. The insert-before-send ordering is quoted here because it is
load-bearing:

```rust
self.pending.write().await.insert(correlation_id.clone(), tx);
// ORDERING IS LOAD-BEARING: the owner is recorded BEFORE the send, and
// the drain pops the pair only AFTER the send, so an owner recorded here
// is always visible to the drain that will look it up.
if let Some(owner) = owner {
    self.owners.write().await.insert(correlation_id.clone(), owner.to_string());
}
```

The success-path removal lands in `handle_response`, beside the `pending.remove` it belongs with —
`src/server/server_request_dispatcher.rs:283-288`:

```rust
if let Some(tx) = pending.remove(correlation_id) {
    // Released before taking the `owners` lock: the two are always taken
    // in the order pending -> owners and never held together.
    drop(pending);
    self.owners.write().await.remove(correlation_id);
```

Both leak fences exist: `test_dispatcher_owners_cleared_after_timeout` and
`test_dispatcher_owners_cleared_after_success`. The second is the one that fails if the removal is
written only into `dispatch_owned`.

### The dispatcher is provably outside `Mutex<Server>`

`ServerState`'s new field, quoted to prove the placement:

```rust
pub(crate) struct ServerState {
    server: Arc<tokio::sync::Mutex<Server>>,
    config: Arc<StreamableHttpServerConfig>,
    allowed_origins: AllowedOrigins,
    v1: v1::V1State,
    /// … HERE, on `ServerState`, and deliberately NOT inside `Mutex<Server>`. …
    peer_channel: peer_channel::PeerChannel,
}
```

### The outbound drain resolves the ORIGINATING session

`peer_channel::route_outbound`, both branches:

```rust
let Some(session_id) = dispatcher.owner_of(&correlation_id).await else {
    dispatcher.fail_pending(&correlation_id, NO_OWNER).await;
    return;
};
…
if v1::route_to_session_stream(&state.v1, &session_id, message).is_some() {
    dispatcher.fail_pending(&correlation_id, NO_LIVE_STREAM).await;
}
```

`owner_of` is what makes the existing `(String, ServerRequest)` channel type sufficient — the
session is not in the tuple, it is recorded against the correlation id. `fail_pending` drops the
`oneshot::Sender`, so the awaiting caller returns AT ONCE rather than holding the server mutex for
the whole dispatch timeout.

### An explicit dispatcher timeout, and what it actually bounds

`HTTP_DISPATCH_TIMEOUT = 30s`, stated in the module doc, deliberately shorter than the 60-second
in-process `DEFAULT_DISPATCH_TIMEOUT`. The doc records the reasoning the plan asked for: because
`dispatch_public_request` holds the server mutex across the handler, a timed-out peer call is what
RELEASES it — the dispatch returns `REQUEST_TIMEOUT`, the handler returns, the guard drops. So this
value is the transport's real upper bound on how long one absent client can serialize the server,
not just a pending-map bound.

### `cargo semver-checks` caught a MAJOR break that no compiler warning would

Adding `Arc<dyn PeerHandle>` and `Arc<dyn Fn(Notification)>` to `TransportBackchannel` silently
removed `UnwindSafe` and `RefUnwindSafe` from the PUBLIC `ProtocolContext`. First run:

Fixed with explicit (safe) `impl std::panic::UnwindSafe`/`RefUnwindSafe` for

`pub(crate)`, so the field itself is semver-MINOR; the auto-trait loss was the only major signal
and it is gone.

## Task 3: the classification, quoted

Both call sites, and the one function they share.

`handle_post_fast_path_inner` (second statement, after `read_and_classify_fast`):

```rust
if let Some(accepted) =
    peer_channel::try_route_inbound_response(&state, &ingress, session_id.as_deref()).await
{
    return Ok(accepted);
}
```

`handle_post_with_middleware_inner` (second statement, after `read_and_classify_with_middleware`):

```rust
if let Some(accepted) =
    peer_channel::try_route_inbound_response(&state, &ingress, session_id.as_deref()).await
{
    return Ok(accepted);
}
```

It is deliberately NOT called from `handle_post_request`: that function owns the axum `Body`, a
single-pass stream, and reading it there would consume the request and break every non-response
POST. No new body read is introduced anywhere —
`grep -nE "to_bytes|Body" src/server/streamable_http_server/peer_channel.rs` returns nothing; the
module consumes the already-parsed `HttpIngress`, so the existing `MAX_*` bounds guarded by
`v2_bounded_reads_tripwire` apply unchanged.

### The rejection shape, and why it is not an enumeration oracle

```rust
if dispatcher.owner_of(&correlation_id).await.as_deref() != session_id {
    debug!("Discarded inbound response for correlation {}: not owned by the presenting session", correlation_id);
    return StatusCode::ACCEPTED.into_response();
}
```

Three negative cases — unknown correlation id, id owned by a DIFFERENT session, and no session
presented — all answer the same `202 Accepted`, with no body and no distinguishing header, and none
of them calls `handle_response`. `owner_of` answers `None` for an unknown id, so unknown and
wrong-session collapse into one comparison and one answer. A `404` for unknown and a `403` for
wrong-session would let a client enumerate live correlation ids (T-118.1-10-03). The correlation id
is logged at `debug`; the payload never is.

### Surviving `TransportMessage::Response` occurrences

`git grep -n 'TransportMessage::Response' src/server/streamable_http_server.rs` → 10 hits. Eight are
OUTBOUND construction (`envelope_for_live_request`, `extract_negotiated_version`,
`build_sse_response_from_single_message`). The two inbound ones are lines 4378 and 4511: the
narrowed dispatcher arms. They are **unreachable by construction** — `try_route_inbound_response`
matched and answered every response envelope before either dispatcher ran — and survive only
because a Rust match must stay exhaustive. Both now call
`peer_channel::route_inbound_response(..)`, so even an unreachable arm ROUTES rather than discards.
**No reachable silent-discard path for a client's answer remains.**

## Deviations from Plan

### 1. [Rule 2 — missing critical functionality] The transport SYNTHESISES an absent `ProtocolContext`

- **Found during:** Task 2
- **Issue:** The plan's seam attaches the `TransportBackchannel` to the already-resolved
  `ProtocolContext`. But `run_v2_header_gate` short-circuits to `(None, Passthrough)` for any server
  that is not v2-opted-in (D-04's zero-era-code rule) — which is every stock `Server::builder()`, on
  exactly the v1 stateful sessions the server-to-client channel exists for. Attaching only to a
  `Some` context would have delivered G-3 to v2-opted-in servers and to no default deployment.
- **Fix:** `attach_session_backchannel` synthesises a v1 context when there is none, through the
  SAME shared unit `fold_v1_handshake_capabilities` uses for its own `None` arm
  (`first_v1_version` over the server's accept-list). Dispatch already synthesises exactly this
  value one layer down, so what reaches the handler is unchanged in every field but the new one.
  Attachment happens AFTER every era-gated stage, so `era`, `sessions_on` and the legacy-version
  guard all still read the ORIGINAL `None`. `initialize` is excluded (no SSE stream can exist yet).
- **Verification:** `v1_handler_client_capabilities`, `v1_byte_identity_after_cut`,
  `v2_stateless_http`, `v2_retired_methods`, `v2_bounded_reads_tripwire`,
  `session_validation_tests`, `streamable_http_spec_compliance`, `v2_subscriptions` — 136 tests, all
  pass. `v2_dispatch_response_status` and `sessions_active_for` were read directly and both treat
  `Some(Era::V1)` and `None` identically, so the synthesis is behaviour-neutral by construction as
  well as by measurement.
- **Committed in:** `280832d1`

### 2. [Rule 1 — correctness] `dispatch` and `dispatch_owned` share one body

- **Found during:** Task 2
- **Issue:** The plan said "do NOT change `dispatch`" and described `dispatch_owned` as "`dispatch`'s
  body with ONE addition". Taken literally that duplicates ~45 lines of pending-map bookkeeping
  across two functions — in the exact area this plan exists to keep consistent.
- **Fix:** Both delegate to a private `dispatch_with_owner(owner: Option<&str>, ..)`. `dispatch`
  passes `None`, records no owner, and is behaviourally byte-identical; `new_with_channel`, the
  channel type and `spawn_server_request_drain` are untouched, so `Server::run` compiles and behaves
  unchanged. `test_dispatch_records_no_owner` fences that claim.
- **Committed in:** `280832d1`

### 3. [Rule 1 — bug] Explicit `UnwindSafe` / `RefUnwindSafe` on `TransportBackchannel`

- **Found during:** Task 2 (`cargo semver-checks`)
- **Issue:** The new `Arc<dyn PeerHandle>` field silently removed both auto traits from the public
  `ProtocolContext` — `auto_trait_impl_removed`, a MAJOR break, contradicting the plan's own
  no-new-major-lint criterion. No compiler warning surfaces this.
- **Fix:** Manual safe impls with a `// Why:` block: both fields are opaque, immutable-after-
  construction `Arc` capability handles, and every piece of mutable state they reach is behind a
  `tokio::sync::RwLock`, which has no poisoning and therefore publishes no broken-invariant signal
  to a `catch_unwind` caller. Adding `+ RefUnwindSafe` to `PeerHandle` instead would be a MAJOR
  break of its own.
- **Committed in:** `280832d1`

### 4. [Rule 3 — blocking] `try_route_inbound_response` is `pub(super)`, not `pub(crate)`

- **Found during:** Task 3
- **Issue:** `HttpIngress` is private to the transport module, so a `pub(crate)` signature naming it
  is `private_interfaces` (a warning, and `-D warnings` in the gate).
- **Fix:** `pub(super)`. Both call sites live in that module, so it is exactly wide enough.
- **Committed in:** `325a39e1`

**Total deviations:** 4 — one Rule 2, two Rule 1, one Rule 3. No architectural change; no user
decision needed.

## HAND-OFF TO PLAN 11 — read this first

Plan 10 built the channel; plan 11 makes the peer visible to handlers. Concretely:

1. **`attach_peer` must prefer the request-scoped peer.** Both impls
   (`src/server/mod.rs` and `src/server/core.rs`) receive `extra` AFTER
   `.with_protocol_context(..)` has been applied, and `RequestHandlerExtra::protocol_context` is a
   `pub` field, so the read needs NO signature change:
   `extra.protocol_context.as_ref().and_then(ProtocolContext::transport_backchannel).and_then(TransportBackchannel::peer)`,
   falling back to `self.peer_handle`.
2. **The backchannel is present for v1 sessions on a stock server.** Deviation 1 above closed the
   `None`-context gap, so `attach_session_backchannel` fires for any non-init POST on a live v1
   session regardless of v2 opt-in. Verify with the fence rather than by inspection.
3. **`progress_notify` has its vehicle already.** `peer_channel::session_notification_sink` builds
   the `Arc<dyn Fn(Notification) + Send + Sync>` typed exactly as `ServerProgressReporter::new`'s
   second parameter, and it is already on every attached backchannel. `SessionPeerHandle::progress_notify`
   carries a `// Plan 11 Task 2 replaces this` marker.
4. **The five red fence tests are your acceptance criteria.** They should go green in order:
   `http_peer_sample`, `http_peer_list_roots`, `http_peer_elicit`, then the saturation test, then
   `a_server_to_client_request_reaches_only_the_issuing_session` — which is the one a naive global
   `peer_handle` will fail while passing all the others.
5. **Do not let the guard regress.** `response_post_is_answered_while_a_tool_handler_holds_the_server_mutex`
   is green now. If it ever times out again, something has been added ahead of
   `try_route_inbound_response` on a POST entrypoint.
