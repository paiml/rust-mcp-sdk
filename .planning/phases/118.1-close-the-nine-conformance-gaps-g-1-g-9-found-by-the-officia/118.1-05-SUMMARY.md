# Phase 118.1 Plan 05: Close G-5 — v2 Method Retirement Keyed on the Method String Summary

v2 retirement widened from the two `ClientRequest` variants it matched to all five methods the
2026-07-28 core schema removes, keyed on the peer's method **string** at the ingress gate so it
also reaches the requests whose params never deserialize.

## What Shipped

`V2_RETIRED_METHODS` — a single named table in `src/server/streamable_http_server.rs` pairing each
retired method with its successor mechanism:

| Retired method | Replacement recorded in the table |
|---|---|
| `initialize` | `server/discover` |
| `ping` | *(none — the transport removed the liveness RPC outright)* |
| `logging/setLevel` | the `io.modelcontextprotocol/logLevel` request `_meta` key |
| `resources/subscribe` | `subscriptions/listen` |
| `resources/unsubscribe` | `subscriptions/listen` |

`v2_retired_method` matches by exact byte equality and returns the **table's own** `&'static str`,
so a rejection message can never be assembled from peer-supplied bytes. `retire_v2_method` converts
an accepted v2 request for a retired method into a `METHOD_NOT_FOUND` rejection; the HTTP status is
still chosen by `v2_status_for_code`, with no call-site status choice.

## Which of the Five Were RED, and Why

The plan asked for this to be recorded one line each. Measured on the unfixed tree by
`tests/v2_retired_methods.rs` (full log at `target/118.1-05-red.log`, copy in the session
scratchpad). The fence collects every offender rather than aborting on the first, so all five were
observed in one run:

| Method | Pre-fix v2 answer | RED? | Why |
|---|---|---|---|
| `initialize` | **HTTP 200** with a full `InitializeResult` (`protocolVersion: "2025-11-25"`, `resultType: "complete"`, `serverInfo`) | **RED** | No era branch anywhere: the server accepted `initialize` on both eras for backward tolerance |
| `ping` | **HTTP 200**, `result: {}` | **RED** | `ClientRequest::Ping` falls into the `src/server/mod.rs:1897-1901` catch-all arm that answers `Ok(json!({}))` with no era branch |
| `logging/setLevel` | **HTTP 200**, `result: {}` | **RED** | The same catch-all arm |
| `resources/subscribe` | 404 + `-32601` | green | Already matched by the old two-variant `v2_retired_method_of` |
| `resources/unsubscribe` | 404 + `-32601` | green | Same |

Nine assertion violations across three methods; 4 tests run, 3 passed, 1 failed — a non-zero
selected count and a non-zero exit, as the RED gate requires.

**This confirms RESEARCH Pitfall 4 exactly.** The official suite's `initialize` and
`logging/setLevel` checks were already green on a server that retired neither, because its probe
sends `params: {_meta: …}` and nothing else — a typed-parse failure that
`map_unparsed_body_for_v2` coincidentally answers with the same `-32601`/404. Only `ping` was
failing the suite. The suite will gain **one** check, not three. `tests/v2_retired_methods.rs`
carries a module comment stating that those two suite checks must not be used to validate this fix.

## A Correction to the Plan's Model of `ping`

The plan and RESEARCH both treat `ping` as "parses fine and answers `{}` at 200", which is right —
but for a non-obvious reason worth recording, because a reasonable reader will conclude the
opposite from the types. `ClientRequest::Ping` is a **unit** variant of an adjacently-tagged enum,
so `serde_json::from_value::<ClientRequest>(json!({"method":"ping","params":{…}}))` fails with
*"invalid type: map, expected unit variant"* for ANY params object, including an empty one
(measured directly). The wire path does not hit that: `parse_client_request`
(`src/shared/protocol_helpers.rs:195-219`) special-cases `ping` and **drops its params entirely**
before deserializing. So `ping` reaches a typed `Request` on the wire while a naive
`from_value` round trip on the same body does not.

## Era-Matrix Baselines — Before and After

`crates/pmcp-team-servers/baselines/era-deltas.yaml`. **Two** rows moved, not one.

| Row | Subject | Before | After | Why this is the retirement widening, not drift |
|---|---|---|---|---|
| ERA-11 | `method:logging/setLevel` | v1 `served` / v2 `served`, `kind: era-agreement` | v1 `served` / v2 `error:-32601`, `kind: method-removed` | This is the successor state the tripwire's own pre-flip failure message named, **verbatim**. It is also the row's originally SEEDED value, which plan 118-07 had to correct downward to `served` precisely because the retirement was missing |
| ERA-01 | `method:initialize` | v1 `served` / v2 `served`, `kind: era-agreement` | v1 `served` / v2 `absent`, `kind: method-removed` | **Not named in the plan.** `initialize` is one of the five retired methods, so widening past the two `resources/*` variants necessarily reaches it. Also the originally seeded value, and it now agrees again with `crates/mcp-tester/baselines/era-deltas.yaml` ERA-01, which independently declares v1 `served` / v2 `absent` / `method-removed` |

The v2 token for ERA-01 is `absent` rather than `error:-32601` because that probe's classifier
(`classify_initialize` in `crates/pmcp-team-servers/src/conformance/era_observations.rs:769-775`)
tokenizes on the presence of a JSON-RPC `result`, not on the refusal code. That is the probe's
existing rule and was not changed.

**No other row moved.** ERA-02 (`server/discover`) does not reference `logging/setLevel` and is
untouched; ERA-03 (`header.mcp_session_id`) is derived from the same `initialize` probe but reads
only the session header, and still measures `never-minted-inbound-ignored` on v2. The full
`era_matrix_is_conformant` diff before the flip listed exactly two `[UNEXPECTED]` rows — ERA-01 and
ERA-11 — and nothing else.

**`kind: era-agreement` now has ZERO occupants.** `MAXIMUM_AGREEMENT_ROWS` in
`crates/pmcp-team-servers/tests/era_baseline.rs` is a `<=` cap, so the file stays conformant. The
cap was deliberately **not** lowered to zero: a `<=` cap with no occupants keeps the mechanism
available for a genuinely measured sameness, whereas lowering it would make the next legitimate use
a gate change — the pressure that gets caps raised silently.

### Deliberate Departures from the Plan's Wording

**6. `map_unparsed_body_for_v2`'s ordering premise is inverted for this architecture**

The plan says *"After this change, retired methods are answered earlier and never reach it"* and
asks the rustdoc to name the methods that "now short-circuit before it". That is not what the
pipeline does: `map_unparsed_body_for_v2` runs on the **parse-failure branch of
`read_and_classify_fast`**, which is *earlier* than `run_v2_header_gate`, not later. Retired methods
with well-formed params never reached it before this plan either — they parsed. Writing the plan's
sentence would have installed a false claim in the rustdoc.

What was written instead is the accurate relationship: a retired method reaches `-32601`/404 on v2
by **two disjoint routes** — this function when its params do not deserialize, and
`retire_v2_method` at the gate when they do — with the same code and status either way, which is
precisely why the suite's two checks passed for the wrong reason.
