<assumption_delta_decision>
**Detector signal:** `optional` — "Optional OpenAPI spec layer" (the generalized identity is
"a config-only server package may carry zero or one auxiliary schema payloads").

**Decision: add-alongside (no promotion).** The spec layer is added as its own per-kind media
type beside the shared generic config layer, exactly as D-13 locks it — one generic
`mcp-server.config.v1+toml` shared across all three Shape A siblings, and a per-kind
`mcp-server.openapi-spec.v1` that names the kind. Promoting the spec layer to a generic
"schema payload" identity was explicitly rejected in D-13 because `pmcp-workbook-server` takes
a `--bundle-dir` DIRECTORY, so a generic form would have to mean an archive — speculative
generalization from a single example. Optionality is likewise not promoted into a general
"optional layers" mechanism: D-14 rejected an absence marker, so absence is simply the layer
not being present in the media-type index.

**Rationale (one line):** the half that provably generalizes (the config layer) is already
shared; the half that does not (the spec) stays per-kind until a second real sibling exists.
</assumption_delta_decision>

## Cross-AI review responses (120-REVIEWS.md — Codex, source-grounded)

- **HIGH — "The permutation property test is incomplete for content-addressed manifests."**
  INCORPORATED. Re-verified against source: `OciLayout::write_blob` derives both the blob path
  and the descriptor digest from the bytes (`oci/layout.rs:76-84`), and
  `read_the_one_manifest` calls `read_verified_blob` on `index.manifests()[0]` — i.e. it
  digest-verifies the index descriptor's declared digest against the manifest bytes BEFORE
  parsing (`oci/unpack.rs:42-53`). So "rewrite the manifest blob with the permuted order" is
  not implementable: writing permuted bytes creates a DIFFERENT content-addressed path that
  the unchanged index never points at (test silently reads the original manifest and passes
  vacuously), and overwriting the original path fails `verify` before the media-type lookup is
  ever reached. Task 3 now specifies an explicit `rewrite_manifest_layers` helper with the
  five-step content-addressed rewrite, and the acceptance criteria machine-check that the
  helper calls `write_manifest` and `write_index`.
- **MEDIUM — "The stated `artifact_type_from_manifest_json` fallback mechanism is
  inaccurate."** INCORPORATED. Confirmed at `cargo-pmcp/src/commands/package/kind.rs:64-84`:
  the function returns `artifactType` first, then `config.mediaType`, and only then
  `layers[0].mediaType`. Because `finalize_pack` always writes the standard empty-OCI-config
  descriptor, the `config.mediaType` arm ALWAYS returns first for a PMCP package, so the
  `layers[0]` tier is unreachable in this shape and the plan's original rationale was wrong.
  The real mechanism is `inspect.rs:75-86`, which aggregates candidates — raw-parse result,
  `manifest.artifact_type()`, the config media type, and EVERY layer media type — and takes
  the first that `detect_kind` recognizes. Task 3's rationale text and its new direct CLI test
  are rewritten against that path.
- **MEDIUM — "The fuzz-target extension may add little coverage."** INCORPORATED. Confirmed by
  reading `cargo-pmcp/fuzz/fuzz_targets/fuzz_package_kind.rs` in full: it forwards `data: &[u8]`
  straight into `artifact_type_from_manifest_json` and chains `detect_kind` on any candidate.
  There is NO seed/alphabet and no structured-manifest synthesis, so the originally prescribed
  edit ("add the new media-type strings to whatever seed/alphabet the target uses") has no
  place to land. The target itself is left unchanged; reachability is raised the honest way,
  by adding a seed corpus file carrying a config-only manifest shape, and the acceptance
  criterion moves off the (now impossible) source grep onto the corpus file plus a bounded
  `cargo fuzz run`.
- **LOW — "'0.1.x envelope' detection is heuristic rather than an actual version marker."**
  INCORPORATED as documentation. `detect_legacy_shape` recognizes a SHAPE (an envelope object
  carrying a `binary_ref` key), not a producer version — any future or third-party envelope
  carrying that extension key is labelled the same way. Task 2 now requires the helper's
  rustdoc and its error text to say "shape", and to avoid asserting authoritative provenance.
