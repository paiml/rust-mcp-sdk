the two refusals that keep it honest about its scope.

Plan 01's tracer proved the path — `save` writes a tar, `load` reads it back into a layout `inspect`

without inventing a single fact that is not derivable offline from the package alone.

D-15 subject-mismatch verdict, and `save`'s kind guard plus its deliberate hard-error divergence.

looking for a component list on a server package; there is none.

Do NOT move `inspect.rs`'s renderers into it. `inspect` is shipped, its output is a surface people
already read, and this phase has no mandate to churn it. Instead, match `inspect`'s VISUAL vocabulary —
the same label/value shape its `field` and `header` helpers produce — so a reader moving between

**Slot rendering (SC1's "prints the slots").** Take `&[ConfigSlot]`, call `required_slots`, and render
each `RequiredSlot`. Two things must not be garbled: the slot's `name` is the environment variable the
target environment sets, and `config_key` is the dotted config path the resolved value is written to —
label them distinctly and never print the config path where the variable name belongs, because a
derived variable built from a config path is one no environment can portably set. Render `class`
(identity-bearing versus behavior-relevant) so an operator can see which entries are credentials.
`config_key` is `Option`; a `None` renders as "fills no config key", not as an empty string.

`required_slots` is the enumerator here — NOT `detect_deviation`. PKG-04's correction is that
`detect_deviation` compares one already-known tested/proposed pair and short-circuits on
identity-bearing slots, so it could never name the credential. The two answer different questions and
this rendering asks the enumeration question. Record that in the function's rustdoc so nobody
"improves" it by switching. (`detect_deviation`'s endpoint-drift rendering was left to discretion;
this plan declines it, on the ground that `load` has exactly one environment in hand — the package's —
and a drift report needs two.)

**Pin-fact rendering (D-14).** Walk a component's `ComponentRef`s and render THREE states, never two:
a `Range` is declared-but-unresolved; a `Pinned` with `resolved_from: Some(range)` shows declared range
alongside resolved version and digest; a `Pinned` with `resolved_from: None` was pinned directly and the
declared range CANNOT BE REPORTED. That third state is not a formatting nicety —
`reference.rs:93-97` names this phase and states the obligation verbatim: treat `None` as "cannot
report" and NEVER as "no skew", because reading an absent fact as a positive claim is precisely the
failure the field exists to prevent. Quote that obligation in the renderer's rustdoc.

End the pin section with a line stating that comparing these pins against what the target environment
actually runs is `import`'s job, platform-side. That is not decoration: it is the boundary D-14 draws,
and an operator who does not see it stated will assume the CLI checked something it cannot check.

**Carriage-state rendering (three states).** Unattested; attested-and-matching; attested-mismatched
with issuer, claimed subject and actual unattested digest side by side. Read the verdict from
`SubjectVerdict::matches()` — never re-derive a digest comparison in the CLI, because a CLI-side copy
would drift from `inspect`'s. Render `claimed` and `issuer` as DATA: they are attacker-controlled
strings from layer annotations, so bound their rendered length the way `inspect`'s `truncate` does and
never use either as a path.

**Determinism.** Every list this module renders must have a specified order. `required_slots` already
guarantees ordering by slot key with a stable sort that preserves equal-keyed duplicates — render in
the order it returns and say so. For component pin facts, sort by component name then type, and state
the tiebreak. Add a unit test asserting that rendering identical inputs twice yields identical strings.

Structure the module so every renderer returns a `String` (or writes into a `&mut String`) rather than
printing directly, with printing left to the caller. That is what makes the determinism test possible
and what lets `load` and `pull` gate printing on `should_output()` without duplicating format logic.
Keep the module free of `clap` and `GlobalFlags` so it stays testable under `cargo test --lib`.

the full diagnostic before the command fails.

**The two verdicts stay different (D-15 / 122 D-03).** An integrity failure surfaces verbatim from
inside `unpack_*` — the V6 rule, never bypassed and never re-wrapped into something friendlier — and
writes nothing. A subject mismatch writes the layout, renders issuer, claimed subject and actual
unattested digest, and exits 1. Corrupt bytes mean the package is broken; a mismatched subject means the
bytes are fine and the claim is wrong. Write that distinction into `load.rs`'s module header in its own
words, together with the instruction that the two must not be harmonized in a later cleanup — the same
sentence `inspect.rs:44-56` carries, because this is the second place in the codebase where somebody

The non-zero exit exists so this is gateable in CI without parsing stdout. Make that the stated reason
in the rustdoc, so nobody replaces it with a warning.

**Reading order — restated against plan 01's staging design, because the reviewed draft had it wrong.**
The draft read *"verification happens before any write, the layout is written, and only then is the
package unpacked and reported"*, which put `unpack_*`'s substantive validation (`unpack.rs:625-660`)

1. `read_verified` — framing, integrity and descriptor-graph gates, entirely in memory, zero

3. render, from the result step 2 returned;
4. the D-15 subject check and its exit code.

the subject check into `install_layout`'s staging gate: that would harmonize two verdicts 122 D-03
