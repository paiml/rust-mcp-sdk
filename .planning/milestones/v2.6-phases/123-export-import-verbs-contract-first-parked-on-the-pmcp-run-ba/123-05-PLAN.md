<objective>
Land `pull` — the remote leg of PKGX-02 — as a COMPLETE pipeline with exactly one seam, so that when
the platform ships `getPackageArtifact` the unparking is deleting a gate rather than writing the
security-relevant half.

D-04 is explicit about why this is not a stub: the verification half is the security-relevant part
(§5.1's *transport is never trusted*) and it is fully testable with no backend. A contract-plus-error
stub would mean that when the backend ships, unparking is WRITING the verification path — the exact
anti-pattern Phase 122 established the discipline against.

This plan joins the two Wave-1 halves. Plan 01 built the reader and the layout writer; plan 02 built
the operation string and its pure codec; plan 03 built the renderer. `pull` is: resolve environment
(reusing the seam SC3 names, which already exists) -> build request (pure) -> ONE impure transport step
-> verify in memory -> write -> report. Everything except that one step already runs offline.

Purpose: prove SC3 by reuse rather than by construction, and prove SC4's named failure by wrapping every
failure of the pull path with the missing capability's name while keeping the cause chain intact.
Output: `pull.rs` decomposed into six named stages, the transport seam plus its offline double, the
`graphql.rs` transport function, and the offline tests that drive the whole pipeline from a local tar.

`export` is retired (D-01): there is no upload direction here, and no hook left for one. The shipped
`import` verb is untouched (D-03).

**Wave 4, and why `depends_on` grew.** Task 3 feeds plan 04's independently-authored golden fixtures
through the transport seam, which is what makes the `pull` path provable against bytes neither the
SDK's writer nor this test produced. That is a real content dependency on plan 04 and it was missing
from the reviewed draft's metadata.
</objective>

**Where the pipeline lives, and why it is not all in `pull.rs` (review finding H2 — read this first).**
The reviewed draft put the whole pipeline in `cargo-pmcp/src/commands/package/pull.rs` and expected
`cargo-pmcp/tests/package_portability_contract.rs` to inject a fake transport into it. That cannot
work, and the reason is structural rather than stylistic: `cargo-pmcp/src/lib.rs` does not declare
`mod commands`, so anything declared only under `commands/package/` is compiled into the BIN target and
nowhere else. A file under `cargo-pmcp/tests/` is an external crate linking the LIB; it cannot see a
bin-private module, and it certainly cannot implement a trait declared in one. The draft's entire
offline testability argument rested on a seam no test could reach.

Split the verb in two:

- **`cargo-pmcp/src/commands/package/pull_pipeline.rs` (new, dependency-light, LIB-MOUNTED).** Holds
  the transport-seam trait and pipeline stages 2 through 6. Mount it in `lib.rs` beside the existing
  mounts, in their exact shape:

  ```
  #[doc(hidden)]
  #[path = "commands/package/pull_pipeline.rs"]
  pub mod package_pull_pipeline;
  ```

  Mount it into the LIB ONLY — do NOT also declare `pub mod pull_pipeline;` in
  `commands/package/mod.rs`. A single mount is what keeps the trait one type rather than two, which is
  what lets the bin's live implementation and the test's fake implementation be interchangeable.

  Inside it, reach collaborators by their LIB-TREE paths — `crate::package_artifact` (plan 01),
  `crate::package_render` (plan 03), `crate::pmcp_run_graphql` (plan 02) — never `crate::commands::*`,
  which would resolve in the bin tree and fail here. Import no `clap`, no `GlobalFlags`, no `reqwest`.

- **`cargo-pmcp/src/commands/package/pull.rs` (new, BIN-ONLY, thin).** `PullArgs`, the `GlobalFlags`
  handling, `auth::get_credentials()`, construction of the live transport, one call into
  `cargo_pmcp::package_pull_pipeline`, and printing. Nothing else. It reaches the pipeline back through
  the lib crate by name — the same bin-consumes-its-own-lib shape `src/bin/capture_contract.rs:55`
  already uses. Any stage reimplemented here is a stage no offline test can reach, which is the
  failure this split exists to prevent; say that in `pull.rs`'s module header.

**Keep the seam's signature free of dual-compiled types.** `artifact.rs` and `render.rs` are each
compiled TWICE (once into the bin, once into the lib), so `commands::package::artifact::VerifiedArtifact`
and `cargo_pmcp::package_artifact::VerifiedArtifact` are DISTINCT types to the compiler even though
they share one source file. The pipeline's public entry point must therefore take and return only
plain types — `&str`, `&Path`, `bool`, `String`, `anyhow::Result`, and the seam trait declared in the
pipeline itself. Nothing dual-compiled crosses the boundary, so the confusion cannot arise. Write that
constraint into the entry point's rustdoc, because it is exactly the kind of thing a later "just return
the artifact" refactor would break in a way whose error message names neither cause.

**Decompose into six named functions — this is a hard constraint, not a style note.** CI runs
`pmat quality-gate --fail-on-violation --checks complexity` at cognitive complexity 25, and a single
`execute` doing resolve, request, transport, verify, write and report will trip it. One function per
stage, exactly as `capture.rs` already models with its `execute`/`submit`/poll/report split. Name them
for their stage so a stack trace reads as the pipeline.

**Stage 1 — resolve the environment, by REUSE. SC3 is a reuse-and-prove criterion, not a build
criterion.** Call `auth::get_credentials()` with the same not-authenticated context message
`capture.rs` uses. Do NOT read any environment variable for a base URL, do NOT add a constant, do NOT
construct a cache path: `get_api_base_url()` already implements the precedence SC3 names and
`configured_api_base_url()` already routes through `configure`'s resolver. Write into `pull.rs`'s
module docs that this stage adds nothing and why — that is the criterion being satisfied by
construction, and a future contributor who "adds a `PULL_API_URL` for convenience" breaks it.

**Stage 2 — build the request, purely.** Call plan 02's `get_package_artifact_request_body` with the
reference. Split a `name@version` reference with the existing splitter in `mod.rs` if the reference
needs decomposition; do not write a second parser. Refuse an empty reference here, before any network
work.

**Stage 3 — the transport seam (D-04, rated `costly`).** Define ONE narrow seam and put both impure
steps behind it: POST the GraphQL operation, then GET the returned `downloadUrl`. Return the artifact
bytes plus the declared `payloadDigest`. Shape it as a trait with an async method (or an async function
pointer / boxed closure) so an offline test can substitute a double that returns bytes read from a
local file — that substitution is the entire testability argument for this plan, and it is why the seam
is the LAST thing to be wired live.

Keep the seam's surface minimal: it takes a reference and credentials, it returns bytes and a declared
digest, and it knows nothing about layouts, verification or rendering. A wide seam constrains the live
wiring later; D-04 already flags the shape as `costly` for that reason.

Implement the live side in `graphql.rs`, beside the operations that already live there.

**First, hoist the HTTP client to module scope and give it a stated timeout policy (review finding
H3).** MEASURED: the `static CLIENT: OnceLock<reqwest::Client>` at `graphql.rs:481` is declared inside
`execute_graphql_at`'s BODY, so it is function-scoped and no new function can reach it; and it is built
with `reqwest::Client::new`, which carries no timeout of any kind. The reviewed draft said to "reuse the
shared client" and cited `:167`'s timeout builder as the precedent — but `:167` belongs to
`upload_to_s3`, a separate client with a 300-second budget appropriate to large uploads and wrong for
a GraphQL call. Both halves of that instruction were unimplementable as written.

- Move the `OnceLock` out of the function body to MODULE scope in `graphql.rs`, named `HTTP_CLIENT`,
  and build it with `reqwest::Client::builder()`. Put on the CLIENT only what is genuinely shared: a

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| pmcp.run GraphQL endpoint -> `pull` | Untrusted remote; the response's fields are validated and its declared digest is never taken as authority over the bytes. |
| presigned `downloadUrl` -> the artifact bytes | Fully untrusted transport. §5.1: transport is never trusted; every digest is re-derived locally. |
| `downloadUrl` itself -> logs, errors, disk | The URL is a bearer credential to a different origin; crossing this boundary is a disclosure event. |
| verified bytes -> the destination directory | One-way: nothing reaches the destination that has not passed every gate. |

| T-123-45 | Denial of Service | an oversized or endless download body | high | mitigate | A named byte cap enforced while reading, chunk by chunk via `Response::chunk()` with a running total (NOT `bytes_stream()` — reqwest's `stream` feature is not enabled here), refusing on overflow rather than collecting then measuring; a connect timeout on the shared client plus a per-request download timeout constant. |
