Create `scripts/release-version-sweep.sh` as a permanent, committed, **reporting-only** tool
(the discretion CONTEXT leaves open resolves to permanence: it is ~40 lines, adds no
dependency, and is the only mechanism that can detect a phantom delta — a failure class this
repo has now hit at least seven times).

Header: follow the `scripts/lint-plan-verify-commands.sh` convention — a numbered rationale
block stating (1) what a phantom delta is: a crate whose in-tree version equals its published
version while its source has moved since that version was published, so `release.yml`'s
already-published skip makes it silently not ship; (2) why the published-version oracle is
the crates.io API v1 and not Cargo — `cargo search` and `cargo info` report the in-tree path
override as published state, measured on this repo during Phase 122; (3) why a `User-Agent`
header is mandatory — without one the versions endpoint returns an empty body and every probe
looks like a fetch failure; (4) why the diff base is the earliest `v*` tag *containing* the
crate's version-bump commit rather than the latest tag or the bump commit itself; (5) why this
script reports and never gates.

Discovery: mirror the coverage gate exactly — root members via `cargo metadata --no-deps
--format-version 1` filtered by `.publish == null`, plus the `crates/*/Cargo.toml` scan for
manifests carrying their own `[workspace]` table, each classified through a second `cargo
metadata --manifest-path` call with the same predicate. Emit name, version and manifest path
per crate. A sweep that cannot see what the gate sees would reintroduce the very blind spot
plan 01 closed.

Published version — three separate concerns, and conflating them is what makes a sweep lie:

  1. **The probe.** `curl` the crates.io API v1 versions endpoint for the crate name with a
     `User-Agent` header identifying the tool and a contact address, capturing the HTTP status
     separately from the body. Retry a failed or unparseable probe a bounded number of times
     with a short sleep before giving up; record the attempt count.
  2. **Classification of the response.** Three distinct outcomes, and the report must
     distinguish all three: a parsed version list; `UNPUBLISHED` (a well-formed response
     saying the crate has no versions, or a 404); and `PROBE_FAILED`. A body that parses as
     JSON is not automatically data — measured during the review, twice in about eight
     requests and for both `pmcp` and `mcp-tester`, crates.io returned a **200 whose body was
     a type descriptor rather than data** (`{ meta: { next_page: null, total: int }, versions:
     [{ audit_actions: [{ action: string, ...`), which is not parseable as the versions
     payload. Treat any parse failure as `PROBE_FAILED`. Never as `UNPUBLISHED`: an
     `UNPUBLISHED` reading against a crate whose in-tree version is unchanged renders as a
     phantom delta, and a false phantom delta can authorise a permanent version bump that was
     never needed. D-05 anticipated only the empty-body-without-`User-Agent` failure; this is
     a second, distinct shape and the header must name both.
  3. **Selection of the published version.** Do NOT take `versions[0]` — the array's ordering
     is observed, not documented. Filter out yanked releases, then select the maximum by
     SEMVER comparison. A lexicographic sort is wrong and silently so: it orders `0.10.0`
     below `0.9.0`. Record the yanked state of the selected version in the TSV.

Diff base — and be honest in the report about how much this is worth. Derive the crate's
version-bump commit with `git log -1 --format=%h -L '/^version = /,+1:'<manifest>`, then take
the earliest `v*` tag containing it (`git tag --list 'v*' --contains <bump>
--sort=creatordate`, first entry). Then diff `<tag>..HEAD` limited to the crate directory (for
the root crate, `src/` and `Cargo.toml`) and print the shortstat.

**Tag containment is a heuristic, not a publication oracle, and the script must say so per
crate.** It assumes every tag published every crate, which is false in this repository by its
own record: `scripts/check-release-coverage.sh:6-9` documents two crates that were tagged but
had no publish step at all — `pmcp-openapi-server` and `pmcp-tasks`, the latter discovered
only because a downstream consumer could not pin it — and `pmcp-workbook-runtime` is
documented as published out-of-band. So emit a **BASELINE PROVENANCE** field per crate with an
explicit confidence, at minimum distinguishing:

  - `tag:<name>` — a containing tag was found (heuristic, unconfirmed);
  - `tag:<name>+confirmed` — a containing tag was found AND corroborated against published
    artifact evidence;
  - `no-tag` — no tag contains the bump commit, so this version has never been released and
    ships at the next tag. This is a marker, not an empty delta.
  - `unresolved` — the bump commit itself could not be located (a `git log -L` result is
    fragile: it depends on manifest formatting and rename history and can resolve an unrelated
    `version = ` line). This is a FAILURE, not a low-confidence reading.

`unresolved` sets `fail=1`.

**Exit code discipline.** Any `curl`, `cargo`, `git`, `jq` or parse failure, any
`PROBE_FAILED`, and any `unresolved` baseline sets `fail=1`, prints a named `::error::` line,
and makes the script **exit non-zero after the complete report has been printed**. Print the
whole report first — a partial sweep that stops at the first failure is less useful than a
complete one that refuses to claim success. A report containing failure markers must never be
mistakable for a completed sweep, and an exit status is the only part of the output a caller
cannot overlook.

Output: emit a machine-readable TSV (name, in-tree version, published version, HTTP status,
yanked state, baseline provenance, delta) as the primary artifact, and render the human-facing
aligned table from that same data rather than formatting twice. This is a report a human
reads, so alignment and a stable column order matter — but the TSV is what plan 05 and plan 07
consume, and deriving both from one source is what stops them disagreeing.

**Version comparison is exact string comparison of the semver literal as written.** `0.3.0`
does not equal `0.3`. Where the manifest string and the registry `num` string differ only in
form, report the mismatch rather than normalising it away — a human reading the table is the
right resolution for that case, and silent normalisation is how a bump gets skipped.

Then add a `release-sweep` Make target in the `lint-plans` shape — a `$(BLUE)` announce, the
script invocation, a `$(GREEN)✓` line — with a comment above it stating that unlike
`lint-plans` this target is deliberately NOT chained into `quality-gate`, because it needs
network access and because a version delta is legitimate right up until a release, so gating
on it would produce false CI failures on every ordinary branch. Add the `.PHONY:` line above
the target.

Do not add `release-sweep` to the `quality-gate` recipe.

Step B — classify every crate the sweep reports into exactly one of four buckets, and record
the classification with the evidence that supports it:
  - **clean** — in-tree equals published, no delta. Nothing to do.
  - **already bumped** — in-tree is ahead of published; the bump has no containing tag, so it
    ships at this phase's tag as-is. Nothing to decide.
  - **phantom delta, non-source** — in-tree equals published and the delta touches only
    formatting or a manifest dependency requirement. Recommend leaving, and say why.
  - **phantom delta, source-visible** — in-tree equals published and the delta changes code
    or public API. Recommend a bump and name the axis, with the reasoning stated.
For each source-visible delta, read the actual diff before classifying — a shortstat is not a
classification. RESEARCH's prior run found two in this bucket (`pmcp-code-mode-derive`, whose
generated code moved from a synchronous SQL validation call to an async one; and

Record which corroboration was used and upgrade the crate's provenance to `tag:<name>+confirmed`.
