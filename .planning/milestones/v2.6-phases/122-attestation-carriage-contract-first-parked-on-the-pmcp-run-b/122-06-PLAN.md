**The sandbox-parent snapshot, replacing the weaker layout enumeration.** A previous revision of this property asserted only that the layout directory contained no unexpected file. Cross-AI review correctly observed that enumerating the layout directory can prove its own contents are expected but cannot detect a path-traversal write landing OUTSIDE it — which is precisely what a `..`-bearing annotation would produce. Build it this way instead:

- Create a `tempfile::tempdir()` as the SANDBOX PARENT, and create the `OciLayout` in a subdirectory of it (for example `parent.path().join("layout")`), never at the parent root. The empty sibling space inside the parent is what a traversal write would land in.
- Write a small recursive snapshot helper in the test file: walk the parent with `std::fs::read_dir`, recursing into directories, and collect a sorted `Vec<(PathBuf, u64)>` of every entry's path relative to the parent plus its byte length. Do NOT add a `walkdir` dependency — a new crate would have to be admitted to the D-13 allowlist, and a fifteen-line recursion is cheaper than that conversation.
- Snapshot the parent AFTER the pack and BEFORE the unpack, run `unpack_server`, snapshot again, and assert the two `Vec`s are EQUAL. `unpack_server` is a pure reader — it writes nothing at all — so equality is the correct and strongest assertion, and any difference is a real finding rather than an expected-set bookkeeping exercise.
- Record the blind spot in the property's rustdoc, per the repo convention that a mechanism states what it cannot see: this detects a write anywhere beneath the sandbox parent, but not an absolute-path write elsewhere on the filesystem. Pair it with the source-level statement that the annotation values are only ever moved into `UnpackedAttestation` fields and never passed to any `std::fs` or `Path` API, and note that the two together — a runtime snapshot plus a reviewed data-flow — are what carry the claim.

For the digest-difference property, reuse the scratch unattested pack already computed for the subject and assert inequality against the attested digest.

Add the valid-JSON case as a plain `#[test]` alongside the properties, with a rustdoc sentence saying why it exists: an accidental `canonicalize` on the payload would be invisible to a non-JSON payload (it would simply fail) but would silently reorder a valid JSON object's keys, so this case is the one that catches it.

## Recorded exception — proptest instead of a `cargo fuzz` target (ALWAYS requirement)

`CLAUDE.md`'s ALWAYS requirements list FUZZ testing and PROPERTY testing as separate mandatory deliverables for every new feature. This phase ships property tests (Task 1) and does **not** add a `cargo fuzz` target. That is a deliberate, recorded exception rather than a silent substitution, and it is written down here so the absence is a visible decision. The executor must restate it in `122-06-SUMMARY.md`.

Four measured reasons:

1. **The `make test-fuzz` gate enforces nothing today.** `Makefile:538-548` pipes every fuzz target through `timeout 30s ... || echo`, so a crashing target is swallowed and the target exits green regardless. Adding a fuzz target would add a line to a gate that cannot fail.
2. **`cargo fuzz` requires nightly.** The repo's CI toolchain is `dtolnay/rust-toolchain@stable`, so a libFuzzer target on this boundary would never run in CI at all — a gate blind spot of exactly the class plan 122-01 exists to close, introduced by the act of "satisfying" the requirement.
3. **There is no home for the target.** `fuzz/` is the ROOT crate's fuzz workspace, and `pmcp-package` is workspace-EXCLUDED (`crates/pmcp-package/Cargo.toml` carries its own `[workspace]` table). A target in `fuzz/` cannot reach this crate's `pack_server`/`unpack_server` without a new manifest wiring that nothing else in the repo has.
4. **The property suite covers the same input space, and it actually runs.** Task 1 generates arbitrary `Vec<u8>` payloads (including invalid UTF-8, embedded NULs, JSON-shaped-but-not-JSON, and the empty vector) and adversarial annotation strings, and `make pmcp-package-gate` — which this plan additionally hardens with a nonzero-test-count assertion — executes it inside `make quality-gate` on stable, where a failure is a red gate rather than an echoed line.

Scope of the exception: it covers only the attestation carriage boundary this phase adds. It is not a precedent for dropping fuzz coverage elsewhere, and it should be revisited if `make test-fuzz` ever stops swallowing failures.
