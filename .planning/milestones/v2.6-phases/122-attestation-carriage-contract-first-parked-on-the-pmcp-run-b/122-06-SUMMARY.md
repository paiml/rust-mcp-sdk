**Opacity became a checked invariant over generated bytes rather than a single fixture — and the adversarial-annotation property found a real defect on its first run: a control character in an attestation annotation produced a package that packed cleanly and could never be unpacked, now refused before the first write.**

## Accomplishments

- **The property did the thing properties are for.** It was not a restatement of a passing fixture: its FIRST run failed on `issuer = "\0"`, exposing that `canonicalize` (OLPC/TUF Canonical JSON, which `olpc-cjson` implements) writes C0 control characters LITERALLY while RFC 8259 forbids them unescaped inside a JSON string. Any control character in an annotation therefore produced manifest bytes that no JSON parser will read — a package that packs, whose digest verifies, and which then fails to unpack here and in every other OCI tool.
- **The no-writes claim is now carried by a mechanism that can see an escaping write.** Cross-AI review's MEDIUM finding was implemented as specified (sandbox-parent snapshot), and the falsifiability control proved it: with an escaping write injected, the snapshot caught `escaped-by-the-issuer` sitting at the PARENT level, outside the layout — precisely what the layout-only enumeration could not have seen.
- **Every artifact is gate-REACHED, proven by name and by count, with a red control for each.** `make pmcp-package-gate` prints `Running tests/attestation_opacity.rs`, asserts `286 tests` (up from the 278 baseline), and executes the example. ## The defect the property found, and the fix

**Root cause, confirmed rather than inferred.** `olpc-cjson-0.1.4/src/lib.rs:191` carries the comment *"Only quotes and backslashes are escaped in canonical JSON"*, and its own test docs state plainly: *"Canonical JSON prints literal ASCII control characters instead of escaping them."* That is correct for the OLPC/TUF spec and incompatible with RFC 8259. Observed failure:

```
thread 'adversarial_annotation_values_come_back_as_inert_data' panicked:
an attested layout must unpack: Serialize(Error("control character ( -)
found while parsing a string", line: 1, column: 1237))
minimal failing input: issuer = "\0", payload_type = "../"
```

**Fix (deviation Rule 2 — missing critical input validation).** `pack_server` now REFUSES such an attestation before its first blob write:

```rust
PackageError::AttestationAnnotationInvalid { annotation: String, reason: String }
fn reject_attestation_annotations_that_break_canonical_json(Option<AttestationFile<'_>>) -> Result<()>
```

called first in `validate_pack_preconditions`. `reason` names the code point and its byte offset; it never reproduces the value, following the rule `ConfigSlotViolation`'s rustdoc sets.

**Rejected alternatives, and why:**

| Alternative | Rejected because |
|---|---|
| Make the unpack side tolerant | The bytes are genuinely invalid JSON; tolerating them needs a bespoke lenient parser and leaves the artifact unreadable by every other OCI tool |
| Change `canonicalize` to escape control characters | It is the crate's ONE canonicalizer; escaping differently would move every existing manifest digest — a change of a completely different magnitude, and Rule 4 territory |
| Narrow the property's strategy to exclude control characters | Weakening a test to hide a real finding |

**The gate is bounded in both directions.** It covers `issuer` and `payload_type` only — `subject` is validated one gate later as `sha256:<64 hex>`, which admits no control character, so duplicating a weaker check would only change which of two refusals a caller sees. And `a_non_ascii_attestation_annotation_is_accepted` pins that a legitimate internationalized issuer still packs, so "refuse anything unusual" would not pass.

**Wider blind spot, recorded not silently assumed away.** The same canonical-JSON hazard applies to every OTHER string this crate canonicalizes: a `ConfigFile`/`OpenApiSpecFile` `file_name` (which becomes the `org.opencontainers.image.title` annotation) and every `String` inside `ServerPackage`. Those are author-supplied rather than platform-supplied — a different trust class — and are deliberately out of this plan's scope. Stated in `reject_attestation_annotations_that_break_canonical_json`'s own rustdoc and appended to `.planning/WINDOWS.md` (item #32, `deviation`, open).

## Falsifiability controls

All four were run against the real tree, observed to fail, and fully reverted. `git status` after each revert was clean.

### Control A — a canonicalizer applied to the attestation payload

**Mutation:** `plan_attestation_layer` changed to pass `canonicalize(&serde_json::from_slice::<serde_json::Value>(bytes)?)` instead of `attestation.bytes`.

**Observed:** `test result: FAILED. 0 passed; 5 failed`

Both predicted failures occurred, in the predicted shapes:

```
---- a_valid_json_payload_is_carried_verbatim_and_never_canonicalized ----
assertion `left == right` failed: a valid-JSON attestation payload must be carried
VERBATIM — a key reordering or a whitespace strip here means the payload was parsed
and re-emitted

---- arbitrary_attestation_bytes_survive_a_pack_unpack_round_trip_byte_identically ----
INJECTED FALSIFIABILITY CONTROL: Error("expected value", line: 1, column: 1)
```

The valid-JSON case is the one that matters: a canonicalizer FAILS loudly on a non-JSON payload, but on a valid JSON object it succeeds while silently sorting keys and stripping whitespace. That case is the only assertion in the suite that can see it.

### Control B — an escaping write derived from an annotation value

**Mutation:** `read_attestation_layer` gained `std::fs::write(layout.root().join(issuer), b"x")`.

**Observed via the property:** `4 passed; 1 failed`, but proptest shrank to `issuer = "\\"` — a write landing INSIDE the layout, which the weaker layout-only enumeration would also have caught. That is not the claim being made.

**Observed via the named deterministic case** (`a_traversal_shaped_issuer_writes_nothing_beside_the_layout`, added for exactly this reason):

```
right: [("escaped-by-the-issuer", 1), ("layout", 0), ("layout/blobs", 0), ...]
assertion `left == right` failed: a `../`-shaped annotation must not produce a write
beside the layout
```

`escaped-by-the-issuer` sits at the sandbox-PARENT level, OUTSIDE the layout — the exact region a layout enumeration cannot see. That is the gap cross-AI review identified, demonstrated closed.

**Recorded blind spot** (in the property's own rustdoc): this detects a write anywhere beneath the sandbox parent, but NOT an absolute-path write elsewhere on the filesystem. The other half of the claim is a reviewed data flow — the three annotation values are read by `required_annotation`, moved into `UnpackedAttestation`'s fields, and never passed to any `std::fs` or `Path` API. The runtime snapshot and the reviewed data flow carry the claim jointly; neither carries it alone.

## Recorded exception — proptest instead of a `cargo fuzz` target (ALWAYS requirement)

Restated verbatim from the plan, as the plan requires:

> `CLAUDE.md`'s ALWAYS requirements list FUZZ testing and PROPERTY testing as separate mandatory deliverables for every new feature. This phase ships property tests (Task 1) and does **not** add a `cargo fuzz` target. That is a deliberate, recorded exception rather than a silent substitution, and it is written down here so the absence is a visible decision.
>
> Four measured reasons:
>
> 1. **The `make test-fuzz` gate enforces nothing today.** `Makefile:538-548` pipes every fuzz target through `timeout 30s ... || echo`, so a crashing target is swallowed and the target exits green regardless. Adding a fuzz target would add a line to a gate that cannot fail.
> 2. **`cargo fuzz` requires nightly.** The repo's CI toolchain is `dtolnay/rust-toolchain@stable`, so a libFuzzer target on this boundary would never run in CI at all — a gate blind spot of exactly the class plan 122-01 exists to close, introduced by the act of "satisfying" the requirement.
> 3. **There is no home for the target.** `fuzz/` is the ROOT crate's fuzz workspace, and `pmcp-package` is workspace-EXCLUDED (`crates/pmcp-package/Cargo.toml` carries its own `[workspace]` table). A target in `fuzz/` cannot reach this crate's `pack_server`/`unpack_server` without a new manifest wiring that nothing else in the repo has.
> 4. **The property suite covers the same input space, and it actually runs.** Task 1 generates arbitrary `Vec<u8>` payloads (including invalid UTF-8, embedded NULs, JSON-shaped-but-not-JSON, and the empty vector) and adversarial annotation strings, and `make pmcp-package-gate` — which this plan additionally hardens with a nonzero-test-count assertion — executes it inside `make quality-gate` on stable, where a failure is a red gate rather than an echoed line.
>
> Scope of the exception: it covers only the attestation carriage boundary this phase adds. It is not a precedent for dropping fuzz coverage elsewhere, and it should be revisited if `make test-fuzz` ever stops swallowing failures.

**A fifth reason, earned during execution rather than argued in advance:** the property suite found a real, previously-unknown defect in the shipped carriage path on its first run. Reason 4 predicted equivalent coverage; the outcome demonstrated it.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing Critical] Control characters in an attestation annotation produced an unreadable package**

- **Found during:** Task 1, on the adversarial-annotation property's FIRST run
- **Issue:** documented in full above. `pack_server` accepted an annotation value carrying a C0 control character and produced a manifest that is not RFC 8259 JSON; `unpack_server` (and every other OCI tool) then fails on it. The package packs, its digest verifies, and it is permanently unreadable.
- **Fix:** `PackageError::AttestationAnnotationInvalid` plus `reject_attestation_annotations_that_break_canonical_json`, called first in `validate_pack_preconditions` so the refusal precedes the first write. Bounded by a complementarity assertion in the property and a non-ASCII acceptance test in `negative.rs`.
- **Files modified:** `crates/pmcp-package/src/error.rs`, `crates/pmcp-package/src/oci/pack.rs`, `crates/pmcp-package/tests/negative.rs`
- **Verification:** `an_attestation_annotation_carrying_a_control_character_is_refused_before_any_write` (both fields, with a full pre-write layout snapshot), `a_non_ascii_attestation_annotation_is_accepted`, and the property's two-armed assertion.
- **Committed in:** `2b15f27f`

**2. [Rule 1 - Bug] The property's filesystem assertion needed a NAMED escaping case, not only a generated one**

- **Found during:** Task 1, while reproducing falsifiability control B
- **Issue:** the plan's acceptance criterion requires the snapshot to fail "for at least one generated `..`-bearing annotation", proving it detects an ESCAPING write. Under the injection, proptest shrank to `issuer = "\\"` — a write landing inside the layout. The property failed, but for a reason that does not demonstrate the claim; a reader could have recorded a control as passed while the specific gap remained unproven.
- **Fix:** added `a_traversal_shaped_issuer_writes_nothing_beside_the_layout`, a deterministic `#[test]` naming the escaping shape, with its rustdoc explaining why sampling is not enough here. Under the injection it fails showing a file at the PARENT level.
- **Files modified:** `crates/pmcp-package/tests/attestation_opacity.rs`
- **Verification:** control B, run against this named test; reverted.
- **Committed in:** `2b15f27f`

**3. [Rule 3 - Blocking] The plan's round-trip-only annotation assertion became unsatisfiable**

- **Found during:** Task 1
- **Issue:** the plan specifies the annotation property asserts the values "come back equal to what went in" and the call "does not panic". With deviation 1's refusal in place, a control-character annotation never round-trips at all — so the property as literally written could not both include control characters in its strategy and pass.
- **Fix:** the property asserts a two-armed contract instead, and asserts the arms are EXACTLY complementary (refusal ⟺ a control character is present). This is strictly stronger than the original: it additionally forbids the new gate from widening onto legitimate input. The test re-implements the control-character predicate rather than importing the crate's private one, so the two cannot be wrong together.
- **Files modified:** `crates/pmcp-package/tests/attestation_opacity.rs`
- **Verification:** the property passes at 256 and at 1000 cases; the non-ASCII acceptance test pins the non-widening arm deterministically.
- **Committed in:** `2b15f27f`
