## The CR-01 fix decision, and the evidence behind it

Three options were on the table. The decision was made against a reproduction run at plan time, not
against preference.

### Evidence: what cargo actually does with a `version`-carrying dev-dep

An isolated two-crate probe was built and run at plan time (cargo 1.98.0, macOS). A consumer crate
with a `[dev-dependencies]` path dep on a leaf crate that does not exist on crates.io:

- **Form A — `{ version = "0.2", path = "../leaf" }`:** `cargo package --no-verify --allow-dirty`
  FAILS: `error: failed to prepare local package for uploading` / `no matching package named
  'zz-planner-probe-leaf' found` / `location searched: crates.io index`. This is CR-01's exact
  failure, reproduced independently of the code reviewer.
- **Form B — `{ path = "../leaf" }`:** `cargo package --no-verify --allow-dirty` SUCCEEDS
  (`Packaged 4 files`), and the generated `Cargo.toml` inside the produced `.crate` tarball carries
  an **empty** `[dev-dependencies]` table — the entry is stripped wholesale. No crates.io resolution
  is attempted for it.

So the mechanism is settled: the `version` key, not the `path` key and not the `exclude = ["tests/"]`
line, is what forces the registry lookup.

### Also measured: the naive acceptance criterion does not work here

`cargo package -p pmcp-openapi-server --no-verify --allow-dirty` was run against the real crate at
plan time. It fails — but on `pmcp-server-toolkit = "^0.1.2"` (`candidate versions found which
didn't match: 0.1.1, 0.1.0`), which is a normal, expected release-order artifact: the toolkit
publishes at an earlier `release.yml` step, so 0.1.2 exists by the time openapi-server publishes.
Cargo reports the FIRST unresolvable requirement and stops, so `pmcp-package` is never even reached.

**Consequence for this plan:** a bare `cargo publish -p pmcp-openapi-server --dry-run` exiting 0 is
NOT an achievable acceptance criterion in a local tree, and asserting "the failure output no longer
mentions `pmcp-package`" would pass vacuously today. Task 1 therefore isolates the real manifest in
a scratch copy where every path-carrying dep EXCEPT `pmcp-package` is de-versioned, which makes
`pmcp-package` the only requirement that can fail — and then runs the check in both directions.

A second measured gotcha, recorded because it silently inverted a probe run at plan time: piping
`cargo package` into `tail` makes `$?` report `tail`'s status, so a FAILING cargo run printed
`EXIT=0`. Task 1's commands must capture cargo's own status (`${PIPESTATUS[0]}`, or no pipe at all).

### Decision

**CHOSEN — Option (a): drop the `version` key, path-only dev-dep.**
— **Reversibility: `reversible`.** It is a one-line manifest edit, and because cargo strips the
entry entirely from the published manifest, nothing outside this repository can observe it. Re-adding
the key is a one-line revert. No `checkpoint:decision` is inserted, because the gate reserves that
for `one-way` ratings and this is not one.

**REJECTED — Option (b): reorder `release.yml` so `pmcp-package` publishes before line 339.**
— **Reversibility: `one-way`** — it changes a published-release contract that has already run. Three
concrete costs, each grounded in a file read at plan time:
  1. `release.yml:426-436` states the four experimental 0.x crates (`pmcp-package` ->
     `pmcp-cfn-renderer` -> `pmcp-agent` -> `pmcp-team-servers`) publish late *specifically* so "a
     failure here must not gate the already-published core `pmcp` SDK". Hoisting `pmcp-package` to
     before line 339 puts an experimental 0.x crate ahead of `pmcp-openapi-server`, `mcp-tester`,
     `mcp-preview` and `cargo-pmcp`, inverting that stated risk posture.
  2. `pmcp-package` is workspace-EXCLUDED (its own `[workspace]` table at
     `crates/pmcp-package/Cargo.toml:6`) and publishes via `--manifest-path`, not `-p`.
     `scripts/check-release-coverage.sh:14-16` records it as a KNOWN BLIND SPOT of the machine
     check, so a reorder is verified by nothing but the hand-maintained CLAUDE.md prose ledger.
  3. That prose ledger would have to be edited in lockstep or the two drift — the exact failure the
     ledger has already suffered twice (`pmcp-openapi-server` 2026-07-27, `pmcp-tasks` 2026-08-21).
— Option (b) also does not actually fix anything option (a) leaves broken: nothing outside this repo
  consumes `pmcp-openapi-server`'s dev-dependencies.

**REJECTED — Option (c): drop the dev-dep entirely and assert the pin some other way.**
`crates/pmcp-openapi-server/tests/roundtrip_e2e.rs` calls into `pmcp-package` to pack in environment
A and unpack in environment B. The dev-dep IS the PKG-04 deliverable's dependency; removing it
deletes SC1-SC4. Rejected as non-viable, not as second-best.

### What the tripwire guarantees after this change, and what it no longer guarantees

D-03 gave the tripwire a purpose: "a silent `0.2` -> `0.3` drift fails loudly rather than resolving
to a version the round-trip E2E was never written against."

- **LOST:** there is no longer a version-requirement *string* in the manifest to assert. The literal
  caret-`0.2` check is gone and cannot come back without reintroducing CR-01.
- **RETAINED, and strengthened:** the tripwire re-anchors D-03's actual guarantee to
  `crates/pmcp-package/Cargo.toml`'s own `version` field — the crate the path dep genuinely resolves
  to. A caret requirement string only constrains what *would* be accepted from a registry; the path
  dep ignores the registry entirely, so asserting the resolved crate's version is a strictly stronger
  statement about what the E2E actually compiled against.
- **GAINED:** a new publish-safety assertion that fires if anyone re-adds a `version` key — i.e. the
  tripwire now catches CR-01 instead of mandating it.
- **STILL NOT COVERED (unchanged, already documented in the file's module doc):** `cargo-pmcp`'s own
  `pmcp-package` pin, the `cargo-pmcp/src/templates/agent.rs` scaffold emitter, and the
  `pmcp-agent` / `pmcp-team-servers` / `pmcp-cfn-renderer` manifests. Each has its own guard.
