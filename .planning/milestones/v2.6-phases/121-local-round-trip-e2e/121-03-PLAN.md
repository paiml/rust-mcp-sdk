<objective>
Prove the round-trip test is sensitive to real regressions and insensitive to manifest shape —
both directions, both machine-checked — and correct the one stale doc comment this phase's
reading surfaced.

SC4 has two halves and they fail in opposite ways. The RED half (a real regression must turn
the test red) is proven by negative tests over a deliberately-degraded environment B, asserting
the SPECIFIC mismatch rather than merely that something failed. The GREEN half (a manifest-shape
refactor must leave the test green) is proven by a structural guard that machine-checks SC4's
"contains no assertion on manifest structure" clause instead of trusting review.

Purpose: without the red half, the phase ships a test nobody has ever seen fail. Without the
green half, SC4's durability claim is an unverified promise, and the milestone expects manifest
refactors.

Output: four new test functions (two negatives, the RAII env-guard restoration proof, and the
structural guard), the deny-list constant and the span scanner in `roundtrip_e2e.rs`, plus a
one-paragraph rustdoc correction in `crates/pmcp-package/src/slot/deviation.rs`.

**Two shapes this plan explicitly does NOT use, and why** (both were recommended by one of the
two cross-AI reviewers and both were adjudicated against source):
- **A per-line scan for the structural guard.** It reads only lines containing an assertion
  keyword, so a forbidden token on a rustfmt-produced continuation line is never examined. The
  guard scans delimiter-balanced assertion SPANS instead (Task 2).
- **A trailing restore line for the environment variable.** It is skipped by any earlier
  assertion failure and leaks the mutated variable into every later test in the binary. The
  unfilled-slot negative uses `common::EnvVarGuard`'s RAII restore instead (Task 1).
</objective>

  <action>
Add `roundtrip_e2e_asserts_nothing_about_manifest_shape`, a plain `#[test]`, with all six
properties below. Dropping any one of them degrades the guard into something that can pass
while measuring nothing.

**1. Read the file at compile time.** Declare a const holding `include_str!` of this test file's
own name. The argument resolves relative to the test file, so there is no runtime path
resolution and no manifest-directory join to get wrong — the same mechanism the sibling pin
tripwire uses.

**2. Scan assertion SPANS, not lines.** This is the property the whole guard turns on, and a
per-line scan is the shape it must NOT have.

  a. **Sanitize each line before anything else.** Produce a scanning copy of the line with
     string-literal contents removed (walk the characters tracking whether you are inside a
     `"` literal, honouring `\` escapes; treat an `r#"..."#` raw literal the same way) and with
     any trailing `//` line comment removed. Both the delimiter counting in (c) and the
     deny-list matching in property 3 operate on this sanitized copy, never the raw line.
     Sanitizing is what lets a comment — including this file's own explanatory header, and a
     trailing comment inside a span — name a forbidden shape without tripping the guard.
     Removing string contents is not optional either: assertion messages in this repo routinely
     contain parentheses (`parity_replay.rs:418-419` is a live example), and a naive counter
     would never see such a span close.
  b. **Detect a span start.** A span starts on a sanitized line containing any of the six
     macro-start tokens `assert!`, `assert_eq!`, `assert_ne!`, `debug_assert!`,
     `debug_assert_eq!`, `debug_assert_ne!`.
  c. **Accumulate to the close.** From the start line, track the running depth of `(`, `[` and
     `{` against their closers over the sanitized text. The span ends on the line where that
     depth returns to zero. Accumulate the sanitized text of every line in the span.
  d. **Guard against runaway.** Cap a span at a stated maximum number of lines. If the cap is
     reached without balancing, do NOT silently drop the span — end it at the cap, keep what
     was accumulated, and count it. A scanner that abandons unbalanced spans is a scanner an
     unusual formatting choice can switch off.

  This replaces the per-line scan the earlier draft specified, which could only ever see the
  `assert_eq!(` line itself. A forbidden token on a continuation line contains no assertion
  keyword and would never be examined — and because `cargo fmt --all -- --check` is an
  acceptance criterion of every task in this phase, rustfmt ACTIVELY PRODUCES that shape by
  splitting long assertion invocations across lines. The multiline form is the normal case in
  this repo, not an edge case (REVIEWS HIGH).

**3. Deny-list as a named constant, applied to the whole span.** Declare a `const` array of
string slices, each token traceable to SC4's own wording ("manifest field names, layer ordering,
digest values"). The list must cover at minimum: the word for a content hash and its
algorithm-prefixed form; the indexed accessors for the manifest collection and the layer
collection; the layer accessor call; both the snake-case and camel-case spellings of the
media-type field; the artifact-type field; the blob-read and index-read accessors; and the
annotations field. Keep it as data in a named constant so it reads as a list, not as a regular
expression. For each completed SPAN, assert none of the deny-list entries appears anywhere in
the span's accumulated sanitized text, with a failure message naming the offending token, the
span's starting line number, and the span text.

**4. A nonzero-SPANS-scanned floor.** Count completed spans — not lines — and assert that count
is at least a stated floor. Measure the real span count in the current file first and set the
floor to that measured number less a margin of no more than a quarter, never below 10; write
BOTH numbers into the comment (the measured count and the floor derived from it) so a later
reader can see it was measured rather than picked. A round number chosen for looking safe is the
brittleness the review flagged: unrelated assertion refactoring drifts the real count, and a
floor with no stated derivation gives the next person nothing to re-derive it from. The failure
message must say the guard is not reaching the file. Without this, a renamed file, an over-tight
filter, or an unexpected `include_str!` target makes the loop body never execute and the test
passes having examined nothing. This is the same discipline the Makefile applies to test counts.

**5. A multiline-coverage self-check — the guard's guard.** Also count the total number of lines
covered by all spans, and assert that total is STRICTLY GREATER than the number of spans. That
inequality is false if and only if every span was exactly one line long, which is precisely what
