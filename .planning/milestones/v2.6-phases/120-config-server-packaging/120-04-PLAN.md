## Locked-decision notes carried into the tasks

- **D-17 (locked, post-research).** D-04's `${VAR}` requirement is scoped to VALUE slots
  (endpoint, credentials). The auth-mode key is exempt as structural: `AuthConfig` is
  `#[serde(tag = "type")]` (`http/auth.rs:58-60`), so `type = "${AUTH_MODE}"` is an
  unparseable `unknown variant` error — no placeholder form of that key can exist. AuthMode
  stays a declared slot (PKG-03's three are unchanged); its baked value is the default and
  deviation surfaces through slot classification, not a placeholder.
- **D-18 (locked, post-research).** These toolkit changes are additive and their reversibility
  is `costly`: the `[[config_slots]]` schema becomes part of the toolkit's published config
  surface.

## Layering note: who owns the ConfigSlotDecl -> ConfigSlot mapping

The cross-AI review's HIGH cross-plan finding is that Phase 120 had no authoritative
slot-declaration flow: this plan parses `[[config_slots]]` into toolkit-local `ConfigSlotDecl`
values, while plan 120-05 built matching `pmcp_package::ConfigSlot`s BY HAND in its tests, so
nothing forced the two representations to agree and D-01's "pack reads them" was never
exercised by the real API path.

The resolution, stated here so this plan's boundary is unambiguous:

- **The toolkit does NOT map to `pmcp_package` types, and must not.** `pmcp-package` is the
  workspace-excluded leaf; a toolkit dependency on it inverts the layering. The acceptance
  criteria below machine-check that no such dependency appears.
- **`pmcp-package` re-parses the SAME config bytes.** Plan 120-05 promotes `toml` to a runtime
  dependency anyway, so `pack_server` extracts the `[[config_slots]]` table from the config
  bytes it is already being handed and requires exact agreement with `package.config_slots` on
  key / kind / name / tested_value. That makes the TOML declaration the source of truth,
  reached through the real API path, with no cross-crate dependency in either direction.
- **What this plan owes that flow:** field names and a validated `kind` vocabulary stable
  enough for the package side to compare against. That is why `ConfigSlotKind` exists.
