**Vocabulary, fixed by D-05 and non-negotiable.** Protocol eras are `v1` (2025-11-25) and `v2`
(2026-07-28). The crate is ALWAYS written with its name attached — "pmcp 2.18" — never as a bare

exactly the confusion this rule exists to prevent. The chapter opens, immediately after its H1,
with the disambiguation callout in the book's only callout form: a blockquote with a bolded lead.

**Structure.**

`# Chapter 12.17: Migrating to MCP 2026-07-28 (v2)`, the era callout, then a three-paragraph
intro closing with an "After this chapter you should be able to …" sentence. State the thesis up
front: pmcp is dual-version, negotiation is PER REQUEST, and the answer to "how do I opt into v2"
is genuinely different depending on whether you own a server, a client, or an agent — so find
your track and stop.

`## The dual-version story` — one short section: one binary, both eras, negotiated per request;
what that means for deployment (you do not run two servers); and where the era boundary actually
sits.

`## For servers` — the first role track, and the longest.
  - There is NOTHING to opt into. A pmcp server built normally already answers both eras.
  - The only lever is opting OUT of v1:
    `cargo build -p pmcp --no-default-features --features full-v2`. Explain why
    `--no-default-features` alone proves nothing (`default` includes `logging`, so stripping
    defaults would also strip the HTTP transports and "prove" v1 severable by never compiling the
    transport at all) and why an inverted `v2-only` feature was rejected (cargo features are
    additive and cannot be subtracted, so any crate anywhere in the graph enabling a negative
    feature would silently strip v1 for every other consumer). The `Cargo.toml` comment is
    quotable prose; use it.
  - **The stateless / Lambda subsection — D-12's core.** v2 statelessness is a PER-REQUEST era
    gate, not a build-time switch: `examples/s47_v2_stateless_mrtr.rs` runs the STATEFUL default
    HTTP config, still mints sessions for v1 clients, and yet no v2 response carries a session id.
    Cite the example by its full runnable invocation. Then connect it to Lambda: the
    `pmcp-server-lambda` crate is the standard pattern for running any pmcp server on AWS Lambda,
    and v2's sessionlessness is what makes a multi-instance serverless deployment coherent.
  - **`PMCP_REQUEST_STATE_KEY` — the security-relevant deployment decision.** Quote the runtime
    WARN the server actually emits when it is unset, and state the requirement as a MUST: the
    SAME 32-byte base64url (or hex) value on EVERY instance, or a multi-round-trip follow-up that
    lands on a different instance behind a load balancer cannot be resumed and will be
    re-elicited. Document `PMCP_REQUEST_STATE_KEY_PREVIOUS` alongside it — it joins the ACCEPTING
    set only, for rotation. Document both or neither; a rotation story with only one key is worse
    than none. **If you show a generation command, use a CSPRNG** (`openssl rand -base64 32` or
    reading 32 bytes from `/dev/urandom` and base64-encoding). **Never print a fixed example key
    value** — a copy-pasteable constant in published documentation is a forgeable continuation
    token in someone's production deployment.

`## For clients` — the second track.
  - The opt-in is EXPLICIT: `ClientBuilder::with_protocol_version` with the v2 protocol-version
    constant. Show the shape from the method's own rustdoc doctest.
  - Explain why there is NO auto-probe: the Phase-113 D-08 lock, carried in-source at
    `src/client/mod.rs:1101` and `:5153`, forbids the client probing `server/discover` to CHOOSE
    an era. Say why a silent probe would be worse than an explicit choice.
  - Name what changes on the wire for a v2 client: no `initialize` handshake, no
    `Mcp-Session-Id`, no `Last-Event-Id` SSE resumption, and the three v2 error codes with their
    HTTP-400 mapping (`-32020` header mismatch, `-32021` missing required client capability,
    `-32022` unsupported protocol version) and their payload shapes.

`## For agents` — the third track, deliberately short.
  - `pmcp-agent` prefers v2 with a v1 fallback, and the era probe lives in `pmcp-agent`, NOT in
    `Client` — that placement is the Phase-117 A-D08 amendment and it is what keeps the D-08 lock
    intact.
  - Lead with the CLI: `cargo pmcp agent new` and `cargo pmcp agent dev`. Name no other agent
