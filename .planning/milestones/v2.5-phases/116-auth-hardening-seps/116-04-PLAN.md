Keep the module's constraints: ungated, no `reqwest`/`webbrowser`/`dirs`, `url` and

`validate_issuer_url(issuer) -> Result<Url>` is the hardened parse every other function in this
family calls first. Parsing as an absolute `url::Url` is NOT enough — cross-AI review flagged this as
too permissive, and RFC 8414 §2 constrains the issuer far more tightly than "absolute URL". The rules,
each with its reason written into the rustdoc:
- **Scheme** MUST be `https`, with exactly one exception: `http` is permitted when the host is a
  loopback literal (`127.0.0.1`, `::1`, `localhost`). That exception exists because pmcp's own
  development and test flows use loopback and RFC 8252 §7.3 blesses loopback `http`. Every other
  scheme — including `ftp`, `file`, `data` and `javascript` — is rejected by name in the error.
- **Userinfo** MUST be absent. An issuer of the form `https://honest.example@evil.example` reads as
  the honest host to a human and resolves to the attacker's. There is no legitimate issuer with
  userinfo.
- **Fragment** MUST be absent and **query** MUST be absent — RFC 8414 §2 says so directly, and a
  query would survive into the candidate URL and be attacker-influenceable.
- **Host** MUST be present and non-empty.
Return the parsed `Url` so callers do not re-parse. Every rejection names the specific rule violated,
never a generic "invalid URL".

`same_origin(a, b) -> bool` compares scheme, host and EFFECTIVE port (so `https://x` and
`https://x:443` are the same origin). 116-06 and 116-07 use it to reject a discovery HTTP redirect
that leaves the issuer's origin; a redirect within the origin is permitted.

`classify_discovery_failure(failure) -> DiscoveryOutcome` is the phase's discovery outcome matrix,
made a pure function so both discovery call sites cannot drift and so the matrix is testable offline.
Falling through to a later candidate on "any" failure turns an issuer mismatch, malformed metadata or
an oversized body into a silent DOWNGRADE event — an attacker who can make candidate 1 fail in a
security-relevant way gets the client to accept candidate 3 instead. The three terminal rows are the
whole point: `IssuerMismatch`, `BodyOverCap` and `MalformedSecurityMetadata` abort discovery outright
and are never a fallback trigger. `Retry` means "re-attempt THIS candidate within the existing
`max_retries` budget, then treat it as `Fallback`"; state that composition rule in the enum's rustdoc
so 116-06 and 116-07 implement the same loop. Write the matrix as a table in the function's rustdoc,
row for row, so a reviewer can compare code to doc without reading the body.

`discovery_url_candidates(issuer) -> Result<Vec<Url>>` calls `validate_issuer_url` FIRST, then
implements the spec's normative ordered lists verbatim (both are quoted in RESEARCH § Code Examples).
The rule, stated so the implementation cannot drift: take the validated URL's path with any trailing
slash trimmed; if the
remaining path is non-empty, emit the three path-form candidates in the order above; if it is empty,
emit the two path-less candidates in the order above. The well-known suffixes are
`oauth-authorization-server` (RFC 8414's default, which MCP adopts and which pmcp never tries today)
and `openid-configuration` (OIDC Discovery 1.0's).

Write down in the rustdoc, as the function's reason to exist, that this is an ORDERED PROBE SEQUENCE
and NOT a replacement: RFC 8414 §3.1 specifies insertion for the `oauth-authorization-server` suffix,
OpenID Connect Discovery 1.0 §4.1 specifies appending for `openid-configuration`, and RFC 8414 §5
reconciles them with a fallback order the MCP spec makes a client MUST. Cite the measured Entra ID
result (append 200, both inserted forms 404) as the reason the appended form must remain in the list.
The function derives candidates only; the PROBING (and therefore the network) belongs to the callers
in 116-06 and 116-07 — that split is what makes the MUST-ordered sequence testable offline.

`issuer_matches_metadata(issuer_used_to_build_url, document_issuer) -> bool` is a simple string
comparison with NO normalization — the same rule as `iss`, from the same family of specs (RFC 8414
§3.3 / OIDC Discovery §4.3). Its rustdoc must carry the spec's worked example verbatim: a document
fetched from `https://attacker.example/.well-known/oauth-authorization-server` that contains
`"issuer": "https://honest.example"` MUST be rejected. State plainly why this function exists at all:
without it, AUTH-01's `iss` comparison is anchored on an attacker-chosen value and the whole RFC 9207
check is decorative (RESEARCH Pitfall 1).

Write `tests/oauth_discovery_urls.rs` modelled on `tests/pkce_helper.rs` — a header enumerating the
