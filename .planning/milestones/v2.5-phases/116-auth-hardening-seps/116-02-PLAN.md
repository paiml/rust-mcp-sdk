`IssPresence` is `#[non_exhaustive]` with variants `Required` and `Optional`. There is deliberately

`AuthorizationRequestRecord` holds `expected_issuer`, `code_verifier`, `state` and `iss_presence` as
PRIVATE fields with a `new(..)` constructor and read-only accessors. Private fields are the semver
choice, not a style choice: RESEARCH A1 shows `OAuthConfig`, `DcrRequest` and `OidcDiscoveryMetadata`
are all-pub-field non-`#[non_exhaustive]` structs where adding a field is a MAJOR break; a struct with
private fields is not exhaustively constructible, so future fields stay minor. Its rustdoc must state
the spec's record requirement: issuer, verifier and state MUST live in ONE per-request record — three
separate locals is exactly how `state` became structurally unbindable at `src/client/oauth.rs:712`.

`validate_authorization_response(raw_query, record)` takes the RAW query component (no leading `?`)
so a platform handler that only ever sees a query string can call it. Decode with
`url::form_urlencoded::parse(raw_query.as_bytes())` — RFC 9207 §2.4 REQUIRES the
`application/x-www-form-urlencoded` decode before comparison and this performs it; never hand-roll a
percent-decode. Evaluation order is fixed and load-bearing:
1. `state` — must be present and equal `record.state()`, else `Error::state_mismatch()`.
2. `iss` — the four-row table against `record.expected_issuer()` using `==` on the decoded strings.
   Simple string comparison per RFC 3986 §6.2.1. Apply NO normalization of any kind.
3. `error` — only now may an AS-supplied `error` be surfaced. The spec's MUST NOT is explicit: on an
   `iss` mismatch the client must not act on or display `error`, `error_description` or `error_uri`,
   which is why steps 1 and 2 precede this one.
4. `code` — present ⇒ `Ok(code)`; absent with no `error` ⇒ a protocol error naming the missing
   parameter.

Before step 1, apply two fail-CLOSED input guards. First, reject a `raw_query` longer than
`MAX_CALLBACK_QUERY_BYTES` (8 KiB) with an error naming the limit and the observed length and
echoing no query bytes — the callback URL is peer-controlled and the loopback listener in 116-09
reads it off a socket. Second, count occurrences of each of `state`, `iss`, `code`, `error` and
`error_description`; ANY of them appearing more than once is an error. A "first wins" rule on a
security parameter is a request-smuggling primitive — a proxy or a server that picks the LAST
occurrence and a client that picks the FIRST disagree about what was validated. Unknown/vendor
parameters may repeat freely; they are ignored either way. Say both rules in the rustdoc.

The D-04 precedence resolver is SPLIT into two pure functions so an invalid environment value cannot
fail open silently (a hostile-input case cross-AI review flagged):

- `parse_iss_env_value(value) -> Option<IssPresence>` accepts `"strict"` ⇒ `Required` and
  `"lenient"` ⇒ `Optional`, compared case-insensitively after trimming, and returns `None` for
  anything else — including `"true"`, `"1"` and `"yes"`, which a reasonable operator might type.
- `iss_presence_from(env_override, builder, discovery_flag) -> IssPresence` takes the ALREADY-PARSED
  override. Precedence is env > builder > discovery flag. `discovery_flag` is `Some(true)` ⇒
  `Required`, `Some(false)`/`None` ⇒ `Optional`.

The split is the point: with a single function taking `Option<&str>`, an unrecognized value is
indistinguishable from an unset variable, so an operator who typed `PMCP_OAUTH_ISS_VALIDATION=true`
believing they had enabled strictness gets silence. With the split, 116-09 can see `Some(raw)` +
`None` parse and `tracing::warn!` naming the variable and its two accepted values before falling
through. State that reasoning in `parse_iss_env_value`'s rustdoc so nobody re-merges them.

The env var NAME (`PMCP_OAUTH_ISS_VALIDATION`) is read at the CALL SITE in 116-09, never inside this
module — D-07's I/O-free discipline applies to the pure tier too.
