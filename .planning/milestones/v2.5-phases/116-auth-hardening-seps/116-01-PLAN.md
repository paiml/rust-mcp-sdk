1. `oauth_authorization_response_validation` — AUTH-01/D-12. Formula covers the fixed evaluation
   order `state` → `iss` → AS `error` → `code`; the four-row RFC 9207 table keyed on
   `IssPresence::{Required, Optional}`; and exact string comparison with NO normalization.
   Invariants to state, each derived from the RFC rather than restated from the implementation:
   - A present `iss` that differs from the record's expected issuer is rejected under EVERY
     `IssPresence` value (the amended AUTH-01 text: rejected on every era)
   - Under `IssPresence::Required`, an absent `iss` is rejected
   - Under `IssPresence::Optional`, an absent `iss` is accepted — the ONLY leniency
   - `Ok` implies the decoded `state` equalled the record's state
   - No AS-supplied `error`/`error_description`/`error_uri` is surfaced when `state` or `iss` failed
   - A duplicate occurrence of any of `state`, `iss`, `code`, `error` is rejected

2. `oauth_discovery_anchor` — AUTH-01/AUTH-03/D-13/SEP-2351. Formula covers
   `discovery_url_candidates` (the spec's ordered probe) and `issuer_matches_metadata` (RFC 8414
   §3.3). Invariants:
   - The OIDC appended form is present in every candidate list (Pitfall 2 regression fence)
   - Every candidate preserves the issuer's scheme, host and port
   - Metadata never escapes the fetch boundary unless its `issuer` string-equals the issuer used
     to build the URL
   - `IssuerMismatch`, `BodyOverCap` and `MalformedSecurityMetadata` are TERMINAL and never trigger
     candidate fallback

3. `oauth_credential_binding` — AUTH-03/SEP-2352. Formula covers the
   `(issuer, account, server)` credential key and the schema 1 → 2 migration. Invariants:
   - A lookup differing in ANY of the three key components is a miss
   - Credentials are never re-keyed to an issuer that was not recorded with them
   - The DCR-issued `client_id` lives in the same record as the credentials it belongs to
   - The migration reports both a migrated and a dropped count
