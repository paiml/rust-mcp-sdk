<objective>
Wire AUTH-01 into the CLI authorization-code flow: build the spec-mandated per-request record before
the redirect, bind the `state` value that is currently an unnamed temporary (D-12), validate the
callback through the pure tier BEFORE the browser response is committed, and make redemption
unreachable without a passing validation (D-01/D-02/D-03/D-04).

Purpose: at `src/client/oauth.rs:712` the CSRF `state` is generated inline as a temporary —
`.append_pair("state", &Self::generate_code_verifier())` — never bound to a variable, so it is not
merely unchecked but STRUCTURALLY IMPOSSIBLE to check. The callback at :697-700 extracts `code` and
nothing else.

**One design change from the previous revision, driven by cross-AI review (Codex HIGH #3).** The
earlier plan had the listener task serve the browser HTML and THEN hand the raw query to the parent
for validation. That ordering is self-contradictory: a callback later rejected for `state` or `iss`
would already have rendered the success page, and the plan's own requirement that a FAILURE page be
served becomes unselectable — the task has no idea whether validation will pass. Validation must
happen before the HTTP response is committed. The listener calls the same pure validator and sends a
`Result` to the parent; the parent still cannot redeem on the `Err` branch.

**Complexity budget is a live risk here.** `authorization_code_flow_inner` is already ~150 lines
(`:621-772`) and the PR-blocking `pmat quality-gate --checks complexity` caps cognitive complexity at
25. Extract into helpers and into the pure tier; do not inline.
Output: a validated callback that cannot redeem a code it did not verify, and cannot lie to the user
about which happened.
</objective>

Introduce the per-request record, bind `state`, land the override, and open the browser seam.

**Record construction.** Before building the authorization URL, construct an
`AuthorizationRequestRecord` from four values: the expected issuer, the PKCE code verifier, the state,
and the resolved `IssPresence`. The spec requires these to live in ONE per-request record rather than
as separate locals — three locals is exactly how `state` became unbindable in the first place.

Expected issuer is `metadata.issuer` per D-02: the anchor is the value the AS itself published in its
discovery document, not `config.issuer` (a user-typed seed) and not the effective issuer computed at
`:505`. The attack being defended against is "this response came from a different AS than the one
whose metadata I fetched," so the DISCOVERED issuer is the semantically correct anchor. As of 116-06
that value is validated at fetch time against the issuer used to build the URL, which is what makes it
a trustworthy anchor at all.

**State.** Replace `.append_pair("state", &Self::generate_code_verifier())` with the record's state,
generated by `pmcp::shared::pkce::generate_state()`. Reusing the PKCE VERIFIER generator for a CSRF
token conflates two distinct RFC roles; `generate_state()` already exists for this and is already
ALWAYS-covered.

**D-04 override.** Add `OAuthHelper::with_iss_validation(self, presence: IssPresence) -> Self` as an
inherent consuming builder, backed by a new PRIVATE field on `OAuthHelper`. It must NOT be a field on
`OAuthConfig`: that struct is public, all-pub-field and not `#[non_exhaustive]`, so a new field is
`constructible_struct_adds_field` = MAJOR and would break three in-repo literal sites plus every
downstream user's.

Read `PMCP_OAUTH_ISS_VALIDATION` at the CALL SITE inside the flow, never in a constructor — the
I/O-free-construction discipline that D-07 imposes on the store applies here too, so a platform can
supply the policy as a parameter instead of through a process environment. Parse it with
`parse_iss_env_value`; when the variable is SET but parses to `None`, `tracing::warn!` naming
`PMCP_OAUTH_ISS_VALIDATION`, the value observed and the two accepted values, then fall through. That
warn is the point of 116-02's two-function split: an operator who typed
`PMCP_OAUTH_ISS_VALIDATION=true` believing they enabled strictness must not get silence. Then hand
the parsed `Option<IssPresence>` to `iss_presence_from(env_override, builder, discovery_flag)`;
precedence is env > builder > discovery flag. Do not re-implement the precedence logic here.

**Discovery flag.** Route the flow's metadata fetch through

`authorization_response_iss_parameter_supported` value reaches `iss_presence_from`. Keep the existing

Make the loopback callback a CALLER of the pure tier, and make BOTH redemption and the served page
consequences of one validation result.

**Validate before the response is committed — this is the change cross-AI review forced.** The
previous shape had the task serve HTML and then hand the raw query to the parent. That cannot work:
the task does not know the outcome at the moment it must choose which page to write, so either the
success page is served for a callback that is about to be rejected, or the failure page is
unreachable. Both were true of the earlier plan simultaneously.

New shape:
1. The listener helper reads the HTTP request line under a hard cap of
   `MAX_CALLBACK_REQUEST_LINE_BYTES` (16 KiB) — read with a bounded reader, not `read_line` into an
   unbounded `String`. Anything on the local machine can connect to this port and send an unbounded
   line; refusing at 16 KiB costs nothing legitimate, because the authorization response is a query
   string, not a payload.
2. It isolates the query component (the existing
   `Url::parse(&format!("http://localhost{}", path))` step is a fine way to do that).
3. It calls `validate_authorization_response(&raw_query, &record)` — the SAME pure function, one
   implementation, now invoked at the point where the answer is needed. `query_pairs()` inside that
   function is the right decoder; RFC 9207 §2.4 REQUIRES the `application/x-www-form-urlencoded`
   decode before comparison and it performs it. Do not hand-roll a percent-decode anywhere.
4. On `Ok(code)` it writes the existing SUCCESS HTML; on `Err(e)` it writes the existing FAILURE
   HTML. Neither page gains any AS-supplied text — the spec forbids acting on or displaying an
   AS-supplied `error_description` after an `iss` mismatch, so the failure page must stay the fixed
   bytes it is today.
5. It sends `Result<String>` (the code, or the typed error) to the parent over the `oneshot`.
6. The parent propagates `Err` and returns; only the `Ok` branch may reach the token exchange. This
   is the single most important behavior in AUTH-01 and the `expect(0)` mock on `/token` is what
   proves it.

The record must therefore be available inside the task. Move it in by `Arc` or by clone before the
spawn; `AuthorizationRequestRecord` is a small owned struct, so a clone is fine — say which you chose
in the summary. Validation still exists in exactly ONE place (the pure tier); what changed is WHERE it
is called from, and calling it inside the listener is the only ordering that makes both the served
page and the redemption decision consequences of the same result.

**Failure HTML is unchanged.** D-03 says so explicitly. Serve the same bytes as today.

**Complexity.** `authorization_code_flow_inner` is already ~150 lines and cog-25 is PR-blocking.
Extract the whole listen-read-validate-respond block into its own private async helper returning
`Result<String>`, so the flow function shrinks rather than grows. If
`pmat quality-gate --checks complexity` still reports a violation after that, extract further — do
NOT reach for `#[allow(clippy::cognitive_complexity)]`, which is reserved for irreducible parsers and
protocol dispatch and requires a `// Why:` annotation per CLAUDE.md.

Write `tests/oauth_iss_integration.rs` on the mockito harness from `tests/oauth_dcr_integration.rs`,
with `discovery_body` parameterized so the document can set or omit
`authorization_response_iss_parameter_supported`. Drive the flow through the Task 1
`BrowserLauncher` seam: the test's launcher captures the authorization URL, extracts the `state`, and
then performs an HTTP GET against the loopback callback with whatever parameters the case requires.
That is what makes these end-to-end tests deterministic instead of impossible.

Assert THREE things per rejection case, because the timing fix is what is being tested:

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → loopback callback listener | Anything on the local machine can hit the loopback port with a forged callback and an arbitrarily long request line |
