<objective>
Land SEP-2352's credential storage as a wasm-clean pure tier — the key, the record, the on-disk
format, the schema 1→2 migration, the platform trait and its administrative sibling — plus the
in-memory impl, and fence the wasm-cleanliness of the whole pure tier in CI (D-06).

Purpose: `~/.pmcp/*.json` is not a viable credential store for ANY hosting target — `~` is unwritable
on Lambda and per-container on Workers and Cloud Run. The trait is what makes the SDK serve the
durable-agent case (N servers, M providers, one user) and the single-user CLI with one seam.

**Two things changed from the previous revision, both owner decisions taken after cross-AI review:**

- **D-116-R1 — the key is `(issuer, account, server)`, not `(issuer, account)`.** CONTEXT's D-07
  wording is SUPERSEDED. Two MCP servers that share one authorization server and one account
  otherwise collide: they may hold different DCR registrations, different client IDs and different
  granted scopes, migration can overwrite one with the other, and `logout` on one deletes the
  other's credentials. Deferring RFC 8707 (`b2bf9157`) removed the audience binding that would have
  mitigated this. AUTH-03's requirement text was amended to `(issuer, account, server)` in commit
  `0aebf7f6` and is authoritative.
- **D-116-R2 — the trait grows administrative operations.** Five methods could not support 116-13's
  `auth status`, `auth logout --all`, accurate deletion counts or migration reporting, so those
  commands could not be thin wrappers over the declared seam. They land on a separate
  `CredentialStoreAdmin` trait so the narrow platform seam stays narrow.

Output: the pure storage tier, the two traits, the in-memory impl, and a wasm32 build fence.
The gated file implementation is 116-16.
</objective>

**The key is three-part.** `CredentialKey::new(issuer, account, server)`. This is D-116-R1 and it is
in AUTH-03's amended requirement text, not a planner preference — do not "simplify" it back. State
the reason in the rustdoc, because the two-component version reads perfectly reasonable in isolation:
two MCP servers can share one authorization server and one user account while holding DIFFERENT DCR
registrations, different client IDs and different granted scopes. Under a two-part key they collide —
`logout` on one deletes the other's credentials, and migration can overwrite one with the other. RFC
8707's `resource` parameter would have bound the audience and mitigated this; it is DEFERRED by owner
decision (`b2bf9157`), so the key carries the binding instead. The `server` component is the value
`normalize_server_key` produces, so trailing-slash and host-case variants of one MCP server URL do not
become two keys.

`CredentialKey` and `StoredCredentials` use PRIVATE fields with constructors and accessors. This is
the semver choice: RESEARCH A1 shows `OAuthConfig`, `DcrRequest` and `OidcDiscoveryMetadata` are
all-pub-field non-`#[non_exhaustive]` structs where a future field would be a MAJOR break. Private
fields make these extensible at minor forever. Say so in the rustdoc so nobody "simplifies" them
to pub fields later — and note that this is what lets `registered_application_type` (116-10's echo
observability) and `granted_scopes` (116-12's refresh scope) be added without a semver event.

`StoredCredentials`' serde names must match cargo-pmcp's existing `TokenCacheEntry` exactly where
they overlap (snake_case, `#[serde(default, skip_serializing_if = "Option::is_none")]` on the
optionals, `skip_serializing_if = "Vec::is_empty"` on `scopes`). D-19 keeps `oauth-cache.json` as the
surviving file and the migration source, so a field-name divergence here would silently drop data in
116-13. Implement `Debug` MANUALLY so tokens never reach a log through a derived `{:?}`; print a
sha256 prefix or a fixed redaction marker instead of the value. This is the platform's proven
never-log-raw convention, adopted as a design input.

**The FORMAT and the MIGRATION live here, in the pure tier — not in the file impl.** `CredentialSnapshot`
is the in-memory document; `parse_credential_snapshot(bytes)` and `CredentialSnapshot::to_bytes()` are
the only places the on-disk shape is known. Three reasons, all load-bearing: (1) a platform storing
the same JSON blob in DynamoDB or KV gets identical migration behavior to the CLI with no filesystem —
which is the whole point of D-06/D-07; (2) the migration becomes fuzzable over arbitrary bytes with no
I/O (116-08); (3) 116-16's `FileCredentialStore` reduces to lock + read + parse + mutate + serialize +
atomic write, which is a reviewable amount of I/O.

On-disk v2 shape: a top-level object with `schema_version: 2`, a `credentials` map nested
issuer → server → account → `StoredCredentials`, and an `issuers` map of normalized-server-key →
last-seen issuer string (D-18's tracking). Nesting rather than concatenating a composite string key
avoids inventing a separator that an issuer URL could contain. Use `BTreeMap` at every level so
`to_bytes()` is byte-stable across writes — assert that with a test, because byte-stability is what
makes a `git diff` of a credential file meaningful and what stops an atomic write churning on every
save.

Migration: dispatch on `schema_version`. Version 2 deserializes directly. Version 1 deserializes into
a private `V1Cache` mirror of cargo-pmcp's `TokenCacheV1` (`schema_version` + `entries: BTreeMap<String,
V1Entry>` where `V1Entry` has `access_token`, optional `refresh_token`, optional `expires_at`,
`scopes`, optional `issuer`, `client_id`) and is re-keyed in memory: each entry with an issuer becomes
`CredentialKey::new(issuer, "", <the v1 map key>)` — the v1 map key IS the normalized server URL, so
the widened key is populated LOSSLESSLY from data v1 already recorded — and contributes
`issuers[<v1 map key>] = <issuer>`. Anything else is an error naming the observed and supported
versions.

An entry with NO `issuer` cannot be re-keyed without GUESSING which AS issued it — precisely what
SEP-2352 forbids and precisely why D-17 discards the core cache. Drop such entries and record a
`DroppedEntry` naming the server key and the reason, so 116-13's CLI can report it. Record this
refinement of D-17's "every existing login is preserved" in the plan summary: every login that
RECORDS ITS ISSUER is preserved losslessly; one that does not cannot be, and the phase chooses a named
report over a guess. `parse_credential_snapshot` does NOT log — it RETURNS the report, so the caller
decides between `tracing::warn!` and CLI output.

`parse_credential_snapshot` must not panic for any input. No `unwrap`, no indexing, no `expect`. It is
fuzzed in 116-08.

`normalize_server_key` is a straight port of cargo-pmcp's `normalize_cache_key` semantics into core —
port it, do not re-derive it, and carry its property test across.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authorization server A credentials → authorization server B | The cross-AS replay SEP-2352 exists to prevent |
| MCP server X credentials → MCP server Y sharing one authorization server | The collision D-116-R1 closes; RFC 8707's audience binding is deferred, so the key carries it |
| stored credential bytes → in-memory snapshot | Peer- or disk-supplied bytes reach a parser that must never panic |
| platform implementor → CredentialStore trait | A trait that assumes a filesystem or an identity model pushes the SDK's choices into someone else's runtime |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-116-13 | Elevation of Privilege | cross-authorization-server credential reuse | mitigate | The store key INCLUDES the issuer, so a different AS is a cache miss by construction; asserted by the cross-issuer `load` test which returns `None` with no enforcement branch involved |
| T-116-13a | Elevation of Privilege | cross-MCP-server credential reuse when two servers share one authorization server and account | mitigate | D-116-R1: the key's third component is the normalized server key, so two servers are two entries; asserted on the live path AND on the migration path, since migration is where an overwrite could have happened silently |
| T-116-13b | Denial of Service | `logout` on one MCP server deleting a different server's credentials | mitigate | `delete_by_server` operates on the key's `server` component and returns an exact count; tested with a three-credential fixture spanning two servers |
| T-116-15 | Information Disclosure | tokens leaked through a derived `Debug` | mitigate | `StoredCredentials` implements `Debug` manually with redaction; asserted by a test on `format!("{:?}", ..)` |
| T-116-16 | Tampering | schema-1 entry with no issuer re-keyed by guessing | mitigate | Unkeyable entries are DROPPED and reported as a `DroppedEntry` naming the server key, never assigned to an issuer |
| T-116-16a | Denial of Service | panic in the credential-file parser on hostile or corrupt bytes | mitigate | `parse_credential_snapshot` is total and unwrap-free (grep-asserted), returns errors that echo no input bytes, and is fuzzed over arbitrary bytes in 116-08 |
| T-116-16b | Repudiation | a migration silently dropping a login with no report | mitigate | `MigrationReport` carries a migrated count and a per-entry dropped list; `take_migration_report` on the admin trait is how 116-13 surfaces it to the operator |
