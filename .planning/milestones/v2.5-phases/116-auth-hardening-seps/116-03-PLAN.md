<objective>
Give `DcrRequest` and `DcrResponse` typed access to OIDC Dynamic Registration's `application_type`
(SEP-837 / AUTH-02) through the existing `#[serde(flatten)] extra` map, per D-09 — inherent methods,

constrained to an additive 2.x minor. Phase 115's escape hatch (mark it `#[non_exhaustive]` first) is
unavailable — that is itself a major break.
Output: three inherent accessors, a documented precedence rule, and a collision test.
</objective>

  <behavior>
    - A default `DcrRequest` returns `None` from `application_type()`
    - After `set_application_type("native")`, `application_type()` returns `Some("native")`
    - `serde_json::to_value(&request)` contains a TOP-LEVEL `"application_type": "native"` key — not nested under `extra` — proving the flatten carrier produces field-identical wire bytes
    - Round-trip: serialize then deserialize a `DcrRequest` carrying `application_type`, and `application_type()` still returns the same value
    - Collision (D-09's documented precedence): a caller who inserts `extra.insert("application_type", json!("web"))` by hand and THEN calls `set_application_type("native")` ends with `Some("native")` — last write wins, one key, no duplicate emitted on the wire
    - Collision, other order: `set_application_type("native")` then a raw `extra.insert("application_type", json!("web"))` ends with `Some("web")` — same rule, stated symmetrically
    - A non-string value in the map (e.g. `json!(42)`) makes `application_type()` return `None` rather than panicking or stringifying
    - `DcrResponse::application_type()` reads the AS's echoed value from its own `extra`, returning `None` when absent
  </behavior>
  <action>
Add a `pub const DCR_APPLICATION_TYPE_KEY: &str = "application_type";` at module scope and three
inherent methods that route through it. Do NOT add a field to `DcrRequest` or `DcrResponse`, and do
NOT mark either struct `#[non_exhaustive]`.

`DcrRequest::application_type(&self) -> Option<&str>` reads `self.extra`, projecting only a JSON
string value (`Value::as_str`); a non-string value yields `None`.

`DcrRequest::set_application_type(&mut self, value: impl Into<String>)` inserts a
`serde_json::Value::String` under the same key. Use a `&mut self` setter rather than a consuming
`with_` builder because the DCR construction site at `src/client/oauth.rs:241-257` builds the struct
by literal and then needs to mutate it; a consuming builder would force a rebind there for no gain.

`DcrResponse::application_type(&self) -> Option<&str>` — read-only; the AS's echoed value. RFC 7591
explicitly permits the AS to modify requested metadata, so there is deliberately no setter on the
response type.

The rustdoc on all three must state the precedence rule D-09 requires, in the shape
`src/types/protocol/mod.rs:386-398` uses for `with_meta` (which names both the round-trip property
and the collision hazard). The rule to write down: the accessors and a hand-written raw
`"application_type"` key address the SAME single map entry, so there is no "typed vs raw" duality and
no possibility of two `application_type` keys on the wire — LAST WRITE WINS, whichever route it came
through. State that a caller mixing both routes should prefer the accessor, and that
`DCR_APPLICATION_TYPE_KEY` is exported precisely so a caller who insists on raw access cannot
misspell the key.

Also record in the rustdoc, citing SEP-837, the two permitted values `"native"` and `"web"` and the
consequence of omission ("defaults to `web` under OIDC, which can conflict with native-style redirect
URIs; non-OIDC servers safely ignore the parameter"). Do NOT validate the value in the setter — the
spec permits an AS to define others, and D-09's setter is also the override path for D-10's
derivation.

Put the tests in the file's existing `#[cfg(test)] mod tests`, following the house habit of a
one-line doc per test naming the invariant it pins.

Note for 116-08: `DcrResponse` and `DcrRequest` are public and their `extra` carrier is public, so
`serde_json::from_slice::<DcrResponse>(arbitrary_bytes)` followed by `.application_type()` is
reachable from a fuzz target with no new surface. 116-08 fuzzes exactly that pair to satisfy
CLAUDE.md's ALWAYS-fuzz requirement for AUTH-02; nothing extra is needed here.
