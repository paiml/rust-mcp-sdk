Compose the DCR body at `src/client/oauth.rs:241-257`.

**application_type (D-09/D-10/D-11).** After building the `DcrRequest`, call
`derive_application_type(&request.redirect_uris)?` and write the result through
`request.set_application_type(app_type.as_str())`. Derive from the redirect URIs actually being
registered rather than from `config.redirect_port`, so the value stays correct if the port or the URI
shape changes. pmcp's own call registers `http://127.0.0.1:{port}/callback` and therefore derives
`native`; a platform `oauth-proxy` registering an https redirect derives `web`.

Send it UNCONDITIONALLY, on both eras. `application_type` has been a standard OIDC Dynamic
Registration field since 2014, the spec states plainly that "non-OIDC servers safely ignore the
parameter", and era-gating would require plumbing a protocol era into DCR that — exactly like the
callback in 116-09 — does not exist before an MCP connection is established.

A mixed `redirect_uris` vector propagates `derive_application_type`'s error rather than picking one.
D-10 is explicit that this is an ERROR, never a silent choice.

**grant_types (SEP-2207).** Change `grant_types` from `vec!["authorization_code"]` to
`vec!["authorization_code", "refresh_token"]`. The spec's landed text says clients that desire refresh
tokens SHOULD include `refresh_token` in their `grant_types` client metadata. This is the missing
prerequisite for D-14's refresh work in 116-12 and for D-08's headless mode: an AS that was never told
the client wants refresh grants has every reason not to issue one.

**offline_access (SEP-2207) — at BOTH the stages it belongs at, and neither more.** Cross-AI review
found the previous revision handled this at the wrong protocol stage: writing `offline_access` into
DCR CLIENT METADATA declares what the client is permitted to ask for; it does not ASK for it. The
request happens at the authorization request. Get the lifecycle right in three places, two of them
here:

1. **DCR client metadata (this task).** Pass the discovery metadata into
   `do_dynamic_client_registration` (a private method, so the signature change is free) and, when
   `metadata.scopes_supported` contains `offline_access`, include it in the registration request's
   `scope`. The spec says MAY, conditioned on the AS advertising it — so the check is the whole point
   and adding it unconditionally would be wrong.
2. **The authorization request (this task).** When `metadata.scopes_supported` contains
   `offline_access`, add it to the `scope` parameter of the authorization URL 116-09 builds. This is
   the stage that actually requests it. Compose the value: `config.scopes` plus `offline_access`,
   deduplicated, order-stable. Do NOT mutate `config.scopes` — it is a public field on a public
   struct and a caller who reuses one `OAuthConfig` across two flows must not watch it grow.
3. **Refresh (116-12, NOT here).** Refresh sends only what was GRANTED, or no `scope` at all. Adding
   a scope at refresh that was never granted can violate an AS's refresh-scope rules
   (RFC 6749 §6 permits narrowing, never widening). 116-12 owns that; this plan must not pre-empt it.

**Record what was GRANTED, not what was asked.** When the token response carries `scope`, that is the
granted scope and it is what `StoredCredentials::with_granted_scopes` records. When the response omits
`scope`, RFC 6749 §5.1 says the granted scope equals the requested scope — record the requested value
in that case, and say which rule applied in a comment, because the two branches look interchangeable
and are not. This is the value 116-12 refreshes with, so getting it wrong here silently re-widens or
narrows every subsequent refresh.

Extend `tests/oauth_dcr_integration.rs` rather than starting a new file: it already has the harness,
and its `Matcher::PartialJsonString` idiom is exactly the mechanism needed — the mock matches only
when the body contains the asserted fields, so a regression that drops `application_type` yields a 501
and a red test. Assert the WIRE BODY, never the in-memory struct: the whole point of D-09's `extra`
carrier is that it produces field-identical bytes, and only a wire assertion proves that.

Handle the response half of DCR.

**Echo divergence (D-11), made observable WITHOUT a new public field.** After a successful
registration, read `response.application_type()` and compare it to what was sent. On divergence,
`tracing::warn!` naming BOTH values and the registration endpoint. NEVER fail the registration:
RFC 7591 explicitly permits the AS to modify requested metadata, and failing here would turn a legal
server behavior into an outage. Treat an OMITTED value as "no echo", not as divergence — the AS is not
required to echo.

Cross-AI review flagged the previous wording ("record the AS's value where the flow can see it") as
having no implementation path, and warned that the obvious route — adding a field to
`AuthorizationResult` — is exactly the `constructible_struct_adds_field` MAJOR break the whole phase
is built to avoid. Two mechanisms instead, neither of which touches a public constructible type:

1. **A private pure helper.** `fn application_type_divergence(sent: &str, echoed: Option<&str>) ->
   Option<(String, String)>` returns `None` for an equal echo AND for an absent echo, and
   `Some((sent, echoed))` otherwise. The `tracing::warn!` is driven by its `Some` branch. Unit-test it
   inline in this file's `#[cfg(test)] mod tests` over all four cases — that is where the divergence
   RULE is pinned, deterministically, with no log capture and no new surface. (`tracing-subscriber` is
   an OPTIONAL dependency behind the `logging` feature in this repo, not a dev-dependency, so log
   assertions are not available by default; do not build the test on one.)
2. **Persistence through the store.** `StoredCredentials::with_registered_application_type` /
   `registered_application_type()` (116-05) exist precisely for this: `StoredCredentials` has PRIVATE
   fields, so carrying the AS-registered value costs no semver event. Thread the value out of this
   function so 116-11's store wiring persists it with the credentials it belongs to. A later
   diagnosis then reads the store rather than hunting a log line, which is what "where the flow can
   see it" was reaching for.

State in the summary that a field on `AuthorizationResult` was considered and REJECTED as a MAJOR
semver break, so the choice is visible rather than looking accidental.

**Registration rejection (SEP-837 ¶3).** The spec obliges clients to surface a MEANINGFUL error when
registration is rejected, because the most common cause is a redirect-URI constraint tied to the
`application_type`. Today the error path returns a bare status. Compose an error naming: the HTTP
status; the AS's `error` and `error_description` if the body parses as an RFC 7591 error response; the
`application_type` that was sent; and the `redirect_uris` that were sent. Those last two are what turn
"registration failed with 400" into an actionable message, because they are exactly the pair the AS
rejected.

Do NOT implement the spec's optional retry with an adjusted `application_type`. The text says clients
MAY retry; an automatic retry would silently register a client under a different type than the
operator asked for, which is the opposite of surfacing a meaningful error. Record the non-adoption of
the MAY in the plan summary so the choice is visible rather than assumed.

Keep the error message free of raw body content beyond the parsed `error`/`error_description` fields —
the same rule the bounded-read refusals follow, so a hostile registration endpoint cannot use the
error path as an echo channel.

Extend `tests/oauth_dcr_integration.rs` with the six behavior rows. For the divergence-warns case,
assert the registration SUCCEEDED — that is the load-bearing behavior ("never fatal") and it is
observable end to end. The divergence RULE itself is pinned by the inline unit tests of
`application_type_divergence` over its four cases, not by log capture. 116-11 adds the persistence
assertion once the store is wired; do not block this plan on it.
