<objective>
Replace the flat, issuer-less token cache with the `(issuer, account, server)`-keyed `CredentialStore`
(SEP-2352 / D-07/D-16/D-17/D-19, with the key widened by owner decision D-116-R1), and make an
authorization-server substitution visible instead of invisible (D-18, refined by RESEARCH A4).

Purpose: today `~/.pmcp/oauth-tokens.json` holds a single flat token with NO issuer field
(`src/client/oauth.rs:151-156`). It cannot be re-keyed without GUESSING which AS issued it — precisely
what SEP-2352 forbids — so D-17 discards it. Once storage is issuer-keyed, SEP-2352's two mandates
fall out of the key shape rather than out of enforcement code: a different AS is a cache miss, and
since the DCR-issued `client_id` lives in the same record (a client_id issued by AS-A is meaningless
at AS-B), re-registration is automatic. The key's THIRD component — the normalized MCP server key —
closes the case SEP-2352 does not name: two MCP servers that share one authorization server and one
account, holding different DCR registrations and different granted scopes, which a two-part key would
collapse into one entry. RFC 8707's `resource` parameter would have bound the audience instead; it is
deferred by owner decision, so the key carries the binding. But issuer-keying also makes an AS
substitution SAFE and INVISIBLE — the user is simply walked through a fresh login at an IdP they did
not expect. D-18 makes it loud.
Output: the CLI flow on the store, with the substitution announced.
</objective>

  <action>
Wire `OAuthHelper` to the credential store.

**The store field.** Add a private, lazily-resolved store to `OAuthHelper`, plus
`with_credential_store(self, Arc<dyn CredentialStore>)` and
`with_account_scope(self, impl Into<String>)` as inherent consuming builders. Both must be builder
methods, not `OAuthConfig` fields: `OAuthConfig` is public, all-pub-field and not
`#[non_exhaustive]`, so a new field is `constructible_struct_adds_field` = MAJOR and would break the
three in-repo literal sites plus every downstream user's.

`OAuthHelper::new` must NOT call `default_credential_path()` — resolve the default
`FileCredentialStore` on FIRST USE, honoring `config.cache_file` when set and
`default_credential_path()` otherwise. D-07's I/O-free construction is a platform-proven constraint,
and a constructor that reads `dirs` makes the type unusable in a Lambda that will inject its own store
a line later.

**Replace the cache functions.** Retire `load_cached_token` / `cache_token` / the `TokenCache` struct
in favor of `store.load(&key)` and `store.save_with_issuer(&key, &creds, &server_key, &issuer)` where
`key = CredentialKey::new(effective_issuer, account_scope, server_key)` and
`server_key = normalize_server_key(config.mcp_server_url)?`.

The THIRD key component is D-116-R1 and it is in AUTH-03's amended requirement text (commit
`0aebf7f6`). Do not drop it back to two: two MCP servers behind one authorization server, logged in
under one account, hold different DCR registrations, different client IDs and different granted
scopes. Under a two-part key they share one entry — so `logout` on one deletes the other's
credentials, and whichever authenticated last silently overwrites the other. Compute the server
component with `normalize_server_key` so trailing-slash and host-case variants of one server URL do
not become two logins.

Use `save_with_issuer` rather than `save` followed by `record_issuer`: two separate writes leave a
window in which the store names one issuer while holding another's credentials, and 116-16's file
store implements the combined method as one atomic read-modify-write precisely so this call site can
be correct for free.

The effective issuer is the same value AUTH-01 uses as its anchor: the issuer from the AS's discovery
document. Persist the effective `client_id` in the record — this is not optional and not a
convenience: it is what makes SEP-2352's "MUST re-register with the new authorization server"
automatic, and it is what 116-12 needs to fix D-14's second defect (DCR flows currently cannot refresh
at all because `client_id` is read from `config` where a DCR-issued id never lives). Persist the
GRANTED scopes and the AS-registered `application_type` that 116-10 produced, through
`StoredCredentials::with_granted_scopes` and `with_registered_application_type`; both are private
fields on `StoredCredentials`, so neither costs a semver event, and the granted scope is what 116-12
refreshes with.

**Discard the legacy cache (D-17, core half).** `~/.pmcp/oauth-tokens.json` must never be read as
credentials. Emit one `tracing::warn!` per helper instance if the path exists, naming the path, the
reason (no issuer recorded ⇒ cannot be re-keyed without guessing, which SEP-2352 forbids) and the
consequence (one forced re-login). Do not delete or rename the file — leave it for the user. Do not
attempt any migration of it; the cargo-pmcp file, which DOES record an issuer per entry, is the one
that gets a real migration, and that lands in core's `FileCredentialStore` (116-05) and in 116-13.

Write `tests/oauth_store_wiring.rs` against `InMemoryCredentialStore` for the key-shape behaviors and
against a `tempfile::tempdir()`-backed `FileCredentialStore` for the persistence behaviors. The
legacy-discard test must assert the file is NOT read — plant a syntactically valid legacy file with a
distinctive token and assert that token never appears in any result.

The D-116-R1 collision test is the load-bearing one and needs a doc comment saying so: build two
helpers for two different MCP server URLs against one mock authorization server with one account,
complete both flows, and assert (a) two distinct keys exist, (b) each `load` returns its own

the key count — a two-part key would produce one key holding the last writer's credentials, and a
count assertion alone would read as "1 != 2" without showing what was lost.

  <action>
Detect and announce an authorization-server substitution.

Once the effective issuer is known for a connection, call
`store.last_issuer(&normalize_server_key(server_url)?)`. On a change, branch on CREDENTIAL PROVENANCE —
this is RESEARCH A4's refinement of D-18, and it is what makes the AUTH-03 booking defensible against
the spec text, whose two adjacent sentences prescribe different remedies:

- **DCR-issued** (`config.client_id.is_none()`): warn and proceed. The spec's requirement for DCR
  credentials is "MUST NOT reuse client credentials from a different authorization server and MUST
  re-register with the new authorization server" — which issuer-keyed storage already accomplishes by
  missing the cache. The warning is what makes the automatic re-registration visible. Hard-failing here
  would convert a legitimate operational event (a tenant move, a provider migration) into an outage,
  which D-18 explicitly rejects.
- **Pre-registered** (`config.client_id.is_some()`): return `Error::reauth_required(new_issuer, ..)`.
  The spec says pre-registered credentials are inherently specific to one AS and that clients SHOULD
  surface an error rather than silently attempting to use mismatched ones. Silently re-running a
  browser login against an unexpected IdP with a client_id provisioned for a different one is the exact
  case the spec is warning about.

Both paths must name BOTH issuers and the server URL. Then record the new issuer so the next
connection compares against it.

Write down, in the rustdoc of whatever function performs this check, the DEPENDENCY the owner deferred:
the spec specifies AS-change detection as "detected via updated protected resource metadata" (RFC
9728), which pmcp does not implement — it derives the AS from the MCP base URL directly
(`src/client/oauth.rs:366-390`). RFC 9728 Protected Resource Metadata discovery is DEFERRED by owner
decision (2026-08-02), so this detection uses the provenance signal available today: the issuer that
discovery actually resolved for this server URL. State that plainly rather than implying spec parity.
The deferral and its named dependency are recorded again in 116-15's deferred-items file.

`record_issuer` / `last_issuer` have default impls returning `Ok(())` / `Ok(None)`, so a platform store
that does not implement them degrades to today's behavior rather than breaking. Cover that with a test
using a minimal hand-written implementor that overrides only `load`/`save`/`delete`.

The detection is PER SERVER: `last_issuer` is keyed by `normalize_server_key(server_url)`, so an
issuer change observed for one MCP server neither warns nor errors for another, even one that shares
the old issuer. Add the isolation test — it is the D-116-R1 property expressed on the issuer-tracking
side, and without it a multi-server agent would produce spurious reauth-required errors.

| Boundary | Description |
|----------|-------------|

| MCP server URL → discovered issuer | A server that changes the AS it points at can walk a user through a login at an unexpected IdP |
| legacy on-disk token file → live credentials | An issuer-less token cannot be attributed to an AS without guessing |
