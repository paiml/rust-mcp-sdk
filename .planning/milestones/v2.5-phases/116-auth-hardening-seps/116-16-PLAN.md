<objective>
Ship the default on-disk credential store: thin, gated I/O over the pure format 116-05 defined, with
cargo-pmcp's proven permission and atomicity behavior plus the concurrency discipline cross-AI review
found missing.

Purpose: 116-05 deliberately put the format, the migration and the report in the ungated pure tier so
a platform storing the same bytes in DynamoDB gets identical behavior. What remains here is I/O — and
I/O is where the review found the real gap: an atomic rename prevents a TORN file, not a LOST UPDATE.
Two processes (or two tasks) that read the same snapshot and each write their own back silently
discard one another's credentials, and because `save` and `record_issuer` were separate operations,
a store could end up naming one issuer while holding another's tokens. This plan makes a
read-modify-write the unit of work and serializes it.

This plan exists as a separate plan, rather than as three more tasks on 116-05, because D-116-R1 and
D-116-R2 grew 116-05 past its context budget. The wave structure is unchanged.
Output: `src/shared/credential_file.rs` plus its suite.
</objective>

    Construction and basic I/O:
    - `FileCredentialStore::new(path)` performs NO filesystem and NO environment access — constructing it against a path inside a non-existent directory succeeds; only a write creates directories
    - `save` then `load` round-trips through a real file in a `tempfile::tempdir()`
    - `load` on a non-existent file returns `Ok(None)`, not an error
    - `load` on a file whose JSON is corrupt returns an `Err` whose message names the PATH and tells the operator to delete it to reset — never a panic, never a silent empty store, and never a byte of the corrupt content
    - A file written by this store carries `schema_version: 2`
    Permissions and atomicity (ported, not re-derived):
    - On unix, after `save`: the file mode is `0o600` and its parent directory mode is `0o700`
    - `save` is atomic: written via a same-directory temporary and renamed, never truncated in place
    - A pre-existing file with looser permissions (0o644) is tightened to 0o600 by the next `save`
    Concurrency — the lost-update cases:
    - Two `save` calls for DIFFERENT keys, issued concurrently from the same process against one store, BOTH survive: a final `list_keys()` contains both. (Under a naive read-modify-write with no serialization one of them is lost.)
    - Two `FileCredentialStore` instances over the SAME path, saving different keys concurrently, both survive — this is the cross-process case, exercised with two instances rather than two processes
    - A save while the lock is held by another instance BLOCKS and then succeeds, rather than failing or overwriting
    - A lock file older than `CREDENTIAL_LOCK_STALE_SECS` is treated as stale and broken, so a crashed process cannot wedge the store permanently; the break emits a `tracing::warn!` naming the lock path
    - `load` does NOT take the lock (a read of a renamed-into-place file is already consistent) — assert that a `load` succeeds while a lock file exists
    Atomic combined update:
    - `save_with_issuer(key, creds, server_key, issuer)` is OVERRIDDEN here and performs ONE read-modify-write under ONE lock: after it, `load(key)` and `last_issuer(server_key)` are both observable, and the file was written exactly once (assert by watching the file's modification count or by a same-bytes check against a two-call baseline)
    Migration:
    - A schema-1 file in cargo-pmcp's `TokenCacheV1` shape containing two entries that each carry an `issuer` is read successfully; both entries are reachable via `load`; `take_migration_report()` reports 2 migrated, 0 dropped
    - `load` does NOT rewrite the file: after a migrating `load`, the on-disk `schema_version` is still 1; after the next `save`, it is 2
    - A schema-1 entry with NO `issuer` is dropped and appears in the report's dropped list
    - An UNKNOWN future `schema_version` returns `Err` naming the observed and supported versions
    Admin ops against a real file:
    - `list_keys`, `delete_by_server`, `clear_all` behave exactly as `InMemoryCredentialStore`'s tests assert, but through the file — including the exact counts

`src/shared/mod.rs`, and re-export `FileCredentialStore` and `default_credential_path` at crate root

**This module knows no JSON.** Every format decision lives in `parse_credential_snapshot` and
`CredentialSnapshot::to_bytes`. If you find yourself writing a `serde` derive or a field name here,
the split has been broken — put it in 116-05's module instead.

**Port `write_atomic`, do not rewrite it.** `cargo-pmcp/src/commands/auth_cmd/cache.rs:91-123` already
does tempfile-in-same-dir → `create_dir_all` → parent `0o700` → file `0o600` → `persist` (rename).
The only permitted changes are swapping `anyhow` for `pmcp::Error` and taking the bytes from
`CredentialSnapshot::to_bytes()`. Carry `write_sets_0600_perms_on_unix` across too.

**`FileCredentialStore::new(path: PathBuf)`** takes the path as a PARAMETER and does nothing else —
no `dirs` lookup, no `create_dir_all`, no read. D-07's I/O-free-construction rule is a
platform-proven constraint from `cognito_external_provider.rs`, not a style preference. The `dirs`
lookup lives in the free function `default_credential_path()`, which the CALLER invokes; state that
split in the rustdoc of both.

**Concurrency — the review's MEDIUM finding, and the reason this plan exists separately.** An atomic
rename guarantees a reader never sees a half-written file. It guarantees nothing about two writers.
Process A reads the snapshot, process B reads the same snapshot, A writes its version, B writes its
version — A's credential is gone, with no error anywhere. Make the unit of work a serialized
read-modify-write:

1. A private `with_snapshot_mut<F, T>(&self, f: F) -> Result<T>` that acquires the lock, reads and
   parses the current file (treating a missing file as an empty snapshot), calls `f(&mut snapshot)`,
   writes atomically if `f` mutated it, and releases the lock. EVERY mutating trait method —
   `save`, `delete`, `save_with_issuer`, `record_issuer`, `delete_by_server`, `clear_all` — goes
   through it. None of them re-reads independently.
2. In-process serialization: a `tokio::sync::Mutex` field on the store. Two tasks in one process using
   ONE `FileCredentialStore` cannot interleave.
3. Cross-process serialization: an advisory lock file at `<path><CREDENTIAL_LOCK_SUFFIX>` created with
   `std::fs::OpenOptions::new().create_new(true)`, which is atomic on every platform pmcp supports
   and needs NO new dependency (the phase's dependency delta must stay empty — do not reach for
   `fs2` or `file-lock`). On `AlreadyExists`, retry with a short bounded backoff. If the lock file's
   mtime is older than `CREDENTIAL_LOCK_STALE_SECS` (30), treat it as abandoned by a crashed process:
   `tracing::warn!` naming the lock path and the age, remove it, and retry. Release by removing the
   file in a guard type's `Drop` so a `?` on the way out cannot leak it.
4. Write the LIMIT of this scheme into the rustdoc honestly: an advisory lock is cooperative — a
   different program writing `oauth-cache.json` directly will still clobber it — and the 30-second
   staleness window means a process that stalls longer than that can have its lock broken under it.
   Both are acceptable for a per-user credential file on a developer machine; neither would be
   acceptable for a multi-writer server, which is exactly why the trait exists and why a platform
   implements its own store. Say that, rather than implying the file store is generally concurrent.

**Override `save_with_issuer`.** 116-05's default impl calls `save` then `record_issuer` — two
read-modify-writes, two lock acquisitions, and a window in which the store names one issuer while
holding another's credentials. Here it is ONE `with_snapshot_mut` closure doing both mutations, which
is the atomicity 116-05's rustdoc asks a transactional implementor to provide.

**Migration must not rewrite the file as a side effect of `load`** — parse in memory and let the next
mutating call persist v2. That keeps a read-only operation read-only and gives 116-13 a natural place
to report the migration. Store the `MigrationReport` from the most recent migrating parse in a field
so `take_migration_report()` can hand it over once.

Add a rustdoc note on `FileCredentialStore` recording the FORWARD-COMPAT TRAP: an already-installed
`cargo-pmcp` at 0.18.0 hard-errors on an unknown `schema_version` (`cache.rs:74-80`), so once this
store writes version 2 that older binary fails with "upgrade cargo-pmcp" rather than degrading. The
message it prints is already actionable; nothing in this repo can change an installed binary. 116-15
records it as a released-behavior note.

Write `tests/oauth_credential_file.rs` against `tempfile::tempdir()`. The two concurrency tests are
the load-bearing ones and each needs a doc comment saying what silently breaks without them. Drive the
same-process case with `tokio::join!` over two `save` futures on one store, and the cross-instance case
with two `FileCredentialStore` values over one path. Assert on the FINAL `list_keys()` containing both
keys — asserting "no error occurred" would pass under the lost-update bug.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| pmcp process → on-disk credential file | Bearer and refresh tokens at rest, readable by any process running as the user if permissions slip |
| concurrent writers → one credential file | Two readers of one snapshot each writing back destroy one another's work with no error |
| a crashed process → its lock file | An abandoned lock that is never broken wedges every future login |
| an already-installed older cargo-pmcp → a schema-2 file | A binary in the field meets a format it was written to reject |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-116-14 | Information Disclosure | credential file readable by other local users | mitigate | Ported `write_atomic`: file `0o600`, parent `0o700`, tempfile-in-same-dir then rename; asserted by a unix permission test plus a tightening test over a pre-existing 0o644 file |
| T-116-17 | Denial of Service | partial/torn credential file after a crash mid-write | mitigate | Atomic rename semantics from the ported `write_atomic`; `load` on corrupt JSON returns an actionable error naming the path and no content |
