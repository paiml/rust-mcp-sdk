Fix `refresh_token` and the credential write.

**Defect 1 — the stored refresh token is destroyed on every successful refresh.** `TokenResponse`'s
`refresh_token` is `#[serde(default)]`, so an omitted field deserializes to `None`, and the credential
write puts that `None` over a perfectly good token. Many OIDC servers omit the field meaning "keep the
one you have". Fix: when the response omits a refresh token, PRESERVE the stored one; replace it only
when the response actually supplies one. Write the rule down in a comment next to the assignment,
because the defect is invisible at the call site — `None` looks like data.

**Defect 2 — DCR flows can never refresh.** `client_id` is read from `self.config.client_id`, but
under DCR the client_id is ISSUED and lives in the authorization result, never in config. Source it
from the stored record via
`store.load(&CredentialKey::new(issuer, account, normalize_server_key(config.mcp_server_url)?))`
(116-11 persists it there precisely for this), falling back to `config.client_id`. The key is
THREE-part per D-116-R1 — a two-part lookup would read a different MCP server's client_id whenever
two servers share one authorization server and account, which is the exact collision this phase
exists to close. Only when BOTH are absent is it an
error, and that error must name both places it looked.

**Defect 3 — `scope` is never sent.** Add it, conditionally, exactly the way the sibling
`TokenExchangeClient::refresh_token` at `src/client/auth.rs:378-394` already does — build the form as a
`Vec` and push `("scope", ..)` when there is a scope to send.

**The value is `StoredCredentials::granted_scopes()` and nothing else.** Cross-AI review corrected the
previous revision here: it proposed adding advertised `offline_access` to the REFRESH request even if
the authorization server had never granted it. RFC 6749 §6 is explicit that a refresh request's scope
MUST NOT include any scope not originally granted, so that would be a spec violation and, at a
conforming AS, an `invalid_scope` error that breaks refresh entirely — the opposite of what D-14 is
for. The correct lifecycle, whose first two stages 116-10 owns:

1. `offline_access` is DECLARED in the DCR client metadata when advertised (116-10).
2. `offline_access` is REQUESTED in the authorization request when advertised (116-10).
3. What the AS actually granted is RECORDED from the token response's `scope`, or, when that field is
   absent, taken as the requested scope per RFC 6749 §5.1 (116-10, persisted by 116-11).
4. Refresh sends EXACTLY that recorded set, or omits `scope` entirely when it is empty. It never
   introduces a scope, never consults `scopes_supported`, and never falls back to `config.scopes` —
   `config.scopes` is what was ASKED for, and a server that narrowed the grant must not be silently
   re-widened at every refresh.

Write that four-stage list as a comment next to the form construction. It is the single easiest thing
in this phase to "fix" wrongly, because reaching for `config.scopes` looks obviously right at the call
site and is obviously wrong two protocol stages away.

**Bounded error-path read.** Replace `response.text().await.unwrap_or_default()` at :941 with
`collect_reqwest_body_within_cap`. This site is one of D-113-V's population and it is on an error path,
which is exactly where a hostile IdP has the most freedom.

Write `tests/oauth_refresh.rs` on the mockito harness. Defect 1's test is the important one and should
carry a doc comment saying so: it is the difference between an unattended agent that keeps working and
one that demands a human after its first hour.

Make headless operation an explicit opt-in mode, not environment sniffing.

Add `#[non_exhaustive] pub enum Interactivity { Interactive, RefreshOnly }` and
`OAuthHelper::with_interactivity(self, mode)` as an inherent consuming builder backed by a private
field. `Interactive` is the default, so today's fall-through survives untouched for every existing
caller — this is deliberate and is why D-08 specifies an opt-in rather than a behavior change.

Under `RefreshOnly`, refresh failure must return `Error::reauth_required(issuer, reason)` IMMEDIATELY.
The requirement is stronger than "skip the browser": the interactive branch must be UNREACHABLE BY
CONSTRUCTION, not merely guarded by an `if`. Structure `get_access_token` so the `RefreshOnly` path
returns before the interactive branch is in scope — for instance by splitting the token-acquisition
tail into two private functions, one of which contains the listener and the browser call and is only
ever called from the `Interactive` arm. A reviewer must be able to see that no control-flow edge leads
from `RefreshOnly` to `webbrowser::open`.

State in the mode's rustdoc what it is for and what it costs: today's silent fall-through binds a
loopback listener nothing can reach and waits five minutes per attempt in a Lambda; `RefreshOnly`
turns that into an immediate typed error the caller can convert into whatever its runtime calls a
consent-required condition. The reason it is a MODE and not environment sniffing is that sniffing
guesses, and a guess that is wrong in the interactive direction costs five minutes while a guess that
is wrong in the headless direction breaks a CLI login.

Prove the "no listener" property observably rather than by timing alone — a wall-clock assertion can
pass on a fast machine for the wrong reason. Use TWO observables: install a recording
`BrowserLauncher` (116-09's seam) and assert its invocation count is zero, AND confirm the configured
`redirect_port` is still bindable immediately after a `RefreshOnly` failure. The launcher count is the
direct assertion; the port check is the one that also catches a listener bound before the browser call.
