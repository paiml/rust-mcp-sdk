<objective>
Give the emitter a level to filter on, on both eras: v1's `logging/setLevel` stored PER SESSION
(D-11), v2's `io.modelcontextprotocol/logLevel` request `_meta` key read per request (D-10), and `info`
as the default when nothing set one (D-12).

Purpose: `LOG_LEVEL_REQUEST_META_KEY` (`src/server/streamable_http_server.rs:1429`) exists and is
referenced **only** by the `V2_RETIRED_METHODS` table (`:1485`). v2 today advertises a replacement
mechanism that does nothing — closing that is part of D-10.

**Why the level cannot live on the server.** `ServerState.server` is one
`Arc<tokio::sync::Mutex<Server>>` shared by every session (`streamable_http_server.rs:479`). Putting
the level there would let client B's `setLevel` change client A's filtering — the same defect class as
the deferred cross-session `client_capabilities` misattribution. The per-session home already exists and
is already v1-gated, which matches `setLevel`'s life exactly since v2 retired it. On a `full-v2` build
`V1State` is a zero-sized twin, so those builds allocate nothing for a mechanism they do not have —
structural, not a runtime branch someone can forget to take.

**RESEARCH Open Question 1, resolved here:** capture at the HTTP layer next to the retirement table and
write the RESOLVED level onto the request's `ProtocolContext`, so the dispatch arm (plan 08) only has to
answer `Ok(json!({}))` and the filter read is O(1) at emit time rather than a lock per record.

**The carrier correction (cross-AI review finding 3, HIGH as a plan defect).** The reviewed draft of
this plan declared a `with_log_level` write onto `RequestHandlerExtra.log_level` from
`src/server/streamable_http_server.rs`. That file **never constructs a `RequestHandlerExtra`** —
verified: zero matches for `RequestHandlerExtra::new` anywhere under `src/server/streamable_http_server*`;
the constructors live in `src/server/core.rs` and `src/server/mod.rs`. So the declared write was
impossible.

The corrected flow, in two owned halves:
- **Plan 06 owns the carrier** — a crate-private `ProtocolContext::resolved_log_level` with
  `with_resolved_log_level` / `resolved_log_level()` accessors, plus the shared
  `attach_request_log_sink` unit that moves it onto `RequestHandlerExtra.log_level` at BOTH dispatch
  roots. Plan 06 also ships a fence proving that hop works before any writer exists.
- **This plan owns the WRITER** — resolve the level at the HTTP ingress and call
  `with_resolved_log_level(..)` on the request's context.

`peer_channel.rs` is deliberately NOT in `files_modified` and is deliberately not the carrier:
`attach_session_backchannel` returns early on `!site.sessions_on || site.is_init_request`
(`src/server/streamable_http_server/peer_channel.rs:610`) and v2 has no sessions, so it structurally
cannot carry a v2 `_meta` level. The two ingress call sites in `streamable_http_server.rs` — the fast
path at `:4423`/`:4438` and the middleware path at `:5201`/`:5213` — both have the session id, the era
and the parsed request, and both already own a `ProtocolContext` at that point. That is where the write
belongs, and **it must happen at BOTH** or one deployment shape silently ignores the level.

Output: the storage, both capture paths, both ingress writes, the null twin, and the isolation fence.
