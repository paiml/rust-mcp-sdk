<objective>
Close **CR-02**: terminal stream errors are queued out-of-band and can silently pair one tool call's
result with a different, unrelated call.

Purpose: this is a **data-correctness hazard**, not a robustness nicety. The verifier confirmed both
halves in the merged source:

1. Every terminal reason this phase introduced — D-02 overflow, D-05 parse failure, D-03 budget
   exhaustion, a 405 on reconnect, a failed re-open, a dropped POST stream — is delivered by pushing
   `Err(..)` onto the SAME `mpsc<Result<TransportMessage>>` the responses ride
   (`src/shared/streamable_http.rs:2050-2070` documents this as intentional). The only consumer is
   `Client::dispatch_request`, so an error raised while the application is idle **sits in the queue
   and fails the next, unrelated request** — a `tools/call` that succeeded on the wire comes back
   reporting a session-stream failure from ten minutes earlier.
2. `Client::dispatch_request`'s receive loop (`src/client/mod.rs:3721-3735`) returns on the FIRST
   `TransportMessage::Response(..)` it pops with **no comparison of `response.id` against
   `request_id`**, and unconditionally removes `request_id` from `active_requests`. Once one
   out-of-band entry desynchronises the queue, call *n+1* silently receives call *n*'s result.

The missing id check pre-dates this phase. What 118.2 supplied is the *stock of out-of-band queue
entries* that makes the desync reachable without any server-side bug — which is why it is correctly
in scope here rather than deferred.

Both halves must land: the latch alone removes today's known supply of poison, and the id check
alone leaves the poison in the FIFO. Neither alone makes the phase's "usable end to end by pmcp's
OWN client" claim true.

Output: a private, sticky, write-once terminal latch with a wake signal; a `receive()` that drains
the queue before consulting it; id correlation in `dispatch_request`; and two fences driven through
a real `pmcp::Client`, the second of which is the desync assertion the verification report demanded.
</objective>

**`pmcp::Error` does NOT derive `Clone`** — `src/error/mod.rs:15` is `#[derive(Error, Debug)]`, and
so is `TransportError` at `:256`. A latch therefore cannot store an `Error` and hand out clones. The
terminal reasons this phase produces are exactly two shapes:
`TransportError::InvalidMessage(String)` (D-02 overflow, D-05 parse failure) and
`TransportError::Request(String)` (budget exhaustion, 405 on reconnect, failed re-open, POST-stream
drop). Store the reconstructable pair and rebuild.

**Argument-count discipline.** `read_sse_body` already takes five arguments and is reached from two
call sites; plan 17 adds a shutdown receiver and a per-reader cursor on top of what this plan adds.

**The `watch` precedent and why it, not `Notify`.** `tests/client_sse_stream.rs:243-249` already
records the reasoning in this repo's own words: `Notify::notify_waiters` wakes only the tasks
ALREADY parked on it, so a signal raised between two iterations of a loop is lost and the waiter
hangs until its bound. A `tokio::sync::watch` generation counter has no lost-wakeup window provided
the consumer SUBSCRIBES BEFORE it checks the latch. `tokio::sync::watch` is already available — the
root `Cargo.toml:191` enables tokio's `sync` feature — so no manifest change is needed.
`watch::Sender::send` errors when there are no receivers; `send_modify` does not, which is why the
harness uses `send_modify` and this plan must too.

**`Transport::receive`'s current body** is three lines (`:2075-2082`): lock the receiver mutex,
`recv().await`, map `None` to `TransportError::ConnectionClosed`. Its rustdoc above it
(`:2044-2074`) carries a five-row taxonomy table and three numbered rules. Rule 1 currently
justifies putting the terminal reason on the queue on FIFO-ordering grounds; that justification is
what CR-02 falsifies, and the table's ordering CLAIM stays true under the latch (already-queued
messages still come first) while its MECHANISM changes. Rewrite both, and keep the row for an
ordinary EOF exactly as it is — WR-05 is out of scope.

**`StreamableHttpTransport`'s fields are ALL private** (`:649-694`), and the struct is `#[derive(Clone)]`
with every field either an `Arc` or a `Copy` scalar. `max_collected_body_bytes`'s own rustdoc
(`:684-693`) records the measured reason this matters: a field on `StreamableHttpTransportConfig`
would fail `constructible_struct_adds_field` and force a MAJOR version, whereas a field on THIS
struct is invisible to `cargo semver-checks` (T-113-95). Both new fields go here.

**`Client::dispatch_request`'s loop and its cleanup invariant** (`src/client/mod.rs:3664-3800`): the
whole body after the `active_requests` registration runs inside an inner async block whose result is
inspected at `:3796-3798`, so every error exit removes the pending entry exactly once (WR-04). The
happy path removes it inline at `:3726`. A mismatch must remove NOTHING — the request is still
pending — so the `continue` has to sit ahead of that inline removal.

**`RequestId`** (`src/types/jsonrpc.rs:30-35`) is `String(String) | Number(i64)`. Equality is the
derived structural kind, so `String("1") != Number(1)`. That is correct per JSON-RPC 2.0 ("It MUST
be the same as the value of the id member in the Request Object"), and it is also a behaviour change

get a wait. The `tracing::warn!` must name BOTH ids so that wait is diagnosable rather than mute.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| remote MCP server -> pmcp client receive queue | every frame, including the `id` of a JSON-RPC response, is peer-controlled and reaches the correlation decision |
| pmcp client SSE reader tasks -> `Client::dispatch_request` | a shared single-consumer queue crossed by out-of-band terminal reasons the application never asked for |
