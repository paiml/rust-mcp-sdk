## Client stream bound + lifecycle

### Q1 — Which of the two whole-body collect sites should switch to incremental reads?

| Option | Description | Selected |
|--------|-------------|----------|
| Both sites | GET (`:1002`) and POST-response SSE (`:1543`). The POST case matters more than the roadmap says: a POST answering `text/event-stream` stays open and can carry notifications AND server→client requests before the response frame — so collecting it whole deadlocks in-tool elicitation | ✓ |
| GET stream only | Exactly the roadmap's criterion 1 and nothing more; smallest diff; POST-stream deadlock stays open | |
| GET now, POST behind a fence | Stream the GET, land a RED test proving the POST deadlock without fixing it | |

**User's choice:** Both sites
**Notes:** Deliberate scope widening beyond the roadmap's stated criterion 1, on the strength of the deadlock argument surfaced during scouting.

### Q2 — What bounds the streams once `max_collected_body_bytes` no longer does?

| Option | Description | Selected |
|--------|-------------|----------|
| Reuse the collected-body cap as the parser bound | `with_max_buffer_size(self.max_collected_body_bytes)`, 16 MiB default, already user-overridable, no new public config; parser bound already hardened by Phase 113 CR-01/CR-02 | ✓ |
| A separate `max_sse_buffer_bytes` knob | Decouples whole-body budget from in-flight-event budget; costs a second public number | |
| Reused cap PLUS a lifetime byte budget | Bounds slow-drip exhaustion; but any lifetime ceiling is a timer on a session stream meant to live as long as the session | |

**User's choice:** Reuse the collected-body cap as the parser bound

### Q3 — A live session stream ends or errors mid-flight. What should the client transport do?

| Option | Description | Selected |
|--------|-------------|----------|
| Bounded auto-reconnect with `Last-Event-ID` | Parser already tracks `last_event_id()`, `apply_resumption_header` already exists; without it the fix regresses to `NO_LIVE_STREAM` the first time a proxy idle-drops | ✓ |
| Surface and stop | Resumption stays caller-driven via `SendOptions::resumption_cursor`; adds no retry policy to a public transport | |
| Reconnect forever | EventSource semantics; a broken endpoint becomes an invisible hot loop | |

**User's choice:** Bounded auto-reconnect with `Last-Event-ID`
**Notes:** Raised at ask time and carried into CONTEXT.md as a constraint — `apply_resumption_header` is `#[cfg(feature = "v1-compat")]`, so `full-v2` builds have no cursor to send.

### Q4 — What bounds the queue between the reader task and the consumer?

| Option | Description | Selected |
|--------|-------------|----------|
| Bounded queue, reader awaits capacity | Real TCP backpressure; never drops a frame, which matters because this queue carries back-channel *requests* | ✓ |
| Bounded queue, drop-newest | Follows the server-side `V2_PROGRESS_QUEUE_CAPACITY = 64` precedent; cannot wedge, but silently drops requests | |
| Keep it unbounded | Smallest diff; makes the per-event bound a paper guarantee over an endless stream | |

**User's choice:** Bounded queue, reader awaits capacity

### Q5 — A frame on the live stream fails to parse (today silently dropped at `:1051`).

| Option | Description | Selected |
|--------|-------------|----------|
| End the stream with a named error | Matches the parser's own overflow prescription; a swallowed server→client request hangs with no signal at either end | ✓ |
| Log and skip | Preserves tolerance, needs a `warn!` so the drop is visible | |
| Skip notifications, end on requests | Most precise; requires parsing a frame that failed to parse | |

**User's choice:** End the stream with a named error

**Continue check:** Next area.

## Emitter API shape

**Context supplied before asking:** `ServerProgressReporter::new` takes `Arc<dyn Fn(Notification) + Send + Sync>` — a sink carrying *any* notification, already plumbed into both dispatch roots but only built when `req._meta` carries a progress token.

### Q1 — Where does a tool handler reach the log emitter from?

| Option | Description | Selected |
|--------|-------------|----------|
| `RequestHandlerExtra` only | Mirrors `report_progress`; no trait changes, so criterion 3's semver verdict is "no public trait surface touched" | ✓ |
| Both — mirror the progress pattern | Defaulted `PeerHandle::log_message` plus the extra method, as `progress_notify`/`report_progress` coexist; what the roadmap anticipated | |
| `PeerHandle` only | `notifications/message` is not request-correlated, so peer scope is arguably natural; but forces `extra.peer()` unwrapping in the common case | |

**User's choice:** `RequestHandlerExtra` only
**Notes:** Diverges from the roadmap's criterion 3 prose, which anticipated a defaulted `PeerHandle` method. CONTEXT.md records that the phase-split justification survives independently.

### Q2 — How should the notification sink be un-gated from the progress token?

| Option | Description | Selected |
|--------|-------------|----------|
| Hoist to a shared per-request unit | One function builds the sink; the token gate applies only to the `ProgressReporter`; both roots call it — the `attach_request_peer` pattern from 118.1 | ✓ |
| A separate log sink field, built per root | Fully decoupled, at the cost of a second place the twin roots must agree | |
| Un-gate `ProgressReporter` entirely | Smallest plumbing diff; conflates two concerns on a public trait | |

**User's choice:** Hoist to a shared per-request unit

### Q3 — `extra.log(..)` with no sink — what happens?

| Option | Description | Selected |
|--------|-------------|----------|
| `Ok(())`, silently dropped | Matches `report_progress` exactly; handlers stay callable outside a server | ✓ |
| `Err` naming the missing sink | Consistent with `PeerHandle::elicit`'s deliberately-failing default and with Q5 above | |
| `Ok(())` but `tracing::warn!` once per handle | Middle path; hole visible in logs | |

**User's choice:** `Ok(())`, silently dropped
**Notes:** The one place in this discussion where the quiet option was chosen over the loud one. Recorded in CONTEXT.md as an accepted production-diagnostics hole, with the reasoning that the conformance fence still fails loudly.

### Q4 — Should the log emitter rate-limit like `ServerProgressReporter` (100ms)?

| Option | Description | Selected |
|--------|-------------|----------|
| No rate limit | Progress values are supersedable; log records are the only copy of their information | ✓ |
| Same 100ms limit as progress | One flood-control story for both notification kinds | |
| No limit, but count drops if the queue refuses | Never rate-limit at the emitter; report `N records dropped` on drain | |

**User's choice:** No rate limit

**Continue check:** Next area.

## Level filtering across eras

### Q1 — Should the emitter filter by level at all in this phase?

| Option | Description | Selected |
|--------|-------------|----------|
| Both eras | Honour v1 `logging/setLevel` and read v2's `io.modelcontextprotocol/logLevel` `_meta` key — a constant that exists but is referenced only by the retirement table | ✓ |
| v2 only, v1 stays accepted-and-ignored | Per-request `_meta` needs no session state, sidesteps the shared-`Arc` problem entirely | |
| No filtering — emit everything | Least machinery; `setLevel` stays a lie on both eras | |

**User's choice:** Both eras

### Q2 — Where does v1's client-set level live?

| Option | Description | Selected |
|--------|-------------|----------|
| The existing `v1::V1State` session map | Per-session home already exists, already v1-gated, zero-sized twin on `full-v2` | ✓ |
| Per-session home, and fold in the `client_capabilities` fix | Same mechanism, one plumbing pass instead of two; larger diff, touches 118.1 plan 08 | |
| On the shared `Arc<Mutex<Server>>` | Smallest change; reproduces the misattribution defect code review just found | |

**User's choice:** The existing `v1::V1State` session map
**Notes:** The `client_capabilities` fold-in was explicitly offered and declined. Recorded as a deferred item with the finding's provenance so it is not lost.

### Q3 — What level applies before a client has set one?

| Option | Description | Selected |
|--------|-------------|----------|
| `info` | Conventional; suppresses `debug` until asked; conformance scenario passes unconfigured | ✓ |
| `debug` — emit everything until told otherwise | Nothing lost by default; costs bandwidth on every session | |
| No default — no filtering until set | Most literal reading of `setLevel` | |

**User's choice:** `info`

### Q4 — Fix the `SetLoggingLevel` twin-root divergence here?

| Option | Description | Selected |
|--------|-------------|----------|
| Yes — both roots agree | The `Server` arm stores-and-honours on v1 and retires on v2; 118.1 collapsed exactly this class of divergence for `completion/complete` | ✓ |
| No — HTTP-layer retirement is the measured surface | Nothing observable changes; record as a named residual | |
| v1 storage yes, v2 retirement no | Do only what the emitter needs | |

**User's choice:** Yes — both roots agree
**Notes:** Scoped in CONTEXT.md to `SetLoggingLevel` alone; the other three arms of the residual (`Subscribe`/`Unsubscribe`/`Ping`) stay deferred.

**Continue check:** Next area.
