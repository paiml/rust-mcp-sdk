<objective>
Close the wedge that moved from the receive path to the SEND path — a defect no review and no prior
verification saw, found by re-verification at HEAD `5caeed05`.

Purpose. `dispatch_request` holds the single transport write guard across the whole send: the v2
`send_raw` path and the v1 `send` path both await inside it, and both reach `post_once`, which awaits
the peer's response headers. The hyper client is built with only a pool idle timeout — there is no
request timeout on any request path in the file. A peer that accepts the POST and never writes
response headers therefore holds the transport write guard forever, and every other operation on that
`Client`, `close()` included, blocks at acquisition with nothing to bound it. Fence 26 cannot see
this: its harness answers POST headers promptly and holds only the SSE answer FRAME, so it measures
the receive path only, and its own panic message now names a construct that no longer exists while
the live one goes unfenced.

**Why the bound is the wrong fix here, stated up front because the verification offers it.** A
response head arrives when the server writes it; for a JSON-answering server — including every
Lambda-hosted pmcp server, a first-class deploy target — that is when the handler finishes. Any
finite deadline on the send therefore fails a legitimate long `tools/call` that works today. Rounds
two and three each traded one permanent failure for a narrower one; a deadline here would be the
third such trade. The other option the verification names — release the guard around the round trip —
costs nothing that works today.

**What the failure mode becomes.** Before: a stalled peer freezes every operation on the `Client`,
`close()` included, with no error, no log and no recovery. After: the stalled peer's OWN call keeps
waiting — pmcp's deliberate, documented no-default-timeout behaviour, unchanged and not made worse —
and nothing else on that `Client` is affected. No new failure is created for any caller: transports
without a shared-send path take the identical exclusive route they take today, and the transport that
has one performs the identical POST with the identical error propagation. The blast radius shrinks
from "the whole client" to "the one call whose peer stalled", which is where it belonged.

Output: one additive trait accessor with a defaulted `None`, one handle implementation over a
transport that is already `Clone`, four client send sites routed off the guard, one deterministic
fence, one corrected assertion text, and a semver verdict at this HEAD.

**Locked decisions this plan preserves rather than revisits.** D-15's rule carries forward verbatim:
the fence is RED against the unfixed tree before the fix lands. D-06's principle — external
implementors are not to be broken — is honoured in the stronger form: the new method carries a
default body, so no external `Transport` implementor is even defaulted-around in behaviour, it simply
keeps today's path. D-01's POST-response streaming contract is untouched. D-02's "no new public
config" holds: nothing configurable is added.
</objective>

delegating to it, which is purely additive and leaves every existing caller untouched.

**The trait, and the shape of the addition.** `src/shared/transport.rs` carries TWO definitions that
must stay in lockstep: the native one at `:279` (`#[async_trait]`, `pub trait Transport: Send + Sync +
Debug`) and the wasm32 mirror at `:390` (`#[async_trait(?Send)]`, `pub trait Transport: Debug`). The
file's own convention, stated at `set_negotiated_protocol_version` (`:414`), is that the mirror is
"kept identical so the two trait definitions cannot drift". The new accessor and the new handle trait
both need that treatment, with the wasm handle trait relaxed to no `Send + Sync` exactly as the wasm
`Transport` is.

**`Client<T>` is generic, not `dyn`.** The field is `transport: Arc<RwLock<T>>`
(`src/client/mod.rs:498`), so the accessor's return type is what carries the dynamism. A
`dyn`-object handle behind an `Arc` is the only shape that works for both the generic client and a
`Client<Box<dyn Transport>>`.

**Why a read guard is not enough, and must be said in the code.** tokio's `RwLock` is fair: a writer
that arrives while a reader holds the lock parks, and every reader arriving after that writer parks
behind it. A read guard held across an HTTP round trip therefore blocks `pump_once`'s `write()` and
`close()`'s `write()` just as completely as a write guard would. The handle must be taken and the
guard DROPPED before the send is awaited.

JSON answer built by `call_answer` (`:869`). The harness's own comment inside `serve_post_sse_answer`

JSON-answered POST blocks the client INSIDE `send()`, still holding the transport lock and never
reaching the receive path at all. That comment is the specification for the new mode — park BEFORE
the head is written, not after.

**Fence 26 (`:3238`).** Its harness answers POST headers promptly and holds the answer FRAME; its
panic text at `:3277` describes a receive-path construct that no longer exists. The bound
`LOCK_PROBE_BOUND` (`:257`) is 5 s and the probe is `client.cancel_request(..)`. Reuse both idioms.

**There is no `Client::close`.** `grep -n "pub async fn close" src/client/mod.rs` returns nothing;

guard. The fence must therefore assert on operations a consumer can actually reach and say so
plainly, rather than pretending to fence a method that does not exist.
