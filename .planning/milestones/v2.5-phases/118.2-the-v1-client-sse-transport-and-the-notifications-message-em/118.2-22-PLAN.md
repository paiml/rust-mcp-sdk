<objective>
Break the self-sustaining half of CR-02 — the one that survived the per-id router under a rename and
is, at HEAD, disclosed nowhere in `.planning/`.

Purpose. At HEAD `5caeed05` a call that dies at its ceiling leaves its own real answer on the shared
transport queue with no owner. The next call pops it, finds no owner, books it
`PumpStep::Unmatched`, and arms its OWN `UNMATCHED_RESPONSE_TIMEOUT` on frame one. Against a peer
whose honest round trip exceeds ten seconds that fails every subsequent call on that `Client`,
permanently — the identical shape CR-02 described, one rename later. The source admits it in its own
rustdoc; nothing in the planning record does.

The fix is a classification fix, not a bound fix. `pump_once` today answers one question — "does any
LIVE request await this id?" — and treats both `no` answers alike: a frame the peer mis-addressed
(genuine misbehaviour, must spend budget) and a frame this client asked for and then stopped waiting
for (our own debris, must not charge anyone). Separating those two is the whole change.

**What the failure mode becomes, stated as the round's own rule requires.** Before: one stray frame
plus a slow peer fails every later call on the `Client` for the life of the process, silently.
After: a peer that mis-addresses frames still fails the call that is awaiting, within the same two
bounds, with the same named and counted error; a peer that answers a call we already abandoned is
absorbed once and charges nobody. Nothing that succeeds today starts failing, no bound is loosened,
and the failure that remains is bounded, named, and confined to the call whose peer actually
misbehaved. That is strictly better rather than narrower: the class of victims shrinks from "every
later call" to "the call being mis-answered", and no new class is created.

Output: one deterministic integration fence, three unit fences, a bounded ledger type, three wiring
points, and a corrected rustdoc.

**Locked decisions this plan preserves rather than revisits.** D-15's rule carries forward verbatim:
the fence is demonstrated RED against the unfixed tree before the fix lands, and the RED is recorded
with its exact failure text. D-02's "no new public config" spirit is honoured — the ledger's cap is a
private constant, as `UNMATCHED_RESPONSE_TIMEOUT`, `MAX_UNMATCHED_RESPONSES` and `PUMP_RECEIVE_SLICE`
all are. D-17 is preserved: no new requirement ID is minted; this is CONF-09 evidence.
</objective>

**The three sites where an id leaves `active_requests`, and which of them can leave debris:**

| Site | Symbol | Leaves debris? |
|---|---|---|
| `:4072` | `pump_once`'s owner lookup | NO — it removes the entry precisely BECAUSE the answer arrived |
| `:4004` | `dispatch_request`'s single WR-04 exit cleanup, on every `Err` | YES when the entry was still registered |
| `:3581` | `cancel_request` | YES when it removed a live `Pending` |

Both debris sites already have the right shape for the fix: each performs a `remove` whose
`Option<Pending>` return distinguishes "there was still a live registration" (debris possible) from
"the pump already took it" (answer already delivered, nothing to absorb). Record ONLY on `Some`.

**The exact chain, re-derived from source rather than from any summary:**
`dispatch_request` `:4004` removes the registration and drains nothing → the peer's real answer for
that id lands on the shared receive queue → the next call's `pump_once` pops it at `:4070`, finds no
owner at `:4072`, warns and returns `PumpStep::Unmatched` at `:4078` → `dispatch_request` calls
`budget.record()` at `:3960`, arming a deadline on frame one.

**Why the fence uses the COUNT bound and not the deadline.** `UnmatchedBudget::deadline` is built
from `web_time::Instant::now()`, which on native IS `std::time::Instant`. `tokio::time::pause()` does
NOT move it, so a paused-clock fence would never expire the deadline, and a real-time fence would
need eleven seconds of wall clock and would be load-sensitive — the exact defect class this repo has
already recorded for `tests/client_sse_stream.rs`. `exhausted` fires when `seen >= 32` OR the
deadline passed, so a fence that controls the COUNT exactly is deterministic with no clock in it.

**The harness in `tests/client_sse_stream.rs`, and where the spray goes.** `RecordingServer` is a raw
HTTP/1.1 listener over `Shared`. An answered call is built by `call_answer_body` (`:894`) and
delivered either as JSON by `serve_post` or, when `answer_calls_with_sse` is set, as a chunked
`text/event-stream` by `serve_post_sse_answer` (`:1047`). That second function is the seam: it writes
the head, flushes, optionally waits at the stagger gate, then writes ONE data chunk and the
terminating chunk. Extra frames written before that data chunk arrive on the same POST-response body
and are pushed onto the client's shared receive queue by the detached reader, in order.

**Existing harness precedent for a test-local mirror of a private constant:**
`SHIPPED_RECONNECT_BUDGET` (`:152`) and `SHIPPED_MIN_RECONNECT_DELAY` (`:190`) each mirror a private
`src/` constant with a doc comment naming the source symbol. The new fence's count mirror follows
that idiom exactly.

**Two existing fences that must be read before touching this area, because the new one sits beside
them and must not duplicate either:** `two_concurrent_calls_each_receive_their_own_answer` (`:3171`,
fence 25 — proves a live caller's answer is routed, not destroyed) and
`an_outstanding_call_does_not_block_another_operation` (`:3238`, fence 26 — proves the receive path
releases the transport guard). Neither can see the chain: fence 25 has no DEAD call, and fence 26
asserts nothing about budgets.
