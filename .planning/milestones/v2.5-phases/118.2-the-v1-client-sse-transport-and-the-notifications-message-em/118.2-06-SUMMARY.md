# Phase 118.2 Plan 06: One Shared Log-Sink Unit, Both Dispatch Roots — Summary

`extra.log(..)` now reaches a client. One function resolves a request's notification sink AND lifts
its resolved log level onto the `extra`; both native dispatch roots call it at the same
post-authorization site they already call `attach_request_peer` from; and the log-level carrier the
HTTP ingress will write in plan 07 ships here with a fence proving it reaches the emitter before any
writer exists.

## The Unit, Verbatim

`src/server/core.rs:4606`, immediately beside its `attach_request_peer` twin:

```rust
#[cfg(not(target_arch = "wasm32"))]
pub(crate) fn attach_request_log_sink(
    extra: crate::server::cancellation::RequestHandlerExtra,
    fallback: Option<Arc<dyn Fn(crate::types::Notification) + Send + Sync>>,
) -> crate::server::cancellation::RequestHandlerExtra
```

Body, in order:

1. clone the request-scoped `TransportBackchannel::notification_sink` out of the borrow;
2. copy `ProtocolContext::resolved_log_level` out of the *same* borrow;
3. apply `with_log_level(level)` when `Some`, leave `log_level` alone when `None` so plan 05's
   `DEFAULT_LOG_LEVEL` applies at emit time;
4. `with_log_sink(request_scoped)` → else `with_log_sink(fallback)` → else `extra` unchanged.

Both reads happen **before** either `with_*` builder consumes `extra` — the same capture-before-move
discipline the peer unit uses, and the reason the sink is read back off the already-constructed
`extra` rather than captured before `with_protocol_context` moved the context in (Pitfall 12).

The rustdoc carries the `# Precedence`, `# Why the LEVEL is applied here too`, `# Ordering`
(post-`tool_authorizer`, ASVS V4) and `# The progress token does NOT gate this` sections the plan
asked for.

## Both Call Sites

| Root | Site | Fallback |
|------|------|----------|
| `ServerCore` | `src/server/core.rs:767`, inside `ServerCore::attach_peer` | literal `None` |
| `Server` | `src/server/mod.rs:1265`, inside `Server::attach_peer` | `self.notification_tx_sink()` |

**`attach_peer` was EXTENDED rather than joined by a sibling `attach_log_sink`.** Both forms were
sanctioned by the plan; extension was chosen because it makes the both-roots property structural
instead of remembered: all 9 production dispatch sites (4 on `ServerCore`, 5 on `Server`) already
call `attach_peer`, so none had to be edited, and a 10th cannot be added that gets a peer but no log
sink. The name is kept for its call-site history and both rustdocs now open with an
`# It attaches the LOG SINK too` section saying exactly that.

`ServerCore`'s literal `None` is commented at the call site in the terms the plan asked for — it has
no `notification_tx` of any kind, so a request-scoped `TransportBackchannel` is the only sink that
root can ever supply, and "do not fix this by inventing a channel here" is stated outright. It is
also fenced: `the_server_core_root_has_no_fallback_sink_of_its_own`.

## The Carrier, Verbatim

`src/types/protocol/context.rs`, modelled on the crate-private `mrtr` / `mrtr_verified` fields:

```rust
// :300  — field
pub(crate) resolved_log_level: Option<crate::types::notifications::LoggingLevel>,

// :365  — reader (OWNED Option; LoggingLevel is Copy)
pub(crate) fn resolved_log_level(&self) -> Option<crate::types::notifications::LoggingLevel>

// :380  — builder
#[must_use]
pub(crate) fn with_resolved_log_level(
    mut self,
    level: crate::types::notifications::LoggingLevel,
) -> Self
```

Initialised to `None` in `ProtocolContext::new` (the only construction site in the crate — verified:
`grep -rn mrtr_verified src/` shows the field appears in the declaration, in `new`, and in one test
assertion, nowhere else).

The field's rustdoc names the problem (the ingress knows the level but never builds a
`RequestHandlerExtra`; the roots build the `extra` but know nothing about sessions), names the
rejected carrier (`peer_channel::attach_session_backchannel`, which returns early when sessions are
off and so cannot carry a v2 level), and states the isolation argument for T-118.2-06-05.

**Debug:** printed **verbatim**, not as presence. A severity threshold is not sensitive, and "which
level was resolved for this request" is precisely the fact a developer chasing "my log records went
nowhere" needs — consistent with `RequestHandlerExtra`'s `Debug`, which plan 05 made print its own
`log_level` verbatim. The redacted neighbours are all capability handles and decrypted state; this is
neither.

**Both accessors carry `#[allow(dead_code)]` with a stated reason** (comment above the attribute, per
rustfmt). The reader's sole caller is `attach_request_log_sink`, which is
`#[cfg(not(target_arch = "wasm32"))]`; the builder's writer is the HTTP ingress landing in plan 07.
Without the allows, `RUSTFLAGS="-D warnings"` fails the wasm32 build and the native build
respectively.

## The Single `notification_tx`-to-Sink Conversion

**Location: `src/server/mod.rs:1292`, `Server::notification_tx_sink`.**

Reached by all three consumers:

| Consumer | Site |
|----------|------|
| progress reporter | `Server::progress_notification_sink` (mod.rs:1287, tail) |
| log sink | `Server::attach_peer` (mod.rs:1265) |
| cancellation manager | `Server::run` (mod.rs:1157) |

The third one is a **deviation** — see below. Before this plan there were two hand-rolled `try_send`

`grep -rn 'try_send(notification)' src/` returns two hits, and the second
(`streamable_http_server.rs:2465`) is `new_v2_progress_queue`'s per-request v2 queue over a locally
created channel — a different channel, not `Server::notification_tx`. Mechanized as
`exactly_one_site_converts_the_server_notification_tx_into_a_sink`.

## Fence Placement — Which Form Fence 3 Took, and Why

**Both forms, not one.**

The plan's Task 2 puts all five fences in `tests/log_emitter.rs`. Fences 1, 2, 4 and 5 **cannot** be
written there: `attach_request_log_sink`, `TransportBackchannel`,
`ProtocolContext::with_resolved_log_level`, `Server::attach_peer`, `Server::notification_tx` and
`Server::progress_reporter_for` are all `pub(crate)` or private, so an integration test cannot
construct the request-scoped half of the precedence rule at all. (`RequestHandlerExtra::log_sink`,
`log_level`, `with_log_sink` and `with_log_level` ARE public — plan 05 made them so — which is why
fence 7 below works from there.)

So the fences went where the 118.1 `attach_peer` suite went, for the reason that suite states in its
own header comment ("both of which need crate-internal access … so they live here rather than in an

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 — Missing critical functionality] `Server::run` carried a second `notification_tx`-to-sink conversion**

- **Found during:** verifying Task 1's acceptance criterion "the number of places converting
  `self.notification_tx` into an `Arc<dyn Fn(Notification)>` closure is exactly 1".
- **Issue:** the criterion was false. `Server::run` (mod.rs:1157) hand-rolled its own
  `Arc::new(move |n| { let _ = tx.try_send(n); })` for the cancellation manager, identical in every
  respect to the one inside `progress_notification_sink`. Extracting the helper without folding this
  site in would have left the plan's own single-site claim technically untrue and kept a second
  chance to disagree about the send discipline.
- **Fix:** `Server::run` now calls `self.notification_tx_sink()`. `set_notification_sender` takes the
  same `Arc<dyn Fn(Notification) + Send + Sync>`, so the substitution is type-identical.
- **Files modified:** `src/server/mod.rs`, `tests/log_emitter.rs` (added the counting fence)
- **Commit:** `71fb2138`

### Plan-Prescribed Placement That Cannot Work As Written

Task 2 puts all five fences in `tests/log_emitter.rs`. Four of them need `pub(crate)` items an
integration test cannot reach (detailed above under **Fence Placement**). Resolved by putting the
behavioural fences beside the units they measure — the placement 118.1 used for the identical
problem — and giving `tests/log_emitter.rs` the structural both-roots fence plus a name-existence
guard over all ten crate-internal fences, so deleting one is a red test rather than a silent loss of
coverage. Every named fence from the plan exists; only two of them live in a different file.

### Plan-Prescribed Verify Command That Cannot Pass As Written

`grep -E 'Summary.*\] [1-9][0-9]* tests? run: [1-9][0-9]* passed, 0 skipped'`. The `0 skipped`

test as skipped. Actual output is `9 tests run: 9 passed, 1 skipped`. Verified against the task's own
**acceptance criterion** instead — "a NON-ZERO test count with 0 failed, strictly greater than plan
05's recorded count" — which holds: **9 > 5**.

### Out-of-Scope Discovery, Logged Not Fixed

`make lint` exits 101 at the branch tip on a `clippy::let_underscore_future` at

It is a **lint** issue, not a functional one: `spawn_sse_reader` returns a `tokio::task::JoinHandle`,

`drop(self.spawn_sse_reader(response.into_body()));`.

Recorded in `deferred-items.md` rather than swept into these commits, per the executor scope
boundary. Flagged there as the blocker to sweep FIRST, because unlike the `fmt-check` and `audit`
blockers it is trivially closable and it gates every remaining plan in the phase.
