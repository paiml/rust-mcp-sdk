# Phase 118.2 Plan 01: The v1 client session stream — open it AND read it

The pmcp client now opens its GET SSE session stream after the `notifications/initialized`
202 (and only after that one), reads it frame at a time under a parser bound, and reports
overflow, an unparseable frame, or a transport failure as a terminal error that actually
reaches `Transport::receive()` — over a bounded queue that applies real TCP backpressure
instead of growing without limit.

### Task 1 — the harness

A raw-TCP `RecordingServer` on an ephemeral port that records every HTTP **request line**
(method + path + version only — never a header, never a body, so a harness change cannot leak an
`Authorization` header into a CI log), answers `initialize` with a JSON-RPC result and every other
POST with a bare `202 Accepted`, and answers `GET` with a chunked `text/event-stream` it holds open
forever, writing frames the test pushes. Surface: `url()`, `request_lines()`,
`open_get_connections()`, `frames_written()`, `frame_sender()`, `push_frame()`, `shutdown()`.
Plans 03 and 04 extend this file rather than rewriting it.

## The exact predicate and internal signature

`post_body`'s `is_notification: bool` was **replaced**, not re-purposed:

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
enum OutboundFrame {
    InitializedNotification,
    Other,
}

impl OutboundFrame {
    fn of(message: &TransportMessage) -> Self {
        match message {
            TransportMessage::Notification(crate::types::Notification::Client(
                crate::types::ClientNotification::Initialized,
            )) => Self::InitializedNotification,
            _ => Self::Other,
        }
    }
}

async fn post_body(&self, body_bytes: Vec<u8>, outbound: OutboundFrame) -> Result<()>
```

Both callers updated: `send_with_options` classifies the TYPED message before serializing it, and
`Transport::send_raw` passes `OutboundFrame::Other` (the v2 raw path has no handshake and therefore
no initialized notification).

The predicate is a **typed variant**, not the method string `"notifications/initialized"`. That is
stricter than the plan's literal wording and satisfies its actual requirement — "derived from the
TYPED outbound message, never re-parsed from the serialized body", so a hostile body cannot
influence which client branch runs (T-118.2-01-08). `ClientNotification::Initialized` carries
`#[serde(rename = "notifications/initialized")]`, so the wire identity is the same one; the method
string appears in a comment at the 202 arm and in `OutboundFrame`'s rustdoc.

The 202 arm now reads:

```rust
if response.status() == StatusCode::ACCEPTED {
    if outbound == OutboundFrame::InitializedNotification {
        let _ = self.start_sse(None).await;   // 405 tolerated, as the dead branch did
    }
    return Ok(());
}
if !response.status().is_success() { /* non-2xx mapping, unchanged */ }
```

## `CLIENT_RECEIVE_QUEUE_CAPACITY` and its rationale

`const CLIENT_RECEIVE_QUEUE_CAPACITY: usize = 64;`

Worst-case in-flight memory is `64 x max_collected_body_bytes`. The policy is **await capacity,
never drop** — deliberately the opposite of the same-sized server-side `V2_PROGRESS_QUEUE_CAPACITY`
drop-newest precedent: this queue carries `sampling` / `roots` / `elicit` **requests**, and a
dropped request strands a correlation until it times out, whereas a dropped progress frame is
superseded by the next one. Both facts are in the constant's rustdoc, not only here.

Caller-task sites go through a new `queue_from_caller`, which `try_send`s and fails with
`TransportError::Send` naming the capacity. Blocking there would self-deadlock:
`Client::dispatch_request` calls `send()` and only then loops on `receive()`.

## The terminal-error taxonomy as shipped

Recorded verbatim in `Transport::receive`'s rustdoc:

| End reason | On the queue | `receive()` returns |
|---|---|---|
| A message arrived | `Ok(msg)` | `Ok(msg)` |
| Parser overflow (D-02) | `Err(Error::Transport(TransportError::InvalidMessage))` — *"a session-stream chunk pushed the buffered stream state past the {N}-byte parser bound; the buffered bytes were discarded and the stream was ended"*, no body content echoed | that error, once, behind every already-queued message |
| Unparseable frame (D-05) | `Err(Error::Transport(TransportError::InvalidMessage))` — *"a session-stream frame did not parse as a JSON-RPC message ({cause}); the stream was ended. Frame: {<=200 chars}…"* | as above |
| Transport failure mid-body | `Err(Error::Transport(TransportError::Request(<hyper error>)))` | as above |
| Ordinary EOF, `close()`, or last-clone drop | nothing — the reader returns silently | keeps awaiting, exactly as before |

Reconnect-budget exhaustion (D-03) is documented in the same table as plan 04's slot; nothing emits
it yet. **No new `TransportError` variant was minted** — no semver event.

Three rules hold the taxonomy together, and are stated in the code: FIFO ordering puts the terminal
`Err` behind every delivered message; at most ONE terminal error per reader (the reader returns
immediately after sending it); a failed `sender.send` means the receiver was dropped, so the reader
returns rather than retrying — which is what makes "dropping the last transport clone terminates
the reader" true without a `Drop` impl.

## The streaming-middleware contract, as stated in `start_sse`'s rustdoc

> The HTTP response-middleware chain does NOT run over the session stream's body, for the same
> reason `Self::post_streaming` gives for the `subscriptions/listen` body: the chain processes a
> complete `Vec<u8>` body, and a stream has none by construction. Request middleware and
> response-HEADER processing are unaffected. A deployment with a body-rewriting middleware will see
> it applied to POST responses and not to this stream.

Rejected alternatives are recorded at the reader: prohibiting body-transforming middleware
(unenforceable — the chain is a public extension point) and a frame-aware middleware API (new
public surface, and a semver event this phase does not plan for).

### 2. [Rule 1 — the fence would have been vacuous] Backpressure frame sizing

- **Found during:** Task 1
- **Issue:** the plan sized fence 6 at `BACKPRESSURE_FRAME_BYTES = 8 KiB` x `COUNT = 128` = 1 MiB
  total, "chosen so that COUNT frames exceed any plausible kernel socket buffer". But the client's
  own receive queue (capacity 64, minted by task 2) absorbs 64 x 8 KiB = **512 KiB** before the
  socket is even involved, leaving ~512 KiB against an auto-tuned macOS loopback buffer. The stall

- **Fix:** `16 KiB x 256` = 4 MiB, of which the queue can hold 1 MiB. The reason, including the
  arithmetic, is written into both constants' rustdoc.
- **Files:** `tests/client_sse_stream.rs` · **Commit:** `e08cdb4c`
