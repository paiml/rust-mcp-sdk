# Phase 118.2 Plan 22: Break CR-02's Surviving Half Summary

**A call that dies at its ceiling no longer poisons every later call on the same `Client`: its own late answer is now classified as our own debris and absorbed once, instead of being booked as the peer's misbehaviour against the next request's `UnmatchedBudget`.**

## Performance

- **Duration:** ~47 min
- **Tasks:** 3 of 3
- **Files modified:** 2 (`src/client/mod.rs`, `tests/client_sse_stream.rs`)
- **Base commit:** `5c823990`

## Accomplishments

- **The chain is broken at every link.** `pump_once` used to answer one question — "does any LIVE request await this id?" — and treat both `no` answers alike. It now asks a second question when the first says no, and only a frame addressed to an id this client never minted spends budget.
- **`AbandonedRequestIds`**, a private ledger beside `UnmatchedBudget`: a `VecDeque<RequestId>` at a fixed private cap (`MAX_ABANDONED_REQUEST_IDS = 64`), oldest-evicted, entries consumed on first `take`. It can only ever hold ids that came back from an `active_requests::remove`, i.e. ids this client minted, so a hostile peer cannot grow it at all.
- **Three wiring points**, all keyed on the `Option<Pending>` the existing `remove` already returns: `dispatch_request`'s single WR-04 exit cleanup and `cancel_request` record on `Some` (the registration was still live, so no answer had been delivered); `dispatch_request`'s registration takes any stale entry before inserting.
- **Fence 27**, deterministic by COUNT: three sequential calls sprayed 32 / 31 / 0 un-owned frames. Call one must die at the count bound; call two must be answered because its 31 sprays stay one under the bound unless call one's leftover answer is also charged to it; call three must be answered because the damage must not chain forward.
- **A per-answer spray schedule on the harness**, default empty so every existing fence observes byte-identical bytes.

## What the failure mode IS after this plan

Stated as a comparison rather than as an absence, for plan 24's ledger:

> **Before**, one abandoned call plus a peer whose honest round trip outlasts the ceiling failed *every subsequent call on that `Client`*, silently and for the life of the process — because each dead call left its own real answer un-owned on the shared receive queue, and the next call booked that answer as the peer's misbehaviour and armed its own ten-second deadline on frame one. **After**, a peer that mis-addresses frames still fails *the call that is awaiting*, within the same two unchanged bounds (32 frames, 10 s), with the same named and counted error; a peer that answers a call we already abandoned is absorbed exactly once and charges nobody. No bound was loosened, nothing that succeeded before now fails, and the class of victims shrinks from "every later call on this client" to "the call whose peer is actually misbehaving" — a strictly smaller victim set with no new class created. What remains unbounded, deliberately and as a product decision rather than a review gap, is a peer that has simply gone quiet: pmcp still has no default request timeout, and giving every call a blanket deadline would break long-running `tools/call` handlers.

## Decisions Made

See `key-decisions` in the frontmatter. The one worth restating inline: **the registration-path unit fence counts instead of racing.** The plan asked for a fence that "drives the registration path". The obvious shape — `tokio::select!` a never-completing dispatch against a poll of `active_requests` — is not available, because `MockTransport::receive` returns `Err("No more responses")` on an empty queue, so the dispatch completes immediately and the `unreachable!()` arm fires. The replacement dispatches the same id **twice** and asserts the ledger holds exactly **one** entry for it: two entries would mean the second registration did not take the first abandonment, which is precisely the shadowing the take exists to prevent. Deterministic, no clock, no race, and it still drives the real `dispatch_request` path.

**1. [Rule 3 – blocking] The rtk output proxy corrupts `cargo test` and `grep`, silently breaking two of this plan's verify commands**

- **Found during:** Task 2 (units) and Task 3 (the rustdoc grep)
- **Issue:** This machine's `rtk` hook rewrites bare `cargo` and `grep` invocations and reformats their output. `cargo test --lib client` printed `cargo test: 221 passed, 1786 filtered out` instead of the `test result: ok.` line the plan's verify block greps for — a **false RED** on a passing suite. `grep -c "wearing the router" src/client/mod.rs` printed `0 matches for 'wearing the router'` instead of the bare `0` that `| grep -qx 0` needs — a **false RED** on a correct edit. (Failing runs are *not* reformatted, which is why the task-1 RED capture came through verbatim: the corruption is asymmetric and only ever manufactures false negatives on green.)
- **Fix:** every status- or text-bearing command in this plan was re-run through an absolute path — `~/.cargo/bin/cargo`, `/usr/bin/grep`, `/usr/bin/make`. The verify commands' *assertions* were not changed; only the binaries invoking them.
- **Files modified:** none — this is an environment deviation, recorded so a re-runner does not mistake a proxy artifact for a regression.

**2. [Rule 1 – bug] Two clippy violations in this plan's own new code**

- **Found during:** Task 3 (`make lint`)
- **Issue:** `DEBRIS_CHAIN_BOUND = Duration::from_secs(60)` trips `clippy::duration_suboptimal_units` (rust 1.97), and the cap-eviction unit fence's `id as i64` trips `clippy::cast_possible_wrap`. Neither is visible to `cargo fmt` or to `cargo test`, which is why they surfaced only at the gate.
- **Fix:** the bound became `from_secs(45)` — still a generous hang guard against a chain that completes in under a second, and not a whole number of minutes; the cast became `i64::try_from(MAX_ABANDONED_REQUEST_IDS)`.
- **Commit:** `cba66f36`
