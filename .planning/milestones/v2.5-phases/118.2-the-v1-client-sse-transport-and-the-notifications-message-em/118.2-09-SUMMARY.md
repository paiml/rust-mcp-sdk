# Phase 118.2 Plan 09: The Fixture Learns to Log — Summary

`examples/s54_v2_dual_conformance.rs` "logged" three times per call for the whole of Phase 118.1 and
scored zero on `tools-call-with-logging`, because it logged with `tracing::info!` — which reaches the
process's subscriber and never the MCP wire. It now emits three real `notifications/message` records
through `extra.log(..)`, measured on the socket rather than inferred from a diff, and the second
logging tool was split out because it carries the OPPOSITE contract.

## The Wire, Verbatim

`target/118.2-09-log-records.json`, recorded by `tests/log_records_example_run.rs` against the
spawned example binary. Three records precede the result frame on the v1 session stream:

```
data: {"jsonrpc":"2.0","method":"notifications/message","params":{"level":"info","message":"Tool execution started"}}
data: {"jsonrpc":"2.0","method":"notifications/message","params":{"level":"info","message":"Tool processing data"}}
data: {"jsonrpc":"2.0","method":"notifications/message","params":{"level":"info","message":"Tool execution completed"}}
data: {"jsonrpc":"2.0","id":2,"result":{"content":[{"type":"text","text":"Tool with logging completed"}],"isError":false}}
```

| Leg | Era | Tool | Records | Required |
|---|---|---|---|---|
| A | v1 (2025-11-25) | `test_tool_with_logging` | **3** | `>= 3` |
| B | v2 (2026-07-28) | `test_logging_tool`, NO `_meta` log level | **0** | exactly 0 (SEP-2575) |
| C | v2 (2026-07-28) | `test_logging_tool`, WITH `_meta` log level | **1** | `>= 1` (positive control) |

## The Referee Scenario, As Read From the Pinned Bundle

`conformance/node_modules/@modelcontextprotocol/conformance/dist/index.js:1296`, the
`tools-call-with-logging` class (`introducedIn: '2025-06-18'`, `removedIn: F` — v1-only). Its
`run()` body, verbatim:

```js
let r = await ut(t,{},e.specVersion),
    i = new pt(r.client);
await r.client.setLoggingLevel(`debug`),
await r.client.callTool({name:`test_tool_with_logging`,arguments:{}}),
await new Promise(e=>setTimeout(e,200));
let a = i.getNotifications(), o=[];
a.length===0 ? o.push(`No log notifications received`)
             : a.length<3 && o.push(`Expected at least 3 log messages, got ${a.length}`)
```

Its `**Behavior**` block names the three message strings this fixture now quotes character for
character, and states *"the delays are important to test that clients can receive multiple log
notifications during tool execution"*.

Two facts that shaped the rewrite and are not obvious from the paraphrase:

1. **`getNotifications()` returns ONLY logging notifications.** The collector (`:1128`) registers two
   handlers and keeps two lists: `getNotifications(){return this.loggingNotifications}`. A progress
   frame cannot inflate the count, so the three records have to be real.
2. **`test_logging_tool` is a DIFFERENT scenario's tool.** Grepping the bundle for it returns exactly
   one consumer — `sep-2575-server-no-log-without-loglevel` — which calls it with a `_meta` that does
   not carry `io.modelcontextprotocol/logLevel` and FAILS the server if a single
   `notifications/message` frame comes back. See the split below.

## Task 2: The Arm

### Computed sleep budget

`LOG_RECORD_INTERVAL = 15 ms`, **2 gaps, 30 ms total**, and **no trailing sleep** — the emit-first /
sleep-only-between shape copied from `test_tool_with_progress` immediately above it. Down from
3 × 50 ms = 150 ms, which spent three quarters of the referee's 200 ms window inside the call before
dispatch latency was counted. The interval is kept non-zero so the scenario's stated purpose survives:
the three records arrive as three separate frames rather than one burst at completion, which the
recorded stream above confirms.

The constant's rustdoc contrasts it against `PROGRESS_INTERVAL` (120 ms), which is large for a REASON —
it must clear `ServerProgressReporter`'s 100 ms rate-limit window. The log emitter has no rate limit
(D-09), so nothing forces this number upward.

### The `tracing` decision: KEPT alongside, not ambiguous

`tracing::info!` stays on every one of the three records, immediately above its `extra.log(..)` twin,
under a comment naming the two audiences explicitly. The argument is positive rather than inertial:
the example's own `main()` installs `tracing_subscriber::fmt().with_env_filter("pmcp=info,s54_v2_dual_conformance=info")`
(`:1613`), so the `tracing` line genuinely reaches the terminal of an operator running the fixture by
hand against a live suite. Deleting it would remove working operator diagnostics; leaving it
un-commented would preserve exactly the confusion that kept this scenario red. T-118.2-09-01 is
discharged by the comment, which says which mechanism the referee can see.

### The split — the defect the plan did not name

The plan asked for one arm rewritten. Rewriting it would have broken a currently-passing scenario.

`"test_tool_with_logging" | "test_logging_tool"` shared a body. Those two names carry **opposite**
contracts: one requires at least three records, the other requires **zero**. While the arm emitted
nothing at all the two looked identical, and merging them was invisible. Making the shared arm emit
would have turned `sep-2575-server-no-log-without-loglevel` from green to red. They are now two arms.

`test_logging_tool`'s body emits only when `extra.log_level.is_some()` — i.e. only when the request
actually authorized a level, which is exactly SEP-2575's rule.

## The SDK Gap This MEASURED (and did not fix)

**RED mutation 2 below is the measurement.** With the fixture's guard replaced by `if true`, a v2
`tools/call` that carried NO `params._meta["io.modelcontextprotocol/logLevel"]` came back with a
`notifications/message` frame on its POST body.

The vendored schema is explicit: *"If absent, the server MUST NOT send any `notifications/message`."*
`resolve_request_log_level` (`src/server/streamable_http_server.rs:1677`) returns `None` there, and its
own rustdoc states the intent — *"`None` is not 'no logging' — it is 'nothing overrode the default'"* —
so `DEFAULT_LOG_LEVEL` (`info`, D-12) applies at emit time and the record goes out.

That default is **correct on v1** ("the server MAY decide which messages to send automatically") and
**wrong on v2**, where absence is a prohibition rather than a non-answer. One constant currently
answers for two eras that disagree about what "nobody asked" means.

**Not fixed here.** This plan's `files_modified` are two examples and `Cargo.toml`; the fix is an era
branch inside `resolve_request_log_level`, a behaviour change in `src/` that alters what every v2 pmcp
server puts on the wire. Recorded in `deferred-items.md` and appended to `.planning/WINDOWS.md`
(kind `unmet-truth`) so it is visible at ship time. The guard in the fixture carries the gap's name in
a comment, so the next reader cannot mistake the guard for the fix.

## Deviations from Plan

### Beyond Plan: the arm had to be SPLIT, not just rewritten

The plan says "replace the arm's body". Doing only that would have made
`sep-2575-server-no-log-without-loglevel` fail — it drives `test_logging_tool`, which shared the arm
and requires ZERO records. Treated as **Rule 1 (bug)**: emitting from both names is a defect
regardless of what it emits. Full reasoning under **The split** above.

### Beyond Plan: a wire fence was added (`tests/log_records_example_run.rs`)

The plan's `files_modified` name no test file, and its verification list is builds plus greps. But the
plan's own `must_haves.truths` claims *"the fixture emits at least 3 MCP log records per call, **on the
wire**"* — and `cargo build` + `grep 'extra.log'` cannot distinguish that from the `tracing::info!`
defect this plan exists to remove. With the official suite unrunnable locally (Node 20), an unverified
wire claim would have shipped. Treated as **Rule 2 (missing critical verification)**.

Placed in its own test binary on port **8159** rather than appended to `tests/v2_sse_progress.rs`,
because `spawn_example` binds a FIXED port and nextest runs sibling example-run legs concurrently —
8153, 8155 and 8157 are already held. `read_v1_session_stream` is copied rather than imported: it is
private to `tests/v2_sse_progress.rs`, and a v1 session SSE stream never ends, so no shared
read-to-EOF helper can drive it.

### Plan-Prescribed Content That Does Not Exist

Task 1's action asks the example to call `extra.log_warn(..)` and `extra.log_error(..)`. **Those
methods do not exist.** Plan 05 shipped exactly two — `log` and `log_with_data` — and explicitly
DEFERRED the three severity wrappers as sugar (`118.2-05-SUMMARY.md`, Deferred Items). Adding them
here would be a new public API in `src/server/cancellation.rs`, outside this plan's `files_modified`
and with its own semver consequence. The example demonstrates the identical shapes through explicit
levels (`LoggingLevel::Warning`, `LoggingLevel::Error`), which is the surface that actually ships.

### Plan-Prescribed Detail Not Followed

Task 1's action says the example should print each captured notification with
`serde_json::to_string_pretty`. It prints the **compact** one-line form instead. The acceptance
criterion is that stdout carries the literal `notifications/message`, which holds; and one record per
line is closer to what an SSE `data:` frame actually looks like on the wire, which is the example's
whole claim. Recorded rather than silently taken.
