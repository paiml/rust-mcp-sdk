<objective>
Enforce the required v2 HTTP headers (`Mcp-Method`/`Mcp-Name` alongside `MCP-Protocol-Version`) on the streamable-HTTP path, driven by the SAME `_meta`-resolved era Plan 04 threads (the HTTP layer CONSUMES the resolved `ProtocolContext`; it does NOT run a second era resolver). Classify EVERY header/`_meta` presence combination via a defined matrix, reject any v2-vs-v1/absent/invalid conflict fail-closed, strict-reject a v2 request missing any of the three required headers (D-05), cross-check `Mcp-Method`/`Mcp-Name` against the body (D-06), and emit the required headers outbound on success AND error — all HTTP-only and v1-untouched. Every NEW header-violation error sources its JSON-RPC code from Plan 03's `error_codes::` table (VERS-06).

Purpose: VERS-05 is exactly what the official conformance suite (Phase 118) will test; lenient-now means a breaking tightening later.

**Reviewer concerns addressed (Codex HIGH #3/#6, MEDIUM Mcp-Name / outbound-headers):** (1) Plan 04 already resolves era from per-request `_meta` on ALL transports (D-11). If this plan judged "is this v2" from a raw header independently, a request could get v2 dispatch via `_meta` while bypassing header enforcement (RESEARCH Pitfall 2). So the v2 determination MUST be Plan 04's resolved signal, CONSUMED here (not re-derived). **This honors LOCKED D-11:** `_meta` stays era-authoritative; the HTTP header is an HTTP-only requirement RECONCILED against the resolved era, not a second era source. (2) VERS-05 requires `MCP-Protocol-Version` too — this plan mandates all THREE headers on the v2 path and defines every presence cell of the header/`_meta` matrix, closing the downgrade/bypass gaps. (3) `Mcp-Name` semantics and outbound-header/error-path behavior are now specified.

**Concrete threading mechanism (WARNING 2 — named, not improvised):** the HTTP inbound handler in `streamable_http_server.rs` calls Plan 04's `resolve_protocol_context(self.supported_protocol_versions(), meta)` ONCE, uses the resulting `Option<ProtocolContext>` for its header gate, AND passes that SAME value into `core.rs::handle_request_internal` through the `Option<ProtocolContext>` parameter Plan 04 adds. Core.rs therefore does NOT re-resolve `_meta` at dispatch — it threads the value the HTTP layer already resolved. (Because `resolve_protocol_context` is pure/deterministic, a duplicate call could not disagree; this is a one-authoritative-value threading requirement, not a correctness fix — but the mechanism is specified here so wave-4 execution does not invent a second call path.)

Output: `MCP_METHOD`/`MCP_NAME` constants; a full v2-classification matrix over the Plan-04 era + strict inbound validation + method/name body cross-check + outbound emission on success and error, with new error codes from `error_codes::`, routed and tested through the real HTTP path (not in-memory transport), with a proptest over the untrusted classification.
</objective>
