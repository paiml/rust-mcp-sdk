<objective>
Wire the v2 opt-in accept-list into the builder and thread a per-request `ProtocolContext`, resolved ONCE at ingress by a single shared resolver from the configured accept-list + per-request `_meta`, through BOTH native dispatch sites — the load-bearing "spine" of Phase 112. Also add the `extensions` builder convenience for VERS-08.

**Scope note (wasm) — verified against the live tree:** this phase's server plumbing is NATIVE-ONLY. `src/server/core.rs`, `src/server/mod.rs`'s `ServerCore`, `src/server/cancellation.rs`'s `RequestHandlerExtra`, and `src/server/builder.rs` are all excluded from wasm32 builds (`#[cfg(not(target_arch = "wasm32"))]`, src/server/mod.rs:37/49). On wasm32 the only server is `WasmServerCore` (`src/server/wasm_core.rs`) — a separate minimal standalone impl with no capabilities/opt-in/per-request-context — which is **OUT OF SCOPE** for this phase (v2 support for it, if ever needed, is a separate future phase). There is therefore NO "wasm parity" to deliver here and nothing to mirror: `src/shared/cancellation.rs` is a dead orphan (never compiled) and Plan 02 does not touch it. The only wasm obligation is that the native-only additions must not BREAK the wasm build — `resolve_protocol_context()` lives in the cfg-agnostic `src/types/protocol/context.rs` so it still compiles on wasm32 (with no wasm caller), and `cargo build --lib --target wasm32-unknown-unknown` must stay green.

Purpose: This is where era-detection actually happens. The opt-in accept-list (D-01/D-02) makes v1-only the default (D-04) and dual/v2-only expressible with one API; the shared resolver (VERS-01) makes era available to every handler and to the HTTP header gate (Plan 06 CONSUMES this resolved context — it does not re-resolve). Wiring at both dispatch sites via ONE cfg-agnostic resolver is the exact Phase-109-00 precedent (Pitfall 3).

**Reviewer concerns addressed (Codex HIGH #1 "not resolved once at ingress", HIGH #2 "accept-list reduced to a boolean"):** this plan replaces the previous `is_v2_opted_in()`-only design with a genuine resolver that (a) enforces the configured accept-list, and (b) produces ONE authoritative `ProtocolContext` that is threaded — Plan 06's HTTP layer validates headers against THIS resolved context rather than deriving a second verdict. **This honors LOCKED D-11 (era is `_meta`-authoritative and transport-agnostic; HTTP headers are an HTTP-only concern):** the single ingress resolution reads `_meta` on every transport; the HTTP header is reconciled against that result downstream (Plan 06), never used as an independent era source.

**Concrete threading mechanism (Plan 06 reconciliation):** `handle_request_internal` gains a new `protocol_context: Option<ProtocolContext>` parameter (alongside `auth_context`). On the native/stdio ingress path core.rs calls `resolve_protocol_context(...)` once and passes the result in. On the HTTP path, `streamable_http_server.rs` (Plan 06) resolves the context once — it needs the era for its header gate — and passes THAT already-resolved `Option<ProtocolContext>` into `handle_request_internal`, making core.rs's use a pass-through rather than a fresh invocation. Because `resolve_protocol_context` is pure/deterministic, this is a threading-clarity requirement (one authoritative value), not a correctness hazard.

Output: `.with_supported_protocol_versions()` + v1-only default stored on ServerCore; a shared cfg-agnostic `resolve_protocol_context()` + `ProtocolNegotiationError`; ingress resolution (opted-in servers only); a new `Option<ProtocolContext>` parameter on `handle_request_internal`; `.with_protocol_context()` in the extra chain at core.rs and mod.rs; `.with_extension()` builder convenience; an end-to-end handler-visibility test.
