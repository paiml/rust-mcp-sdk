<objective>
Close verification Gap A from `112-VERIFICATION.md`: `server/discover` (VERS-04, ROADMAP SC#3) is 100% unreachable in production. The crate-private routing seam (`parse_request_or_internal`, `IngressRequest::Internal`, the `handle_discover` projection) exists and is unit-tested, but every production transport calls only `crate::shared::parse_request()`, which maps `IngressRequest::Internal → -32601` on every era.

Wire a LIVE production caller of the internal-dispatch seam on the HTTP transport using the **classify-then-continue** design mandated by the cross-AI review (findings #1, #3, #4 — all CONFIRMED against the live tree). The previous revision proposed an early-return interception BEFORE the POST pipeline; the reviewers proved that bypasses authentication, session validation, legacy-version validation, response middleware, and event storage, and that its "success-response assembly" needs values not available pre-parse. It also asserted v1 byte-identity while today's HTTP v1 path returns a `PARSE_ERROR` 400 (`id: null`), not `-32601`.

The corrected design: introduce a crate-LOCAL `HttpIngress::{Public(TransportMessage), Discover{id, raw_meta}}` classification at BOTH POST parse entrypoints, and let both pipelines CONTINUE through every normal stage (session → v2 header matrix → legacy-version → auth → dispatch → event store → per-path response assembly). `server/discover` is routed only at the final response-assembly step, where it calls `Server::handle_discover` → the shared `build_discover_response` free fn.

Purpose: `server/discover` is the stateless replacement for `initialize`'s capability exchange (D-09) — the phase's headline SC#3. It must actually answer on a v2 connection (exposing the `extensions` map) AND be subject to the same security/transport invariants as every other method.

**Scope decision (transport):** HTTP transport only (VERS-04 SC#3 requires "at least one real transport"). The stdio actor and the `ProtocolHandler` adapter/wasi transports receive an already-parsed `TransportMessage::Request` before dispatch, so routing an internal method through them requires a `TransportMessage`-level internal variant — a semver-sensitive change (public enum matched in ~30 sites; `cargo-semver-checks` must stay MINOR). The crate-LOCAL `HttpIngress` enum used here avoids that (it never touches `TransportMessage`'s public variants). Document the non-HTTP discover follow-up honestly (HTTP: supported; stdio/adapters/WASI: not yet; a separate semver-reviewed design) — NOT via a stale dead-code justification comment.

**Scope decision (v1 behavior — review finding #4, CONFIRMED):** `server/discover` is a v2-only method that NO conforming v1 client sends. Today an internal method over HTTP incidentally hits `PARSE_ERROR` 400 (`id: null`) via the generic parse path. This plan standardizes the non-v2 discover response on JSON-RPC `-32601` at **HTTP 200** with the **original request id** (what D-10 describes). This is a DELIBERATE, benign v1 HTTP behavior change: it alters only the response to a request no real v1 client makes, so it does not violate the milestone's byte-identity invariant for any response a v1 client relies on. Record this as an explicit decision note in code (referencing D-10 + the pre-change `PARSE_ERROR` 400 shape) so the reconciliation is auditable.

**Scope note (wasm):** unchanged — `wasm_core.rs` is out of scope; only `cargo build --lib --target wasm32-unknown-unknown` must stay green.
