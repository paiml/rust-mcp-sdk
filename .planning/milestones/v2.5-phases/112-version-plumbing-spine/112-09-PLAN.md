<objective>
Close verification Gaps B and C from `112-VERIFICATION.md`: the per-request `_meta`/`ProtocolContext` spine is wired for `tools/call` ONLY. This plan (a) generalizes `extract_request_meta_value` to read `_meta` from `GetPrompt` and `ReadResource`; (b) threads the resolved `protocol_context` + `request_meta` into the `RequestHandlerExtra` built inside `handle_get_prompt`/`handle_read_resource` at BOTH native dispatch sites (`core.rs` and `mod.rs`); and (c) — folding cross-AI review finding #2 (CONFIRMED against the live tree) — makes the HTTP header gate's logical-name extraction **method-aware** so `resources/read` cross-checks `Mcp-Name` against `params.uri` (the request has `uri`, NOT `name`), instead of a `params.name` that does not exist.

This closes:
- `extra.era()`/`.client_info()`/`.trace_context()` inside prompt AND resource handlers (VERS-01, VERS-03, VERS-09);
- a correct v2 `_meta` signal to the HTTP header gate so a compliant v2 `prompts/get`/`resources/read` is accepted instead of 400 (VERS-05, Gap C) — including a standards-shaped `resources/read` that carries no synthetic `params.name`;
- the already-generic `inject_v2_result_envelope` firing `resultType`/`serverInfo` for those two methods (VERS-07).

Purpose: the phase's headline claim — "ProtocolContext resolved once at ingress is threaded through dispatch to EVERY handler" — is currently false for 2 of the 3 documented name-bearing methods, AND the reviewers proved a standards-shaped `resources/read` would STILL be rejected even after the `_meta` fix because the gate cross-checks a non-existent `params.name`. Both must be fixed together for VERS-05 to actually be TRUE.

Output: generalized `extract_request_meta_value` + protocol-context/request-meta threading at four handler sites (core.rs ×2, mod.rs ×2); method-aware logical-name extraction in `streamable_http_server.rs`; unit + fuzz-style-proptest coverage; handler-visibility tests through the REAL dispatch entrypoints distinguishing `None` / `Some(Era::V1)` / `Some(Era::V2)` and asserting `trace_context()`; live HTTP `prompts/get` + `resources/read` v2 acceptance built from real typed requests; and v1 RAW-byte golden-fixture identity for both methods.

**Scope note (v1 byte-identity):** Adding `.with_request_meta(..)`/`.with_protocol_context(..)` populates the in-memory `RequestHandlerExtra` ONLY; it does not touch the wire response. `inject_v2_result_envelope` remains gated on `era==Era::V2` (None on v1/non-opted-in), so v1 output stays byte-for-byte identical. This is proven by RAW-byte capture + golden comparison, not by asserting two keys absent (review finding #5a).

**Scope note (wasm):** the wasm32 `RequestHandlerExtra` is the zero-field stub at `src/server/mod.rs:162`; `core.rs`/`mod.rs` dispatch are `#[cfg(not(target_arch = "wasm32"))]`.
