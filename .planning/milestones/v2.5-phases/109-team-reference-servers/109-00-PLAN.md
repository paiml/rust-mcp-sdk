<objective>
Prerequisite pmcp-core enablement plan (the shared, independently-confirmed CRITICAL review finding). Locked decision D-14 requires depth + ancestor-chain guard state to travel as namespaced `_meta` on `tools/call`. Today that is IMPOSSIBLE: `RequestMeta` (src/types/protocol/mod.rs:315) has only `progress_token` + `_task_id` and no `#[serde(flatten)]` catch-all, so custom namespaced keys are silently dropped on deserialize; and both `Client::call_tool` (577) and `Client::call_tool_with_task` (624) hardcode `_meta: None`, so no client API can send them. This plan makes D-14's route (A) real with a TIGHT, ADDITIVE change to pmcp core (which is clippy-gated via `make quality-gate`): (1) extend `RequestMeta` with a flattened extensible namespaced map and propagate the request `_meta` into `RequestHandlerExtra`; (2) add two client APIs that forward `_meta` — `call_tool_with_task_and_meta` (task + `_meta`, consumed by team-mcp 109-05) and `call_tool_with_meta` (non-task + `_meta`, consumed by the conformance runner 109-07). We choose route (A) over Gemini's route (B) "smuggle guard state inside `arguments`" because D-14 is LOCKED and explicitly says the guard state is namespaced `_meta`, not tool arguments — carrying it in `arguments` would violate the locked decision and pollute every member tool's input schema.

Purpose: Unblock TEAM-05 (guard `_meta` + related-task hop) and TEAM-06 (conformance runner must send `_meta` per fixture). Without this, Plans 05 and 07 are not executable.
Output: An additive, non-breaking pmcp-core change: extensible `RequestMeta`, handler-visible request `_meta`, and two `_meta`-forwarding client methods.
</objective>
