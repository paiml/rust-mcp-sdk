<objective>
Implement the approval-mcp reference server (TEAM-03) with the 109-04 review's internal-model fixes. Task lifecycle reuses `InMemoryTaskStore` (`.task_store()`) for the observable pending→resolved transition, but the approval-DOMAIN state that a task store cannot hold (question, options, target role, verdict, optional subject ref) lives in an explicit `ApprovalRepository` adapter — the plan no longer pretends `TaskStore` alone stores approval data. Define the OWNER POLICY: dev servers have no auth, so approvals are SERVICE-OWNED (a fixed service owner on the task store) and therefore resolvable from ANY connected client (D-10) rather than owner-scoped to the creator. Define the LIFECYCLE (pending→resolved), ATOMIC first-writer resolution (a second resolve is rejected/idempotent), decision-vs-option-set validation, and ask→notify failure semantics (create the record FIRST, then notify; a notify failure warns and leaves the approval resolvable, never unreachable). Console + webhook channels are notify-ONLY (D-10/D-11); the webhook uses a bounded timeout and non-blocking failure and never logs the shared secret (V7). Advertise `resolve_approval` + `get_approval` UNNAMESPACED plus one `team_approval__ask_<role>` per human role. Records carry an optional `subject_task_id`/`subject_ref` echoed back (D-12); approval ids are deterministic for conformance. Fill the HTTP-first `approval-mcp` dev binary.

Purpose: Ship the approval reference server with a real internal state + authorization + lifecycle model, one deterministic CI-safe resolution path, and linkable (agent output, human verdict) pairs.
Output: `src/approval/{channels,repository,server}.rs` + `src/bin/approval_mcp.rs`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| MCP client → approval tool args | Untrusted ask/resolve args incl. optional subject refs and decision strings |
| server → configured webhook URL | Outgoing POST to operator-configured endpoint |
| concurrent clients → resolve_approval | Multiple clients may race to resolve the same approval |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-109-04-01 | Information Disclosure | webhook shared secret in logs | mitigate | Secret never placed in a `tracing`/`println` field; grep-verified (Task 1). HIGH — blocking. |
| T-109-04-02 | Denial of Service | webhook egress hang | mitigate | `reqwest::Client` bounded connect+request timeout; failure is non-blocking (warn + proceed); timeout test (Task 1). HIGH — blocking. |
| T-109-04-03 | Tampering / Elevation | double or out-of-set resolution | mitigate | Atomic first-writer `resolve` under a mutex (second resolve rejected/idempotent); decision validated against the original option set (Task 2). |
| T-109-04-04 | Server-Side Request Forgery | configured webhook URL | accept | Dev/CI-only, opt-in (`webhook` feature + `--webhook-url`), notify-only; URL documented as operator-configured trusted input; platform keeps hardened egress. |
| T-109-04-05 | Denial of Service | unknown-role ask / malformed args / unreachable approval | mitigate | Unknown role errors (never panic); ask creates the record BEFORE notify so a notify failure never yields an unreachable approval (Task 2). |
| T-109-04-SC | Tampering | dependency graph | mitigate | `reqwest` already vendored, feature-gated behind `webhook`, off by default; `parking_lot` existing dep; no new registry package. |
</threat_model>
