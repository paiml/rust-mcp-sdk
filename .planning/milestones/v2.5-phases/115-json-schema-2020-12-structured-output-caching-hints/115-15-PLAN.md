<why_rename_invariance_is_the_independence_mechanism>
WR-02 is not discharged by writing the same walk a fourth time in a different type. It asks for an
invariant that a RULE defect cannot satisfy. Two candidate mechanisms were considered:

**Rejected — a keyword-list-free total scan.** "Walk every key with no skip at all, collect every
string-valued `$schema`, assert all equal the 2020-12 URI" is genuinely list-free, but it fires on
legitimate DATA (a `$schema` string inside a real `const` payload must survive), so it needs a
precondition excluding documents that contain a data-only keyword. That precondition can only be
expressed by NAME — and the defect's whole shape is a `$defs` entry NAMED `default`, which the
precondition would then skip. The mechanism is provably blind to exactly the case it must catch.

**Chosen — rename invariance, a metamorphic relation.** The keys of `properties`,
`patternProperties`, `$defs`, `definitions` and `dependentSchemas` are AUTHOR-CHOSEN NAMES with no
keyword semantics — a fact from the JSON Schema 2020-12 core/applicator vocabularies, not from
pmcp's source. Therefore: **normalizing an entry must not depend on the name it is filed under.**
Two documents differing only in that name must normalize to the same subtree.

That relation is derived, not restated. It consults no `DATA_ONLY_KEYWORDS` list at all. It fires on
the shipped defect immediately (`$defs.default` normalizes to itself; `$defs.__rename_probe__`
normalizes rewritten; the subtrees differ). And it would equally catch a FUTURE rule defect that
special-cases some other name, or that gains a sixth data-only keyword without gaining the position
exception — which is the property WR-02 says is missing today.

The only list it needs is the five container keywords, which it declares for itself from the spec
rather than importing from the crate. A defect could hide from it only if the crate's list and the
fence's list were wrong in the SAME way, and that list is small, closed and citable.
</why_rename_invariance_is_the_independence_mechanism>
</context>
