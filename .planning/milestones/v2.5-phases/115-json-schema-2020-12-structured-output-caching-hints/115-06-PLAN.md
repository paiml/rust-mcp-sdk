<objective>
Wire 115-05's shared projector into every dispatcher: ensure the hints on the v2 wire, strip them off
the v1 wire, and do it at ONE shared point.

Purpose: SCHM-03, D-07, D-08, D-11, D-12. CONTEXT.md required the planner to first confirm that a
shared serialization chokepoint covering all the result types actually exists. **It does for the two
NATIVE dispatchers:** `inject_v2_result_envelope` (`src/server/core.rs:1561`) is already era-gated,
payload-gated, object-gated, post-serialization, method-agnostic, twin-sited and separately tested.
Four production call sites carry every affected method.

Four things this plan must get right that are easy to get wrong:

1. **The v1 direction is not free.** `inject_v2_result_envelope` early-returns on non-v2, so a
   handler that sets `ttl_ms` on a `ListResourcesResult` and then serves a **v1** client would put
   `ttlMs` on the v1 wire — the exact leak D-11 forbids. The projection must therefore run on BOTH
   eras: ensure-on-v2, **strip-on-v1**.
2. **There is a THIRD dispatcher, and it is not on that chokepoint.**
   `src/server/wasm_server.rs` is `#[cfg(target_arch = "wasm32")]` (`src/server/mod.rs:229-230`),
   carries no `ProtocolContext` at all, and serializes handler-returned `ReadResourceResult` /
   `ListResourcesResult` values DIRECTLY. The cross-AI review found that once 115-05's builders
   exist, a wasm handler can set a hint that reaches that server's v1 wire with no strip. This plan
   closes it by calling the SAME cfg-free projector from `wasm_server.rs` with `era: None`, which is
   the strip arm.
3. **The method is not in scope at the native chokepoint.** `request` is moved into
   `handle_request_internal` (`core.rs:3207`, `mod.rs:1654`) before injection runs, so the
   discriminator must be captured upstream while `request` is still borrowed.
4. **The projection is NOT the final mutation of the response.** `core.rs:3249` calls
   `process_response_with_context(&mut response, &context)` AFTER the injection, and
   `src/shared/middleware.rs:481` takes `response: &mut JSONRPCResponse`. A registered response
   middleware can therefore still add or remove the projected keys. This plan does not reorder that
   (moving the injection after middleware would change what middleware observes about Phase 114's
   `resultType`/`serverInfo`, a v2 behaviour change outside SCHM-03's scope) — it DOCUMENTS the
   prohibition, TESTS the actual behaviour so the limitation is measured rather than assumed, fences
   the ordering with a tripwire in 115-08, and books it as a deferred item.

Output: a `Cacheable` claim captured before the request is moved at both native dispatchers, a call
to the shared projector at all three dispatchers, and unit coverage in the chokepoint's own test
module including the middleware-ordering measurement.
</objective>
