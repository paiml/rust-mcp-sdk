<objective>
Prove SCHM-03 on the wire: six methods, two eras, both native dispatchers, raw response bytes.

Purpose: 115-06 proved the projection at unit level over a synthetic `JSONRPCResponse`. This plan
proves the whole path — dispatcher builds the result, serde serializes it, the chokepoint projects
it, the HTTP transport writes it — because that is the only level at which "every v2 list/read
response carries both fields" is a checkable claim.

Two failure modes this plan exists to catch, both recorded as having bitten this repo before:
- **Pitfall 6, twin-site drift.** The high-level `Server` has its own dispatch and its own injection
  call at `mod.rs:1705`. A `ServerCore`-only change leaves half the SDK non-conformant, and the
  repo's own comments call this out because it has happened.
- **Pitfall 7, the missing sixth type.** The requirement text and CONTEXT.md both say "five".
  `server/discover` — the v2 replacement for `initialize`, the FIRST thing a v2 client calls — is
  `DiscoverResult extends CacheableResult` in the pinned schema. A suite with exactly five method
  tests is the shape of that defect.

**A structural bound the pre-review plan set did not know about — read `<measured_era_reachability>`
before writing the `ServerCore` half.** `extract_request_meta_value` (`src/server/core.rs:3833`)
reads the per-request `_meta` era signal from EXACTLY THREE `ClientRequest` variants: `CallTool`,
`GetPrompt` and `ReadResource`. `ListTools`, `ListPrompts`, `ListResources` and
`ListResourceTemplates` carry no typed `_meta` field at all, by a documented semver decision, and
resolve to the v1 fallback on any non-HTTP ingress. So of the six cacheable methods, **only
`resources/read` can reach `Era::V2` through the in-process `ServerCore` route.** The pre-review
instruction to "extend `duplex.rs` minimally" for the list methods was not achievable; this plan
covers what is reachable in-process, covers the rest over HTTP, and names the bound at a test so a
future reader does not re-derive it.

Output: `tests/v2_caching_hints.rs`, a small addition to `tests/common/duplex.rs`, and a v1 leak
fixture added to `tests/v1_lists_golden.rs`.
</objective>

<measured_era_reachability>
<!-- Measured during the 2026-08-01 `--reviews` replan. This bounds what the in-process
     ServerCore half can prove, and it is NOT a defect to be worked around. -->

`ServerCore::handle_request` resolves the era via `resolve_ingress_protocol_context`
(`src/server/core.rs:3874`), which needs BOTH:
  (a) the server's accept-list to be v2-opted-in — `with_supported_protocol_versions([V1, V2])`, and
  (b) a per-request signal read by `extract_request_meta_value` (`src/server/core.rs:3833`).

`extract_request_meta_value` matches EXHAUSTIVELY and returns the `_meta` object for exactly:
    ClientRequest::CallTool, ClientRequest::GetPrompt, ClientRequest::ReadResource
and `None` for every other variant, INCLUDING:
    ClientRequest::ListTools, ListPrompts, ListResources, ListResourceTemplates
Its rustdoc (`src/server/core.rs:3796-3831`) states the reason: those structs have no typed
`_meta` field, and adding a `pub` field to a constructible `pub` struct is a MAJOR semver break
(`cargo semver-checks` `constructible_struct_adds_field`), which the additive-scoped v2.5 milestone
will not take. The streamable-HTTP transport instead reads the RAW body's `params._meta` via
`Server::resolve_raw_meta_protocol_context` (`src/server/mod.rs:1429`) and has FULL method coverage.

Therefore, of the six cacheable methods:
  | Method                     | v2 over HTTP | v2 in-process (typed `ClientRequest`) |
  |----------------------------|--------------|---------------------------------------|
  | `resources/read`           | yes          | **YES** — `ReadResource` carries `_meta` |
  | `tools/list`               | yes          | no — `ListTools` has no `_meta` field   |
  | `prompts/list`             | yes          | no                                      |
  | `resources/list`           | yes          | no                                      |
  | `resources/templates/list` | yes          | no                                      |
  | `server/discover`          | yes          | no — internal route, not `ClientRequest`|

`server/discover` rides the crate-private internal-request route (`Server::handle_discover` →
`core::build_discover_response`), NOT the `ClientRequest` dispatch, so its hints come from the
`Cacheable::Yes` named at `core.rs:1794` rather than from `request_is_cacheable`.

**The observable v2 witness** (same mechanism 115-04 uses): `inject_v2_result_envelope` adds
`resultType` ONLY when the resolved era is `Era::V2`, so `resultType`'s presence in the response is
in-band proof that the dispatcher actually resolved v2 — and its absence is proof of v1.
</measured_era_reachability>
