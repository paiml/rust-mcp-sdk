<objective>
Ship SCHM-02 as what it measurably is: a sibling constructor, an era statement in rustdoc, and tests
that prove the existing permissiveness is deliberate **on v2** — with the era observable rather than
assumed.

Purpose: D-05 asked for the "2.15 object-only bridge" to be LOCATED before being relaxed.
115-RESEARCH § Finding 6 located it — **it is not in pmcp's code.** `structured_content` is already
`Option<Value>` (`src/types/tools.rs:565`); both dispatchers (`core.rs:823`, `mod.rs:2215`) hand the
handler's `serde_json::Value` straight through with no shape check; a repo-wide `is_object()` grep
returns zero hits on any structured-content path. The object-only constraint lived in the **v1 spec
text** (`structuredContent?: { [key: string]: unknown }` plus *"Currently restricted to `type:
"object"` at the root level"* on `outputSchema`), and the 2026-07-28 schema removes both
(115-01 measured `$defs.CallToolResult.properties.structuredContent` as an unconstrained value).

So there is **no guard to remove and no derivation to change**. The executor must NOT go looking for
a bridge to dismantle.

**What the cross-AI review changed about this plan — read this before writing a test.** The
pre-review version claimed "v2 through both dispatchers" but its tests would have run as **v1**.
`tests/common/duplex.rs:104-113`'s `call_via_core` passes `None` as the third argument to
`core.handle_request(id, request, None)` — that parameter is `auth_context`, not the protocol context
— and the era is resolved INSIDE the dispatcher from the server's accept-list plus the request's
`_meta`. A `Client`-driven `call_tool` emits no `_meta` protocol-version signal and the default
accept-list excludes `2026-07-28`, so every one of those tests would have proven only pre-existing v1
permissiveness. This plan adds era-aware helpers and makes `Era::V2` **observable in the response**.

Output: `CallToolResult::structured_value`, era rustdoc on `structured_content` and on both
constructors, era-aware helpers in `tests/common/duplex.rs`, and non-object coverage on both
dispatchers on both eras.

**Why `depends_on: ["115-01", "115-02", "115-11"]`:** 115-01 vendors the artifact whose
`structuredContent` shape this plan's rustdoc quotes; 115-11 records the `structured_content_shape`
contract this plan implements (contract-first). 115-02 captures the pre-change v1 goldens — nothing
here changes a wire byte, so that ordering is discipline rather than necessity.

<measured_era_plumbing>
<!-- Measured during the 2026-08-01 `--reviews` replan. This is what makes an era-aware
     in-process helper possible AT ALL, and what bounds which methods it can cover. -->

`ServerCore::handle_request` resolves the era at ingress via
`resolve_ingress_protocol_context(&self.supported_protocol_versions, &request)`
(`src/server/core.rs:3172`, free fn at :3874), which:
  1. returns `Ok(None)` unless the server's accept-list is v2-opted-in
     (`is_v2_opted_in`), AND
  2. reads the per-request signal from `extract_request_meta_value(request)`.

Opt-in APIs, both PUBLIC:
  `ServerCoreBuilder::with_supported_protocol_versions([...])`   src/server/builder.rs:802
  `ServerBuilder::with_supported_protocol_versions([...])`       src/server/mod.rs:3001

The `_meta` key is `pmcp::testing::META_PROTOCOL_VERSION`
(= `"io.modelcontextprotocol/protocolVersion"`, private const at
`src/types/protocol/context.rs:304`, re-exported publicly through `pmcp::testing` — see
`tests/common/v2.rs:78`). The `testing` feature is included in `full`.

⚠ **HARD COVERAGE BOUND — read `src/server/core.rs:3796-3832` before designing any helper.**
`extract_request_meta_value` reads `_meta` from EXACTLY THREE `ClientRequest` variants:
`CallTool`, `GetPrompt`, `ReadResource`. Every other variant — including `ListTools`,
`ListPrompts`, `ListResources`, `ListResourceTemplates` — yields `None` and resolves to the v1
fallback BY DESIGN. The rustdoc there states the reason explicitly: widening those structs with a
`pub` field is a MAJOR semver break (`constructible_struct_adds_field`), so the streamable-HTTP
transport reads the RAW body's `params._meta` instead
(`Server::resolve_raw_meta_protocol_context`, `src/server/mod.rs:1429`) and has full method coverage.

Consequence for THIS plan: `tools/call` IS `_meta`-bearing, so full in-process v2 coverage of
SCHM-02 on both dispatchers is reachable. (Consequence for 115-07: the list methods are NOT, and
that plan routes accordingly.)

`v1_initialize_gate_applies(stateless_mode, era)` (`src/server/core.rs:3925`) returns `false` for
`Some(Era::V2)` — a v2 request needs NO `initialize` handshake, so an era-aware helper can send a
v2 request as the FIRST message on the transport.

`CallToolRequest` is `#[non_exhaustive]` and its `new()` has no `_meta` seam, so a test crate cannot
struct-literal it. Build it through `serde_json::from_value::<ClientRequest>(...)` on the real
wire shape `{"method":"tools/call","params":{"name":…,"arguments":…,"_meta":{…}}}` — that is exactly
what the transport does, and it exercises the D-113-A `_meta` spelling rather than bypassing it.

**The observable v2 witness.** `inject_v2_result_envelope` (`src/server/core.rs:1561`) adds
`resultType` (and `serverInfo`) to a v2 result and returns early on any non-v2 era. So the presence
of `resultType` in the raw `JSONRPCResponse` result object is a POSITIVE, in-band proof that the
dispatcher resolved `Era::V2` for that request — and its absence is proof of v1. That is what turns
"we asserted v2" from a claim into a measurement.
</measured_era_plumbing>
