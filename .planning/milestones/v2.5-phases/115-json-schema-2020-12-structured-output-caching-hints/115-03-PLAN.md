<objective>
Pin schema validation to Draft 2020-12 on v2 — **safely** — and leave v1 behaviourally frozen.

Purpose: SCHM-01, D-01, D-02. The naive implementation of this requirement
(`jsonschema::draft202012::new(schema)`) is a **silent validation bypass**, not a "may validate
differently" surprise: 115-RESEARCH § Finding 1 measured, across five crate versions, that a schema
declaring draft-04/06/07 compiles under the 2020-12 pin into a validator that accepts EVERY instance
— `type`, `required`, `properties`, `enum`, `$ref`, `minimum` and `additionalProperties` are all
dropped. Today's `validator_for` enforces those schemas correctly, so a naive pin would *regress*
working output validation into a no-op. The fix — measured to fully restore enforcement — is to
normalize the document's `$schema` to the 2020-12 URI before compiling under the pin.

This is also the first era branch in a module that has never had one, and the second-order
consequence must be handled in the same change: the process-global validator cache is keyed on schema
text alone, so after the branch a v1 compile and a v2 compile of the same text collide and whichever
era arrives first wins for the process lifetime.

**Two things the cross-AI review added to this plan:**
1. SCHM-01's wasm-clean claim was never tested with validation ENABLED. `Makefile:61`'s `wasm-build`
   runs `--no-default-features --features wasm`, so `jsonschema` is never compiled for wasm32 by any
   gate. This plan adds the explicit
   `cargo build --target wasm32-unknown-unknown --no-default-features --features "wasm,validation"`
   command. It was probed during the `--reviews` replan and PASSES on `jsonschema 0.46` today, so a
   failure after the 0.49 bump is a real finding about 0.49, not about the command.
2. `$schema` normalization is extracted as a PURE function `normalize_schema_dialect`, separately
   testable and separately property-testable (115-09). Behavioural equivalence through
   `schema_mismatch` cannot prove that ONLY `$schema` changed.

Output: `jsonschema` bumped across all three workspace manifests; `Era` usable as a map key;
`output_validation.rs` era-branched with a pure `$schema` normalizer, an uncached compile path and an
era-keyed cache; the two dispatch call sites passing the era; SCHM-01's behaviour fenced by unit
tests including a draft-07 case and an external-`$ref` case.

**Why `depends_on: ["115-01", "115-02", "115-11"]` when nothing here touches the wire:**
115-01 vendors the pinned artifact whose `outputSchema.$schema` declaration this plan's D-02
reasoning cites, and 115-11 records the `output_schema_draft_pin` contract that this plan implements
(contract-first, CLAUDE.md). 115-02 captures the pre-change v1 golden bytes, and D-13 is explicit that
once any field lands they are unrecoverable. Nothing in this plan changes a wire byte, so the 115-02
ordering is discipline rather than necessity — but the discipline is cheap and the alternative is a
golden capture taken on a partially-changed tree.
