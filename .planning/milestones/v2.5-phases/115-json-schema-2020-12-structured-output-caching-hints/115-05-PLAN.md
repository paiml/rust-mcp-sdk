Give the six `CacheableResult` types a place for `ttlMs` / `cacheScope`, add the closed `CacheScope`
enum with the spec's security semantics carried verbatim, add the **cfg-agnostic projection
function** that every dispatcher — native and wasm — will call, and lock the wire spellings against

Purpose: SCHM-03, D-07, D-09, D-10, D-11, D-12. **This plan adds the SLOTS and the PROJECTOR; it does
not wire the projector into the dispatchers** — that is 115-06. The split is deliberate: modelled as
`Option` fields that serialize to nothing when unset, this plan is byte-neutral on both eras and
115-02's golden fixtures must stay green through it.

**The trap this plan exists to avoid:** D-07 says the fields are REQUIRED on the v2 projection. That
is a statement about the **wire**, not the Rust type. 115-RESEARCH § Finding 9 measured the two
designs: `Option` + inject-on-v2 **fails closed** (a missed path just omits a hint on v2), while
non-`Option` + strip-on-v1 **fails open** (a missed path leaks a v2 field onto the v1 wire, breaking
D-11 and the milestone's severability story for Phases 116-119). Model them as `Option`.

**What the cross-AI review changed about this plan.** The pre-review version put `Cacheable` and the
projector in `src/server/core.rs` and treated `WasmMcpServer`'s bypass as merely "missing v2
defaults". That is wrong in direction: `src/server/wasm_server.rs`'s `WasmResource` trait returns
handler-constructed `ReadResourceResult` and `ListResourcesResult` which `wasm_server.rs` serializes
DIRECTLY (`:135`, `:241`, `:248`, `:264`). Once this plan adds `with_ttl_ms` / `with_cache_scope`, a
wasm handler can set a hint that reaches the wasm server's **v1** wire with no strip — a D-11
violation, not a conformance gap. The fix is structural: the projector lives in `src/types/caching.rs`,
which carries no `cfg` and compiles on every target, so 115-06 can call it from `core.rs` AND from
`wasm_server.rs`.

caching-hint slots on six result types, builders on the three handler-reachable types, ~26 in-crate

/**
 * A result that supports a time-to-live (TTL) hint for client-side caching.
 * @internal
 */
export interface CacheableResult extends Result {
  /**
   * A hint from the server indicating how long (in milliseconds) the
   * client MAY cache this response before re-fetching. Semantics are
   * analogous to HTTP Cache-Control max-age.
   *
   * - If 0, The response SHOULD be considered immediately stale,
   *   The client MAY re-fetch every time the result is needed.
   * - If positive, the client SHOULD consider the result fresh for this many
   *   milliseconds after receiving the response.
   *
   * @minimum 0
   */
  ttlMs: number;

  /**
   * Indicates the intended scope of the cached response, analogous to HTTP
   * `Cache-Control: public` vs `Cache-Control: private`.
   *
   * - `"public"`: The response does not contain user-specific data. Any
   *   client or intermediary (e.g., shared gateway, caching proxy) MAY cache
   *   the response and serve it across authorization contexts.
   * - `"private"`: The response MAY be cached and reused only within the
   *   same authorization context. Caches MUST NOT be shared across
   *   authorization contexts (e.g., a different access token requires a
   *   different cache).
   */
  cacheScope: "public" | "private";
}
