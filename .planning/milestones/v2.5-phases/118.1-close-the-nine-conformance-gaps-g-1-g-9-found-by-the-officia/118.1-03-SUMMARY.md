## The XOR rule and the neither branch

**The chosen rule is deterministic-prefer on output and reject on input, and it is stated as ONE sentence** because it covers the XOR and the neither branch together. From the `text` field's rustdoc (`src/types/content.rs:119-136`), quoted verbatim:

> `EmbeddedResource.resource` is `TextResourceContents | BlobResourceContents` (`schema.ts:1734-1748`), an XOR: exactly one of `text` or `blob` reaches the wire. The emitter follows one rule: **`blob` is emitted only when `blob` is `Some` and `text` is `None`; otherwise `text` is emitted, using the empty string when it is `None`.**
>
> So a value carrying NEITHER serializes as `{"type":"resource","resource":{"uri":"u","text":""}}`, a valid `TextResourceContents`, and never as an object matching no arm of the union.

And from the `blob` field's rustdoc:

> On INPUT a payload carrying BOTH `text` and `blob` is REJECTED with a deserialization error, because the spec type is an XOR and an object carrying both is out of contract.

**Why reject on input but resolve on output.** Rejecting at INPUT is the mitigation for T-118.1-03-01: a hostile payload carrying an innocuous `text` beside a malicious `blob` is refused at the parse boundary rather than being handed to a consumer that inspects only one of them. Refusing at OUTPUT would be different in kind and worse: D-03's tolerant reader accepts the legacy flat shape, and a relay such as `src/composition/mcp_client.rs` or `crates/mcp-tester` that deserializes then re-serializes would fail at RESPONSE time, turning a compatibility affordance into a runtime fault on the serving path. The same argument is why the neither branch emits `text: ""` rather than erroring — a value the reader may legitimately produce must always be emittable.

The rule's implementation is a single function, `embedded_resource_union` (`src/types/content.rs:250-262`), whose `(None, None) => (Some(""), None)` arm is the neither branch. `test_content_resource_neither_branch_emits_an_empty_text_arm` asserts the exact bytes `{"type":"resource","resource":{"uri":"file://test.txt","text":""}}`, and `test_emitter_resolves_text_and_blob_deterministically_to_text` asserts the XOR resolution.

## The implementation, in outline

**Emitter.** `Content`'s derived `Serialize` is replaced by a hand-written impl over `WireContentOut<'a>`, a BORROWED shadow enum. Only the `Resource` arm is hand-shaped; `Text`, `Image`, `Audio` and `ResourceLink` are delegated to the derived shadow carrying the pre-2.19.0 serde attributes verbatim, so their bytes cannot drift. `test_non_resource_arms_are_byte_identical_to_the_previous_derive` asserts all four.

Every field of `WireResourceContentsOut<'a>` borrows (`&'a str`, `&'a Option<String>`, `Option<&'a str>`), mirroring the existing `Rc<'a>` shadow in `resource_contents_serde`, **so a base64 blob is never deep-cloned per tool result. `#[serde(into = "…")]` was NOT used and was not needed** — the borrow was straightforward, so the plan's fallback clause never came into play.

**Reader.** `#[serde(try_from = "WireContentIn")]`. The `Resource` arm's payload is a single struct with an optional `resource` and an optional `uri` — **not** a `#[serde(untagged)]` pair. The plan suggested untagged "e.g."; a single struct is strictly better here and eliminates RESEARCH assumption A1 rather than testing around it. An untagged enum disambiguates by trying arms in declaration order, which makes two silent failure modes reachable: a payload satisfying both arms is resolved by declaration order with no diagnostic, and a payload satisfying neither reports `data did not match any variant`, destroying the field-level reason. Both are threat T-118.1-03-03 exactly. With one struct the choice is explicit and total: `resource` present ⇒ the spec's nested shape; else `uri` present ⇒ the legacy flat shape; else a `missing field \`uri\`` error, which is also the message the derive used to produce (`test_tolerant_reader_rejects_a_payload_with_no_uri_at_all` pins it). A hybrid payload carrying both keys resolves to the SPEC shape, deterministically, because that branch is tested first.

**Error messages.** The plan's first named hazard — `try_from` changing deserialization error text — was checked: `git grep 'from_value::<Content>\|from_str::<Content>' -- src tests` finds exactly two sites, `src/server/task_dispatch.rs:911` (uses `.is_ok()`, no text) and `src/types/content.rs:388` (the flat projection, which wraps whatever comes back). No assertion on `Content` deserialization error text exists anywhere, so nothing flipped. The second hazard — `Content` inside a `#[serde(untagged)]` enum or behind `#[serde(flatten)]` — was also checked: none of the nine `serde(untagged)` enums or seventeen `serde(flatten)` fields in `src/` involves `Content`.

## Decisions Made

- **One sentence for the whole union.** Rather than a separate XOR rule and a separate neither-branch rule, the emitter has a single total rule with three arms in one function. It is quoted identically in the field rustdoc, the function rustdoc and the CHANGELOG, so there is one statement to keep true instead of three.
- **Reject the XOR on input, resolve it on output.** See § The XOR rule above. The asymmetry is deliberate and its rationale is recorded because a future reader will otherwise "fix" the inconsistency and reintroduce a runtime fault on the relay path.
- **A single struct, not `#[serde(untagged)]`.** Removes the plan's own named unproven assumption (A1) by construction. The rustdoc on `WireResourceIn` carries the reasoning so it is not re-litigated.
- **`Content::with_meta` added.** Not in the plan. `#[non_exhaustive]` makes `meta` unsettable from outside the crate, and the MCP Apps scaffold template sets it — without this builder, `cargo pmcp new --kind mcp-app` would emit crates that cannot compile. Adding a public fn is MINOR and adds nothing to the D-15 delta.
- **`with_annotations` / `with_meta` cover `Resource`, `Audio` AND `ResourceLink`.** All three model the field; `Text` and `Image` do not and are returned unchanged, stated in the rustdoc. The match is exhaustive without a wildcard, so a future variant carrying annotations cannot be silently skipped.
- **Property tests live in the normal `--lib` run**, following `types::caching`, not behind `--ignored`. `make test-property` runs `cargo test -- --ignored property_`, so an `#[ignore]`d property test is invisible to `cargo test` AND reachable only by that one target; the `caching` module's own comment records that trade.
- **The `[2.19.0]` CHANGELOG section is new**, ahead of a Cargo.toml bump. The repo already carries three unreleased sections (2.16.0, 2.17.0, 2.18.0) against a Cargo.toml at 2.18.0, so the CHANGELOG leading the version is established practice here, and the `#[deprecated(since = "2.19.0")]` attribute has to name a version.
