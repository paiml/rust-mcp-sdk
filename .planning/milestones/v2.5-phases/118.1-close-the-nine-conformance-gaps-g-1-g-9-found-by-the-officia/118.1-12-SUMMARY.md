### Assertions read `Resp.raw`, not `Resp.body` — quoted

`Resp.body` is SSE-UNWRAPPED (it returns the FIRST parseable `data:` payload), so
it cannot see frame count or frame order. The frame-order assertion, verbatim:

```rust
let all = frames(&response.raw);
let result_index = all
    .iter()
    .position(|f| f.get("result").is_some() || f.get("error").is_some())
    .unwrap_or_else(|| panic!("no result frame on the stream; raw: {}", response.raw));
assert_eq!(result_index, all.len() - 1, "the result frame must be LAST; raw: {}", response.raw);
for (index, frame) in all.iter().enumerate().take(result_index) {
    assert_eq!(
        frame.get("method").and_then(Value::as_str),
        Some("notifications/progress"),
        "frame {index} before the result must be a progress notification; raw: {}",
        response.raw
    );
}
```

`frames()` itself parses every `data:` line off `raw` in wire order — the whole
file's decoding goes through it, so no assertion in the file can accidentally
consult `body`.

### T-118.1-12-02 — the no-independent-requests constraint is a TYPE, quoted

```rust
enum V2ResponseFrame {
    /// A one-way notification — today only `notifications/progress`.
    Notification(crate::types::Notification),
    /// The terminal result frame, carrying the LIVE request id (HTTP-05).
    Result(crate::types::JSONRPCResponse),
}
```

There is no request arm, so an independent server-to-client request on a v2
response stream is unrepresentable. Contrast `TransportMessage`, which carries
`Request { id, request }` and is therefore deliberately NOT the stream's item
type. The projection is one-directional:

```rust
fn into_transport_message(self) -> TransportMessage {
    match self {
        Self::Notification(notification) => TransportMessage::Notification(notification),
        Self::Result(response) => TransportMessage::Response(response),
    }
}
```

Nothing maps back, so the missing arm cannot be reintroduced through this seam.
`no_independent_request_frame_on_the_stream` is the wire-level guard that the
type-level control actually reaches the wire.

### T-118.1-12-01 — the queue is BOUNDED

```bash
$ git grep -n 'unbounded_channel' src/server/streamable_http_server.rs
src/server/streamable_http_server.rs:2362:/// `build_sse_response_from_single_message` uses `mpsc::unbounded_channel`; that
src/server/streamable_http_server.rs:2637:    let (tx, rx) = mpsc::unbounded_channel();
```

Two hits, and only ONE is code. `:2637` is inside
`build_sse_response_from_single_message`, the pre-existing exactly-one-message
helper, where an unbounded channel that receives exactly one send is sound.
`:2362` is a rustdoc line on `V2_PROGRESS_QUEUE_CAPACITY` stating that this
helper's choice is deliberately NOT copied. Neither is on the new multi-frame
path, which uses:

```rust
pub const V2_PROGRESS_QUEUE_CAPACITY: usize = 64;
// ...
let (tx, receiver) = mpsc::channel(V2_PROGRESS_QUEUE_CAPACITY);
```

The rustdoc states the number (64 — the scenario asks for three, and a
rate-limited handler emits ten per second, so 64 is ~6 s of well-behaved
reporting) and the overflow policy (**DROP-NEWEST**: the producer is a
synchronous `Fn(Notification)` that cannot await, so `try_send` drops and warns
rather than blocking or growing). Both are asserted directly, bypassing
`ServerProgressReporter` so the rate limiter is not the thing under test:

- `the_progress_queue_is_bounded_at_its_stated_capacity` pushes
  `CAPACITY + 500` and asserts the drain length is exactly `CAPACITY`
- `the_overflow_policy_is_drop_newest` pushes `CAPACITY * 2` and asserts the last
  survivor is frame `CAPACITY - 1` — i.e. the EARLIEST frames are kept

### T-118.1-12-03 — termination

The multi-frame body is a COMPLETE buffer before axum sees it: dispatch is awaited
before the response is assembled, so the handler has finished and the queue is
drained with `try_recv`. There is no long-lived stream, no keep-alive to schedule,
and the stream terminates on the result frame because the result frame is the last
byte written. This is also why the middleware twin needed no streaming contract.

### T-118.1-12-05 — content negotiation

Eligibility is decided BEFORE dispatch, so an ineligible request never allocates a
queue:

```rust
era == Some(Era::V2)
    && !state.config.enable_json_response
    && accept.is_some_and(|accept| accept.contains(TEXT_EVENT_STREAM))
```

Covered by `json_only_accept_keeps_a_json_response` and
`json_mode_server_never_emits_sse`.

### Judgement calls worth flagging

**The A3 scratch server is Node, not Rust.** The plan said "a small scratch v2
server" without naming a language. Node was chosen deliberately: A3 is a question
about the REFEREE's client, and answering it with pmcp would have confounded the
referee's behaviour with pmcp's own (which emitted `text/event-stream` on no POST
at all at that moment). A Rust probe could not have separated "the suite rejects
this vehicle" from "pmcp emitted it wrongly". The scratch server is preserved at
`target/118.1-12-a3-scratch-server.mjs` and quoted in the frame record above.

**The multi-frame body is a buffer, not a stream.** The plan described "a builder
that holds the channel open, forwards queued frames as they arrive, then sends the
final result frame". Measurement showed that is unnecessary and strictly worse:
dispatch is awaited before the response is assembled, so every frame is already
queued. Draining makes the frame order deterministic, removes the keep-alive
question entirely, satisfies T-118.1-12-03 structurally rather than by mitigation,
and is what lets the middleware twin work at all (middleware requires a complete
`Vec<u8>` body). The plan's `X_ACCEL_BUFFERING` and `Cache-Control` treatment is
still applied.

**The framing is hand-rendered, against the plan's "reuse the framing exactly".**
Same reason — the middleware path needs bytes and axum's `Event` exposes no
serializer. Rather than run two different renderers on the two paths (a real drift
risk), there is ONE renderer and a test,
`the_hand_rendered_framing_matches_axum_event`, that pins it byte-for-byte against
what `build_sse_response_from_single_message` actually produces through axum,
modulo the per-frame uuid. That is a stronger control than reusing the type would
have been, because it is measured rather than assumed.
