<objective>
Close G-9: make `RequestHandlerExtra::client_capabilities()` return the capabilities a v1 client
advertised in its `initialize` handshake, at EVERY handler-dispatch construction site, so a
server-side capability gate reads the same value under v1 as under v2.

Purpose: the v1 handshake writes to `*self.client_capabilities.write().await` (`src/server/mod.rs:1684`),
a server-level `RwLock`. The handler reads `protocol_context.client_capabilities`
(`src/server/cancellation.rs:406-410`), which `resolve_protocol_context` populates ONLY from the v2
`_meta` key. The two never meet, so any v1 capability gate reads permanently `false`.

Output: a one-directional fold at every construction site, a per-handler-kind test, and an explicit
disposition for every site including the ones where no context exists.
</objective>

    fold is ONE-DIRECTIONAL: it must never overwrite a value the v2 `_meta` path already supplied.
    State that precedence in a comment at the fold, and let the v2 non-regression test prove it.

    Prefer ONE shared helper called from both dispatchers over nine copies — this is the twin-site
    parity rule, and nine copies of a lock read is exactly the drift this repo keeps paying for. A
    small `pub(crate)` function in `core.rs` taking the current `Option<ProtocolContext>` plus the

    unavoidable at some site, that site carries a comment naming its twin's file and line.

    Do NOT make `client_capabilities()` read the server lock directly. It is a sync method on a value
    that is moved into the handler, and the dispatch path already holds the lock — that shape
    deadlocks.

    `RwLock` inside a hot dispatch path repeatedly is both a contention cost and a correctness
    hazard if the value can change mid-dispatch.

    signature. If a public signature change is unavoidable, stop and record it as a DEFERRED
