## Key Critical & Major Findings

### 1. Major Architectural Gap: `RequestHandlerExtra::with_peer` is Unreachable from HTTP Dispatch (Plan 11)
* **Plan Claim (`118.1-11-PLAN.md:33-36, 108-121`):**  
  Plan 11 states that the HTTP dispatch path (`src/server/streamable_http_server.rs:3001-3005`) will construct a session-bound peer handle per request and inject it via `RequestHandlerExtra::with_peer(...)` after tool-level authorization.
* **Source Code Verification (`src/server/streamable_http_server.rs:3001-3005`, `src/server/mod.rs:1634`, `src/server/mod.rs:2084`, `src/server/core.rs:638`):**  
  In `streamable_http_server.rs:3001-3005`, `dispatch_request_or_retire` invokes:
  ```rust
  let server = state.server.lock().await;
  server.handle_request_with_context(id, request, auth_context, protocol_context).await
  ```
  The signature of `handle_request_with_context` in [`src/server/mod.rs:1634`](file:///Users/guy/Development/mcp/sdk/rust-mcp-sdk/src/server/mod.rs#L1634) is:
  ```rust
  pub(crate) async fn handle_request_with_context(
      &self,
      id: RequestId,
      request: Request,
      auth_context: Option<AuthContext>,
      protocol_context: Option<ProtocolContext>,
  ) -> JSONRPCResponse
  ```
  `RequestHandlerExtra` is **instantiated internally** deep inside `Server::call_tool_with_context` ([`src/server/mod.rs:2084`](file:///Users/guy/Development/mcp/sdk/rust-mcp-sdk/src/server/mod.rs#L2084)) and `ServerCore` ([`src/server/core.rs:638`](file:///Users/guy/Development/mcp/sdk/rust-mcp-sdk/src/server/core.rs#L638)) where `self.attach_peer(...)` is called. `self.attach_peer` attaches `Server::peer_handle` (the single global handle).  
  The HTTP dispatch entrypoint has **no parameter seam** to pass a `RequestHandlerExtra` or a custom per-request `PeerHandle` into `handle_request_with_context`!
* **Impact:** As currently designed in Plan 11, calling `with_peer` at the HTTP dispatch site in `streamable_http_server.rs` is impossible because `RequestHandlerExtra` is not constructed or accessible at that call site.
* **Required Remediation:**  
  Update `handle_request_with_context` (and `call_tool_with_context` / `ServerCore`) to accept an optional `peer_handle: Option<Arc<dyn PeerHandle>>` parameter (or extend `ProtocolContext` to carry a session-bound `PeerHandle`), allowing `streamable_http_server.rs` to pass the session-bound handle into the tool execution context.

### 2. Major Technical Defect: `ServerRequestDispatcher` Outbound Channel Missing `session_id` Context (Plans 10 & 11)
* **Plan Claim (`118.1-10-PLAN.md:88-95, 227-242` & `118.1-11-PLAN.md:108-125`):**  
  Plan 10 Task 2 creates `ServerRequestDispatcher::new_with_channel(tx)` with an `mpsc::channel::<(String, ServerRequest)>(100)` and states that the background drain task in `peer_channel.rs` will read `(correlation_id, ServerRequest)` off the channel and call `v1::route_to_session_stream(&state.v1, session_id, message)` for the originating session.
* **Source Code Verification (`src/server/server_request_dispatcher.rs:70, 98-128`):**  
  In [`src/server/server_request_dispatcher.rs:109-134`](file:///Users/guy/Development/mcp/sdk/rust-mcp-sdk/src/server/server_request_dispatcher.rs#L109-L134), `ServerRequestDispatcher::dispatch` takes only `ServerRequest`, generates `correlation_id` via `Self::next_correlation_id()` (which outputs `"dispatch-1"`, `"dispatch-2"`, etc., line 100), and pushes `(correlation_id, request)` onto `outbound_tx`:
  ```rust
  let correlation_id = Self::next_correlation_id(); // "dispatch-1"
  self.outbound_tx.send((correlation_id.clone(), request)).await
  ```
  `ServerRequestDispatcher` has **zero knowledge of HTTP `session_id`**! The tuple emitted on `outbound_tx` is `(String, ServerRequest)` where `String` is purely `"dispatch-N"`.
* **Impact:** When `peer_channel.rs` pops `(correlation_id, ServerRequest)` from `outbound_tx`, it has **no `session_id` attached** and cannot determine which session's SSE stream should receive the message!
* **Required Remediation:**  
  Either:
  1. Encode the `session_id` into the `correlation_id` string when minting (e.g. `format!("{session_id}:{correlation_id}")`), or
  2. Maintain a lookup map (`HashMap<correlation_id, session_id>`) inside `peer_channel.rs` when initiating requests, or
  3. Generalize `ServerRequestDispatcher` or supply a session-keyed channel payload wrapper `(session_id, correlation_id, ServerRequest)`.

### 3. Stream Consumption Hazard: Pre-Auth JSON-RPC Response Classifier in Axum (Plan 10)
* **Plan Claim (`118.1-10-PLAN.md:301-305, 313-328`):**  
  Plan 10 Task 3 states: "Classify a JSON-RPC RESPONSE envelope at the very TOP of `handle_post_request`, before `resolve_v2_gate` and before `extract_and_validate_auth`."
* **Source Code Verification (`src/server/streamable_http_server.rs:2030-2044, 3593-3604`):**  
  `handle_post_request` in [`src/server/streamable_http_server.rs:2030`](file:///Users/guy/Development/mcp/sdk/rust-mcp-sdk/src/server/streamable_http_server.rs#L2030) receives `request: axum::extract::Request<Body>`. In Axum, `Body` is a single-pass stream. Reading the body bytes to parse JSON at the top of `handle_post_request` consumes the `request`. If the payload is a standard JSON-RPC Request or Notification (not a Response), `request` can no longer be passed down to `handle_post_fast_path` or `handle_post_with_middleware`.
* **Impact:** Attempting to read `request` before buffering `Bytes` will consume the stream and break all subsequent POST request processing.
* **Required Remediation:**  
  Body buffering MUST use `axum::body::to_bytes` (mirroring `read_and_classify_fast` at [`src/server/streamable_http_server.rs:3604`](file:///Users/guy/Development/mcp/sdk/rust-mcp-sdk/src/server/streamable_http_server.rs#L3604)) to yield reusable `Bytes`, or the response envelope classifier must be invoked directly inside/immediately following `read_and_classify_fast`.

### Conclusion & Verdict
The implementation plans `118.1-01` through `118.1-14` are **conceptually sound, meticulously detailed, and spec-compliant**, but **Plans 10 and 11 require the three interface adjustments noted above** prior to executing Waves 8 and 9.

### Agreed Concerns (raised independently by BOTH — highest priority)

**1. HIGH — G-3 has no implementable peer-injection seam. (Codex HIGH#2, Gemini Finding#1+#2)**

This is the strongest signal in the review: two reviewers converged on it from different
directions, and the orchestrator confirmed it at source.

- Plan 11 line 123 instructs "inject via `RequestHandlerExtra::with_peer(...)` at the HTTP
  dispatch site." That site is `streamable_http_server.rs:3001-3004`, which calls
  `handle_request_with_context(id, request, auth_context, protocol_context)` — four
  parameters, **no peer seam**.
- `RequestHandlerExtra::new` is constructed only inside `src/server/core.rs` (639, 907, 931,
  981); the peer is applied by `attach_peer` (`core.rs:532`, `mod.rs:1205-1217`) from the
  single global `Server::peer_handle`.
- Plan 10 mandates `mpsc::channel::<(String, ServerRequest)>` (line 228), then its drain
  (line 242) calls `route_to_session_stream(&state.v1, session_id, message)` using a
  `session_id` **that is not in that tuple**. `ServerRequestDispatcher::dispatch` mints
  `"dispatch-{N}"` and carries no session identity in either the channel or the pending map.

Mitigating nuance: plan 10 lines 248-255 *does* name session-to-correlation binding as "the
security-critical part," explicitly rejects the single global handle (citing defect T-113-07),
and asks the executor to choose and record one of two shapes. So the plan is **internally
inconsistent** rather than oblivious — it mandates a concrete channel type that cannot carry
the binding its own drain snippet requires.

Remediation: thread session identity through the outbound item and pending ownership, and pass
a session-bound peer into `Server::handle_request_with_context` (new parameter, or extend
`ProtocolContext`).
