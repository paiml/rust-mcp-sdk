<decisions>
## Implementation Decisions

### G-1 / G-2 — the embedded-resource wire format

**Root cause, established during discussion and not previously written down:**
`Content::Resource` is doing double duty for two *different* spec types.
`ReadResourceResult.contents` already gets a custom projection
(`resource_contents_serde`, `src/types/content.rs:325`) that strips the `type` tag and emits
flat `uri`/`text`/`mimeType` — and that is **spec-correct**, because `ResourceContents` *is*
flat (`schema.ts:1514-1560`). The defect is only in the *other* position:
`CallToolResult.content` and `GetPromptResult.messages[].content`, where the derived
`Serialize` emits that same flat shape but the spec wants
`EmbeddedResource { type: "resource", resource: TextResourceContents | BlobResourceContents }`
(`schema.ts:1734-1745`).

- **D-01: Fix the default; keep the flat projection.** `Content::Resource`'s derived
  `Serialize` emits the spec `EmbeddedResource` shape; `resource_contents_serde` keeps emitting
  flat for `ReadResourceResult`. Both positions become spec-correct on both eras. **The Rust
  API is unchanged** — all 130 call sites keep compiling; only emitted bytes change. G-2 (blob)
  is the same edit, because `resource` is `TextResourceContents | BlobResourceContents`.
  - `_meta` and `annotations` sit at the **content level** in the spec, *outside* `resource`
    (`schema.ts:1740-1744`). The MCP Apps widget path that destructures `{ uri, meta, .. }`
    reads `_meta` at content level and is therefore already correct — nesting `resource` does
    not disturb it.
- **D-02: Ships as a 2.x minor, as a conformance FIX.** pmcp is at 2.18.0 and v2.5 is declared
  additive/no-3.0; that promise holds. The Rust API semver contract is unbroken, and reliance
  on the flat shape was reliance on a bug that made pmcp incompatible with every other MCP
  implementation. Requires a prominent CHANGELOG wire-change callout and a migration note.
  **No opt-out escape hatch.**
- **D-03: Tolerant reader, strict emitter.** Accept BOTH nested and flat on input; emit only
  nested. This also fixes a **second defect found during discussion that the suite could not
  have caught**: `Content` has only the derived `Deserialize` (no manual impl), so with
  `#[serde(tag = "type")]` and a required top-level `uri`, a spec-conformant
  `{"type":"resource","resource":{...}}` from any other SDK's server **fails to parse today** —
  pmcp as a *client* cannot read a conformant embedded resource. The suite tests pmcp as a
  server, which is why this never surfaced. The tolerance is a documented compatibility
  affordance, not a second supported format.
- **D-04: Fenced by spec-derived byte literals + the suite as external oracle.** Extend the
  `tests/v1_lists_golden.rs` byte-literal pattern to the tool-result and prompt-message
  embedded-resource positions on BOTH eras, with expected bytes **derived from the vendored
  `schema.ts`, not from pmcp's own serializer output**. Add a flat-input round-trip test for
  the tolerant reader. **Each fence must be demonstrated RED against the unfixed tree before
  the fix lands.**
  - *Why this matters:* `cargo semver-checks` and `cargo public-api` are **structurally blind**
    here — they read the Rust API surface, and D-01 changes no signature. The milestone's
    Pitfall-5 semver guard will pass green on a wire break. So will the existing goldens:
    `v1_lists_golden.rs` pins `tools/list`, `prompts/list`, `resources/list`,
    `resourceTemplates/list` and `resources/read`, but **nothing pins a tool result carrying an
    embedded resource** — the blind spot sits exactly where the fix lands.
  - Known test to flip: `test_content_resource_meta_serialization` (`src/types/content.rs`)
    asserts `json["uri"]` at top level.

### Scope and batching

- **D-05: One phase, five waves by cluster.** (1) content types G-1+G-2, (2) dispatch G-4+G-5,
  (3) v2 error codes and discover G-6+G-7+G-8, (4) HTTP server→client back-channel G-3,
  (5) v1 capability plumbing G-9. Conformance re-measurement happens **once at the end over the
  union**, so the phase has one coherent, defensible before/after.
- **D-06: `set_result_meta` and `annotations` are in scope.** The `set_result_meta` drop on the
  `ToolOutput::Result` verbatim path is not a conformance gap but is load-bearing — G-3's
  elicitation wiring runs straight through that path, so fixing G-3 without it may only
  relocate the failure. `annotations` is a spec field `Content::Resource` lacks, and D-01 is
  rewriting exactly that type's serialization.
- **D-07: `PeerHandle::elicit` is in scope.** G-3 is really *the whole server→client
  back-channel over HTTP* — it blocks `tools-call-with-progress` (progress notifications via
  `notification_tx`) and server→client `sampling/createMessage` and `roots/list` (via
  `peer_handle`). The seam that makes sampling and roots work is the same one `elicit` uses;
  excluding it would leave G-3's elicitation scenarios red while its siblings go green.
- **D-08: Hold the suite pin at 0.2.0-alpha.11 for the fix work; re-pin as the FINAL task.**
  Fix against the exact referee that measured the baseline so the delta is attributable to the
  SDK alone. Then bump to the newest release, re-measure once, and report the bump's delta
  **separately** from the fixes' delta. Two clean numbers, not one confounded one.

### Exit criteria and the gate

- **D-09: Per-gap proof, then widen the gate to what genuinely passes.** Each of the nine needs
  a **named scenario or test demonstrably flipped RED→GREEN**, plus a stated before/after on
  both legs. The blocking gate then widens to cover exactly the surfaces that pass after
  re-measurement. **D-21 is carried forward verbatim: no `--expected-failures`, no allowlist,
  no known-failure baseline.**
  - **A pass-count assertion may become available and is deferred to measured evidence.** The
    v2 oscillation (124/54 ↔ 123/55) has a single proximate cause: `http-header-validation`'s
    `ServerAcceptsWhitespaceHeaderValue` picks a tool out of `tools/list`, and when it picks an
    elicitation tool the call errors with *"no server→client channel on this transport"* — G-3
    exactly (`118-08-SUMMARY.md:519-529`). Closing G-3 **plausibly** removes that
    nondeterminism, which reopens the question D-21 closed. Treat it as a prediction to
    measure, never as a planning assumption. Decide it AFTER re-measurement.
- **D-10: Three-state disposition, with a blocking sign-off on any non-FIXED verdict.** Every
  gap ends in exactly one of **FIXED** (named RED→GREEN proof), **REFUTED** (measured evidence
  it was never a defect — as already happened to `negotiate_protocol_version`), or **DEFERRED**
  (named residual with an owner and a stated reason). **None may end silently.** Any REFUTED or
  DEFERRED verdict additionally requires a `checkpoint:human-verify gate="blocking"`, the
  pattern Phases 114 and 115 used. `118-CONFORMANCE-GAPS.md` is **AMENDED** with each
  disposition, never rewritten.
  - *Why:* Phase 118's own planning premise was **false** — RESEARCH assumed missing fixtures
    and measurement found structural defects. The same can happen to any of these nine.
- **D-11: Wire goldens bounded to what the nine touch.** Embedded resource in tool and prompt
  positions, the v2 error-code responses for G-6/G-8, `server/discover`'s `supportedVersions`
  for G-7. Each golden cites the `schema.ts` line it was derived from, so the derivation is
  auditable. NOT generalized to a full wire-conformance suite; NOT codegen'd.

### Post-research decisions (2026-08-10, resolved with user before planning)

Research (`118.1-RESEARCH.md`) surfaced two findings that contradicted or extended the locked
decisions above. Both were resolved with the user before the planner ran. These are LOCKED with
the same force as D-01..D-14.

- **D-15 (amends D-01/D-02 for G-2/annotations): batch + `#[non_exhaustive]` + constructors,
  with a documented semver delta.** Research measured (`cargo semver-checks 0.49.0 --list`) that
  NO representation of G-2's `blob` or D-06's `annotations` on the exhaustive public `Content`
  enum is additive — `enum_struct_variant_field_added`, `enum_variant_added`, and
  `enum_variant_marked_non_exhaustive` are ALL major. The decision: one batched edit adds
  `blob` + `annotations`, marks `Content::Resource` `#[non_exhaustive]` in the same commit (so
  all FUTURE spec fields become minor), and ships constructors
  (`Content::resource_with_blob`, `.with_annotations`) — mandatory, not optional, because
  `#[non_exhaustive]` makes external struct-literal construction impossible. The accepted
  `cargo semver-checks` delta is recorded EXPLICITLY in the phase gate as a one-time documented
  conformance exception — it must never read as an unnoticed regression. D-01's "Rust API
  unchanged" is amended to: unchanged for the nesting (G-1); extended with a one-time documented
  delta for blob/annotations (G-2/D-06). D-02's 2.x ship holds.
  **Tripwire for plans:** a Wave-1 acceptance criterion asserting
  "`cargo semver-checks` no update required" is UNSATISFIABLE under this decision — its presence
  in a plan means the decision was ignored.
- **D-16 (scopes G-3's v2 half IN): multi-frame SSE on the POST response, both legs.**
  `tools-call-with-progress` is red on BOTH legs, and v2 has no session stream — the only
  vehicle is an SSE-formatted POST response body, which pmcp never emits today. The fix
  generalizes the existing `build_sse_response_from_single_message` helper to a stream that
  emits queued `notifications/progress` frames then the final result frame, constrained exactly
  as the suite's `HttpServerNoIndependentRequestsOnStream` demands: notifications + result
  frames ONLY, never an independent server→client request — those stay MRTR on v2. Phase 117's
  "no session/SSE baggage on v2" is not violated: this is a response-body format on a single
  POST, not session state or resumability.
