**`server/discover` now advertises the spec-required `supportedVersions`, sourced from the SAME `Server::supported_protocol_versions()` slice that an unsupported-version rejection reports as `error.data.supported` — with the single-source rule enforced by the compiler, not by convention.**

## Decisions Made

1. **`#[serde(default)]` was added, which the plan did not specify.** The plan required non-`Option`
   and no `skip_serializing_if`; both hold, and emission is unconditional. `#[serde(default)]`
   affects DESERIALIZATION only. Without it, adding a required field to a `Deserialize` struct
   makes `Client::server_discover` hard fail against any peer that omits it — an avoidable
   interop regression, and the inverse of the phase's own D-03 tolerant-reader/strict-emitter rule.
2. **The golden fixture names a real two-entry accept list**, so it pins that `supportedVersions`
   reproduces the caller's list in order rather than some derived value. The two capability-only
   projection tests use the `#[cfg(test)]` conversion, which is exactly its documented purpose.
3. **The `#[cfg(test)]` conversion advertises an EMPTY list, not a plausible default.** A test that
   ends up reading `supportedVersions` through it fails loudly on `[]` instead of passing against a
   real-looking list it never asked for.

## Deviations from Plan

### 1. [Rule 3 — Blocking issue] The plan's threading design collided with plan 06's file; redesigned to avoid the edit

- **Found during:** Task 2.
- **Issue:** The plan prescribed "`discover_result_from_capabilities` gains a parameter carrying
  the accept list; `build_discover_response` gains one and passes it through." The plan's author
  believed `build_discover_response` had exactly one caller (`Server::handle_discover`). **It has
  two.** `src/server/streamable_http_server.rs:6727` — inside plan 06's file — calls it directly
  from the `#[cfg(test)]` helper `projected_capabilities`. Adding a 5th parameter would have
  broken that call site, and Rust has no default arguments, so **every** arity-changing design
  required editing a file this executor was instructed not to touch.
- **Fix:** Bundled the two values into a new `pub(crate) struct DiscoverSource<'a> { capabilities,
  supported_versions }` and made `build_discover_response`'s second parameter
  `impl Into<DiscoverSource<'a>>`. Plan 06's call site keeps compiling unchanged (it passes
  `&ServerCapabilities`), while `Server::handle_discover` passes an explicit
  `DiscoverSource::new(&self.capabilities, self.supported_protocol_versions())`.
  The `From<&ServerCapabilities>` conversion is `#[cfg(test)]`, which is what upgrades the
  single-source rule from a convention to a compile-time guarantee: in a non-test build that impl
  does not exist, so **there is no way to call `build_discover_response` without naming an accept
  list**.
- **Files modified:** `src/server/core.rs`, `src/server/mod.rs` (both mine). **Zero edits to
  `src/server/streamable_http_server.rs`, `src/types/protocol/context.rs`, or
  `tests/v2_meta_validation_codes.rs`** — verified by `git diff --stat`.
- **Verification:** `cargo build --features full --tests` clean; plan 06's
  `discover_projection_and_listen_gate_read_the_same_predicate` passes untouched.
- **Committed in:** `bf3b49f7`.

### 2. [Rule 3 — Blocking issue] `src/types/caching.rs` needed the new field, and is outside the plan's declared file list

- **Found during:** Task 2.
- **Issue:** `src/types/caching.rs:696` constructs `ServerDiscoverResult` with a struct literal
  inside a `#[cfg(test)]` fixture. Adding a required field broke the test build (`E0063`). The
  plan's `files_modified` did not list this file; it is not plan 06's either.
- **Fix:** Added `supported_versions: Vec::new()` with a comment stating why the accept list is
  irrelevant to that fixture (it asserts the ABSENCE of unset cache hints).
- **Verification:** test build clean; the fixture's own assertions still pass in the 3048-test run.
- **Committed in:** `bf3b49f7`.
