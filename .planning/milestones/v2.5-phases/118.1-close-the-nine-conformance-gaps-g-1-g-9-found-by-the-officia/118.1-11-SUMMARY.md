### The SSE wire encoding was wrong, and the fence caught it in one step

With the peer wired, all five round trips still failed — but with a NEW diagnosis. The frame on the
wire was:

```json
{"id":"dispatch-1","request":{"method":"sampling/createMessage","params":{...}}}
```

not a JSON-RPC request. `sse_event_for_message` was calling `serde_json::to_string(msg)` on an
`#[serde(untagged)]` `TransportMessage`. `serialize_message`'s own rustdoc had already named this
exact hazard — *"serializing the untagged `TransportMessage` enum directly would instead emit
`{"id":…,"request":…}`, which no MCP server can parse"* — and the SSE writer was the one encoder
that did not use it.

It stayed latent because only `TransportMessage::Response` had ever reached a v1 SSE stream, and for
that variant the two encodings are byte-identical. Plan 10 added an outbound REQUEST path and this
plan adds a NOTIFICATION path; both are broken under the raw encoding, and a `Notification::Progress`
would have serialized as a bare params object with no `method` and no `jsonrpc` at all — so
`notifications/progress` would never have been observable regardless of the reporter wiring. Fixed
in `src/server/streamable_http_server/v1_session.rs` with a table in the rustdoc showing where the
two encodings agree and where they do not. After the fix all six original fence tests went green in
one run.

### Task 2: the reporter, and why `progress_notify` alone would have been a green plan and a red scenario

`src/server/mod.rs:1288-1302`:

```rust
    fn progress_notification_sink(
        &self,
        #[cfg_attr(target_arch = "wasm32", allow(unused_variables))]
        protocol_context: Option<&crate::types::protocol::ProtocolContext>,
    ) -> Option<Arc<dyn Fn(Notification) + Send + Sync>> {
        #[cfg(not(target_arch = "wasm32"))]
        if let Some(sink) = protocol_context
            .and_then(crate::types::protocol::ProtocolContext::transport_backchannel)
            .and_then(crate::types::protocol::context::TransportBackchannel::notification_sink)
        {
            return Some(Arc::clone(sink));
        }
        let tx = self.notification_tx.as_ref()?.clone();
        Some(Arc::new(move |notification| {
            let _ = tx.try_send(notification);
        }))
    }
```

`self.notification_tx` is assigned by `Server::run()` and by nothing else, and
`StreamableHttpServer` never calls `run()` — so on HTTP it is always `None`. That, plus
`RequestHandlerExtra::report_progress`'s silent `Ok(())` on a `None` reporter, is why the gap
produced no error anywhere and could only be found by asserting on observed frames.

`progress_reporter_for` keeps the `progressToken` lookup exactly as it was and replaces only the
sender resolution. It is now the ONE construction site for the tools, prompts and resources
dispatchers, which previously held three byte-identical copies.

**`ServerCore::handle_call_tool` builds NO progress reporter** — `git grep -n
'with_progress_reporter' src/server/core.rs` returns nothing. So v1 HTTP progress rides the
`Server` dispatcher only, which is the one the transport actually calls
(`dispatch_public_request` → `Server::handle_request_with_context`). Nothing to mirror there.

### The sink is v1-only, and the v2 branch is inert by construction

`attach_session_backchannel` returns the context UNCHANGED when `!site.sessions_on`, so a v2 request

### The queue bound (T-118.1-11-03), measured not asserted

The v1 session stream is `mpsc::UnboundedSender<TransportMessage>`
(`src/server/streamable_http_server/v1_session.rs:121`), so the QUEUE imposes no limit and never
did — that is a pre-existing property shared with every other v1 outbound message, not something
this plan introduced.

**The bound on progress emission is `ServerProgressReporter`'s own policy**, and it is real:
`rate_limit_interval` is 100 ms (`src/server/progress.rs:100`), so at most one non-final
notification per 100 ms per request, plus a monotonic-progress rule that makes a non-increasing
report a no-op. Measured by `a_tight_progress_loop_is_bounded_by_the_reporter_rate_limit`: a handler
calling `report_progress` **200** times back to back with no awaits produced **1** frame, against a
declared ceiling of 20. The assertion is `frames.len() <= 20` rather than `== 1` so a slow machine
fails on a real regression rather than on scheduling.

## Task 3: what the era matrix actually measures now

The tripwire's own instruction said: *"If this now reports `completed`, G-3 HAS BEEN FIXED."* It does

```

```

That is plan 10's `fail_pending(NO_LIVE_STREAM)`: the peer was present, the request WAS issued, and

consequential finding.

### A NEW gap, and it is CLIENT-side

`StreamableHttpTransport::start_sse` (`src/shared/streamable_http.rs`) issues the GET and then calls
`Self::collect_body_within_cap(response, ..)` — a WHOLE-BODY read — before handing the bytes to
`SseParser::feed_complete_body`. Its own rustdoc states the design: *"this body was already read
into memory in one piece, not a chunk of a live stream"*. A v1 session SSE stream never ends, so
there is nothing to collect; pmcp's own client therefore registers no receiver and can receive NO
server-initiated message over v1 HTTP.

**This is not gap G-3 and it is not a server defect.** The server half is closed and measured green
by `tests/http_peer_roundtrip.rs`, whose client is a raw TCP reader that DOES hold the stream open —
all three round trips complete there. Failing the correlation at once rather than parking the
handler for the 30-second dispatch timeout is exactly what plan 10's fail-fast path exists to do.

Recorded in `deferred-items.md` with the owner and the reason it is not fixed here: making a public
client transport read a live SSE stream incrementally is an architectural change (Rule 4), outside
this plan's `files_modified`, and it needs its own concurrency, shutdown and in-flight-bound design.

## Deviations from Plan

### 1. [Rule 1 — bug] The v1 SSE writer used the wrong wire encoding

- **Found during:** Task 1, immediately after the peer injection landed
- **Issue:** `sse_event_for_message` serialized the `#[serde(untagged)]` `TransportMessage`
  directly. Correct for `Response` (byte-identical to the shared encoder), unparseable for `Request`
  (`{"id":..,"request":{..}}`) and for `Notification` (the params object alone, no `method`, no
  `jsonrpc`). Latent until plan 10 gave the transport an outbound request path.
- **Fix:** route through `crate::shared::transport::serialize_message`, the single source of truth
  every other transport uses, with a rustdoc table showing where the two encodings agree. A
  serialization failure yields an empty data payload rather than the previous `.unwrap()` panic —
  unreachable in practice, since the only serde failure mode is non-finite floats and
  `ServerProgressReporter::validate_values` rejects those before a notification is built.
- **Files modified:** `src/server/streamable_http_server/v1_session.rs`
- **Verification:** the five peer round trips went from "wrong frame shape" to green in one run; 150
  HTTP/SSE/v1/v2 regression tests across 17 binaries still pass, and the full `pmcp` suite is
  3100/3100.
- **Commit:** `7de5e633`

### 2. [Rule 2 — missing critical functionality] The sink closure captured `ServerState`

- **Found during:** Task 2
- **Issue:** plan 10's `session_notification_sink` did `state.clone()`, capturing the whole
  `ServerState` — including `Arc<Mutex<Server>>` — into a closure that outlives the request.
  T-118.1-11-07 names exactly this.
- **Fix:** capture `state.v1.clone()` (a `Clone` `V1State` holding only the stream map, the session
  table and the event store) plus the session id.
- **Commit:** `698fb9ea`

### 3. [Rule 3 — blocking] The era target needed a third status

- **Found during:** Task 3
- **Issue:** the plan instructed a flip to `DEP_STATUS_COMPLETED`. The measurement produces neither
  `completed` nor `capability-not-offered` but a propagated transport error, which aborts the tool
  call and yields no observation at all.
- **Fix:** `DEP_STATUS_NO_LIVE_STREAM` on the era target, with the error under `detail`; the two v1
  tools report it instead of propagating. `crates/pmcp-team-servers/src/conformance/era_target.rs`
  is outside the plan's `files_modified` list — noted here because the alternative was to assert a
  value the system does not produce.
- **Commit:** `ff932efb`

### 4. [Rule 1 — correctness] `SessionPeerHandle` gained a hand-written `Debug`

- **Found during:** Task 2
- **Issue:** adding the sink field to a `#[derive(Debug)]` struct would have made a `{:?}` print a
  capability handle and the session token, contradicting the presence-only redaction discipline
  `TransportBackchannel` and `ServerRequestDispatcher` already apply (T-118.1-10-09).
- **Fix:** hand-written `Debug` printing `SessionPeerHandle { .. }`.
- **Commit:** `698fb9ea`
