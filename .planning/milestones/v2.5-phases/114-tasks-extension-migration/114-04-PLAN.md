<objective>
Open the two additive trait seams `tasks/update` needs (D-12) and implement input delivery on the
in-crate `InMemoryTaskStore` (D-13 site 3), so the core path and the phase's paired example work
standalone with no `pmcp-tasks` dependency.

Purpose: `tasks/update` is the one genuinely-new v2 feature, and it must reach the backends
without a second registration knob and without breaking any existing implementor. The established
in-file precedents are exact: `set_result`/`get_result` + `supports_results()` on `TaskStore`, and
`create_workflow_task` defaulted-to-an-error on `TaskRouter`.

Output: one defaulted method + one probe on `TaskStore`, one defaulted method on `TaskRouter`, the
`InMemoryTaskStore` override, and the internal-record fields the kinds are read from.

**Why the record carries the kinds (D-17, security-bearing):** `tasks/update`'s `inputResponses`
entries must be decoded KIND-DIRECTED, and the kinds must come from what the *server itself*
recorded — never from anything the client sends. The persisted task record is the tasks analogue
of Phase 113's AEAD-sealed continuation. 113-27 closed **D-113-O**, where untagged "first shape
that fits" decoding mis-typed an elicitation answer as Sampling (`ElicitResult` and
`CreateMessageResult` structurally overlap) and a handler re-elicited 16 times before dying on a
misleading error. Storing `inputRequests` on the record is what makes the correct decoder
reachable in 114-14.
</objective>

lock/entry guard so the whole operation is atomic with respect to concurrent callers (the in-crate
store uses `dashmap`; hold the entry, do not read-then-write across an await):

- Look up the record; `NotFound` if absent. Then `Self::validate_access(record, task_id, owner_id)`
  so a wrong owner surfaces as `NotFound` — never a distinguishable owner error. This is
  PROJECT.md's standing no-info-leak decision and must be routed through the existing helper, not
  re-expressed.
- Refuse unless the current status is `InputRequired`. A `Completed`, `Failed` or `Cancelled` task
  cannot be fed. Use `TaskStatus::can_transition_to` for the transition validity check rather than
  a hand-written match.

  answered are ACCEPTED and merged into `record.input_responses`; every other key is IGNORED (not
  an error). Report both sets plus whether the outstanding set is now complete via
  `TaskInputDelivery`.
- Transition `InputRequired → Working` and bump `last_updated_at` **only when the delivered set
  COMPLETES the outstanding set**. A partial delivery persists the responses and the task STAYS
  `input_required` — this is the spec qualification of D-16 that research surfaced ("A server MAY
  accept a partial set; the task then remains `input_required` until the rest arrive"). The atomic
  unit is *(persist responses [+ transition iff now complete])*.
- Do not enforce byte/count/depth bounds here — those are enforced at ingress in 114-14, before
  any decode, using the **four** existing input-response MRTR constants (`MAX_INPUT_RESPONSES`,
  `MAX_INPUT_RESPONSE_BYTES`, `MAX_INPUT_RESPONSES_TOTAL_BYTES`, `MAX_INPUT_RESPONSE_DEPTH`). The
  fifth constant read above, `MAX_REQUEST_STATE_LEN`, bounds the MRTR request-state token and does
  NOT apply to `tasks/update`, which carries no continuation token. Note the division of

  not add a fifth check here by miscount.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client-supplied `inputResponses` → persisted task record | Untrusted values are persisted; only the KEYS the server already recorded may be accepted |
| caller A's owner id → caller B's task record | The store is the enforcement point for owner isolation |
| out-of-tree implementor → trait contract | A defaulted method must fail explicitly, never succeed silently |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-114-10 | Information Disclosure | `InMemoryTaskStore::deliver_task_inputs` owner check | mitigate | Routed through the existing `Self::validate_access`, so a wrong owner yields `NotFound`; test asserts the rendered message contains neither `owner` nor the other owner's id |
| T-114-11 | Tampering | client choosing which input kind its answer is decoded as | mitigate | `input_requests` on the internal record is written only by the server and is documented MUST-NOT-be-client-settable; it is the kinds source 114-14 decodes against (D-113-O class) |
| T-114-12 | Tampering | replay of an already-answered `inputRequests` key | mitigate | Already-answered keys are IGNORED, not re-accepted (`deliver_inputs_ignores_a_key_already_answered`); the spec requires keys be unique over a task's lifetime and never reused after a response is delivered |
| T-114-13 | Tampering | lost update on concurrent delivery | mitigate | The in-crate store performs the read/partition/write under one entry guard with no intervening await; the CAS equivalent for the production backends is 114-07's `put_if_version` path |
| T-114-14 | Elevation of Privilege | feeding a terminal task | mitigate | Refused unless the current status is `InputRequired`, validated via `TaskStatus::can_transition_to` (46 existing transition tests) |
| T-114-15 | Denial of Service | oversized `inputResponses` | transfer | Bounds are enforced at ingress in 114-14 using the five existing MRTR constants; this plan mints no new limits and records the division of responsibility in both rustdocs |
| T-114-SC | Tampering | npm/pip/cargo installs | accept | Zero packages installed; `Cargo.toml`/`Cargo.lock` byte-unchanged |
