<objective>
Implement `tasks/update` delivery: bounds first, then kind-directed decoding against the kinds the
server itself recorded, then the atomic transition, then an empty acknowledgement (TASK-02, D-16,
D-17), plus the fuzz and property coverage CLAUDE.md requires.

Purpose: this is the phase's one genuinely new feature and its most security-sensitive decode path.
**D-17 is a security decision, not a convenience one.** 113-27 closed **D-113-O**, where untagged
decoding (try Roots, then Sampling, then Elicitation — first that fits) mis-typed an elicitation answer
as Sampling because `ElicitResult` and `CreateMessageResult` structurally OVERLAP; the handler's
`Elicitation` arm never matched, it re-elicited **16 times**, and the operation died on a misleading
error. Any independent decoder that guesses at overlapping shapes reproduces that bug class exactly.
The persisted task record is the tasks analogue of 113's AEAD-sealed continuation: it holds
server-minted kinds the client cannot choose.

The parameter name is `inputResponses` — measured from the vendored schema, **not** `inputs` as the
requirement text and CONTEXT.md's grounding note both say. It is a name-for-name and shape-for-shape
match with pmcp's existing `InputResponses` (`BTreeMap<String, InputResponse>`), which makes D-17's
reuse exact rather than analogous, and means the five DoS bounds come free.

Output: the delivery body, a fuzz target, a property test, and a full semantics suite.
</objective>

  1. **Parse** `params` into `{ taskId: String, inputResponses: BTreeMap<String, serde_json::Value> }`
     — a RAW map, deliberately NOT into `InputResponses`. Cross-AI review flagged this and it
     verifies: `InputResponse` is a union over `CreateMessageResult | ListRootsResult | ElicitResult`,
     so deserializing straight into `InputResponses` runs the UNTAGGED decoder before any
     kind-directed validation — which is exactly the D-113-O bug class this route exists to avoid,
     re-introduced one layer earlier. A malformed body (missing `taskId`, `inputResponses` not an
     object) is a structured `-32602`.
  2. **Bounds, BEFORE any decode**, over that raw map. `check_input_response_bounds`
     (`src/types/mrtr.rs:1030`) is currently a PRIVATE `fn` — promote it to `pub(crate)` in this plan
     (it is crate-private either way, so `cargo semver-checks` is unaffected) rather than writing a
     second bounds function in `task_dispatch.rs`. Apply the **four** input-response bounds:
     `MAX_INPUT_RESPONSES` (64 entries), `MAX_INPUT_RESPONSE_BYTES` (64 KiB per entry),
     `MAX_INPUT_RESPONSES_TOTAL_BYTES` (256 KiB total) and `MAX_INPUT_RESPONSE_DEPTH` (32). The fifth
     MRTR constant, `MAX_REQUEST_STATE_LEN`, bounds the MRTR continuation token and does NOT apply
     here — `tasks/update` carries no token. They must fire FIRST: bounding after decoding means the
     decoder already did the work. Do not mint new constants — bounds chosen independently here would
     diverge from the MRTR path on the same server.
  3. **Load the outstanding-input snapshot** through 114-04's owner-scoped
     `TaskStore::task_input_snapshot(task_id, owner_id)` (or the router's `Value` equivalent), so the
     owner-scoped read happens before anything is trusted. `TaskStore::get` returns only `Task`
     (`src/server/task_store.rs:249`) and `TaskRecord` is private (`:404`) — the snapshot accessor is
     the ONLY supported way to reach the server-recorded kinds, and this step is why this plan depends
     on 114-04. The owner is the one 114-09's identity table resolved; never read an owner from
     `params`. A `NotFound` snapshot is the oracle-free `-32602` from 114-11.
  4. **Kind-directed decode.** For each delivered key, look up its kind from the snapshot's
     SERVER-recorded `inputRequests` via `InputRequest::kind()`, then `mrtr::decode_for(kind, value)`
     on the RAW `Value`. A key the snapshot does not hold is IGNORED (never issued / already answered /
     superseded) — the spec says ignore, not error. A key it DOES hold whose value cannot decode as
     that kind is **REFUSED** with a structured `-32602`. Never call `try_from_value_untagged` on this
     path. Only AFTER this step does a typed `InputResponses` exist to hand to `deliver_task_inputs`.
  5. **Deliver.** Store-first: if `store.supports_inputs()`, call `deliver_task_inputs`; on
     `NotFound`/unsupported, fall through to `TaskRouter::handle_tasks_update` — the same
     store-first/router-fallthrough precedence every other tasks route uses. Never a hard error when a
     router could serve it.
  6. **Transition** per D-16 as qualified by the spec: `InputRequired → Working` iff the delivered set
     COMPLETES the outstanding set; a partial set persists and the task STAYS `input_required`. The
     backends already implement this atomically (114-04 / 114-07) — dispatch must not re-implement it,
     and must not read-then-write around it.
  7. **Respond** with `UpdateTaskResult` — an EMPTY acknowledgement, `resultType: "complete"`. Document
     that the ack is eventually consistent: the server MAY ack before a subsequent `tasks/get` reflects
     the change, so no wait or re-read is inserted to make it look synchronous.

Two refusal-message constraints: a `-32602` for an undecodable value must name the KEY (server-assigned,
bounded, and provably from the record — take it via the record's own key so the rendered string cannot
be a client-chosen value) and must NEVER render the VALUE. A key the record never held is CLIENT-chosen
by definition and must be carried programmatically but **never rendered** — echoing it both amplifies
and poisons logs. This is `MrtrParseError`'s established discipline and 113-27's provenance rule.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client `inputResponses` → typed input model | The highest-risk decode in the phase; overlapping result shapes make untagged decoding actively wrong |
| client-chosen key → log output / refusal message | A client-chosen key is unbounded-ish and attacker-shaped; rendering it amplifies and poisons logs |
| client payload size → server memory | `inputResponses` is the only large client-supplied structure on this route |
| caller A → caller B's task inputs | Feeding another owner's task would be a write-side IDOR |
