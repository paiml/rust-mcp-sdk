Ship the paired runnable example that makes this phase's central claim checkable rather than asserted
(D-05, D-06).

**Scope corrected from cross-AI review:** every change to `src/client/mod.rs` moved to **114-19**,
which lands era-aware v2 decoding, `tasks_update()` and the input-supplying poll helper together.
Review measured — and it verifies at `src/client/mod.rs:1069/1140/1233/1385/1435` — that the client
still decodes NESTED v1 `CreateTaskResult`/`GetTaskResult`/`CancelTaskResult` shapes and that
`wait_for_task` ends by calling the v2-retired `tasks/result`. Adding `tasks_update` alone (this
plan's original Task 1) would not have made the agent example runnable. This plan is therefore
examples-only, depends on 114-19, and has ZERO file overlap with it.

Purpose: the owner steer for this phase is that one SDK serves both servers and agent clients, and that
aligning to v2 tasks is a small symmetric change on each side. That claim is only checkable if both halves
exist and run. CLAUDE.md's ALWAYS list also requires a runnable `cargo run --example` for every new
feature. The client half is **agent-shaped on purpose** — an autonomous poll loop, not an interactive chat
client — because that is the shape 113 D-07 made first-class and the one that matters for pmcp's
enterprise/Lambda focus.

Output: `examples/s50_v2_tasks_server.rs` and `examples/s51_v2_tasks_agent.rs`.

**Numbering, measured (PATTERNS Fact 2):** `s49` is already taken TWICE (`s49_sampling_host.rs` and
`s49_v2_subscriptions_client.rs`; 52 `sNN_` examples total), so RESEARCH's proposed `s49_v2_tasks_server.rs`
would be a third collision. The next free pair is **`s50`/`s51`**.

**Pitfall 3, decided (DQ8):** the server half uses the **in-crate `InMemoryTaskStore`**, which has no
`allow_anonymous` check. `pmcp-tasks`' `GenericTaskStore` rejects both `ANONYMOUS_PRINCIPAL` (`""`) and
`"local"` while `allow_anonymous` defaults to `false`, so pairing a no-auth example server with a
pmcp-tasks backend would fail the first time anyone ran it. The choice is deliberate and the example says
so in a comment, pointing at 114-07's `anonymous_owner_is_refused_by_default_on_this_backend` test for the
production-backend story.

**Boundary with Phase 117 (D-06):** this client half is agent-*shaped*. Wiring it into the actual
`pmcp-agent` crate remains CLNT-03 / Phase 117, which inherits a de-risked surface rather than a blank one.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| example server → any local caller | The example has no auth provider, so it is a shared-bucket demo and must say so |
| task input channel → agent trust model | The spec is explicit that a task is NOT a higher-trust channel; a client-side obligation the agent half must not violate |
| example code → user expectations | An example that prints success regardless of behaviour teaches the wrong contract |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-114-88 | Information Disclosure | shared owner bucket in the example server | accept | No auth provider by design for a runnable demo; the caveat is stated in a comment (D-07) together with what a real deployment does instead; bound to localhost by default |
| T-114-89 | Spoofing | treating a task payload as higher-trust than an elicitation | mitigate | The spec's rule ("Hosts MUST apply the same trust model to these payloads as they would to standard elicitation/sampling requests. A task is not a higher-trust channel") is stated in the agent example's rustdoc, and the example's responder produces values programmatically without executing anything from the server |
| T-114-90 | Repudiation | an example that passes regardless of behaviour | mitigate | Every `demo_*` returns `Err` on a divergence and `main` propagates; a recorded control shows the example exiting non-zero with the server route disabled |
| T-114-91 | Denial of Service | unbounded client-side input round loop | transfer | The poll helper and its input-round bound live in **114-19** (T-114-101); this plan only consumes them, and its acceptance criteria assert the example drives the production helper rather than a local loop |
| T-114-92 | Tampering | example drifting from the SDK via a re-implemented loop | mitigate | The example drives production client methods only; acceptance criteria assert no local poll loop exists (the 110-06 precedent) |
