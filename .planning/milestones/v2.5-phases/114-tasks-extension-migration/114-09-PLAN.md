<objective>
Make v2 task owner binding fail closed using Phase 113's identity table verbatim, and land the two
refusals in the order the design requires (D-07, D-08, D-09's precondition, D-10).

Purpose: TASK-05 is this phase's central security control and the ROADMAP calls it "the critical
no-session cross-caller-leak guard". v2 is session-free by design, so the owner must come from the
authenticated subject or not at all. `TaskDispatch::resolve_owner` today takes only `auth_context`
and — on the router path — delegates to `pmcp_tasks::security::resolve_owner_id`, whose chain is
`subject → client_id → session_id → "local"`. TASK-05 forbids a session-id fallback outright, and
`client_id` is disqualified too: it is per-application (OAuth `azp`) and would collapse per-user
isolation to per-app isolation.

Output: an era-aware `resolve_owner`, `has_auth_provider` + `client_capabilities` threaded in at both
dispatch sites, the ordered refusals, the v1 migration warn, and a unit/integration matrix. The
live-socket cross-caller proof is 114-15.

**Resolved scope decision recorded here (DQ3, from 114-RESEARCH Q3):** two refusals, two codes, two
meanings — because on a tasks method a single `-32003` would be ambiguous between "you did not
declare the extension" and "you are not authenticated", which is the exact undiscoverability D-08
chose `-32003` to avoid.
  - `-32003 AUTHENTICATION_REQUIRED` — the **auth** refusal (D-08 verbatim; the shape 113-23 already
    landed for `subscriptions/listen`).
  - `-32021 MISSING_REQUIRED_CLIENT_CAPABILITY` — the **non-declaring-client** refusal, with
    `error.data.requiredCapabilities` as an OBJECT (`{"extensions":{"io.modelcontextprotocol/tasks":{}}}`),
    never an array.
Both constants already exist, so no new wire value is minted under the schema hold. Research measured
that the ext-tasks prose uses `-32003` for missing-capability while the core draft schema uses
`-32021`; that disagreement is recorded as its own row in `114-SPEC-RECHECK.md` and is re-checked at
the gate, not guessed at here.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unauthenticated v2 caller → task store | The fail-closed row is the only thing preventing an anonymous caller from minting or reading tasks on an auth-configured server |
| client-supplied params → owner identity | The owner must come from `AuthContext` only; any params-derived owner is an IDOR |
| session id / client_id → owner identity | Both are explicitly disqualified on v2 (TASK-05 forbids session; `client_id` is per-application) |
| refusal message → caller | A refusal must not become an authentication or existence oracle |

| T-114-39 | Information Disclosure | shared-bucket collapse on a no-auth server | accept | Documented plainly in `resolve_owner`'s rustdoc (D-07's stated caveat), not implied. Independently bounded on production backends by `allow_anonymous: false` (114-07 test 8) |
