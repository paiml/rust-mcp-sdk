<objective>
Reshape the v2 task result surface: flat payloads, the `ttlMs`/`pollIntervalMs` renames, the
status-conditional `result`/`error`/`inputRequests` fields, empty acknowledgements, and
`NotFound → -32602` — all above the `serde_json::Value` seam so v1 bytes never move (TASK-04, D-15,
D-11, Pitfall 5, Pitfall 6).

Purpose: this is the reshape TASK-04 names, and research corrected the requirement text in three ways
the plan must honour. **(1) TASK-04's four-field enumeration is incomplete:** `Task`'s `required` array
is `taskId`, `status`, `createdAt`, `lastUpdatedAt`, `ttlMs` — five fields — with `pollIntervalMs`
optional. **(2) `ttl`→`ttlMs` and `pollInterval`→`pollIntervalMs` are renames, not just re-nesting.**
**(3) THREE result shapes change on v2, not one** — `GetTaskResult` becomes flat, and `CancelTaskResult`
and `UpdateTaskResult` become empty acks. CONTEXT.md mentions only `CreateTaskResult`.

Output: additive projection types, the projection in `task_dispatch.rs`, the not-found code change,
and a per-shape suite asserting against the vendored schema.

**Discretion resolved (from CONTEXT.md's Discretion list):** research leaned toward a **separate v2
projection type** over additive `skip_serializing_if` fields on `Task`, because the spec models the
detailed task as five *distinct status-discriminated variants with per-variant required fields*,
which one flat struct cannot express — and because additive fields on `Task` risk v1 byte drift if any
`skip_serializing_if` is missed. This plan takes the projection-type route. The v1 types in
`src/types/tasks.rs` are additive-only targets: no existing field is renamed, re-nested, or has its
serde attributes changed.
</objective>

| Boundary | Description |
|----------|-------------|
| store error → client error code | The not-found path is where an existence oracle would appear, because owner mismatch deliberately surfaces as NotFound |
| v2 projection → v1 wire | One serde slip on a shared type moves v1 bytes for every existing tasks server |
| task result payload → client | A terminal result may contain tool output; TTL-bounded purge must still cover it |

| T-114-51 | Information Disclosure | `inputRequests` inlined for the wrong caller | mitigate | The inline happens after owner binding (114-09), so the record is only reachable through the owner-prefixed key; 114-15's cross-caller matrix covers it per method |
