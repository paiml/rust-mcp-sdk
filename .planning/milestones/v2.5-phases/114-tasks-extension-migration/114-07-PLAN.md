<objective>
Implement `tasks/update` input delivery once, in `GenericTaskStore<B>`, so memory + DynamoDB + Redis
all gain it (D-13), reach it from `TaskRouterImpl` across the `Value` seam, and prove the pre-114
persisted records still read.

Purpose: D-11's claim is that DynamoDB/Redis-backed tasks work on v2 from day one and the v1.x
storage investment survives. That claim is only true if the one genuinely-new v2 feature also works
on the production backends. `GenericTaskStore<B>` is exactly the type for it — "domain logic once,
backends are dumb KV stores; 3 backends share identical domain logic; zero divergence".

**Stated plainly because TASK-06's text says "unchanged":** this touches `crates/pmcp-tasks`
**additively** — one trait method with a default, one domain implementation, one delegation line, one
router override. No rewrite, no schema migration, no storage-layer redesign. That is inside the
reshape-not-rewrite line, and it should not be discovered in review.

**F12's correction the plan must not lose:** D-13 says "two impls" but it is really **three sites**.
`crates/pmcp-tasks/src/store/memory.rs`'s `InMemoryTaskStore` is a DELEGATING WRAPPER around
`GenericTaskStore`; omitting its one-line delegation makes it silently inherit the not-supported
default, and every memory-backed test would report "backend does not accept inputs" while the
Dynamo/Redis paths worked. That is the failure mode this plan's delegation-completeness tripwire
exists to make structural.
</objective>

Two changes.

**(a) `crates/pmcp-tasks/src/store/mod.rs`** — add
`async fn deliver_inputs(&self, task_id: &str, owner_id: &str, responses: Value) -> Result<Value, TaskError>`
to this crate's `TaskStore` trait with a DEFAULT body returning
`TaskError::StoreError("store does not support task input delivery".into())`. Params and return are
`serde_json::Value` because this crate sits BELOW the seam (D-11) — the typed
`InputResponses`/`TaskInputDelivery` shapes live in pmcp above it. Carry the crate's `# Errors`
bullet-list convention, and add the sentence that this is additive-with-a-default specifically so
existing implementors compile unchanged.

**(b) `crates/pmcp-tasks/src/store/generic.rs`** — implement it for `GenericTaskStore<B>`, copying
`complete_with_result`'s two-mutations-in-one-CAS shape exactly:
  1. `check_anonymous_access(owner_id)` first (the crate's existing gate — do not bypass it).
  2. `make_key(owner_id, task_id)` → `backend.get` → `deserialize_record`; set `record.version`.
  3. Owner-mismatch check returning **`NotFound`** with the existing `tracing::warn!` shape. Never
     `OwnerMismatch` on this path — a wrong owner already yields a different key, so this branch is
     defence in depth, and PROJECT.md's standing decision is that the caller learns `NotFound`.
  4. `is_expired` → `TaskError::Expired`.
  5. Refuse unless the current status is `InputRequired`, validated through the existing
     `validate_transition` / `can_transition_to` path. A `Completed`, `Failed` or `Cancelled` task
     cannot be fed.
  6. Partition the delivered keys against the record's outstanding `inputRequests`: accept keys that
     are outstanding and unanswered, IGNORE every other key (never issued, already answered,
     superseded) — ignoring is what the spec requires, not erroring.
  7. Merge accepted responses into the record; set `last_updated_at`; and transition
     `InputRequired → Working` **only if the outstanding set is now COMPLETE**. A partial delivery
     persists and STAYS `input_required`. The atomic unit is *(persist [+ transition iff complete])*.
  8. ONE `serialize_record` + ONE `put_if_version(&key, &bytes, versioned.version)`. A version
     conflict propagates as the crate's existing conflict error — first writer wins, second sees the
     conflict. Do NOT retry internally and do NOT take a mutex around the read-then-write: that is
     the lost-update bug on DynamoDB/Redis that `put_if_version` exists to prevent.
  9. Return a `Value` describing accepted keys, ignored keys and whether the set is now complete, so
     the pmcp side can build its typed `TaskInputDelivery` without a second read.

Fields on the persisted record for outstanding requests, delivered responses **and the terminal
JSON-RPC error** must deserialize **absent-means-empty**, because records written by a pre-114 build
carry none of them. Use `#[serde(default)]` (and `skip_serializing_if` on the write side so an
untouched record's bytes do not grow). Do not introduce a record version bump or a migration.

**(c) The three read/write accessors pmcp needs above the seam.** 114-04 adds
`task_input_snapshot`, `record_input_requests`, `set_error` and `get_error` to pmcp's `TaskStore`
because `TaskStore::get` returns only `Task` and `TaskRecord` is private. Mirror them on this crate's
trait and implement them on `GenericTaskStore<B>` in the same `Value`-in / `Value`-out discipline as
`deliver_inputs`:
  - a snapshot read returning outstanding requests + delivered responses + status, owner-scoped, with
    the same `NotFound`-on-mismatch rule;
  - a recorder that writes SERVER-authored input requests and transitions to `InputRequired` in ONE
    `put_if_version`, refusing rather than overwriting when requests are already outstanding;
  - error persistence for a `failed` task, so a v2 `tasks/get` can inline it (114-11).
Each is one CAS. None re-derives the owner from params.

**(d) Source-compatibility fence on the public record type.** `TaskRecord` in this crate is PUBLIC
(unlike pmcp's private one), so `#[serde(default)]` preserves persisted-DATA compatibility but does
NOT preserve downstream Rust struct literals — and root-crate `cargo semver-checks` does not cover
this unpublished crate. Add `#[non_exhaustive]` to it if it is not already, or if that itself breaks
in-crate construction, add a `#[test]` constructing it exclusively through its constructor/builder and
a comment recording that a struct-literal construction site is a source break. Record which route was
taken in the SUMMARY.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| pmcp dispatch → pmcp-tasks store (`serde_json::Value` seam) | Params arrive as already-validated, already-bounded, already-kind-decoded values with the owner passed explicitly |
| owner A → owner B's persisted record | The owner-prefixed key is the structural isolation; the explicit check is defence in depth |
| pre-114 persisted record → post-114 code | Durable data outlives the wire change; an absent field must never become a hard error |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-114-25 | Tampering | lost update on concurrent `tasks/update` | mitigate | One `put_if_version` CAS per delivery, no internal retry, no mutex; `concurrent_deliver_inputs_first_writer_wins` via the existing `CasConflictBackend`, with a recorded control replacing CAS with a plain `put` |
| T-114-26 | Information Disclosure | cross-owner task feed | mitigate | `make_key(owner_id, task_id)` structural isolation + explicit check returning `NotFound`; test asserts the message renders neither `owner` nor the other id |
| T-114-27 | Elevation of Privilege | feeding a terminal task to resurrect it | mitigate | Refused unless `InputRequired`, validated through the existing 46-test transition machine; one test per terminal status |
| T-114-28 | Tampering | replay of an answered `inputRequests` key | mitigate | Already-answered keys are IGNORED and reported; spec requires keys be unique over a task's lifetime |
| T-114-29 | Denial of Service | unbounded `responses` value reaching the backend | transfer | Bounds are enforced above the seam in 114-14 with the five existing MRTR constants; recorded in the trait rustdoc at both ends so neither side assumes the other checked |
| T-114-30 | Denial of Service | pre-114 record read failure (availability of durable data) | mitigate | `#[serde(default)]` absent-means-empty, pinned by a raw-BYTE fixture rather than a struct round trip |
| T-114-31 | Spoofing | owner re-derived from client params inside the router | mitigate | `handle_tasks_update` reads `owner_id` from the parameter only; `resolve_owner_id`'s `session_id` chain is explicitly not used (TASK-05 forbids it) |
| T-114-SC | Tampering | npm/pip/cargo installs | accept | Zero packages installed; `crates/pmcp-tasks/Cargo.toml` and the workspace `Cargo.lock` must be byte-unchanged |
