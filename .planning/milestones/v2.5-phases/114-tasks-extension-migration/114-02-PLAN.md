Write a local `assert_v1_bytes(raw, expected_result)` helper modelled on
`assert_v1_byte_identical`: parse the raw text, compare the whole JSON-RPC frame structurally
against `{"jsonrpc":"2.0","id":<id>,"result":<expected>}`, and additionally assert the RAW
string does not contain `resultType` or `serverInfo`.

**Do NOT copy the third `_meta` assertion verbatim.** `build_task_created_response` deliberately
emits `_meta.relatedTask` on the v1 create envelope (`task_dispatch.rs` around lines 527-532), so
a blanket `!raw.contains("_meta")` would fail for the wrong reason. Instead: assert `_meta` is
ABSENT on `tasks/get`/`list`/`cancel`/`result`, and on the create envelope assert `_meta` is
PRESENT and contains exactly the `relatedTask` key it carries today — with a comment naming why
the asymmetry exists.

Where a field is time-dependent (`createdAt`, `lastUpdatedAt`, `taskId`) do not pin the value —
**substitute a fixed-width placeholder token in the RAW STRING before comparing, then compare the raw
strings**, rather than dropping to a structural JSON comparison. Cross-AI review is right that a
structural comparison of parsed JSON cannot detect key ORDER, whitespace, or omission-vs-explicit-null
— which are precisely the three things a serde-level reshape changes while every structural assertion
stays true, and D-14 item 2 exists because "the suite passes" is not evidence of byte identity.

So `assert_v1_bytes` does BOTH:
  - a **raw-string** comparison after replacing each dynamic value with a same-width placeholder
    (the id is a v4 UUID at a known length; the two timestamps are fixed-width RFC-3339), so key
    order, spacing and null-vs-absent are all in scope; AND
  - the structural comparison already described, as the readable failure message.
When a value is not naturally fixed-width, pad or normalize it to a constant width in the
substitution — never delete the key, because deleting it is what hides an omission-vs-null change.

**Cover BOTH backend paths, not just the in-crate store.** D-11's whole claim is that the v2 reshape
sits above the `serde_json::Value` `TaskRouter` seam and leaves router-backed servers untouched; a
golden suite that only exercises `InMemoryTaskStore` cannot detect a v1 byte change on the router
path, which is the path DynamoDB and Redis deployments actually use. Parameterize each of the six
fixtures over two servers — one store-backed, one backed by a `TaskRouterImpl`-shaped router — and
record in the SUMMARY which fixtures differ legitimately between the two (the router path has its own
envelope on create) so a later diff is attributable.

State in a file-level rustdoc that this is a byte-identity fixture whose purpose is to FAIL when
Phase 114's reshape leaks into v1, that a future editor must treat a diff here as a v1 wire break and
not a fixture to update, and that the placeholder substitution is the ONLY permitted normalization.
