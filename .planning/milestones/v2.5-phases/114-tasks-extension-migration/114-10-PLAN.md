<objective>
Fix the highest-severity finding in this phase's research before any plan depends on it: Phase 113's
reserved-field registry **silently deletes** the top-level `inputRequests` key from any v2 result
whose disposition is not `InputRequired`, and a v2 `tasks/get` on an `input_required` task must carry
that field as a **required** top-level field with `resultType: "complete"`.

Purpose: this is the finding most likely to ship a schema-invalid response while every test passes.
The removal is silent BY DESIGN — a `tracing::warn!`, not an error — so an integration test asserting
only "the request succeeded" or "status == input_required" would pass against a response the spec
rejects. The registry introduced its ownership model when `InputRequired` was the ONLY minter of
these fields; Phase 114 introduces a second legitimate minter that the model does not know about.

Output: an explicit ownership input replacing the derived flag, the registry's documented table
updated, and a test suite that reproduces the defect before fixing it.

**Ordering correction applied from cross-AI review (verified, not assumed):** an earlier draft of this
plan also removed the `#[cfg_attr(not(test), allow(dead_code))]` from `ResponseDisposition::Task`
(`src/server/core.rs:1150`). That removal moved to **114-12 Task 2**. Measured: `make lint` runs
`cargo clippy --features "full" --lib --tests` with `RUSTFLAGS = -D warnings` (Makefile lines 11 and
150-152), and the `--lib` half is a NON-test build. Nothing constructs the `Task` variant in
production until 114-12 wires the v2 create trigger — and matching on a variant (as `as_wire_str`
does) is not constructing it — so removing the allow here, at wave 5, would break `make lint` for
waves 5 and 6.

**Resolved scope decision recorded here (DQ2, from 114-RESEARCH Q2):** pass MRTR/tasks ownership
**explicitly** rather than extending the disposition model. It is the smallest change to the
registry's model, and it removes a derivation the registry's own rustdoc already flags as a
convenience (`"mrtr_owned is derived from the disposition rather than passed separately"`).
Explicitly rejected: re-adding the field after stripping, and special-casing by method string —
both re-create the divergence the single-registry design exists to prevent.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| tool handler → v2 result envelope | A handler is untrusted with respect to reserved protocol fields; it must not be able to forge an MRTR continuation or an input-request set |
| tasks dispatch → v2 result envelope | A second legitimate minter, which must be granted exactly one extra key and no more |
| egress → conformant client | A silently-deleted required field produces a schema-invalid response that no in-repo test would notice |

|-----------|----------|-----------|-------------|-----------------|
| T-114-44 | Spoofing | handler forging `requestState` to mint a continuation | mitigate | `REQUEST_STATE_KEY` remains MRTR-only; the tasks owner is explicitly denied it and `tasks_minted_request_state_is_still_stripped` asserts the strip plus the warn |
| T-114-45 | Spoofing | handler forging `inputRequests` on an ordinary tool result | mitigate | `handler_supplied_input_requests_is_still_stripped` keeps the original protection; the fix grants the key per-OWNER, never per-key-globally |
