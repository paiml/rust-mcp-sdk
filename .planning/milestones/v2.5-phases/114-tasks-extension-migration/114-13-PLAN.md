<objective>
Route `tasks/update` to `TaskDispatch` without adding a variant to a public exhaustive enum, on every
transport, at both dispatch sites — and replace the compile-time protection this routing choice
structurally loses.

Purpose: TASK-02's plumbing. Research flagged as its single HIGH-risk unverified assumption whether
`ClientRequest` is `#[non_exhaustive]`. **It is not** — `src/types/protocol/mod.rs:479-483` carries
`#[derive(Debug, Clone, Serialize, Deserialize)]` and `#[serde(tag = "method", content = "params", rename_all = "camelCase")]`
with no `#[non_exhaustive]`. Adding `ClientRequest::TasksUpdate` would therefore be a semver-**MAJOR**
break (`enum_variant_added` on a public exhaustive enum) and would fail D-14's 223/223 additivity bar
for a reason unrelated to the traits. The repository already documented both the rule and the
workaround, at `src/server/streamable_http_server.rs:1389-1395`.

Output: an `InternalClientRequest::TasksUpdate` variant (crate-private), a `classify_internal_method`
arm, routing at both dispatch sites, the `TaskDispatch` entry point, and the substitute tripwire.

**Route choice, decided and recorded:** use `InternalClientRequest` + `classify_internal_method` +
`parse_request_or_internal` (the `server/discover` route), **not** the HTTP-only `HttpIngress` route
that `subscriptions/listen` uses. `parse_request_or_internal` lives in
`src/shared/protocol_helpers.rs`, so the classification seam itself is transport-agnostic;
`subscriptions/listen` uses `HttpIngress` only because it opens an HTTP stream, which `tasks/update`
does not.

**Transport reach, corrected and scoped honestly (cross-AI review, verified).** An earlier draft
claimed this design makes `tasks/update` work "over stdio as well as streamable HTTP". Measured: the
ONLY production consumer of `IngressRequest::Internal` today is
`src/server/streamable_http_server.rs:1451-1455`. The public `parse_request` deliberately maps the
`Internal` variant to `-32601` (`protocol_helpers.rs:85-90`), which is the v1-byte-identical
behaviour, and the `InternalClientRequest::ServerDiscover` reference at `src/server/core.rs:3747` is
inside a `#[cfg(test)]` module — **not** a production dispatch arm. So `server/discover` itself is
HTTP-only in practice today, and copying its precedent gives `tasks/update` the same reach.

Task 2 therefore has an explicit, measured obligation: wire the HTTP path, then determine BY
MEASUREMENT whether the native `ServerCore` / `Server` dispatch paths reach an internal-request route
at all. If they do not, do NOT claim stdio support — record the limitation in the SUMMARY and in the
plan's success criteria, and note that v2-over-stdio is already documented as out of scope for this
milestone. The design still admits stdio later without a semver break, which is the actual benefit.

**The protection that is lost, and its replacement.** RESEARCH's F16 table of "5 match sites a
`ClientRequest::TasksUpdate` must reach" is the WRONG table under this design — nothing is added to
that enum, so `client_request_mrtr_eligible`'s exhaustive no-wildcard match (`core.rs:1607`) will not
fire, and Pitfall 4's compile-error protection does not apply. Pitfall 4 is severe: `splice_mrtr_params`
removes `inputResponses` and `requestState` **unconditionally**, and `tasks/update`'s entire payload
*is* `inputResponses` — so an MRTR-eligible `tasks/update` would have its request body deleted and
would return a successful-looking empty ack while the task never left `input_required`. Task 3
replaces the compile-time guard with an explicit runtime + source assertion.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| raw request body → classifier | The classifier runs before the header gate, auth and negotiation; it must never reject or interpret a body |
| tasks/update payload → MRTR ingress | Routing the payload through MRTR would silently delete it; the two surfaces share a key name and a value type, which makes the wrong inference natural |
| public API surface → downstream crates | A variant on a public exhaustive enum breaks every downstream exhaustive match |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-114-62 | Tampering | `tasks/update` payload deleted by `splice_mrtr_params` | mitigate | Three independent guards: a runtime `mrtr_eligible == false` assertion, a source tripwire with a justified allowlist and an anti-vacuity check, and a public-enum absence assertion — each with a recorded negative control |
| T-114-63 | Elevation of Privilege | classifier deserializing params ahead of the auth refusal | mitigate | Params stay RAW in the classifier (asserted by grep) and test 4 measures the ordering by sending malformed params unauthenticated and requiring `-32003` |
| T-114-64 | Denial of Service | parse-error DoS on an unauthenticated path | mitigate | The classifier does no deserialization; the body is parsed only after the era, negotiation, declaration and auth gates have run |
| T-114-65 | Repudiation | accidental semver-major release | mitigate | Nothing added to a public enum; `cargo semver-checks check-release` no-update-required and `cargo public-api diff` zero-added are both acceptance criteria, plus test 7 as an in-repo guard |
| T-114-66 | Tampering | divergent gate copy at the second dispatch site | mitigate | Both sites call the shared entry point; `src/server/mod.rs` adds only wiring, asserted by `git diff` review criterion |
| T-114-SC | Tampering | npm/pip/cargo installs | accept | Zero packages installed; `Cargo.toml`/`Cargo.lock` byte-unchanged |
