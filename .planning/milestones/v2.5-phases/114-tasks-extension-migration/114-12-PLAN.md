<objective>
Make v2 task creation reachable. On v2 the create trigger is "the client declared
`io.modelcontextprotocol/tasks` on this request", replacing v1's `CallToolRequest.task` field, which
does not exist in the v2 extension at all.

Purpose: this is the scope question research flagged as highest-impact, and it is resolved IN SCOPE.
pmcp's create gate requires `task_requested == true`, sourced from `CallToolRequest.task`
(`src/types/tools.rs:484`) — v1's client-signals-task field. **The v2 extension has no such field.**
If the gate keeps requiring it, no v2 `tools/call` can ever produce a `CreateTaskResult`, TASK-04
cannot be demonstrated end to end, and 114-11's flat create shape is dead code reachable only from a
hand-built unit test.

Output: an era-aware create gate at both sites, and an end-to-end suite driving a real v2 `tools/call`.

**Resolved scope decision recorded here (DQ1, from 114-RESEARCH Q1 / Pitfall 2):** CONTEXT.md defers
"unsolicited / server-directed task handles" on the grounds that the spec marks it `MAY`. Research
measured that the `MAY` governs *whether a server elects to materialize a task for a given request*,
not *whether creation may be server-initiated* — the spec states that *"Task creation is
server-directed… The server is the sole decider; clients do not signal task preference on the request
itself."* Read literally, the deferral makes v2 task creation unreachable. ROADMAP success criterion 2
requires a demonstrable v2 `CreateTaskResult`, and the ROADMAP is the phase contract. So:
  - **IN SCOPE (this plan):** the v2 create trigger — the server decides, gated on the client's
    per-request declaration, which is also the spec's `MUST NOT return CreateTaskResult to a
    non-declaring client`.
  - **USER-APPROVED PRE-EXECUTION:** this scope change was put to the user directly at the plan-phase
    checker gate and **explicitly approved on 2026-07-27** ("Approve DQ1 + DQ4"). That approval
    **supersedes CONTEXT.md's deferral** for the create-trigger question specifically. It is recorded here
    so an executor does not re-open a settled scope decision, and so a later reviewer can see the deferral
    was overridden deliberately, by the owner, before any code was written — not silently widened by a plan.
  - **STILL DEFERRED (unchanged):** the broader client-compatibility question the original deferral was
    plausibly protecting — a v2 client having to handle a task handle back from *any* task-capable
    tool, and the surrounding UX/opt-in design. That remains out of scope and is re-recorded as such.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client declaration → server decision to mint a task | The declaration is self-reported; it gates what the server may RETURN, never who the caller is or what they may access |
| two dispatch sites → one gate | A divergent second copy of the gate is how one era's trigger gets implemented in one path and missed in the other |
| task handle → client that cannot handle it | Returning a task handle to a non-declaring client breaks it, and the spec forbids it |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-114-57 | Spoofing | declaration mistaken for authorization | mitigate | The gate decides only WHETHER a task is minted; the task's OWNER comes from `AuthContext` via 114-09's identity table, never from the declaration. Stated in the gate rustdoc |
| T-114-58 | Tampering | divergent second copy of the gate | mitigate | `core.rs`'s inline duplicate replaced by the shared predicate; acceptance criteria assert the condition appears exactly once in `src/` |
| T-114-59 | Denial of Service | task creation by any anonymous v2 caller | mitigate | The gate requires a store AND a declaration, and 114-09's owner binding refuses the unauthenticated caller on an auth-configured server before the create path is reached; `max_tasks_per_owner` (default 100, hard reject) bounds accumulation per owner |
| T-114-60 | Information Disclosure | task handle leaked to a non-declaring client | mitigate | Test 2 asserts `taskId` appears nowhere in the response bytes for a non-declaring caller |
| T-114-61 | Tampering | v1 trigger regression | mitigate | v1 arm byte-frozen; test 4 compares a full golden create envelope; `v1_tasks_golden.rs` green |
| T-114-SC | Tampering | npm/pip/cargo installs | accept | Zero packages installed; `Cargo.toml`/`Cargo.lock` byte-unchanged |
