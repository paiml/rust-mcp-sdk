<objective>
Land the client half of extension negotiation (D-04) and make tasks requests carry the spec's
routing header (DQ4).

Purpose: the owner steer for this phase is explicit — one Rust SDK serves both servers and agent
clients, and aligning to v2 tasks must be a small symmetric change on each side. The server half
(114-05) is meaningless to an agent that cannot declare the extension or cannot tell it was refused.
D-04 reuses the era-aware `assert_capability` mechanism 113-05 landed rather than adding a second
one, and gives Phase 117's agent task polling a clean precondition.

Output: per-request client declaration, a `"tasks"`-on-v2 arm in `assert_capability`, a tasks
name-key table for the header emitter, and the decoupling test that replaces a protection this
phase structurally loses.

**Resolved scope decision recorded here (DQ4, from 114-RESEARCH Q4):** the spec says a client
sending `tasks/get|update|cancel` over Streamable HTTP **MUST** set `Mcp-Name` to
`params.taskId`; pmcp's client emits `Mcp-Name: ""` today, violating it, and Phase 118's
conformance run grades it. It is fixed here. **It is fixed with a SEPARATE table**, because
`logical_name_key` derives from `MRTR_METHODS` and so does `mrtr_eligible` — adding a tasks row to
`MRTR_METHODS` would make `tasks/update` MRTR-eligible, and `splice_mrtr_params` removes
`inputResponses` unconditionally, which would **delete the entire `tasks/update` payload**
(Pitfall 4). Server-side enforcement is deliberately NOT switched on this phase: `cross_check_name`
returns `Ok(())` for a non-name-bearing method, so a conformant client's header is already accepted,
and a tolerant server accepts both conformant and legacy callers. Turning enforcement on is a
separable hardening decision for Phase 118.
</objective>

Rustdoc, at both tables, must record why there are two:

  `logical_name_key`, so a conformant `Mcp-Name: <taskId>` is accepted and a legacy empty value is

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client declaration → server behaviour | The client's extensions map is self-reported; it gates what may be SERVED to it, never who it is |
| request body → emitted headers | Header and body must be derived from the same bytes or an intermediary can be told one thing while the server reads another |
| MRTR ingress → tasks payload | Sharing one table between eligibility and naming would route `tasks/update` through a pipeline that strips its payload |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-114-20 | Tampering | header/body desync on tasks requests | mitigate | `Mcp-Name` derived from the SAME serialized bytes via `frame_routing_pair` (T-113-08's existing property), never from a separate caller-supplied argument |
| T-114-21 | Tampering | `tasks/update` payload destruction via MRTR eligibility | mitigate | Separate name-key table; `mrtr_eligible` reads only `MRTR_METHODS`; `tasks_methods_are_name_bearing_but_not_mrtr_eligible` pins both halves, and a recorded negative control demonstrates the trap |
| T-114-22 | Spoofing | client declaration mistaken for identity | mitigate | Builder-method rustdoc states the declaration is self-reported and is never an authorization signal; owner binding reads `AuthContext` only (114-09) |
| T-114-23 | Information Disclosure | fail-fast message content | accept | The refusal names the extension key (a public, non-secret protocol identifier) so the fix is discoverable; no server state, task id or principal is rendered |
| T-114-24 | Denial of Service | header value injection via a taskId | mitigate | Values pass through the existing `encode_header_value` sentinel codec (T-113-47), which is the ONE codec the server's decoder understands; no second encoder is written |
| T-114-SC | Tampering | npm/pip/cargo installs | accept | Zero packages installed; `Cargo.toml`/`Cargo.lock` byte-unchanged |
</threat_model>
