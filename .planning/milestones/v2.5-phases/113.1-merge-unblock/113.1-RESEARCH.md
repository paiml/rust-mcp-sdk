**D-113-R — the quadratic scan in `SseParser`**

- **D-12: The fix is a scan-window cursor, and it is SMALLER than `deferred-items.md:942-953`
  suggests.** That sketch was written against an older shape (a per-line `drain(..=line_end)`);
  the code at `:500-535` already uses a single `consumed` cursor with one drain at the end. The
  actual change: capture `scan_start = self.buffer.len()` **before** `self.buffer.push_str(data)`
  and start the `find('\n')` search there instead of at 0. `consumed` still starts at 0 so the
  final `drain(..consumed)` and the `line_end > consumed` CRLF lookback guard are unchanged.
  Sound because the retained prefix is newline-free on entry.
- **D-13: Three-part proof.** (1) a **RED-first** 1-byte-chunk time budget that fails on today's
  code and passes after; (2) a **chunking-invariance property test** — for an arbitrary byte stream
  split at arbitrary boundaries, the emitted event sequence AND the retained tail are identical
  regardless of chunking; (3) a fuzz run over the existing `fuzz/fuzz_targets/subscription_listen_frames.rs`
  target. (2) is the property this specific optimisation can violate, and it is warranted: this
  function's one historical remote crash (T-113-67, a byte-vs-character index confusion that
  panicked on remote bytes) was found by a property test, not by review.
- **D-14: The existing `sse_parser_feed_stays_within_its_linear_time_budget` (`:1051`) cannot be
  the guard and must not be treated as one.** At its 4 KiB chunking the re-scan is single-digit
  milliseconds; a negative control (injecting a per-chunk full-buffer copy) moved it 6.7 ms → 11.7 ms
  and it still passed. Its rustdoc already says so — read it.
- **D-15: Replace the `debug_assert!(!self.buffer.contains('\n'))` at `:474` with a dedicated
  test.** After the fix this invariant is the *soundness precondition* (skipping the retained
  prefix is only correct because that prefix cannot contain a newline), but the assertion is itself
  a full scan of the retained buffer on every call — so the quadratic survives in debug builds,
  which is exactly where a 1-byte-chunk proptest runs. Delete the per-call scan; keep the invariant
  as a comment stating what it guarantees, and pin it with one explicit unit test asserting the
  buffer is newline-free after feeds of every shape (mid-line split, CRLF split across chunks,
  empty line, multi-byte character). Rejected: keeping it and running perf tests `--release`;
  cfg-gating it.
- **D-16: Give `feed` the same TWO-guard pair its sibling already has.** `take_utf8_prefix` carries
  both `..._stays_within_its_linear_time_budget` (`:894`) **and**
  `..._cost_grows_linearly_not_quadratically` (a ratio test across two input sizes). `feed` only
  ever got the budget half. Add the ratio test — it is the machine-independent one, so a slow or
  loaded CI box cannot flake it and a merely-worse-but-under-ceiling regression cannot slip through.
  **Keep** the existing 4 KiB test (it covers the many-lines-per-chunk shape — a different failure
  mode, the one fixed in `0493d9fb`), with its rustdoc amended to state plainly what it does and
  does not catch.

## Summary

**CONTEXT.md is unusually complete and its technical claims hold up.** This research verified every
cited code shape, line number, API claim and measurement against live code and live tool runs at
HEAD `4ad2ac1f`. The code is byte-identical to the CONTEXT's gather point `97cbbd08`
(`git diff 97cbbd08..HEAD -- src/ tests/ examples/ Cargo.toml fuzz/` is empty), so the CONTEXT's
measurements are current. D-02's `reqwest::chunk()` claim, D-14's "the existing budget test cannot
catch it" claim, D-18's 18-read count across four files, and D-113-R's measured cost table all
reproduce exactly. A short table of line-number drift is in § "Corrections to CONTEXT.md
References" — all cosmetic, none changing a decision.

**Three findings materially change how the phase must be planned, and none of them is in
CONTEXT.md.**

1. **D-06's two prescribed extractions do not clear the gate, let alone reach D-10's ≤20.**
   Measured by applying the extractions in a scratch tree and re-running PMAT: `resolve_v2_gate` +
   `dispatch_message_fast` land the handlers at **26 and 28** — both still above the hard ceiling
   of 25. The reason is that PMAT's cognitive score for these functions tracks `nesting_max`
   almost exactly (cog ≈ 3 × nest), so an extraction that does not remove the *deepest* nested
   block buys **zero** points. § "Architecture Patterns → Pattern 1" gives a measured menu of
   extraction candidates with exact deltas and names the minimal set that reaches ≤20.

2. **D-12 (the cursor fix) and D-15 (removing the `debug_assert`) cannot be separate tasks.** In a
   debug build — which is what `cargo test` produces — the cursor fix *alone* leaves the scan
   quadratic, because the `debug_assert!(!self.buffer.contains('\n'))` is itself a full-buffer scan
   per call. Measured: at 256 KiB in 1-byte chunks the cursor fix alone goes 2015 ms → 1067 ms
   (still 15.3× growth for a 4× input step — the O(n²) signature), while cursor + assert-removal
   goes to 13.55 ms (4.0× growth — linear). D-13's RED-first budget test and D-16's ratio test
   both stay RED after D-12 unless D-15 lands with it.

3. **Bounding `connect_sse` with a `chunk()` accumulator moves the defect from one tripwire list
   to another.** The tripwire's `ACCUMULATION_NEEDLES` include `extend_from_slice(` and `push_str(`,
   and `src/shared/sse_optimized.rs` is in scope with an existing pinned population of
   `push_str(` count=1. A `chunk()` loop appending into a buffer will either create a new
   un-allowlisted `(file, needle)` population or move the pinned count — either way
   `every_peer_byte_accumulation_is_reviewed` **fails**. D-05 only covers `WHOLE_BODY_ALLOWLIST`;
   the accumulation `ALLOWLIST` needs its own entry naming the 16 MiB running-total as the bound.

Two further verified facts de-risk the phase: **D-19 arm 2 shows no drift** (the live conformance
predicate at HEAD `89c2c045` is byte-identical in its disjunct set to the pinned `a865118`), making
it a small record-only task rather than an open investigation; and **`chunk()` introduces no wasm
regression**, because `--target wasm32-unknown-unknown --features sse` already fails to build at
HEAD with 17 pre-existing errors.

**Primary recommendation:** Plan three independent workstreams (they share no files), but inside
the complexity workstream size the extractions against `nesting_max` using the 0.5-second scratch-tree
probe in § "Code Examples", and inside the parser workstream treat D-12+D-15 as one atomic change
with the RED-first test written first.

### Pattern 3: Scan-window cursor over a newline-free retained prefix (D-12)

**What:** Keep `consumed` at 0 (it drives the drain and the CRLF lookback) but introduce a separate
`search_from` cursor initialised to the pre-`push_str` buffer length.

```rust
fn drain_complete_lines(&mut self, data: &str) -> Vec<SseEvent> {
    // INVARIANT (was a debug_assert!, removed per D-15 because it is itself an
    // O(len) scan per call and would keep this function quadratic in debug
    // builds): the drain loop below runs to exhaustion, so every call RETURNS a
    // newline-free buffer, and it starts empty. Pinned by
    // `drain_leaves_no_newline_in_the_retained_buffer`.
    //
    // That invariant is what makes `scan_start` sound: no '\n' can hide in the
    // retained prefix, so starting the search after it cannot miss a line.
    let scan_start = self.buffer.len();
    self.buffer.push_str(data);
    let mut events = Vec::new();

    let mut consumed = 0usize;
    let mut search_from = scan_start;
    while let Some(offset) = self.buffer[search_from..].find('\n') {
        let line_end = search_from + offset;
        // unchanged: byte-index CRLF lookback, `> consumed` (not `> 0`) so an
        // empty line never reads the previous line's terminator.
        let line_start_len =
            if line_end > consumed && self.buffer.as_bytes()[line_end - 1] == b'\r' {
                line_end - 1
            } else {
                line_end
            };
        let line = self.buffer[consumed..line_start_len].to_string();
        if let Some(event) = self.process_line(&line) {
            events.push(event);
        }
        consumed = line_end + 1;
        search_from = consumed;
    }
    self.buffer.drain(..consumed);
    events
}
```

**Correctness note the planner should pin with a test (this is D-15's CRLF-split case):** when the
retained prefix ends with `\r` and the new chunk begins with `\n`, `line_end == scan_start` and
`line_end - 1 == scan_start - 1` points *into the retained prefix*. The guard `line_end > consumed`
is `scan_start > 0`, which is true, so the `\r` is correctly trimmed. Keeping `consumed` at 0 —
rather than seeding it to `scan_start` — is what makes this work, and is why D-12 is right that
`consumed` must not move.

### Anti-Patterns to Avoid

- **Weakening the PMAT gate.** CLAUDE.md forbids disabling/weakening/removing it without
  Phase-level approval, and D-113-U repeats the prohibition. The hard cap for a `// Why:`-annotated
  `#[allow(clippy::cognitive_complexity)]` is 50, and D-113-F already ruled the escape hatch
  **not justified** for these two functions because they are reducible — which this research
  confirms (16/16 is reachable).
- **"Harmonising" the legacy-version guard call sites.** D-08. The asymmetry is load-bearing;
  `validate_protocol_version_with_error_hook`'s own rustdoc (`:3303-3304`) documents the folded
  init check.
- **Treating `sse_parser_feed_stays_within_its_linear_time_budget` as the D-113-R guard.** D-14,
  independently confirmed here: at 4 KiB chunking the defect is invisible.
- **Relying on `pmat analyze complexity --file <path>` to check your work.** It reports the two
  handlers at **14 and 18** — see § Pitfall 4.
- **Assuming `make quality-gate` covers PMAT.** Verified: it does not (`Makefile:673-690`).

## Common Pitfalls

### Pitfall 1: D-12 alone leaves the scan quadratic in debug builds — D-15 is load-bearing, not cleanup

**What goes wrong:** The planner treats D-12 (cursor) and D-15 (remove the `debug_assert`) as two
independent tasks, or sequences D-15 after D-12. D-13's RED-first budget test and D-16's ratio test
then stay RED after the "fix" lands, and someone concludes the cursor fix does not work.

**Why it happens:** `debug_assert!(!self.buffer.contains('\n'))` (`sse_parser.rs:487-490`) is itself
an O(retained-length) scan executed on **every** call. `cargo test` builds with
`debug_assertions = on`, so the assertion runs. Removing the `find` rescan while leaving the
`contains` rescan halves the constant factor and changes nothing asymptotically.

**Measured** — 1-byte chunks, no newline, `min` of 3 runs, this machine:

| n | HEAD today | D-12 cursor **only** | D-12 + D-15 |
|---|---|---|---|
| **debug** (`opt-level=0`, `debug-assertions=on` — what `cargo test` does) |
| 16 KiB | 9.58 ms | 5.14 ms | 0.83 ms |
| 64 KiB | 130.9 ms | 69.6 ms | 3.38 ms |
| 256 KiB | 2014.7 ms | 1067.0 ms | 13.55 ms |
| *growth for a 4× input step* | **13.7×–15.4× (O(n²))** | **13.5×–15.3× (still O(n²))** | **4.07×, 4.01× (O(n))** |
| **release** (`-O`, `debug-assertions=off`) |
| 16 KiB | 4.68 ms | 0.10 ms | 0.09 ms |
| 64 KiB | 50.3 ms | 0.27 ms | 0.26 ms |
| 256 KiB | 824.6 ms | 1.02 ms | 1.04 ms |

Note the release column reproduces `deferred-items.md` § D-113-R's recorded table (16 KiB → 5.6 ms,
64 KiB → 59 ms, 256 KiB → 833 ms) to within measurement noise — independent corroboration that the

### Pitfall 2: `#[deprecated]` on `OptimizedSseTransport` breaks `make lint` at the re-export and at every impl block

**What goes wrong:** D-01's `#[deprecated]` lands, `make lint` (which runs
`cargo clippy --features "full" --lib --tests` with `RUSTFLAGS = -D warnings`, `Makefile:11,152`)
fails with `error: use of deprecated struct` — in `src/shared/mod.rs`, not in the example D-04
anticipated.

**Why it happens:** rustc's `deprecated` lint fires on uses **within the defining crate**,
including `pub use` re-exports and the bodies of `impl` blocks on the deprecated type. Verified
empirically in this session with a minimal crate under `#![deny(warnings)]`:

- `pub use inner::Old;` where `Old` is `#[deprecated]` → **error** (`#[deny(deprecated)]` implied by
  `#[deny(warnings)]`)
- `impl T for Old { fn go(&self) -> u8 { self.n } }` → **4 errors** (the impl header and each field
  access)
- Both silenced by `#[allow(deprecated)]` on the item

`[VERIFIED: rustc empirical test, 2026-07-27]`

**How to avoid:**
1. Put `#![allow(deprecated)]` as an **inner attribute at the top of
   `src/shared/sse_optimized.rs`** — this covers all 15 in-file references to the two types in one
   line, rather than annotating each `impl`.
2. Add `#[allow(deprecated)]` to the re-export at `src/shared/mod.rs:106`.
3. **Deprecate only `OptimizedSseTransport`, not `OptimizedSseConfig`.** Verified: the only other
   in-crate consumer is `tests/sse_optimization_tests.rs`, which imports **`OptimizedSseConfig`
   only** (9 uses, no `OptimizedSseTransport`). `make lint` lints `--tests`, so deprecating the
   config would force a `#![allow(deprecated)]` on that test file too. Deprecating just the
   transport keeps it clean. This resolves the Claude's-Discretion item on `#[deprecated]` scope.

**Related correction to D-04's reasoning:** D-04 is right that `make lint` does not lint examples,
but `make quality-gate` → `test-all` → `test-examples` (`Makefile:361, 247-260`) **does build every
example** with `--all-features`. It still cannot fail on the deprecation, for two reasons verified
here: (a) the Makefile has no `export RUSTFLAGS` and `test-examples` does not prefix
`RUSTFLAGS="$(RUSTFLAGS)"`, so `-D warnings` is not in effect there; and (b) the recipe swallows
every failure into a yellow "requires specific features (skipped)" message and can never fail.
So D-04's `#![allow(deprecated)]` is correct hygiene, and the example's real verification must be
an **explicit** `cargo build --example t03_sse_optimized --features sse` in the plan — not a
reliance on `make`.

### Pitfall 3: The `chunk()` fix trips the tripwire's *accumulation* check, which D-05 does not cover

**What goes wrong:** D-113-Q is bounded, `WHOLE_BODY_ALLOWLIST` goes to 0 per D-05, and then
`every_peer_byte_accumulation_is_reviewed` fails with
`NEW accumulation site(s): src/shared/sse_optimized.rs ...`.

**Why it happens:** the tripwire has **two** allowlists. `ACCUMULATION_NEEDLES` (`:741`) is
`["extend_from_slice(", "push_str(", ".extend(", ".append("]`, and `src/shared/` is in scope. The
current pinned population for that file is:

| path | needle | count |
|---|---|---|
| `src/shared/sse_optimized.rs` | `push_str(` | **1** |

A `chunk()` loop must append somewhere. If it uses `buf.extend_from_slice(&chunk)`, that is a
**new** `(file, needle)` population with no `Accumulation` entry → `report_unreviewed` fires. If it
uses `push_str`, the pinned count moves 1 → 2 → `lines.len() > entry.count` fires. Either way the
test goes RED.

`[VERIFIED: tests/v2_bounded_reads_tripwire.rs:741, :855-900, and the ALLOWLIST population table]`

**How to avoid:** the plan needs an explicit task adding an `Accumulation` entry for the new site,
whose `why` names the mechanism — the running total checked against `DEFAULT_HTTP_SSE_BUFFERED_BYTES`
before each append — and satisfies `MIN_JUSTIFICATION_CHARS = 40`. This is the *good* outcome: it
is exactly the "the reasoning lives in the allowlist" design the tripwire documents. But it is a
second tripwire edit that D-05 does not mention, and a plan that only does D-05 will fail.

**Warning signs:** a plan for D-113-Q with exactly one `tests/v2_bounded_reads_tripwire.rs` task.

1. **Does `resolve_v2_gate` need `&HttpIngress` or can it take the three discriminating booleans?**

     `Public(_)` fallthrough, and use `matches!(ingress, Discover{..})` for the method override.
     Passing `&HttpIngress` reproduces both exactly.
   - *What's unclear:* whether borrowing `ingress` across the `.await` conflicts with the later
     `match ingress` (by value) on the fast path. On the middleware path `ingress` is moved into
     `dispatch_message_with_middleware` *after* the gate, and that already works today with the
     inline `match &ingress`, so the borrow ends before the move.
   - *RESOLVED (plan 113.1-01 Task 1):* take `&HttpIngress`. The existing inline code already borrows it across the
     same `.await`, so this is a no-op change in borrow terms. Verify at compile time, not by
     analysis.

2. **Should the read/classify preamble extraction be one helper or two per path?**
   - *What we know:* the measured 23 / 21 deltas came from collapsing body-read + `validate_headers`
     + parse + `is_init_request` into a single `Result<_, Response>` helper per path. The fast path's
     parse-error arm calls `map_unparsed_body_for_v2`, which returns a `Response`, so a single
     `Result` return type works.
   - *What's unclear:* whether one helper returning a 5-field struct reads better than two smaller
     ones, and whether Phase 114 will want to insert a step in the middle.
   - *RESOLVED (plan 113.1-05 Task 1):* one helper per path returning a named struct (`FastIngress` / `MwIngress`),
     mirroring the existing `FastPathDispatch` / `MiddlewareDispatch` convention for "bundle of
     per-request values threaded onward." Do **not** share one helper between the paths — that is
     the pipeline unification D-06 rejects.

## Security Domain

> `security_enforcement` is not set to `false`, so this section is included. Both D-113-R and
> D-113-Q are security defects, not merely quality defects — that is the whole reason HTTP-09
> exists and the reason this phase blocks a merge.

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no | Untouched. The 18 auth-surface reads are explicitly deferred to Phase 116 (D-18) |
| V3 Session Management | **indirectly** | The v2 gate must resolve **before** session resolution (HTTP-01); D-11's negative control A is what proves the extraction preserves that ordering |
| V4 Access Control | **indirectly** | `assemble_subscriptions_listen` is reached only after the full auth pipeline — *"a held-open stream must not be a way around auth"* (`:3221-3223`). Extracting `dispatch_message_fast` must not move it earlier |
| V5 Input Validation | **yes** | `validate_headers`, `run_v2_header_gate`'s fail-closed matrix, and the SSE tokenizer all run on peer bytes. No hand-rolled validation is added |
| V6 Cryptography | no | None involved |
| **V12/V13 — Resource consumption & API abuse** | **yes — the phase's subject** | Bounded reads (`DEFAULT_HTTP_SSE_BUFFERED_BYTES`, `collect_body_within_cap`) and O(n) scans over peer-chosen input |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation | Status |
|---------|--------|---------------------|--------|
| **Algorithmic complexity attack via chunk framing** — a peer sends 1-byte chunks; each `feed()` rescans the whole retained buffer | **Denial of Service** | Scan-window cursor (D-12) + remove the per-call `contains('\n')` scan (D-15) + falsifiable O(n) guards (D-13/D-16) | **OPEN — D-113-R.** Measured 833 ms of CPU for 256 KiB of peer input; quadratic, so 1 MiB ≈ 13 s |
| **Unbounded memory allocation from a peer-sized response** | **Denial of Service** | `chunk()` loop with a running total against a 16 MiB ceiling (D-02/D-03) | **OPEN — D-113-Q** |
| **Same defect class at a different trust boundary** (18 IdP reads) | Denial of Service | Same fix shape | **DEFERRED to Phase 116 by D-18** — semi-trusted IdP, not arbitrary peer. Recorded, not swept in |
| **Order-of-operations bypass** — v2 gate moved after session resolution or after legacy version validation | Elevation of Privilege / Spoofing | Ordering is currently enforced **only by prose comments** at `:3115-3124` and `:3571-3579` | **This phase's refactor is the risk event.** D-11's recorded negative controls are the mitigation; a permanent ordering tripwire was considered and deferred |
| **Response-id replay across requests** (HTTP-05) | Spoofing | `envelope_for_live_request(payload, live_id)` on every response path | Already enforced; the `dispatch_message_fast` extraction must preserve the `live_id = id.clone()` capture *before* dispatch consumes `id` |
| **Regression by omission** — a fix round caps the sites that round names, next review finds another | *(process)* | HTTP-09's "enumerable, not narrative" tripwire | The mechanism exists and is green; D-05 ratchets it to its floor |

**Threat-model note the planner should carry into the deferred item (D-18):** the distinction is
not severity, it is *who chooses the bytes*. `drain_complete_lines` and `connect_sse` read from an
arbitrary remote peer. The 18 auth reads read from an IdP the deployment configured. Same defect
class, different trust boundary — which is exactly why Phase 116, whose subject is re-examining
that trust assumption (RFC 9207 `iss` validation, DCR `application_type`), is the right owner.
