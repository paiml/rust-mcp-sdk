## 2. What was built

Four helpers, two per path, all **private**.

| Helper | Path | Effect |
|---|---|---|
| `read_and_classify_fast` → `FastIngress` | fast | 26 → 19 |
| `read_and_classify_with_middleware` → `MwIngress` | middleware | 28 → 18 |
| `guard_legacy_version_fast` | fast | 19 → 15 |
| `guard_legacy_version_with_middleware` | middleware | 18 → 15 |

**Two helpers per stage, never one shared helper.** A shared preamble is the pipeline unification
D-06 rejects, and the two genuinely differ: the middleware path converts the axum request, builds
the middleware context, runs the request-middleware chain, and hooks `report_middleware_error` on
header-validation failure.

### Struct field lists — stated exactly, not approximately

- **`FastIngress` — SIX fields**: `headers`, `body`, `ingress`, `session_id`, `protocol_version`,
  `is_init_request`. Verified: the struct has 6 fields and its rustdoc says SIX.
- **`MwIngress` — SIX fields, not the eight the plan sketched**: `server_request`, `http_context`,
  `ingress`, `session_id`, `protocol_version`, `is_init_request`. The plan anticipated this
  ("*if the lifted code leaves `headers` and `body` reachable through `server_request` … carry six
  fields here and say so in the struct's rustdoc*"), and that is the case: the handler reads
  `server_request.headers` and `server_request.body` downstream, so lifting them into separate
  fields would duplicate state. The struct's rustdoc says exactly this. Verified: 6 fields, rustdoc
  says SIX.

Both are documented as *different bundles at different pipeline stages* from `FastPathDispatch` /
`MiddlewareDispatch` (five fields), so the counts are not conflated.

### D-08's asymmetry preserved verbatim, and documented so it is not re-litigated

| | condition | callee |
|---|---|---|
| `guard_legacy_version_fast` | `!is_init_request && !is_v2_request` | PLAIN `validate_protocol_version` |
| `guard_legacy_version_with_middleware` | `!is_v2_request` **only** | `validate_protocol_version_with_error_hook`, passing `is_init_request` **in** |

The wrapper's own rustdoc reads *"A no-op for init requests"* — the init check is folded inside it
by design, and it additionally fires `report_middleware_error`, which the plain call cannot. Each
new helper's rustdoc states its own condition and cites **D-08** explicitly.

### What was deliberately NOT extracted

- **Session resolve and auth, on both paths.** RESEARCH measured all four at a **literal zero
  delta**; extracting them adds indirection for no gate movement.
- **`FastPathDispatch` / `MiddlewareDispatch` merge** — D-07, out of scope. Still two structs.

## 4. ⚠️ A defect this plan INTRODUCED and caught — both handlers lost their rustdoc

Worth recording because no gate would have caught it.

Inserting `guard_legacy_version_fast` / `guard_legacy_version_with_middleware` and the preamble
helpers immediately above each handler **silently re-attached each handler's 75-01 rustdoc to the
newly inserted helper**, leaving `handle_post_fast_path` and `handle_post_with_middleware` with **no
documentation at all**.

A doc comment has no anchor of its own — it binds to whatever item follows it. Because the resulting
comment was still *well-formed*, rustdoc emitted no warning, `make lint` stayed green, `make
quality-gate` stayed green, and the PMAT gate stayed green. It was caught by **reading the region**
while doing Task 3, not by any automated check.

Both rustdocs were moved back to their handlers and extended per Task 3. Recorded as a hazard for
any future phase inserting helpers adjacent to a documented item.
