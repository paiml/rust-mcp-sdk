<objective>
Close D-113-R: `SseParser::drain_complete_lines` restarts its `find('\n')` search at offset 0 on
every `feed()` call, so a peer that chooses 1-byte chunk framing gets one full-buffer rescan per
byte. Measured at 833 ms of CPU for 256 KiB of peer input in release, 2015 ms in debug — quadratic,
so 1 MiB is roughly 13 s. Both incremental feeders (`connect_sse` at `src/shared/http.rs:371-378`
and the listen client at `src/client/subscriptions.rs:248-255`) call `feed` once per peer-chosen
frame, so the framing is entirely the attacker's to pick.

Purpose: this is HTTP-09's clause 3 — *"no scan over peer-chosen input is worse than O(n)"* — and it
is the reason HTTP-09 stands at `[ ]` on the merits. It is a remote CPU-exhaustion channel, not a
tidiness issue.

Output: a scan-window cursor, the removal of the per-call `debug_assert` full-buffer scan (these two
are ONE atomic change — see Task 1), four new falsifiable guards, an amended rustdoc on the existing
weak guard, and a recorded fuzz campaign.

## Why the guards and the fix land in ONE task and ONE commit

The GSD executor commits after each task, and this project's CLAUDE.md makes green quality gates a
precondition for every commit. A task that deliberately ends with two failing tests would either be
blocked at commit time or, worse, land a RED commit in the branch history that any `git bisect` or
intermediate CI run would trip over. So Task 1 does the whole RED → GREEN cycle and commits once, at
green.

The RED evidence discipline is NOT weakened by this — it is strengthened. Task 1 requires **two**
recorded measurements, not one:

1. the **pre-fix RED run** (guards written, production untouched), captured verbatim as the
   uncommitted intermediate state; and
2. a **post-fix negative control** — revert the cursor to `find` from offset 0, watch the same two
   guards go RED again, record verbatim, restore.

(2) is the durable half: it is reproducible by anyone reading the committed tree, whereas (1) exists
only in the SUMMARY. A guard that cannot go RED is not a guard, and this phase requires both proofs.

### Phase A — write the four guards, run them, record RED (DO NOT COMMIT)

Add four tests to the existing `#[cfg(test)] mod tests` block. Write them BEFORE any production
change and run each one; record the measured value for every run.

**Guard 1 — absolute budget (D-13.1).** `sse_parser_feed_1b_chunks_stays_within_its_linear_time_budget`.
Constants: `const CHUNKS: usize = 512 * 1024;` and `const CEILING: Duration = Duration::from_secs(1);`.
Body: inside `min_elapsed(3, || { ... })`, build a fresh `SseParser`, feed a single byte per call
`CHUNKS` times using a byte that is neither `\n` nor `\r` (so nothing ever drains and the retained
prefix grows monotonically — that is the adversarial shape), and `std::hint::black_box` the parser.
Then pin correctness at the budget size the way the sibling does: assert `parser.buffered_bytes()`
equals `CHUNKS` and that no event was emitted, so "fast" has to mean "fast AND still holding every
byte". Emit the measurement on success with `eprintln!` naming the ceiling. The assert message must
name the ONE shape it excludes and must say **"Do NOT raise this number to make the test pass"**,
mirroring `:924-926`.

RESEARCH's extrapolated margins for the rustdoc table: fixed shape roughly 27 ms (about 37x under),
today's shape roughly 8 s (about 8x over). **Replace both with the values you actually measure** —
the rustdoc table must be measurement, not extrapolation.

The `max_buffer_size` default must admit 512 KiB. Read the parser's constructor before choosing
`CHUNKS`; if the default bound is smaller, construct the parser with an explicit larger bound rather
than shrinking the test, and say so in the rustdoc.

**Guard 2 — ratio (D-16).** `sse_parser_feed_cost_grows_linearly_not_quadratically`. Copy
`take_utf8_prefix_cost_grows_linearly_not_quadratically`'s shape exactly, including the
`RESOLUTION_FLOOR` skip and its note. Constants: `const SMALL: usize = 64 * 1024;`,
`const BIG: usize = 4 * SMALL;`, `const RESOLUTION_FLOOR: Duration = Duration::from_micros(50);`,
`const MAX_RATIO: f64 = 8.0;`. Both sizes fed in 1-byte chunks. RESEARCH measured the fixed shape at
4.01x and today's shape at 15.4x; 8.0 sits between them with roughly equal log-scale headroom.
Record your own measured numbers in the rustdoc and in the assert message.

**This is the machine-independent guard** — a slow or loaded CI box cannot flake it, and a
merely-worse-but-under-ceiling regression cannot slip past it. Guard 1 is the secondary.

**Guard 3 — chunking invariance (D-13.2).** `property_feed_chunking_invariance`, inside the existing
`proptest::proptest! { }` block next to `feed_never_panics_on_arbitrary_text`. Reuse that block's
established strategy `"(\\PC|\r|\n|\u{2602}|\u{4f60}){0,40}"` — it deliberately mixes `\r`, `\n` and
multi-byte characters, which is exactly the alphabet this property needs. Generate one text plus two
independent split-point vectors; feed the same text through two fresh parsers under the two
splittings; `prop_assert_eq!` the concatenated event sequences AND the retained buffers. Use
`prop_assert` forms, never bare `assert`, matching the block's convention.

**Both splittings MUST be at character boundaries**, and the guard's name and rustdoc must claim
exactly that and no more. `feed` takes `&str`, so a byte-level split is not merely untested — it is
**unrepresentable**: every `&str` is valid UTF-8 by construction, so no `feed` call can ever receive
half a character. Write the claim as *"arbitrary text under arbitrary character-boundary chunking"*,
NOT *"arbitrary byte stream"* — the strategy generates Unicode text, not arbitrary bytes. State in
the rustdoc that byte-fragment behavior is `take_utf8_prefix`'s responsibility and already has its
own coverage there, so a reader does not conclude this property has a hole.

Implement the splitting by generating the chunk vector directly and concatenating it to form the
reference text (which makes character-boundary safety structural), or by splitting on character
counts via `char_indices`. Never on raw byte offsets — that will not even compile against `&str`
slicing without panicking on a non-boundary index.

**Guard 4 — the invariant D-15 removes the assertion for.** `drain_leaves_no_newline_in_the_retained_buffer`.
It reaches the private `buffer` field directly through `use super::*` (the file's existing tests
already do this). Assert `!parser.buffer.contains('\n')` after each of: a mid-line split; a `\r` fed
in one chunk and the matching `\n` in the next; a bare empty line (`"\n\n"`); **a chunk boundary
placed immediately before and immediately after a multi-byte character** (not "a multi-byte
character split across two feeds" — that is impossible through `&str`, see Guard 3); and a chunk
that is exactly one `\n`. Give it a rustdoc in the shape of
`feed_does_not_panic_on_a_multibyte_char_before_a_later_cr` (`:1517`), naming what it guarantees and
stating plainly that it replaces the per-call `debug_assert` deleted below in this same task because
that assertion was itself an O(len) scan.

**Run all four now.** Guards 1 and 2 MUST be RED; guards 3 and 4 MUST be GREEN. Record every measured
number verbatim — the RED measurement is the evidence D-14 demands, because the file's existing
`sse_parser_feed_stays_within_its_linear_time_budget` was written to catch exactly this defect class
and PASSES on the defective shape. **Do not commit at this point.**

**Do NOT** run the perf guards with `--release` to make them behave. D-15 rejects that explicitly:

### Phase B — the atomic fix (D-12 + D-15), still uncommitted

Two edits. RESEARCH § Pitfall 1 measured why they cannot be separated: `cargo test` builds with
`debug_assertions = on`, and `debug_assert!(!self.buffer.contains('\n'))` is itself an
O(retained-length) scan on every call. The cursor fix ALONE moves 256 KiB from 2015 ms to 1067 ms —
still 15.3x growth for a 4x input step, i.e. still quadratic — so the guards would stay RED and
someone would conclude the fix does not work.

**Edit 1 — the cursor (D-12).** Capture `let scan_start = self.buffer.len();` **immediately before**
`self.buffer.push_str(data);`. Introduce `let mut search_from = scan_start;` alongside the existing
`let mut consumed = 0usize;`. Change the loop head to search from `search_from` instead of `consumed`
and compute `let line_end = search_from + offset;`. At the bottom of each iteration, set both
`consumed = line_end + 1;` and `search_from = consumed;`.

**`consumed` MUST stay initialised to 0.** It drives the final `self.buffer.drain(..consumed)` and the
CRLF lookback guard. Seeding it to `scan_start` would break the case RESEARCH pins: when the retained
prefix ends with `\r` and the new chunk begins with `\n`, `line_end == scan_start` and `line_end - 1`
points INTO the retained prefix; the guard `line_end > consumed` is then `scan_start > 0`, which is
true, so the `\r` is correctly trimmed. With `consumed` seeded to `scan_start` that guard would be
false and the `\r` would leak into the line.

Everything else in the loop is unchanged and must stay so: `line_end` remains a BYTE index; the CRLF
lookback stays `self.buffer.as_bytes()[line_end - 1] == b'\r'` and never `chars().nth(...)` (that was
the remote-panic bug T-113-67); the guard stays `line_end > consumed`, not `> 0` and not
`> search_from`. The final `self.buffer.drain(..consumed)` is unchanged.

**Edit 2 — delete the `debug_assert` (D-15).** Remove the whole `debug_assert!(...)` statement at
`:487-490`. Replace it with a prose comment stating (a) the invariant — the drain loop runs to
exhaustion and `process_line` never touches `buffer`, so every call RETURNS a newline-free buffer and
it starts empty; (b) why that invariant is now the SOUNDNESS PRECONDITION for `scan_start` — no `'\n'`
can hide in the retained prefix, so starting the search after it cannot miss a line; (c) why the
assertion was deleted rather than kept — it was itself an O(len) scan per call and kept the function
quadratic in debug builds, which is where `cargo test` and the 1-byte-chunk proptest run; and (d) the
name of its replacement pin, `drain_leaves_no_newline_in_the_retained_buffer`. Follow
`feed_complete_body`'s precondition-block convention at `:441-460`.

Also update the existing "LINEAR, not quadratic" comment at `:494-499`: it currently describes only
the per-LINE drain quadratic fixed in `0493d9fb`. Extend it to name the distinct per-CALL quadratic
this change fixes (D-113-R) so a future reader does not conflate them.

Now re-run all four guards. All four MUST be GREEN, and the ratio guard MUST report growth near 4x,
not near 15x. Record every measured value and write the real numbers into both perf guards' rustdoc
tables, replacing Phase A's provisional entries.

**Do NOT** `#[cfg]`-gate the assertion instead of deleting it, and do not move the perf tests to
`--release`. D-15 rejects both.
