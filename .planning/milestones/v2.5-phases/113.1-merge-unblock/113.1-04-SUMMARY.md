**Method.** Column 1 is a NAIVE line-grep for the tripwire's `WHOLE_BODY_NEEDLES`
(`tests/v2_bounded_reads_tripwire.rs:562`) — what a raw grep of the source returns. Column 2 counts
the additional `.json()` / `.text()` / `.bytes()` chains that rustfmt has **split across lines** so
`.await` lands on the next line, which a raw grep misses; found by a line-pair scan. **The tripwire
itself sees both columns — 33 — because its scanner strips whitespace first.** Column 3 is the
reviewed subset: every match in columns 1 and 2 opened and read, minus those confirmed bounded or
at a different boundary.

**Why CONTEXT and the roadmap undercounted.** ⚠️ **Corrected after review — my first statement of
this was wrong.** I wrote that the tripwire's needles are single-line substrings that miss
rustfmt-split chains. They are not: the scanner's `strip()`
(`tests/v2_bounded_reads_tripwire.rs:324`) removes ALL whitespace before matching, and
`scanner::a_rustfmt_broken_chain_is_matched_and_reports_its_first_line` (`:1050`) pins exactly that
on `body\n.collect()\n.await`. **The tripwire would find all 33.**

The "18" is simply what a raw line-grep returns (measured: 19). The real and only reason these
reads go unreported is the **SCOPE FENCE** — the four files are in neither `SHARED_DIR` nor
`EXTRA_SCOPE`, so the scanner is never pointed at them. The count of **31** reviewed-unbounded is
unaffected by the correction; the explanation is.

Even the raw column corrects CONTEXT: `src/client/oauth.rs` measures **5** raw matches, not 4, so
CONTEXT's 5/5/4/4 = 18 should have been 5/5/4/5 = 19. (The roadmap's "three files" is also wrong;
CONTEXT's correction to four is right.)

All matches sit above each file's `mod tests` (`:770`, `:431`, `:536`; `oauth.rs` has none), so
every one is production code, not test code.

### Two exclusions — recorded, not rounded away

The plan required that a match already carrying a local bound be *excluded and said so*, rather than
kept to preserve a round number. Two qualified:

1. **`src/client/oauth.rs:282`** (`.bytes().await`) is **ALREADY BOUNDED** —
   `const MAX_DCR_RESPONSE_BYTES: usize = 1_048_576` at `:280`, checked at `:285`. Excluded.
   Recorded for Phase 116 with a caveat that matters: it is a **post-hoc** check — the body is
   allocated whole and *then* measured — so it bounds what is ACCEPTED, not what is ALLOCATED. That
   is strictly weaker than `collect_body_within_cap`'s streaming bound, and is the shape 113-20
   deliberately moved away from.
2. **`src/client/oauth.rs:953`** (`tokio::fs::read_to_string(cache_file)`) reads the SDK's **own
   token-cache file off local disk**. Not an IdP read, not a network read, not this defect class.
   Excluded.

A grep of the four files for cap machinery (`MAX_*BYTES`, `content_length`, `Limited::`,
`within_cap`, `max_bytes`) returns hits in `oauth.rs` only — confirming the other three files carry
no bound anywhere.

### The trust-boundary distinction, stated as the reason and not as an excuse

`drain_complete_lines` (D-113-R) and `connect_sse` (D-113-Q) read from an **arbitrary remote peer**:
anyone who can open a connection chooses those bytes. These 31 read from an **issuer the deployment
configured**. Same defect class, different adversary — a statement about *who chooses the bytes*,
not a claim the reads are harmless. The entry says so explicitly: a compromised, misconfigured or
MITM'd IdP reaches the same `Vec` growth, and an `unwrap_or_default()` error-path read will happily
allocate a multi-gigabyte "error message".

**Why Phase 116 owns it:** its subject is re-examining exactly that trust assumption (RFC 9207 `iss`
validation, DCR `application_type`, issuer-keyed credential storage). A bound landed before that
re-examination would defend a trust model about to change.

**Why the fence was not widened:** it mirrors HTTP-09's text verbatim, which scopes to a
peer-controlled read on the v2 transport path. Widening needs a home requirement first — editing
HTTP-09 is forbidden by this phase's success criterion, and minting a new one is milestone-scoping
work inside a merge unblock. Cross-referenced to the existing deferred idea rather than duplicated.

**A corollary handed to Phase 116 — also corrected:** widening the fence is SUFFICIENT. The needle
set needs no change, because the scanner already resolves rustfmt-split chains. Adding
`src/server/auth/` and `src/client/oauth.rs` to `EXTRA_SCOPE` surfaces all of them unaided.
