## 2. The bounded read

`collect_sse_text_within_cap(mut response, max_bytes) -> Result<String>`, placed immediately before
`connect_sse`, implementing the two-refusal doctrine verbatim from
`streamable_http.rs`'s `collect_body_within_cap`:

1. **Advisory** — a declared `Content-Length` over the cap refuses before a single body byte is
   read. Never the authority.
2. **Authoritative** — bytes are accumulated through `Response::chunk()` with a running total
   checked **before each append**, so an over-cap body is never held whole.

The over-cap comparison is `chunk.len() > max_bytes - accumulated.len()`, **overflow-safe by
construction**: `accumulated.len() <= max_bytes` is the loop invariant, so the subtraction cannot
underflow and no unguarded `a + b` is ever computed.

`chunk()` and not `bytes_stream()` (D-02): `chunk()` carries no `cfg`, while `bytes_stream()` is
behind `#[cfg(feature = "stream")]`, which this crate does not enable. **Zero dependency-surface
change.**

Decoding is `String::from_utf8_lossy`, matching the lossy tolerance `.text()` already had — so this
is a bound and not also a strictness change.

`max_bytes` is a **parameter**, not a new `OptimizedSseConfig` field: that struct's fields are all
`pub`, so adding one is `constructible_struct_adds_field`. Verified no field was added.

The caller's `let response` stayed **immutable**; the `mut` is on the helper's parameter, because
the helper takes the response by value and a `mut` at the call site would never be read and would
trip `unused_mut` under `-D warnings`.

## 3. The test set and the recorded negative control

Five tests at `const CAP: usize = 512;` — costing bytes, not megabytes, which is exactly why
`max_bytes` is a parameter.

| Test | What it pins |
|---|---|
| `connect_sse_one_byte_over_the_cap_is_refused` | Over-cap refused with **no `Content-Length` at all** (`with_chunked_body`), so only the authoritative running total can produce the pass (T-113-93) |
| `connect_sse_at_exactly_the_cap_is_admitted` | The comparison is `>` and not `>=`; the admitted body still carries its `data:` line, blocking a "fast because it read less" regression |
| `declared_content_length_over_the_cap_is_refused_without_reading_the_body` | The early-refusal branch — a stated truth of this plan, so it gets a test. 513 bytes vs a 512 cap exercises it exactly; no 16 MiB transfer needed |
| `connect_sse_under_the_cap_still_delivers_a_message_to_recv_tx` | The **wiring** test: an admitted body still flows through `connect_sse` itself into the channel |
| `assert_over_cap_refusal` (helper) | The refusal NAMES the limit and echoes **no** body content |

**The wiring test earned its keep immediately.** It failed on first run — not because of the cap,
but because my fixture body `{"jsonrpc":"2.0","method":"ping"}` does not deserialize into a
`TransportMessage` (a bare `method` with an `id` is not a valid variant). `connect_sse` silently
drops unparseable `data:` lines (`if let Ok(msg) = …`), so without this test the plan would have
shipped believing delivery was proven. Corrected to a `Notification` frame,
`{"jsonrpc":"2.0","method":"notifications/initialized"}`, which round-trips. This is precisely the
failure mode the plan added the wiring test to catch.
