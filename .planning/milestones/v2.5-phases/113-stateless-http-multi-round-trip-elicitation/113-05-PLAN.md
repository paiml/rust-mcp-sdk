<objective>
Make the pmcp `Client` a v2 speaker: an explicit per-connection opt-in mirroring the server
accept-list, a DEFINED mechanism for getting that selection into the transport, per-request
`_meta` carrying `protocolVersion`/`clientInfo`/`clientCapabilities`, the three required
outbound headers with correct `Mcp-Name` derivation and base64-sentinel encoding, no
`initialize` handshake, no `Mcp-Session-Id`, era-aware capability enforcement, and a
`server/discover` call.

Purpose: RESEARCH Pitfall 7 measured the gap — the client transport emits ZERO
`Mcp-Method`/`Mcp-Name` headers today, so against pmcp's own Phase-112 strict header gate every
v2 request from a pmcp client is rejected.

Cross-AI review raised four HIGH issues here, all resolved in this revision: (1) the plan never
said how a generic `Client<T>` propagates the mode into `T` — it now uses an additive defaulted
`Transport` method, and `StreamableHttpTransport` already owns a `protocol_version` field that
feeds header emission; (2) `assert_capability` reads `server_capabilities`, which is populated
ONLY by `initialize` — on v2 every `call_tool` would fail locally before sending, so enforcement
is now era-aware; (3) the plan's "name-less methods emit no `Mcp-Name`" contradicted the
server's `require_three_headers`, which demands presence — the locked rule is presence-always
with an EMPTY value; (4) the non-ASCII live test needs plan 04's server decoder, so this plan
now depends on 113-04 and moves to wave 3.
Output: an additive transport seam, an opt-in builder method, a v2-aware transport emitter, and
a live client↔server suite.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → network | Outbound headers and `_meta` cross an untrusted network and any intermediary/WAF |
| caller → client capability claims | The application decides which host handlers exist; the client must not let a caller over-claim |
| server → client capability enforcement | On v2 the server, not a stale local cache, is the authority on what it supports |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-113-08 | Tampering | header/body desync originating at the client | mitigate | `Mcp-Method`/`Mcp-Name` are DERIVED from the body the transport is about to send, using the same `logical_name_key` table the server reads — the two cannot be constructed independently |
| T-113-12 | Spoofing | client over-claiming `clientCapabilities` | mitigate | Capabilities are derived from `ClientHostRegistry` rather than caller-supplied; documented that a lying client only harms itself and that the server must never derive authorization from `clientCapabilities` |
