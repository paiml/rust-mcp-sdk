<objective>
Take the `subscriptions/listen` fuzz seam back out of the shipped public API, give the
libFuzzer campaign an invariant that could actually have caught the GAP-A defect, and run
the cross-cutting phase gate over the whole gap-closure round.

This plan is WAVE 3, not wave 2, and depends on 113-20 as well as 113-17 and 113-18. That is
deliberate: its Task 2 is the phase gate for the ENTIRE round, so it must run after the last
plan that changes code. When 113-20 was split out of 113-17 it took the collected-body cap
with it; leaving this plan in wave 2 would have let the gate run in parallel with — or before
— that work, and the gate would then have certified a tree that did not contain it.

Purpose: two findings the verifier recorded remain open. `decode_listen_chunks_for_fuzz` is
`pub` inside `pub mod client` → `pub mod subscriptions`, so `#[doc(hidden)]` hides it from
rustdoc but not from semver or from downstream callers — real public-API surface that plan
113-16 never declared, committing the SDK to a `&[&[u8]]` chunk model, an unvalidated
`max_buffer_size: usize` (`0` is accepted and latches the parser on the first non-empty
chunk), and errors flattened to `String`. Separately, the fuzz target's Invariant 3 ("the
latch never clears") cannot fail for any input at any bound — `overflowed` has exactly one
write site and no clearing path — while the property the campaign exists to defend,
bounded memory, is asserted nowhere. That is structurally why 20,000 green runs coexisted
with the still-open GAP-A defect.

Output: the seam gated behind the crate's established `fuzzing` feature, a real
peak-retention assertion in the target, a re-run recorded campaign, and the phase-level
build/semver/quality gate over plans 113-17 + 113-18 + this one.
</objective>
