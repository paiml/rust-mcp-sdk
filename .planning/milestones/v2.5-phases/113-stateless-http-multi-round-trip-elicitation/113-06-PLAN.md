<objective>
Wire the server-side INGRESS half of MRTR: extract `inputResponses`/`requestState` from the raw
request params at HTTP ingress (rejecting malformed input rather than ignoring it), thread them
on the Phase-112 `ProtocolContext`, verify the token against the live principal and originating
request using the SERVER-OWNED codec, route the four verdicts per D-15 with EXACT re-elicitation
mechanics, and surface the decrypted continuation plus the input responses to the handler
through `RequestHandlerExtra`.

Purpose: HTTP-03's "a client retry resumes the operation" is entirely this path. It is also
where the phase's security posture is decided — the conformance suite's
`sep-2322-reject-tampered-state` check fails a server that re-prompts on a tampered token, while
D-04's multi-instance degradation requires exactly the opposite behavior for an unknown key.

Both reviewers converged hardest on ONE gap here: the original plan said `UnknownKey` and
`Expired` should "return an `input_required` result with a FRESH `requestState` and no
`inputRequests`" — but with no decrypted continuation there is nothing meaningful to seal, and a
state-only result tells the client to retry into the same failure forever. This revision defines
the mechanics precisely: STRIP the MRTR fields and RE-RUN the original handler, which
regenerates both the `inputRequests` and the continuation from scratch. Plan 03 now returns
`Expired(Continuation)` so the round counter survives.
Output: a MRTR-aware `ProtocolContext`, one shared ingest helper called from both dispatch sites,
new `RequestHandlerExtra` accessors, and a live-HTTP verdict suite.
</objective>
