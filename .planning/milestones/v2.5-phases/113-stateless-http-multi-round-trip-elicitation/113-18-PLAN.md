<objective>
Resolve the `subscriptions/listen` reconnect ambiguity by making the fresh-id contract
EXPLICIT and TRIPWIRED, and by making the duplicate refusal RETRYABLE — not by trying to
detect remote liveness, which the transport cannot do. Then close GAP-C's semaphore leak.

Purpose: `113-VERIFICATION.md` recorded an ordinary reconnect being answered `-32600

the HTTP class for "do not retry" — for a condition that is purely transient server state.
The wrong half of that is the NON-RETRYABILITY, and that is what this plan fixes. The
"detect the dead incumbent and reclaim its key" half is not implementable at this layer
(see `<disclosed_decision>`), and pursuing it would repeat 113-15's failure of shipping a
fix for a state production cannot enter.

Output: `DuplicateSubscriptionId` answered with the retryable `RATE_LIMITED`, the fresh-id
contract documented in three places and pinned by a live tripwire, the four protected
113-14 tests carried forward with updated assertions but intact protective intent, and the

<disclosed_decision>
## The liveness-aware reclaim is deliberately NOT implemented

This must be carried verbatim into `113-18-SUMMARY.md` so the re-verifier reads an
evidenced choice, not an unclosed gap.

**Fact 1 — `sender.is_closed()` cannot observe remote death.**
`src/server/streamable_http_server.rs:2973` builds the SSE body as
`futures_util::stream::unfold((receiver, guard), ...)`. The `mpsc::Receiver` and the
`ListenGuard` live in the SAME stream-state tuple. A dead remote TCP peer does not close
the receiver; the receiver stays alive until Hyper drops the response body — at which
moment the guard drops too and RAII already reclaims the entry. So throughout the entire
~15 s keep-alive window the regression describes, `is_closed()` is `false` and a same-id
reconnect is STILL refused. The reclaim would only ever fire in a window where the entry is
being removed anyway.

**Fact 2 — pmcp's own client never reuses a subscription id.**
`src/client/mod.rs:3953` in `Client::subscriptions_listen` does
`let request_id = RequestId::String(Uuid::new_v4().to_string());` — a fresh UUID per call.
The scenario cannot occur with pmcp's client at all.

**Consequence.** The verifier's reproduction was doubly artificial: it dropped the receiver
while holding the guard (a state production cannot produce) AND reused the id (which pmcp
never does). Both the reported severity and the previously-planned fix rested on that same
artificial premise.

**Residual, stated plainly.** A THIRD-PARTY client that reuses a subscription id after an
ungraceful disconnect still waits out the incumbent guard. What changes is that it now
receives a RETRYABLE refusal and can back off, and pmcp's own client is structurally
immune. Automatic same-id takeover of a connection the server still considers live is NOT
safe for co-tenants without an authenticated takeover token, which is out of scope for this
gap-closure round.
</disclosed_decision>

1. **Understand the reachability before you write the test.** `Semaphore::try_acquire_owned`

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated client → `ListenRegistry::register` | The `subscriptionId` half of `ListenKey` is CALLER-CHOSEN (it is the JSON-RPC request id). The `principal` half is SERVER-derived from `AuthContext.subject`, or an `anonymous_principal()` per-stream counter when no auth provider is configured. |
| co-tenants of ONE principal → each other's streams | Several tabs, a shared service account, or a token with a constant `sub` collapse onto one principal and can choose the same id. This is the half `ListenKey`'s pairing does NOT close. |
| remote TCP peer → the server's view of stream liveness | **NOT OBSERVABLE at this layer.** The receiver and the guard live in one `stream::unfold` state tuple, so a dead peer is indistinguishable from a live one until Hyper drops the response body.
