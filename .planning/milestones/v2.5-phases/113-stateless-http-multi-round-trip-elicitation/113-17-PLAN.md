<objective>
Make `SseParser`'s `max_buffer_size` an actual upper bound on everything the parser
retains, so a hostile or merely broken v2 server can no longer grow a pmcp client's heap
by streaming ordinary newline-terminated `data:` lines on a long-lived
`subscriptions/listen` stream.

Purpose: `113-VERIFICATION.md` gap item 3 is still OPEN and was independently reproduced
against the built crate — `feed("data: AAAAAAAA\n")` x100,000 under
`with_max_buffer_size(64)` accumulates **899,999 bytes** with `overflowed() == false`, and
a single `data:` line of **1,000,000 bytes** delivered with its terminating newline is
accepted whole with `overflowed() == false`. Plan 113-15 bounded only the case where the
peer never sends a newline at all, which is the artificial edge case rather than the
realistic one. HTTP-04 / Success Criterion 3 ("memory-bounded long-lived stream") cannot
be verified until this closes.

Output: an unconditional in-flight bound in `SseParser::feed`, a `buffered_bytes()`
accessor that makes the bound observable, an explicit `feed_complete_body` bypass for the
two collected-body transport call sites, corrected contract documentation, and regression
tests that drive NEWLINE-CARRYING floods (the input class every existing bounding test
and doctest avoids — review IN-03).
</objective>

<config_surface_decision>
## Neither public config struct may gain a field — MEASURED, not assumed

This plan needs two independently configurable byte limits. Both are for CLIENT transports,
and neither may be expressed as a new `pub` field on the existing public config structs.

**The measurement.** A scratch probe added one `pub` field to `HttpConfig`
(`src/shared/http.rs:26`) and ran the gate:

`cargo semver-checks check-release --baseline-version 2.17.0 -p pmcp`
→ `223 checks: 222 pass, 1 fail` —
`constructible_struct_adds_field: externally-constructible struct adds field` —
`Summary semver requires new major version: 1 major and 0 minor checks failed`.
The probe was reverted (`git checkout -- src/shared/http.rs`, tree clean).

`HttpConfig` derives `Default`, and that does NOT help: the lint fires because a downstream
crate can construct the struct with a literal listing every field, which `Default` does not
prevent. `StreamableHttpTransportConfig` (`src/shared/streamable_http.rs:99`) is worse — all
fields `pub`, no `Default` derive, and its own rustdoc contains THREE struct-literal examples
enumerating every field (lines 64-96). Neither struct is `#[non_exhaustive]`, and RETROFITTING
`#[non_exhaustive]` is itself a breaking change for exactly the same reason.

This matters beyond style: plan 113-12 established `cargo semver-checks` 223/223 with no
update required and `cargo public-api` zero removed items as the milestone's provably-additive
property. v2.5 must stay a 2.x MINOR. A `pub` field on either struct forfeits that.

**Decision — option (a): named constants plus non-breaking override seams.**
For each limit: a named module constant for the default, a PRIVATE field on the TRANSPORT
struct initialised from it, and an additive inherent builder method to override it. Verified
feasible: `HttpTransport` (`src/shared/http.rs:55`) and `StreamableHttpTransport`
(`src/shared/streamable_http.rs:291`) both have entirely PRIVATE fields, so adding one is
invisible to semver, and adding an inherent method is additive.
- the SSE in-flight ceiling (THIS plan, Task 2 item 4) → `DEFAULT_HTTP_SSE_BUFFERED_BYTES` +
  a seam on `HttpTransport`
- the collected-body cap (plan **113-20**, wave 2) → its own named constant + a seam on
  `StreamableHttpTransport`
This block governs BOTH, and 113-20 references it rather than restating the measurement.

`StreamableHttpTransportConfigBuilder` is NOT the right home for 113-20's cap: its `build()`
returns `StreamableHttpTransportConfig`, which cannot carry the value without the break above.

**And the "one concept, one surface" goal is explicitly DROPPED (option c's honesty clause).**
The two limits are NOT unified, and the earlier instruction to wire them through one surface
was based on a shared surface that does not exist — `grep -c HttpConfig src/shared/streamable_http.rs`
is 0; the structs have no shared field and no embedding. They are also two DIFFERENT concepts:
this plan's ceiling bounds INCREMENTAL in-flight retention on a long-lived reader, while
113-20's cap bounds a ONE-SHOT collected body. Document both, and document that they are deliberately separate.
</config_surface_decision>

In `src/shared/sse_parser.rs`:

1. Add `pub(crate) fn buffered_bytes(&self) -> usize` returning
   `self.buffer.len() + self.current_event.data.len()` — the two UNBOUNDED accumulators.
   `pub(crate)` deliberately, not `pub`: its only consumers are this file's tests,
   `src/client/subscriptions.rs`, and (via that module) the fuzz seam, so it must not widen
   the shipped public API. Document it precisely (review LOW): it is NOT "total retained
   bytes". It EXCLUDES `current_event.id`, `current_event.event` and `last_event_id`, and an
   `id:` value is retained TWICE (once in `current_event.id`, once in `last_event_id`).
   Those fields are each ASSIGNED from a single line rather than appended to, and a line can
   only reach `process_line` if the chunk carrying it satisfied the bound, so each is itself
   bounded by roughly `max_buffer_size` and none can grow with stream age. State that the
   true ceiling is therefore a small constant multiple of `max_buffer_size`, and that
   `buffered_bytes` bounds the only two quantities that accumulate ACROSS lines — which is
   the property that matters and the one GAP-A violated.

2. Replace `feed`'s pre-check. Today it reads
   `self.buffer.len().saturating_add(data.len()) > self.max_buffer_size && !data.contains('\n')`.
   DROP the `!data.contains('\n')` term entirely — that term is precisely what makes the
   bound unenforceable (CR-02), and its accompanying comment (the paragraph claiming the
   `data` condition "is what keeps a single legitimately large COMPLETE body working")
   must go with it. The new condition is
   `self.buffered_bytes().saturating_add(data.len()) > self.max_buffer_size`, unconditional.
   Keep the existing discard behaviour on trip: latch `self.overflowed = true`, clear
   `self.buffer`, reset `self.current_event` to `EventBuilder::new()`, leave
   `self.last_event_id` untouched (it is stream-level resumption state), and return an
   empty `Vec`. Never truncate-and-emit.
   **DECIDED, and it must be documented rather than glossed (review MEDIUM-1): this bound is
   `retained state + THIS CHUNK`, not "one in-progress event".** A chunk carrying many
   individually small COMPLETE events is refused whenever the chunk total exceeds the limit,
   so behaviour depends partly on the transport's framing. We ACCEPT that rather than
   restructuring, because evaluating the bound only over what survives after splitting
   complete events out of the chunk would require parsing the whole unbounded chunk first —
   i.e. performing exactly the allocation the bound exists to prevent. The mitigations are
   that Task 2 item 4 makes the general ceiling configurable, and that the listen path's 256 KiB
   sits well above a typical transport read frame. The obligation this creates is on the
   PROSE: no rustdoc, comment or error message anywhere may claim that "one undelivered
   event exceeded the bound". They must say the retained state plus the incoming chunk
   exceeded it. This constrains item 6 here and both messages in Task 2.

3. Change the POST-drain residual check from `self.buffer.len() > self.max_buffer_size` to
   `self.buffered_bytes() > self.max_buffer_size`, so the invariant that holds on RETURN
   from `feed` is over both accumulators. Its existing comment about a chunk that begins
   with a newline stays accurate and should be extended to name the event accumulator.

4. Add `pub(crate) fn feed_complete_body(&mut self, body: &str) -> Vec<SseEvent>` — the
