<objective>
Correct a false statement about the MCP specification that pmcp currently ships in public
rustdoc, and record a decision for the one subscriptions coverage gap the phase has never
scoped.

Purpose: `src/server/subscriptions.rs:17-18` tells every reader of pmcp's docs that "there is
no polling shape for change notifications anywhere in the MCP spec". The spec defines exactly
that: `caching.mdx` § 110-118 specifies TTL-driven re-fetch through `ttlMs` and `cacheScope`
(SEP-2549) and explicitly blesses relying on it *instead of* `listChanged`. The sentence is
load-bearing — it is the stated reason D-11 positions Tasks-polling as pmcp's recommended
enterprise mechanism — so leaving it wrong means the positioning rests on a falsehood even
though the positioning itself is correct. pmcp implements none of `ttlMs`/`cacheScope`
(measured: zero hits in `src/`), which is tracked as SCHM-03 in Phase 115, and that is the
honest thing for the doc to say.

The second half is a scoping question the phase has quietly carried: the schema says
`subscriptions/listen` exists for "consistent behavior between HTTP and STDIO", and pmcp serves
it on HTTP only. This plan does not implement stdio listen and does not pretend the gap does
not exist. It records the gap as a deferral with its evidence and the specific reason it is
blocked, so the decision is reviewable and reversible instead of invisible.

Output: a corrected and self-guarding rustdoc, a recorded D-113-Q deferral, and dispositions
written back into the addendum for Findings 13 and 14(a).
</objective>

THE FALSE CLAIM, VERBATIM AND IN CONTEXT

  `src/server/subscriptions.rs` module rustdoc, the `# D-11` block. The paragraph reads:

    "It is, however, a pmcp EXTENSION and **not** a conformant substitute: there is
     no polling shape for change notifications anywhere in the MCP spec. This
     stream exists because it is the only spec-conformant delivery shape for
     `listChanged`, ..."

  Two clauses are wrong, not one. The second ("the only spec-conformant delivery shape") is
  wrong for the same reason as the first: `caching.mdx` blesses TTL re-fetch as an alternative
  to `listChanged`. Correct BOTH; correcting only the sentence the addendum quoted leaves the
  same falsehood standing one clause later.

  What is TRUE and must survive the edit: the D-11 conclusion. Tasks-polling is a pmcp
  extension and is not a conformant substitute for `subscriptions/listen`. That stays. What
  changes is WHY: not "the spec has no polling shape" but "the spec's polling shape is
  `ttlMs`/`cacheScope`, which is a different mechanism from Tasks-polling and which pmcp does
  not implement yet".

MEASURED FACTS (verified; cite, do not re-derive — but DO re-run the grep to confirm it still
holds at execution time, because SCHM-03 could land before this plan runs)

  `grep -rn "ttlMs\|cacheScope\|CacheableResult" src/` returns ZERO hits.
  SCHM-03 in `.planning/REQUIREMENTS.md:93` reads: "The five list/read results carry

THE SELF-DEFEAT HAZARD (read this before writing the test)

  A test that asserts "the forbidden sentence is absent from this file" fails immediately if it
  spells the sentence as a string literal, because the literal IS in the file. Assemble the
  forbidden phrase at RUNTIME from two or more fragments that are individually harmless (for
  example a fragment ending mid-phrase and a fragment beginning mid-phrase), concatenate them,
  and search for the concatenation. Then add a second assertion that the concatenated phrase is
  non-trivially long, so a future refactor that reduces a fragment to the empty string cannot
  turn the test into a tautology. This is the Rust form of the repository's grep-gate hygiene
  rule and it is the difference between a real guard and a decoration.

  `include_str!(concat!(env!("CARGO_MANIFEST_DIR"), "/src/server/subscriptions.rs"))` reads the
  file at compile time from inside that same file; this is legal and is the cheapest way to make
  the check self-contained. Do not read the file at runtime with `std::fs` — the published crate
  excludes nothing here but the compile-time form cannot go stale relative to what compiled.

STDIO `subscriptions/listen` — THE EVIDENCE THIS PLAN RECORDS (verified; do not re-derive)

  Routing: `subscriptions/listen` is classified and served ONLY in
  `src/server/streamable_http_server.rs` (via its `HttpIngress` classification). There is no
  route on the stdio dispatch path. `src/server/mod.rs` owns the `ListenRegistry` and the
  notification fan-out, so the registry itself is transport-agnostic; the ROUTE is not.
  Client side: plan 113-13 made `Client::subscriptions_listen` generic over a NEW narrow
  `EventStreamTransport` trait rather than a fourth defaulted `Transport` method, with the
  recorded reason that "an incrementally-read body is an HTTP concept and stdio/WebSocket/wasm
  must not carry a meaningless default". That decision is a deliberate transport-shape stance,
  not an oversight.

  The blocking reason is MISSING INFORMATION, and it must be stated as such rather than as
  difficulty. Specifically: Phase-112 D-05 is LOCKED and requires `Mcp-Name` on EVERY v2
  request. `Mcp-Name` is an HTTP header. stdio has no headers. The phase therefore has no
  resolved answer to "what does a v2 request look like on stdio at all", and that answer is a
  prerequisite for routing ANY v2 method there — `subscriptions/listen` is merely the first
  place the absence shows. No source artifact in this milestone contains it: 113-RESEARCH.md,
  113-CONTEXT.md and REQUIREMENTS.md all scope the v2 transport work to HTTP (the requirement
  family is literally named "Stateless HTTP & Multi-Round-Trip").

  It is also not covered by any requirement: HTTP-04/06/07/08 and CLNT-05 are the subscriptions
  requirements and none of them mentions stdio. Implementing it here would be scope EXPANSION
  past the requirement set, which is a different failure from scope reduction and is equally
  unwanted.
