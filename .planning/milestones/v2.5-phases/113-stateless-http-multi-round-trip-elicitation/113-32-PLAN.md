<objective>
Give the phase's binding re-verification gate a second arm, so that the source HTTP-08 actually
depends on is watched at all.

Purpose: `113-SPEC-RECHECK.md`'s re-verification obligation pins a schema sha and re-checks
three error-code constants against it. That covers most of HTTP-04's obligations. It does not
cover HTTP-08's. HTTP-08's advertise-implies-serve rule has no spec sentence behind it — the
subscriptions specification document contains no capability-gating rule and `ServerCapabilities`
has no `subscriptions` capability. The rule's entire provenance is a TypeScript predicate in a
DIFFERENT repository, on a DIFFERENT release cadence, which pmcp pins nowhere and re-reads never.

The asymmetry is the danger. Because the schema arm exists and is rigorous, running it feels
like running "the gate", and a `PUBLISHED-CONFIRMED` verdict would then be recorded while a
requirement whose grading comes from somewhere else went unchecked. Finding 8 in the same
addendum is the proof that this class of drift is real rather than theoretical: three error-code
constants were renumbered AFTER a locked release candidate. A predicate in a fast-moving
conformance repository is at least as mobile as a schema constant.

This plan does not change any pmcp behaviour. It records what upstream currently says, binds
pmcp's implementation to that recorded text mechanically, and makes the gate say out loud that
it has two arms.

Output: a verbatim § B.6 predicate pin, a two-armed re-verification obligation, and a test that
fails when either side of the binding moves.
</objective>
