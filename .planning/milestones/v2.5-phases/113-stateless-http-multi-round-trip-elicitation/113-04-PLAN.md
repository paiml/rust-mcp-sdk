<objective>
Era-gate the streamable-HTTP transport's session machinery so a v2 request runs handshake-free
and session-free on the EXISTING code path, and add the v2 HTTP status mappings the spec
requires: GET/DELETE → 405, unknown method → 404, header/body rejection → 400 with structured
`data`.  v1 behavior stays byte-identical.

Purpose: HTTP-01 is the load-bearing "stateless" requirement. The failure mode RESEARCH
Pitfall 1 names is subtle and total: `stateless()` is a BUILD-TIME config, so a dual-version
server built with `Default::default()` mints session ids for v2 requests unless the era
overrides the config per request. This plan makes the era, not the config, the decider.

Cross-AI review raised one HIGH cross-plan contradiction here (the `Mcp-Name` matrix vs plan
05) and two MEDIUMs (rejections cannot carry `-32022`'s required `supported` payload; the 404
mapping only applied to already-built typed responses). All three are resolved below.
Output: one `sessions_active` predicate wired through four sites, the raw-level 405/404/400
mappings, structured reject data, and a live-HTTP acceptance suite that deliberately uses the
stateful default config.
</objective>

Five spec-mandated behaviors, all era-gated so v1 is untouched.

**(a) Lock the `Mcp-Name` matrix — this is the cross-plan contradiction the review found.**
Plans 04 and 05 must implement ONE rule. The rule, verified against the code and locked by
Phase-112 D-05 (which reviewers cannot override), is:

> `Mcp-Name` MUST be PRESENT on every v2 request. Its VALUE is cross-checked against the
> request's logical name only for the name-bearing methods (`tools/call`, `prompts/get` →
> `params.name`; `resources/read` → `params.uri`). For every other v2 method the value is the
> EMPTY STRING and is not cross-checked.

`require_three_headers` already enforces presence and `cross_check_name` already skips the
value comparison for non-name-bearing methods, so the SERVER already implements this — the
change here is documentary plus tests. Add a doc comment on `require_three_headers` stating the
rule verbatim and citing `113-SPEC-RECHECK.md`'s `## Mcp-Name Header Rule`. Add unit tests
asserting that a `tools/list` request with `Mcp-Name: ""` classifies as `EnforceOk` and one with
the header ABSENT classifies as `Reject`. Plan 05's client emits exactly this.

**(b) 405 on GET/DELETE (v2).** GET carries no body, so `_meta` is unavailable and the ONLY era
signal is the `MCP-Protocol-Version` header. Reuse the existing non-panicking
`decode_version_header`: when it returns `HeaderProtocolVersion::V2`, return
`StatusCode::METHOD_NOT_ALLOWED` from `handle_get_sse` and `handle_delete_session` before any
other work — including before session validation, so a v2 GET never touches session state.
Every other header value keeps today's behavior exactly. pmcp is dual-version, so do NOT remove
the routes.

**(c) Status mapping at the RAW level, not only on typed responses.** The spec is explicit: "If
the server does not implement the requested RPC method, it MUST respond with 404 Not Found and
a JSON-RPC error with code -32601." An unknown method string may never produce a typed
`ClientRequest`, so a mapper that only inspects an already-built typed response can miss it
(Codex Plan-04 MEDIUM). Implement ONE era-gated mapper that runs at the POST response-assembly
point and takes as input (i) the resolved era, (ii) the raw request id extracted from the body
bytes, and (iii) the JSON-RPC error code about to be emitted — whether that error came from the
header gate, from raw-body parse failure, from unknown-method detection, or from dispatch:
- on `Era::V2`: `METHOD_NOT_FOUND` (-32601) → HTTP 404; `HEADER_MISMATCH` (-32020),
  `MISSING_REQUIRED_CLIENT_CAPABILITY` (-32021) and `UNSUPPORTED_PROTOCOL_VERSION` (-32022) →
  HTTP 400; `PARSE_ERROR` / `INVALID_REQUEST` → HTTP 400; everything else → HTTP 200.
- on v1 / not-opted-in: every code → today's status (200 for JSON-RPC errors), unchanged.
`-32021` is emitted by dispatch (plan 09), not by this gate, so the mapper MUST be code-driven,
not call-site-driven. Preserve the original request id in every error envelope, taking it from
the raw body when the typed parse failed (HTTP-05 depends on this and plan 08 asserts it).
Do not introduce a bare `-32xxx` literal anywhere: every code comes from the table.

**(d) Widen `V2GateOutcome::Reject` to carry structured data.** `-32022` requires an
`error.data.supported` list and `-32021` requires an object-shaped
`error.data.requiredCapabilities`; the current `Reject(i32, String)` cannot express either
(Codex Plan-04 MEDIUM). Change the variant to
`Reject { code: i32, message: String, data: Option<serde_json::Value> }` and update its match
arms. Route the gate's rejection cells through `error_codes::HEADER_MISMATCH` for the
missing-required-header and header/body-mismatch cases (data `None`), and through
`UNSUPPORTED_PROTOCOL_VERSION` with a `data` object carrying a `supported` array listing the
server's accept-list for the unsupported-version case. `create_error_response` gains an
`Option<Value>` data parameter (or a sibling `create_error_response_with_data`) so the payload
reaches the wire.

**(e) Decode the `Mcp-Name` sentinel before the body cross-check.** The Phase-112 gate compares
the inbound `Mcp-Name` header to the body's logical name verbatim. A conformant client MUST send
a non-header-safe name in the `=?base64?<b64>?=` sentinel form, which would fail that comparison
and 400 a legitimate request. Pass the raw header value through
`crate::types::mrtr::decode_header_value` before comparing, and treat a `None` (malformed
sentinel) as a `HEADER_MISMATCH` rejection. Use the SAME shared codec the client emitter uses in
plan 05 — do not write a second decoder. Also delete the module-local `logical_name_key` at :477
and re-point `is_name_bearing_method` / `extract_body_method_and_name` at
`crate::types::mrtr::logical_name_key` so the client and server read one table.

Add `#[cfg(test)] mod tests` unit coverage for the pure classifier parts (era → status mapping
over every code in the table, the sentinel-decoded name cross-check, the empty-name acceptance,
the absent-name rejection) and leave the live-HTTP assertions to Task 3.
  </action>
