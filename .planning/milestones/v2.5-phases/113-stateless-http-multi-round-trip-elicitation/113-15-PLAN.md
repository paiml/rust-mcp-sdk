<objective>
Close gap item 3 from `113-VERIFICATION.md`: bound `SseParser`'s internal line
buffer, wire the already-documented `SseConfig::max_buffer_size` knob to
something that actually reads it, and make an overflow OBSERVABLE to the
long-lived `subscriptions/listen` consumer instead of an unbounded heap.

Purpose: `src/client/subscriptions.rs` feeds a REMOTE server's bytes into the
shared parser chunk by chunk. `SseParser::feed` pushes every chunk into
`self.buffer` and only ever drains as far as a `\n`. A hostile or broken v2
server that accepts `subscriptions/listen` and then streams without ever
emitting a newline grows the client's heap until it OOMs. The module already
bounds its two other untrusted-input surfaces — `MAX_ECHOED_FRAME` for error
text and the incomplete-UTF-8 tail — but not the line buffer.

Both the code review (CR-03) and the verifier independently found this, and the
`/code-review --fix` pass DELIBERATELY declined to patch it, on the grounds that
choosing a bound on a parser shared with the main transport is a design decision
rather than a mechanical fix. That decision is made here, in
`<design_decision>`, with the alternatives recorded.

Output: a bounded parser whose limit is real config, an observable overflow
signal, and a client stream that fails loudly rather than growing silently.
</objective>

<design_decision>
## Where the bound goes, and what happens when it is hit

**The fact that drives this** — verified before planning, and the executor must
re-verify it before choosing differently:

`SseParser::feed` has exactly five non-doctest callers in the crate:

| Caller | Feeds | Long-lived? | Guarded by this plan |
|--------|-------|-------------|----------------------|
| `src/shared/streamable_http.rs:528` (POST response) | `feed(&body)` — a COMPLETE collected body | no | n/a — unreachable |
| `src/shared/streamable_http.rs:1150` (`start_sse` GET) | `feed(&body)` — a COMPLETE collected body | no | n/a — unreachable |
| `src/client/subscriptions.rs::drain_sse_payloads` | one decoded CHUNK at a time | **yes** | Task 2 |
| `src/shared/http.rs:148` (`HttpTransport::connect_sse`) | one decoded CHUNK at a time, inside `while let Some(chunk) = body.frame().await` | **yes** | Task 2 |
| `fuzz_targets/subscription_listen_frames.rs` | arbitrary bytes | n/a | plan 113-16 |

The two `streamable_http.rs` sites hand `feed` a whole body that hyper already
bounded by collecting it, and that body drains to completion in one call. They
cannot grow the buffer across calls. It is therefore NOT true that "a naive cap
truncates legitimately large MCP results on the pre-existing transport path" —
those results arrive complete and drain immediately.

**There are TWO incremental, remote-driven feeders, not one.** `HttpTransport::connect_sse`
(`src/shared/http.rs:141-148`) holds ONE `SseParser` for the lifetime of a
spawned reader task and feeds it frame by frame — structurally identical to the
listen consumer. `HttpTransport` is `pub use`d at `src/shared/mod.rs:100`, is
re-exported from the crate root, and has a live in-repo consumer
(`crates/pmcp-team-servers/src/conformance/runner.rs:238`). It is not dead code.

This matters because the bound in Task 1 is enforced INSIDE `feed`, so it applies
to that caller automatically. Bounding it without also observing the overflow
there would mean a legitimately large single `data:` line on that transport gets
silently discarded with no error anywhere — strictly worse than today's unbounded
behaviour, and the exact silent-truncation failure mode this plan rejects as
option D below. Task 2 therefore guards BOTH incremental callers.

### Options considered

**A. Bound inside `SseParser`, overflow observable via a flag. — CHOSEN.**
One enforcement point covers every present and future feeder, including the two
transport sites (where it is unreachable in practice, so behaviour is unchanged)
and the fuzz target. `SseConfig::max_buffer_size` finally has a reader. Additive
API only: a new constructor, a new observer, a new PRIVATE field — `cargo
semver-checks` stays at "no update required".

**B. Bound at the consumer (`PayloadState` in `src/client/subscriptions.rs`),
checking `bytes.len()` before feeding.** Rejected: it bounds the wrong thing. The
UTF-8 staging buffer is already drained every chunk by `take_utf8_prefix`; the
buffer that grows is the parser's, which the consumer cannot see. It would also
leave `max_buffer_size` dead, which is half the gap item.

**C. Change `feed` to return `Result<Vec<SseEvent>, _>`.** Rejected: a breaking
change to a `pub` method on a `pub` type, for a condition that is pathological
rather than routine. This crate gates on `cargo semver-checks check-release`
reporting no required bump within the 2.x line.

**D. Truncate silently and keep parsing.** Rejected outright: silent truncation
on untrusted input produces a corrupted frame that then fails JSON parsing with a
misleading error, which is strictly worse for the operator than a named failure.

### The chosen semantics, precisely

- Default limit stays **1 MiB**, taken from the value `SseConfig::default()`
  already documents, so the number is not newly invented.
- On overflow the parser DISCARDS the oversized partial line, resets the
  in-progress event, and latches an `overflowed` flag. It does not panic, does
  not truncate-and-emit, and does not stop functioning.
- The flag is LATCHING (never auto-clears) so a caller that checks once per
  chunk cannot miss it.
- BOTH incremental callers check it and end their stream with a named error: the
  listen consumer after each drain, and `HttpTransport::connect_sse` after each
  `feed`. The two whole-body `streamable_http.rs` sites do NOT check it — they
  cannot reach the branch, so a check there would be dead code.
- The listen path bounds tighter (256 KiB) than the shared default (1 MiB),
  because its frames are notifications and small by construction.
  `HttpTransport::connect_sse` keeps the 1 MiB default: it carries arbitrary
  JSON-RPC results, so tightening it would be a behaviour change to a
  pre-existing exported transport, which is out of this gap's scope.
</design_decision>

| remote server -> `HttpTransport::connect_sse` reader task | The SECOND long-lived incremental feeder; one parser per connection, frame by frame. Exported from the crate root and consumed in-repo by `pmcp-team-servers` |
| remote server -> `StreamableHttpTransport` POST/GET bodies | Whole collected bodies fed to the same parser type |
