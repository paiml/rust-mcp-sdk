<objective>
Type the client's `inputResponses` by the kind the server actually asked for, instead of
guessing from overlapping untagged shapes.

Purpose: `InputResponse::decode_for` already exists and is documented as "the CORRECT decoding
path"; the client uses it. The server does not — it cannot, today, because at parse time it has
not yet opened the `requestState` and so does not know which key maps to which kind. So it
calls `try_from_value_untagged`, which tries Roots, then Sampling, then Elicitation and takes
the first that fits. `ElicitResult` and `CreateMessageResult` overlap: an object with `action`,
`content` and `model` matches Sampling first. The handler's `Elicitation` arm then never
matches, it re-elicits, the client answers the same way, and the operation loops with no error
raised anywhere — the failure D-113-O spells out. The server DOES know the kinds: it minted
them. They simply never travel.

Output: the requested kinds carried inside the AEAD-sealed continuation, a kind-directed
re-decode after verification with a typed mismatch rejection, the untagged path retained only
where the kind is genuinely unknowable and documented as such, and an end-to-end test that the
looping scenario now terminates.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| remote client → `inputResponses` | the client chooses the SHAPE of every answer, including shapes that satisfy more than one variant |
| sealed continuation → server policy | the kinds map is server-minted and AEAD-protected, so it is the only trustworthy record of what was asked |
| server ingress → handler | a mistyped value reaches the handler as a variant it will never match, producing a silent loop rather than an error |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-113-127 | Tampering | `try_from_value_untagged` reclassifying an answer into a variant the server did not request | mitigate | kind-directed `decode_for` against the sealed kinds map, with a typed `INVALID_PARAMS` rejection on mismatch |
| T-113-128 | Denial of Service | the silent re-elicitation loop the reclassification causes | mitigate | the mismatch now errors at the first wrong answer; composes with plan 113-24's round ceiling, which bounds any residual loop |
| T-113-129 | Spoofing | a client answering under a key the server never asked for | mitigate | unsolicited keys are rejected against the continuation's kinds map |
| T-113-130 | Tampering | a client choosing which kinds the server believes it requested | mitigate | the kinds ride inside the AEAD-sealed continuation; the client cannot mint one |
| T-113-131 | Denial of Service | in-flight tokens failing during a rolling deploy | accept, guarded | `#[serde(default)]` plus documented degradation to untagged for an empty kinds map; not a bypass, since an attacker cannot mint a continuation at all |
| T-113-132 | Denial of Service | the kinds map pushing a minted token past `MAX_REQUEST_STATE_LEN` | mitigate | measured at 64 entries with a guard added if the bound is at risk; a server must not mint a token its own ingress rejects |
| T-113-133 | Information Disclosure | a rejection message echoing attacker-controlled answer content | mitigate | the message names the server-assigned KEY only, matching `MrtrParseError`'s existing Display discipline |
</threat_model>
