<objective>
Make `feed_complete_body`'s byte-cap precondition TRUE by enforcing a real, overridable
collected-body cap at both of `StreamableHttpTransport`'s `response.collect()` sites.

Purpose: plan 113-17 gives the parser an unconditional in-flight bound and routes the two
whole-body transport call sites through a `pub(crate) feed_complete_body` bypass that skips
it. That bypass is only sound if the caller has already capped the body — and today neither
caller has. `src/shared/streamable_http.rs:498` (POST response) and `:1012` (`start_sse`
GET) both use a bare, uncapped `response.collect()`; `read_body_with_limit` /
`max_request_bytes` guards the SERVER path, not these CLIENT paths. Without this plan the
bypass moves the unboundedness upstream of the parser while the threat model marks the
boundary as capped — strictly worse than the status quo, because it would then be
DOCUMENTED as safe. 113-17's `T-113-84` is therefore recorded as `mitigate — in plan
113-20`, and this plan is what discharges it.

Output: a named cap constant, a private field on `StreamableHttpTransport` initialised from
it, an additive inherent builder seam to override it, enforcement at both collect sites,
per-site behaviour tests, per-site negative controls, and the recorded deferral of the
GET-path incremental-parsing rewrite.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| remote HTTP server → `StreamableHttpTransport`'s POST-response `collect()` | The peer chooses the body's size. Before this plan nothing bounded it on the client side. |
| remote HTTP server → `StreamableHttpTransport`'s `start_sse` GET `collect()` | The same, on a path that is NOMINALLY an SSE stream and can therefore be long-lived — the more dangerous of the two. |
| collected body → `SseParser::feed_complete_body` | The bypass that skips the parser's incremental bound. This plan is what makes the "already capped" precondition on that boundary true. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-113-84 | Denial of Service | uncapped `response.collect()` upstream of `feed_complete_body` | mitigate | The threat 113-17 deferred to this plan. A named cap constant, a private `StreamableHttpTransport` field, an additive builder seam, and enforcement at BOTH sites before the parser is reached (Task 1.1-1.3). Proven per-site by an over-cap behaviour test asserting on the returned `TransportError`, and per-site by a negative control that fails when the check is removed. |
| T-113-92 | Denial of Service (residual) | a body WITHIN the cap | accept | An attacker can still make the client allocate up to the configured cap per request. Bounded per-request rather than by stream age, and overridable by the operator. This is the same accepted shape as 113-17's T-113-83. |
| T-113-93 | Spoofing | a lying `Content-Length` | mitigate | The header is a peer-controlled hint used only to refuse early. The cap is ALSO enforced on the actual collected length, so a peer that understates or omits `Content-Length` gains nothing (Task 1.3). |
