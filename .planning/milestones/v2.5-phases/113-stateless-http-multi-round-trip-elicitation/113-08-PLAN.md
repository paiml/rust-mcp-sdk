<objective>
Close HTTP-05's two independent obligations: SSE resumability is not offered on the v2 path
(`Last-Event-ID` is ignored, the event store is neither read nor written), and a DIRECT
response's JSON-RPC id is always derived from the live request rather than from anything cached
— the general fix for the documented id-replay / discovery-cache bug class.

Purpose: The spec is verbatim on the first half ("Resumable SSE streams via `Last-Event-ID` are
not supported"; "A `Last-Event-ID` header: ignore it"), and the official suite has already
retired its `sse-polling` scenario for this revision. The second half is the one that has
actually bitten this project in production, and MRTR independently reinforces it: retries MUST
use a different id, so any id replay becomes immediately visible.

Cross-AI review found the original invariant as stated ("every response id equals the live
request id on BOTH eras") contradicts v1 replay, whose historical events legitimately retain
their original ids — so a literal implementation would either break v1 resumability or make the
assertion vacuous. This revision scopes the invariant to DIRECT responses and asserts historical
identity separately. Review also asked for a structural guarantee rather than a `debug_assert!`,
a spy proving zero event-store traffic on v2, and a fixture that actually reuses a cached
payload.
Output: an era-gated resumability predicate, a structural envelope constructor, an event-store
spy, and regression tests.
</objective>

**Scope the invariant precisely (Codex Plan-08 HIGH).** The claim being enforced is:

> Every DIRECT response to a live request carries that request's id, on both eras. A REPLAYED
> historical event is not a direct response and legitimately retains its original id.

Write that distinction as a doc paragraph under the v2 section banner so the two behaviors are
never conflated again.

1. **Make the invariant structural, not asserted (Codex Plan-08 MEDIUM).** A source-audit comment
   plus a `debug_assert!` catches a regression only in debug builds and only if someone runs the
   right test. Instead introduce ONE constructor that is the only way a direct response envelope
   is built:
   `fn envelope_for_live_request(payload: ResponsePayload, live_id: RequestId) -> JSONRPCResponse`
   It takes the PAYLOAD (the `result`/`error` value) and the live id as separate arguments, so a
   caller physically cannot pass a whole cached envelope through. Refactor every direct-response
   assembly site — including the plan-04 error paths and `build_sse_response_from_single_message`
   — to call it. Where a cache exists, ensure what is retained is the PAYLOAD, never the envelope.
   Keep a `debug_assert!` inside the constructor as a belt-and-braces check, but the argument
   shape is the actual guarantee.
2. **Audit and record.** Walk every place the HTTP layer assembles, clones, caches or stores a
   response and record the audit as a short comment block under the v2 section banner listing each
   site examined and its verdict (direct-response → routed through `envelope_for_live_request`;
   historical event → intentionally retains its original id), in the style of the Phase-112
   repo-wide error-code audit note. If any site is found reusing an envelope for a direct
   response, fix it and note the fix explicitly in the plan summary.

     server never caches that response, so the fixture must force the reuse.
   - `last_event_id_ignored` — a v2 request carrying `Last-Event-ID: 12345` returns 200 with its

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → transport (`Last-Event-ID`) | An attacker-supplied replay cursor selects which stored events are re-emitted |
| cached/stored payload → a different caller | A retained envelope can be delivered to a caller that did not issue it |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-113-07 | Spoofing | JSON-RPC id replay across callers (the discovery-cache bug class) | mitigate | `envelope_for_live_request(payload, live_id)` makes a stale id structurally unconstructible for direct responses; backed by a concurrent-callers regression test with ≥8 in-flight requests and a deliberately-reused cached payload |
| T-113-29 | Information Disclosure | `Last-Event-ID` replaying another caller's stored events on the stateless v2 path | mitigate | The v2 path does not read the header at all and never reaches `replay_events_after` / `replay_sse_events_from_header`; the spy proves zero replay calls |
| T-113-30 | Information Disclosure | dead retention of v2 response envelopes in the event store | mitigate | The v2 path also stores nothing; the spy proves zero writes, and the non-zero v1 counterpart proves the assertion is not vacuous |
| T-113-19 | Spoofing | v1 resumability regression | mitigate | The `EventStore` trait, `LAST_EVENT_ID` constant and v1 replay code are untouched; `v1_resumability_unchanged`, `v1_replayed_event_retains_original_id` and `tests/server_subscriptions.rs` are the guards |
| T-113-58 | Repudiation | an over-broad id invariant silently breaking v1 replay | mitigate | The invariant is scoped to DIRECT responses in both the doc and the tests, with historical replay identity asserted separately as correct behavior |
</threat_model>
