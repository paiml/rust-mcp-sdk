<objective>
Settle — by execution, not by inspection — whether pmcp can emit the spec-prohibited `-32002`
on a v2 request, era-gate whichever sites the trace proves reachable, and leave behind a
tripwire so a future plan cannot reintroduce a prohibited code on the v2 path.

Purpose: the draft spec's § Error Codes section says implementations of protocol version
2026-07-28 **MUST NOT** emit `-32002` (or `-32042`). pmcp has two `-32002` emission sites. Both
are commented as v1-scoped, and both comments are assertions nobody has tested. This is an
independent, semantics-agnostic prohibition — it does NOT contradict the phase's earlier
`-32002`→`-32602` conclusion, which concerned *resource-not-found semantics* and remains
sound. That conclusion was about what `-32002` MEANS; this is about whether the number may
appear on the wire at all.

Two facts make the trace non-optional rather than a formality. First, `ProtocolHandler` is a
PUBLIC trait (`src/server/core.rs:58`) and `ServerCore::handle_request` is its public entry
point — consumed in-repo by `src/server/wasi_adapter.rs` and `crates/pmcp-tasks`, and by any
downstream embedder — so the `core.rs` site is NOT behind the streamable-HTTP transport whose
era gating Phase 113 built. Second, `src/server/task_dispatch.rs` contains no era gating
whatsoever: a repository-wide grep for `era` in that file returns two matches, neither of them
a gate. The v2 tasks surface belongs to Phase 114 (TASK-01..06, all `[ ]`), so today a v2
`tasks/result` reaches a v1 code path that was never era-reviewed.

Output: an executed reachability record, the era guards the record justifies, a restated
rustdoc on `V1_TASK_PENDING`, and a tripwire suite that fails on any future prohibited-code
emission reachable from v2.
</objective>
