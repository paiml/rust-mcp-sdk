<objective>
Give the MRTR round counter a server-side ceiling, so the D-09 security bound stops being
enforced solely by the party it exists to constrain.

Purpose: `seal_input_required` mints `round + 1` on every resend and compares it to nothing.
The only limit in the tree is `ClientBuilder::mrtr_round_limit` (default 8) — client-side. A
non-pmcp or hostile client simply ignores it, resends `tools/call` with the echoed
`requestState` forever, and the server obligingly re-runs the handler and re-mints each time.
The counter saturates at 255, so a handler that tries to self-limit on `extra.mrtr_round()`
cannot distinguish round 255 from round 3000, and nothing in the SDK ever terminates the loop.
This bears directly on HTTP-02 and HTTP-03, both currently recorded as "implemented; pending
final schema".

Output: a named `MAX_MRTR_ROUNDS` constant, a typed refusal at the ingress verdict (before the
handler runs), an independently sufficient backstop at the mint site, unit tests at both
points, an end-to-end loop test, and recorded negative controls proving the two enforcement
points are not redundant.
</objective>

    (server-minted, integrity-protected), which is why the ceiling can be enforced on it.

DESIGN DECISIONS — implement as written; these are not open questions for the executor:
  1. `MAX_MRTR_ROUNDS: u8 = 16`, a CONSTANT, not a builder knob. A configurable ceiling would
     have to live on `ServerCoreBuilder` and `ServerBuilder`, which plan 113-25 is editing in
     this same wave, and a knob is not what closes D-113-L — an enforced bound is. Record in
     the constant's rustdoc that per-server configurability is deliberately deferred and why.
  2. Refusal code `INVALID_PARAMS` (-32602), matching the sibling MRTR reject so the v2 HTTP
     status mapping (`v2_status_for_code` → 400) is unchanged and no new code enters the
     pre-final `-3202x` range that the publication gate covers. Do NOT introduce a new error
     code for this.
  3. Its message is DISTINCT from `MRTR_REJECT_MESSAGE` and names the ceiling. The generic
     message exists to avoid an authentication oracle; a ceiling refusal happens AFTER
     successful verification, so specificity costs nothing and saves the operator a debugging
     session.
  4. `Verdict::Expired` at or above the ceiling is REFUSED, not re-elicited. The expired path
     preserves the round precisely so the bound cannot be reset; letting it re-elicit at the
     ceiling would hand back the bypass D-15 closed.
  5. `Verdict::UnknownKey` continues to reset to round 0 and is NOT a bypass: it is
     indistinguishable from the client starting a fresh operation, which it can always do.
     State this explicitly in the rustdoc so a future reviewer does not re-litigate it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| remote client → MRTR ingress | the client chooses whether to resend, how often, and whether to honour any limit of its own |
| verified `Continuation` → server policy | the round value is server-minted and AEAD-protected, so it is trustworthy input to a policy decision |
| handler → mint | a handler can return `input_required` an unbounded number of times |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-113-110 | Denial of Service | unbounded MRTR resend loop driven by a non-pmcp client | mitigate | `route_mrtr_verdict` refuses at `MAX_MRTR_ROUNDS` with `INVALID_PARAMS` before dispatch; proven by a raw-frame loop test that counts handler invocations |
| T-113-111 | Elevation of Privilege | a security counter enforced only by the party it constrains | mitigate | the bound moves server-side; the client limit becomes a courtesy, not the enforcement |
| T-113-112 | Tampering | resetting the bound by letting tokens expire | mitigate | `Verdict::Expired` at or above the ceiling is refused, not re-elicited — the D-15 round-preservation property is extended rather than bypassed |
| T-113-113 | Tampering | resetting the bound by presenting an unknown key id | accept | `UnknownKey` → round 0 is indistinguishable from starting a fresh operation, which any client may always do; documented in the verdict table so it is not re-litigated |
| T-113-114 | Repudiation | `extra.mrtr_round()` saturating at 255 and hiding the real depth | mitigate | with the ceiling at 16 the counter can no longer reach saturation; a property test asserts it |
| T-113-115 | Denial of Service | a future refactor silently dropping the ingress bound | mitigate | the independent mint-site backstop, whose non-redundancy is measured by NC-1 |
</threat_model>
