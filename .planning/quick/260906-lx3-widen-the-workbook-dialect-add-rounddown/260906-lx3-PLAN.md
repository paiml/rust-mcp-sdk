<objective>
Widen the constrained Excel workbook dialect from 13 to 17 first-class functions
(ROUNDDOWN, MAX, MIN, XLOOKUP) and close a live silently-wrong-answer bug in
VLOOKUP/MATCH, whose exact-match contract is documented but unenforced.

Purpose: the dialect's ethos is deny-by-default with a precise BA-actionable
repair. Today `MATCH(x, rng, 1)` and a bare `MATCH(x, rng)` — whose Excel
default is APPROXIMATE — both evaluate as EXACT and return a wrong number with no
signal. A silently wrong answer is strictly worse than a refusal. Every narrowing
this plan adds is a located, typed rejection carrying a repair.

Output: a 17-name whitelist bound to the spec, a dialect version at 1.1, real
evaluator bodies with pinned Excel semantics, a parse-time call-shape gate, unit +
property tests, and a runnable example.
</objective>

<decisions>

**D-Q1 — Exact-match enforcement: OPTION (a). Require the argument, present and exact.**
`VLOOKUP` demands a 4th argument that is literally `FALSE` or `0`; `MATCH` demands a
3rd argument that is literally `0`. A bare 3-arg VLOOKUP / 2-arg MATCH is REJECTED.
Chosen because the fixture audit above proves the blast radius is ZERO — every
authored call already writes the exact argument — and because option (b) would
require the dialect to silently deviate from Excel's default on the very form that
is most likely to be pasted in from a real workbook. Option (a) is the option most
consistent with the user's steer, and here it is also free.

**D-Q2 — The rejection lives at PARSE time, in `formula::parser`.**
Justified on four verified grounds:
1. The parser is the only layer with an AST. The linter's `extract_function_tokens`
   (`linter.rs:330-338`) is a token scan with no argument structure, and the linter
   deliberately does not re-parse (`linter.rs:240-241`: "Reads the OWNED
   `is_array_formula` flag, not a re-parse"). It structurally cannot see arity.
2. A `ParseError` IS located: `compiler/src/lib.rs:625-626` prefixes it with
   `"parse {sheet}!{addr}: "` before surfacing it as `CompileError::Lint`.
3. It matches the existing security precedent — the whitelist gate is
   parse-time-and-typed (T-93-03-INJ), and refusing before the node is built means
   a rejected shape never reaches the IR.
4. `ParseError` is `#[non_exhaustive]`, so the new variant is not a breaking change.
The evaluator keeps a typed `ExcelError` backstop for the same conditions —
defense in depth, mirroring `apply`'s existing `_ => Err(ExcelError::Name)`
backstop for a name the parser should already have rejected.

**D-Q3 — Dialect version: `SUPPORTED_DIALECT_VERSION` 1.0 → 1.1. Baseline stays 1.0.
The narrowing does NOT justify a major bump. Reasoning goes in the spec, on the record.**
Under spec §7.3 a declared version is accepted when the major matches and the minor
is `<=` supported, so 1.1 keeps every `1.0`-declaring and every undeclared workbook
accepted. A strict reading says a narrowing should therefore be a major bump. It
should not be, for three reasons that must be written into §7.6 rather than left in
a commit message:
1. Nothing CORRECT is being removed. `semantics.rs:192-194` and `:247-249` already
   published EXACT-ONLY as the contract; the approximate form was never supported,
   it was silently mis-evaluated. This is a bug fix that makes a documented refusal
   real, not a capability withdrawal.
2. The measured blast radius is zero (fixture audit, above).
3. A major bump to 2.0 would fail closed on EVERY existing workbook — all declare
   1.0 or nothing — which is a catastrophic response to fixing a wrong answer.

**D-Q4 — XLOOKUP's constrained form.**
`XLOOKUP(lookup_value, lookup_array, return_array, [if_not_found])`:
- exact match ONLY; no `match_mode`, no `search_mode`. A 5th or 6th argument is a
  typed parse-time rejection.
- `return_array` must be single-column.
- `lookup_array` and `return_array` must be CONFORMABLE (equal member count).
- omitted `if_not_found` on a miss → `#N/A` (Excel-accurate).
Statically-knowable violations (arity; and non-conformability or a multi-column
`return_array` when BOTH array arguments are literal `Expr::Range`) are refused at
parse time with a repair message. Everything else is a typed `ExcelError` at eval.

**D-Q5 — Crate `[package].version` is NOT bumped in this change; CHANGELOG is.**
`pmcp-workbook-dialect` is 0.1.1, `-runtime` 0.2.0, `-compiler` 0.1.1 — all
published, all on the `release.yml` ledger. A 0.x MINOR bump is
semver-INCOMPATIBLE, so bumping the dialect would drag `compiler`'s pin
(`compiler/Cargo.toml:45`, `pmcp-workbook-dialect = "0.1.0"`) and the compiler's own
version with it under CLAUDE.md item 13's move-as-one-set rule. Doing half of a
coordinated set move is the failure mode that rule exists to prevent, and the task
brief puts release/publish out of scope. So: add a `## [Unreleased]` CHANGELOG
section that STATES the required bump axis and the one-set constraint, and leave
every `[package].version` untouched. The DIALECT version (1.0 → 1.1) is a separate
contract from crate semver and IS bumped here.

**ALWAYS requirements (CLAUDE.md) — which apply, honestly judged:**
- **UNIT — APPLIES.** Every new evaluator body and every new refusal path.
- **PROPERTY — APPLIES.** The rounding and aggregate edge cases are exactly what

</decisions>
